# P161 — Reusing a file from the Mediathek was refused by the platform that offered it

**Raised by:** the client, 03.09.2026, from the console on `5297304` with the
network panel open — _"i am creating a new course, and i want to reuse the
videos from mediathek, and i see many errors."_

**Branch** `claude/education-platform-roadmap-3vgrqh`, from `origin/main` at
`5297304`.

Three defects in one screenshot, and they are not three reports. They are one
feature — reuse a file across courses — meeting three separate rules that were
each written before it existed.

## The evidence, and what it settled

```
POST https://api.digitalspital.com/admin/courses/test-course/uploads/view  404
```

and, on screen:

> Die Vorschau konnte nicht geladen werden. Die Datei ist weiterhin gespeichert…
>
> Die Länge konnte nicht aus der Datei gelesen werden. Das kommt bei **Servern
> ohne CORS-Freigabe** und bei adaptiven Streams vor…

and, in the console, on picking a PDF:

```
Loading plugin data from 'https://nbg1.your-objectstorage.com/dscme/…/material-….pdf'
violates the following Content Security Policy directive: "default-src 'self'".
Note that 'object-src' was not explicitly set, so 'default-src' is used as a
fallback. The action has been blocked.
```

The second sentence is the one worth stopping on. It is fluent, it names two
plausible causes, and neither was the cause — the browser never reached the
file, because our own API answered 404. An author acting on it would have gone
and edited a bucket CORS policy that was already correct. That is §11's failure
mode rendered on a screen, and P70-01 is what it costs when somebody believes it.

## P161-01 — a key is minted once, and the course it was minted under is for ever

`UploadService.view` required the key to sit under **this course's** prefix:

```ts
key.toLowerCase().startsWith(coursePrefix(actor.customerId, courseId));
```

Keys are minted under the course being edited at the time and objects are never
copied, so a video uploaded while building course A carries A's prefix for the
rest of its life. Pick it again from the Mediathek while building course B —
which is exactly what P88-02 put an **"Aus Mediathek wählen"** button beside
every upload field for — and the reference in B's form points at A's prefix.
Every preview and every length probe then 404s.

This is §9.2 with the halves the other way round: not a control the API refuses,
but a **feature the API refuses**, shipped complete and never reconciled with
the rule one layer down.

### The rule's own comment is why nobody looked again

```
 * 3. The key must sit under *this course's* prefix. Stricter than (2) on
 *    purpose: without it, an author who may edit one course could read every
 *    object their customer owns by naming a key from another course.
```

**Verified against the current code, and it is false.** `AUTHOR_ROLES` in
`upload.controller.ts` is `["customer_admin", "super_admin"]` — there is no
`course_editor` on this controller and no per-course scoping anywhere in the
uploads module. Both of those roles can already:

- `GET /admin/media` — list every asset the customer owns, and
- `POST /admin/media/{id}/view` — mint a read URL for any row in that list,

both `@Roles(...AUTHOR_ROLES)`, the same roles, the same objects, one route
along. The course-prefix rule was refusing a shipped feature and granting no
protection at all. CLAUDE.md §11 rule 9: a comment is a claim, not a fact — and
a confident one stops the next person checking, which is precisely what happened
when the picker shipped.

### What it is now

The key must be one the customer **owns**: under this course's prefix, _or_ a
row in this customer's Mediathek (`media_assets`, under RLS, so a row from
another tenant is invisible rather than false).

This is deliberately **not** "any key under the customer prefix". A key that is
in the bucket with no library row — a mint nobody completed, a path somebody
guessed — is still refused. It is _exactly_ the authorisation `viewAsset`
already applies, which is the point: two routes handing out read URLs for the
same objects must not disagree about who may have one.

The library lookup runs only when the cheap prefix test has already failed, so
a course showing its own files costs no extra query.

**Written red first.** The new integration case reproduced the client's own
404 on the same route shape before the fix:

```
FAIL  uploads.integration.test.ts > shows a file this course reuses from the customer's Mediathek
{"type":"…/not_found","status":404,"instance":"/admin/courses/kurs-a-65524811/uploads/view"}
expected 404 to be 200
```

Then 580/580 green.

The old rule's own test — _"refuses an object belonging to another course in the
same tenant"_ — is **kept and passes unchanged**, because its fixture mints a
ticket and never completes it, so there is no library row. It has been re-aimed
and its comment corrected: what it proves now is that a key the library does not
know is refused, which is the guard on the relaxation rather than a claim about
a role that does not exist.

## P161-02 — the third CSP directive, found the same way as the first two

`<embed>` is governed by `object-src`. The console's policy did not set it, so
it fell back to `default-src 'self'` and every PDF preview in the Mediathek was
blocked. The console message names the mechanism exactly.

That is the third time:

| Ticket  | Directive     | What was invisible until somebody clicked |
| ------- | ------------- | ----------------------------------------- |
| P67-01  | `connect-src` | the presigned PUT — no upload could start |
| P74-03  | `media-src`   | `<video>` — no preview, no length probe   |
| P161-02 | `object-src`  | `<embed>` — no PDF preview                |

Each was reported from a browser and none could have been caught on the server:
a CSP refusal happens entirely inside the browser, so the API log is clean, the
deploy is green, and the only evidence is a console message on somebody else's
machine (§9.13).

### P161-02a — the class, derived rather than listed

The tempting fix is to list every directive. The Caddyfile argues against that
in its own words and is right: a directive naming an origin for a request nobody
makes is a permission granted for nothing, and the next person to copy the policy
inherits it.

So `scripts/check-csp-directives.mjs` derives the answer from the code. In the
files that render a signed bucket URL — the ones importing `media-preview.js` —
every element loading its `src` from an expression is mapped to the directive
that governs it (`<img>`→`img-src`, `<video>`/`<audio>`/`<track>`→`media-src`,
`<embed>`/`<object>`→`object-src`, `<iframe>`→`frame-src`), and the console's
policy must name `{$S3_ORIGIN}` there. It reports **both** directions: a missing
directive, and a directive naming the bucket for an element nothing renders any
more. In `pnpm verify` and CI.

`connect-src` is not derived — a `fetch` is not an element and cannot be
recognised by a tag. Its presence is asserted and no more, and the script says so.

**Watched to go red six ways**, including the production bug itself:

| Sabotage                                | What it said                                                             |
| --------------------------------------- | ------------------------------------------------------------------------ |
| `object-src` removed                    | names `MediaCard.tsx (<embed>)` and "blocked … with a clean server log"  |
| `object-src` set but without the bucket | "is set but does not name `{$S3_ORIGIN}`"                                |
| `<embed>` swapped for an `<iframe>`     | `frame-src` missing **and** `object-src` now a permission for nothing    |
| `connect-src` deleted                   | "missing entirely — the presigned upload PUT is a fetch, not an element" |
| the console block loses its policy      | "served on default-src alone"                                            |
| no `{$ADMIN_DOMAIN}` block              | refuses rather than guessing                                             |

**A defect in the check, found by the sabotage pass and worth recording.** The
first draft located the console's policy by searching for the one containing
`{$API_DOMAIN_URL}`. Deleting `connect-src` from the console's policy then made
that search match the **portal's** instead, and the script went on reporting
confidently about a policy serving a different app — §9.1's second form, in a
check written to prevent §9.1. It addresses the `{$ADMIN_DOMAIN}` block now,
which is the thing that actually decides which app the policy is served with.

## P161-03 — a message that named a cause it had not observed

`readableUrl` returning `undefined` (our API refused) and `probeDurationSec`
returning `undefined` (the browser reached the file and could not read it)
collapsed into one `"failed"` state, which renders the CORS sentence.

They are now two states with two messages. The new one says the refusal came
from the platform rather than the storage, and says what to do:

> Auf diese Datei konnte nicht zugegriffen werden — die Vorschau und die
> Längenmessung wurden von der Plattform abgelehnt, nicht vom Speicher. …
> wenn das bleibt, ist es ein Fehler und kein Einstellungsproblem.

`MeasuredDuration` is exported for the test and for nothing else: the transition
lives in an effect, and an effect nothing drives is a rule with no caller (§9.3).
Two tests, both watched red — restoring `onState("failed")` for the refused case
fails the first with `expected "vi.fn()" to be called with arguments: [ 'unreadable' ]`.

## Three gates I got past and should not have

`pnpm verify` went red three times before it went green, and none of the three
was in the product. They are recorded because each is a check being _weaker
than it looks_ from where the work happens:

1. **`pnpm --filter @ds/api exec tsc -p tsconfig.json` exited 0 with a type
   error in the API's own tests.** That project does not include test files, so
   the "typecheck clean" I read after changing `UploadRepositoryPort` was a
   narrower claim than I treated it as. `pnpm verify`'s typecheck found the fake
   repository missing `findAssetByKey`. §9.1's second form, in my own tooling
   use rather than in a script.
2. **`vitest run` passed a test whose fixture does not typecheck** — a
   `MediaSourceWrite` with a `kind` property that does not exist. Vitest does
   not typecheck; `pnpm test` green is not `pnpm typecheck` green, and reading
   one as the other is how a broken fixture reaches a commit.
3. **A lint rule the component tests have no local runner for.**
   `import()` type annotations are forbidden and `vi.importActual<typeof
import("…")>` is the idiom that reaches for one. `MediaDialog.test.tsx`
   already had the right form — `import type * as Module` — and I did not look
   before writing.

And a fourth that _was_ about the product, and was my test being wrong rather
than the code: the refusal audit row is deliberately recorded against the
course's own prefix rather than the client-supplied reference, so an assertion
looking it up by key finds nothing. The comment in `view` says so. The test now
asserts what the key _can_ answer — that no `read` row was written, so no
capability was issued — and that assertion was watched red by relaxing the rule
to "any key under the customer prefix", which makes the case answer 200.

- [ ] Confirmed in a browser against the installation — the client's, after deploy

## Not done, and named rather than absorbed

**The journey does not reuse a file across courses.** `apps/e2e` uploads a video
into a fresh course and never picks one from the library, so P161-01 was
structurally invisible to it — §9.13 exactly. The API half now has an integration
test that goes red; the browser half does not, and adding it needs a Docker
daemon this sandbox does not have. It is the single highest-value addition to the
journey and it is not in this ticket.

**`GET /admin/media` and `POST /admin/media/{id}/view` are customer-wide for
`customer_admin` and `super_admin`, and that is now written down** rather than
implied by a comment claiming the opposite. If `course_editor` is ever given
upload routes, per-course scoping has to be enforced on the **library** — the
list and the asset view — and not on one course route, or it will be the same
non-defence again. Raised here; not a change anybody should make quietly.

**The CSP check covers the console only.** The portal and widget render no
`<embed>`, `<object>` or `<iframe>` today, so there is nothing to derive for
them; if that changes the script needs its second block.
