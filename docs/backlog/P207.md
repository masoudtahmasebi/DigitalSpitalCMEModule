# P207 — three red jobs, and what each of them was hiding

The client, 07.09.2026: _"the github actions has a couple of failing jobs"_.

Three, with three unrelated causes. Two of them had been red for weeks and the
third was a check discovering a cost of last hour's change. None was a defect in
the running product; all three were checks doing their job into a void.

---

## P207-01 — the nightly secret scan had never once been green

`Security audit` fails on every **scheduled** run. Five scheduled runs exist.
Five failed, from the first.

### What it finds

Five `generic-api-key` findings, all in one commit, all in one file:

```
622fb7680a86b8f17391e8c0f3278b3224340ae1
apps/api/test/integration/participant-auth.integration.test.ts:661,664,672,673,684
```

Read in the commit rather than inferred from the redacted log: four German
fixture passwords in the password-reset suite —
`ein-ganz-neues-passwort-2026`, `erste-wahl-2026-lang`, `zweite-wahl-2026-lang`,
`zu-spaet-2026-lang`. They authenticate nothing. They exist because
`MIN_PASSWORD_LENGTH` is 12 and the suite needs two that differ, so that a link
already spent can be told from a fresh one.

Handled the way `.gitleaksignore`'s own header requires: **fixed forward** to
`first-password-for-tests` and friends, with the five fingerprints added only
for the history the fix cannot reach. Never for a value that is, or was, real.

**Verified:** `gitleaks detect` locally, the same 8.24.3 the action installs —
`leaks found: 5` before, `no leaks found` after, 440 commits and 12.46 MB in
two seconds. The 30 cases in `participant-auth.integration.test.ts` still pass
with the renamed fixtures.

### The part that matters more than the finding

`gitleaks-action` picks its scope from the event type. A push or a pull request
scans **that push's range**; only `schedule` runs `gitleaks detect` over
`git log -p --full-history --all`.

So a fixture that looks like a credential does not fail the pull request that
adds it. It fails a nightly, days later, on a commit that has nothing to do with
it — which is precisely the failure `.gitleaksignore`'s header already describes
from P33-02: _"a check that passes because of what it did not look at is not
passing"_. The fingerprints were added then; the **scope** was not.

And the consequence is worse than a delayed report. The nightly has been red
continuously since 11.08. An alert that is always red is an alert that cannot
tell you anything, and a genuinely committed credential would have arrived in
exactly the same colour, on the same job, with nobody looking.

So the full-history scan now runs on **every event**, as its own step beside the
action. 440 commits and 12 MB in two seconds — there was never a cost reason for
it to be the nightly's job alone.

**Watched red:** a planted high-entropy key in a throwaway commit is reported as
`File: sabotage-leak.ts` and the step exits 1; on the clean tree it exits 0.
Both directions, with the step's own command, verbatim.

## P207-02 — the post-deploy journey went red because the console now says it twice

The deploy of `08d8d0f` **succeeded**; the browser journey after it did not.
`journey.spec.ts` passed. `zwei-module.spec.ts:84` failed:

```
Error: the console accepted a second Lernerfolgskontrolle in one module (P87-06)
strict mode violation: getByText('/bereits eine Lernerfolgskontrolle/u')
  resolved to 2 elements:
    1) <div role="alert" …>Es ist ein Fehler aufgetreten Das Modul „Modul 2 · Therapie" hat bereits eine…
    2) <span>Das Modul „Modul 2 · Therapie" hat bereits eine L…
```

**The product is correct.** The console refused the second exam and said why.
It now says it twice: the form's own `SaveProblem` notice, and P205-01's toast.
Element 1 is the inline notice (it carries `de.error.title`); element 2 is the
toast (the sentence alone, in a bare span).

This is the cost P205.md recorded as _"screens with inline messages now also
toast … worth a per-screen pass later"_, arriving in a form I had not
anticipated: it does not merely look redundant, it **breaks locators**.

### Why not `.first()`

Two reasons, and the second is the one that would have bitten later:

- `.first()` picks whichever element is first in the DOM, which depends on where
  the toast host is mounted — a property of `App`'s layout, not of the assertion.
- **The toast auto-dismisses after twelve seconds.** An assertion that lands on
  it is an assertion that can fail on a slow runner for a reason having nothing
  to do with the product. `.first()` would have made this flaky rather than red.

So `inlineError()` in `apps/e2e/support/console.ts` targets the notice by the one
difference in the markup that is a property rather than a coincidence of
position: the inline `Notice` carries a title and the toast does not.

**The class, not the instance.** A sweep of every `getByText` in the e2e suite
found this is the only assertion about a _failure_ today — the rest assert
`Gespeichert.` and success messages never toast. But the shape applies to every
future one, which is why this is a helper with the reasoning in its header rather
than a fixed locator in one spec.

### Still owed

The per-screen pass. Two costs are now recorded rather than one, which is the
argument for doing it: the duplication is not only cosmetic.

The rule that pass should apply, written down here so it is not re-derived: a
`422` is a refusal _about the form the person is filling in_, and the form is
where it belongs. Everything else — a 409 on a delete, a 500, a network failure
— is the toast's job, and the client's original report was a 409. Suppressing
422 in `announcing` is the small version; it needs a check that every screen
which can receive a 422 renders `SaveProblem`, or it re-opens the silence P205
closed. That check is the work.

### #58 — a derived type that stopped being callable

```
src/auth/jwks.provider.ts(57,32): error TS2349: This expression is not callable.
  Not all constituents of type 'KeyInput | JWTVerifyGetKey<…> | CryptoKey'
  are callable. Type 'CryptoKey' has no call signatures.
```

`KeyResolver` was `Parameters<typeof jwtVerify>[1]`, under a comment claiming
that deriving it _"keeps this correct across future jose majors without another
edit here"_. Read in both versions of jose's own `.d.ts`, that is backwards:

- **6.2.4** declares one `jwtVerify`, second parameter `JWTVerifyGetKey` — a
  function, so the derivation was callable.
- **6.2.10+** overloads it, and the second overload takes
  `KeyInput | JWTVerifyGetKey` so callers can forward either form.
  `Parameters<>` on an overloaded function resolves to the **last** overload, so
  the alias silently became a union including `CryptoKey`.

`verifyToken` only forwards the resolver and never minded. `JwksProvider`
**calls** it, twice, on the token-validation path — that is what stopped
compiling. One name had been covering two different things: what `verifyToken`
accepts, and what `JwksProvider` produces and invokes.

Fixed by naming the type jose exports for exactly this. §11.9 again — a comment
is a claim, and this one had been carried since jose 6 landed.

**This is auth.** §2's review gate applies: `KeyResolver` is the type of the
thing that resolves the key every bearer token is verified against. The change
is type-level with no runtime effect, and the 687 integration tests verify real
tokens against a live JWKS server — but the gate is not about how confident the
author is.

### #4 — nginx yes, Node no

Two bumps in one PR, and they are not the same kind of thing.

`nginx:1.27-alpine` → `1.31-alpine` on the three static images: routine, taken
here.

`node:22-bookworm-slim` → `node:26-bookworm-slim` on `deps` and on the **API
runtime**: held. The build dies immediately —

```
#8 [deps 2/7] RUN corepack enable
#8 0.059 /bin/sh: 1: corepack: not found
ERROR: process "/bin/sh -c corepack enable" did not complete successfully: exit code: 127
```

Node no longer ships corepack in that image, and corepack is what pins pnpm from
`packageManager` so _"an image cannot drift to a different pnpm than CI used"_ —
the Dockerfile's own comment. Beyond the mechanics: `.nvmrc` says `22` and
`engines` says `>=22`, so merging this would run the production API on a major
that nothing in CI tests against.

A runtime major on the production image, the day after launch, is a decision the
client makes in a ticket (CLAUDE.md §3) — not something absorbed while tidying
dependabot. Doing it properly means moving `.nvmrc`, the CI runner and the image
together, and replacing `corepack enable` with an explicit pnpm install of the
pinned version; that is its own ticket.
