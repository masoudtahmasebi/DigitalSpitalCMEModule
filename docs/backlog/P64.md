# P64 — An operator could not set a password, and a seeded tenant showed nothing

Raised 12.08 by the client, twice, after the P63 deploy. Both items are things a
person sat in front of the product could not do, and both had an explanation on
our side that was not an answer.

---

## P64-01 · No way to create an admin-panel account with a password, or to change one · 3 h

**Touches auth — human review.**

### What was wrong

The Konten screen offered exactly one way to create an operator: **Konto
einladen**, which mints a single-use link. There was no field for a password,
and no control anywhere to change an existing operator's password. The only
other path was self-service _Passwort vergessen_, which needs a configured SMTP
sender **and** needs the operator to still be able to read the mailbox.

So two ordinary jobs were impossible:

- "create an account and tell this person their password"
- "this operator is locked out — give them a new one"

The previous answer to the first was a paragraph explaining that invitation-only
is deliberate. That is a design rationale, not a capability, and the client had
asked for the capability four times.

### What changed

| Where                             | What                                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------ |
| `POST /admin/staff`               | Optional `password`. Present → the account is usable at once, no token is minted, `token: null`. |
| `POST /admin/staff/{id}/password` | New. Sets or changes any account's password.                                                     |
| Konten screen                     | A **Passwort (optional)** field on the create form, and **Passwort setzen** on every row.        |

The invitation path is untouched and is still what an empty password field
means, so nothing that worked before works differently.

### Who may do it, and why that is the same rule as scope

`canGrant` against the account's **existing** grants — exactly the check
`setScope` makes. A `customer_admin` can set a password inside their own
customer and cannot touch a `super_admin`.

The reasoning is one sentence: being able to set somebody's password is being
able to act as them, so it must not reach further than being able to define
them. A weaker check here would be a privilege-escalation path that looks like a
convenience feature.

### What it does besides writing a hash

- The password goes through `checkPassword` — the same policy the invitee's own
  choice goes through, so an administrator cannot set a weaker password than the
  person could. A rejection is a **422 naming the rule in German**, never the
  value (§9.5).
- **Every session** the account holds is revoked. A password change that left
  old sessions alive would not lock out whoever prompted it.
- **Every outstanding invitation and reset token** is revoked. A live invite
  link would otherwise be a second credential for an account that now has a
  password.

### Verified against a running API

On a freshly migrated, freshly seeded database, signed in as the `ds`
`customer_admin`:

```
1. POST /admin/staff  … "password":"…"    → 201 {"status":"created","token":null,"delivered":false}
2. POST /admin/auth/login as that account → 201    (usable immediately, no link)
3. POST /admin/staff/{id}/password        → 204
4. login with the OLD password            → 401
5. login with the NEW password            → 201
6. POST …/password with "kurz"            → 422 "Das Passwort ist zu kurz. Es braucht
                                                  mindestens 12 Zeichen."
```

### Acceptance criteria

- [x] An administrator can create an operator account with a password they
      choose, and that account can sign in with no further step
- [x] An administrator can change any operator's password they may manage
- [x] Neither path requires SMTP
- [x] The permission is exactly `canGrant` against the existing grants
- [x] Setting a password revokes sessions and outstanding links
- [x] A rejected password is a 422 naming the rule in German, never the value
- [x] The endpoints are in `contracts/openapi.yaml` and the generated SDK
- [ ] **Human review** — auth. The reviewer's question is **whether a
      `customer_admin` should be able to set passwords at all**, or whether this
      should be `super_admin` only. Setting a password is impersonation; the
      counter-argument is that a `customer_admin` can already invite, disable and
      re-scope those accounts, so withholding it changes little and leaves the
      lockout case unsolved.

## P64-02 · A seeded tenant with an empty catalogue is not a seeded tenant · 2 h

### What was wrong

`/medice` answered `{"kind":"unknown"}` because the MEDICE seed had never run on
that host. P63 fixed the seed so it could run — and P63-02 made it seed the
course as a **draft**, because no seed could furnish a VNR password and
`courses_published_cme_is_complete` refuses a published CME course without one.

That was truthful and it was the wrong outcome. Running the seed would have
produced a portal with **nothing in it**, and "seed the tenant, then set a VNR
password, then publish" is three steps to see a demo where the client asked for
one. A tenant nobody can look at is not a seeded tenant.

### Why the seed could not set a password, and what actually blocked it

Not policy — **a missing dependency edge**. The cipher lived in
`apps/api/src/shared/secret-cipher.ts`, and a package may not reach into an app,
so `packages/seed` had no way to produce a valid `vnr_password_enc`. One import
that could not exist, three layers below a symptom that read as "the product is
broken".

### What changed

- `packages/secrets` — the cipher, moved unchanged. `apps/api` keeps
  `shared/secret-cipher.ts` as a re-export so a dozen call sites stay put.
- Both seeds write a **random placeholder** VNR password and publish the course.
- Neither seed overwrites a password already there:
  `vnr_password_enc = COALESCE(courses.vnr_password_enc, EXCLUDED.vnr_password_enc)`.
  `deploy.sh` runs a seed on every deploy, and replacing a real credential with a
  placeholder would break every Punktemeldung from that deploy onward, silently.

### Why a seeded credential is safe here, and where the real guard is

It authenticates nothing, and it goes with a VNR that authenticates nothing —
`0000000000000000000` for MEDICE unless `SEED_MEDICE_VNR` says otherwise, and a
fictional Ärztekammer for the DS demo. A Punktemeldung carrying it is refused by
EIV-FOBI, and it cannot reach EIV-FOBI at all: the deploy refuses a live
`EIV_BASE_URL` without `EIV_ALLOW_LIVE=yes` (ADR-0005). **That** is the guard,
and it has not moved.

It is random rather than a constant because a constant is a credential in the
repository, and "it is only a placeholder" is how a real one eventually gets
committed next to it. Nothing needs to read it: a VNR password is used
server-side only and is never returned by any API.

The seed's summary now says both values are placeholders and names the screen
that replaces them.

### Verified against a running API

Fresh database, all migrations, all three seeds, API booted against it:

```
GET  /tenants/medice                    → {"kind":"portal","customerName":"MEDICE Arzneimittel Pütter GmbH & Co. KG"}
POST /auth/participant/sign-in  medice  → 200   (demo@medice.example)
GET  /courses                   medice  → 200
       adhs-akademie-adult    ADHS Akademie adult    4 CME-Punkte
       total: 1 course(s) visible
```

That is the sequence the client was running, and the answer at each step.

### Acceptance criteria

- [x] All three seeds complete against a freshly migrated database
- [x] Every seeded course is `published`
- [x] `/tenants/medice` resolves and `/courses` returns the course to a signed-in
      participant
- [x] The seeded VNR password is real ciphertext under `SECRETS_KMS_KEY`
- [x] A re-run does not overwrite a VNR password an operator set
- [x] The seed's output says the VNR and its password are placeholders and names
      the screen that replaces them

## P65-01 · A seed the deploy cannot run is a seed nobody runs · 1.5 h

### What was wrong

`deploy.sh` seeded only `ds-default`. The two client tenants were excluded on
purpose and for a good reason — both rebuild a course's content tree
unconditionally, and `resetCourseContent` deletes the contents that
`content_progress` rows point at. A deploy that did that on every push would
delete every learner's progress, silently.

The reasoning was right about the seeds as they were. The **conclusion** was
wrong, because its consequence was that `https://…/medice` answered "Diesen
Bereich gibt es nicht" on a correctly deployed, fully working installation, for
the single reason that nobody had opened an SSH session and typed one command.

That was reported three times across P40, P42-02 and again today. Each time the
answer was "run `./dsc seed medice`", and each time that was true and did not
happen. Four months of a repository state that was not the installation's state
(CLAUDE.md §9.9's corollary), with the fix living in a runbook.

### What changed

Both seeds take `--if-missing`, the flag `seedDsDefault` already had: read one
row, return before the first write once the tenant exists. `deploy.sh` runs both
under it, after the default customer.

The destructive rebuild is untouched and is still what `./dsc seed medice` does
when an operator deliberately reloads a fixture. It is simply no longer what an
unattended deploy does.

`SEED_CLIENT_TENANTS=no` turns it off for an installation that manages its
tenants by hand.

### The one subtlety, which would have been silent

The check sits **after** `enterTenant`, not at the top of the function.
`customers` is under RLS: read on the bare connection it matches zero rows, the
guard would always conclude "missing", and the seed would rebuild the tenant on
every deploy — the exact destruction the flag exists to prevent, arriving via
the flag meant to prevent it. That is CLAUDE.md §9.6 verbatim.

### Red check

The guard was deleted and the suite run:

```
× writes nothing at all on a second run with --if-missing
AssertionError: expected 'Seeded the MEDICE ADHS course.\n  cus…' to contain
                'nothing was written'
      Tests  1 failed | 11 passed (12)
```

The test asserts by _effect_ as well as by the summary: a course title changed
by hand, both seeds run with the flag, and the title and the `contents` row
count have to be unchanged afterwards.

### Acceptance criteria

- [x] `--if-missing` returns before any write when the tenant exists
- [x] The guard runs inside the tenant context, so RLS cannot make it always say
      "missing"
- [x] `deploy.sh` runs both client seeds under the flag
- [x] An operator's deliberate `./dsc seed medice` still rebuilds
- [x] `SEED_CLIENT_TENANTS=no` opts out
- [x] Verified red by deleting the guard

## P65-02 · The check that was red in CI and green locally · 0.5 h

### What was wrong

CI had been failing on `Configuration drift` — `scripts/env-audit.mjs`, which
refuses an environment variable read by the code and documented in neither
template. Two were undocumented: `DEV_KEYCLOAK_PORT`, pre-existing since P52-02,
and `SEED_CLIENT_TENANTS`, added an hour ago by P65-01.

Both are one-line omissions. What matters is that **`pnpm verify` could not
find either**, because `env-audit` ran only in the CI workflow — CLAUDE.md
§9.1's first form, verbatim: _"the check is not run where the work happens"_.
The same entry already records `check:sdk` doing exactly this, and two commits
went out with a stale SDK before it was moved.

So the red build was not information anybody had while writing the code. It
became information after a push, which is the wrong end.

### What changed

`check:env` is a script and is in `pnpm verify`, between `check:runtime-config`
and `check:local-ports`. Both variables are documented where they belong —
`SEED_CLIENT_TENANTS` in `config.env.example` next to `SEED_DEFAULT_CUSTOMER`,
`DEV_KEYCLOAK_PORT` in `.env.example` next to the real `KEYCLOAK_PORT`, with the
sentence saying they are not the same thing.

### Acceptance criteria

- [x] `pnpm verify` fails on an undocumented environment variable
- [x] `env-audit` reports no drift
- [x] Both variables documented, each next to the one it is confusable with
