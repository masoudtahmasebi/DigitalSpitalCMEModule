# P119 — EIV says the EFN was rejected, and nobody is told

**Status:** specified, not built. New scope — see §Cost.
**Human review required** — `eiv` and `certificates`.

Derived from source while answering _"does the server send us a result if the
efn is wrong? can we check it and show the appropriate result for the
teilnehmende and also for the admin panel?"_ — labelled as derived, not
reproduced (§9.9).

---

## The answer to the question: yes, and we already classify it

`packages/eiv-client/src/client.ts` distinguishes the two permanent failures,
and its header already says why the distinction is load-bearing:

> - **`business` (406)** — the VNR is unknown or blocked, or the
>   `teilnahmedatum` is outside the accredited period. The submission is
>   well-formed; the _event_ is the problem, and only an operator or the
>   Ärztekammer can fix it.
> - **`validation` (422)** — the payload is malformed: a failed EFN check
>   digit, a point value out of range. **The physician's EFN is the problem.**
>
> Retrying either forever hides the problem until the correction window has
> closed. Reporting them identically sends an operator to the wrong place.

So the platform knows, at the moment it happens, whether the physician's own
number was refused. It stores the kind in `eiv_submissions.last_error`.

## Where it goes

| Audience                                 | What they get today                                                     |
| ---------------------------------------- | ----------------------------------------------------------------------- |
| The **physician**                        | **Nothing.** No endpoint returns their own submission's state to them.  |
| The **operator**, Punktemeldungen screen | The raw kind — the literal string `validation` — rendered in a `<code>` |
| The **operator**, Teilnehmende screen    | `abgebrochen`, and no reason at all                                     |

The first row is the defect that matters. A physician completes the course,
downloads a Teilnahmebescheinigung, and believes they hold four CME points. If
their EFN was mistyped, the Kammer refused the Meldung, **the certificate is
still valid and still says four points**, and nothing anywhere tells them the
points were never credited. They find out at their next Fortbildungsnachweis,
years later, with the correction window long closed.

ADR-0004 already names this as the worst available failure _because it looks
like success_. This is that failure with a mechanism.

It is §9.3 in its purest form yet: the rule is written, tested, commented with
its own justification — and read by no screen. And §9.4: the one person who can
fix a mistyped EFN is the physician, and the platform never tells them.

## What to build

### P119-01 · One rule, two audiences

`punktemeldungOutcome({ status, lastError })` in `@ds/domain`, returning a kind
that both UIs map to their own copy (§5 keeps the German in locale files):

| kind             | from                                                | who acts                |
| ---------------- | --------------------------------------------------- | ----------------------- |
| `none`           | no submission row                                   | —                       |
| `pending`        | queued, held, failed_retryable                      | nobody, it is in flight |
| `reported`       | submitted                                           | —                       |
| `withdrawn`      | withdrawn                                           | —                       |
| `check_efn`      | failed_permanent + `validation`                     | **the physician**       |
| `event_problem`  | failed_permanent + `business`                       | the operator / ÄKWL     |
| `not_configured` | failed_permanent + `missing_vnr_password` or `auth` | the operator            |
| `window_closed`  | window_closed                                       | the operator, on paper  |

The split matters in exactly one direction: **never tell a physician to check
their EFN when the VNR was the problem.** That is §9.2 — an instruction that
cannot help, aimed at the person least able to act on it.

### P119-02 · The physician is told, on the screen they finished on

`punktemeldung` on the enrolment state the widget already reads, and a panel on
the Zertifizierung tab. For `check_efn` it says the number was not accepted and
offers the EFN field again — the physician owns that field, `PUT /profile/efn`
already exists, and after P118-01 a requeue picks the correction up.

The EFN is never echoed back into the message. `GET /profile/efn` is how the
learner reads their own (P54-02); a rejection message that quoted it would put
it in a place ADR-0004 does not allow.

### P119-03 · The operator gets a sentence, not an enum

`validation` in a `<code>` block is the API's vocabulary, not the operator's.
Each kind gets a sentence naming what to do — and for `check_efn`, that is
_"the physician has been asked to check their EFN"_, because an operator
cannot correct it and must not be sent looking for a way.

## What this deliberately does not do

**It does not revoke the certificate.** Course completion and CME certification
are separate by design (P51-01): the physician did the work, and the
Teilnahmebescheinigung records that. A refused Punktemeldung is a reporting
failure, not a learning one. Whether ÄKWL considers a certificate valid while
its Meldung is outstanding is a question for them, not an assumption to encode.

**It does not guess EIV's rejection text.** Only the classification we already
make is used. The far end's message can carry the EFN and the server, and it is
neither shown nor stored beyond the kind (§9.5).

## Cost

Roughly **5–7 h**: the rule and its tests, one field through the contract and
the SDK, a widget panel with tests, the console's sentences, and an integration
test that a rejected submission reaches the learner's own state and nobody
else's.

New scope against a fixed 140 h budget, so it is named here rather than
absorbed (§3). The declared trade lever is the admin console (P9).

## Open
