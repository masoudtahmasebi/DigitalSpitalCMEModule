# P21 · Participants, memberships and tenants in the path

Three requests that turn out to be one change:

1. A **participant** the admin console can create, who signs in to
   `fortbildung.digitalspital.com` when it is not embedded in anyone's website.
2. A learner who **belongs to more than one customer**.
3. The **tenant in the URL** — `/medice`, `/ds` — deciding which catalogue a
   signed-in learner sees.

**Review gate: human — auth.** P21-01 changes the key that identifies a
physician, and P21-02 adds a way to authenticate one. A wrong result here
credits the wrong person's CME account.

---

## What is in the way, precisely

`users` is keyed `UNIQUE (keycloak_realm, keycloak_sub)`, and the realm comes
from `projects.keycloak_issuer` per request. **A person who appears in two
customers' realms is two rows and two `user.id`s.**

That is not a cosmetic duplicate. `efn_profiles` is `PRIMARY KEY (user_id)` —
one EFN per person, deliberately, because ADR-0004 records what divergent EFNs
across courses do: a Punktemeldung credits the wrong physician's account, which
looks exactly like success. Two `user.id`s for one physician is two EFNs on
file, and the platform cannot tell that anything is wrong.

Asked directly, the answer was **one person, many customers** — one `user.id`,
one EFN, one certificate history. That is the right answer for CME, because the
EFN belongs to the physician and not to the customer, and it is the more
expensive one. This ticket is the expense.

## P21-01 · A person, their credentials, and their memberships — **done**

- **Estimate:** 5 h · **Depends on:** — · **Review gate: human — auth**

Identity splits into three things that were one:

| Table             | Is                                     | Keyed on                            |
| ----------------- | -------------------------------------- | ----------------------------------- |
| `users`           | the **person**                         | `id`                                |
| `user_identities` | a **credential** they can sign in with | `(provider, realm, subject)` unique |
| `user_customers`  | a **membership**                       | `(user_id, customer_id)` unique     |

`users.keycloak_realm` and `users.keycloak_sub` moved into `user_identities` as
one row per existing user, so nothing was lost and no `user.id` changed. That
matters: `enrolments`, `efn_profiles` and `certificates` all reference
`users(id)` and none of them may be rewritten.

Shipped as `db/migrations/0025_person_credentials_memberships.sql` **together
with** the code that reads it — the schema change and the code change are one
commit or they are an outage.

### The rule that must not be got wrong

**Two credentials are linked to one person only by an explicit, verified act —
never automatically because two identity providers reported the same email.**

An automatic email match is account takeover: any provider that does not verify
email addresses can then assert its way into an existing physician's CME history
and EFN. Some do not verify. The platform cannot tell which.

So a new `(provider, realm, subject)` creates a **new person** by default. The
merge is a deliberate operation, recorded in `admin_audit_log`, and it belongs
to P21-05 rather than here — because a merge that runs by accident is not
reversible in any way a physician would accept.

**Acceptance criteria**

- [x] Migration 0025 adds `user_identities` and `user_customers`, backfills one
      identity row per existing user, and keeps every `users.id`
- [x] `users` keeps no provider columns after the backfill — one place a
      credential can live, not two that can disagree
- [x] `user_customers` is RLS-scoped like every other tenant table; a customer
      admin sees their own memberships and no others
- [x] `users` stays **global**, deliberately: a person is not a tenant's
      property. What is tenant-scoped is the membership
- [x] Linking two credentials to one person is impossible on any authentication
      path. `provision_learner` resolves a credential or creates a person; it
      has no branch that attaches a credential to somebody who already exists
- [x] The tenant-isolation suite gains cases: a membership in one customer does
      not make the person visible in another, and an enrolment still resolves to
      exactly one person across both

### Two things running it found that reading it did not

Both were in the SQL this ticket originally drafted, and both would have shipped
as silent wrongness rather than as an error.

**1. The backfill would have inserted nothing.** It derives memberships with
`SELECT DISTINCT user_id, customer_id FROM enrolments`, and `enrolments` is under
`FORCE ROW LEVEL SECURITY` — which applies to the table _owner_, which is
`ds_migrator`, which is who runs migrations. Measured directly:

```
As ds_migrator, with FORCE on:   SELECT count(*) FROM enrolments  →  0
As the superuser, what is there: SELECT count(*) FROM enrolments  →  2
```

The `INSERT ... SELECT` would have succeeded having inserted nothing, the
migration would have reported success, and every existing learner would have
found themselves a member of no customer. The draft's `DISABLE ROW LEVEL
SECURITY` was on the _target_ table, which does not help — it is the read that
is filtered. Fixed with `ALTER TABLE enrolments NO FORCE ROW LEVEL SECURITY`
around the one statement: it exempts the owner and nobody else, takes ACCESS
EXCLUSIVE so no other session reads the table meanwhile, and is DDL inside the
migration's transaction so a failure below restores it.

**2. The policy used the shape migration 0014 exists to replace.** The draft
wrote `current_setting('app.customer_id', true)::uuid`. `set_config(…, true)` is
transaction-local and reverts to the _empty string_ rather than disappearing, so
on any pooled connection that has served a tenant request, a context-free query
meets `invalid input syntax for type uuid: ""` instead of returning no rows.
0014 predicted this in as many words — _"a future policy written by copying this
shape inherits the same defect"_ — and that is exactly what happened. The
integration suite caught it. The shape is `nullif(current_setting(…, true), '')`.

### And one thing the split cost that had to be bought back

`provisionOrUpdate` used to be a single `INSERT … ON CONFLICT (keycloak_realm,
keycloak_sub) DO UPDATE`, and that is _why_ it was race-free on the hot path of
every authenticated request: the database resolved concurrent first sights, not
the application.

"Insert a person, then insert their credential" has a window in which two
requests both create a person and one loses the credential insert — leaving a
person row nobody can ever sign in as, which no later request cleans up.
`provision_learner` (migration 0025) closes it in one round trip: the PL/pgSQL
sub-block is a savepoint, so the loser's person row rolls back with its
credential and the loop simply re-reads.

Verified with 640 concurrent calls across 40 unseen credentials:

```
rounds with a split identity: 0   (must be 0)
users created: 40 for 40 credentials   (must be 40)
people with no credential: 0   (must be 0)
```

## P21-02 · A participant the console can create — **open**

- **Estimate:** 6 h · **Depends on:** P21-01 · **Review gate: human — auth**

`IdentityProvider` (P12-02) is already a port, and `identity_provider` is
already a column on `projects` whose only legal value is `keycloak`. This adds
`local`.

A local participant is an email, an Argon2id password hash and the same
opaque-cookie session the staff plane uses (ADR-0012) — reusing that code
rather than writing a second one, because the second one is where the timing
leak goes.

**What it is not.** Not self-service signup: that is on the deferred list in
`CLAUDE.md` §3 and stays there. A participant is created by a customer admin,
or invited by one.

**Acceptance criteria**

- [ ] `identity_provider = 'local'` on a project routes to the new provider
- [ ] Password hashing, session issuance and rate limiting are the **same code**
      the staff plane uses, not a copy
- [ ] A participant belongs to a person (`users`), so a physician who is also a
      MEDICE learner is one person with two credentials — subject to P21-01's
      rule that only an explicit act links them
- [ ] MEDICE's learners are untouched. Their project keeps
      `identity_provider = 'keycloak'` and their realm, because the WordPress
      bridge depends on it

## P21-03 · The tenant in the path — **done (routing); deploy cleanup open**

- **Estimate:** 4 h · **Depends on:** P21-01 · **Review gate: human — auth**

Reported twice from the live deployment:

> still `https://fortbildung.digitalspital.com/` in here anmelden goes to medice,
> and the link is `https://login.medice.de/realms/medice/protocol/openid-connect/auth?…`
> and this even does not have any links to come back to our page

Two separate faults with one cause.

**The portal was one customer's front door.** `PORTAL_PROJECT_SLUG` in the
deployment named it, so the root _was_ MEDICE, no other customer was reachable
through it, and a visitor was pushed at MEDICE's identity provider before being
told where they were.

**And that is not how MEDICE signs anybody in.** Their WordPress plugin —
supplied, and read — uses the resource-owner password grant from a form on their
own site, with a client secret the plugin holds server-side. The portal was
inventing a second authentication route into the same realm: one MEDICE never
asked for, whose branding is Keycloak's rather than theirs, and which the
learner could not navigate back out of.

### What it is now

```
/                    a welcome page. No tenant, no login, no redirect.
/medice              MEDICE's catalogue, under MEDICE's name.
/medice/kurs/x       a course inside it.
```

How a tenant signs learners in is the **tenant's own configuration**, read from
the public `GET /tenants/{slug}`, and the portal links rather than deciding:

| `login_url` set | The customer's own page. A link, with `rel="noopener"`. This is MEDICE. |
| `login_url` null | The portal's own participant sign-in (P21-02). |

**Acceptance criteria**

- [x] `/` lists no customers and starts no login. Enumerating tenants would
      publish which pharmaceutical companies DigitalSpital works with — a
      commercial fact belonging to those customers, not routing metadata
- [x] A path naming a customer that does not exist is a **200 `unknown`** from
      the API and a plain "this does not exist" page, not a 404 — a 404 would be
      a project-slug oracle for one unauthenticated request (ADR-0007)
- [x] `X-DS-Project` is derived from the path, so the API's tenant resolution
      and RLS are unchanged
- [x] Migration 0028 adds `projects.login_url`, constrained to `https://` — the
      value is rendered as an `href`, so `javascript:` there is stored XSS with
      a customer administrator as the author, and `//evil.example` is an open
      redirect wearing a relative path. All four shapes probed and refused
- [x] `resolve_project_signin` deliberately returns **no issuer**. A public
      payload carrying one invites a second login flow, which is the exact
      mistake being undone
- [x] The tenant segment is validated against the slug grammar before it can
      reach a header. 12 traversal and injection shapes are tested
- [ ] `PORTAL_PROJECT_SLUG` still exists in `config.env`, `domains.sh` and
      `deploy.sh`. The portal ignores it, so nothing is broken — but a required
      key nobody reads is exactly the residue P18-01's guard exists to catch,
      and removing it touches the deploy test suite. Next commit

### Still open, and it needs an answer

For a `login_url` tenant the portal links out and **does not receive a token**,
so a MEDICE learner cannot yet complete a course _on the portal_ — they complete
it inside medice.de, through the WordPress plugin, which is where MEDICE's
learners already are.

Making the standalone portal work for them needs one of: MEDICE enabling the
authorization-code flow for `ds-portal` and us carrying `/medice` through the
redirect; or MEDICE issuing us a client secret so our API can mirror the
plugin's password grant server-side — which means handling physicians' MEDICE
passwords and using a grant deprecated in OAuth 2.1. **Asked, not yet answered.**
Recorded in `docs/show-stoppers.md`.

## P21-04 · Managing participants in the console — **done**

- **Estimate:** 5 h · **Depends on:** P21-02 · **Review gate: human — auth**

### What it turned out to be

P25-02 gave the learner plane a local credential and left exactly one way to
create one: run a seed from a shell on the production host. That is a
development fixture standing in for a product feature. A customer could not
onboard a physician, could not reset a forgotten password, and could not stop
an account belonging to somebody who had left — and "ask DigitalSpital to SSH
in" is not an answer for any of the three.

| Route                                          | What it does                                                  |
| ---------------------------------------------- | ------------------------------------------------------------- |
| `GET /admin/participants`                      | People, across the customer                                   |
| `POST /admin/participants`                     | Create one; the response is the **only** copy of the password |
| `POST /admin/participants/{id}/reset-password` | A new one, and every session ended                            |
| `POST /admin/participants/{id}/disabled`       | Stop or restore an account                                    |
| `POST /auth/participant/password`              | The participant chooses their own                             |
| `GET /auth/participant/me`                     | now also reports `mustChangePassword`                         |

The last row is what makes the requirement a requirement. Reporting the flag
only on the sign-in response would let a participant shown the change screen
press F5 and land in the catalogue — the session is already perfectly valid,
and nothing else would object. It has to be re-derivable from the database on
every page load, or it is advice.

### It is **not** a reuse of P12-05's screens, and the ticket was wrong to say so

The two answer different questions. Moderation is about _enrolments_ — a row per
person per course — and can only show somebody who has already started
something. This is about _people_. A participant created five seconds ago has no
enrolment and appears on no moderation screen at all, which makes moderation
exactly the wrong place to create them from.

### Three decisions worth recording

**`disabled_at` is a separate column from `locked_until`.** The lockout is
automatic and expires by itself; this is a deliberate act and nothing but
another one clears it. One column for both would mean an administrator blocking
an account by writing a timestamp far in the future, and a sweep one day
clearing it.

**Nothing is ever deleted.** Enrolments, certificates and EIV submissions hang
off the person; none may lose their owner because somebody left a job.

**The password is shown once and is not retrievable.** The alternative — mailing
an invitation link — is a credential-delivery channel that needs the SMTP
decisions S8 has not answered. Handing the administrator a password to pass on
is the honest interim, and `must_change` is what stops it being the physician's
password for ever.

**Acceptance criteria**

- [x] An administrator creates a participant who can immediately sign in and
      see the catalogue — across two connections and two transactions, either
      half of which missing gives a working sign-in followed by a 403
- [x] The password appears in exactly one response body, is stored only as an
      Argon2id hash, and appears in no list response
- [x] A new account carries `must_change`, and the portal **blocks** on
      `ChangePassword` until it is satisfied — so P25-02's note that the flag
      "pointed nowhere" is discharged rather than restated
- [x] The requirement survives a reload: `GET me` re-derives it from the
      database, so a valid session is not enough to reach the catalogue
- [x] An administrator's reset raises it again — a reset leaves a password
      somebody else chose, exactly as a fresh account does
- [x] `checkPassword` catches the **local part** of an address, not only the
      whole one. Its comment always claimed it did; it did not, and that was
      the platform's single password policy, so the staff plane had the same
      hole
- [x] Disabling stops a sign-in **and** ends the sessions already open
- [x] Another customer's participant answers **404**, not 403 — a 403 confirms
      the id names somebody and turns the route into an enumeration oracle
- [x] `customerId` comes from the session, never the body
- [x] A federated participant's buttons are disabled rather than offered and
      then refused with a 409
- [x] The password policy is `checkPassword` from `packages/domain` — the same
      one the staff plane uses, not a second, weaker copy

Probe: deleting the `isMember` check fails exactly the two boundary tests.

## P21-05 · Merging two credentials into one person — **done**

- **Estimate:** 4 h · **Depends on:** P21-01 · **Review gate: human — auth**

The deliberate act P21-01 refuses to do automatically. Needed the first time a
physician who already learns with MEDICE is given a DS participant login.

### The rule, and why it is three refusals rather than a merge strategy

`planCredentialMerge` in `packages/domain` refuses when the merge would have to
**choose** something, and each refusal is a question rather than a policy:

| Refused                             | Because                                                                                                                                                   |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two **different EFNs** on file      | Both sides are already reporting to an Ärztekammer under a different number. Picking one silently re-attributes the other's points. Named in this ticket. |
| A **course both sides are on**      | Two watch histories and two quiz-attempt sets on one course. Whichever survives, a physician loses progress they earned — and both may have completed.    |
| A person merged **into themselves** | Never what the operator meant, and an operation that silently does nothing is one somebody repeats while looking for the effect.                          |

The verdict is symmetric, deliberately: an operator who reverses the arguments
to get past a refusal has resolved nothing. Ten unit tests, including that
symmetry.

The EFN comparison is a **SHA-256 digest**, never the digits. The domain only
asks whether two numbers differ, and carrying the number out of the database
would put it in this process's heap and in any exception that quotes a
parameter, for no gain (ADR-0004).

### What running it found that reading it did not

**The merge was written as ordinary `ds_app` SQL, and it moved nothing —
silently.** Every table it reads and every table it moves is tenant-scoped under
`FORCE ROW LEVEL SECURITY`, and the whole point of the operation is a physician
who exists in _two_ places, frequently two customers. With the request's tenant
context set to one of them:

- the `SELECT` for the other side returned no EFN and no enrolments, so
  `planCredentialMerge` saw two empty records and **allowed every merge**;
- `UPDATE enrolments SET user_id = …` matched zero rows and reported success.

A merge that reports success and moves nothing is worse than one that fails: an
operator confirms an irreversible operation, is told it worked, and finds the
records where they were. Only the integration suite could have caught it — this
is the third time in this project that a tenant-scoped read inside an
inherently cross-tenant operation has produced silent nothingness (P21-01's
backfill, migration 0014's `current_setting` shape, and now this).

Migration 0033 is the fix: `participant_merge_side` and `merge_participants`,
SECURITY DEFINER, owned by a **fourth** narrow BYPASSRLS role `ds_merge` that
owns those two functions and nothing else — asserted in the migration's own
transaction, as `ds_erasure` and `ds_customer_registry` are. `EXECUTE` is
granted to `ds_app` alone.

A second thing running it found: **BYPASSRLS grants no table privileges.** The
first version of the migration omitted the GRANTs and every merge failed with
"permission denied for table users", which reads like an application bug and is
a missing grant. They are listed table by table and verb by verb rather than
`ALL ON ALL TABLES`, because the role's justification is that its reach fits on
one screen.

### The authorization decision

**`super_admin` only**, deliberately not the participant roles. A merge
routinely spans two customers, and a customer-scoped administrator is correctly
unable to see the other side — so they would be confirming against a record they
cannot read. Being above every tenant is the only position from which both sides
are visible.

The console still shows the button to everybody and lets the API answer 403,
rather than hiding it: a customer admin who cannot perform the operation should
still be able to find out that it exists and who can.

### The confirmation, and the audit row

Two endpoints. `POST /admin/participants/merge/preview` reads and writes
nothing and returns both sides plus the verdict; `POST /admin/participants/merge`
does the irreversible thing and requires `confirm` to equal `targetUserId`. The
plan is **re-computed** at merge time rather than trusted from the preview —
between the two calls a physician can start a course, and the confirmation the
operator is holding would be a verdict about a state that no longer exists.

`admin_audit_log` is written **inside the same transaction**. `AuditService`
deliberately writes on its own connection so an entry survives the failure of
what followed; the opposite is right here. The detail carries ids and counts
only — no EFN, no name.

### Sessions are ended, not moved

A session was minted for a credential whose person has just changed, and the
safe answer to "is it still valid?" is no. Naming each table in the function is
what made that a decision; an `ON UPDATE CASCADE` on the person id would have
carried them across without anyone choosing it.

`certificates`, `eiv_submissions`, `content_progress`, `quiz_attempts` and the
evaluation responses hang off `enrolment_id`, so moving the enrolment carries
them — checked with an assertion rather than assumed, because a merge that moved
the enrolment and left the certificate would produce a PDF in one person's name
against another's record and nothing would have failed.

**Acceptance criteria**

- [x] A confirmation naming both credentials, and a second decision (`confirm`)
      that a mis-click cannot make
- [x] An `admin_audit_log` entry, in the same transaction as the merge
- [x] Refused when both sides already have **different** EFNs on file
- [x] Refused when both sides are enrolled on the same course — the same
      reasoning, applied to the other thing a merge would have to choose
- [x] A refusal moves nothing. Asserted by effect, and probed by deliberate
      violation: removing the overlap check fails exactly those tests
- [x] `super_admin` only, enforced by the guard chain and asserted over HTTP
