# P21 · Participants, memberships and tenants in the path

Three requests that turn out to be one change:

1. A **participant** the admin console can create, who signs in to
   `fortbildung.digitalspital.com` when it is not embedded in anyone's website.
2. A learner who **belongs to more than one customer**.
3. The **tenant in the URL** — `/medice`, `/ds` — deciding which catalogue a
   signed-in learner sees.

**Review gate: human — auth.** P21-01 changes the key that identifies a
physician, and P21-02 adds a way to authenticate one. A wrong result here
credits the wrong person's CME account.

---

## What is in the way, precisely

`users` is keyed `UNIQUE (keycloak_realm, keycloak_sub)`, and the realm comes
from `projects.keycloak_issuer` per request. **A person who appears in two
customers' realms is two rows and two `user.id`s.**

That is not a cosmetic duplicate. `efn_profiles` is `PRIMARY KEY (user_id)` —
one EFN per person, deliberately, because ADR-0004 records what divergent EFNs
across courses do: a Punktemeldung credits the wrong physician's account, which
looks exactly like success. Two `user.id`s for one physician is two EFNs on
file, and the platform cannot tell that anything is wrong.

Asked directly, the answer was **one person, many customers** — one `user.id`,
one EFN, one certificate history. That is the right answer for CME, because the
EFN belongs to the physician and not to the customer, and it is the more
expensive one. This ticket is the expense.

## P21-01 · A person, their credentials, and their memberships — **open**

- **Estimate:** 5 h · **Depends on:** — · **Review gate: human — auth**

Identity splits into three things that are currently one:

| Table             | Is                                     | Keyed on                            |
| ----------------- | -------------------------------------- | ----------------------------------- |
| `users`           | the **person**                         | `id`                                |
| `user_identities` | a **credential** they can sign in with | `(provider, realm, subject)` unique |
| `user_customers`  | a **membership**                       | `(user_id, customer_id)` unique     |

`users.keycloak_realm` and `users.keycloak_sub` move into `user_identities` as
one row per existing user, so nothing is lost and no `user.id` changes. That
matters: `enrolments`, `efn_profiles` and `certificates` all reference
`users(id)` and none of them may be rewritten.

### The rule that must not be got wrong

**Two credentials are linked to one person only by an explicit, verified act —
never automatically because two identity providers reported the same email.**

An automatic email match is account takeover: any provider that does not verify
email addresses can then assert its way into an existing physician's CME
history and EFN. Some do not verify. The platform cannot tell which.

So a new `(provider, realm, subject)` creates a **new person** by default. The
merge is a deliberate operation, recorded in `admin_audit_log`, and it belongs
to P21-05 rather than here — because a merge that runs by accident is not
reversible in any way a physician would accept.

**Acceptance criteria**

- [ ] Migration 0025 adds `user_identities` and `user_customers`, backfills one
      identity row per existing user, and keeps every `users.id`
- [ ] `users` keeps no provider columns after the backfill — one place a
      credential can live, not two that can disagree
- [ ] `user_customers` is RLS-scoped like every other tenant table; a customer
      admin sees their own memberships and no others
- [ ] `users` stays **global**, deliberately: a person is not a tenant's
      property. What is tenant-scoped is the membership
- [ ] Linking two credentials to one person is impossible in this migration.
      There is no code path that does it, so there is none to get wrong
- [ ] The tenant-isolation suite gains cases: a membership in one customer does
      not make the person visible in another, and an enrolment still resolves to
      exactly one person across both

### The migration, drafted and deliberately not in `db/migrations/`

It is written out below rather than committed as `0025_*.sql`, and the reason
is not caution for its own sake: `@ds/migrator` runs **every `*.sql` in that
directory** on the next deploy. This one drops `users.keycloak_realm` and
`users.keycloak_sub`, and **77 references across eight source files still read
them** — the auth guard, the user repository, subject erasure, authoring, the
Drizzle schema, the seed and six integration suites.

Committing it before those move would break the running platform at the
migration step of the next deploy, after the backup and before the swap. The
schema change and the code change are one commit or they are an outage.

```sql
-- A person, their credentials, and the customers they belong to (P21-01).
--
-- ## The problem this fixes
--
-- `users` is keyed `UNIQUE (keycloak_realm, keycloak_sub)`, and the realm comes
-- from `projects.keycloak_issuer` per request. A physician who appears in two
-- customers' realms is therefore **two rows and two user ids**.
--
-- That is not a cosmetic duplicate. `efn_profiles` is `PRIMARY KEY (user_id)` —
-- one EFN per person, deliberately, because ADR-0004 records what divergent
-- EFNs across courses do: a Punktemeldung credits the wrong physician's
-- account, which looks exactly like success. Two user ids for one physician is
-- two EFNs on file and no way for the platform to know.
--
-- Asked directly, the client chose **one person, many customers** — one user
-- id, one EFN, one certificate history. This migration is what that costs.
--
-- ## The shape
--
--   users            the *person*.        Keyed on id. Global, not tenant-scoped.
--   user_identities  a *credential*.      Unique on (provider, realm, subject).
--   user_customers   a *membership*.      Unique on (user_id, customer_id).
--
-- Every existing `users.id` survives: `enrolments`, `efn_profiles` and
-- `certificates` all reference it and none of them may be rewritten. The
-- provider columns move rather than being re-derived, so the backfill cannot
-- lose or invent a credential.
--
-- ## Why `users` stays global
--
-- A person is not a tenant's property. Their EFN, their certificates and their
-- name belong to them across every customer they learn with — that is the whole
-- point of the decision above. What *is* tenant-scoped is the membership, and
-- `user_customers` carries the `customer_id` and the RLS policy accordingly.
--
-- ## The rule this migration enforces by having no code for it
--
-- **Two credentials are linked to one person only by an explicit, verified
-- act.** Never automatically because two identity providers reported the same
-- email address: a provider that does not verify email can then assert its way
-- into an existing physician's CME history and EFN, and the platform cannot
-- tell which providers verify.
--
-- So a new `(provider, realm, subject)` creates a **new person**. The merge is
-- P21-05, deliberate, audited, and refused when both sides already have
-- different EFNs on file — that is not a merge, it is a question for a human.
--
-- There is no path in this migration that links two credentials, which is the
-- strongest form the rule can take.

-- ---------------------------------------------------------------------------
-- Credentials
-- ---------------------------------------------------------------------------
CREATE TABLE user_identities (
    id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,

    -- Matches `projects.identity_provider`, whose only value today is
    -- 'keycloak'. 'local' arrives with P21-02.
    provider   text NOT NULL CHECK (provider IN ('keycloak', 'local')),

    -- The issuer for an OIDC provider. For 'local' it is the platform itself,
    -- spelled 'ds:local' rather than left empty — an empty string in a unique
    -- key is a value that looks like an accident.
    realm      text NOT NULL,

    -- `sub` for OIDC. For 'local', the participant account's own id.
    subject    text NOT NULL,

    created_at timestamptz NOT NULL DEFAULT now(),

    -- One credential authenticates one person. Without this, two rows could
    -- claim the same subject and the guard would have to choose.
    UNIQUE (provider, realm, subject)
);

CREATE INDEX user_identities_user_idx ON user_identities (user_id);

-- Move, do not re-derive. Every existing user gets exactly one credential, and
-- its user_id is unchanged.
INSERT INTO user_identities (user_id, provider, realm, subject)
SELECT id, 'keycloak', keycloak_realm, keycloak_sub FROM users;

-- The old key goes, so a credential cannot live in two places and disagree.
ALTER TABLE users DROP CONSTRAINT users_keycloak_realm_keycloak_sub_key;
ALTER TABLE users DROP COLUMN keycloak_realm;
ALTER TABLE users DROP COLUMN keycloak_sub;

-- ---------------------------------------------------------------------------
-- Memberships
-- ---------------------------------------------------------------------------
CREATE TABLE user_customers (
    id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    customer_id uuid NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
    created_at  timestamptz NOT NULL DEFAULT now(),
    UNIQUE (user_id, customer_id)
);

CREATE INDEX user_customers_customer_idx ON user_customers (customer_id);

-- Tenant-scoped like every other table carrying a customer_id, and FORCE so
-- that ds_migrator is held to it too (ADR-0002). `true` on current_setting so
-- an unset context yields NULL and the policy simply excludes every row,
-- rather than erroring — migration 0014's rule.
ALTER TABLE user_customers ENABLE ROW LEVEL SECURITY;
ALTER TABLE user_customers FORCE ROW LEVEL SECURITY;

CREATE POLICY user_customers_tenant_isolation ON user_customers
  USING (customer_id = current_setting('app.customer_id', true)::uuid)
  WITH CHECK (customer_id = current_setting('app.customer_id', true)::uuid);

GRANT SELECT, INSERT, UPDATE, DELETE ON user_identities TO ds_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON user_customers TO ds_app;

-- Backfill the memberships that already exist implicitly: anybody enrolled in a
-- customer's course is a member of that customer. Derived rather than assumed,
-- so the first deploy does not lock existing learners out of their own courses.
--
-- Runs as ds_migrator, which FORCE RLS also applies to — hence the explicit
-- context-free INSERT ... SELECT is not possible. The policy is dropped for the
-- duration of the backfill instead of granting BYPASSRLS to anything.
ALTER TABLE user_customers DISABLE ROW LEVEL SECURITY;
INSERT INTO user_customers (user_id, customer_id)
SELECT DISTINCT user_id, customer_id FROM enrolments
ON CONFLICT (user_id, customer_id) DO NOTHING;
ALTER TABLE user_customers ENABLE ROW LEVEL SECURITY;
```

Two details in it worth a reviewer's attention:

- **The backfill derives memberships from `enrolments`.** Anybody enrolled in a
  customer's course is already a member of that customer, and deriving it is
  what stops the first deploy locking existing learners out of their own
  courses.
- **It disables the policy for the backfill rather than granting `BYPASSRLS`.**
  `FORCE ROW LEVEL SECURITY` applies to `ds_migrator` too, so a context-free
  `INSERT ... SELECT` inserts nothing. A fourth `BYPASSRLS` role would be a
  permanent privilege bought to solve a one-statement problem.

## P21-02 · A participant the console can create — **open**

- **Estimate:** 6 h · **Depends on:** P21-01 · **Review gate: human — auth**

`IdentityProvider` (P12-02) is already a port, and `identity_provider` is
already a column on `projects` whose only legal value is `keycloak`. This adds
`local`.

A local participant is an email, an Argon2id password hash and the same
opaque-cookie session the staff plane uses (ADR-0012) — reusing that code
rather than writing a second one, because the second one is where the timing
leak goes.

**What it is not.** Not self-service signup: that is on the deferred list in
`CLAUDE.md` §3 and stays there. A participant is created by a customer admin,
or invited by one.

**Acceptance criteria**

- [ ] `identity_provider = 'local'` on a project routes to the new provider
- [ ] Password hashing, session issuance and rate limiting are the **same code**
      the staff plane uses, not a copy
- [ ] A participant belongs to a person (`users`), so a physician who is also a
      MEDICE learner is one person with two credentials — subject to P21-01's
      rule that only an explicit act links them
- [ ] MEDICE's learners are untouched. Their project keeps
      `identity_provider = 'keycloak'` and their realm, because the WordPress
      bridge depends on it

## P21-03 · The tenant in the path — **open**

- **Estimate:** 4 h · **Depends on:** P21-01

`fortbildung.digitalspital.com/medice` and `/ds`. The path segment names the
customer, and it decides which catalogue a signed-in learner sees.

This removes `PORTAL_PROJECT_SLUG`, which is why the portal today _is_ MEDICE's
front door and there is no way to reach the DS tenant through it. It is the
same removal P18-03 wants for the console's default project.

**Acceptance criteria**

- [ ] `/` lists the customers the signed-in person is a member of, and goes
      straight through when there is exactly one — a chooser with one option is
      a click nobody should have to make
- [ ] A path naming a customer the person is **not** a member of is a 404, not a
      403: whether a customer exists is not a fact an outsider should learn
- [ ] `X-DS-Project` is derived from the path, so the API's tenant resolution
      and RLS are unchanged
- [ ] The OIDC redirect URI carries the path back, or a learner returns from
      Keycloak to the wrong tenant
- [ ] `PORTAL_PROJECT_SLUG` is gone from `config.env.example`, `domains.sh` and
      the runbook

## P21-05 · Merging two credentials into one person — **open**

- **Estimate:** 4 h · **Depends on:** P21-01 · **Review gate: human — auth**

The deliberate act P21-01 refuses to do automatically. Needed the first time a
physician who already learns with MEDICE is given a DS participant login.

**It is not reversible in any way a physician would accept**, so it wants a
confirmation naming both credentials, an `admin_audit_log` entry, and a refusal
when both sides already have **different** EFNs on file — that is not a merge,
it is a question for a human.
