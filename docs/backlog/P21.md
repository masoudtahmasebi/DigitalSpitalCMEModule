# P21 · Participants, memberships and tenants in the path

Three requests that turn out to be one change:

1. A **participant** the admin console can create, who signs in to
   `fortbildung.digitalspital.com` when it is not embedded in anyone's website.
2. A learner who **belongs to more than one customer**.
3. The **tenant in the URL** — `/medice`, `/ds` — deciding which catalogue a
   signed-in learner sees.

**Review gate: human — auth.** P21-01 changes the key that identifies a
physician, and P21-02 adds a way to authenticate one. A wrong result here
credits the wrong person's CME account.

---

## What is in the way, precisely

`users` is keyed `UNIQUE (keycloak_realm, keycloak_sub)`, and the realm comes
from `projects.keycloak_issuer` per request. **A person who appears in two
customers' realms is two rows and two `user.id`s.**

That is not a cosmetic duplicate. `efn_profiles` is `PRIMARY KEY (user_id)` —
one EFN per person, deliberately, because ADR-0004 records what divergent EFNs
across courses do: a Punktemeldung credits the wrong physician's account, which
looks exactly like success. Two `user.id`s for one physician is two EFNs on
file, and the platform cannot tell that anything is wrong.

Asked directly, the answer was **one person, many customers** — one `user.id`,
one EFN, one certificate history. That is the right answer for CME, because the
EFN belongs to the physician and not to the customer, and it is the more
expensive one. This ticket is the expense.

## P21-01 · A person, their credentials, and their memberships — **done**

- **Estimate:** 5 h · **Depends on:** — · **Review gate: human — auth**

Identity splits into three things that were one:

| Table             | Is                                     | Keyed on                            |
| ----------------- | -------------------------------------- | ----------------------------------- |
| `users`           | the **person**                         | `id`                                |
| `user_identities` | a **credential** they can sign in with | `(provider, realm, subject)` unique |
| `user_customers`  | a **membership**                       | `(user_id, customer_id)` unique     |

`users.keycloak_realm` and `users.keycloak_sub` moved into `user_identities` as
one row per existing user, so nothing was lost and no `user.id` changed. That
matters: `enrolments`, `efn_profiles` and `certificates` all reference
`users(id)` and none of them may be rewritten.

Shipped as `db/migrations/0025_person_credentials_memberships.sql` **together
with** the code that reads it — the schema change and the code change are one
commit or they are an outage.

### The rule that must not be got wrong

**Two credentials are linked to one person only by an explicit, verified act —
never automatically because two identity providers reported the same email.**

An automatic email match is account takeover: any provider that does not verify
email addresses can then assert its way into an existing physician's CME history
and EFN. Some do not verify. The platform cannot tell which.

So a new `(provider, realm, subject)` creates a **new person** by default. The
merge is a deliberate operation, recorded in `admin_audit_log`, and it belongs
to P21-05 rather than here — because a merge that runs by accident is not
reversible in any way a physician would accept.

**Acceptance criteria**

- [x] Migration 0025 adds `user_identities` and `user_customers`, backfills one
      identity row per existing user, and keeps every `users.id`
- [x] `users` keeps no provider columns after the backfill — one place a
      credential can live, not two that can disagree
- [x] `user_customers` is RLS-scoped like every other tenant table; a customer
      admin sees their own memberships and no others
- [x] `users` stays **global**, deliberately: a person is not a tenant's
      property. What is tenant-scoped is the membership
- [x] Linking two credentials to one person is impossible on any authentication
      path. `provision_learner` resolves a credential or creates a person; it
      has no branch that attaches a credential to somebody who already exists
- [x] The tenant-isolation suite gains cases: a membership in one customer does
      not make the person visible in another, and an enrolment still resolves to
      exactly one person across both

### Two things running it found that reading it did not

Both were in the SQL this ticket originally drafted, and both would have shipped
as silent wrongness rather than as an error.

**1. The backfill would have inserted nothing.** It derives memberships with
`SELECT DISTINCT user_id, customer_id FROM enrolments`, and `enrolments` is under
`FORCE ROW LEVEL SECURITY` — which applies to the table _owner_, which is
`ds_migrator`, which is who runs migrations. Measured directly:

```
As ds_migrator, with FORCE on:   SELECT count(*) FROM enrolments  →  0
As the superuser, what is there: SELECT count(*) FROM enrolments  →  2
```

The `INSERT ... SELECT` would have succeeded having inserted nothing, the
migration would have reported success, and every existing learner would have
found themselves a member of no customer. The draft's `DISABLE ROW LEVEL
SECURITY` was on the _target_ table, which does not help — it is the read that
is filtered. Fixed with `ALTER TABLE enrolments NO FORCE ROW LEVEL SECURITY`
around the one statement: it exempts the owner and nobody else, takes ACCESS
EXCLUSIVE so no other session reads the table meanwhile, and is DDL inside the
migration's transaction so a failure below restores it.

**2. The policy used the shape migration 0014 exists to replace.** The draft
wrote `current_setting('app.customer_id', true)::uuid`. `set_config(…, true)` is
transaction-local and reverts to the _empty string_ rather than disappearing, so
on any pooled connection that has served a tenant request, a context-free query
meets `invalid input syntax for type uuid: ""` instead of returning no rows.
0014 predicted this in as many words — _"a future policy written by copying this
shape inherits the same defect"_ — and that is exactly what happened. The
integration suite caught it. The shape is `nullif(current_setting(…, true), '')`.

### And one thing the split cost that had to be bought back

`provisionOrUpdate` used to be a single `INSERT … ON CONFLICT (keycloak_realm,
keycloak_sub) DO UPDATE`, and that is _why_ it was race-free on the hot path of
every authenticated request: the database resolved concurrent first sights, not
the application.

"Insert a person, then insert their credential" has a window in which two
requests both create a person and one loses the credential insert — leaving a
person row nobody can ever sign in as, which no later request cleans up.
`provision_learner` (migration 0025) closes it in one round trip: the PL/pgSQL
sub-block is a savepoint, so the loser's person row rolls back with its
credential and the loop simply re-reads.

Verified with 640 concurrent calls across 40 unseen credentials:

```
rounds with a split identity: 0   (must be 0)
users created: 40 for 40 credentials   (must be 40)
people with no credential: 0   (must be 0)
```

## P21-02 · A participant the console can create — **open**

- **Estimate:** 6 h · **Depends on:** P21-01 · **Review gate: human — auth**

`IdentityProvider` (P12-02) is already a port, and `identity_provider` is
already a column on `projects` whose only legal value is `keycloak`. This adds
`local`.

A local participant is an email, an Argon2id password hash and the same
opaque-cookie session the staff plane uses (ADR-0012) — reusing that code
rather than writing a second one, because the second one is where the timing
leak goes.

**What it is not.** Not self-service signup: that is on the deferred list in
`CLAUDE.md` §3 and stays there. A participant is created by a customer admin,
or invited by one.

**Acceptance criteria**

- [ ] `identity_provider = 'local'` on a project routes to the new provider
- [ ] Password hashing, session issuance and rate limiting are the **same code**
      the staff plane uses, not a copy
- [ ] A participant belongs to a person (`users`), so a physician who is also a
      MEDICE learner is one person with two credentials — subject to P21-01's
      rule that only an explicit act links them
- [ ] MEDICE's learners are untouched. Their project keeps
      `identity_provider = 'keycloak'` and their realm, because the WordPress
      bridge depends on it

## P21-03 · The tenant in the path — **open**

- **Estimate:** 4 h · **Depends on:** P21-01

`fortbildung.digitalspital.com/medice` and `/ds`. The path segment names the
customer, and it decides which catalogue a signed-in learner sees.

This removes `PORTAL_PROJECT_SLUG`, which is why the portal today _is_ MEDICE's
front door and there is no way to reach the DS tenant through it. It is the
same removal P18-03 wants for the console's default project.

**Acceptance criteria**

- [ ] `/` lists the customers the signed-in person is a member of, and goes
      straight through when there is exactly one — a chooser with one option is
      a click nobody should have to make
- [ ] A path naming a customer the person is **not** a member of is a 404, not a
      403: whether a customer exists is not a fact an outsider should learn
- [ ] `X-DS-Project` is derived from the path, so the API's tenant resolution
      and RLS are unchanged
- [ ] The OIDC redirect URI carries the path back, or a learner returns from
      Keycloak to the wrong tenant
- [ ] `PORTAL_PROJECT_SLUG` is gone from `config.env.example`, `domains.sh` and
      the runbook

## P21-05 · Merging two credentials into one person — **open**

- **Estimate:** 4 h · **Depends on:** P21-01 · **Review gate: human — auth**

The deliberate act P21-01 refuses to do automatically. Needed the first time a
physician who already learns with MEDICE is given a DS participant login.

**It is not reversible in any way a physician would accept**, so it wants a
confirmation naming both credentials, an `admin_audit_log` entry, and a refusal
when both sides already have **different** EFNs on file — that is not a merge,
it is a question for a human.
