## P247-01 — participant reset sends a link; disable is per membership

**Review gate:** human (auth) · closes SEC-1

**Context**

A merge copies every membership and every identity onto one person
(`db/migrations/0033_participant_merge.sql:171`, `:173`). Every local identity
has the realm `ds:local` (`apps/api/src/auth/local-identity-provider.ts:76`),
so a merged person can hold two local credentials. Both the console's reset
(`participant.repository.ts:131`, `credentialIdFor`) and sign-in
(`participant-auth.repository.ts:128`, `findParticipant`) pick one with an
unordered `LIMIT 1`. Customer A's admin passes `isMember` for a person who also
belongs to customer B, and `resetPassword` returns `{ temporaryPassword }`; when
both queries pick the same credential, A's admin can sign in as the physician at
B. Disable sets `learner_credentials.disabled_at`, so A can lock them out at B.

Verified: the lines above, read on `0208b64`. Not reproduced against a
database. The comment in `participant-auth.service.ts` ("only the one for the
named project is touched") is false for sign-in.

Rejected: super-admin-only reset (takes a support task from customers);
refusing shared people (the client chose per-customer disable).

**Scope**

- `POST /admin/participants/:userId/reset-password` no longer sets or returns a
  password. It sends the person the existing P40 reset link
  (`beginPasswordReset`), using the caller's customer's local project; it
  answers 202 with no body. Contract and SDK change first.
- Disable moves to the membership: `user_customers.disabled_at` (and
  `disabled_by`), migration with backfill from `learner_credentials.disabled_at`
  onto every membership of that person. Sign-in and reset at customer B ignore
  a block set at A. `learner_credentials.disabled_at` is no longer read.
- `merge_participants` keeps exactly one local credential — the most recently
  used — and records which it dropped in the merge audit row.
- Console: the reset control says a link was emailed to the address on file
  and what to do if it does not arrive; nothing shows a password. Copy in the
  locale file. The disable control says it applies to this customer only.
- The false comment is corrected.

**Acceptance criteria**

- [x] An integration case merges a person across customers A and B; A's admin
      calls reset-password; the response carries no password field and the
      person's credential hash is unchanged. Red on `0208b64`.
      — `participant-cross-customer` › _a reset by A's admin returns no password
      and leaves the hash unchanged_. Red: `{"temporaryPassword":"…"}: expected
    201 to be 202`.
- [x] A reset link is mailed only when the caller's project is `local` and can
      send; otherwise the answer is the same 202 and no token is minted (§9.5).
      — _mints a token only when the project is local and can send_ (A: 1
      token; B, no sender: 0; C, sender only on its Keycloak project: 0; all
      202 with an empty body). Red: `expected 201 to be 202`.
- [x] A's admin disables the merged person; sign-in at B still succeeds and
      sign-in at A is refused. — _a block at A does not reach B_. Red:
      `expected 401 to be 200` (B refused).
- [x] After a merge of two people with local credentials, exactly one
      credential remains; sign-in with the dropped password is refused. —
      _keeps one local credential, the most recently used_. Red: `expected 2
    to be 1`.
- [x] `pnpm check:roles` and the console screen agree: no control offers a
      password. — `check:roles` green (route and roles unchanged);
      `ParticipantAccounts.test.tsx` › _says a link was mailed, and shows no
      password, after a reset_. **Deviation:** _create_ still shows the new
      account's one-time password — see "Not done" below.

### Existing tests changed, and why

Four existing cases asserted exactly what the client withdrew. They were
rewritten to the new behaviour, not deleted:

- `participants` › _resetting a password_ asserted the reset returned a new
  password and ended every session → now: 202, empty body, old password and
  session still work.
- `participants` › _raises the requirement again after an administrator resets_
  → _leaves a self-chosen password in place…_: no password is planted, so
  `mustChange` stays false.
- `participants` › _cannot disable another customer's participant_ now reads
  beta's membership row instead of the credential.
- `participant-merge` › _moves every credential…_ asserted `2` local identities
  after the merge → `1`.

`support/reset-each-file.ts` also clears rate-limit buckets in `beforeAll`: a
file's own `beforeAll` sign-ins inherited the previous file's spent
`participantSignIn` bucket, and `participants` answered 429 before any case ran.

### Assumed

- **Which project sends.** The console scopes a request to a customer, not a
  project, so the reset uses the **oldest `local` project of the caller's
  customer whose sender `canSend`**. A Keycloak project is never used even if
  it has a sender. This cannot mis-send across tenants (every candidate is the
  caller's own customer's, read under RLS) and cannot mint a link nobody can
  deliver. Whether a customer with two local portals wants a different choice
  is a product question.
- **The link's host** is `PORTAL_BASE_URL`; when it is empty nothing is minted.
- **Backfill** copies an existing credential block onto **every** membership of
  that person — wider than the one customer that set it, and the only reading
  that does not silently unblock somebody.
- A merge **carries a block across**: if either side was blocked at a customer,
  the merged person is blocked there.
- People merged **before** 0057 may still hold two local credentials. They are
  not deleted by the migration; every reader now picks one with the merge's
  ordering.

### Not done — a product decision, raised rather than guessed

**Creating** an account still returns and shows the generated password once
(`POST /admin/participants`, `IssuedPassword`). The ticket's scope changes the
reset only, and an emailed invitation for new participants is a new flow the
client has not specified. The residual: an administrator at A knows a new
account's initial password until the physician changes it (`must_change`), and
a later merge onto a person at B would carry it there if it is the most
recently used. Recommend a follow-up ticket: create mails the P40 link instead.

**Not in scope**

Federated (Keycloak) participants — their passwords are not ours (unchanged).

## P247-02 — media and SMTP hosts cannot point inside the network

**Review gate:** human (certificates: SMTP delivers them) · closes SEC-2

**Context**

`authoring.dto.ts:327` accepts any media URL; `media-check.service.ts:102`
fetches it with redirects followed and returns the status, an oracle into the
internal network. `projects.smtp_host` is the same class.

**Scope**

- Media URLs: `https:` only, on write.
- One outbound-address guard used by the media check and SMTP: resolve the
  host, refuse loopback, private, link-local, CGNAT and unspecified addresses,
  and names that resolve to them; no redirect following in the media check.
- The refusal names the field, never the value (§9.5).

**Acceptance criteria**

- [ ] Unit: `http://127.0.0.1:5432/` and `https://169.254.169.254/` are
      refused with no fetch made (fetch counter = 0).
- [ ] Unit: a redirect from a public URL to a private one is not followed.
- [ ] Integration: saving an `http:` media URL answers 400 naming `url`.

### Plan

**Interfaces**

- Produces: `isForbiddenAddress(ip: string): boolean` and
  `resolvePublicAddress(host: string, lookup?: LookupAll): Promise<string>` in
  `apps/api/src/shared/outbound-address.ts` (throws `OutboundAddressRefused`).
- Produces: `SmtpDeliveryChannel` option `vetHost?: (host) => Promise<string>`
  and transport key `SMTP_KEYS.publicOnly`; with it set the channel connects to
  the vetted address with `servername` = the name (no second resolution).

- [ ] **1. Failing unit tests** — `media-check.service.test.ts`:
      `http://127.0.0.1:5432/` and `https://169.254.169.254/` → verdict
      `failed`, fetch counter `0`; a public URL answering `302 Location:
http://10.0.0.1/` → counter `1`, verdict not `seekable`, `redirect:
"manual"` passed. `outbound-address.test.ts`: loopback, RFC 1918,
      link-local, CGNAT `100.64/10`, unspecified, IPv6 `::1`, `fc00::/7`,
      `fe80::/10`, v4-mapped — refused; a name resolving to any of them refused.
- [ ] **2. Failing integration** — `authoring.integration.test.ts`: saving a
      content with `sources: [{ url: "http://…" }]` → 422 problem naming `url`,
      body not containing the value.
- [ ] **3. Implement** — `mediaReference` and `mediaSourceWriteSchema.url`
      accept `https://` or `s3://` only; the media check calls
      `resolvePublicAddress` before `fetchImpl`, with `redirect: "manual"`;
      project-sourced SMTP (certificate delivery `kind === "project"`, the P40
      participant reset) sets `publicOnly`; the API's channels are built with
      `vetHost = resolvePublicAddress`.
- [ ] **4. Pass, break, restore; commit** — `P247-02: refuse internal addresses for media and SMTP`.

## P247-03 — one JWKS fetch per lifetime; staff sign-in throttled per IP

**Review gate:** human (auth) · closes SEC-3, SEC-4

**Scope**

- `jwks.provider.ts`: refresh the snapshot only when missing or older than
  `JWKS_CACHE_TTL_SEC`; one in-flight refresh per issuer. Also settles the
  "revoked key" needs-verification item: a `kid` absent from a fresh fetch is
  not served from the snapshot.
- `@RateLimit("staffLogin")`, keyed by client IP, on staff `login` and
  `totp/verify`, alongside the existing per-account lockout.

**Acceptance criteria**

- [ ] Unit: ten verifications within the TTL make at most one JWKS fetch
      (counter). Red on `0208b64`.
- [ ] Integration: the n+1th staff login from one IP inside the window answers
      429 with a problem document; another IP is unaffected.

### Plan

- [ ] **1. Failing unit test** — `apps/api/src/auth/jwks.provider.test.ts`, a
      local HTTP JWKS server counting requests: ten verifications within the
      TTL → `requests <= 1` (old code: 11). Second case: a `kid` in the Redis
      snapshot but absent from a fresh fetch is refused. Third: ten concurrent
      verifications with an expired snapshot → one refresh.
- [ ] **2. Implement** — `JwksProvider` keeps `snapshotAt` and one in-flight
      refresh promise; refresh only when missing or older than `cacheTtlSec`
      (clock injectable); `fetchImpl` used for the snapshot too; the Redis
      fallback only on a fetch failure, never on `JWKSNoMatchingKey`.
- [ ] **3. Failing integration** — `hierarchy.integration.test.ts` (or a new
      `staff-throttle` block): n+1 `POST /admin/auth/login` from
      `X-Forwarded-For: 203.0.113.7` → 429 `application/problem+json`; one from
      `203.0.113.8` → not 429. Same for `totp/verify`.
- [ ] **4. Implement** — `staffLogin` in `RATE_LIMIT_RULES`; the guard keys it
      on `request.ip` whatever principal is present; `@RateLimit("staffLogin")`
      on `login` and `totp/verify`.
- [ ] **5. Pass, break, restore; commit** — `P247-03: fetch JWKS once per lifetime and throttle staff sign-in per IP`.

### Review focus

- A person who is a member of A only, merged into one of B only, then disabled
  at A and reset at B — the B link must still be minted (§9.6 second tenant).
- Two local projects at one customer: the reset uses the earliest with a
  complete sender (see `Assumed:` under P247-01).
- DNS rebinding between the media check's resolution and `fetch`'s own: not
  closable without a pinned dispatcher; SMTP is pinned.
- Concurrent JWKS refresh for N+1 verifiers on a cold provider (§11.10).
- A staff login behind a shared NAT: the per-IP limit must stay above what an
  office of operators needs.
