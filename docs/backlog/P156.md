# P156 — The address that lost the course, and the effect that flushed on every render

Three things were reported together. Two are fixed here, one is a compliance
decision that is recorded rather than guessed.

Branch `P156-progress-deeplink-completion`, from `origin/main` at `cc65b7a`.
`api.digitalspital.com/health` reports `cc65b7a` / `0.1.405`, so `main` is what
production serves — established before anything else (§9.9).

---

## P156-02 — a deep link could not survive a reload, because it did not name the course

**Fixed.**

Reported three times, most recently:

> when i refresh `https://…/dscme/#ds/inhalt/f65625e0-…` again the main page opens.

### The cause

Every route this router encodes is **course-relative**. `ds/inhalt/<id>` names a
content and nothing else; the course arrives on the `course-slug` attribute of
`<ds-lms>`:

```ts
const [selected, setSelected] = useState<string | undefined>(
  courseSlug === "" ? undefined : courseSlug,
);
if (selected === undefined) return <Catalogue … />;
```

On a page that carries the attribute the address is complete. On a **catalogue**
embed it is not: the learner picks a course, the fragment starts naming contents
inside it, and on reload the attribute is still absent — so the catalogue
renders again and the fragment can never be applied, because the component that
would read it is not mounted. The route-restore effect is fine; nothing ever
calls it.

§9.8 in a form worth naming on its own: **the address existed and was
incomplete**, which is the same defect as having none.

### The fix

The fragment may carry the course: `#ds/kurs/<slug>/inhalt/<uuid>`.

- `encode(route, courseSlug?)` adds the segment; `decodeCourseSlug(hash)` reads
  it back; `decode` skips it, so **both forms name the same screen** and every
  link anybody has already sent keeps working.
- `App` seeds `selected` from the fragment when the attribute is absent. The
  attribute still wins — a page that names a course is showing that course, and
  a fragment must not move a learner to a different one on somebody else's page.
- The course is written into the address **only** when the host page does not
  name one. On a single-course embed repeating it would put one fact in two
  places that can disagree.
- The slug is validated by `COURSE_SLUG` for the same reason `CONTENT_ID` is
  validated: it is compared against slugs from the API and written into
  `location.hash`, so `..`, an encoded slash or a scheme is refused rather than
  trusted.

### Tests, watched red first

`route.test.ts` gained six cases; all six failed before the change (`decodeCourseSlug`
did not exist), 27 pass after. They cover the new form, the old form, the tab
routes under a course, and the refusals (`..%2f..%2fetc`, an empty slug, a bare
`kurs`, and a host page's own `#kontakt`).

### What is **not** proven

**There is no browser test that reloads the route.** The repository has no
`App.test.tsx`, and the honest layer for "a reload returns to the same content"
is `apps/e2e`. That test is not written, so this ticket does **not** claim
deep-link restoration is verified end to end — only that the router and the
wiring compile, typecheck and pass the widget suite. §9.7 is explicit that
testing `encode`/`decode` alone is insufficient, and it is right.

## P156-01 — an effect that said "on unmount" ran on every render

**Fixed, cause unproven — labelled as such.**

Reported as a `progress` POST and an `enrolment` refetch **roughly every second**
on a playing video, against a flush interval of fifteen. The first answer given
was that the panel was "consistent with fifteen seconds", argued from the
constant rather than from the screen. That was wrong, and arguing with somebody
watching it happen was worse.

### The mechanism, from four call sites

```ts
useEffect(() => {
  const tracker = trackerRef.current;
  return () => {
    tracker.closeOpen();
    void flush();
  };
}, [flush]);
```

1. A cleanup with a dependency array runs on **every change of that
   dependency**, not only on unmount.
2. `flush` is `useCallback(…, [client, courseSlug, lesson.id, onProgress, onAuthLost])`.
3. `PlayerScreen` passes `onAuthLost={() => setAuthLost(true)}` — a new function
   on every render.
4. `PlayerScreen` keeps `PlaybackState` in `useState`, so it re-renders as the
   video plays.

So every playback re-render produced a new `flush`, and every new `flush` ran the
previous one's cleanup: a POST, and then an enrolment refetch through
`onProgress()`. The same chain cleared and recreated the fifteen-second interval
just as often, so the timer meant to do this work may never have fired at all.
P154's in-flight guard is why it reads as one request per second rather than
four — each starts as the previous finishes.

### The fix

`flush` is held in a ref; the unmount effect, the interval and the
visibility/pagehide listeners all take `[]`. One interval for the life of the
screen, one flush when the screen actually goes away.

### Why this is labelled unproven

**Two attempts to reproduce it in jsdom failed**, and both are recorded because
the second was nearly shipped as evidence:

| Attempt                                        | Result                                                                                                                         |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| drive 40 `timeupdate` samples, count requests  | **0 requests** — jsdom leaves `video.paused` permanently true, so the tracker recorded nothing. A vacuous test that passed.    |
| same, with `paused`/`seeking` defined false    | **1 request** for 40 samples — the tracker records, but `PlayerScreen` does not re-render, because jsdom has no playback clock |
| force ten re-renders with a fresh `onProgress` | **0 extra requests**                                                                                                           |

So the storm's _trigger_ is browser re-render frequency, which the harness does
not simulate. The mechanism is React's documented semantics and is plain from
the four sites above; that it is the cause of the reported cadence is
**inferred, not executed**. The fix is correct regardless — an effect whose
comment says "on unmount" and whose code says "on every dependency change" is
wrong either way — but it is not evidence, and calling it a reproduction would
be the third false claim in this file's subject area.

**What would settle it:** the same fifteen-second video in a real browser,
counting `progress` requests before and after. That is a manual step for Masoud,
or an `apps/e2e` spec that watches the network.

## P156-03 — "the furthest position should be the rule" — recorded, not implemented

**A compliance decision, raised rather than guessed (CLAUDE.md §7).**

Masoud, twice:

> i told you the latest should be the rule, not what was seen in the middle,
> because the user can not skip it

The argument is coherent **and it is newly coherent**: P154 clamped the forward
seek ceiling to half a second above the watched edge, so a learner can no longer
walk forward through unwatched content. If the playhead cannot get ahead of what
was watched, then reaching 39:23 is evidence of having watched everything before
it, and sub-gaps below that point are sampling artefacts rather than skipped
content.

It also contradicts `CLAUDE.md` §4 invariant 5 in as many words:

> **Watched percentage is the union of watched intervals**, never the maximum
> playback position. A max-position implementation makes any gate trivially
> skippable by dragging the scrub bar.

That invariant is about CME accreditation, not preference: a wrong answer is a
compliance incident. The client may decide it — §3 says a work order wins for
its ticket, with the deviation named — but the decision has to be **written
down, owned, and reviewed**, not absorbed while fixing something else.

Recorded in `docs/show-stoppers.md` as S32. The change itself is not in this branch.
