# P145 — A designed-in stall is still a bug

The client, reading P144's own summary:

> "what do you mean 90-second stall?! is that how aws works? why are you
> creating bugs instead of real solutions?"

Both halves are right, and they are two separate mistakes.

---

## P145-01 — The 90-second budget was wrong about how S3 works

**Status:** done.

P144 gave `completeMultipart` a ninety-second deadline with this justification:

> "This is the one call where the bucket is doing real work while we wait — it
> assembles the parts server-side, and a 2 GB video is not instant."

**The API never carries a byte of the video.** The browser PUTs every part
directly to a presigned URL — `packages/sdk`'s `putPart`, an `XMLHttpRequest`
against the bucket. `CompleteMultipartUpload` sends a few hundred bytes of XML
naming the parts, and the store records a manifest; it does not concatenate
anything. It answers in well under a second.

So ninety seconds was not a safety margin. It was seventy-five extra seconds of
outage on the day the bucket is unreachable, bought with a belief about the
protocol that was simply false. It is now `CONTROL_DEADLINE_MS`, like every
other control call, and the test that guards it says why rather than asserting a
number.

`TRANSFER_DEADLINE_MS` is still right where the API genuinely streams —
`backup/store.ts` sends the dump itself — and that path holds no database
connection, which is the whole difference.

## P145-02 — And a bounded stall is still a stall

**Status:** done.

The deeper objection is the correct one. P144 ended by saying the worst case was
now "a bounded stall rather than an outage", and named the remaining problem
(P143-05) as something to do later. That is the wrong answer to _"make sure the
api does not hang"_: fifteen seconds of the whole platform being unavailable
because an object store is slow is not a fixed bug, it is a shorter one. It is
the same shape as "a pool of one would deadlock" — technically true, and the
reason nobody looked again (§9.10a).

### What actually causes it

`TenantTransactionInterceptor` opens the RLS transaction around the **whole**
request. That is the right default for the routes that read and write and do
nothing else, and it is what makes it impossible for a handler to forget
`runInTenant`.

It is the wrong default for a handler that calls **somebody else's server** in
the middle. Every upload route has the same shape:

    read some rows → talk to the object store → write one row

Under the ambient transaction, the connection is held for all three. So the
middle step — a network call to a bucket — occupies one of ten pooled
connections for as long as that bucket takes.

### The fix

`@NoAmbientTransaction()` on the five routes that call the object store. They
receive a `TenantRunner` instead of an open `Db`: a function that opens a
transaction, runs one database segment, and closes it. The connection is held
for the reads and for the write, and **released while the bucket is thinking**.

`RunnerUploadRepository` delegates to `UploadRepository` rather than
reimplementing it — two copies of a query under RLS is how one of them quietly
stops matching the policy.

It is opt-in per route, not a new default, because it gives something up: the
request is no longer one atomic transaction. On these routes nothing spans the
gap that atomicity protected — by the time `rememberAsset` runs the object is
already in the bucket, `rememberAsset` is idempotent on
`(customer_id, storage_key)` by design, and no invariant relates the mint that
was read to the row that is written. A route where that is not true keeps the
ambient transaction.

### The test, and what it does on the old code

The fixture had to change first. `startFakeS3` gains `stall()`, which **holds**
responses rather than refusing them — a bucket that answers 500 releases the
connection immediately and would prove nothing. That is §9.13's rule about
fixtures again, and the third time it has been the missing piece: a bucket that
always answers cannot find a caller that waits.

Then: twelve concurrent `uploads/complete` against a stalled bucket, and one
unrelated `GET /admin/media`.

|                                                  |                          |
| ------------------------------------------------ | ------------------------ |
| With `@NoAmbientTransaction()`                   | **200, in under 300 ms** |
| With the ambient transaction restored (sabotage) | **500, after 5 361 ms**  |

The 5.36 s is `connectionTimeoutMillis` from P141 — every connection held by a
stalled upload, the unrelated request queued behind them, and P141's deadline
being the only reason it answered at all rather than hanging. **That is the
outage of 01.09.2026, reproduced in five seconds by a test.**

Sabotage run and recorded; the suite is 575 green with the fix and 1 red without
it.

## What is still true

`ds_pg_pool_waiting` (P144-02) is what would have named this from outside, and
the watchdog thresholds on it.

Browser-side calls still have no deadline (P143-04), so a hung API is still a
spinner rather than a message. That costs a spinner, not a connection.

And the deploy is still manual: none of P140–P145 is on the server.
