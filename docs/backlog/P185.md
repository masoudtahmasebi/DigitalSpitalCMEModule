# P185 — The platform's own sender carries a certificate the customer cannot

**Raised by:** the client, 04.09.2026:

> if the customer has not set a email delivery smtp, our own admin smtp delivery
> would be used and we should make that clear in the customer page.

**Branch** `claude/education-platform-roadmap-3vgrqh`. Touches **certificates**,
so `needs-human-review` and no self-merge (CLAUDE.md §2).

---

## What happened before this ticket, which was correct and was not enough

`delivery.repository.ts` read the transport from `projects` alone. With no
`smtp_host`, `SmtpDeliveryChannel` answers

```
{ status: "permanent", reason: "no SMTP host configured" }
```

so the certificate is abandoned immediately rather than retried for a day. The
failure is classified correctly, the support panel says so, and nothing is
broken. What was missing is that the platform **has** a mail server — the one
that already sends invitations and password resets — and would not use it.

## P185-01 — one sender, chosen whole

`deliverySender` in `@ds/domain`: a project sends as itself when it has both a
host and a From address of its own; otherwise the host, port, credentials, From
address, From name **and TLS setting** are the platform's. Never a mix.

### Why not `COALESCE(project.x, platform.x)` per column

This is the decision the whole ticket turns on, and the obvious implementation
is the wrong one.

A `From:` of `fortbildung@medice.com` sent through **our** server fails SPF —
MEDICE's DNS does not authorise our host to send as them — and under a DMARC
policy of `quarantine` or `reject` the recipient's server files it as spam or
refuses it. That happens at the far end, so the SMTP transaction we see
**succeeds**: `delivered` on every row, and no physician receives anything. It
is the failure shape CLAUDE.md keeps naming, the one that looks exactly like
success.

A per-column fallback creates it the moment somebody fills in a From address and
leaves the host blank — the likeliest half-configuration there is. So the
identity moves whole, and a customer who wants their own address on the envelope
configures their own server, which is also the only way that address can be
authorised to carry it.

Asserted at both levels, and each watched red:

| Sabotage                                        | What went red                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------ |
| `host: row.smtpHost ?? row.platformSmtpHost`    | `never sends the customer's address through the platform's server` |
| `secure: null` for the platform                 | `carries the platform sender's TLS setting`                        |
| a platform host the console cannot set          | 3 integration cases                                                |
| the console sentence replaced by the old intro  | 3 `Organisation.test.tsx` cases                                    |
| `setPlatformSender` without the `canSend` guard | `promises nothing from an address whose sender is incomplete`      |

### The defect in the first attempt, caught before it was committed

The first version of this added six SMTP columns to `platform_settings` in a new
migration 0053 — beside the EIV settings, because that is where P180-01 put the
platform's other operational settings.

**`platform_smtp` has held exactly that value since P40-01**, is written by
Sicherheit → E-Mail-Versand der Plattform, and is what invitations and password
resets already send from. Two homes for one value is §9.10b, and the quiet
direction is the expensive one: an operator fills in the screen they can find,
the worker reads the columns nobody filled in, and a certificate is abandoned
with both screens looking configured.

The migration was deleted and the delivery repository joins `platform_smtp`.
Nothing new is stored by this ticket at all — the table, the endpoint and the
screen that writes it all predate it.

`inner join`, not `left`: the row is inserted by its own migration, so its
absence means a database older than this code rather than "unconfigured", and a
left join would turn that into a certificate abandoned for a missing sender —
§9.6's shape exactly.

### The TLS setting, which is the field that would have been dropped

`platform_smtp.secure` has been honoured by the reset mail since P40-01;
`projects` has no such column and the channel infers implicit TLS from port 465.
Carrying the chosen sender's transport but not its TLS flag would open a plain
socket to a host expecting TLS on connect, fail, and read as "the platform's
SMTP is broken" rather than as a field this path did not carry. So `secure` is
on `SenderTransport` — `null` meaning "nobody said" — and travels with the rest
of the identity.

### `usable` trims, because `canSend` trims

`canSend` in `apps/api/src/shared/mailer.ts` is the answer the Sicherheit screen
shows, and it trims. A stored `"  "` would otherwise be a host to the worker and
not a host to the screen: "Plattform-Versand ist nicht vollständig" beside a
worker sending through it.

## P185-02 — the customer page says which sender it will use

The client's actual sentence — _"we should make that clear in the customer
page"_ — is §9.4: the SMTP fields on Organisation decide something an operator
cannot otherwise see, because the fallback lives on a screen they may not think
to open.

Under the SMTP fieldset of every project, one of two sentences:

- **A platform sender exists** — it names the address certificates will come
  from, and says plainly that the customer's own address appears only if they
  also configure their own server, because a foreign address over our server is
  filed as spam by many recipients (SPF/DMARC). That last clause is the part
  nobody would guess, and it is said where somebody is deciding whether to fill
  the fields in.
- **It does not** — nothing is sent for this project, the certificate stays
  valid and downloadable in the portal, and the sentence **names the screen that
  fixes it**: Sicherheit → E-Mail-Versand der Plattform. Every operator can
  reach that screen (P22-02), so naming it is not §9.2.

The screen reads the same endpoint Sicherheit writes, and uses the server's own
`canSend` verdict rather than restating the rule in the browser: a From address
beside no host would otherwise be offered as a fallback the worker refuses.

## P185-03 — the correction on the other screen

`platformMailIntro` said:

> Für Teilnehmende gelten stattdessen die SMTP-Angaben des jeweiligen Projekts.

True until P185-01 and false after it. A comment is a claim (§11 rule 9), and a
locale string is a claim read by more people than any comment. Both it and
`platformMailIncomplete` now say that this sender is the fallback for
Teilnahmebescheinigungen and that changes here reach participants.

## Acceptance criteria

- [x] A project with no SMTP host sends its certificates through the platform's
      sender, with the platform's From address.
- [x] A project with its own server is untouched.
- [x] The customer's From address never travels over the platform's server.
- [x] The platform's TLS setting travels with its transport.
- [x] Neither configured behaves exactly as before — an empty host, which the
      SMTP channel answers permanently.
- [x] The Organisation screen names the sender each project will use, including
      the SPF/DMARC consequence and, where there is none, the screen that fixes
      it.
- [x] No second home for the sender: `platform_smtp` only, no migration.
- [x] Every assertion watched red before it was green.

## Not done, and deliberately

- **No test-send button for certificates.** Sicherheit already has one for the
  platform sender (`platformMailTest`), and it exercises the same row this path
  now reads. A second button would be a second answer to "does this work".
- **No per-project override of the platform sender's From name.** That is the
  mixed identity this ticket exists to refuse.
