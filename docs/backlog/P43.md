# P43 · Three seed failures, one cause: the host is not the repository

> as mentioned this should not be image based, but if the image exists it
> should use it
>
> `Seeding the MEDICE course failed: duplicate key value violates unique
constraint "customers_slug_key"` — since i created medice already myself
>
> the seeder should be also for ds: `Seeding the DS tenant failed: new row for
relation "projects" violates check constraint "projects_identity_provider_check"`
>
> [the deploy] failed: `EIV_VNR_PASSWORD is set in …/config.env, where nothing
reads it`
>
> why is everything so hard with implementation and i have to repeat everything
> multiple times?

The last line is the ticket. Four symptoms, and **the answer to the fourth
explains the third**: the deploy has never succeeded on that host, so the
database is behind the code, so a seed writing a value that has been legal since
migration `0030` is refused by a constraint written in `0019`. The report was
about a database eleven migrations old and read as a broken seed.

That is CLAUDE.md §9.9 for the third time — the repository's state is not the
installation's state — and §9.12's first question, _which build and which
data?_, would have got there before any code was read. It was not asked, which
is the reason this had to be reported twice.

The other two are real defects in this repository, both derivable from source,
both the same shape: **a mechanism that was correct about the case it was
written for and silent about the case it met.**

---

## P43-01 · A seed must not collide with a tenant somebody already made — **done**

- **Estimate:** 2 h · **Review gate: none**

Every `INSERT` in `packages/seed` says `ON CONFLICT (id) DO UPDATE`, and the ids
are fixed constants — chosen because `customers`' RLS policy checks
`id = app.customer_id`, so the id has to be known before the row exists. That
makes `id` the one unique key the collision can never happen on. `slug` is
unique too, and an operator who creates "medice" in the console owns that slug
under a _random_ id. The clause named the key that never fires, and the seed
died on its first write.

The seed was idempotent in every respect except the one that decides whether it
is idempotent at all.

### Adopt, do not refuse

`resolveCustomerId` (`packages/seed/src/lib.ts`) looks the slug up before
entering the tenant and uses whatever id holds it. Refusing would have been
correct and useless — CLAUDE.md §9.10 — because the remedy would be _delete your
tenant so the seed can create the same tenant_.

The lookup is deliberately cross-tenant, which is precisely what RLS hides from
`ds_migrator`: on the bare connection it matches zero rows and "nobody has this
slug" is indistinguishable from "you cannot see who does" (§9.6). It runs as
`ds_customer_registry` under `SET LOCAL`, inside a savepoint so a database
predating migration `0021` degrades to the fixed id rather than aborting.

Tested by effect in `seed-default.integration.test.ts`: a customer is created
with a random id the way the console would, the seed runs, and the course has to
land under **that** id — a test that fails on the old code at the first `await`.

## P43-02 · Refuse to seed a database older than the image — **done**

- **Estimate:** 3 h · **Review gate: none**

`deploy.sh` is the only thing that runs migrations. The seeds and the erasure
tool are separate entrypoints in the same image, launched by hand, and nothing
connected the two — so an image newer than the last successful deploy wrote to a
schema that predates it and failed deep inside a statement, as a constraint
name.

`pendingMigrations` (`@ds/migrator`) is the read-only half of `runMigrations`;
`assertSchemaCurrent` (`apps/api/src/schema-freshness.ts`) calls it before the
first write of all three seeds and refuses with the gap and the command that
closes it. A fresh database — no `schema_migrations` table at all — answers
"everything is pending" rather than throwing, because that error would land in
exactly the position the helpful one was meant to occupy.

**Not** migrating on the way past: that would be a second migration path, run
without the backup `deploy.sh` takes first. One command that both seeds and
migrates is a command whose blast radius nobody can state.

## P43-03 · `./dsc` uses the image that exists; it does not build one — **done**

- **Estimate:** 2 h · **Review gate: none**

`docker compose run` builds a service whose image is absent, and the tag is
`${DS_COMMIT}` — the commit the _clone_ is on. So `git pull` was enough to make
`./dsc seed medice` spend forty seconds compiling the whole API, from the
wrapper whose own header says it deliberately does not deploy, and then run a
seed from a different build than the API beside it. A seed writes rows the
running API reads; the schema it expects has to be the running one.

`ds_resolve_image_tag` (`infra/deploy/images.sh`) prefers the checkout's image,
falls back to what is actually running — printing the discrepancy rather than
hiding it — and never builds. `pull_policy: never` on the five locally built
services removes the `pull access denied for ds-education/api` warning that
preceded every one of these runs: there is no registry (ADR-0013), so the pull
could only ever fail, and a warning naming a missing repository and a login step
in front of an operator reading real output is noise that teaches skimming.

`images.test.sh` stubs `docker` on `PATH` — which is what makes the three states
(checkout's image present, only an older one running, nothing at all) reachable
from a test runner. Confirmed by breaking the resolver twice and watching it go
red (§9.1).

## P43-04 · The refusals say what to type — **done**

- **Estimate:** 0.5 h · **Review gate: none**

`deploy.sh` refuses when `EIV_VNR_PASSWORD` is set in `config.env`, and the
refusal is right: the VNR and its password belong to the _course_, encrypted at
rest and set on the Fortbildung's settings screen, so a value in `config.env` is
a credential at rest for nothing plus an operator who believes the worker is
configured when every completion will be abandoned `missing_vnr_password`.

It fires in an unattended GitHub Actions deploy where the message is the whole
interface, and it named the problem and the screen without naming the edit
(§9.4). It now prints the `sed` line, and says the rotation is a consequence of
the value having been on disk rather than an optional extra.

The refusal itself is unchanged. CLAUDE.md §3: the security baseline is costed
in and is not reducible.

## P43-05 · The shell tests run where the work happens — **done**

- **Estimate:** 0.5 h · **Review gate: none**

`domains.test.sh`, `secrets.test.sh` and `deploy-vars.test.sh` ran only in CI.
That is §9.11's own example of the thing it warns about — a check that runs only
in CI is a check the person writing the code does not run — sitting unfixed in
the repository that wrote it down. `pnpm check:shell` runs all of them, and
`pnpm verify` runs that.

---

## What was not done, and why

**Deploying.** Every symptom above except P43-01 is downstream of a host running
older code, and closing that gap is a deploy of work spanning auth, EIV and
certificates — which CLAUDE.md §2 puts behind a human review gate. The branch is
pushed; the merge and the deploy are the client's call, not something to take
while nobody is looking.
