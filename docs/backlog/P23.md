# P23 · Uploads, and everything that has to be true for them to be safe

"How can I upload a video?!" — reported from the live console, and the honest
answer at the time was **you cannot**. The course editor accepted a URL and
nothing else. There was no upload path anywhere in the platform.

The request that followed named four things, and they belong together rather
than as one feature and three chores:

> we have to make it possible to upload directly to s3 from here, and the s3 is
> divided by each customer and only customers can read their own files, and we
> should have backup mechanism and logs in place for both s3 and also our own db

Uploading is the easy part. What makes it safe is that a bucket has **no
row-level security**: the isolation guarantee Postgres gives us for free has to
be built by hand for object storage, and a guarantee built by hand is one you
have to be able to audit and restore.

---

## P23-01 · Direct-to-S3 upload, with the key derived from the session — **done**

- **Estimate:** 6 h · **Review gate: human — tenant isolation**

Two calls, and the second one is not optional:

```
POST /admin/courses/{slug}/uploads            → a signed PUT, and a key
      (the browser uploads straight to the bucket)
POST /admin/courses/{slug}/uploads/complete   → the reference to store
```

### Why the bytes do not come through the API

A 700 MB lecture through a Node process is a request that outlives every proxy
timeout in the path, a memory profile that depends on how many authors upload at
once, and a body-size limit somebody has to raise everywhere from Caddy down.
The API's part is a few hundred bytes of JSON.

### What the client is allowed to decide: almost nothing

It names a purpose, a type and a size. It never names a key, a prefix, a bucket
or a filename — those are derived from the validated session and from a course
row RLS already agreed the caller can see. There is no request shape that writes
into another customer's space, which is the point: `keyBelongsToCustomer` is the
whole isolation guarantee for object storage, and it is worth nothing if a
client can choose the key.

The filename is generated (`uploadObjectName`) rather than sanitised. The name a
file picker reports is attacker-influenced, may carry a working title or a
patient name nobody meant to publish, and would have to be forced into
`SAFE_SEGMENT` anyway. Generating it removes the class.

### What the signature carries, and what it cannot

`Content-Type` **and** `Content-Length` are signed headers, so the bucket refuses
a body of a different length or type — and a browser computes `Content-Length`
from the body and forbids script from setting it, which is what makes signing it
a real constraint. That is the size limit's actual enforcement.

What a signature cannot carry is what the bytes _are_. The API never sees them,
so there is no `sniffFontFormat` equivalent here. Three things carry that weight
instead, and they are written down in `packages/domain/src/upload.ts` rather than
left implicit:

1. the stored content type is one from the closed list, because it is signed;
2. the bucket is a **different origin** from the app, so markup that got in has
   no session, no cookie and no DOM to reach;
3. the object is verified afterwards and **deleted** when it disagrees with what
   was approved.

### Acceptance criteria

- [x] `planUpload` — closed per-purpose type list and size ceiling, pure, exhaustively tested
- [x] `presignPut` / `presignHead` / `presignDelete` sharing one canonical-request implementation
- [x] The key is `<customerId>/courses/<courseId>/<generated>`, never client-supplied
- [x] `complete` HEADs the object, compares against the recorded approval, deletes a mismatch
- [x] Media fields accept `s3://` references; a reference outside the caller's prefix is a 422
- [x] Contract first: `contracts/openapi.yaml`, then the SDK, then the console
- [x] A round-trip test against a bucket that verifies the signature the way Hetzner does

### Deliberately not done

**Multipart / resumable upload.** A failed PUT starts again from zero, so the
video ceiling is 2 GiB — where a single PUT stops being sensible, not where
storage stops. A 25-minute lecture weighs 300–800 MB and that is comfortable;
much beyond it is not, and the number lives in one place so it moves with the
feature that fixes it. Raised as its own item rather than smuggled in here.

**Transcoding.** `CLAUDE.md` §3 lists media transcoding as deferred. Uploads
accept files that are already web-ready and say so.

## P23-02 · The storage audit log — **done**

- **Estimate:** 3 h · **Review gate: human — tenant isolation**

Every mint, store, refusal, read and deletion, append-only, RLS-scoped.

### Why object storage needs its own log

Postgres refuses a cross-tenant read itself; the attempt is a row nobody got. A
bucket has none of that. When the guarantee lives in application code and not in
the store, you have to be able to audit it — and the events worth auditing are
the **refusals**, which is exactly what an implementation that logged successes
only would throw away.

### The one design decision worth reading

The recorder writes on **its own connection, in its own transaction**, not the
request's. Every refusal here is the handler throwing, and
`TenantTransactionInterceptor` rolls the request's transaction back when it does
— so an audit row written on that connection would be rolled back with it. The
log would faithfully record every upload that worked and nothing else.

It also matches the facts: these events describe something that happened in a
bucket, and a bucket does not participate in a Postgres transaction.

Verified by probe — moving the recorder onto the request connection fails three
integration tests, and only those three.

### The log is also load-bearing

`complete` reads the approved size and type out of the recorded `mint`. Taking
them from the request body would let a client choose both sides of the
comparison and make verification decorative. The row is append-only in the
database, so the application cannot revise its own record of what it agreed to.

### Acceptance criteria

- [x] `storage_audit_log`, append-only enforced by `REVOKE` with an in-migration assertion
- [x] RLS with the post-0014 `nullif` policy shape
- [x] No personal data: two UUIDs, a generated filename, and a reason from a closed set
- [x] Refusals survive the request rolling back
- [x] Recorded in `docs/gdpr.md` with a retention period

## P23-03 · Backups for Postgres and for object storage — **done**

- **Estimate:** 6 h

Three jobs, and the third is the one that makes the other two mean anything.

    backup database   pg_dump | AES-256-GCM | upload | confirm | prune
    backup objects    server-side copy of course media into a second bucket
    backup verify     is there a copy newer than 26 hours? — exit 1 if not

### Why `verify` is a separate unit

A timer that stopped firing three weeks ago is indistinguishable from one that
is working. Nothing inside the backup job can report a run that never happened,
so the freshness check runs on its own schedule, twice a day, and its non-zero
exit is what pages.

### Three things the tests found

**`openssl enc` cannot decrypt AES-GCM.** The restore drill was written to use
`openssl enc -d -aes-256-gcm`, which is what one would naturally put in a
runbook and which refuses outright — _"AEAD ciphers not supported"_. The
authentication tag is the reason GCM was chosen, so the answer was a different
tool, not a weaker cipher. The runbook now carries a Node snippet, and the
integration test **executes that snippet** rather than quoting it.

**A signed header that is not sent is a 403.** `presignCopy` signed
`x-amz-copy-source` and returned only a URL, so the request never carried the
header the signature covered. It now returns the headers with the URL.

**S3 answers a failed copy with 200 and an error document.** The single most
notorious trap in the API: a caller checking `response.ok` records a backup that
does not exist. The fake bucket reproduces it, and the first version of the test
for it was passing on the 403 above rather than on the error document — so the
test now asserts the status too.

### Acceptance criteria

- [x] Encrypted before it leaves the host, with a key that is **not** `SECRETS_KMS_KEY`
- [x] Grandfather-father-son retention, pure and exhaustively tested; an unrecognised name is never deleted
- [x] Pruning happens only after the new copy is confirmed present in the bucket
- [x] Object mirroring by server-side copy, incremental, into a second bucket
- [x] A restore drill in CI: real `pg_dump`, real decrypt with the runbook's own snippet, real `pg_restore`, and the row is found
- [x] A tampered dump is refused rather than restored
- [x] `docs/runbook-backup.md`, including what this does **not** protect against

### Deliberately not done

**Point-in-time recovery.** The granularity is the nightly dump, so up to 24
hours of participation records can be lost. WAL archiving would fix it and has a
real cost; it is the client's decision, and it is stated in the runbook rather
than assumed away.

## P23-04 · The console's upload UI — **done**

- **Estimate:** 4 h

A file picker in the course editor with real progress, because a lecture takes
minutes and a spinner with no percentage in front of that is indistinguishable
from a hang — and the reasonable response to a hang is to reload, which discards
everything transferred so far.

- [x] Video renditions, poster, captions and the Mediathek file
- [x] `XMLHttpRequest`, because `fetch` cannot report upload progress
- [x] A stored reference renders as a chip, not as an editable key
- [x] Nothing is sent to the bucket but the ticket's own headers — no cookie, no token
- [x] Component tests for every state, and a browser pass on the built bundle

### A finding on the way

Media uploads have their own rate-limit bucket now. They shared `adminUpload`'s
20/minute with the font and certificate-image routes, whose limit is about
writing bytes into the database through this process. Seeding a fifteen-lesson
course is dozens of files and two requests each — so the shared limit produced a
429 partway through exactly the task the feature exists for.
