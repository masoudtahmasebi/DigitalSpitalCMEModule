# P191 — A score is not a pass

**Raised by:** the client, 04.09.2026, with a screenshot:

> I have created a new course with one long video and questionnaire. I have
> given the pass percentage to 85%. I have finished the questionnaire and I have
> scored 60%. […] I cannot retake the exam again, although I didn't clear the
> exam. […] You could see in the same screenshot it says bestehen 85%, and the
> user passed with 60, which should not be the case, where is this coming from?
> are there similar issues? is this because again you are not reading details
> from where you should and you are checking the value from somewhere else?

**Yes — that is exactly what it was.** Touches **assessment**, so
`needs-human-review` and no self-merge.

---

## What the screen showed

One page contradicting itself:

| Panel             | Value                                                                                                           |
| ----------------- | --------------------------------------------------------------------------------------------------------------- |
| **Bestehen**      | 85 % · Mind. 5 von 5 richtig                                                                                    |
| Three lines below | _"Sie haben diese Lernerfolgskontrolle bereits mit **60 %** bestanden. Sie kann nicht erneut abgelegt werden."_ |

And no way back into the exam — on a course whose API would have accepted
another attempt, because `POST attempts` refuses only a score that actually
cleared the threshold.

## The cause: two readers of one rule

`PlayerScreen.tsx` compared:

```ts
const quizScore = recordedQuizScore(state, quiz.id);
const quizPassed = quizScore !== undefined && quizScore >= state.passThresholdPercent;
```

`App.tsx`, mounting the exam screen, did not:

```tsx
passedScorePercent={recordedQuizScore(state, screen.contentId)}
```

`recordedQuizScore` returns `progress.scorePercent` — **the best score, graded
or not**. The prop it fed is named `passedScorePercent`, and `QuizScreen` treats
any value in it as a pass: it renders `de.quiz.alreadyPassed(score)` and
replaces the start button with "the way on".

So the _presence_ of a score was the pass. Score 1 % on a 90 % course and the
exam closed behind you.

CLAUDE.md §4 invariant 6 — one rule, one reader — and the quiet half of §9.10b:
of the two readers, the one that skipped the comparison is the one a learner
meets. The accessor was never wrong; it says what it returns. **The prop name
claimed more than the value carried**, and a name that overclaims is how the two
came apart.

## P191-01 — the comparison has one home

`passedQuizScore(state, contentId)` in `player.ts`: the score, only if it
reaches `state.passThresholdPercent`. Both screens call it. `recordedQuizScore`
is **deleted** rather than kept beside it — an honest accessor next to the safe
one is an invitation to reach for it again (§9.3).

`>=`, not `>`: an 85 on a course set to 85 passes. Asserted, because a course
that refused its own threshold is the off-by-one nobody reports — it looks like
a strict examiner.

Zero is a score, not an absence: `score === undefined`, never `!score`. On a
course with a threshold of 0 the difference is a learner told they passed and a
learner told nothing at all.

### Why the threshold and not the stored `status`

Both were available — `upsertQuizProgress` writes `status = "completed"` exactly
when the attempt passed. The threshold is used because
`state.passThresholdPercent` is **the course's live value** since P174-01, so
this agrees with the API's own refusal by construction: `assessment.service`
compares against `enrolment.passThresholdPercent`, which `findEnrolment` reads
from `courses`. Screen and server now derive one verdict from one number.

### The stale comment this turned up

`assessment.service.ts` claimed:

> `passThresholdPercent` is the enrolment's snapshot, so re-tightening a
> published course cannot retroactively reopen an exam somebody has already
> passed.

False since P174-01, which moved the three gating thresholds onto the course.
The consequence is the **reverse** of what it claimed, and it is deliberate:
re-tightening a course does reopen an exam cleared under the old threshold,
because the client's decision was that the course wins for work still in
progress. What it cannot do is take away something finished. Corrected in place
(§11 rule 9).

## The sweep — "are there similar issues?"

The shape: **a raw figure treated as a verdict**. Every reader, listed.

| Reader                               | Verdict?                                                                        |
| ------------------------------------ | ------------------------------------------------------------------------------- |
| `player.ts` `passedQuizScore`        | the only place a score becomes a pass                                           |
| `QuizScreen.tsx` ×3 (the result bar) | renders `attempt.scorePercent` — the attempt's own number, a fact not a verdict |
| `PlayerScreen.tsx`                   | comment only, after this ticket                                                 |

`watchedPercent` **never had this defect**, and the reason is worth writing
down: the widget never compares it to `requiredWatchPercent` anywhere. It
renders the number and reads `gate: "available" | "locked"` — the server's
verdict, sent as a field. The watch gate could not drift because the browser was
never asked to decide it.

That asymmetry is the finding under the finding: the quiz pass was the one
compliance verdict the widget derived for itself, and it is the one that drifted.

## Why no test caught it

`player.test.ts` covers the rule and would have stayed green through all of
this — the rule was not wrong, it was **not called**. §9.7 exactly: a pure
function tested in isolation proves nothing about the screen unless something
names the caller.

So the new cases drive `App` with a course at 85 % and a recorded 60 %, and
assert what a physician sees. Both watched red against the restored defect:

```
× does not tell the learner they passed it
× still offers the exam
```

The first asserts the exam screen is actually mounted before asserting the
sentence is absent — without that it would pass on every other screen in the
product, which is §9.1's second form.

## Acceptance criteria

- [x] A score below the course's threshold does not read as a pass.
- [x] The exam stays open to a learner who has not cleared it.
- [x] A score at the threshold passes; a score one below does not.
- [x] Zero is treated as a score.
- [x] One reader of the rule; the unsafe accessor deleted.
- [x] Screen and API derive the verdict from the same live value.
- [x] Wiring tested, not just the rule, and watched red.
- [x] The class swept and the full result listed.

## Not done

- **The prop keeps its name.** `passedScorePercent` is now accurate — it is
  fed a passed score — so renaming it would be churn. What made it dangerous
  was that its input did not match it, and that is fixed at the source.
