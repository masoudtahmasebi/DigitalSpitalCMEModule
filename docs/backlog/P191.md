# P191 — An audit for P190's shape, everywhere else

**Raised by:** the client, 04.09.2026, immediately after P190:

> can you please check if any similar issue exist anywhere in the application?
> not just with score, with other logical statement, logically wrong
> comparisons and not correct flow?

---

## What was searched for

P190 was not "a bug in the quiz". Its shape was:

1. a raw figure treated as a verdict (**presence implies truth**);
2. **two readers of one rule**, one of which skipped the comparison;
3. a **name that claimed more than its value** carried;
4. a compliance verdict **derived in the browser** that the server also derives.

Each became a search, plus the classic arithmetic ones — truthiness that
swallows zero, `>` where `>=` was meant, and comparisons between different
units.

## The result, graded honestly

**No second live defect was found.** Three latent drift risks were, one is
fixed, and one check was extended so this class is findable by machine next
time. Everything below is evidence, not impression.

### Clean — searched, nothing there

| Class                                            | Result                                                                                          |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Truthiness swallowing zero                       | 5 hits, all on booleans or `NaN`-guards (`charCodeAt() \|\| 0`). None on a meaningful zero.     |
| Unit mismatches (sec vs ms, percent vs fraction) | none                                                                                            |
| Verdict names fed by presence checks             | 4 hits; 3 are `has*` names checking presence, which is what they say. The 4th was mine (below). |
| Other client-derived gates in the widget         | none — every other screen reads `gate: "available" \| "locked"` from the server                 |
| Auth and session boundaries                      | `>=` for expiry, `<` for lockout, consistent, single-reader                                     |
| `requiredWatchPercent`, `maxQuizAttempts`        | one reader each                                                                                 |

The watch gate is worth naming: it **never had P190's defect**, and the reason
is structural. The widget never compares `watchedPercent` to
`requiredWatchPercent` — it renders the number and reads the server's `gate`.
It could not drift because the browser was never asked to decide it. The quiz
pass was the one compliance verdict the widget derived for itself, and it is the
one that drifted.

### P191-01 — a magic `3` against a budget of `4` — **fixed**

`admin.service.ts` flagged a queued Punktemeldung as `needs_attention` at
`attemptCount >= 3`. The budget is `MAX_ATTEMPTS = 4` in `@ds/domain`, and
nothing tied them together.

It happened to mean "one retry left", which is what an early warning should
mean. It would have gone on saying `3` if the budget moved: at 3 it fires only
once the queue has given up, duplicating `attempts_exhausted`; at 10 it fires on
almost every row. Now `MAX_ATTEMPTS - 1` — same behaviour today, one home for
the number (§9.10b).

### P191-02 — three domain verdicts nobody reads — **reported, not changed**

`EivDeadlines` computes `isOverdue`, `shouldStopRetrying` and `needsAlert` on
every call. **Nothing outside `packages/domain` reads any of them** — verified
by grep across the repository.

They are not a missing feature. Each duplicates a decision something else
already makes:

| Field                | What actually decides it                    |
| -------------------- | ------------------------------------------- |
| `needsAlert`         | `dueAlerts`, in `eiv-alert.service`'s sweep |
| `shouldStopRetrying` | `planEivAttempt`, in the worker             |
| `isOverdue`          | `admin.service`'s own `reportDueAt <= now`  |

So §4 invariant 8 **is** implemented — the alarm exists, fires a webhook, and
audits itself. What these are is a **second answer waiting for somebody to reach
for it**, which is precisely what P190 shipped as a defect.

And they already disagree at the boundary. `resolvePhase` treats the deadline
as inclusive — `now <= reportDueAt` is still `reporting_open`. `admin.service`
treats it as exclusive — `reportDueAt <= now` is already `needs_attention`. One
instant wide, no consequence today, and two rules about one deadline.

**Not changed**, because both directions are decisions rather than repairs:
deleting them removes options somebody chose to compute, and wiring them up
changes what the console flags. It needs a decision, not a guess (§7).

Same list, same grading, smaller stakes: `EivAttemptPlan.alertAdmin` (the
domain marks every terminal outcome as needing a human; the worker writes an
audit row and the console shows it, but nothing reads the flag),
`PunktemeldungOutcome.participantMayAct` (the API forwards `kind` and `actor`
and drops this one, directly under a comment about not having a second opinion
about the rule), and `PasswordContext.knownBreached` — an optional input **no
caller ever supplies**, so `too_common` is unreachable and breached-password
rejection is inert. That last one is auth, and it is the one most worth a
decision.

### P191-03 — the check that should have found this could not — **fixed**

`scripts/unused-rules.mjs` exists for exactly this class: _"exported,
exhaustively unit-tested, called from nowhere"_. It reported none of the above,
and it was right to: it scans the **names** `index.ts` re-exports. It cannot see
inside one, and every finding here is a **field of a returned verdict**.

A check that covers less than it appears to is §9.1's second form, so it now
also reports fields of publicly exported interfaces that nothing outside the
domain reads. Its first run found nine, including all three `EivDeadlines`
judgements.

Two limits, stated rather than discovered later:

- The filter is "the interface is re-exported from `index.ts`". Requiring the
  _type name_ to appear outside was tried first and finds nothing: nobody names
  `EivDeadlines`, because callers write `eivDeadlines(...).reportDueAt`.
- Fields shorter than five characters are skipped — `id`, `at`, `by` appear
  everywhere for unrelated reasons, and their absence is unprovable by a text
  scan.

### P191-04 — one in P190's own fix — **fixed**

`PlayerScreen` read `const quizScore = passedQuizScore(...)`. The value is a
_passed_ score and the name said `quizScore` — the same overclaiming-name trap
one layer along, introduced by the fix for it. Renamed `passedScore`.

## Acceptance criteria

- [x] Each of P190's four shapes searched across domain, API, widget and console.
- [x] The arithmetic classes searched: zero-swallowing truthiness, unit
      mismatches, boundary operators.
- [x] Every hit read in context rather than reported from a grep.
- [x] Findings graded: fixed, or reported with the decision named.
- [x] The check that missed this class extended, with its limits stated.

## Not done

- **The three `EivDeadlines` fields are left in place.** See P191-02.
- **No breach corpus is wired to `knownBreached`.** Supplying one is a feature
  with an I/O dependency and a cost; what this ticket does is record that the
  rule is currently inert, so nobody reads `checkPassword` and believes
  otherwise.
