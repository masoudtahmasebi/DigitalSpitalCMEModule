# P55 — What the QA pass through enrolment and gating found

Raised 11.08 by the QA agent's Section 4 (enrolment, sequential gating,
progress persistence). Eight of nine cases passed as built. The ninth is below.

---

## P55-01 · The first playback report had no wall-clock floor · 2 h

**Status: done.** Touches the watch gate — human review.

### What was wrong

`watch.ts` says it plainly in its own header: _"the load-bearing check is
`faster_than_wallclock`: without it, a client can post `[0, duration]` in a
single call and complete any video instantly."_

It did not apply to the first report on a video. The budget was:

```ts
existing === undefined ? content.durationSec : now - existing.updatedAt;
```

— the video's whole duration whenever no `content_progress` row existed yet, on
the reasoning that there was no earlier timestamp to measure from. There was
one: the learner enrolled at some point, and every other content they have
touched carries a timestamp too.

There is exactly one first report per video, so the effect was that **each video
in a course could be claimed whole, in one request**:

```
PUT  /courses/adhs-akademie-adult/enrolment                          200
POST …/contents/{video}/progress  {"segments":[{"startSec":0,"endSec":1524}]}
  → 200  accepted 1, rejected [], watchedPercent 11    ← 170 s of a jump, credited
```

Five requests would have satisfied a 100 % watch requirement on a five-module
course. Nobody had reported it because no real player does it — the widget
flushes every 15 seconds and reports what was actually played — but the gate
either holds against a scripted client or it is decoration, and a CME point
issued behind it would be indefensible.

**The union rule was never the problem** and is untouched: a scrub past the
start credits only the seconds sent, and the seek ceiling never rises above the
end of what was watched. What was missing was the other half — that the seconds
sent must fit in the time that has passed.

### What changed

The budget is now the elapsed time since the learner was last seen doing
anything **on this enrolment**: the newest `content_progress.updated_at`,
falling back to `enrolments.created_at` when they have touched nothing yet.

It grows exactly as fast as a person can watch, so nothing legitimate is
refused:

| Situation                                                 | Budget            |
| --------------------------------------------------------- | ----------------- |
| enrolled this second, claims the whole 25-minute chapter  | ~0 s → refused    |
| enrolled 20 minutes ago, reports a 10-minute chapter once | 20 min → accepted |
| watched chapter 1 a minute ago, claims chapter 2 whole    | 1 min → refused   |
| came back a week later                                    | a week → accepted |

A player that buffers a whole chapter and reports at the end still took the
chapter's length to get there, and that time is in the budget. The refusal is a
**200 with the segment in `rejected`**, not a 4xx: the request was well-formed,
and the answer tells the player what was credited so it can report again once
the time has passed.

### The tests

Three unit cases and three integration cases. Two of the three unit cases go red
on the old budget — verified — and the third is the guard in the other
direction: it fails if the budget is ever simply tightened to nothing, which is
the obvious wrong fix.

The change also went red across four integration suites, and that is worth
recording rather than hiding: **every playback fixture enrols and then watches
ten minutes of video in a few milliseconds**, which is precisely the shape the
rule refuses. The suites now move the clock, through one shared
`backdateLearnerClock` helper that moves both timestamps — the old local helper
moved only `content_progress.updated_at`, which after this change left every
first-report case with a budget of zero.

### Acceptance criteria

- [x] A whole video claimed on a fresh enrolment is refused, and nothing is
      stored — asserted separately, because a refusal reported but written
      anyway is the failure worth catching
- [x] A jump from 30 s to 200 s in the same second is refused, and the stored
      union stays at 0–30
- [x] A learner who enrolled 40 minutes ago can still report a 25-minute
      chapter in one call
- [x] The seek ceiling never rises on a refused segment
- [x] Verified red on the previous budget
- [x] `pnpm verify` green; 471 integration tests green
- [ ] **Human review** — this is the watch gate, and the watch gate is what a
      CME point is issued against.

### Still open from P50

**The 15-second flush interval is not enforced.** A client may still report in
one large chunk per interval-worth of real time, and nothing requires reports to
be evenly spaced. Closing that would mean the server holding a per-session
schedule, which buys little: the total is already bounded by elapsed time,
which is the property the accreditation cares about.

## What Section 4 confirmed as already correct

Recorded because "it worked" is evidence too, and these are the cases a later
change must not break:

- **Enrolment is idempotent.** `PUT /courses/{slug}/enrolment` twice returns the
  same `enrolmentId` and leaves one row. (There is no `POST …/enroll`; the
  contract is a PUT, which is what makes it idempotent by construction.)
- **The rollup tree** comes with the enrolment: modules → chapters → contents,
  each with a `gate` and a `progress` node, all `not_started` on a fresh
  enrolment. There is no separate `/progress` endpoint — one rollup path
  (CLAUDE.md §4 invariant 6).
- **The sequential gate is server-side.** Posting progress for chapter 2 while
  chapter 1 is untouched answers **403**, and so does opening its lesson.
- **Completing chapter 1 opens chapter 2** on the next read, with no client-side
  state involved.
- **Resume survives a new session.** A new token for the same subject reads back
  `lastPositionSec: 142`, with `resumeAtSec: 120` — a deliberate rewind to the
  last whole minute, so a physician re-establishes context rather than landing
  mid-sentence.
- **Module rollup** advances one module at a time and the course-level counts
  agree with it; the last module stays `in_progress` at 100 % watched because it
  carries the Lernerfolgskontrolle.
- **`watched_percent` is union ÷ duration**, not furthest position ÷ duration.
  QA's formula was the second one; the first is CLAUDE.md §4 invariant 5 and the
  difference is the whole anti-skip design.
