### P10-01 · Security review

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 6 · **Depends on:** P9-07
- **Review gate:** human — auth

**Context**
The system holds named physicians' participation records and their EFN — personal
data processed for an accreditation purpose. M4's definition of done requires this
review to be signed off.

**Scope**
- Review the auth path end to end: token validation, role resolution, tenant
  context, super-admin "act as".
- Verify no secret is reachable through any endpoint at any role: SMTP
  credentials, VNR passwords, tokens.
- Verify personal data — EFN, free-text evaluation responses, names — is absent
  from logs and error payloads.
- Dependency audit; security headers; CORS restricted to the MEDICE origins.

**Acceptance criteria**
- [ ] No endpoint returns a secret at any role, verified by an enumerating test
- [ ] No EFN appears in any log at any log level, verified by test
- [ ] CORS allows only configured origins; a wildcard is impossible to configure
- [ ] Security headers present; error responses carry no stack trace, internal
      hostname or identifier
- [ ] Findings are recorded with a disposition — fixed, accepted with a reason, or
      deferred with a ticket. Signed off in writing.

### P10-02 · Tenant isolation test suite

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 6 · **Depends on:** P10-01
- **Review gate:** human — tenant isolation
- **Verifies:** ADR-0002

**Context**
This is the suite ADR-0002 exists to make possible. Isolation is claimed as a
property of the database, so it must be demonstrated against the database rather
than argued from code review.

**Scope**
- Attempt cross-tenant reads and writes against every tenant-scoped table.
- Prove `ds_app` cannot bypass RLS.
- Prove the pooled-connection leak is impossible: interleaved requests for two
  customers over a single pooled connection.
- Prove super admin is not a bypass — it acts as one customer at a time.

**Acceptance criteria**
- [ ] Every tenant-scoped table is covered; a newly added table without a policy
      fails the suite
- [ ] Cross-tenant writes are rejected by the database `with check`, not by
      application code — verified by disabling the application filter in the test
- [ ] Interleaved two-tenant requests over one connection show no leakage
- [ ] `ds_app` is confirmed not `BYPASSRLS` and not table owner in the deployed
      environment, not just locally

### P10-03 · Rate limiting

- **jira:** _(unassigned)_
- **Estimate:** 1 h · **Week:** 6 · **Depends on:** P10-02
- **Review gate:** none

**Scope**
- Rate limits on auth, progress heartbeats, quiz submission and certificate
  download.
- Limits per user and per IP, backed by Redis so they hold across instances.

**Acceptance criteria**
- [ ] Limits hold across multiple API instances, not per process
- [ ] Progress heartbeats from a legitimate learner are never throttled during
      normal playback
- [ ] Quiz submission limits cannot be used to lock a learner out of a legitimate
      retry
- [ ] Exceeded limits return 429 with a retry hint, not a generic error

### P10-04 · Hetzner provisioning and CI deploy

- **jira:** _(unassigned)_
- **Estimate:** 2.5 h · **Week:** 6 · **Depends on:** P10-03
- **Review gate:** none
- **Blocked by:** Hetzner account and DNS ownership (roadmap §12 item 6)

**Context**
Hetzner Cloud in Germany was chosen for GDPR posture (roadmap §2). Containerised
and portable — no dependency on a Hetzner-specific managed service, so the choice
stays reversible.

**Scope**
- Provision the environment: API, Postgres, Redis, TLS, DNS.
- CI deploy from the default branch; migrations run as `ds_migrator`, application
  as `ds_app`.
- Secrets from the environment, never from the image.

**Acceptance criteria**
- [ ] All data at rest is in Germany
- [ ] Migrations run as `ds_migrator` and the application as `ds_app`, enforced by
      the deploy pipeline rather than by convention
- [ ] No secret is baked into an image or present in the repository
- [ ] TLS is valid and enforced; HTTP redirects to HTTPS
- [ ] A deploy is repeatable and a rollback is possible
- [ ] The stack could be moved to another provider without code changes

### P10-05 · Backups and restore drill

- **jira:** _(unassigned)_
- **Estimate:** 1 h · **Week:** 6 · **Depends on:** P10-04
- **Review gate:** none

**Context**
A backup that has never been restored is a hypothesis. The CME participation
record is the one dataset here that cannot be reconstructed from any other source.

**Scope**
- Automated encrypted Postgres backups with a defined retention period.
- A restore drill performed and documented.

**Acceptance criteria**
- [ ] Backups run automatically and are encrypted at rest
- [ ] A restore into a clean environment has actually been performed, with the
      elapsed time recorded in the runbook
- [ ] The restored database enforces RLS identically — verified by running P10-02
      against it
- [ ] Retention satisfies the documented GDPR retention decision

### P10-06 · Observability and alerting

- **jira:** _(unassigned)_
- **Estimate:** 1 h · **Week:** 6 · **Depends on:** P10-05
- **Review gate:** none

**Context**
The failure this must catch is the quiet one from ADR-0005: EIV submissions
accumulating unsent while everything else looks healthy.

**Scope**
- Structured logging with no personal data; error tracking with redaction.
- Health checks and uptime monitoring.
- Alerts: API errors, failed logins, EIV submissions approaching deadline, failed
  certificate deliveries, backup failure.

**Acceptance criteria**
- [ ] An EIV submission approaching its deadline alerts a human before the
      deadline passes
- [ ] A failed backup alerts, rather than failing silently
- [ ] Logs contain no EFN, name, email or free-text evaluation content
- [ ] Alerts route to a real recipient, verified by firing one deliberately
