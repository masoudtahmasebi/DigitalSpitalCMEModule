### P10-01 · Security review

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 6 · **Depends on:** P9-07
- **Review gate:** human — auth

**Context**
The system holds named physicians' participation records and their EFN — personal
data processed for an accreditation purpose. M4's definition of done requires this
review to be signed off.

**Scope**

- Review the auth path end to end: token validation, role resolution, tenant
  context, super-admin "act as".
- Verify no secret is reachable through any endpoint at any role: SMTP
  credentials, VNR passwords, tokens.
- Verify personal data — EFN, free-text evaluation responses, names — is absent
  from logs and error payloads.
- Dependency audit; security headers; CORS restricted to the MEDICE origins.

**Acceptance criteria**

- [ ] No endpoint returns a secret at any role, verified by an enumerating test
- [ ] No EFN appears in any log at any log level, verified by test
- [ ] CORS allows only configured origins; a wildcard is impossible to configure
- [ ] Security headers present; error responses carry no stack trace, internal
      hostname or identifier
- [ ] Findings are recorded with a disposition — fixed, accepted with a reason, or
      deferred with a ticket. Signed off in writing.

### P10-02 · Tenant isolation test suite

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 6 · **Depends on:** P10-01
- **Review gate:** human — tenant isolation
- **Verifies:** ADR-0002

**Context**
This is the suite ADR-0002 exists to make possible. Isolation is claimed as a
property of the database, so it must be demonstrated against the database rather
than argued from code review.

**Scope**

- Attempt cross-tenant reads and writes against every tenant-scoped table.
- Prove `ds_app` cannot bypass RLS.
- Prove the pooled-connection leak is impossible: interleaved requests for two
  customers over a single pooled connection.
- Prove super admin is not a bypass — it acts as one customer at a time.

**Acceptance criteria**

- [ ] Every tenant-scoped table is covered; a newly added table without a policy
      fails the suite
- [ ] Cross-tenant writes are rejected by the database `with check`, not by
      application code — verified by disabling the application filter in the test
- [ ] Interleaved two-tenant requests over one connection show no leakage
- [ ] `ds_app` is confirmed not `BYPASSRLS` and not table owner in the deployed
      environment, not just locally

- **Review gate:** none

**Scope**

- Rate limits on auth, progress heartbeats, quiz submission and certificate
  download.
- Limits per user and per IP, backed by Redis so they hold across instances.

**Acceptance criteria**

- [ ] Limits hold across multiple API instances, not per process

### P10-04 · Hetzner provisioning and CI deploy

- **jira:** _(unassigned)_
- **Estimate:** 2.5 h · **Week:** 6 · **Depends on:** P10-03
- **Review gate:** none
- **Blocked by:** Hetzner account and DNS ownership (roadmap §12 item 6)

**Context**
Hetzner Cloud in Germany was chosen for GDPR posture (roadmap §2). Containerised
and portable — no dependency on a Hetzner-specific managed service, so the choice
stays reversible.

**Scope**

- Provision the environment: API, Postgres, Redis, TLS, DNS.
- CI deploy from the default branch; migrations run as `ds_migrator`, application
  as `ds_app`.
- Secrets from the environment, never from the image.

**Acceptance criteria**

- [ ] All data at rest is in Germany
- [ ] Migrations run as `ds_migrator` and the application as `ds_app`, enforced by
      the deploy pipeline rather than by convention
- [ ] No secret is baked into an image or present in the repository
- [ ] TLS is valid and enforced; HTTP redirects to HTTPS
- [ ] A deploy is repeatable and a rollback is possible
- [ ] The stack could be moved to another provider without code changes

### P10-06 · Observability and alerting

- **jira:** _(unassigned)_
- **Estimate:** 1 h · **Week:** 6 · **Depends on:** P10-05
- **Review gate:** none

**Context**
The failure this must catch is the quiet one from ADR-0005: EIV submissions
accumulating unsent while everything else looks healthy.

**Scope**

- Structured logging with no personal data; error tracking with redaction.
- Health checks and uptime monitoring.
- Alerts: API errors, failed logins, EIV submissions approaching deadline, failed
  certificate deliveries, backup failure.

**Acceptance criteria**

- [x] An EIV submission approaching its deadline alerts a human before the
      deadline passes — two levels (48 h, 12 h) plus `overdue`, each raised
      once, escalation recorded in the append-only audit log so it cannot be
      un-raised. Logged at `error` always; posted to `ALERT_WEBHOOK_URL` when
      configured. Runs **before** the submission sweep and in its own
      try/catch, so a broken EIV interface cannot suppress the alarm about the
      EIV interface being broken.
- [ ] A failed backup alerts, rather than failing silently — `deploy.sh` exits
      non-zero, so CI reports it; nothing watches a backup that fails between
      deployments. **Open.**
- [x] Logs contain no EFN, name, email or free-text evaluation content —
      asserted in `problem-details.filter.test.ts` and in the alert payload
      test; the EIV worker logs counts only
- [ ] Alerts route to a real recipient, verified by firing one deliberately —
      **open, and blocked on DigitalSpital choosing a destination.** The
      webhook is generic on purpose so that choice is an environment variable
      rather than a code change.

### P10-08 · White-label branding and admin-uploadable fonts

- **jira:** _(unassigned)_
- **Estimate:** 3 h · **Week:** 6 · **Depends on:** P9-01
- **Review gate:** none

**Context**
The platform is sold to more than one customer, so logo, colours, corner radius
and typeface are data on the project, not constants in a stylesheet. The
typeface is **uploaded**, not linked: a field asking for a font URL would be
filled in with a Google Fonts link within the week, and a German healthcare site
that loads a webfont from Google transmits every visitor's IP to a US service —
unlawful without consent per LG München I, 3 O 17493/20.

**Scope**

- `projects.branding` JSON plus font columns; `parseBranding` in
  `packages/domain` with strict grammars, validated on write and again on read.
- Public `GET /branding` and `GET /branding/font`, served through narrow
  SECURITY DEFINER functions that cannot see the Keycloak binding or the SMTP
  settings on the same row.
- `PUT`/`GET`/`DELETE /admin/branding/font`, with the format decided by the
  file's container signature rather than its declared type.
- Console branding screen; widget applies the branding as CSS custom properties
  and declares the `@font-face` in the document.

**Acceptance criteria**

- [x] A branding value that could terminate a CSS declaration is dropped, not
      repaired — and dropped again on read, not only on write
- [x] SVG cannot be stored or served as a font, by magic bytes and by a CHECK
      constraint
- [x] A font with data appended to it is refused (the header's own length field
      must match the file)
- [x] No third-party host is contacted for any frontend asset
- [x] An unknown project slug returns empty branding with 200, not a 404
      (ADR-0007)

### P10-09 · S3 course media, isolated per client

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 6 · **Depends on:** P5-03
- **Review gate:** none

**Context**
Course video and material files do not belong in the database or on the API's
disk. They go to object storage, and one customer's key must never be signable
for another.

**Scope**

- `courseAssetKey` / `keyBelongsToCustomer` in `packages/domain`, comparing on
  segment boundaries rather than by prefix.
- Hand-written SigV4 query-string presigning, validated against AWS's published
  test vector.
- `MediaResolver` injected into the learning service; passthrough by default so
  a deployment with no object storage still works.

**Acceptance criteria**

- [x] A key belonging to another customer is refused, and the refusal is
      indistinguishable from "no media"
- [x] `customer-10/…` does not match the prefix of `customer-1`
- [x] Presigned URLs match the AWS reference vector byte for byte
- [x] No media URL appears in a catalogue response — media is resolved per
      request, behind the gate

### P10-10 · GDPR: erasure, data minimisation and the processing record

- **jira:** _(unassigned)_
- **Estimate:** 3 h · **Week:** 6 · **Depends on:** P7-05
- **Review gate:** **human review required** — this touches the compliance
  record and the EIV path

**Context**
A CME participation record is retained under a legal obligation (Art. 17(3)(b)):
the Punktemeldung has gone to the Ärztekammer and points are credited against
it. Erasure therefore has to mean pseudonymisation, and the ordering against an
open reporting window has to be decided in code rather than left to whoever runs
it.

**Scope**

- `erase_subject` (migration 0009) plus the `subject-erasure` CLI. Owned by a
  dedicated NOLOGIN BYPASSRLS role; not executable by the API's own role.
- A trigger that keeps an erased profile erased when the subject signs in again.
- Query strings stripped from every log line and from problem-details
  `instance`.
- `docs/gdpr.md`: processing record, legal bases, retention, subject rights,
  sub-processors, and what was deliberately not built.
- Production database passwords taken from the environment rather than the
  development literals in `init-roles.sql`.

**Acceptance criteria**

- [x] The participation record survives erasure; every identifier does not
- [x] Erasure is refused while a Punktemeldung is queued, held or retrying
- [x] A sign-in after erasure cannot rewrite the profile — verified by removing
      the trigger and watching the test fail
- [x] `ds_app` cannot execute the erasure function
- [x] No query string reaches a log line or a response body
- [x] A production deployment cannot come up with the repository's development
      database passwords
- [ ] Retention period for the participation record confirmed with the ÄKWL —
      **open, and owned by MEDICE**
