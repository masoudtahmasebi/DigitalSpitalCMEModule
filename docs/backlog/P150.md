## P150-01 — `tenant-reads.mjs` exemptions were file-scoped, not statement-scoped

**Severity: medium. RLS-adjacent tooling — needs human review.**

### The gap

`ALLOWED` matched on `relative === entry.file` alone. Every reason in it is
written about one specific statement — `subject-erasure.ts`'s is entirely about
the P149-02 audit row — but the entry silenced **every** bare-pool read of
**every** tenant table in that file, for ever. The script's own docstring warns
against exactly this shape.

### Reproduced before fixing

A bare-pool `SELECT id FROM projects` added to `subject-erasure.ts`, unrelated
to the reviewed write:

```
$ node scripts/tenant-reads.mjs
tenant-reads: 24 tenant-scoped tables, 3 reviewed exemptions, no unguarded reads
exit 0          # the gap, confirmed
```

After the fix, the same read:

```
tenant-reads: 1 statement(s) read a tenant-scoped table on the bare pool …
  apps/api/src/subject-erasure.ts:294 — projects
exit 1
```

### The fix

Entries are `{ file, table, statement }` and silence only the statement they
name. The three existing reasons are preserved verbatim.

**A statement fragment rather than a line number — a deviation, flagged.** The
request said "by line number or line range". A line number in this list drifts
whenever anything above the statement is edited, and a check that fails for that
reason trains people to bump the number without re-reading the reason, which is
the review the list exists to force. A fragment moves with the code and stops
matching when the statement genuinely changes.

### Two of the three exemptions were silencing nothing

With the file filter removed, exactly one statement is flagged:
`subject-erasure.ts:266 — audit_log`. The other two call `SECURITY DEFINER`
**functions** — `list_customer_registry()`, `resolve_project_binding()` — so no
`FROM customers` or `FROM projects` ever appears in the argument and the scanner
never flagged them. Their reasons are worth keeping; calling them exemptions was
not, because an inert entry reads as active protection.

They now carry `documents: true`, and the script fails in **both** directions:

| Condition | Verdict |
| --------- | ------- |
| entry without `documents` that silenced nothing | stale exemption → exit 1 |
| entry with `documents: true` that did silence something | mislabelled → exit 1 |

### `ALTER TABLE ONLY` — answered with a grep, and the premise needs a correction

```
$ grep -c "ALTER TABLE ONLY" db/migrations/*.sql | awk -F: '{s+=$2} END{print s+0}'
0
```

**Not a live gap.** Every one of the nine names the regex extracts is a real
table.

The premise that it would "capture ONLY as the table name" is **wrong**, and the
truth is slightly worse. Demonstrated:

```
hardened captures: [ 'enrolments' ]
old captured:      []
```

`[a-z_]+` cannot span the space in `ONLY enrolments`, so the old regex captures
**nothing** — it would silently *drop* the table from the checked set while
still reporting a count. That is §9.1's second form. `(?:ONLY\s+)?` added
defensively.

### Sabotage — real exit codes, not a pipeline's

| Sabotage | `node` exit |
| -------- | ----------- |
| unguarded `projects` read in an exempted file | **1** |
| stale exemption (fragment changed to match nothing) | **1** |
| real exemption mislabelled `documents: true` | **1** |
| restored | **0** |

The first run of these reported `EXIT=0` because the shell was reading `head`'s
status, not node's — the same trap as `docker info` in P148. Re-run without the
pipe.

## P150-02 — an in-flight upload lost its progress when the dialog's tab changed

**Severity: medium. UI only — see the review note below.**

### The mechanism

`MediaDialog` renders `{tab === "upload" ? <UploadTab/> : …}`. `UploadTab` owned
the upload in its own `useState`/`useRef`, so switching to *Mediathek*
**unmounted** it and destroyed the tracking. Nothing aborts the request on
unmount, so the PUT carried on — which is exactly what the reporter's network
panel showed: `video-…mp4?X-Amz-…` still `(pending)`, no progress on screen.

Switching back remounted with `state = { kind: "idle" }` — a file picker over a
live multi-gigabyte upload. The reporter named the consequence: *"he may try to
do a new upload, as he is not seeing the progress"*.

### Multipart — checked, and not applicable

```
$ grep -rn "multipart" apps/admin/src --include=*.ts --include=*.tsx | grep -v test
(no matches)
```

`runUpload` → `uploadToTicket`, which is the single-PUT `XMLHttpRequest` path.
The console never reaches the P129 multipart API, so there is no multipart
resume/abort state to preserve here. Verified rather than assumed.

### The fix — option 1, lifting the state

`useUploadController` lives in `MediaDialog` and is passed to `UploadTab`. Two
properties:

1. **Progress survives a tab switch**, and is rendered at dialog level whenever
   the person is on another tab — so the upload is visible from the Mediathek,
   which is precisely where the confusion happened.
2. **A second upload cannot start while the first is running.** `start` refuses
   when busy.

Option 1 over option 2 (blocking the tab switch) because the tabs are how
somebody checks whether the file is *already* in the library — blocking that
during a long upload takes away the one thing that would stop them uploading a
duplicate. Option 3 alone would have left the invisible-progress complaint
unaddressed.

### Test first, and a hole in it that sabotage found

Written before the implementation and watched fail:

```
× keeps showing the upload after a tab switch, and refuses a second one
AssertionError: the in-flight upload lost its progress indicator on a tab
switch: expected null not to be null
```

Then the sabotage pass caught **my own test being vacuous**. Removing
`if (busy) return;` left it **green**, because once the state is lifted there is
no file input to pick with — the "start a second upload" half never executed.
§9.1, in an assertion of mine, found by breaking the thing it guards.

So the guard is now exercised directly, through the hook, where it can fail. No
path through today's UI can reach it, which is exactly the kind of code that
rots silently unless something holds it.

| Sabotage | Result |
| -------- | ------ |
| remove `if (busy) return;` — **first attempt** | **GREEN** — the test was vacuous |
| remove `if (busy) return;` — after strengthening | **RED** — "a second upload started while the first was still in flight: expected 2 to be 1" |
| put the state back inside the tab (the original defect) | **RED** — 3 tests |
| restored | **GREEN** — 14 passed |
