# P143 — The class behind P142: bounded resources, unbounded waits

P142 fixed the instance. The client asked the right follow-up: _"what other
places can be affected by this in all of the application?"_ This is the sweep,
and it is derived from source, not from memory.

The shape has three parts, and a defect needs only two of them:

1. **A bounded resource** (10 pool connections, 6 browser sockets per origin).
2. **Held across something slow** (a whole request; an HTTP call to a bucket).
3. **With no deadline**, so "slow" and "never" are the same thing.

P142 was all three at once. The rest of this list is what else has two or more.

---

## P143-01 — Six object-store calls run inside the request transaction, with no timeout

**Not fixed. This is the one that can still take the API down.**

`ObjectStorage` takes `fetchImpl: typeof fetch = fetch` — a bare `fetch`, which
has **no default timeout**. Six of its methods are called from inside a request
handler, and therefore inside the RLS transaction, holding a `PG_POOL`
connection for the whole round trip:

| `apps/api/src/shared/object-storage.ts` | called from                     |
| --------------------------------------- | ------------------------------- |
| `verifyUpload` (198)                    | `upload.service.ts:235`, `:850` |
| `beginMultipart` (297)                  | `upload.service.ts:677`         |
| `listParts` (392)                       | `upload.service.ts:815`         |
| `completeMultipart` (449)               | `upload.service.ts:820`         |
| `abortMultipart` (494)                  | `upload.service.ts:835`         |
| `discard` (520)                         | cleanup paths                   |

Ten concurrent uploads against a bucket that does not answer hold all ten
request connections. P142's guard does not fire — this is not a second
checkout, it is the first one held too long — and P141's `statement_timeout`
does not fire either, because no statement is running. Only
`idle_in_transaction_session_timeout` eventually releases them, at **two
minutes**, which is a two-minute outage per stuck batch rather than a permanent
one. Better than P142 and not acceptable.

**The condition that triggers it is documented and has happened.** P70-02: the
API container sat on an `internal: true` network with no route out for months,
so every one of these calls failed asynchronously and nothing said so. A bucket
that is unreachable rather than slow is the worst case here, not the unlikely
one.

**Fix:** a deadline on `fetchImpl` (`AbortSignal.timeout`), and — separately and
more importantly — the storage round trip should not happen inside the RLS
transaction at all. See P143-05.

## P143-02 — Five more untimed calls in `backup/store.ts`

`list` (55), `put` (89), `head` (99), `delete` (112), `copy` (140). Same bare
`fetch`, same absent deadline. These run in the backup path rather than a
request, so they hold no pool connection — the failure is a backup job that
never finishes and never reports, which is P140's subject from the other end: a
job that hangs pings no heartbeat, and the heartbeat is what would have said so.

## P143-03 — The OIDC token exchange has no deadline

`packages/oidc/src/index.ts:161` — the authorization-code exchange against
Keycloak. On the learner sign-in path. An unreachable IdP hangs the sign-in
rather than failing it.

`jwks.provider.ts` was the same and was fixed in P141; this is its twin, and it
was missed because P141 fixed the file the incident pointed at rather than the
class. §9.11, applied to my own fix.

## P143-04 — Nothing in the browser has a deadline either

`apps/admin/src/staff-auth.ts` and the SDK's request path call `fetch` with no
`signal`. That is the client half of what the client actually saw: **`(pending)`
forever, with no error and no message.** A deadline would not have prevented the
outage, but it would have turned an inexplicable dead screen into "Die
Verbindung zum Server ist abgelaufen" — which is the difference between a bug
report that says "the API is not responding" and one that says nothing at all
(§9.4).

The upload path already does this correctly (`xhr.ontimeout`, `sdk:1198`), which
is the evidence that it was a known concern and got applied in one place.

## P143-05 — The RLS transaction wraps the whole request, including non-database work

The design decision underneath all of the above. `TenantTransactionInterceptor`
holds one connection from `BEGIN` to the response, so **every** slow thing a
handler does — an object-store round trip, an SMTP send, a token exchange —
occupies a database connection while it happens.

It is a real trade: the interceptor is why `request.db` is always tenant-scoped
and why no handler can forget `runInTenant`, which is ADR-0002's whole safety
argument. Narrowing it is not a small change and is not obviously right.

What is not a trade is that the cost was never written down. Recorded here so
the next person meets it as a decision instead of a surprise.

## P143-06 — The readiness probe queues behind application traffic

`health.service.ts:79` runs `SELECT 1` on `PG_POOL`. When the pool is exhausted
the probe cannot answer, so the health endpoint reports the failure **by timing
out** rather than by saying "the pool is exhausted" — and a probe that hangs is
indistinguishable from a process that is dead.

That is exactly the 22 hours of `Up 22 hours (unhealthy)` with no explanation.
The probe should use the side pool, or a dedicated connection, and it should
**report pool saturation as a number** rather than as its own silence.

## P143-07 — Redis has no command timeout

`db.module.ts:164` — `new Redis(url, { maxRetriesPerRequest: 3 })`. The retry
bound means a command eventually errors rather than hanging for ever, so this is
the weakest item on the list; noted for completeness because the offline queue
is on by default and this was not a deliberate decision either way.

---

## Why it happened — four causes, none of them "somebody was careless"

1. **The default is the hazard.** `pg`'s checkout wait is `0` = for ever;
   `fetch` has no timeout; ioredis queues offline. Every one of these defects is
   _the absence of a line of code_, and absent lines do not appear in review
   diffs. Nobody chose to wait for ever; nobody chose not to.

2. **Each call site was locally correct.** The audit log genuinely must write
   outside the request transaction. `ParticipantRepository` genuinely must reach
   tables that are not tenant-scoped. Not one of the six was a mistake in
   isolation — the defect only exists in the _interaction_ between the
   interceptor and each of them, which is precisely what a per-file review
   cannot see.

3. **A comment recorded the reasoning and got the bound wrong.**
   `StorageAuditRecorder`'s header said "a pool of one would deadlock". The real
   bound is a pool of N under N concurrent requests. That comment is why nobody
   looked again — §9.10a: a comment that names one consequence of two is worse
   than none.

4. **Every test sends one request at a time.** 573 integration tests, sixteen
   browser tests, a full journey — all sequential. A deadlock that needs N
   concurrent requests is structurally invisible to every one of them. This is
   §9.13 one layer further out: the tests call the API one at a time; the person
   opens a screen that fires ten calls at once.

---

## What would have prevented it

- **A checkout deadline from day one.** Not because 5 s is a good number, but
  because _any_ number converts a permanent silent wedge into a logged failure.
  The cost of guessing wrong is a 500; the cost of no deadline was two outages.
- **The guard.** `guardReentry` is nine lines and found four call sites nobody
  had listed. It could have been written the day the interceptor was.
- **One concurrent test.** A single test firing `max` simultaneous audited
  requests would have failed on the first commit that introduced the second
  checkout, years before a customer saw it.
- **An alert on pool saturation.** `pg_pool_waiting` as a metric, with a
  threshold, would have named the cause in the first minute instead of the
  fourth day.

(7) is the §9.13 rule that keeps being relearned: _a fixture that assumes the
missing setting is present cannot find the missing setting._ A test bucket that
always answers instantly cannot find a call with no timeout. The harness bucket
already had to be made signature-verifying for the same reason in P70-01.

deploy, which is the one thing that matters today.
