# P53 — What the QA pass through the content hierarchy found

Raised 11.08 by the QA agent's Section 3, which asked the API to serve the
course hierarchy to a learner and checked what came back. One ticket so far,
and it is the one the section was written to look for.

---

## P53-01 · Courses are drafts until somebody publishes them · 3 h

**Status: done.** Needs human review — see below.

### What was wrong

There was no editorial state at all. `POST /admin/courses` created a course and
it was in the learner catalogue on the next request:

```
POST /admin/courses  {"projectSlug":"medice-adhs","slug":"qa-halbfertig", …}   201
GET  /courses        (learner)   → ['adhs-akademie-adult', 'qa-halbfertig']
GET  /courses/qa-halbfertig      → 200
PUT  /courses/qa-halbfertig/enrolment → 200
```

An empty course — no modules, no chapters, no content, no VNR, no
Anerkennungsbescheid — listed beside an accredited one and enrollable. An
operator building a course in the console was building it in front of the
physicians, and there was no way to stop them: the only thing that could hide a
course was the validity window (P50-01), and that is a different question.
`valid_from`/`valid_to` say **when an accredited course runs**; nothing said
**whether it is finished being written**.

Nobody had reported it, and nobody would have: the console's own author never
sees the learner catalogue, and the physician who saw the empty course would
report it as a broken course rather than as an unfinished one.

### What changed

`courses.status` — an enum, `draft` or `published` (migration 0038).

- **New courses default to `draft`.** The safe direction for the operation that
  was wrong: an author who forgets to publish shows nobody an unfinished
  course, an author who forgets to unpublish shows everybody one.
- **Every course that already existed was backfilled to `published`.** They are
  live, seen, and some carry completions; defaulting them would have emptied
  three tenants' catalogues on deploy.
- The catalogue filters on it in SQL, beside the tenant and the window.
- The detail route answers **404**, not 403 — an unpublished course must not be
  distinguishable from one that does not exist, or the status code enumerates
  what a customer is working on (§9.5).
- Enrol refuses a new learner.
- `courseAvailability` in `@ds/domain` gained a `"draft"` answer, so the
  existing refusals — playback, quiz, evaluation, completion — cover retraction
  with no new call sites. A course pulled back for editing behaves exactly like
  one whose window has closed (P51-02): **the record is kept, and it cannot be
  advanced.**
- The console has a _Sichtbarkeit_ section: publish, or _Zurückziehen
  (Entwurf)_, with a sentence saying what each state means for a learner.

The German refusal is its own sentence and not the expiry one. "Ihr
Teilnahmezeitraum ist abgelaufen" would send a physician looking for a deadline
they never missed and could do nothing about; _"Diese Fortbildung ist derzeit
nicht verfügbar. Ihre bisherigen Ergebnisse bleiben erhalten."_ is true, and
temporary (§9.4).

### The defect this ticket's own migration had

The backfill matched **zero rows** and the failure surfaced two statements
later as `column "status" of relation "courses" contains null values` — an
error about `SET NOT NULL`, which was fine, caused by an `UPDATE` that was not.

`courses` is under FORCE ROW LEVEL SECURITY. `ds_migrator` owns it and is
deliberately not `BYPASSRLS` (ADR-0002), so with no `app.customer_id` set it
sees nothing. Migration 0016 hit this identically and its fix applies: RLS off
for the length of the transaction, and a `DO` block that refuses to commit if
it was left off.

It did not show up on the QA database, because that one had had the migration
applied by hand as `postgres` — a superuser, which bypasses RLS. **The same SQL
under a different role is not the same outcome** (§9.6, and §9.9's corollary).
It was found by running the migrator, as the migrator's own user, against the
integration database.

### The tests, and what each of them could not have caught alone

Eleven cases in `learning-flow.integration.test.ts`, plus one in `journey` and
one in `authoring`. Two enforcement points exist — the SQL filter and the
domain rule — and neither test covers the other:

| Broken on purpose                          | Went red                                                                         |
| ------------------------------------------ | -------------------------------------------------------------------------------- |
| the `status` filter in the catalogue query | the 2 catalogue cases                                                            |
| `courseAvailability`'s draft branch        | the other 7 (detail, enrol, playback, wording, no-write, evaluation, completion) |

Both were restored and the suite re-run. The first case in the block asserts
the course **is** listed while published — without it every other assertion
passes on an empty catalogue (§9.1).

`journey` now has the publish as a step of the operator's job, asserted from
both sides in one case: the same request by the same signed-in physician
answers differently either side of it. Written as "after publishing, it is
visible" it would have passed on the platform this ticket fixes.

**Twelve integration fixtures inserted courses without a status** and became
drafts overnight — 33 failures in one file. Each now names `'published'`
explicitly, which is also the honest thing for a fixture to do.

### Acceptance criteria

- [x] A course created through `POST /admin/courses` is not in the learner
      catalogue, 404s on its detail route, and refuses enrolment
- [x] Publishing it makes all three work, with no restart
- [x] Retracting a published course keeps every existing enrolment readable and
      refuses playback, quiz, evaluation and completion — with a message saying
      the results are kept
- [x] The refusal does not claim the Teilnahmezeitraum expired
- [x] Every pre-existing course was published by the migration; no catalogue
      changed on deploy
- [x] The migration runs as `ds_migrator` against a database with rows in it,
      and leaves `courses` under FORCE ROW LEVEL SECURITY
- [x] Both enforcement points verified by breaking them and watching the tests
      go red
- [x] `pnpm verify` green; 464 integration tests green
- [ ] **Human review** — the console can now hide an accredited course from the
      physicians enrolled on it. That is the intended behaviour and it is one
      button; a reviewer should agree the wording of the retraction warning is
      strong enough before it reaches a customer admin.

### Deliberately not done

**No scheduled publishing.** "Publish on 01.09" is a third state pretending to
be a second one, and the validity window already exists for the case where the
date matters. Nobody has asked for it.

**`status` is not on the learner-facing `CourseSummary`.** A learner is never
shown a draft, so a field that is always `"published"` for them is a field that
can only ever leak what they cannot see. It lives on `AdminCourseSummary`
only — where the DTO↔SDK parity test caught the first attempt at putting it in
the wrong place.
