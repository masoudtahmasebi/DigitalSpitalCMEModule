# P16 · One domain, and images that do not know where they run

The deployment is for a real server now — `78.47.178.65`, `digitalspital.com` —
and the configuration that got it there was spread across twelve variables in
three places, five of which were baked into container images at build time.

## Why this exists

The stack is four public hostnames. Naming them took eight variables in the
production environment file (`API_DOMAIN`, `ADMIN_DOMAIN`, `PORTAL_DOMAIN`,
`WIDGET_DOMAIN`, `API_DOMAIN_URL`, `PORTAL_BASE_URL`, `STAFF_COOKIE_DOMAIN`,
`CORS_ALLOWED_ORIGINS`) plus six GitHub repository _variables_ repeating three
of them under different names — and the variables were `docker build` arguments,
so the values were inlined into the frontend bundles.

Twelve places to write one domain, and none of the disagreements is loud:

| Disagreement                          | What it looks like                                                      |
| ------------------------------------- | ----------------------------------------------------------------------- |
| `API_DOMAIN_URL` ≠ `API_DOMAIN`       | the console's every request blocked by its own CSP, nothing server-side |
| `CORS_ALLOWED_ORIGINS` missing a host | a blank page and a red browser console, found by a learner              |
| `STAFF_COOKIE_DOMAIN` not a parent    | every staff sign-in succeeds, then reports an expired session           |
| a build argument that had gone stale  | a console quietly talking to the previous deployment's API              |

The client asked for the base domain to be one configurable thing "in frontend
and also for wordpress plugin and so on". That is the same problem stated from
the other end, and this is the whole of it.

## P16-01 · One base domain, every hostname derived — **done**

- **Estimate:** 4 h · **Depends on:** P10-04

**Scope**

- `infra/deploy/domains.sh`: `ds_derive_domains` and `ds_check_domains`.
- `infra/deploy/domains.test.sh`: 36 cases, run by CI and by hand.
- `deploy.sh` sources it; the deploy workflow runs the same derivation before a
  byte reaches the server and publishes the derived API hostname as a job output
  so the smoke test and the environment URL cannot guess differently.

**Acceptance criteria**

- [x] `BASE_DOMAIN=digitalspital.com` produces all four hostnames, the API
      origin, the portal base URL, the widget URL, the cookie scope, the CORS
      list and the frontends' runtime values
- [x] Any of them may still be set explicitly and wins — a derivation that
      cannot be overridden is one you eventually delete
- [x] `EXTRA_CORS_ORIGINS` is where a customer's own origin goes, because that
      one is somebody else's domain and cannot be derived
- [x] The labels are individually overridable (`ADMIN_LABEL=admin`), since the
      German names are DigitalSpital's convention and not a property of the code
- [x] `KEYCLOAK_ORIGIN` is cut from `KEYCLOAK_ISSUER` rather than written twice
- [x] A pasted `https://digitalspital.com`, a port, a path, a trailing dot, a
      single label and an empty value are all refused **by name**, rather than
      producing `api.https://digitalspital.com` and failing inside Caddy's ACME
      client where the message is about a certificate
- [x] `ds_check_domains` asserts the cookie scope, the CORS membership, the CSP
      origin, the project slug and that no two services share a hostname
- [x] Deriving twice changes nothing
- [x] Tested in bash, not reimplemented in TypeScript: the thing that runs on
      the production host is the thing under test

**Verified against the real configuration.** A synthesised
`.env.production` for `digitalspital.com` passes `deploy.sh --check`, and
`docker compose config` resolves every derived value correctly. Eleven
deliberate faults were each refused with a message naming the cause: a pasted
URL, a missing base domain, a missing project slug, a hand-set wrong cookie
scope, a stale API origin, two services on one hostname, a CORS list missing our
own origins, the live EIV endpoint without its guard, an apex redirect that is
not a URL, and a world-readable secrets file.

## P16-02 · The frontends configure themselves at runtime — **done**

- **Estimate:** 4 h · **Depends on:** P16-01

**Scope**

- `infra/nginx/ds-runtime-config.sh`, run by nginx's own entrypoint before the
  server starts, writing `/config.js` from `DS_*` environment variables.
- `configValue` in `@ds/domain` — the precedence rule, shared by both SPAs.
- `apps/admin/src/config.ts`, `apps/portal/src/config.ts` read
  `window.__DS_CONFIG__` first and `import.meta.env` second.
- Both Dockerfiles lose every build argument.

**Acceptance criteria**

- [x] The admin and portal images carry no hostname and are deployable to any
      environment — a rollback is a tag change, not a hunt for the build with
      the right domain in it
- [x] Runtime wins over build-time, so a stale `VITE_*` in an old image can
      never override what the host says
- [x] `import.meta.env` survives as the development path, because `pnpm dev`
      has no container to generate the file
- [x] The generator **refuses** a value containing a quote, a backslash, an
      angle bracket or whitespace rather than escaping it — these are origins
      and slugs, and anything else is a typo worth stopping for
- [x] A missing `DS_API_BASE` stops the container, which the deploy notices in
      seconds, rather than producing a page that loads and fails every request
- [x] The file is written atomically and the partial is removed on every exit
      path — it lives in the web root, so a leftover `.tmp` would be servable
- [x] `/config.js` is `no-store` in both nginx configs: a cached copy would
      point a redeployed console at the previous deployment's API
- [x] CI builds the console image and exercises the generator inside it —
      the happy path, an injection attempt and a missing value

**Verified in Chromium against the real built bundle.** The console's `dist`
was served with the entrypoint's generated `config.js` on top — the container's
exact file layout — and driven with Playwright:

| `config.js` says                         | The bundle does                                                     |
| ---------------------------------------- | ------------------------------------------------------------------- |
| `apiBase: https://api.digitalspital.com` | first request to `https://api.digitalspital.com/admin/auth/session` |
| rewritten to `api.cme.digitalspital.com` | first request follows it — **no rebuild**                           |
| `{}`                                     | renders "Die Verwaltung ist nicht korrekt konfiguriert"             |

The middle row is the ticket's whole claim: the same image, byte for byte,
pointed at a different API by editing one file the container writes at start-up.

## P16-03 · The WordPress plugin takes a base domain too — **done**

- **Estimate:** 1 h · **Depends on:** P16-01

**Scope**

- `DS_LMS_Settings::derive_api_base` and `::sanitize_domain`, plus a
  **Basis-Domain** field with the API URL shown beneath it as it is derived.

**Acceptance criteria**

- [x] `digitalspital.com` yields `https://api.digitalspital.com`, by the same
      rule the server uses
- [x] A pasted `https://digitalspital.com/`, mixed case, a trailing dot or a
      path are all normalised rather than refused — that paste is the mistake
      everybody makes, and left alone it derives `https://api.https://…`
- [x] A port, a single label or anything not domain-shaped becomes empty, which
      the settings page reports and the renderer treats as "not configured"
- [x] The explicit **API-Basis-URL** field still wins, for a staging API on a
      hostname following no convention
- [x] The override field shows the _stored_ value, not the derived one — showing
      the derived value would make the next save pin it and silently stop the
      derivation
- [x] 17 new checks in the plugin's security suite; 53 in total

## P16-04 · The runbook is about this server — **done**

- **Estimate:** 2 h · **Depends on:** P16-01, P16-02

`docs/deployment.md` rewritten for `78.47.178.65` and `digitalspital.com`: the
real DNS (apex plus wildcard, both already in place), one GitHub variable
instead of eight, what the preflight checks so nobody has to, how to point the
WordPress plugin at it, and how to move a domain without rebuilding an image.

**Two things it now says out loud:**

- **The cookie scope.** A flat layout under the company domain means every
  present and future subdomain of `digitalspital.com` receives the staff session
  cookie. It is httpOnly and Secure, so the exposure is a session token in
  somebody else's access log rather than a readable credential — but the fix is
  one line (`BASE_DOMAIN=cme.digitalspital.com`) plus one wildcard DNS record,
  and it is much cheaper before anything else is hosted under the bare domain.
  Listed in §7 as an open item rather than decided unilaterally: the client chose
  the flat layout knowing the trade.
- **The bare domain is not ours.** `digitalspital.com` is free for a promotional
  site. `APEX_REDIRECT_URL` makes Caddy redirect it in the meantime; empty means
  no site block at all, so it can be pointed elsewhere without touching this
  repository.

## Deliberately not done

**Narrowing the staff cookie by removing its `Domain` attribute.** The console
and the API are separate origins, so a host-only cookie would need
`SameSite=None`, which is exactly what the current `Lax` posture exists to
avoid (see the header of `staff-auth.controller.ts`). The alternative that
would genuinely fix it — serving the API under a path on the console's own
origin, making the requests same-origin — is an auth-path change under the human
review gate and is more than this ticket asked for. Recorded here so the next
person meets the reasoning rather than the omission.
