# P221 — deploy 131's post-deploy journey failed on a check that was racing the API

Deploy **131** (`cd0d8f9`, P220) reported **failure**. The deploy itself did
not fail: every step of `Deploy to production` is green, including the
migration, the seed and the two posture reads. What went red is the second job,
`The whole journey, in a browser`, which drives the installation after it is
updated.

```
1) journey.spec.ts:158 › ein Betreiber baut eine Fortbildung, eine Ärztin schließt sie ab

   Error: the catalogue drew no course cards, so the measurements below prove nothing
   Expected: > 0
   Received:   0
     at apps/e2e/tests/journey.spec.ts:799
```

Verified: `actions_list list_workflow_jobs` on run `34653886391` — job
`103441963076` "Deploy to production" `conclusion: success`, job
`103442347365` "The whole journey, in a browser" `conclusion: failure`, failing
step `Drive the deployed installation`.

**So the P220 change is live and correct on production. The red is my own
check.**

---

## The cause

That assertion is mine, from P218-05 (DEP-42, the course cards lining up). It
reads:

```ts
const cards = await learner.locator("article").evaluateAll(/* … */);
expect(cards.length, "the catalogue drew no course cards, …").toBeGreaterThan(0);
```

`evaluateAll()` and `all()` are the two locator methods in Playwright that do
**not** retry. Every other call in this file — `getByRole(…).click()`,
`expect(…).toBeVisible()` — auto-waits, which is why no wait had ever needed to
be written down here. These two resolve against whatever is in the document at
the instant they run, and answer an empty array when the honest answer is "not
yet".

And "not yet" is the normal state at that point in the journey.
`CoursePanel` in `CourseList.tsx` draws its tab row from static copy and its
cards from `list.loading`:

```ts
if (list.loading && list.data === undefined) {
  return <div className={panel}><Spinner label={de.loading} /></div>;
}
```

So the tab row — which the measurement immediately above this one asserts, and
which passed — says **nothing at all** about whether `listCourses` has answered.
The suite was racing the API for the cards, and had been since P218-05.

On the rig it wins that race every time: the API is a process on `127.0.0.1`
answering in single-digit milliseconds. Against an installation it is a request
across the internet to `api.digitalspital.com`, and deploy 131 is where it
finally lost. Deploy 130 ran the same code and won it — which is the part worth
writing down, because two green runs of a racing check is exactly P32-01's
"verified by running twice" (§9.1).

---

## The fix

A wait that states what it is waiting for, before each snapshot — one for the
tab row and one for the cards:

```ts
await expect(
  learner.locator("article").first(),
  "the catalogue never drew a course card",
).toBeVisible({ timeout: 20_000 });
```

This is strictly stronger than what was there. A catalogue that genuinely draws
no card still fails, with the same sentence, after 20 s — so the property
P218-05 wrote the guard for is kept. What goes away is failing because the
answer had not arrived yet.

### Watched red, under the condition that actually occurs (§11.10)

A sequential rerun proves nothing about a race, so the race was **made** to
happen on the rig: `page.route` on the first `/courses` request, delayed 5 s,
installed before the portal load.

| Code             | Result                                                                  |
| ---------------- | ----------------------------------------------------------------------- |
| before the fix   | **red** — `the catalogue drew no course cards`, the exact deploy-131 line |
| after the fix    | **green**, with `SABOTAGE: delaying http://127.0.0.1:3100/courses?…` in the log proving the delay fired |

The log line matters: the first attempt at this sabotage passed, and it passed
because the route was installed too late to intercept anything. A sabotage that
does not fire is a green run that means nothing — the same shape as the check it
was written to break.

## The class (§9.11)

`grep -rn "evaluateAll\|\.all()" apps/e2e/tests apps/e2e/support` returns
exactly two hits, both in the DEP-42 block added by P218-05, and both are fixed
here. There is no third instance: every other locator call in the suite is an
auto-waiting one.

The rule this leaves behind, in the comment at the call site: **a geometry
measurement waits for its subject with an assertion of its own before it
snapshots**, because the two methods that can measure geometry are the two that
do not wait.
