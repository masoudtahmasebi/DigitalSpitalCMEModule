# P62 — Closing what Sections 1–9 left open

Raised 12.08 by the client's pre-Section-10 sweep. Four items, three of which
are checks that do not exist, plus one experiment.

The shape shared by all of them: **a value that is absent renders as an absence
rather than an error**, so nothing refuses and nobody looks. A missing
`fortbildungsnummer` omits a line. An unreachable media host shows a player that
will not seek. A missing `vnr_password` produces a `failed_permanent` row in a
table nobody opens. Each is invisible from the screen that would have to notice.

---

## P62-01 · One review packet for the nine held items · 1 h

**Status: done.**

### What was wrong

Nine items across seven tickets carry `[ ] Human review`. Four of those lines
said only which area they touch — _"certificates."_ — which tells a reviewer
what to be careful about and not what to decide.

And the label has no vehicle: `needs-human-review` is a **pull-request** label
and **there is no open PR for this branch.** The gate exists in Markdown and
nowhere a merge could encounter it. CLAUDE.md §9.3 applied to a workflow.

### What changed

`docs/review/compliance-review-packet.md` — one section per item, each stating
the defect, the fix, **the decision the reviewer owns**, and **what goes wrong
if they decide the other way**, so that approving and rejecting are both
informed. Ordered by what a wrong decision costs rather than by ticket number.

The four thin gate lines now carry their question, so the ticket and the packet
say the same thing.

### Deliberately not done

**No PR opened.** Opening one is the client's call, and it is the single action
that gives the label somewhere to live. The packet is written so it can be
pasted into the description.

## P62-02 · A published CME course could be missing everything the certificate needs · 3 h

**Status: done.** Touches certificates and eiv — human review.

### What was wrong

Nothing refused. A course could be `published`, award CME points, and have no
VNR, no VNR password, no accreditation body, no organiser, no stamp and no
signature. A physician could enrol, watch, pass, evaluate, supply their EFN —
and discover at the end that no certificate can be rendered and no Punktemeldung
can be sent.

This is not hypothetical. On the QA database, at head `5aabd3b`:

```
slug            status     cme_points  vnr                  has_vnr_password
ds-cme-demo     published  3           9999999999999999999  f
qa-quiz-10      published  2           9999999999999999999  t
```

`ds-cme-demo` is published, awards three points, and its Punktemeldung fails
permanently with `missing_vnr_password`. It is a fixture — but nothing about
the platform knows that, and the same row shape is what an author produces by
filling in half a form.

### The client's proposal, and why it is right in idea and wrong in layer

> _"My instinct is a publish-time precondition: a course awarding CME points
> cannot move to published while any field the certificate or the Punktemeldung
> reads is null."_

The rule is right. **Enforcing it only at the publish transition is not**, for
one concrete reason: the offending rows above were never published by anyone.
The seed inserted them with `status = 'published'` directly. A service-layer
publish guard would not have seen them, and CLAUDE.md §9.9's corollary is
exactly this — the repository's state is not the installation's state, and a
check that lives in one code path only covers that path.

The other half is that publishing is not the only transition that can break the
invariant. A published course can be **edited**: clear the VNR on a live course
and the guard, having run at publish time, has nothing to say.

So the invariant is not _"you may not publish an incomplete CME course"_. It is
**"a published CME course is never incomplete"** — a property of the row, true
at every instant, which is a CHECK constraint.

### What changed — two layers, and they are not redundant

| Layer                                                                    | What it does                                                                              | Why the other cannot                                                                        |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `courses_published_cme_is_complete` (migration 0042)                     | Refuses the row. Applies to the API, the seeds, a migration, and an operator with `psql`. | The service never sees a direct INSERT.                                                     |
| `publishBlockers` in `@ds/domain`, called by `AdminService.updateCourse` | Names the missing fields in German, before the write                                      | A CHECK violation is a 500 and a constraint name. The person clicking Publish needs a list. |

The same division as ADR-0002: application code explains, the database
guarantees. Neither is the only defence and neither is decoration.

### What counts as complete

Every field the certificate or the Punktemeldung actually reads, taken from
`missingCertificateFields` and the EIV client rather than from a fresh list —
so the constraint cannot drift from what the renderer needs:

`vnr`, `vnr_password_enc`, `cme_category`, `accreditation_body`, `organizer`,
`event_location`, `scientific_lead_name`, `certificate_issue_place`,
`stamp_image`, `signature_image`. (`title` is already `NOT NULL`; `cme_points`
is the trigger for the rule.)

**Not** `fortbildungsnummer` — see the show-stopper below. **Not** the media
sources, which live on `contents` and are P62-03's problem.

### What the migration does to rows that already violate it

**Demotes them to draft, and says how many.** Not "fails", which would make the
migration unrunnable on every existing installation; not "grandfathers them",
which would leave the exact rows this exists to catch. A published course that
cannot produce a certificate is a course that should not be published, and
demoting it is the truthful outcome — the operator sees a draft and can see why.

`adhs-akademie-adult` survives untouched, which is the calibration test: the
constraint is set to what real accredited content already satisfies.

### Acceptance criteria

- [x] A published, point-awarding course with any of the ten fields unset is
      refused by the database, whatever writes it
- [x] The admin API refuses first, naming the missing fields in German
- [x] A **point-free** course is unaffected — it has no certificate and no
      Punktemeldung to be incomplete for
- [x] A **draft** course may be incomplete; that is what draft is for
- [x] The migration demotes existing violations rather than failing, and counts
      them
- [x] `adhs-akademie-adult` is still published afterwards
- [x] Verified red at both layers
- [x] The integration suite is green again, with the five fixtures that were
      creating the forbidden row fixed rather than exempted
- [ ] **Human review** — certificates and eiv. The reviewer's question is
      **whether "awards CME points" is the right trigger**, and whether
      demoting existing rows is acceptable on the MEDICE installation. Packet
      §10.

### The red check nobody had to arrange

CLAUDE.md §9.1 asks for evidence that a check could have been red. This one
supplied its own, at a scale that was not planned for: the first integration run
after the migration landed failed **18 tests across 5 suites**, every one of them
on

```
new row for relation "courses" violates check constraint
  "courses_published_cme_is_complete"
```

Those five suites had been writing, for months, exactly the row the constraint
forbids — `INSERT INTO courses (…, cme_points, status) VALUES (…, 4,
'published')` with no VNR, no password, no stamp. That is the finding restated:
the shape was so easy to produce that the project's own fixtures produced it
five times without anybody noticing, and no test was capable of noticing because
no test asserted the absence.

The sixth was better than the other five. `moderation` inserted a _point-free_
published course — legal — and then `P13-01` PATCHed `cmePoints: 6` onto it. The
guard refused the whole PATCH, and the failure surfaced two cases later as
"`learningObjectives` is empty". That is the transition the client's proposed
publish-time precondition would have missed entirely: nothing published
anything, and a course that awards no points became one that does.

**Fixed as a class, not as six instances:** `test/integration/support/
accredited-course.ts` holds the paperwork once, furnishes with `COALESCE` so it
can never overwrite a value a suite is asserting on, and requires the caller to
insert a draft — which is also the order an operator works in. The journey now
asserts the refusal and the German sentence naming `VNR-Passwort` as part of the
operator's act, so the guard has a caller-side test as well as a rule-side one
(§9.7).

## P62-03 · A media host that will not seek looks exactly like the anti-skip gate · 2 h

**Status: done.**

### What was wrong

Section 9 found it by accident and it cost an hour. Two different causes, one
symptom:

| Cause                                            | What the learner sees   |
| ------------------------------------------------ | ----------------------- |
| The gate working — you have not watched that far | the playhead snaps back |
| The host does not answer `Range` with `206`      | the playhead snaps back |

The second is a misconfigured server and the first is the product doing its job,
and the person watching cannot tell them apart. Worse, the wrong one is the one
people assume: the player says _"Vorspulen ist nicht möglich"_ on screen, so a
broken host reads as a working feature and nobody investigates.

### What changed

**A check, and a sentence.**

- `GET /admin/courses/{slug}/media-check` performs a one-byte `Range` request
  against every distinct source on the course and reports, per URL, whether the
  answer was `206` with a `Content-Range`. It is an admin route because the
  answer is an operator's, and it names the URL because an operator is entitled
  to it (§9.10).
- The player distinguishes the two refusals. When `video.seekable` is empty
  after metadata has loaded, a seek is refused with _"Dieses Video kann nicht
  gespult werden — der Videoserver unterstützt das nicht. Bitte melden Sie das
  dem Veranstalter."_ rather than the anti-skip wording. The learner is told it
  is not their doing, and told what to do next.

### Acceptance criteria

- [x] The admin check reports 206/no-206 per source URL
- [x] The player says which refusal it is
- [x] Verified red: pointing a course at a server without Range turns the check
      red and changes the player's message

## P62-04 · A 60-second access token, and what actually happens · 1 h

**Status: done.** The experiment found P62-05, below.

Show-stopper **S2** is still open: MEDICE's Keycloak access-token lifespan is
unknown, and at a 5-minute default a 25-minute video outlives its token several
times. Rather than wait for the answer, the dev realm was set to 60 seconds and
a module watched across the expiry.

### What actually happens

Measured, not inferred, at commit `5aabd3b`:

|                  |                                                                                                                                                                                         |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Playback**     | continues indefinitely. The video is a plain `<video>` with no credential; nothing about the token touches it.                                                                          |
| **Progress**     | stops being credited **completely**. Every flush from expiry onwards answers `401`, roughly two per fifteen-second interval, for as long as the learner watches.                        |
| **The database** | `content_progress.watched_percent` stayed at what it was before expiry.                                                                                                                 |
| **The refusal**  | is correct and deliberate: `AUTH_CLOCK_TOLERANCE_SEC` is 5, so a token is honoured for five seconds past `exp` and refused thereafter. A token expired by 40 seconds got a clean `401`. |

The API behaved exactly as designed at every step. **The widget did not.**

## P62-05 · The screen promised an autosave that had stopped happening · 1.5 h

**Status: done.** Found by P62-04's experiment.

### What was wrong

While every flush was being refused, the player still said:

> Ihr Fortschritt wird automatisch gespeichert

It says that permanently, and `LessonScreen` swallowed flush failures on
purpose — with sound reasoning that a 401 invalidates at every step:

| The original reasoning              | Why a 401 breaks it                       |
| ----------------------------------- | ----------------------------------------- |
| "a learner cannot act on it"        | they can: reload and sign in              |
| "the next flush retries"            | it fails identically, forever             |
| "the server converges on the truth" | nothing is accepted, so nothing converges |

The SDK has already spent its single refresh attempt (P5-02) before this catch
runs, so by the time the exception arrives the failure is permanent.

The cost is a physician's evening. Twenty-five minutes of a Fortbildung
credited as nothing, with a reassurance on screen throughout — and the next
sign-in showing the progress bar where they left it before the token lapsed.

### What changed

`isSessionExpired` — pure, in `apps/widget/src/session.ts` — distinguishes a
401 from anything the next flush could recover from. `LessonScreen` calls it in
the catch it already had; `PlayerScreen` swaps the promise for the truth:

> Ihre Sitzung ist abgelaufen — Ihr Fortschritt wird derzeit nicht gespeichert.
> Bitte laden Sie die Seite neu und melden Sie sich erneut an.

What happened, what it costs, and what to do — in that order (CLAUDE.md §9.4).
The silence stays for 408/429/5xx and for a network failure, where the original
reasoning still holds.

### This is a mitigation, not the fix

It makes the loss **visible**. It does not prevent it. Preventing it needs a
token the widget can refresh, which is S2 and belongs to MEDICE. Until then a
learner whose session lapses mid-module loses the unflushed intervals and is
told so.

### Where the test is, and where it deliberately is not

`isSessionExpired` is unit-tested exhaustively, including the statuses that
must **not** trigger it. The wiring from a 401 to the sentence is verified in a
real browser, because jsdom has no media pipeline: the watch tracker never
records an interval, so the flush returns early and a component test would be
asserting against stubs. `PlayerScreen.test.tsx` says so where the test would
otherwise be missing.

The browser run, at `5aabd3b` with the widget rebuilt:

```
token 40s left    : playing=true  on screen: nothing about the session
token 10s left    : playing=true  on screen: nothing about the session
token +10s expired: playing=true  on screen: "Ihre Sitzung ist abgelaufen — …"
token +30s expired: playing=true  on screen: "Ihre Sitzung ist abgelaufen — …"
token +55s expired: playing=true  on screen: "Ihre Sitzung ist abgelaufen — …"
```

### Acceptance criteria

- [x] A 401 on the flush replaces the autosave promise with the truth
- [x] 408/429/5xx and network failures stay silent
- [x] Verified red: making `isSessionExpired` always false turns one unit case
      red; the browser run shows the old behaviour
- [x] Verified live in a browser across a real token expiry

### The minimum lifespan we can tolerate

**Any lifespan longer than the longest single content item, plus a margin.** The
platform's own flush interval is 15 seconds, so a lapse costs at most that much
watched time — but only if the learner notices and reloads, which is what
P62-05 now makes possible.

Concretely, for the MEDICE course: modules run to about 25 minutes, so **30
minutes is the minimum comfortable access-token lifespan** and 60 is better.

**If MEDICE's realm is at the 5-minute default**, one of three things has to
happen, in order of preference:

1. **A refresh token the WordPress plugin can use.** The SDK already has the
   hook (`onUnauthorized`, one attempt, never a loop). This is S2's first
   question and the answer may already be yes.
2. **Raise the realm's access-token lifespan** to 30 minutes for this client.
   A realm-wide change with security implications MEDICE own.
3. **Accept the loss and keep the warning.** A physician reloads every few
   minutes. Workable and unpleasant, and not something to discover at launch.

## Show-stoppers raised, not guessed

Written to `docs/show-stoppers.md` rather than decided here, per CLAUDE.md §7.

**S24 — what is `fortbildungsnummer`?** The column exists in `0001_init`, is
editable in the console, and renders one line on the Zertifizierung tab. It is
**not** read by the certificate or by the Punktemeldung, both of which use the
VNR. The Anerkennungsbescheid names a VNR and nothing else. So either it is a
second name for the VNR that the layout drew separately — in which case the
column should go and the tab should render the VNR — or it is a distinct Kammer
reference nobody has described. It is NULL on every seeded course and the tab
silently omits the line, which is why it has survived unnoticed. **Owner:
MEDICE / ÄKWL.**
