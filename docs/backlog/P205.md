# P205 — Every API failure says something, without every screen having to

**Raised by:** the client, 07.09.2026 — _"at least in here a toast should show
the error and also it should be the same for any other errors happening in the
admin panel."_

The second half is the ticket. P202 fixed the screen that reported it; this is
the "and everywhere else".

---

## Why a wrapper and not 48 edits

`describeError` is called from **48 places across 19 files**. Rewiring each is
48 chances to miss one, and the 49th is written next week with no channel at
all — which is exactly how the course-delete refusal came to be invisible.

Both console clients are built by one function, `staffClient`. So a failure is
observable in **one** place, and a net under every request cannot be forgotten
by a screen that does not exist yet.

A `Proxy` rather than a list of wrapped methods: `ApiClient` grows a method
whenever the contract does, and a hand-maintained list is a list that will be
one short. It re-throws, always — every existing `catch` behaves exactly as
before, and screens keep their inline messages, which carry context a transient
toast cannot.

This is a floor, not a replacement: _something_ is always said.

## What it deliberately does not announce

`401` and `403`. The console routes both already — to the login form and to the
"you are not an admin" screen — and a disappearing toast over a screen whose
whole job is to explain the same thing is noise. A 403 while a role probes what
it may see is not news.

## The test that could not go red, and the trap behind it

`stays quiet for 401 and 403` passed **with the guard removed**.

`expect(queryByRole("alert")).toBeNull()` immediately after the rejection passes
whether or not a toast was published: React has not flushed the state update
yet, so _not there_ and _not there yet_ are the same observation. This is the
P199 trap in a different costume — an assertion about absence, made too early.

It publishes a known sentinel afterwards and waits for it. When the sentinel
appears, anything the 403 published would have appeared too, so exactly one
alert means the 403 published nothing. With that, removing the guard fails.

The first version of the _other_ case had the §9.7 fault: it hand-rolled what
the wrapper does and would have passed with `announcing` deleted. It goes
through `createAdminClient` and a stubbed `fetch` now, so it fails when the
wrapper is removed.

## Watched red

| sabotage             | result                      |
| -------------------- | --------------------------- |
| remove `announcing`  | the real-wrapper case fails |
| announce 401/403 too | the quiet case fails        |

## Not done

Screens that show an inline message now also raise a toast, so a failure they
already report is said twice. That is deliberate for this ticket — the floor
matters more than the duplication — but it is worth a pass later to decide, per
screen, which of the two should stay.
