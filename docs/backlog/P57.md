# P57 — What the QA pass through EFN capture found

Raised 11.08 by the QA agent's Section 6 (EFN capture, storage, isolation).
Storage, validation, correction and isolation all behaved. What did not was the
endpoint's ability to say whether an EFN was needed at all.

---

## P57-01 · `GET /profile/efn` says whether one is needed · 1 h

**Status: done.**

### What was wrong

The endpoint answered `{"efn": null}`, and that sentence has two meanings:

- _we do not need one from you_ — every course you take awards no CME points,
  so there is nothing to report to EIV-FOBI and nothing an EFN would identify;
- _we need one and you have not given it_ — the Punktemeldung is waiting on it.

Only the server can tell them apart: it turns on the `cme_points` snapshotted
onto the learner's enrolments, which no client can see. A physician's own
profile screen, or any "your account is incomplete" nudge, had no way to decide
whether to prompt — and prompting wrongly means asking a doctor for their
Fortbildungsnummer when the platform has no use for it, which ADR-0004 exists to
prevent.

### What changed

`{"efn": …, "required": boolean}`. `required` is true when **any of the caller's
enrolments in this project's customer** awards CME points.

Two decisions worth stating, because both could reasonably have gone the other
way:

- **It describes the courses, not the gap.** It stays true once an EFN is
  supplied. A client that wants to prompt asks `required && efn === null`,
  which is one expression that cannot drift from the server's meaning of either
  half. Flipping it to false on supply would make "is an EFN needed here"
  unanswerable for everybody who already has one.
- **It is scoped to the tenant the request came through**, because that is the
  only data the request may see (ADR-0002). A physician enrolled with two
  customers asks twice and gets two honest answers, rather than one answer
  assembled from rows this request has no right to.

`cme_points` is read off the **enrolment**, not the course: the enrolment
snapshots what the course was worth when it was taken (P3-01), so re-pricing a
course later cannot retroactively change whether somebody was asked for their
EFN.

### The read has its own rate limit now

It shared `efnWrite`'s ten-per-minute bucket, and the completion screen asks on
every mount — so a physician reloading the page while correcting a typo spent
the budget the correction itself needs and was refused **in the middle of the
correction**. QA hit it in the ordinary course of the section.

`efnRead` is 60/minute. Still metered, because a route touching `efn_profiles`
should not be the one unlimited path into that table, but the read is
idempotent, returns one field and can only ever return the caller's own.

### Acceptance criteria

- [x] `required: true` for a learner whose enrolment awards points
- [x] `required: false` when nothing they take does — verified live by making
      every enrolment point-free and back
- [x] `required` stays true after an EFN is supplied
- [x] An account with no enrolments at all is told none is required
- [x] Verified red: hardcoding `required: true` turns one unit and one
      integration case red
- [x] `pnpm verify` green; 476 integration tests green

### No caller in the product yet

Stated plainly rather than left to be discovered: **no screen reads `required`
today.** The widget's completion screen asks per course, through
`outstanding`, which is the right source there, and there is no standalone
profile area in the portal. This is an API affordance for the client that asked
for it — a profile prompt is the obvious thing to build on it, and it can be
built without another API change.

## What Section 6 confirmed as already correct

- **6.2 — invalid EFNs are refused and never echoed.** `"123"`,
  `"ABCDEFGHIJKLMNO"`, sixteen digits, a trailing space and the empty string
  all refused with _"Die EFN muss aus genau 15 Ziffern bestehen."_ and the
  rejected value absent from the response. Three layers agree: the DTO regex,
  `isValidEfn` in `@ds/domain`, and the column's own CHECK.
- **6.3 — stored with `created_at`.** `efn_profiles` holds `user_id`, `efn`,
  `created_at`, `updated_at`.
- **6.4 — correcting it works and keeps its history.** A second write moves
  `updated_at` and leaves `created_at` at the first supply, which is what makes
  "when did this physician first give us their EFN" answerable.
- **6.5 — one physician cannot see another's.** A second learner in the same
  tenant reads only their own; the subject is the principal and never a
  parameter (P54-02), and the case that would catch a regression is in the
  integration suite.
- **6.6 — no EFN in any other response.** Eight endpoints checked — catalogue,
  course detail, enrolment state, materials, quiz, evaluation, certificate,
  `/auth/participant/me` — for the value, for any fifteen-digit run, and for an
  `efn` key. None present anywhere.

### Two differences from the section's wording, not defects

- **The verbs are `PUT` and the refusal is 422.** There is no `POST` or `PATCH
/profile/efn` (both 404). `PUT` is what makes storing an EFN idempotent, and
  422 is what this API answers for a well-formed request whose contents fail
  validation — everywhere, and the contract documents it.
- **There is no `source` column.** Every EFN is supplied by the physician
  through this one route; a `source` would model a second origin that does not
  exist. Keycloak attributes and Salesforce sync were both considered and
  rejected in ADR-0004, and Salesforce is explicitly deferred scope. If it ever
  arrives, the column arrives with it and means something.
