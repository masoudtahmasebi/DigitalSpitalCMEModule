# P32 · The test database was the development database

> please complete the system for a full production cme module based on best
> practices and tests so we don't get issues all the time in testing the system

"Issues all the time in testing the system" was not a vague complaint. It had a
cause, it was measurable, and the measurement is this: **the development
database held 1 096 customers, of which three were real.**

Nobody was careless. The integration suite wrote into `ds_education` — the same
database the console and the portal run against — and nothing cleaned up. About
fifty customers a run, every run, for weeks.

---

## What that actually cost

- **The console's customer picker became a wall.** `tenant-a GmbH`,
  `Pipeline Test GmbH`, `Completion Flow GmbH`, hundreds of them, with `MEDICE`
  somewhere in the middle. "Is this broken or is this leftovers" became a
  question somebody answered by hand before every session.
- **Suites became order-dependent, and one of them had a workaround written
  into it.** `eiv-worker.integration.test.ts` opened by holding every other
  tenant's submissions:

  ```sql
  UPDATE eiv_submissions SET status = 'held' WHERE customer_id <> $1
  ```

  The worker's sweep is global by design — that is the correct design, a
  deadline does not care whose tenant it is — so on a polluted database it
  processed forty other suites' leftovers and counted them in its tally. The
  `UPDATE` made the test pass. It also made the test a test of the workaround.

- **Runs got slower every week**, and a failure could not be attributed without
  first deciding whether it was yours.

**And CI never saw any of it**, because CI's Postgres is a fresh container per
run. So the suite was green in CI and increasingly unreliable at a terminal —
the worst available arrangement, because the signal people actually watch is
the one that lies.

---

## P32-01 · An isolated test database, and one command — **done**

- **Estimate:** 5 h · **Review gate: none** — no production code changed

### What was built

| File                                 | What it is                                                |
| ------------------------------------ | --------------------------------------------------------- |
| `scripts/testdb.mjs`                 | provisions `ds_education_test`: create, roles, migrate    |
| `scripts/run-integration.mjs`        | `pnpm test:integration` — provision, build, truncate, run |
| `apps/api/test/integration/setup.ts` | the three guards every run passes before the first test   |
| `scripts/devdb.mjs`                  | `pnpm db:dev:reset` — rebuild the _development_ database  |

Running the suite used to mean four URLs from memory, from `apps/api`, with the
workspace built beforehand or the run silently tested yesterday's code. Every
one of those is a way to get a wrong answer and all of them were got wrong in
practice. It is now:

```bash
pnpm test:integration                       # every suite
pnpm test:integration -- -t "cross-tenant"  # filters pass through
pnpm test:integration --fresh               # rebuild the database first
```

### The three guards, and why each is a guarantee rather than a check

1. **The database must be local.** These suites truncate. A `DATABASE_URL`
   copied out of a deployment into a terminal is not a far-fetched accident and
   the damage is not recoverable by apologising. There is no override flag, on
   this or on `--fresh`'s refusal to drop a name not ending in `_test`, because
   the only reason to want one is the reason they exist.

2. **The workspace must be built.** `@ds/domain`, `@ds/sdk` and `@ds/eiv-client`
   are consumed through their `dist/`. `turbo` builds them for
   `test:integration`; running vitest directly does not. The symptom is the
   worst kind available — **the fix you just made does not appear, and the test
   fails exactly as before.** It cost five separate debugging detours in one
   session, each ending in "rebuild and it passes".

   The first attempt at this compared `dist/` and `src/` mtimes and was wrong in
   a way worth recording: **a turbo cache hit replays the logs and writes
   nothing**, so `dist/` keeps an older mtime than a `src/` it corresponds to
   exactly. The check reported every up-to-date package as stale. Running the
   build is a guarantee instead of a heuristic and costs 0.45 s warm — cheaper
   than the check it replaced was wrong.

3. **Leftovers must not accumulate.** Every tenant table is truncated before the
   first test.

### Two things Postgres does that the first version got wrong

**`TRUNCATE ... CASCADE` truncates the whole referencing table, not the
referencing rows.** `admin_2fa_policy` was deliberately left out of the
truncation list — migration 0027 seeds its platform row (`customer_id IS NULL`),
which is ADR-0012's strict default and not something a test created. Leaving it
out changed nothing: `admin_2fa_policy.customer_id` has a foreign key to
`customers`, so truncating `customers` emptied it completely. That is not how
`DELETE ... CASCADE` behaves.

**Re-running the migrations does not put it back.** The ledger says 0027 has
applied, so its `INSERT` never runs again. A database truncated once is
permanently missing that row unless something restores it — which is exactly how
a security default disappears without anybody deciding to remove it. `setup.ts`
re-inserts it, and the value is pinned by the `hierarchy` test asserting the
platform starts `required`.

The code already fails safe — a missing row falls back to
`DEFAULT_PLATFORM_SECOND_FACTOR` — so this was never a hole in production. It
was a hole in what the suite could tell you.

### Four tests failed the first time truncation ran

"starts the platform strict", "keeps exactly one platform row", "refuses an
operator removing their own factor", "lets a super admin read the policies".

That is the argument for truncating, not against it. They had been passing on
state a migration established weeks earlier, and nobody could have told you
which state or which migration.

### The workaround came out

`eiv-worker.integration.test.ts` no longer holds other tenants' submissions. All
eleven still pass, and now they pass because the worker does the right thing
rather than because the fixture hid the wrong thing.

### Rebuilding the development database

`pnpm db:dev:reset` drops, migrates, and seeds all three tenants — `medice`,
`ds`, `dscustomer` — through `packages/seed`, which is the code the deploy runs,
so a developer's database and a fresh installation cannot drift. All three
rather than one deliberately: the portal takes its tenant from the URL path, so
`/medice` and `/ds` are only exercisable when both exist, and a single-tenant
database hides every cross-tenant mistake by construction.

It does **not** create a staff account. `bootstrap-admin` prints a password once,
and a password printed by a script somebody ran three weeks ago is not a
credential anybody should still be using.

### CI takes a different path, on purpose

CI runs `pnpm test:integration:ci` (`turbo run test:integration`) against the
database its own named steps just created and migrated. It does not want the
developer's command: its Postgres is a fresh container discarded with the job,
its provisioning is already a sequence of steps that fail visibly, and running
`run-integration.mjs` there would create a second database and test something
other than the one the seed steps check afterwards.

### Acceptance criteria

- [x] The integration suite never writes to `ds_education`
- [x] One command runs it, with no environment variables and with vitest's
      filters intact
- [x] The workspace is built before the suites import through its `dist/`
- [x] Configuration that a migration established survives truncation
- [x] The pollution workaround is gone from `eiv-worker.integration.test.ts`
- [x] Both scripts refuse a non-local host, with no override
- [x] `pnpm db:dev:reset` takes the development database from 1 096 customers
      to 3
- [x] 372 integration tests pass, with `ds_education` untouched
- [ ] ~~Every run starts from the same state — verified by running twice
      consecutively and getting identical results~~ — **two was not enough. See
      P32-02.**

### The lesson, recorded rather than absorbed

A test suite that shares a database with the application it is testing has no
defined starting state, and every test written against it silently encodes
whatever was there that day. The failures that produces do not look like
infrastructure problems — they look like intermittent bugs in the feature you
are working on, which is why this ran for weeks before anybody counted the
customers.

The related lesson is about where the signal lives. CI was green throughout,
and CI was green _because_ it was configured well — a fresh container per run,
exactly what this ticket has now given the developer. A green CI over a local
suite nobody trusts is not a healthy project with a minor annoyance; it is a
project whose one trustworthy signal is measuring a situation nobody actually
works in.

## P32-02 · Two green runs is not evidence — **done**

- **Estimate:** 2 h · **Review gate: none** — test infrastructure only

P32-01 closed with "verified by running twice consecutively and getting
identical results". The third run failed:

```
- Expected   { "considered": 1, "submitted": 1 }
+ Received   { "considered": 2, "submitted": 1 }
```

That criterion was the wrong shape, and worth keeping in the record struck
through rather than quietly edited: **two consecutive passes cannot distinguish
"deterministic" from "the flake did not fire".** The property being claimed is
about every run, and the evidence offered was two.

### What was actually still shared

Truncating once per run fixed the _cross-run_ problem — weeks of accumulated
customers — and left the _within-run_ one untouched. Files run sequentially
(`fileParallelism: false`, for the rate-limiter reason recorded in
`vitest.integration.config.ts`), so file eleven is not racing file ten. It is
simply reading what file ten left behind.

For most suites that is harmless: they seed their own tenant and query within
it, and RLS makes other tenants invisible anyway. `eiv-worker` is the exception,
and not by accident. **`EivService.sweep` is global on purpose** — a reporting
deadline does not care whose tenant it belongs to, and a per-tenant sweep would
need something to enumerate tenants, which is precisely the design the worker
avoids. So a test asserting the sweep's tally is asserting something about the
whole database, and that assertion holds only when the database contains that
test's fixtures and nothing else.

Which file left the extra row varies — `eiv-admin` requeues a submission,
`completion-flow` and `journey` each queue one — and chasing the specific
offender would have produced a fix that lasts until the next suite queues
something.

### The fix, and the fix that was rejected

**Rejected:** weaken the assertion to `submitted: 1` and drop `considered`.
That makes the suite green and removes its ability to notice the worker
considering rows it should not — which is the entire point of a sweep test. A
test changed to stop failing is not the same as a test that passes.

**Taken:** every file starts from an empty database.
`support/reset-each-file.ts` truncates in a `setupFiles` `beforeAll`, which
vitest runs before the file's own `beforeAll`, so a suite still seeds into a
clean schema. The truncation list, the `admin_2fa_policy` restoration and the
local-host refusal moved into `support/reset.ts` so the run-level and file-level
resets are one implementation — a second list would drift, and the table it
forgot would be the one holding the row that makes a suite pass for the wrong
reason.

The local-host refusal moved **into** `resetDatabase` rather than staying with
its callers. It is the only destructive operation in the suite, and a guard on
the caller is a guard somebody can add a caller around.

### It got faster

33.7 s against 39.5 s. Truncating empty-to-small tables seventeen times costs
about half a second in total; every query in every later suite planning against
tables holding one tenant instead of eleven saves more than that.

### Acceptance criteria

- [x] Every file starts from an empty database, and the run-level reset stays
      for the case of a database somebody else left data in
- [x] One truncation implementation, used by both
- [x] The destructive operation refuses a non-local host at the operation, not
      at the caller
- [x] `eiv-worker`'s tally assertion checks the worker's claim predicate against
      an independent statement of the same predicate, rather than against the
      assumption that the database is empty
- [x] 372 tests pass on **four** consecutive runs, not two
- [x] The `\b` flake is fixed at the assertion, and the exact string that failed
      CI is verified to pass while the negative case still fails
- [x] No command truncates a database that has neither been asked to nor is
      named `_test`

### And a second flake, which was nothing to do with shared state

CI went red on a **docs-only commit** — the clearest signal available that
something was flaky rather than broken. The failure:

```
seed-default > the report > prints it when a human is looking at the terminal
AssertionError: expected 'Seeded the default DS customer.…'
                to match /\bPasswort {2}[A-Za-z0-9_-]{32}\b/
```

The report printed `Passwort  iMEZ90eY8ATKWi6aHtza4t7wMJSLVEU-`, which is a
correct 32-character base64url password. The assertion ended in `\b`, and `-`
is not a word character — between it and the end of the line there is no
boundary to match. base64url makes `-` the last character about one time in
sixty-four, so this failed roughly once every sixty runs, on a different
machine each time, with a diff showing the seed doing exactly the right thing.

Anchored to the line (`/^ {2}Passwort {2}[A-Za-z0-9_-]{32}$/m`) instead, and
recorded next to it, because the class is worth separating from the rest of
this phase: **an assertion can be flaky entirely on its own**, with no race and
no shared state — simply by being wrong about a subset of the inputs it was
always going to see.

### And then the same assertion failed again, in CI only

Per-file truncation is verifiably correct — seeding a stray queued submission
into the test database and running that suite alone proves the row is gone
before the file's fixtures are built. And yet CI failed `considered: 2` again,
twice, on a database that had just been truncated, in a run that could not be
reproduced locally after seven consecutive green runs.

**The right response to that is not another attempt to find the second row.**
It is to notice what the assertion was actually claiming. `sweep` is global, so
`considered: 1` means _"the worker claimed one row"_ **and** _"this suite is the
only thing in this database"_. The second half is a property of the harness, and
it had no business being asserted inside a test about the worker — which is
exactly why its failure was so uninformative.

The assertion now counts what the worker ought to claim, immediately before
sweeping, using `claim_due_eiv_submissions`' own predicate written out
independently from migration 0005:

```ts
const due = await countDue(now);
const result = await buildService().sweep(now);
expect(result.considered).toBe(due);
```

This is not the weakening rejected above. A worker that claims a row it should
not, or skips one it should take, still fails — that is the whole content of the
original assertion. What is gone is the accidental claim about the rest of the
database, and with it the coupling that made an unrelated row anywhere fail a
test about the sweep.

`submitted` moved the same way: the count is across every tenant, so the
suite's own outcome is asserted on its own row, where it can be attributed.

### The footgun this phase introduced, and then removed

Per-file truncation ran unconditionally in its first version. That made
`pnpm test:integration:ci` — a script in `package.json` that anybody can run —
empty whatever `DATABASE_URL` named, on the first test file, without a prompt.
Pointed at a development database that is strictly worse than the pollution
this phase set out to fix, and it would have been introduced by fixing it.

Truncation now requires `INTEGRATION_RESET=1` **or** a database whose name ends
in `_test`. `pnpm test:integration` satisfies both; CI sets the flag in the
workflow, where the Postgres is a container discarded with the job. Nothing
else truncates anything.

### The lesson

The first attempt to prove determinism produced a number — 372, twice — that
looked like evidence and was not. Repeating a flaky run twice is roughly a coin
landing heads twice: it happens constantly and it means nothing. The claim
"every run starts from the same state" is not verified by observing runs at all;
it is verified by making the starting state something the harness constructs.
Where a property can be established by construction, measuring it is the weaker
option, and it is the one that reads as rigorous.
