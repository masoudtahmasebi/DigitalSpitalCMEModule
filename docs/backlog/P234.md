# P234 — twenty fields, one click, gone

Package C's unsaved-change protection. The last of the review's list that could
be built without a decision from the client.

---

## P234-01 — nothing guarded an edit in progress

```
$ grep -rn "beforeunload" apps/admin/src
(nothing)
```

Clicking a navigation link discarded an in-progress edit. So did a reload, and
so did closing the tab. Silently, in every case.

The worst instance is `ProjectSettings` in `Organisation`: **twenty-odd fields**
including SMTP host, port, username, password, sender address and sender name,
plus the whole branding object. An operator part-way through configuring a
customer's mail who clicks **Fortbildungen** loses all of it and is told
nothing.

`QuizEditor` is the only screen that has ever mentioned this, and only as a
passive amber note beside a button — it warns, it does not guard.

## The design, and the two things it is not

**A registry, not a prop.** The thing that has to ask _"is anything unsaved?"_
is the **navigation**, which lives in `Console` and knows nothing about the
screen it is replacing. Threading a callback up from ten forms through `Shell`
would put one fact in ten places — §4 invariant 6, and §9.10b. So a form
declares its own state to `useUnsavedChanges`, and `Console` asks
`hasUnsavedChanges()` once.

A module-level `Set` rather than a React context, for two reasons: the answer is
needed inside an event handler rather than during a render, and a context read
would re-render every form whenever any other form changed.

**Edited, not different.** Dirtiness is _"has the operator touched anything
since the last successful save"_, not _"does any field differ from what was
loaded"_.

Comparing field by field would have been twenty-odd comparisons in
`ProjectSettings` alone — and a twenty-first field added later escapes the list
silently, which is §9.3's shape in the thing built to prevent a defect. One
`onChange` on the container catches every control, including any added after it
was written, because React's synthetic `change` bubbles.

The cost is exactly one false positive: typing something and then typing it
back leaves the form "dirty". **That is the safe direction.** A warning about a
loss that is not happening costs a click; a missing warning costs the work.

### Why `window.confirm`, which is ugly

It is the browser's own modal: focus-trapped, announced, dismissable with
Escape, keyboard-operable, in the operator's own language for the OS chrome —
all without a line being written here. This console has no dialog primitive with
those properties, and a hand-rolled one on day one would have fewer of them. A
designed replacement is named below as not done rather than implied.

### And the half no router can see

`beforeunload`, registered only while a form is dirty and removed when it saves.
The text is the browser's own: every engine ignores whatever a page supplies, so
`preventDefault()` is the entire API and writing copy for it would be copy
nobody ever reads.

## The two halves, tested separately, because they never meet

`hooks.unsaved.test.tsx` — a form can **declare**. Six cases: quiet by default,
reports, forgets on save, forgets on unmount, counts two forms separately
(the Organisation screen has a department editor and a project editor open at
once), registers and removes the `beforeunload` listener.

`App.test.tsx` — the console **asks**. Three cases: declining leaves the screen
where it was, accepting navigates, and a clean screen is never asked about.

Both are needed and neither is sufficient. Without the second, the registry
could be perfect and every sidebar link could go on discarding work with both
suites green — §9.7, and the exact shape §9.3 keeps catching here
(`inviteStatus`, `resetStatus`, `invalidBrandingFields`, each exported,
exhaustively tested, called from nowhere).

`CopySettings.test.tsx` gets a third: a **real screen** registers when a field
is typed in. The hook working and a screen calling it are still two claims.

### Watched red

| Sabotage                                     | Result                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| the navigation stops asking                  | _"the console navigated without asking, so an in-progress edit was discarded silently"_                                   |
| the registry never forgets an unmounted form | _"an unmounted form is still registered, so every navigation from now on asks about edits that no longer exist anywhere"_ |
| a container stops listening for changes      | _"typing into a settings field left the registry empty"_                                                                  |

## The defect this ticket's own tests had first

Two of the three navigation cases failed, and **one of the two failures was
fictional**.

`confirm.mockRestore()` at the end of a test body never runs when the test fails
before reaching it. So the second case failing left `window.confirm` stubbed
with a call count of 1, and the third case then reported _"the console asked
about unsaved changes on a screen with none"_ — a defect that did not exist,
described convincingly.

§9.8, in the file written to fix a different §9.8: **reset every ambient store
in `afterEach`, not only the one that broke.** `vi.restoreAllMocks()` in
`afterEach` rather than a restore at the end of each body. The real second
failure was mundane: "Teilnehmende" is both the nav label and the page title, so
`getByText` matched two nodes.

## P234-02 — every screen, and a check that keeps it that way

The first pass covered six forms and deferred three. **That was a partial
guard, and a partial guard has a real cost** — it teaches the operator that the
console warns them, and then one day it does not (§9.2). So it was finished
rather than shipped as a decision for somebody else to make.

### The three editors turned out to be the easy ones

`QuizEditor`, `EvaluationEditor` and `ExpertsEditor` each hold
`draft: T[] | undefined`, where `undefined` means _"rendering the server's
document"_. **`draft !== undefined` already is the answer** — so they need no
`onChange` and no second flag, and a second source for the same fact would be
§4 invariant 6, drifting the first time somebody cleared one and not the other.
One line each. `QuizEditor`'s existing unsaved-changes note is conditioned on
the identical expression.

### And then the check found three more nobody had looked at

Comparing every `useSaver` caller against every `useUnsavedChanges` caller —
which is what `scripts/check-unsaved-guard.mjs` does — turned up screens the
eye had passed over:

| Screen            | What was at risk                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `NewCourse`       | **a whole creation form** — title, slug, description, delivery type, none of which exists anywhere until it is submitted |
| `Learners`        | an open name correction — and that field goes on a Teilnahmebescheinigung                                                |
| `CourseStructure` | three inline editors, each renaming or editing a node                                                                    |

`CourseStructure`'s three register under **separate keys**, because several can
be open at once in one tree and closing one must not clear another's flag.

### The rule, and why `useSaver` is the right trigger

> Every component that calls `useSaver` calls `useUnsavedChanges`, or is named
> in `NOTHING_TO_LOSE` with the reason it cannot hold an edit.

`useSaver` means _"this component performs a write"_, which is exactly the
population that can hold an unwritten one. It is not a perfect proxy — a form
could hand-roll its save — and `check:savers` refuses that separately, so
between the two there is no way to add a saving screen that guards neither its
control nor its draft.

**The exemption list is two entries and both mean "nothing to lose", never "not
done yet".** `Security` saves on change, so there is never a pending draft;
`EivCheck` runs a connection test whose password is never stored, so losing it
costs retyping rather than losing. A list that mixes _correct_ with _pending_ is
the mute button P225's `ANSWERS_WITH_NOT_FOUND` and P230's
`COVERED_DIFFERENTLY` were each written to avoid, and the way it starts is one
entry meaning "later".

Both of the check's rules watched red:

| Sabotage                    | Reported                                                                                                 |
| --------------------------- | -------------------------------------------------------------------------------------------------------- |
| `NewCourse` drops its guard | _"calls `useSaver` and never `useUnsavedChanges`, so an edit in progress … is discarded without a word"_ |
| an exemption nobody needs   | _"but it does not call `useSaver`, or it now guards itself. Remove the entry."_                          |

### Final coverage

**Nine components call `useSaver`; seven guard an edit in progress and two
cannot hold one.** With the five settings forms that do not use `useSaver`,
**twelve screens hold unsaved work and every one of them declares it.** The
check fails if the thirteenth arrives without deciding which it is.

## What is still open in Package C

- **A designed confirmation dialog** to replace `window.confirm`.
- **Focus handling after errors and dialogs.**
- **Retry that preserves input** for a refused mutation.
- **429 with a wait time** — the API sends no `Retry-After` (§11.4).
- **`useSaver`'s `validating`**, which still has nothing that sets it.

## Acceptance criteria

- [x] The absence of any guard established by command
- [x] One registry, asked once by the navigation, declared by each form
- [x] Dirtiness by edit rather than by comparison, with the false positive named
- [x] `beforeunload` for the half no router sees
- [x] Both halves tested separately, plus a real screen proving the wiring
- [x] Three sabotages, each red on the property it is for
- [x] The test file's own leaked-spy defect found, named, and fixed at the class
- [x] Every form's adoption stated — including the two that correctly have none
- [x] The partial guard finished rather than left as somebody else's decision
- [x] A check making the rule universal, with both its rules watched red
- [x] Three further screens found by that check and adopted
