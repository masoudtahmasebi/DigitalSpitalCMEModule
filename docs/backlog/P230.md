# P230 — the button that stayed live, on three writes that change a person's record

The review's **Package B**:

> **Reusable operation feedback** — `idle → validating → submitting → success →
retryable error → permanent error`, with success announced only after server
> confirmation.

The hook already exists. What did not exist is any reason for half the console
to use it, and the drift its own header predicted had happened.

---

## P230-01 — "So it lives here once" was not true, and that sentence is why

`apps/admin/src/hooks.ts` has said since **P9-02**:

> Written out per screen that is six copies of the same
> `setBusy(true) / try / catch / finally` — and the copies drift: one forgets to
> clear the previous error, **one leaves the button enabled during the request
> and double-submits**, one shows "gespeichert" after a failure. So it lives
> here once.

It did not. **Seven components used `useSaver`; six hand-rolled the triplet.**
The prediction came true, and the last sentence is why nobody checked — §11.9,
a comment is a claim rather than a fact, and a comment asserting completeness
is the strongest kind of claim there is.

### The three that were real

| Handler            | Surface  | What a second request does                                                                                                                                     |
| ------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Learners.correct` | records  | a second `learner.name_corrected` row in an **append-only** audit log, so one correction reads as two                                                          |
| `Learners.erase`   | GDPR     | Art. 17 erasure: the second finds no enrolment and 404s, so the screen reports a **failure for an erasure that succeeded**, beside a row that has already gone |
| `Security.save`    | **auth** | two second-factor policies in flight at once, and **network ordering decides which one wins** rather than what the operator chose last                         |

`Learners.correct` had no in-flight state of any kind, while its sibling
`requeue()` ten lines below sets one — the drift, in one file.

`Security.save` is not a button at all: the policy is set from a `PolicyRow`'s
`onChange`, so nothing ever looked like a submit to guard. That is why it
lasted.

### Demonstrated, not argued

`Learners.test.tsx` clicks Speichern three times against a request that has not
resolved, and reported on the shipped code:

```
AssertionError: Speichern stayed live during the request, so one correction
reached the API 3 times — and every one of them writes its own
`learner.name_corrected` entry into the append-only audit log:
expected 3 to be 1
```

and on the erasure path:

```
AssertionError: the confirmation stayed live during the request, so an
irreversible Art. 17 erasure was requested 2 times — and the second finds no
enrolment, so the screen reports a failure for an erasure that succeeded:
expected 2 to be 1
```

The client in both is one whose promise **never resolves until the test says
so**. A promise that resolved immediately would close the window before the
second click and the test would pass on the broken code — §9.1, and §11.10's
"test under the condition that actually occurs" in a component.

Both green after the fix. Both watched red again afterwards by restoring the
old handler, so the tests are not merely passing.

### `useSaver` gained one thing

A per-screen `fallback`. The hook always used `de.error.generic`, and the
handlers it replaces used sentences of their own — a refused name correction
falls back to "Die Änderung konnte nicht gespeichert werden", which at least
names what failed. It remains a **fallback**: where the API wrote a `detail` —
a 409 explaining that the Punktemeldung has gone and what to do instead — that
sentence still wins.

## P230-02 — two of five reports were false, and catching that is the point

`scripts/check-savers.mjs`' first draft reported **five** handlers. Two were
**wrong**:

| Reported             | Actually                                                                       |
| -------------------- | ------------------------------------------------------------------------------ |
| `Security.removeOwn` | behind `ConfirmButton`, which calls `setArmed(false)` **before** `onConfirm()` |
| `Customers.remove`   | same                                                                           |

The confirm button leaves the tree on the first click, and React flushes a
click synchronously, so it has re-rendered before a second click is dispatched.
The two-step confirm **is** the guard.

Two in five is the rate at which a checker stops being read — P227-01 taught
exactly this with three false accessible-name findings — and `removeOwn` was
nearly "fixed" before the call site was checked. That would have been a change
with no defect behind it, asserted in a commit message as a fix. The change was
made and then **reverted**, and the reason it is not a defect is now a comment
at the handler so the next reader does not repeat it.

### And the exemption's own first version was also wrong

It asked "is there a `<ConfirmButton` within 400 characters behind the call
site" — a window that works on the file it was written against and nowhere
else. `Customers.tsx` puts eleven lines of props between the tag and
`onConfirm`, the window missed it, and the checker reported a correctly-guarded
handler: **the same false positive the exemption had just been added to
prevent.**

The element is matched properly now — from `<ConfirmButton` to the `>` that
closes its opening tag, tracking brace depth so a `>` inside `{a > b}` does not
end it early.

The exemption is narrow on purpose: a handler is exempt only if **every** call
site reaching it is a `ConfirmButton`'s `onConfirm`. One guarded call site and
one bare `<Button onClick>` is still reported — which is exactly
`Learners.erase`, a plain button inside a hand-rolled two-step.

A handler with **no** call site this parser can see is also not exempt: a
handler reached some way the check cannot follow is a handler nobody has
checked.

## What this ticket does not do

- **It does not build the six-state machine the review named.**
  `useSaver` is `idle → saving → saved` with a problem string. `validating` and
  the retryable/permanent split belong with Package C's error layer, which
  decides what an error _is_; adding the states here without that would be
  three enum members nothing sets.
- **It does not convert the remaining hand-rolled screens.**
  `CopySettings`, `CourseSettings`, `BrandingSettings`, `PlatformEiv` and
  `CoursePresentation` each guard their control correctly — `check:savers` is
  green on all of them — so converting them is tidiness against an unreviewed
  console, and tidiness is what would hide the next real one in the diff.
- **It does not address the server-side race.** Two concurrent corrections both
  read the enrolment's stage before either writes, so both can pass the
  "already submitted to EIV" conflict check. That is a time-of-check/
  time-of-use question that exists whatever the button does. **Named rather
  than absorbed**, and not fixed here.
- **`BrandingSettings.clear()`** succeeds and announces nothing — there is a
  `de.branding.saved` and no `removed`. The form visibly changes, so it is not
  silent, and it is a copy question rather than a defect. Recorded.

## P230-03 — what a disabled button is, and what it is not

The review's central correction, and it is the one that decides how this ticket
should be read:

> **Client-side single-flight is not idempotency.** … two tabs, two admins, lost
> responses, direct API calls.

Correct, and this ticket must not be mistaken for having fixed the server-side
problem underneath it. Every one of those four goes straight past a disabled
control, because the control is in one browser tab's React state:

| Case                                                           | What this ticket does about it                            |
| -------------------------------------------------------------- | --------------------------------------------------------- |
| Two browser tabs, same operator                                | **nothing**                                               |
| Two operators on the same record                               | **nothing**                                               |
| A lost response — the write succeeded, the reply never arrived | **nothing**; the operator sees an error and presses again |
| A direct API call                                              | **nothing**; there is no button                           |

**`docs/backlog/P235.md` is the work order for the server side**, and it is
where the idempotency keys, the safe-to-repeat erasure, the concurrency control
and the lost-response compliance risk are specified.

It was written as `P231.md` and renumbered before it was pushed anywhere:
**PR #78 already holds P231** for Package C's error layer, on a branch further
down this same stack. Two tickets sharing a number is precisely the thing
CLAUDE.md §10 warns about one level up — "two numbering schemes sharing one
prefix is exactly the kind of thing that reads as correct for a year" — and
`check:backlog` cannot see it, because it only asserts that a heading matches
its own filename and both files would have passed on their own branches. Caught
by listing `docs/backlog/` across every branch of the stack before claiming the
number, which is now the thing to do rather than incrementing the highest number
on the branch in front of you. This ticket is a
console-side guard on three controls and is worth having on its own terms — a
double-click is the common case and now cannot happen — but it is the cheap half
of the problem.

### The wording on the pull request was also wrong

It said _"no server behaviour changes"_, which is true and is the wrong thing to
be reassured by: it reads as "nothing about the server is at issue here". The
accurate sentence, which the review supplied and the PR now carries:

> No server-side implementation or API-contract changes. The PR changes
> client-side operation guarding and feedback behaviour on auth- and
> GDPR-sensitive screens.

### The auth screen's all-scopes disable, now observed

> "In practice" is not strong enough for an auth surface.

Also correct. The claim was that the three `PolicyRow`s are disabled together
while any policy request is open, and it was a sentence in a PR body. It is now
a test in `Security.test.tsx`, driven with a client whose promise does not
resolve until the test allows it — §11.10, because a promise that resolved
immediately would close the window before the second interaction and the test
would pass on the unguarded code.

Three properties, and the second is the security one:

1. every scope becomes read-only while any policy request is open, not only the
   one being changed — `PolicyRow` renders a `<p>` instead of a `<select>`, so
   the observation is "the combobox is gone", which is what a person sees;
2. **no second policy request is dispatched** while the first is open. Before
   this, the control was a `<select onChange>` — nothing about it looked like a
   submit, nothing guarded it, and two policies in flight meant network ordering
   decided which stuck rather than what the operator chose last;
3. the rows come back when the request settles, or the screen is bricked.

Sabotaged by restoring the shipped handler — a bare `try/await/catch` in place
of `saver.run` — which gives:

```
AssertionError: the scope being changed stayed editable during its own request:
expected 'select' not to be 'select'
Tests  1 failed | 12 passed (13)
```

Restored: 13 passed.

### The erasure confirmation flow, confirmed

Asked for by the review, and worth writing down because the answer is _not_ a
`ConfirmButton` and that is why it needed the guard at all:

1. **Löschen** on a row sets `erasing` to that enrolment id. Nothing is sent.
2. The row becomes a **Grund** field (`TextInput`, `maxLength` 200) with its own
   hint, plus **Endgültig löschen** (`variant="danger"`) and **Abbrechen**.
3. **Endgültig löschen** is `disabled` while `eraser.state === "saving"` **and**
   while `reason.trim() === ""` — so an erasure cannot be requested without a
   reason, which is what goes into the audit trail.
4. On success the confirm collapses, the reason clears and the list reloads. On
   failure the row stays open with `eraser.problem` beneath it.
5. **Abbrechen** calls `eraser.reset()` before closing, so a previous failure's
   sentence does not reappear when the row is opened again.

The reason it is a hand-built two-step rather than a `ConfirmButton`: it has a
required text field in the middle, which `ConfirmButton` has no place for. That
is also why the `ConfirmButton` exemption in `check:savers` does not cover it,
and why it was one of the three real findings.

### Scope boundary with PR #78

No overlap, and they touch different files:

|            | #77 (this ticket, P230)                                                | #78                                          |
| ---------- | ---------------------------------------------------------------------- | -------------------------------------------- |
| Question   | **whether a write is dispatched twice**                                | **what the operator is told when one fails** |
| Files      | `Learners.tsx`, `Security.tsx`, `hooks.ts`, `scripts/check-savers.mjs` | the error-description layer                  |
| Dependency | none on #78                                                            | none on #77                                  |

The one place they meet is `useSaver`'s new per-screen `fallback`: this ticket
added it so a converted handler keeps the sentence it had, and #78 changes what
a _failure_ is described as. A fallback is what is used when the API supplied no
`detail`, so #78 narrowing when that happens does not change any behaviour
introduced here.

## A cross-branch note — now resolved rather than predicted (P230-04)

`check:savers` is registered in `pnpm verify` the way its siblings are. **P229
moves that list into `pnpm check:static`**, which is the only thing CI runs — so
when P229 and this both land, `check:savers` has to move into `check:static` or
it is a gate that cannot stop a merge, which is the defect P229 exists for.

The previous version of this paragraph said _"`check:ci-parity` fails if it is
forgotten, which is the point of it"_ and stopped there. The review would not
merge on that, correctly: it is a prediction about a merge nobody has performed.
So the merge was performed, in a throwaway worktree, and both states measured.

**The naive merge** — P229's `check:static` plus this ticket's `check:savers`
still in `verify`:

```
check-ci-parity: 1 problem(s)

  `pnpm check:savers` is a step of `pnpm verify` that no workflow runs, so it
  cannot stop a merge. Put it inside `pnpm check:static`, name it in a
  workflow, or add it to COVERED_DIFFERENTLY with the step that covers it.
exit=1
```

**The resolution** — move `check:savers` into `check:static` and out of
`verify`:

```
check-ci-parity: 10 verify step(s), of which 22 are inside `check:static` and
run by 2 workflow(s); 1 covered under another name, none unreachable from a
merge gate.
exit=0
```

So the answer is not "a check will tell us". It is: **`check:savers` goes inside
`check:static`, before the `check:ci-parity` entry, and comes out of `verify`.**
One line, verified both ways.

### And it is four checks, not one

P229 branched from `main`, so its `check:static` list contains **none** of the
four checks this redesign stack introduces:

| Check                 | Introduced by | In P229's `check:static`? |
| --------------------- | ------------- | ------------------------- |
| `check:aria-props`    | P223 / PR #71 | **no**                    |
| `check:screen-intros` | P227 / PR #74 | **no**                    |
| `check:design-tokens` | P228 / PR #75 | **no**                    |
| `check:savers`        | P230 / PR #77 | **no**                    |

None of the four is even _defined_ as a script on P229's branch, which is why
its own header can list them among the fifteen it found while its `check:static`
does not run them. Each one needs the same one-line move when it meets P229, and
`check:ci-parity` names each one it is missing — but the merge order decides who
does the moving, and nobody had written that down.
