# P35 · A browser suite, and what a closed shadow root means for one

> can you also write playwright tests that actually test the system?

---

## The deviation, stated first

`CLAUDE.md` §6 says: _"Full E2E is not in this budget; do not build a Playwright
suite unless a ticket asks for it."_ A ticket now asks for it, on an explicit
client instruction. This is that deviation, recorded rather than absorbed — the

## P35-01 · `pnpm test:e2e` — **done**

- **Estimate:** 6 h · **Review gate: none** — no production code changed

One command builds the workspace, rebuilds `ds_education_e2e`, seeds the DS
tenant through `@ds/seed`, starts the API and serves both frontends from their
**built `dist/`**, then drives Chromium against them. Nine specs, ~15 s once
built.

Built output rather than dev servers, because a Vite dev server transpiles on
demand and reloads on its own schedule — and in a browser test "the page was
mid-reload" and "the feature is broken" look identical. The bytes Playwright
drives are the bytes the container serves.

### The finding that shaped the suite

`<ds-lms>` attaches its shadow root with **`mode: "closed"`**, deliberately: the
widget renders inside a customer's WordPress page and must not be reachable by
that page's scripts or styles.

**Playwright cannot pierce a closed shadow root.** Its selector engine handles
open ones and stops at closed. So on a screen full of visible German text,
`getByText`, `getByRole` and `toContainText` all see an empty `<main>` — which
is exactly what the first version of the learner spec hit, and what cost two
debugging rounds to recognise as the harness's limit rather than a broken page.

**The root is not being opened for the tests.** The isolation is the feature,
and a product weakened to make a test possible is a trade that outlives the
test. The division of labour instead:

| Surface                                    | Tested by                                                       |
| ------------------------------------------ | --------------------------------------------------------------- |
| Inside the widget — gating, status, player | component tests in `apps/widget` (§6 already assigns them this) |
| Tenant routing, sign-in, session, sign-out | this suite                                                      |
| The **seam** between portal and widget     | this suite, and nothing else can                                |

That last row is the one worth having. The widget's own source records what a
bad mount looks like: a "nicht korrekt eingebunden" message rendered _inside the
closed root_ — invisible to `innerText`, invisible in a screenshot, "accompanied
by no failed request, because a widget that has decided it is misconfigured
never calls the API. That is how /medice came to show a signed-in header above
nothing at all." A closed root means that message cannot be asserted on. Its
**inputs** can, and its **network traffic** can — so the suite asserts the
element is upgraded, carries the right `project` and `api-base`, and that a
request for a catalogue actually leaves the browser.

### Three real defects the harness found on its first runs

1. **`CORS_ALLOWED_ORIGINS` is not the variable the API reads.** It is
   `ALLOWED_ORIGINS`; the former is what the compose file happens to call it.
   Nothing errored: the API booted, `/tenants/ds` answered correctly to `curl`,
   and the browser showed **"Diesen Bereich gibt es nicht"** — because the
   response was blocked before the portal could read it, and a failed lookup is
   indistinguishable from an unknown tenant. Every API test passed while a
   physician would have been told their employer does not exist. That single bug
   is the argument for the suite.
2. **`PORT` is not the variable either** — `API_PORT`. The API started happily
   and listened on 3000 while the harness waited on 3100.
3. **The sign-in rate limiter is real and the suite must not fight it.** Five
   attempts per IP per minute, and every test arrives from 127.0.0.1. Rather
   than keeping the suite under five sign-ins — a constraint the sixth test
   would silently break — it resets the counter before each, and says why: the
   limiter's _refusal_ is asserted in the API suites, where it belongs.

### Acceptance criteria

- [x] One command, no environment variables, from a clean checkout
- [x] Its own database, seeded by the code the deploy runs
- [x] The browser the image already ships — nothing downloads a second Chromium
- [x] Serial, one worker: the suite shares a database and a participant account
- [x] Traces and screenshots on failure only, and git-ignored
- [x] 9 specs green

### Deliberately not done

**No admin-console specs yet.** Signing a staff account in through a browser
needs the bootstrap password parsed out of a CLI's stdout and the platform
second-factor policy relaxed for the E2E database. Both are doable; neither is
free, and the second narrows what the test proves. The console's behaviour is
covered by `hierarchy`, `authoring` and `moderation` against a real Postgres.

**No CI job.** The suite builds the whole workspace and boots four processes; it
belongs in CI once it has a few weeks of local runs behind it and its flake rate
is known. Adding a slow, unproven job to a pipeline people trust is how a
pipeline stops being trusted — P32 is the record of what that costs.
