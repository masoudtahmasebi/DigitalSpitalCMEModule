# P225 — the admin console redesign, PR C: the toast that followed you, and a rule nobody applied

The third of the three pull requests `docs/backlog/P219.md` sequences, and like
A and B **not to be merged or deployed by this session**.

It covers slices 6, 8 and 9 — organisation, participation and the settings
screens — and the thing worth reading first is that **two of its three findings
are defects, not decoration**, and both were found the same way: by signing into
the running console through the e2e rig, walking every screen, and looking.

---

## P225-01 — "Bitte versuchen Sie es später erneut" on every screen after Erscheinungsbild

The worst defect in this PR, and it has been shipping for as long as both its
halves have existed.

**Reproduced** by driving the console with a response listener attached. Opening
**Erscheinungsbild** raises

```
Bitte versuchen Sie es später erneut. (Referenz: fc901aac-6f47-46f4-8eb2-07f91bf60360)
```

and the toast then appears on **Texte**, **Sicherheit** and **Mediathek** as
well — the same reference id each time, which is what said it was one event
followed across four screens rather than four events.

The only failing request is `404 GET /admin/branding/font`.

### Two correct changes, layered

- **P22-08** found exactly this sentence on the screen of every customer who had
  simply not uploaded a font, and fixed it: `BrandingSettings` catches the 404
  and renders an empty upload form. **That fix is still there and still right.**
- **P205-01** then added a blanket net in `api.ts` — a `Proxy` that toasts every
  rejected request except 401 and 403 — so that no failure could be silent. It
  cannot know that this particular rejection is an _answer_, so it announced it,
  **before** the component's own handler ran, into a toast the component does
  not own and cannot clear.

`GET /admin/branding/font` 404s **deliberately**: _"there is no font"_ and
_"there is no project"_ are the same answer on purpose, because a font must not
be evidence that a tenant exists (§9.5, and `branding.controller.ts` says so).
Having no custom font is the normal state of every customer who has not uploaded
one — which, today, is all of them.

It is §9.4 twice over: the sentence is **advice**, and the advice is wrong.
Trying again later will 404 for ever.

### The fix

`ANSWERS_WITH_NOT_FOUND` — a table of calls whose 404 is an answer, keyed by SDK
method name, currently one entry, each entry carrying the sentence that says
why.

**Not "skip every 404".** A 404 is usually exactly what it says: a course opened
from a stale link, a participant deleted in another tab. Those must still be
announced, and they are why the net exists. What is special here is the
**route**, not the status.

The rule moved out of the `Proxy` into an exported `announceable(method,
status)`, so the question "does a font 404 raise a toast?" can be asked without a
browser and a signed-in console. Five cases in the new `api.test.ts`; the one
that matters fails on the previous rule:

```
× stays quiet about the font that was never uploaded
  AssertionError: expected true to be false
```

And re-driven in the browser afterwards: the toast is gone from Erscheinungsbild
and from the three screens it used to follow onto.

## P225-02 — form fields were never capped, and a comment said they were

`Shell`'s own header has claimed since **P100-01**:

> P100-01 capped the things that should be capped: prose at `max-w-3xl`, form
> fields at `max-w-2xl`, each where it is rendered.

Prose was capped. **Fields were not** — `max-w-2xl` appears in exactly one
component in the whole console, and it is not a form field. So the rule was
written, read as done, and never applied (§9.3), and §11.9 is why it survived
nine phases: the comment asserting it is the reason nobody looked.

What it costs is visible on **Konten**, where **Name** and **E-Mail-Adresse**
are **1,100 px-wide** text inputs. A field that wide is harder to use, not
easier: the label is at one end of the screen and the caret at the other.

The cap belongs in `Field`, not at 109 call sites — the same reasoning `Table`
already gives for cell padding (P133-02: _"cell padding belongs to the table, not
to fifty call sites"_). `wide` opts out for the fields that genuinely want the
room, and it is opt-**in** because the default being wrong is how this happened.

The copy editor's inputs are untouched: they do not go through `Field`, and
editing a paragraph of German body copy is the case `wide` exists for.

## P225-03 — two screens printed their own sentence twice

**Texte** and **Plattform-EIV** rendered their intro paragraph immediately below
the identical paragraph `Page` draws from the nav table. The same sentence,
twice, one under the other.

Nothing caught it and nothing could have: both halves are individually correct.
It is §9.10b — one value, two homes — and `Section`'s own documentation already
says which home is right: _"the page chrome belongs to the destination, not to
the component that happens to fill it."_

`node scripts/screen-intros.mjs`, in `pnpm verify`, is the class. It reads the
thirteen `description:` keys out of the nav table and fails if a component
renders one. Re-introducing the duplicate:

```
screen-intros: a screen draws its own sentence twice
  …/PlatformEiv.tsx:102: renders de.platform.intro, which is already this
    screen's nav `description` — `Page` draws it under the title, so it
    appears twice.
```

### And the checker's own defect, for the second time in one change

Its first version flagged `CopySettings.tsx` — for a hit inside **the comment
explaining why the paragraph had been deleted**. That is the `check-deadlines`
defect from CLAUDE.md §11 (_"It was matching prose in doc comments"_), and
`scripts/aria-props.mjs` had been fixed for exactly it an hour earlier.

Twice in an afternoon makes it a shape rather than a slip, and it is written
down in both scripts now: **a checker that greps source is reading the
explanation as well as the code, and the explanation is where the thing being
banned is most likely to be named.** Strip comments first, always.

## P225-04 — the accounts table's row actions

Three bordered buttons and one quiet one did not fit the cell, so every row of
**Konten** wrapped to two lines. P224-01 introduced `quiet` for exactly this and
scoped itself to the authoring tree; these three were missed.

**Überall abmelden**, **Passwort setzen** and **Aktivieren** are quiet now.
`secondary` survives on this screen in the two places it is right: the
invitation notice's copy button, and the cancel inside the password dialog.
Distinguishing those needed reading each call site, which is why there is no
blanket sweep here.

**Honestly: this is better, not fixed.** With three actions the cell still wraps
at 1440 px — it is quiet text wrapping now rather than three bordered boxes, and
the table reads as a table. The real answer is an overflow menu for secondary row
actions, which is a new interaction pattern and deliberately not introduced in a
PR nobody has reviewed yet.

## P225-05 — a refusal answered with advice to retry

Found by working through the error matrix the review asked for, and it is the
**same defect as P225-01 on the other channel**.

`describeError` is the sentence every _inline_ error channel in the console
renders, and its 403 branch read:

```ts
const sentence = isForbidden(error) ? generic : (problemDetail(error) ?? generic);
```

`generic` is `de.error.generic` at every call site — _"Bitte versuchen Sie es
später erneut."_ So an operator who did something their role does not permit was
told to **try again later**, and retrying a refusal refuses for ever. §9.4: the
sentence is advice, and the advice is wrong.

It reached every inline channel, because all of them call this function. The
most visible is a refused action on the courses screen (`setActionProblem`),
which keeps the table on screen and puts the sentence above it.

**The reason a 403 does not carry the API's own `detail` is unchanged and still
right**: that text is written for a developer reading a log, and naming the
missing role tells an operator more than they need in order to act. What changes
is the substitute — `de.error.forbidden`, _"Ihr Konto hat keine Berechtigung für
diese Aktion. Bitte wenden Sie sich an Ihre Administration."_

Deliberately **not** `auth.forbidden`, which says _"keine Berechtigung für die
Verwaltung"_ and is the right words for being refused the console itself. This
one is about a single action inside a console the operator is legitimately in.

### The matrix, as tests

`api.test.ts` now pins both rules — which channel speaks, and what it says:

| Scenario                          | Toast | Inline sentence                     |
| --------------------------------- | ----- | ----------------------------------- |
| font 404                          | no    | the screen's own unconfigured state |
| font 500 / 503 / 422              | yes   | actionable                          |
| any other 404                     | yes   | the API's own detail                |
| 409                               | yes   | the API's own detail                |
| timeout / offline (**no status**) | yes   | retryable — correct here            |
| 401                               | no    | session recovery, by routing        |
| 403                               | no    | permission, **no retry advice**     |

Two of those are guarantees rather than examples, and both were asked for:

- **Nothing else is exempt.** Six other methods' 404s are asserted still
  announced, so the exemption table cannot quietly become a mute button — and
  there is no option, flag or argument a call site can pass to suppress a class
  of errors.
- **The two channels never both announce the same refusal.** A 403 is already a
  complete sentence on screen; a toast as well would be pure noise. The two
  rules have to agree, and nothing but that test makes them.

Three cases fail on the previous rules — the font toast, the retry advice, and
the two-channel agreement.

### What the matrix recorded rather than changed — and is not an endorsement

For a **5xx the toast and an inline channel both speak**, so an operator sees
the same failure twice.

The previous version of this section called that "deliberate design" and moved
on. The review corrected it, and the correction is right: _deliberate_ is the
history of the decision, not an argument that it is good. Both halves are true
and the second matters more:

- **Why it is the way it is.** P205-01 made the toast a floor under 48
  hand-written channels, so that a screen showing nothing is no longer silent.
  It cannot know whether the screen under it also spoke, because the screens do
  not tell it.
- **What it costs.** Two messages for one event, in two places, one of which
  outlives the screen — and the inline one is the better of the two, because it
  is beside the control that failed. There is an argument that the floor should
  yield whenever an inline channel has spoken, and this design does not make
  that possible: the toast fires from the `Proxy` **before** the component's own
  `catch` runs, so at the moment it decides, there is nothing to yield to.

**So it is an open question, not a settled one.** It is unchanged here because
changing it means giving the floor a way to know what the screen did, which is
a different design and a different ticket — not because the current behaviour
has been judged correct. The 403 is the one case where the two rules were made
to agree, and that was a defect fix rather than the general answer.

## P225-06 — the field cap, checked against the cases that want width

The review asked for the cap to be checked against long German copy, multiline
inputs, colour controls, dense rows and mobile rather than inspected on one
screen. Doing that changed the answer in one place.

**The five `Field`s that wrap a `TextArea` now pass `wide`** — the course's
Thema list, the evaluation prompt, a speaker's biography, the catalogue intro
and a quiz prompt. The defect that was found and measured was _single-line_
inputs at 1,100 px; a multiline prose field is a different case that has **not**
been measured, and the conservative action is to leave its width exactly as it
was rather than change it on a hunch.

**The copy editor is untouched and cannot be affected**: `grep -c "<Field"
src/components/CopySettings.tsx` returns **0** — it renders its own inputs, so
the cap never reaches it. That is now asserted rather than inferred from a
screenshot, and `Field`'s opt-out has its own test.

## P225-08 / P225-09 — the 403 verified where the review asked, and the allowlist read as a boundary

### P225-08 — every screen, and both locales

P225-05 changed one branch of one function and the sentence that followed it —
_"this reaches every inline error channel in the console, because all of them
call this function"_ — was asserted by nothing. The console also ships in two
languages, and `overlay` answers a missing key with the German string, so a fix
that is right in German and untranslated in English renders German on an English
console **and no check says so** (§9.1: a fallback that hides its own absence).

Three tests in `api.test.ts`, each watched to go red:

| Property                                                               | Sabotage                                                 | Result                                                                                                |
| ---------------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| the 403 reads the table's string, not a literal                        | 403 branch back to `generic`                             | **4 failed**                                                                                          |
| the sentence is English on an English console, not the German fallback | `error.forbidden` deleted from `en.ts`                   | **1 failed**: _expected 'Ihr Konto hat keine Berechtigung …' to be 'Your account is not permitted …'_ |
| no screen invented its own wording for a screen-level refusal          | one screen's `de.auth.forbidden` replaced with a literal | **1 failed**, naming the file                                                                         |

**The second sabotage is the one worth keeping.** With `error.forbidden` removed
from the English table, `pnpm check:i18n` reports **936/937 strings (99 %)** —
and it fails below **95 %**, so it stays **green**. The coverage gate cannot
catch a single missing key, and a single missing key here is a refusal rendered
in the wrong language. Verified by running it in both states.

**The boundary the third test draws.** Two refusals, two scopes:
`describeError` answers a refused **action** inside a screen the operator is
legitimately in (`de.error.forbidden`); seven screens — Certificates, Learners,
EivQueue, PlatformEiv, Customers, StaffAccounts and the course workspace in
`App.tsx` — additionally catch a 403 on their **mount-time read** and replace
themselves with `de.auth.forbidden`. All seven agree, which is not observable
from any one of them, so it is asserted by reading the sources.

**One thing corrected while verifying, and it is §11.9.** `describeError`'s own
header still read _"A 403 gets the generic line on purpose"_ — true before
P225-05, false after it, and left standing when the branch changed. A stale
comment is worse than none, because it is the reason the next person does not
read the code under it. Rewritten to say what is still true: a 403 does not
carry the API's own `detail`, because that text is written for a developer
reading a log.

### P225-09 — `ANSWERS_WITH_NOT_FOUND` as a boundary

The review asked for the expected-404 allowlist to be reviewed as a security
boundary. It has two halves and the second is the one with teeth.

**What it is.** It suppresses **a toast**. It is not an authorisation decision,
it never reaches the API, and it cannot make any request succeed that would
otherwise fail. An entry can only make the console _quieter_, never more
permissive — so the risk it carries is masking a real failure, and the failure
mode to guard against is an entry added for a route whose 404 is actually a
refusal. That matters more here than it would elsewhere because of §9.6: on a
tenant-scoped table, an RLS-hidden row and an absent row are the same 404, so a
future entry for such a route would turn "you are looking at the wrong tenant"
into silence. Which is why the table is keyed by **route**, is one entry long,
and every entry carries the sentence saying why.

**What actually keeps it safe, and was untested.** The error is **re-thrown
unconditionally** — suppression changes what is announced and never what is
thrown, so every component's own `catch` behaves exactly as before. Now driven
through the real client with `fetch` stubbed to a 404: the call must still
reject with the status intact, or `BrandingSettings` never renders its empty
upload form and the screen shows stale data with no message at all, which is
strictly worse than the toast being suppressed.

Two sabotages:

- make the `Proxy` return `undefined` instead of re-throwing a suppressed
  rejection → **1 failed**, _"the suppressed 404 was swallowed: the caller
  resolved instead of rejecting"_
- widen the rule from the one route to every 404 → **4 failed**, _"a 404 from
  adminListCourses was silenced"_

## P225-10 — the cap measured on six screens, and what the measuring found

The review asked for the cap to be validated against more visual examples than
the one screen it was designed on. Six screens were driven in Chromium at
1440 px and every visible `input`, `select` and `textarea` measured.

| Screen                     | Controls measured                                | Width                                      |
| -------------------------- | ------------------------------------------------ | ------------------------------------------ |
| Erscheinungsbild           | Name der Schriftfamilie                          | **672 px**                                 |
| Konten                     | Name, E-Mail-Adresse, Rolle, Passwort (optional) | **672 px** each                            |
| Sicherheit                 | the customer picker                              | **672 px**                                 |
| Organisation, Teilnehmende | —                                                | no visible form control in the rig's state |
| **Texte**                  | ~270 single-line text inputs                     | **1,110 px** each                          |

672 px is `max-w-2xl` — 42rem — so the cap is doing exactly what it claims
wherever `Field` is the thing rendering the control. Worth saying plainly
because the cap is a class string and a class string is not evidence: this is
the rendered width, in a browser, on the screens an operator uses.

### The finding, which is the same defect one screen over

**Texte is the screen with the most single-line text inputs in the console, and
every one of them is 1,110 px wide.** Not because the cap failed — because
`CopySettings` renders its own `<input>` elements and never reaches `Field`,
which is the property recorded one section up as a _safety_ argument.

Read the other way it is an **unfixed instance of the defect P225-02 fixed**.
The complaint was single-line inputs at 1,100 px; the screen where that is worst
is the one the fix structurally cannot reach. That is §9.11 from the wrong side
— the fix went where the report was.

It is **recorded and not fixed here**, for two reasons, and both are the
client's call rather than mine:

1. Capping ~270 inputs changes the appearance of a working screen that nobody
   has complained about, in a PR whose stated scope is the cap's introduction.
2. The right fix is probably not a cap at all. Those inputs hold **copy** — the
   sentences a physician reads — and a translator comparing a German string to
   its English overlay wants them at the width the reader sees, not at a form's
   measure. That is a design question about the copy editor, not a width
   constant.

What would be wrong is leaving it unsaid, which is what "the copy editor cannot
be affected" did.

**Mobile, at 390 px**: the sidebar collapses behind _Menü_, cards stack and the
project rows reflow to two columns, all correctly. One pre-existing problem is
visible and is **not** this PR's: the Abteilungen table clips its action column
(_"Bear…"_). It is scrollable rather than broken, it predates these changes, and
it belongs to the responsive package rather than here.
