# P239 — the only control on the player was one that greys out

Closes **DEP-44** (_Improve · Course detail page — add state-based CTA to progress
overview_), filed by Philipp on 15.09.2026.

It also corrects **my own comment on that ticket**, which priced the work as a
migration and a new `ContentStatus` value. The client's reply is the whole
specification:

> when a video is not being played, the course is paused, that's so simple

It is, and the state it names was already in the component. I had looked at the
course _detail_ page, found no video there, and concluded the ticket's state 2
had no referent anywhere. It has one on the **player**, which is the screen the
control actually lives on.

---

## What was on the screen

Measured in the rig at 390 px — sign in, open the course, enter the player, do
not start the video:

```
{"videoPresent":true,"videoPaused":true,
 "allCtas":[{"label":"Fortbildung pausieren","disabled":true}]}
```

The video is not playing, and the sole action is a **greyed-out "pause"**. That
is every learner who has just opened a section, and everyone who paused using
the video's own control. `PlayerScreen.tsx` said so in one line:

```ts
disabled: !playback.playing,
```

So the action was _already_ playback-aware. It just removed itself instead of
offering the other half.

## P239-01 — the playback control is a pair

| `playback.playing`        | label                                             | run   |
| ------------------------- | ------------------------------------------------- | ----- |
| true                      | **Fortbildung pausieren** (outlined, pause glyph) | pause |
| false, course started     | **Fortbildung fortsetzen** (accent, play glyph)   | play  |
| false, course not started | **Fortbildung starten** (accent, play glyph)      | play  |

**Never disabled.** A control that can only be grey is §9.2.

The label comes from `playback` — the element's own report — so it cannot claim
the video is paused while it runs, and the learner using the video's own
control, a media key or Picture-in-Picture moves the chrome with them. Which of
the two resume words applies comes from the course's server-side status, the
same input `CourseHeader` and `StickyProgress` read: one rule for one question
(§4 invariant 6).

### The prop had to change, and the reason is the interesting part

`VideoPlayer` took `paused: boolean`, and it could only ever pause. `false`
meant "nothing to say" rather than "play", deliberately — a widget that started
a video by itself would be doing something the learner did not ask for on
somebody else's page. That guarantee is real and is kept.

But it was carried by a value whose `false` had two meanings, which is why the
control could only express one half of the pair. The prop is now a
**`PlaybackCommand`**, `undefined` until the learner presses something — so the
"never start by itself" guarantee is structural rather than a consequence of
`false` happening to mean nothing.

It carries a `seq`, and that is not decoration. A learner who presses
**fortsetzen**, pauses with the video's own control, and presses **fortsetzen**
again sends `{want:"playing"}` twice. The values are equal, so an effect keyed
on the value alone would not re-run and the second press would do nothing.
Written from the dependency array, covered by a test named for it, and it goes
red on the obvious implementation.

`LessonScreen`'s header rule is unchanged and is why this shape was chosen: the
element owns the fact and reports it upward; the chrome only asks.

## P239-02 — the floating panel on a phone had no playback input at all

`StickyProgress` — the teardrop that is the **only** progress panel below `sm`,
because `ProgressCard` is `max-sm:hidden` — took `state`, `onResume`,
`onClaimPoints` and `onOpenCertificate`. Its button read "Fortbildung
fortsetzen" over a running video and offered to navigate to the content the
learner was already watching.

It now takes the player's own playback action, found on the same `PlayerStatus`
the sidebar row and the masthead card are drawn from, so the three cannot
disagree. `find(kind === "playback")` and not `actions[0]`: the exam sits above
the playback control once both exist (P95-02), and taking the first would put
"Lernerfolgskontrolle beginnen" on a panel floating over a video.

On the course detail page nothing is passed and the panel is exactly what it
was — which is also the answer to the rest of DEP-44: **no video ever plays
there, so the course is always "paused" on that screen**, and the CTA should
always read "Fortbildung fortsetzen" once started. That is what
`CourseHeader.tsx:232` already renders. States 2 and 3 collapse there, and
nothing needed changing.

### The sabotage that stayed green (§9.7)

Deleting `playback={…}` from `CourseShell` — the one line connecting the
player's status to the phone's only progress panel — left **all 454 widget
tests passing**. `StickyProgress`'s tests prove it renders what it is handed;
nothing proved anything handed it. That is the same shape P238 hit one day
earlier, in a different package.

`"reaches the floating panel a phone actually has"` is the test written for it,
driven through the real `CourseShell`, and the sabotage is red now.

## And three stale test helpers this surfaced

`inPlayer()` in `App.route.test.tsx` detected the player by the presence of
**Fortbildung pausieren** — true only while that label was unconditional. Two
replacements were wrong before the third was right, and both are recorded at
the helper:

- `<video>`: that file's fixture has no playable source, so the player renders
  its failure state and no element at all.
- the **absence** of the tab row: true of the player and equally true of the
  empty screen before anything renders, so every `waitFor` would be satisfied
  immediately by nothing — P232's shape, surfacing as the _next_ line failing.

It is the shell's own back control now: positive, player-specific, and drawn
only once the screen is really there.
