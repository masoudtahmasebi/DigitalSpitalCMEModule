# P73 — the journey walks one chapter, and a Fortbildung is a sequence

Asked on 13.08:

> _"are other modules working for a complete course registration, playing
> videos, taking quiz and then going to next chapter and also when chapters are
> finished, issuing the certificate?"_

The honest answer has two halves, and they differ.

---

## What is proven, and where

**The sequencing rule is well covered — at the API level.**
`apps/api/test/integration/learning-flow.integration.test.ts` builds a
**two-module** course and drives it over HTTP against a real Postgres with real
RLS:

| Assertion                                                                | What it pins                                  |
| ------------------------------------------------------------------------ | --------------------------------------------- |
| "starts with module 2 locked and everything outstanding"                 | the initial gate                              |
| "withholds the locked lesson's video URL entirely"                       | not hidden — **absent** from the payload      |
| "refuses progress against the locked second module"                      | the server, not the client, enforces order    |
| "unlocks module 2 and moves the resume target once module 1 is complete" | **the transition the client is asking about** |
| "accepts progress on module 2 now that it is reachable"                  | the far side of it                            |
| `achievedWatchPercent === 60` for 600 of 1000 seconds                    | weighted by duration, not averaged per video  |
| "locks every download and withholds its URL before anything is finished" | the Mediathek follows the same gate           |
| "reaches 100 % coverage but still withholds completion"                  | evaluation and EFN are separate conditions    |

So the rules are not in doubt. `packages/domain` covers the pure half
exhaustively on top of that — `gating.test.ts`, `progress.test.ts`,
`completion.test.ts`.

## What is not proven

**Nobody has walked two chapters in a browser.** `journey.spec.ts` builds one
module with one chapter and one video. It therefore never sees:

- the lock **drawn** on a chapter a learner cannot reach yet;
- the click from a finished chapter into the next one;
- the second video **starting** once the first is complete;
- the certificate issued at the end of a course with more than one chapter.

That is precisely the layer the last five production defects lived in (§9.13):
an API test asserts a function answers correctly and cannot assert that a screen
agrees with it. MEDICE's real course is five modules, so "one chapter works" is
not the shape of the thing being shipped.

## Attempted, reverted, and what it cost

A second chapter was added to the journey on 13.08 and backed out rather than
left half-finished. Two things were learned and are worth not re-learning:

1. **The content form has two file pickers.** `input[type="file"]` `.last()` is
   the _Vorschaubild_, not the video. Feeding the recording to it produced a form
   that said "Ein Video braucht mindestens eine Quelle" — the product being
   entirely right about a test that was wrong. Use `.first()`.
2. **"Inhalt hinzufügen" stops being unique.** With two chapters there are two
   such buttons and the existing quiz step hits a strict-mode violation. Every
   structure-screen locator has to become chapter-scoped, the way P71-04 had to
   scope the catalogue card.

Neither is hard; both need a run to verify, and the learner half — watching
chapter 1, seeing chapter 2 unlock, watching it, _then_ the quiz — needs several
more. It is an hour of work, not a patch.

## Acceptance criteria

- [ ] The journey's course has two chapters, each with its own uploaded video
- [ ] The learner sees chapter 2 **locked** before chapter 1 is complete
- [ ] Chapter 2 becomes reachable once chapter 1 is, and its video plays
- [ ] The Lernerfolgskontrolle opens only once **all** chapters are watched
- [ ] The Teilnahmebescheinigung is issued for the multi-chapter course
- [ ] Every structure-screen locator is scoped to its chapter, so the suite does
      not depend on there being exactly one

## Deliberately not done

**Dropping to one module and calling the integration test sufficient.** It is
sufficient for the rule and not for the product. The client has now found five
defects that were green in an API test, and a sixth would be found the same way.

**A second _module_ rather than a second chapter.** The gate is the same rule one
level down, the acts are identical, and a module costs another minute of console
work per run for no additional coverage. Chapters first; if module-level gating
ever diverges from chapter-level, that is its own ticket.
