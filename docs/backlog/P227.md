# P227 — the console at three widths, and every control named

The review's **Package D**, done as verification rather than as a visual pass:

> The current report explicitly says the redesign was mainly reviewed at
> `1440 px`, so this work remains open.

It is open because eyes do not scale. Thirteen screens at three widths is
thirty-nine judgements, and the two properties that actually break are both ones
a browser can answer exactly.

`apps/e2e/tests/konsole-a11y.spec.ts` — three tests, one per width, over the
eleven screens a `customer_admin` is offered.

---

## The two properties

**1. The page body never scrolls horizontally.** A table _may_ — `Table` wraps
itself in `overflow-x-auto` deliberately, because the alternative is truncated
course titles. What must not happen is the **document** growing wider than the
window, which is the difference between "this table scrolls" and "half the
screen is off the edge". Measured as
`documentElement.scrollWidth - clientWidth`, which a table scrolling inside its
own container does not move.

**2. Every interactive control has a non-empty accessible name.** An unnamed
button announces as "button" and the operator guesses from position. This is the
class that P223-02's language switch belonged to.

Neither is checkable anywhere else: jsdom has no layout, and an accessible name
is computed from the whole rendered tree (§9.7, §9.13).

## The result

**Clean at 1440, 834 and 390 px.** No page-level horizontal scroll, no unnamed
control, on any of the eleven screens at any of the three widths.

That is a real finding rather than an absence of one, because getting there
required fixing the check **three times** — and each fix is the more useful half
of this ticket.

---

## Three ways this check was wrong before it was right

### 1. It reported three defects that did not exist

The first version computed the accessible name by hand: `aria-label`, then text,
then `title`, then `label[for=…]` — and only for form roles. It reported three
findings and **all three were false**:

| Reported                             | Actually                                                                                                                                                    |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mediathek search box unnamed         | wrapped in `<label><span>Suchen</span><input/></label>` — an **implicit** label, invisible to a `label[for]` lookup                                         |
| Erscheinungsbild font picker unnamed | has an explicit `label[for="font-file"]`, which the hand-rolled version consulted only for form roles — and the platform reports a file input as a `button` |
| Mediathek upload input unnamed       | same                                                                                                                                                        |

A check that cries wolf is worse than no check, because the next person learns to
skim its output. The name is computed by the thing that computes it for real
now: `getByRole(role, { name: /\S/ })` is Playwright's implementation of the
accessible-name algorithm, and the difference between that set and all visible
controls is the finding.

**Nothing in the console was wrong. My checker was.** That correction matters
more than the original report did.

### 2. It timed out before reporting anything

The corrected version held an element handle per control and compared them
pairwise across the wire — O(n²) round-trips, which on a screen with forty
controls exceeded a four-minute test timeout and reported nothing at all.
Marking the named nodes inside the page with `evaluateAll` is one round-trip per
role.

### 3. It passed at 390 px while visiting **nothing**

The worst of the three, and the one that matters beyond this file.

At phone width the sidebar is collapsed behind the menu button (P30-02). The
loop read `if ((await link.count()) === 0) continue;` — so when the menu had not
opened, **every screen was skipped**, both assertions ran over empty arrays, and
the test passed.

That is deploy 131's exact shape from the other side: a check that measures
nothing reports no problem. It is `cards.length > 0` again, and the fix is the
same — a **census**:

```ts
expect(
  visited,
  `only ${visited.length} of ${SCREENS.length} screens were reached at ${size.width} px,
   so the measurements below cover less than they claim`,
).toHaveLength(SCREENS.length);
```

A screen the harness cannot reach is now a failure that says so, rather than a
silent zero.

---

## And a fourth thing, which is about sabotage rather than about the check

The overflow property was sabotaged by injecting `<div className="min-w-[2400px]" />`
into every screen. **It did not fire**, twice — which looked exactly like a check
that cannot go red.

It was not. Measured:

```
{"present":true,"w":2400,"h":0,"sw":390}  past= 0
```

A **zero-height** element 2,400 px wide does not extend
`documentElement.scrollWidth`. The sabotage was inert. With `h-2` on it:

```
{"sab":1,"sw":2420,"cw":390}  past= 2030      ✘ on all eleven screens
```

**An inert sabotage is indistinguishable from a check that cannot fail**, and the
only way to tell them apart is to measure the sabotage itself. §9.1 says to break
the thing and watch it go red; this is the corollary — when it does not go red,
establish that you actually broke it before concluding anything about the check.

Both properties are proven red:

| Sabotage                               | Result                                                                     |
| -------------------------------------- | -------------------------------------------------------------------------- |
| remove the Mediathek search label      | `Mediathek: <textbox> <input id="ds-media-search" …>` announces as nothing |
| a 2,400 × 2 px element on every screen | `the page is 2030 px wider than the window`, eleven times                  |

---

## What this ticket does not cover

- **Keyboard-only navigation and screen-reader flow.** Focus order, focus after
  a dialog closes, whether a status change is announced. Those need either a
  real assistive technology or a much more opinionated harness, and neither is
  here.
- **`prefers-reduced-motion`.** The stylesheet honours it (`styles.css`), and
  that is asserted by nothing.
- **Colour contrast.**
- **The learner widget**, which has its own shadow-DOM harness.

## A harness limitation, recorded rather than worked around

`signInToConsole` ends when the console has drawn its **sidebar**, which below
768 px correctly does not exist — so at 390 px it reports _"reached neither
enrolment, nor a code prompt, nor the console"_ about a console that is plainly
loaded. This spec signs in at desktop width and then resizes, and says so at the
call site. Teaching the helper about the collapsed state is a change to shared
harness code and belongs to whoever next needs to test signing in _on_ a phone.

## Acceptance criteria

- [x] Every screen a `customer_admin` is offered, at 1440 / 834 / 390 px.
- [x] The page body never scrolls horizontally; a table still may, inside itself.
- [x] Every visible interactive control has an accessible name.
- [x] The accessible name is computed by the platform, not approximated.
- [x] A census makes a vacuous pass impossible.
- [x] Both properties watched red, with the sabotage itself verified to bite.
