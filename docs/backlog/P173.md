# P173 — The release guard says out loud what it was trusting, and a false report about it

**Raised by:** me, wrongly, and then corrected against the run data.

**Branch** `claude/education-platform-roadmap-3vgrqh`, from `5436f17`.
**Not merged.** Nothing here reaches production until the client picks one of
the three options at the bottom.

---

## The report I made, and why it was false

I told the client:

> _"Your deploys are firing from the feature branch, not from `main`. […]
> pushing that branch is what puts code on production. The merge to `main`
> deploys nothing."_

That is wrong. Deploys fire from CI on `main`, exactly as `deploy.yml`
documents.

`Verified:` every deploy run matched against the CI runs on `main`:

| CI on `main`                | completed  | deploy created |
| --------------------------- | ---------- | -------------- |
| `02328b3` (P172 merge)      | 14:37:51 Z | 14:37:56 Z     |
| `c9e6a0f` (P171 merge)      | 14:30:01 Z | 14:30:04 Z     |
| `098cdec` (P170 merge)      | 14:06:49 Z | 14:06:52 Z     |
| `23e36ad` (P168/P169 merge) | 13:16:24 Z | 13:16:26 Z     |

Three to five seconds apart, every time. No branch CI run has ever produced a
deploy.

### What misled me, and the evidence I already had

`GET /actions/runs` reports a `workflow_run`-triggered run's own `head_branch`
and `head_sha` as the **feature branch** and a branch commit, not as the
triggering run's. I read those two fields as "what triggered this" and built a
causal story on them.

The disconfirming evidence was already in my hands: an earlier deploy's own
smoke test reported `23e36ad` serving — a **merge commit**, which cannot come
from a branch-commit trigger. I had quoted that number to the client an hour
earlier and did not reconcile it with the claim.

CLAUDE.md §11.1: no causal claim without a command. I had a command's output
that contradicted it and wrote the claim anyway, an hour after writing a ticket
about exactly this failure. The client then instructed a change to their
deployment path on the strength of it, which is the cost.

## What the change actually is

Not a fix for a hole — **defence in depth**, turning an implicit trust into an
explicit, tested rule.

`release-guards.sh` said, in its own hand:

> a `workflow_run` deploy has already been gated by the workflow's own
> `branches:` filter … and needs nothing further here.

True, as it turns out. It is still a claim about GitHub's behaviour rather than
a rule this repository enforces, and the one thing this project keeps relearning
is that those are different (§11.9). P155-01 closed the same shape for
`workflow_dispatch` after a manual run put a feature branch on the host.

`ds_release_dispatch_allowed` becomes `ds_release_ref_allowed`, taking a fourth
argument — the **triggering run's** `head_branch`:

- `workflow_dispatch` → the ref must be the default branch (unchanged, P155-01);
- `workflow_run` → the triggering branch must be the default branch;
- anything else → refused, so a trigger added to `deploy.yml` later has to come
  here first.

`github.ref` cannot express this: on a `workflow_run` event it is the default
branch whatever the triggering run was on, which is why the existing guard —
reading `$ref` — would have waved a branch-triggered deploy through if the
filter had ever let one reach it.

Six new cases in `release-guards.test.sh`, and both sabotages watched red:
returning 0 for every `workflow_run` (the previous behaviour) fails four; judging
by `$ref` instead of the triggering branch fails three.

## The risk, stated

I have **not** observed what `github.event.workflow_run.head_branch` contains at
job runtime. If it holds what the list API reports rather than the triggering
run's branch, this guard refuses **every** deploy until one line is reverted.

The filter demonstrably works, so the value is almost certainly `main` — and
"almost certainly" is what produced the false report above.

## The decision, which is the client's

1. **Ship and watch** — merge, and confirm on the next deploy that the guard
   passed; one-line revert if not.
2. **Ship as a warning first** — print the values, do not block; enforce once a
   real run has shown what they are. _Recommended:_ it records the rule with no
   risk to a pipeline the client is actively shipping through.
3. **Drop it** — the filter works and `deploy.yml`'s header now describes it
   accurately, which was the only thing that was actually wrong.

`deploy.yml`'s header is corrected either way: it claimed the filter is what
stops a feature branch reaching production. That sentence was right about the
outcome and wrong about the mechanism it credited, and it is the sentence that
made me believe a filter was failing when it was not.
