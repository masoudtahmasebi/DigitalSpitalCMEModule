> let's create sample data and check with `EIV-FOBI` or maybe search for the
> data, i think there is a swagger available as well. can you refactor the code
> base on best practices? can you rewrite the layout of the admin panel based on
> the repository which i gave you for a better design and make it logical for the
> user to understand. can you write and run tests that tests the whole system
> from start to the end […]

Two tasks, and they turn out to be the same finding twice.

P28 named a class of defect this codebase keeps producing: **a mechanism fully
built and reachable through no supported interface**. P30-01 is the eighth
instance — a mock server with seven failure behaviours and no way for the client
to ask for any of them. P30-02 is the same shape one level up: ten screens each
of which had built its own page chrome, so the console had ten headers and no
header.

## P30-01 · The EIV harness could not exercise its own mock — **done**

- **Estimate:** 3 h · **Review gate: human — eiv**

`apps/eiv-harness/src/mock/` implements seven behaviours — accepted, duplicate,
unknown VNR, invalid EFN, rate limited, upstream error, timeout — selected by an
`x-mock-behaviour` request header. Nothing could send that header. The CLI built
its request from `EivClientOptions`, and `EivClientOptions` had no way to add
one. Six of the seven were dead the day they were written, so the retry policy,
the deadline alarm and the permanent-failure path had never been run against
anything but success.

**What changed**

- `EivClientOptions.extraHeaders` — an optional header map, spread into every
  request. **The bearer token is applied after the spread**, so a caller cannot
  forge or replace it; that ordering is the security property of this change and
  is commented as such at the assignment.
- `apps/eiv-harness/src/cli.ts` grew `--behaviour <name>`, validated against a
  `BEHAVIOURS` const array so a typo fails loudly rather than silently
  succeeding.
- **`--behaviour` is refused against any non-local host, exit 2.** A flag that
  asks a server to pretend to fail is a flag that must never reach
  `punktemeldung.eiv-fobi.de`. `isLocal(baseUrl)` was lifted out of
  `checkLiveGuard` so the live guard and the behaviour guard share one
  definition of "local" rather than drifting apart.

**Acceptance criteria**

- [x] Every one of the seven mock behaviours reachable from the CLI
- [x] `--behaviour` against a non-local base URL exits 2 without sending
- [x] The live guard still refuses `punktemeldung.eiv-fobi.de` without
      `EIV_ALLOW_LIVE=yes`
- [x] No caller-supplied header can override `authorization`

**Not done, and deliberately.** The EIV-FOBI swagger could not be retrieved:
`veranstalter-swagger-ui.eiv-fobi.de`, `www.eiv-fobi.de` and `api.blaek.de` are
all refused by this environment's egress proxy. Our request/response shapes
therefore remain **inferred**, not verified, and no amount of local testing
changes that. Recorded as **S24** with MEDICE as the owner: the export has to
come from them or from ÄKWL. Sample data was seeded and pushed through the mock
end to end; that proves our client against our assumption, which is the most a
local run can prove.

## P30-02 · Ten small tools that shared a sidebar — **done**

- **Estimate:** 6 h

The client named **react-admin** as the reference and then, when this went too
far the first time, corrected it: _"do not re implement the complete
react-admin, get the idea and design from it."_ So this takes its **shapes**, not
its code — the dependency would have to earn its way past ADR-0001, and none of
the four state bugs this console actually shipped would have been prevented by
it.

### What was wrong

Each screen drew its own heading, its own intro paragraph and its own empty
state, in slightly different markup. The measurable consequences:

| Symptom                                                                  | Screens                                             |
| ------------------------------------------------------------------------ | --------------------------------------------------- |
| Two competing headings, one from the frame and one from the screen       | Organisation, Sicherheit, Erscheinungsbild, Zugänge |
| An intro paragraph repeated verbatim under the frame's own               | Kunden, Teilnehmende, Bescheinigungen, Konten       |
| A bare "keine Einträge" where an operator needed telling what to do next | five list screens                                   |
| Ten flat navigation entries with nothing saying which part you were in   | the sidebar                                         |
| "Zurück", five levels deep, that did not say where back was              | the course editor                                   |

### What it is now

`apps/admin/src/components/page.tsx` — one file, four exports, and the rule that
**the title is where the title goes and the actions are where the actions go**.

| react-admin                   | here                                        |
| ----------------------------- | ------------------------------------------- |
| `Title` + `ListActions`       | `Page` — title, description, actions        |
| `Breadcrumb`                  | `Page`'s `trail`                            |
| `Empty` — "no X yet" + invite | `EmptyState`                                |
| `ListToolbar`                 | `ListToolbar` — filters left, actions right |
| `Datagrid` in a `Card`        | `Table`, now on its own surface             |
| `Resource` declaring chrome   | `Section` in `App.tsx`'s `NAV`              |

The last row is the one that makes the rest hold. A screen's title and
description are declared **once, on the navigation entry**, next to the
capability that decides who may see it — so a screen cannot draw a heading that
disagrees with the item that navigated to it, because it does not draw one.

The navigation is grouped by the question each part answers, in the order
somebody actually works:

- **Angebot** — what exists to be taken: a customer, its departments and
  projects, the courses inside them.
- **Teilnahme** — who is taking it, how far they have got, what came out at the
  end. Access first: an account must exist before it can have progress.
- **Einstellungen** — the platform itself. Visited once, then rarely.

### Three things that are corrections rather than polish

1. **The group labels were `h2`.** So were the page titles, so a screen reader's
   heading list read "Angebot, Teilnahme, Einstellungen, Fortbildungen" as four
   peers with the one naming the current screen last. They are now `p` elements
   with the list `aria-labelledby` them.
2. **The empty course list offered "Neue Fortbildung" twice** — once in the
   header, once in the empty state — two buttons with one accessible name. The
   header action now stands down while the list is empty, which is what
   react-admin's `Empty` does.
3. **The sidebar was `md:flex` only.** Below `md` it rendered _above_ the
   content, so a phone opened every screen with eleven navigation buttons and the
   operator scrolled past all of them. It now collapses behind a toggle and
   closes on any navigation.

### Acceptance criteria

- [x] Exactly one page heading per screen, and it is the navigation entry's title
- [x] Navigation grouped, each group a list labelled by its heading
- [x] The course editor and the quiz editor carry a breadcrumb that navigates
- [x] Empty lists say what the screen is for and what to do next
- [x] No duplicated create button on an empty list
- [x] The sidebar collapses on a narrow screen and closes on navigation
- [x] Asserted in `App.test.tsx` (jsdom) **and** driven in Chromium against a
      real API and Postgres

### Tested

`apps/admin/src/App.test.tsx` gained a `P30-02` block: grouped navigation, one
`h2` per screen across all nine destinations, the single create button, and a
trail that actually navigates. The same properties were then checked in Chromium
against the built bundle, a real Nest app and a real Postgres — the jsdom test
would pass on markup that never rendered, and the browser run is what proves the
Tailwind responsive classes and the shadow-free surfaces are real.

### Deliberately not done

No routing. The console still has no URLs, so the breadcrumb trail is passed
explicitly rather than derived from a path. Adding a router to make breadcrumbs
automatic would be a second navigation model for the sake of one component, and
the deep part of this console — course → module → chapter → content → quiz —
already knows its parent at every level because it was navigated to from one.
