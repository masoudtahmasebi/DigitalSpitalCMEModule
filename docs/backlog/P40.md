# P40 · Passwort vergessen, on both planes

> forget password is not there at all
>
> — and, on how operator mail should be configured: **"Both, self-configuring"**

---

## P40-01 · The platform's own sender — **done**

- **Estimate:** 5 h · **Review gate: human — auth**

A physician's reset mail leaves through their project's SMTP settings, which a
customer administrator already configures under Organisation and which
certificate delivery already uses. An operator's cannot: a `super_admin` belongs
to no customer, so there is no project whose sender is theirs to borrow, and
borrowing one would put a customer's address on mail about accounts that are not
theirs.

`platform_smtp` is a singleton beside the staff tables — `id boolean PRIMARY KEY
CHECK (id)`, so there is exactly one row and the write path is one
`INSERT … ON CONFLICT DO UPDATE`. Beside them rather than on `customers` for
`admin_2fa_policy`'s reason: it is read on the sign-in path before any tenant
context exists, and `customers` is under FORCE ROW LEVEL SECURITY.

**Configured in the console, not in `config.env`.** That was the client's
instruction and it is the better answer regardless — the same reasoning that
moved `EXTRA_CORS_ORIGINS` and the Keycloak binding onto the entities they
belong to. Changing where the platform's mail comes from should not need SSH.

The password is encrypted with the application KMS key and is write-only: `GET`
returns `hasPassword`, never the value in either form. An omitted field keeps
what is stored and an explicit `null` clears it, so correcting the sender name
cannot silently wipe the credential. Only a super administrator may write it.

## P40-02 · The staff plane — **done**

- **Estimate:** 5 h · **Review gate: human — auth**

`POST /admin/auth/password-reset` answers **202** for an unknown address, a
disabled account, a platform with no sender, and a link that went out. The
console's accounts are named after real people at a named company; a form that
answered differently for a known address is a way to find out who works there.
The service behaves the same way on its side — no token is minted when there is
nowhere to send one — so there is no difference in work done either.

The link's origin comes from the request, checked against `ALLOWED_ORIGINS`,
**never from the body**. A reset flow that lets the caller name the link's host
delivers a real token to a real inbox pointing at a page the attacker controls.

The token arrives in the URL **fragment**, not the query string: a query string
is sent to the server on every request for the page and lands in access logs,
proxy logs and the `Referer` of anything the page loads. It is cleared from the
address bar the moment the page has read it.

Redemption reuses `POST /admin/auth/credentials` — the same endpoint an
invitation is redeemed through, because they are the same act. `kind` decides
the lifetime server-side: seven days against sixty minutes.

## P40-03 · The learner plane — **done**

- **Estimate:** 6 h · **Review gate: human — auth**

`learner_credential_tokens`, shaped like the staff table and not tenant-scoped
for the same reason `learner_credentials` is not: the token is presented by
somebody with no session, so it is resolved before any tenant context can exist.

The mail goes out through the **project's** SMTP settings, so a physician's
reset comes from their customer's own sender.

Same refusal to answer: 202 for an unknown address, for a project whose
participants sign in through a customer's Keycloak — a federated password is not
ours to reset — and for a project with no SMTP settings. Asking whether a given
physician has an account with a named pharmaceutical company is close enough to
health-adjacent information about a named person that the form must not answer
it, which is why the assertions in the suite are mostly that two responses are
_identical_.

### A defect this found, in the shape that hides best

`projectSender` first read `projects` on the bare pool. `projects` is under
FORCE ROW LEVEL SECURITY, so with no `app.customer_id` it matched zero rows —
and the method's shape hid that perfectly: every column came back `null`, which
`canSend` reads as "not configured", so a **correctly configured project
silently sent nothing** and the endpoint still answered 202. It is the same
mistake `findParticipant` documents one method up, and the only reason it was
caught is that the test asserted a token row rather than a status code.

## P40-04 · Both sign-in screens — **done**

- **Estimate:** 4 h · **Review gate: none**

"Passwort vergessen?" on the console's and the portal's sign-in forms, the form
behind it, and the screen that sets the password. `type="button"` on both links,
because a bare `<button>` inside a `<form>` submits it — which would attempt a
sign-in with an empty password every time somebody forgot theirs.

Both confirmations say **wenn** and not **wir haben**: "if there is an account
for this address, a link is on its way". The API refuses to say whether the
address exists, and a screen that confirmed it would give that back in the last
inch.

The reset screen is checked **before** the signed-in branch on both apps.
Somebody following a reset link while still holding a session is somebody who
thinks their account is compromised; dropping them into the console or the
catalogue would be the wrong answer to that.

The platform-sender panel sits on **Sicherheit**, for super administrators only,
and leads with the server's own `canSend` verdict — configured, or "Server und
Absenderadresse fehlen noch", which is the question an operator actually has.

## Verified

- 420 integration tests, including 28 on the learner plane's reset and 98 on the
  staff plane's, covering: an address that exists, one that does not, replay,
  revocation, expiry at both lifetimes, a rejected password not spending the
  link, a federated project minting nothing, and the sender never being
  returned or stored as text.
- 1371 unit tests, 16 browser specs, `env-audit` clean.
- The browser route sweep probes both new contract routes automatically, because
  it is generated from `contracts/openapi.yaml`.

## Deliberately not done

**No test sends a real email.** There is no SMTP server in CI and standing one
up would be testing nodemailer. The seam is the token table: the request writes
a row when it can send and refuses to when it cannot, which is the decision this
code owns.

**Second-factor accounts still meet their second factor after a reset.** A reset
restores the password and nothing else — the account remains enrolled, and under
a `required` policy the next sign-in still asks for a code. Stated because the
opposite would make a reset link a way around 2FA, which is precisely what
`canResetSecondFactorOf` refuses on the other path (P38-07).

## P40-05 · The invitation was a string, not a link — **done**

- **Estimate:** 3 h · **Review gate: human — auth**

Reported from the live console, and it is the sharpest kind of report because
every step of it was reasonable:

> i added one account, it gave me a weird string, no place to even enter a
> password in the super admin panel, it did not say what the string was, now i
> used that string as password, and that wasn't the password

### What the screen actually did

It rendered the bare 43-character token under a sentence beginning **"Dieser
Link wird nicht automatisch versendet"** — so an operator was told to hand over
a _link_ and shown a _string that was not one_, with nothing else to do with it.
Trying it as a password is not a mistake; it is the only interpretation the
screen left available.

### Three things were wrong, and only one of them was the copy

1. **No link.** The console knows its own origin and never used it. It now
   renders `https://verwaltung.…/#passwort-neu?token=…` with a copy button.
2. **No delivery.** There was no platform sender until P40-01, so handing the
   token over by hand was the only channel — and the copy said so in a way that
   read as a temporary state nobody could act on. The API now emails the
   invitation itself whenever a sender is configured, and says which happened.
   The token comes back either way: an invitation must not be lost because a
   mail server was down.
3. **No explanation of what could not be done.** The screen offered no way to
   set a password and gave no reason, so its absence read as an unfinished
   feature rather than a decision.

### Why an administrator cannot set an operator's password

There is no field for it and there will not be one. An invited account is
created with `password_hash NULL` — asserted by an integration test named
_"creates the account without a password, so the invitation is not a
credential"_ — and the invitee chooses their own. A password an administrator
typed is a password an administrator knows, on an account that can read every
physician's participation record for a customer.

The console now says this in as many words at the moment it matters, rather than
leaving it to be inferred from a missing input.

### The link's origin

From the request, checked against `ALLOWED_ORIGINS` — never from the body, on
the reset flow's reasoning. The console builds the same link locally from
`window.location.origin`, and the two agree because both point at the console.
