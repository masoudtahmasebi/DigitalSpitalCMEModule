# Epic P7 · EIV-FOBI & EFN — 12 h

**Weeks 1 (5 h) and 5 (7 h).** Implements ADR-0005. The only external, legally
binding interface in the system, and the only one whose behaviour we have not
observed. Week 1 exists to convert that unknown into a fixed-duration risk.

**Every task in this epic is behind the human review gate.**

**Hard checkpoint:** if EIV sandbox credentials have not arrived by **23.08.2026**
(end of week 4), the fallback applies — launch with submissions queued and held,
flip to live as a follow-up. The learner experience and the certificate are
unaffected by design.

**Demo at end of phase (M3 · CME compliant, 30.08):** full journey — enrol → watch
→ quiz → evaluation → EFN → EIV submission → certificate in the inbox.

### P7-01 · EIV contract test harness

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 1 · **Depends on:** P0-02
- **Review gate:** human — eiv
- **Implements:** ADR-0005

**Context**
Build the test before the integration. The moment credentials arrive — whichever
week that is — the question "does the API behave as documented?" is answered in
minutes rather than days.

**Scope**
- `apps/eiv-harness` — a runnable CLI performing the real sequence: authenticate
  (VNR + password) → JWT → `POST /fobi/veranstalter/push_teilnahme` with a test
  EFN and `rolle: TEILNEHMER`.
- Prints exactly what was sent and exactly what came back, including non-2xx
  bodies and headers.
- `EIV_BASE_URL` is the only difference between mock, sandbox and live.

**Acceptance criteria**
- [ ] The CLI runs end-to-end against the mock with no credentials configured
- [ ] Request and response are reported verbatim, including error bodies
- [ ] Switching to sandbox or live requires changing only `EIV_BASE_URL` and
      credentials — no code change
- [ ] Credentials are read from the environment, never committed
- [ ] The EFN and the VNR password are redacted in printed output

### P7-02 · EIV mock server

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 1 · **Depends on:** P7-01
- **Review gate:** human — eiv
- **Implements:** ADR-0005

**Context**
The mock is what makes week 1 productive and what lets retry, deadline and error
handling be tested in CI permanently — CI can never depend on an external sandbox.
It encodes our *assumptions*, and must be corrected the moment reality is
observed, or it becomes actively misleading (ADR-0005 consequences).

**Scope**
- Local server implementing the documented contract: auth, JWT issue, and
  `push_teilnahme`.
- Configurable responses: success, validation rejection, auth failure, duplicate
  submission, timeout, 5xx.
- A README stating plainly that this is built from documentation, not observation.

**Acceptance criteria**
- [ ] Every failure mode the retry queue must handle can be triggered on demand
- [ ] The mock runs in CI with no network access
- [ ] The mock's assumptions are documented explicitly, field by field, so a real
      divergence is a diff rather than an investigation

### P7-03 · Deadline invariants as pure functions

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 1 · **Depends on:** P0-05
- **Review gate:** human — eiv
- **Implements:** ADR-0005

**Context**
The 8-day reporting obligation and the 7-day correction window are the parts with
legal weight, and they are pure date arithmetic. Keeping them out of the transport
layer is what makes them exhaustively testable with no credentials, no network and
no mock.

**Scope**
- `eivDeadlines(eventEndDate, submittedAt?)` in `packages/domain` returning the
  reporting due date, the correction window end, `isOverdue` and `needsAlert`.
- Time is always an argument — never `Date.now()`.

**Acceptance criteria**
- [ ] Reporting due date is exactly 8 days after event end; the correction window
      is exactly 7 days
- [ ] Boundary cases are covered: submission on day 8 exactly, day 9, correction
      on the last valid day and one day late
- [ ] German DST transitions do not shift a deadline by a day
- [ ] `needsAlert` fires with enough lead time to act, configurably
- [ ] The function is pure — passing the same arguments always yields the same
      result, with no clock read

### P7-04 · VNR credential vault

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 5 · **Depends on:** P7-03, P2-02
- **Review gate:** human — eiv

**Context**
The VNR password authenticates DigitalSpital to a legally binding accreditation
interface on the customer's behalf. It is the highest-value secret in the system.

**Scope**
- Encrypted-at-rest storage of the VNR password per course, using the application
  KMS key.
- Write-only API surface; decryption only inside the submission path.

**Acceptance criteria**
- [ ] The password is never returned by any endpoint, at any role, including
      super admin
- [ ] The plaintext never appears in a log, an error, or a database dump readable
      without the key
- [ ] Rotating the KMS key is possible without re-entering every password
- [ ] Decryption happens only within the submission service, verified by test

### P7-05 · Submission service

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 5 · **Depends on:** P7-04, P4-05
- **Review gate:** human — eiv

**Context**
Triggered by the completion event from P4-05. The EFN is read from our own store
(ADR-0004), so submission and retry never depend on the learner being present.

**Scope**
- Build and send the Punktemeldung on completion: EFN, VNR, `rolle: TEILNEHMER`,
  event data.
- Re-validate the EFN format at submission time, not only at capture.
- Persist the submission record with its external reference and status.

**Acceptance criteria**
- [ ] A submission is built only from a recorded completion
- [ ] The EFN is re-validated immediately before sending
- [ ] Each completion submits exactly once — a duplicate is impossible even under
      concurrent triggers
- [ ] A submission failure does **not** block certificate issue (P8), by design
- [ ] The external reference returned by EIV is persisted for later correction

### P7-06 · Retry queue

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 5 · **Depends on:** P7-05
- **Review gate:** human — eiv

**Scope**
- Durable queue with bounded exponential backoff.
- Distinguish retryable transport failures from permanent validation rejections —
  a rejected EFN must not be retried forever.
- Queue-and-hold mode for the credentials-late fallback in ADR-0005.

**Acceptance criteria**
- [ ] Transport failures retry with backoff; validation rejections do not
- [ ] Retries survive an API restart — the queue is durable, not in-memory
- [ ] Queue-and-hold mode accumulates submissions and releases them in order once
      enabled, which is the launch fallback
- [ ] A permanently failed submission is visible, not silently dropped

### P7-07 · Deadline alerting and audit log

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 5 · **Depends on:** P7-06
- **Review gate:** human — eiv
- **Implements:** ADR-0005

**Context**
A queued submission that never sends looks identical to a healthy system from the
outside: the learner has their certificate, the record exists locally, nothing is
on fire. Only an explicit alert surfaces it. This task is the reason `needsAlert`
is part of the domain function rather than an operational afterthought.

**Scope**
- Every attempt — success and failure — written to the append-only audit log.
- Alert on a submission approaching its deadline, driven by `needsAlert`.
- An operational view of pending, failed and overdue submissions.

**Acceptance criteria**
- [ ] Every attempt is audited, including failures and retries
- [ ] Audit entries cannot be updated or deleted
- [ ] An approaching deadline raises an alert before the deadline, not after
- [ ] A submission that will never succeed is escalated rather than retried
      silently
- [ ] The audit log contains no EFN or VNR password in plaintext
