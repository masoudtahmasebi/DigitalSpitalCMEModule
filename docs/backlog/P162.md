# P162 — Delete answered 500 on every level that still had something inside it

**Raised by:** the client, 03.09.2026, from the console —
_"when you click the … of `Module 3 - Therapie` when it has content inside, it
gives a 500 error, it works when you first delete the inner parts, we should
check why it doesn't delete cascadely, or it should not be enabled to be able to
delete when the inhalt inside there are not empty."_

**Branch** `claude/education-platform-roadmap-3vgrqh`, from `origin/main` at
`5297304`.

## What was wrong

```
DELETE /admin/modules/ab50f0b6-cdf9-43b4-bc5e-08da7844e9c0
{"type":"…/errors/internal","title":"Internal server error","status":500}
```

`chapters.module_id`, `contents.chapter_id` and `quiz_questions.content_id` are
all `ON DELETE RESTRICT` (`0001_init.sql`). `deleteModule` is a plain
`DELETE FROM modules`, so a non-empty one reached Postgres, raised a foreign-key
violation, and nothing caught it. An unhandled constraint error is an internal
error, not an answer.

**Three of the six deletes had this shape**, not one. `deleteDepartment`,
`deleteProject` and `deleteCourse` call `assertRemovable(records, census,
label)` and ask both of `deletionVerdict`'s questions — _is anything inside it_
and _has a learner touched it_. `deleteModule`, `deleteChapter` and
`deleteContent` called `assertDeletable(records)` and asked only the second.

The repository's own comment above those counts says what should have been true:

```
 * Two questions per level, matching `deletionVerdict`: is anything inside it,
 * and has any learner touched anything inside it.
```

CLAUDE.md §9.3 exactly — a rule written is not a rule enforced. The rule exists
in `@ds/domain`, is exhaustively tested, and half its call sites did not use it.
`scripts/unused-rules.mjs` cannot see this: the rule _has_ callers, just not all
of them.

### Why it was invisible

The one module-delete case in the suite creates a module and deletes it on the
next line, so it is always empty. The one chapter case is refused for **learner
records** before children are ever reached. Neither could have gone red —
CLAUDE.md §9.1 in the plainest form.

## P162-01 — every level asks both questions

`censusOfModule` (chapters) and `censusOfChapter` (contents) join the three that
already existed, and `deleteModule`/`deleteChapter` go through `assertRemovable`
like the levels above them. The refusal is the one that was already written:

> Dieses Modul enthält noch 1 Kapitel. Diese müssen zuerst gelöscht werden.

**Not cascaded**, on the client's own reading — _"it should not be enabled to be
able to delete when the inhalt inside there are not empty."_ A module holds
chapters holding contents holding the evidence behind CME points already
reported. `ON DELETE RESTRICT` is deliberate and stays.

A Lernerfolgskontrolle's questions are counted separately by
`countContentQuestions` and refused by `assertNoQuestions`, because a question
is not a `HierarchyLevel`: widening that type to carry one would put a question
into every census and every label map on the platform, none of which are about
quizzes.

**Written red first**, reproducing the client's own error on all three:

```
FAIL > refuses a module that still holds a chapter, and names what is in the way
{"type":"…/errors/internal","status":500,"instance":"/admin/modules/df0d5e37…"}
expected 500 to be 409
FAIL > refuses a chapter that still holds a content          expected 500 to be 409
FAIL > refuses a Lernerfolgskontrolle that still holds questions  expected 500 to be 409
```

Then 584/584, including a fourth case that deletes all three innermost-first
once they are empty — so the refusal cannot be a blanket one.

## P162-02 — and the button is not offered

A 409 with a sentence is better than a 500 and is still §9.2: a control whose
only outcome is a refusal looks like a decision to the person clicking it. The
Delete button is now disabled with a reason naming the count, and the two
reasons are kept apart because they need different answers — children the author
can remove, learner records nobody can.

The counts come from the tree the screen already draws (`chapters`, `contents`,
`questionCount`), so there is nothing new for the API to send.

### A test that encoded the old model

`offers delete where nothing is recorded, and only there` asserted **three**
deletable rows: a module, its chapter and its content. Two of those three
answered 500. The assertion was pinning buttons whose only possible outcome was
an internal error.

Migrated rather than deleted, as P87 established: what it is for — offered
exactly where it can work — is unchanged, and there are now two ways for it not
to be. It asserts one deletable row, five locked ones, and that the two reasons
are told apart. Watched red by making the console stop asking
(`expected 3 to be 1`).

## Acceptance criteria

- [x] Deleting a non-empty module, chapter or Lernerfolgskontrolle answers 409
- [x] The message names what is inside and how many
- [x] Each is deletable once emptied, innermost first
- [x] The button is disabled before it is pressed, with the reason on the row
- [x] Records and children are told apart in both the API and the console
- [ ] Confirmed in a browser against the installation — the client's, after deploy

## Not done

**No cascade, by decision.** If the client later wants "delete this module and
everything in it", that is a separate, explicit affordance with its own
confirmation naming every descendant — not a silent side effect of this button.

**`quiz_attempts` also references `contents` with `ON DELETE RESTRICT`.** It is
almost certainly covered, because a quiz attempt writes `content_progress` and
`countContentRecords` counts that — but _almost certainly_ is not verified, and
I have not written the case that would prove it. If it is not covered, deleting
an attempted exam with no progress row is the same 500 again.
