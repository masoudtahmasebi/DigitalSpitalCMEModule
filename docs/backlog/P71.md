# P71 — the player forgets what it has watched

Reported 13.08, from the portal, with two screenshots of the same module at
0:11 and then stopped at 0:37:

> _"suddenly the video stops and when i press again it goes to start of the
> video, the video player is not robust"_

---

## What was found

`VideoPlayer` keeps a **watermark** of the furthest second reached by ordinary
playback. Its own header says why, twenty lines above the defect:

> `seekCeilingSec` is only as fresh as the last progress flush — fifteen
> seconds — so **enforcing it alone would yank a playing video backwards** the
> moment the playhead passed the last flushed second.

And then:

```ts
// A different lesson in the same mounted player starts its own session.
useEffect(() => {
  reachedRef.current = props.startAtSec;
  setReachedSec(props.startAtSec);
}, [props.startAtSec, props.seekCeilingSec]);
```

The comment says _lesson change_. The dependency list says _the ceiling
changed_ — which happens on **every progress flush**, on the same lesson, four
times a minute. So the watermark was thrown away every fifteen seconds, the
permitted range collapsed back to a stale server ceiling, and the next `seeking`
event — the browser's own during buffering, Picture-in-Picture, a media key, or
the clamp itself — had a limit behind the playhead to snap back to.

The rule was right and its trigger was wrong. That is CLAUDE.md §9.3 one turn
further round: not a rule nothing calls, but a rule **called by the wrong
thing**.

## The fix

A new `contentId` prop, and the reset is keyed on it and nothing else. A ceiling
arriving is news about this session; a different content **is** a different
session. `startAtSec` is read through a ref so the effect has exactly one
trigger, which is the whole of its correctness.

`VideoPlayer.test.tsx` gains two cases, red-checked in both directions:

- a flush arrives with a ceiling **behind** the playhead → the playhead is left
  alone (`expected 30 to be 37` against the unfixed player — the client's
  symptom, in a unit test);
- the content changes → the watermark **does** reset, so finishing module 1
  cannot unlock module 2's scrub bar.

## What this ticket does not claim

**It does not claim to have reproduced the client's screenshots.** That
distinction is the point, not a hedge.

The defect above is real, is demonstrated by a test that goes red without the
fix, and has a compliance consequence: the scrub bar's permitted range collapses
four times a minute, so a learner who has watched to 0:37 is told they may only
reach 0:25. Whether it is also the cause of _their_ stop-and-restart could not be
established from here.

The journey was extended to try, and the attempt is recorded because the
negative result is the useful part:

| Tried                                                                          | Result                                |
| ------------------------------------------------------------------------------ | ------------------------------------- |
| Fixture 8 s → 18 s, so a flush lands mid-playback                              | Green against the broken player       |
| Watching at **1,5×**, the rate in the client's screenshot, with a 25 s fixture | Still green against the broken player |

The reason is that the snap-back needs the server's ceiling to lag the playhead
by more than a second, and in this rig it does not — the API credits the union
promptly, even at 1,5× (`PLAYBACK_RATES` caps at 2× precisely because the API
tolerates it). Something on the installation makes that gap wider, and this
suite does not know what.

So the journey keeps the eighteen-second fixture, because a flush landing during
playback is worth having on its own, and its new assertion is described in the
file as **a monotonicity guard, not the regression test for this report**. A
check whose reach is overstated is how the last four defects survived.

## Reproduced on production, 13.08 16:24 — and not by the fix

The journey ran against the installation after the deploy of `06c291b`, which
**contains the P71-01 fix**, and stopped at the watch step:

```
Error: the video never played past a progress flush, so this act asserted nothing
Expected: > 16
Received:   8
```

`furthest` is the highest `currentTime` observed. The loop exits early when the
element reports `paused`, and the whole test took 29 s — far less than the loop's
own 25 s budget — so it **broke on `paused`, not on the deadline**. The video
stopped by itself at eight seconds, on an eighteen-second file, unprompted.

That is the client's report, reproduced by the suite for the first time, on
production. Three things follow:

1. **The watermark defect was not the whole cause.** It is a real defect and it
   is fixed; the symptom survives it. P71-01 said it could not claim to be the
   cause, and this is the evidence for that caution rather than against it.
2. **`props.paused` is not the mechanism.** It is set true in exactly one place
   — the learner pressing _Fortbildung pausieren_ — which the journey has not
   done at that point.
3. **What remains is candidate 2 below.** A `<video>` pauses and resets when its
   resource selection re-runs, which is what replacing its `<source>` children
   does. That matches "stops, and pressing play starts from the beginning"
   exactly, and nothing else here does.

**It does not reproduce locally.** The same spec against the rig passes, twice.
The difference to chase is why a course fetch on the installation would mint
different media URLs from one on the rig — `onProgress` reloads only the
enrolment today, so the re-render that replaces the sources has to be coming
from somewhere else.

## Still open

**Why the client's video stopped.** Two candidates neither confirmed nor ruled
out:

1. This defect, with a wider ceiling gap than the rig produces.
2. The `<source>` children being replaced on a re-render. They are keyed by
   URL, and a course fetch that re-signs `s3://` references mints a _different_
   URL each time — which would replace the DOM nodes under a playing element.
   `onProgress` reloads only the enrolment today, so this should not fire; it
   has not been proven not to.

Closing it needs something the repository cannot supply: the browser's own view
on the installation. The next report should come with the console open and the
Network tab kept, or the player should carry enough instrumentation to say why
it stopped — which is the shape of the open P68 item on media refusals
(`docs/backlog/P68.md`, "a player that says which refusal it is").

## Acceptance criteria

- [x] The watermark survives a progress flush on the same lesson
- [x] It still resets when the content changes
- [x] Both directions red-checked
- [x] The journey's fixture is long enough for a flush to land during playback
- [x] The journey's new assertion states what it does **not** cover
- [x] The client's report reproduced — on production, 13.08 16:24, by the
      journey. The cause is **not** P71-01 and is not yet identified.

## Deliberately not done

**Weakening the seek clamp.** It is a courtesy rather than the gate — the real
defence is the server-side union — but a clamp that stopped snapping back would
hide the next instance of this instead of fixing it.

**Making the flush interval configurable so the suite can force one.** The
fifteen seconds is production behaviour and a suite that changes it is a suite
testing a configuration nobody runs. A longer fixture costs ten seconds and
tests the real thing.
