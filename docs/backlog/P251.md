## P251-01 — the 18 updates that fit inside the declared ranges

**Review gate:** none (no `auth`, `assessment`, `eiv` or `certificates` source
changed) · lockfile and version ranges only

**Context**

`.github/dependabot.yml` ignores every `version-update:semver-major`, so all
drift on this repository accumulates as patches and minors that nothing ever
applies — Dependabot opens the PRs, and majors are the only thing it is told to
leave alone. Measured drift at `382d542`: **21 outdated**, of which 18 are
inside the declared caret ranges and 3 are majors (P251-02).

A first measurement said 51, all major. That was wrong and is recorded here
because the mistake is reusable: `node_modules` had not been installed in this
container, so `pnpm outdated` was comparing the registry against an empty tree
and reporting `current: undefined`. **`pnpm outdated` is a claim about an
install, not about `package.json`** — run `pnpm install --frozen-lockfile`
first or the number is fiction.

**Scope**

`pnpm update -r`. Every range is a caret, so this moves the 18 and cannot reach
the 3 majors.

Four of the 18 are production dependencies: `@nestjs/common`, `@nestjs/core`,
`@nestjs/platform-express` 12.1.0 → 12.1.2, `@node-rs/argon2` 2.2.1 → 2.2.2 and
`nodemailer` 10.0.10 → 10.0.15.

**Acceptance criteria**

- [x] `pnpm lint`, `pnpm format`, `pnpm typecheck` (31 tasks), `pnpm test`
      (30 tasks), `pnpm check:static` (26 checks), `pnpm test:wp` (166 checks),
      `node scripts/audit-dependencies.test.mjs` (10 passed) and
      `node scripts/audit-dependencies.mjs --prod` all exit 0.
- [x] `pnpm test:integration` — 28 files, 718 tests passed.
- [x] `pnpm test:e2e` — 35 passed, 3 failed, **and the same 3 fail identically
      on `382d542` with the base lockfile installed**, so the update is neutral
      on the journey. The three are pre-existing on `main` and are
      P251-03/P251-04 below, not fallout from this change.

**Definition of done**

The three advisories `pnpm audit` reports are unchanged by this and are all
development-only, proven with `pnpm why -r`: `braces` (high) and
`postcss-selector-parser` (moderate) arrive via `tailwindcss@3.4.19`,
`source-map-js` (high) via `jsdom`/`vitest` through `css-tree`. Nothing they
touch is shipped or served. Two of the three clear only with Tailwind 4, which

## P251-02 — the three majors, each held for a reason a command printed

**Review gate:** none · no code change

Dependabot is configured never to raise these, so a major moves only when
somebody decides to. Each decision below is the decision, with its evidence.

### `typescript` 5.9.3 → 7.0.2 — **held, blocked**

`npm view @typescript-eslint/parser@8.71.1 peerDependencies` prints

```
{ eslint: '^8.57.0 || ^9.0.0 || ^10.0.0', typescript: '>=4.8.4 <6.1.0' }
```

TypeScript 7 is outside that range, and every typescript-eslint line that is
not 8.x is an alpha (`rc-v4: 4.0.0-alpha.16`, `rc-v5: 5.0.0-alpha.42`,
`rc-v6: 7.0.0-alpha.0`). Taking TS 7 today means an alpha linter on a platform
whose lint rules are part of the compliance floor. Nothing else in the
workspace declares a `typescript` peer — checked `@nestjs/core@12.1.2`,
`vite@8.3.3`, `vitest@5.0.3` and `drizzle-kit`, all empty.

Revisit when typescript-eslint publishes a stable line accepting TS 7. It is
then its own ticket, because the native port changes what the compiler API
offers and `scripts/` reads it.

### `tailwindcss` 3.4.19 → 4.3.3 — **held, own ticket**

3.4.19 is the registry's `v3-lts` tag, so the current line is supported rather
than abandoned. Tailwind 4 is a CSS-engine migration, not a version bump: three
`tailwind.config.js` files and the 121-line `packages/config/tailwind.preset.js`
become CSS `@theme`, each app's `postcss.config.js` changes plugin, and default
values move.

The part that needs its own verification before anything is attempted:
`apps/widget/src/element.ts:69` imports the compiled sheet as
`./styles.css?inline` and installs it into a **closed shadow root** via
`adoptedStyleSheets` (`element.ts:504-507`). Tailwind 4 emits `@property`
registrations for its theme variables. Whether those take effect from a sheet
adopted into a shadow root is **not verified here** and is the first thing the
ticket that does this must establish — a silent failure there is every token in
the learner widget falling back to its initial value, which no API test can see
(§9.13).

It is also the only one of the three that would clear two of the three
development-only advisories.

### `@types/node` 22.20.4 → 26.6.4 — **held deliberately, and now enforced**

This one is not "later", it is **wrong**. The runtime is Node 22 in all five
places that declare it:

| Declared in                        | Value                   |
| ---------------------------------- | ----------------------- |
| `.nvmrc`                           | `22`                    |
| `package.json` `engines.node`      | `>=22`                  |
| `.github/workflows/deploy.yml:903` | `node-version: 22`      |
| `Dockerfile:80` (deps stage)       | `node:22-bookworm-slim` |
| `Dockerfile:199` (api stage)       | `node:22-bookworm-slim` |

`@types/node` is not a library, it is a **description of the runtime**. On 26 it
would describe APIs that do not exist in the container, `pnpm typecheck` would
go green on a call that throws at runtime, and the failure would land in
production as a `TypeError` naming a method nobody can find in the docs for the
version actually installed. That is the quiet direction of §9.10b: one value,
six readers, and the one that disagrees is the one nothing checks.

The update itself took it to 22.20.5, which is current _within_ the right major.

**So the hold is a check, not a sentence** — §9.9: a README line instructing a
human to keep two numbers equal is two numbers that will diverge.

`scripts/check-node-version.mjs` makes `.nvmrc` the one home and derives every
other reader from it: each `engines.node` floor, each workflow `node-version:`
literal, each `node-version-file:` (accepted only when it is `.nvmrc` — any
other path is a second home), each `FROM node:` in the `Dockerfile`, and each
`@types/node` range in the workspace. It is `pnpm check:node-version`, inside
`check:static`, so it runs at a terminal and in CI alike — `check-ci-parity`
now reports 27 checks inside `check:static` and none unreachable from a merge
gate.

Prose is deliberately out of scope. `.github/dependabot.yml` and
`docs/deployment.md` both name `node:22-bookworm-slim` in comments; a stale
sentence there misleads a reader without misleading a build, and matching the
shape in every document is how a check ships with an exemption list (§9.1).

**Acceptance criteria**

- [x] Green on the tree: it names Node 22 from `.nvmrc` and the counts that
      agreed with it — 1 engines floor, 5 workflow declarations, 2 images and
      5 `@types/node` ranges.
- [x] Red on `@types/node` at `^26.6.4` — the bump actually on offer — in
      `packages/secrets/package.json` and in the root manifest.
- [x] Red on `engines.node` at `>=24`.
- [x] Red on `deploy.yml` pinning `node-version: 20`.
- [x] Red on a `node-version-file:` pointing anywhere but `.nvmrc`.
- [x] Red on the `Dockerfile` api stage at `node:26-bookworm-slim`.
- [x] Red on a `.nvmrc` holding `lts/*` rather than a version.
- [x] Red when the parser stops matching — the workflow directory renamed
      reports `found 0 workflows declaration(s), expected at least 4`, rather
      than passing over nothing (§9.1's third form).

**The sabotage that proved the check and then proved itself**

The first attempt at the `@types/node` case edited `apps/api/package.json` and
the check stayed **green**. That was not the check failing; `apps/api` does not
declare `@types/node` at all, so the `sed` was a no-op and nothing was ever
exercised. Only five of the twenty manifests declare it — the root,
`apps/e2e`, `apps/eiv-harness`, `packages/eiv-client`, `packages/secrets`.

Recorded because it is §9.1 landing on the person applying §9.1: **a sabotage
is a check too, and an unverified one reports the absence of its own edit as
the presence of a gate.** A sabotage that leaves the tree unchanged is
indistinguishable from a check that works. Confirm the edit landed — `grep` the
sabotaged line — before reading the green as evidence of anything.

## P251-05 — a 404 a handler chose is not the router's 404

**Review gate:** human — touches `auth`'s neighbour, the global exception
filter, and changes what every refusal says · closes P251-03

**Context**

P249-01 (`f5b37ef`, 05.10.2026) rebuilt a 404's `detail` as
`Cannot <method> <path>`, to strip the query string out of the router's own
`Cannot GET <originalUrl>` — which is the one place the filter would otherwise
echo a token it had taken care to keep out of `instance` and out of the log.
Right about the leak, wrong about the population: it switched on **status**, and
a 404 is not only the router's.

Five deliberate 404s are thrown by our own handlers, and the `grep` is the whole
list:

| Site                             | What it means                          |
| -------------------------------- | -------------------------------------- |
| `branding.controller.ts:156`     | no project named, so no font           |
| `branding.controller.ts:160`     | the project has no font                |
| `public-media.controller.ts:88`  | the id is not a uuid                   |
| `public-media.controller.ts:96`  | `resolve_public_image` matched nothing |
| `public-media.controller.ts:109` | the key would not sign                 |

All five began answering that the route did not exist. Both controllers are
`@Public()` — these are the only routes a learner's browser fetches with no
token at all, which is where a false statement about the system is least
affordable (§9.4).

The filter's own header asserted the thing that was wrong — "**except a 404**,
whose message is the router's `Cannot GET <originalUrl>`" — which is §11.9
exactly: a comment is a claim, and this one stopped the next reader looking.

**Why `routes.spec.ts` believed it**

That spec decides "documented but not implemented" from the wording of the 404
body, and it carries a negative control for precisely this risk. The control
did not fire, because it is written for the other direction: it asserts that an
**unrouted** path is still _detected_. P249-01 made a **routed** path
*mis*detected, and nothing asserted against that.

So the missing half is now there — "a routed path that 404s on purpose is not
mistaken for an absent one", over `GET /branding/font` with no project, which is
certainly routed and certainly 404s by design.

**Scope**

`ROUTER_404 = /^Cannot\s+[A-Z]+\s+\//` — the router's wording is what tells
the two apart, because at the filter there is nothing else: same subclass, same
status, no marker. Matching a framework's text is weak and the comment says so;
what makes it acceptable is which way it fails. A handler that happens to phrase
its own 404 that way gets the sentence it asked for, query-free. The expensive
direction — the router's URL reaching a log with a token in it — is the one the
pattern is wide enough to catch, for every method rather than only GET.

**Acceptance criteria**

- [x] A bare `NotFoundException` keeps its own message and the response carries
      no `Cannot GET`. Red before the fix.
- [x] A handler's `NotFoundException("no such object")` answers that detail.
      Red before the fix.
- [x] P249-01's property is kept: the router's own message is still rebuilt
      query-free, the token appears in neither the body nor the log, and it is
      rewritten for POST as well as GET. Green before and after — these two
      cases exist so the fix cannot undo what it was built on.
- [x] `routes.spec.ts`'s new positive control is red on the reverted filter,
      alongside the original `GET /branding/font` symptom, and green on the fix.
      The negative control and the parser floor stay green through both, which
      is what identifies the control that was missing.
- [x] `pnpm test:e2e` — 39 passed, 0 failed.

## P251-06 — the sign-in helper raced two witnesses to one screen

**Review gate:** none (test harness only; no product code) · closes P251-04

**Context**

`signInToConsole` raced four locators and mapped two of them to different
outcomes: the heading "Zwei-Faktor-Authentifizierung einrichten" → `enrol`, and
the field "Sechsstelliger Code" → `code`.

Those are the same screen. `SignIn.tsx` draws one `<form>`; the enrolment panel
— heading, QR, base32 key — is a block **above** the code field, and the field
is rendered under both branches (`SignIn.tsx:243`). So on an enrolment screen
both locators resolve, the race returns whichever Playwright saw first, and when
the field won the helper skipped reading the key and threw

```
e2e-operator@… was asked for a code this harness has no secret for
```

on the screen that was offering the secret three lines up. Nondeterministic by
construction, which is why it passed most runs — §11.10 in a browser: a test
that only ever observes one order of a race has not tested the race.

**Scope**

The field is the right single witness, because it is on **both** screens. Which
of the two it is, is then asked of the screen already up — `isVisible()` on the
heading, not a `waitFor`, since the form is there and there is nothing to wait
for. A `waitFor` would spend its timeout on every ordinary code prompt and give
back the cost the race was written to avoid.

`enrol` is gone from `Outcome`, with the type's comment saying why, so the next
person does not re-add an arm for a state a race cannot see.

**Acceptance criteria**

- [x] `apps/admin/src/components/SignIn.test.tsx` — the first test of this
      component, anywhere. It pins the overlap the helper now depends on: the
      enrolment panel offers a key **and** the field; an ordinary prompt offers
      the field and no key; the field alone therefore cannot tell them apart.
- [x] Red when the key is removed from the enrolment panel (1 failed).
- [x] Red when the field is moved out of the shared form onto the code screen
      only — the overlap gone (2 failed).
- [x] `pnpm test:e2e` — 39 passed, 0 failed.

A single green run does **not** prove a race is gone, and is not claimed to.
What the fix rests on is that there is no longer a race between those two
locators at all, and that their coexistence — the fact the old code got wrong —
is now asserted deterministically in a component test that runs in seconds.

**The class, swept**

`grep -rn 'Promise.race' apps packages` over the whole repository returns two
live sites. `apps/e2e/support/console.ts:158` is this one; its remaining arms
are the code field ("a second factor is asked for"), the two sidebar witnesses
(both mapping to `in`, so coexistence is harmless) and the timeout.
`pool-deadlock.integration.test.ts:118` races work against a deadline, whose
arms are mutually exclusive by construction. No third instance.

## P251-07 — `GET /media/{id}` is public, unauthenticated and not in the contract

**Review gate:** none yet · **not fixed here**, found during P251-05's sweep

`PublicMediaController` serves `GET /media/:id` — `@Public()`, no token, a 302
to a freshly signed object URL, bounded to images by `resolve_public_image`
(migration 0054). `grep -n '^  /media' contracts/openapi.yaml` returns nothing:
the path is absent.

Two consequences, both of the shape §9.1 is about. `routes.spec.ts` derives what
it probes from the contract, so the one public route added since it was written
is the one route it has never probed. And the SDK does not know the path, so
nothing derives a type for it.

Not absorbed into this ticket. Adding a path to `contracts/openapi.yaml` is a
contract-first change with `check:sdk` and contract-test fallout, and CLAUDE.md
§2 makes the contract the thing written **first** — retrofitting one is its own
work order, not a line in a dependency ticket.

Worth asking at the same time whether `routes.spec.ts` should gain the reverse
direction it deliberately does not have today: every `@Public()` route the API
registers must appear in the contract. That is the check that would have caught
this in P212 rather than in P251.
