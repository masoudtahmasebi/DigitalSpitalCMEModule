# P149 — The two decisions P148 left for a human

`P148.md` flagged two items and refused to take them unilaterally. Both have now
been decided. This records the decisions verbatim, what was built, and the
evidence.

The two are deliberate mirror images: **the same check, opposite failure modes**,
and the reason is the deadline rather than the code.

---

## P149-01 — `bootstrap-admin` asserts schema freshness, through a role of its own

### The decision, as given

> Do NOT grant `ds_app` SELECT on `schema_migrations`. Instead, add a separate,
> narrow, read-only database role/connection dedicated to this one check, so the
> application role `ds_app` remains untouched per ADR-0002.

### Reproduction, first

`bootstrap-admin` had no schema check — P148 reverted P147's, because it read
`MIGRATION_DATABASE_URL`, which is set on no compose service, and the documented
invocation runs in the `api` container. Confirmed at the P148 head: the file
carried only a comment explaining the absence, and `pnpm test:e2e` passed 28/28
without it.

### What was built

| Piece                                                                               | Where                                                                        |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `ds_schema_reader` — `LOGIN`, `NOBYPASSRLS NOSUPERUSER NOCREATEDB NOCREATEROLE`     | `infra/postgres/init-roles.sql`, in the existing guarded-`CREATE ROLE` block |
| `GRANT SELECT ON schema_migrations` — its entire authority                          | `db/migrations/0049_schema_reader_grant.sql`                                 |
| `DS_SCHEMA_READER_PASSWORD`, generated once like the others                         | `infra/deploy/secrets.sh`                                                    |
| `ALTER ROLE … PASSWORD` from `\getenv`, so production does not keep the dev literal | `infra/postgres/init-roles.sql`                                              |
| `SCHEMA_READER_DATABASE_URL` on the **api** service                                 | both compose files                                                           |
| `DS_SCHEMA_READER_PASSWORD` on the **postgres** service, for `\getenv`              | `docker-compose.prod.yml`                                                    |
| `schemaReaderDatabaseUrl()`                                                         | `apps/api/src/schema-freshness.ts`                                           |
| The call, failing closed                                                            | `apps/api/src/bootstrap-admin.ts`                                            |

The grant is a migration and not part of `init-roles.sql` because
`schema_migrations` **does not exist** when that file runs on a fresh database —
the migrator creates it on its first run. A grant there would fail on exactly
the installation this exists for.

### The check that would have prevented P148-01

`infra/deploy/deploy-vars.test.sh` now asserts that the api service carries
`SCHEMA_READER_DATABASE_URL` in both compose files, and that the postgres service
carries `DS_SCHEMA_READER_PASSWORD`. Nothing previously compared "what the code
reads" with "what the service provides", which is the whole of P148-01.

**It caught a regression of mine within a minute of existing**: adding a
backslash continuation to `secrets.sh`'s `export` line hid
`POSTGRES_SUPERUSER_PASSWORD_URL` from the test's parser. The export is one line
again, with a comment saying why.

### Evidence — four cases, all run

| Case                                | Command                                                    | Result                                                                                                                                                     |
| ----------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unset                               | `DATABASE_URL=… bootstrap-admin`                           | **exit 1** — "SCHEMA_READER_DATABASE_URL is required (the ds_schema_reader role)…"                                                                         |
| Unreachable                         | `SCHEMA_READER_DATABASE_URL=…127.0.0.1:1/nothing`          | **exit 1** — "connect ECONNREFUSED 127.0.0.1:1"                                                                                                            |
| **Real narrow role, grant present** | `…ds_schema_reader:…@…/ds_education_test`                  | **exit 0** — the administrator was created                                                                                                                 |
| **Grant revoked (sabotage)**        | `REVOKE SELECT ON schema_migrations FROM ds_schema_reader` | **exit 1** — "permission denied for table schema_migrations"                                                                                               |
| Grant restored                      | as above                                                   | check passes again; refuses downstream for the correct reason ("1 active super administrator(s) already exist"), which proves execution got past the check |

It fails **closed** in every failure mode. That is right here: nothing downstream
of a bootstrap is time-critical, and the alternative is P43-02's shape — "column
display_name does not exist" to somebody whose real problem is an un-migrated
database on their first five minutes with the platform.

### The latent path bug, verified in both contexts

P147 finding 8: `assertSchemaCurrent` resolved its migrations directory relative
to its own file — right in the image, wrong in a checkout. P148 fixed it. This
session verified both invocation contexts actually work:

- **from `dist/`** — the four cases above ran `node apps/api/dist/bootstrap-admin.js`
- **from source** — `npx tsx apps/api/src/bootstrap-admin.ts` reached the
  super-admin refusal, which is only possible once the migrations directory
  resolved and the check ran

## P149-02 — `subject-erasure` asserts, warns, and never refuses

### The decision, as given

> Add the `assertSchemaCurrent` check to `subject-erasure.ts`, but it must NEVER
> block a statutory GDPR erasure.
>
> - If the schema is current: proceed normally, no change in behavior.
> - If the schema check fails (stale schema, or the check itself errors for any
>   reason — connection failure, permission error, etc.): log a clear,
>   high-visibility warning/alert and PROCEED WITH THE ERASURE ANYWAY. The
>   erasure must never be delayed or refused because of this check, given the
>   statutory one-month deadline.
> - The warning must include enough detail for a human to act on it: which
>   subject/erasure request, what the schema check reported, and a timestamp.
> - Add an audit log entry noting the erasure proceeded despite a stale/failed
>   schema check, distinct from the normal successful-erasure audit entry.

### Test first, as required

`apps/api/test/integration/subject-erasure-cli.integration.test.ts` was written
**before** the implementation and watched fail:

```
× erases anyway, warns loudly, and records that it proceeded
AssertionError: expected '{\n  "userId": "c82eebba-…' to match /schema/iu
```

Red for the right reason: the erasure completed (exit 0, subject erased) and no
warning existed, because the feature did not.

### What was built

`schemaCheckOutcome()` returns `{ ok }` and **cannot throw** — every path ends in
a value, so `main` has nothing to catch. A `try`/`catch` at the call site would
have worked and would be one edit away from letting an exception escape; making
it structural is the point.

`reportUnverifiedSchema()` speaks in three places, because each fails
differently: the terminal an operator is standing at, the webhook that reaches
somebody who is not (same envelope `EivAlertService` posts, so one receiver reads
both), and an append-only `gdpr.erasure_schema_check_failed` row that outlives
both. Every one is best-effort; the function throws nothing, because it runs
_because_ something already went wrong.

Placed after `--confirm` so a dry run alarms nobody, and **before**
`erase_subject` so the audit row exists even if the erasure itself then fails.

### Evidence

|                                                |                                                |
| ---------------------------------------------- | ---------------------------------------------- |
| Before implementation                          | **RED** — no warning, no audit row             |
| After                                          | **GREEN** — 578 passed (23 files)              |
| Sabotage: suppress the report at the call site | **RED** — `expected '{…}' to match /schema/iu` |
| Restored                                       | **GREEN**                                      |

The test breaks the check by pointing the reader at a refused connection rather
than by rolling back a migration — a genuinely stale schema cannot be arranged
without breaking every other suite sharing the database, and a connection
failure is the case the decision explicitly names.

### One thing the check flagged, correctly

`check:tenant-reads` failed on the new `audit_log` insert: a tenant-scoped table
written on the bare pool. It is a reviewed exemption now, with the reason — the
tool runs as `ds_migrator` outside any tenant context by design (an erasure spans
customers, which is why it refuses to run as `ds_app`), and it inserts
`customer_id NULL`, the shape `AuditService.recordSystem` uses. Wrapping it in
`runInTenant` would require inventing a customer for a cross-customer fact.
Watched red by removing the exemption.

## Deviations from the instructions, flagged rather than improvised past

1. **"Wire it into the api service's compose/env configuration"** — done, and it
   is worth saying that the repository's _existing_ pattern for
   `MIGRATION_DATABASE_URL` is the opposite: passed per-invocation with
   `compose run -e`, never on a service. The instruction is right for this
   variable precisely because the command that needs it is typed by hand and
   carries no `-e` — which is what P148-01 was.

2. **"use whatever alerting mechanism this repo already has"** — there is no
   shared alert helper. `EivAlertService` owns a `WebhookAlertSink` typed to
   `EivAlert`, and P148's `ALERT_WEBHOOK_URL` finding was a boot-time
   `logger.warn`, not a sink. Rather than widen the EIV type or invent a
   framework for one caller, this posts the same JSON envelope directly through
   `withDeadline()` (P144). If a third caller appears, that envelope is the
   thing to extract.

3. **Two environment variables joined `READ_WITHOUT_DOCUMENTATION`** in
   `env-audit.mjs` rather than a template. They are generated into
   `secrets.env`, never set by a human — the same class as
   `DS_APP_PASSWORD_URL`. Documenting them would invite somebody to set one by
   hand and get a role and a URL that disagree.

4. **The CORS report that arrived with these instructions was not a defect.**
   `PATCH` refused at preflight on `api.digitalspital.com/admin/modules/…`. From
   source: `enableCors` sets no `methods`, the `cors` package default is
   `'GET,HEAD,PUT,PATCH,POST,DELETE'` (`node_modules/.../cors/lib/index.js:10`),
   `@Patch("modules/:id")` and `@Patch("chapters/:id")` exist, and the Caddyfile
   states CORS is the API's job and sets no such header — nor has it ever, per
   `git log -S`. Before I could reproduce it the reporter confirmed: **a browser
   CORS extension on the colleague's machine.** No change made. Recorded because
   the near-miss is the point — a `methods` list added "to be safe" would have
   been a permanent fix for a defect that never existed.

## Not addressed — a real defect, out of this ticket's scope

**Upload progress disappears when the media dialog's tab changes.** Reported with
a network panel showing `video-…mp4?X-Amz-…` still `(pending)` while the UI shows
no progress, because switching to _Media library_ and back to _Upload file_
unmounts the progress state. The user's own words: _"he may try to do a new
upload, as he is not seeing the progress"_ — a duplicate multi-gigabyte upload,
which is worse than the missing indicator.

Not fixed here: the instruction for this session was explicit that these are two
isolated changes and no other code path is to be touched. It needs its own
ticket.
