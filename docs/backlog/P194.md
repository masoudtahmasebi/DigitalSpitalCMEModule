# P194 — The posture reads never had the credentials to ask

**Raised by:** the client, 04.09.2026: _"deployment job is failing, fix it and
deploy it"_. Deploy 118 — the first run in which the reads could report their
own errors (P189-01) — finally said why, and the answer was neither of the two
things I had guessed.

**Closes:** the acceptance criterion P189 left open — _"whether the reads answer
on the next deploy is settled by the next run's log"_. They did not. The log
settled it.

---

## What the log said

Both posture steps of deploy 118, verbatim:

```
##[warning]platform_settings could not be read on the host — the read said:
error while interpolating services.api.environment.SECRETS_KMS_KEY:
required variable SECRETS_KMS_KEY is missing a value:
SECRETS_KMS_KEY is required — openssl rand -base64 32
```

`docker compose` interpolates the **whole file** before it looks at which
service the command names, and `docker-compose.prod.yml:211` has

```yaml
SECRETS_KMS_KEY: ${SECRETS_KMS_KEY:?SECRETS_KMS_KEY is required — openssl rand -base64 32}
```

The `:?` form aborts. So `exec postgres psql` never ran — and neither would
`ps`, `logs` or `config`. The command being run has nothing to do with it.

Verified locally rather than reasoned about, with the docker CLI and no daemon,
because interpolation happens client-side:

```
$ env -i PATH=$PATH HOME=$HOME docker compose -f docker-compose.prod.yml ps
… level=warning msg="The \"DS_COMMIT\" variable is not set…"   (×8)
error while interpolating services.api.environment.SECRETS_KMS_KEY: …
exit=1
```

Byte-identical to the deploy's message.

## Why the host has it and the reads did not

`deploy.sh` sources **two** files (its own header says so, lines 15–19):

| file                         | written by                       | holds                                             |
| ---------------------------- | -------------------------------- | ------------------------------------------------- |
| `~/ds-education/config.env`  | a human, once                    | domains, `POSTGRES_DB`, the superuser's _name_    |
| `~/ds-education/secrets.env` | `secrets.sh`, first deploy, 0600 | every password, `SECRETS_KMS_KEY`, the backup key |

Both posture steps sourced only the first. `SECRETS_KMS_KEY` is not in it and
never will be, and neither is `POSTGRES_SUPERUSER_PASSWORD` — so even past the
interpolation the `psql` authentication would have failed too. One omission,
two failures, the first hiding the second.

`dsc` gets this right and its own comment names the trap — _"a shell which has
never seen `secrets.env`"_. The knowledge existed in the repository. The
workflow reproduced the mistake anyway, which is §9.10b: a value with one home
and a second reader that assembled its own.

## The two explanations I published before this one, and why they were wrong

Both are in the repository, in commit messages, and CLAUDE.md §11 rule 13 says
a correction is a claim too — so:

- **P189-01: the login shell.** `deploy.sh` runs over `ssh -tt` and the reads
  over plain `ssh`, so I gave them `bash -lc`. That was the only difference I
  could see and I labelled it a candidate rather than a diagnosis, which was
  right — it was not the cause. A login shell does not source `secrets.env`.
  The change is kept because it costs nothing, not because it did anything.
- **P189-03: the 300-character budget.** Deploy 115 spent all of it on compose's
  warnings about unset `DS_*` variables, so I dropped `level=warning` lines and
  kept the tail. That change was correct and is why deploy 118 could answer at
  all — but I described the warnings as _noise_, and they were not. They were
  the same fault's other half: `deploy.sh` exports those variables and a bare
  read does not. The eight warnings and the one error had a single cause, and I
  filed the warnings under "crowding out the real message" instead of reading
  them as the message.

Four deploys — 115, 116, 117, 118 — and for three of them the journey was
skipped by a guard failing closed on a question it could not ask.

## The same defect in the watchdog, which nobody reported

§9.11: what else has this shape? `infra/deploy/watchdog.sh` loads `config.env`
alone and then calls `compose`. Every call dies at interpolation, and the two
that matter swallow it:

```bash
done < <(compose ps --format '…' 2>/dev/null || true)
```

Verified with a stub `docker` that fails the way compose fails: check 1 iterates
over **nothing** and contributes **zero problems**, on a host where every
container could be down. Check 2 does fire, so the watchdog is not silent — it
reports

```
DS Education on …: 1 problem(s)
API readiness: 000 could not run the check
```

which is an alert about the API for a fault in the watchdog. §9.4: a message
that is wrong about the state is worse than none, and this one has been sending
somebody to look at the wrong service.

`watchdog.sh` is a systemd unit on the host, so **whether it is installed and
running there is not answerable from this repository** (§9.9). What is fixed is
the script; what it does on the installation is a thing to check on the host.

## What changed

| P194-01 | `infra/deploy/host-env.sh` — one home for "the environment a command needs to talk to the stack". Loads both files, **read-only** (`ds_ensure_secrets` generates, which is right for a deploy and wrong for a report), and refuses **by filename** rather than letting compose fail four layers down. `watchdog.sh` uses it and now exits saying the fault is its own. |
| P194-02 | `infra/deploy/host-query.sh` — the connection, assembled once. `./host-query.sh eiv\|mail`. The SQL stays in `eiv-endpoint.sh` and `mail-posture.sh`, which is where `deploy.sh` reads it from. |
| P194-03 | `infra/deploy/eiv-posture.sh` — the verdict that decides whether the journey runs, moved out of a `bash -lc` string inside an `ssh` inside a YAML block scalar, where nothing could execute it. |
| P194-04 | `scripts/check-compose-env.mjs` — the class check, in `pnpm verify` and CI. |
| P194-05 | The watchdog's census no longer reads an empty answer as a healthy one. |

The two workflow steps are now one `ssh` line each, down from roughly forty
lines of nested quoting apiece.

## Watched red

Every check here was broken on purpose and observed to fail, per §9.1:

- `check-compose-env` against **unmodified `main`** names all three real
  defects — `watchdog.sh` and both `run:` blocks — and passes on the fix. Its
  first version reported "2 callers" and would have missed `deploy.sh` and
  `watchdog.sh` entirely, because both reach compose through
  `COMPOSE_FILE="…"` rather than naming the file at the call. That is §9.1's
  second form in the check written to fix §9.1, caught by asking why the number
  was 2 and not 4.
- `host-env.test.sh` — removing the `secrets.env` source fails 3 cases;
  skipping it when absent instead of refusing fails 2.
- `eiv-posture.test.sh` — taking the armed flag from the last field fails
  `live|f|t`; taking consent from the middle fails `live|t|f`.
- `watchdog.test.sh` — reverting the environment load fails the two cases that
  assert it names the file and blames itself; dropping the census guard
  reproduces the exact misleading output above.

One expectation of mine was wrong and the rule was right: `mock|t|t` with **no**
`EIV_MOCK_BASE_URL` correctly answers "files live". `ds_eiv_endpoint_url` maps
an unresolvable choice to `about:unknown` on purpose, so a typo fails closed.
The test now asserts the real behaviour and says why.

## P194-07 — deploy 119, and the third source

The fix worked and the read still failed, with a **different** error — which is
the evidence that the first half was right:

```
xx the query ran but answered nothing usable:
invalid spec: :/etc/caddy/sites:ro: empty section between colons
```

An empty `${DS_SITES_DIR}` in the caddy service's volume list. `DS_SITES_DIR` is
in neither file: it is **derived**, by `ds_derive_domains` in `domains.sh`, and
`deploy.sh` calls it. So the host environment has three sources, not two, and
the third is the one that is easy to miss because it is not a file somebody
forgot — it is a function call.

`ds_load_host_env` now derives too, through `domains.sh` rather than a second
copy of the rule.

The same deploy also printed, from `deploy.sh`'s own read:

```
==> EIV posture: endpoint=live armed=false live-consent=false
```

So the installation is on the live register with the **worker switched off**,
and the journey would in fact have been allowed to run. It was skipped anyway,
because the workflow's read failed and fails closed. That is the guard behaving
correctly on a question it could not ask — and the reason for the whole ticket.

### The check that ends this, rather than the fix that ends this instance

Two deploys, two parse failures, one shape: **compose refuses to parse the
whole file, and a caller addressing one service does not get to skip the rest.**
Both are reproducible with no daemon, no stack and no host, because compose
interpolates client-side.

So `host-env.test.sh` now runs

```
ds_load_host_env && docker compose -f ./docker-compose.prod.yml config --quiet
```

against a fixture state directory. That single case would have caught **both**
failures before either deploy. It was watched red before the fix, with the exact
byte-for-byte message deploy 119 sent back.

When `docker` is not installed it prints `NOTE … did NOT run` rather than
skipping quietly, because a run without this case has not checked the thing the
file exists for (§9.1).
