### P11-01 · Standalone learner portal

- **jira:** _(unassigned)_
- **Estimate:** 8 h · **Week:** post-plan · **Depends on:** P5-01, P9-01
- **Review gate:** human — auth

**Context**
ADR-0007 says the API is headless and hosts are adapters at the edge. With one
host that is a claim rather than a property: anything WordPress happens to
provide can leak into the design unnoticed, and nobody finds out until the second
customer. A second host that shares no code with the first is the test.

It is also a product need in its own right — a customer without a WordPress site,
or DigitalSpital demonstrating the platform without one.

**Scope**

- `apps/portal`: a Vite SPA that authenticates against Keycloak (Authorization
  Code + PKCE), lists courses with the existing facets and pagination, and mounts
  `<ds-lms>` for the course a learner picks.
- Extract the PKCE flow from `apps/admin` into `packages/oidc`, shared by both,
  with the flow's security tests moving to it.
- `scripts/bundle-widget.mjs`: one script that copies the built widget artifact
  into a host adapter. Used by both the WordPress plugin and the portal.
- Dockerfile, nginx config with SPA fallback, a Caddy site with a CSP, a compose
  service, and the deploy workflow.

**Acceptance criteria**

- [x] The portal signs a learner in, lists courses, and opens one in `<ds-lms>`
- [x] The portal holds no refresh token; a 401 sends the browser back through
      Keycloak rather than renewing silently
- [x] The access token is never written to `localStorage`, `sessionStorage` or a
      cookie — asserted by test
- [x] The console's and the portal's PKCE parameters use distinct storage keys,
      so running both on `localhost` does not have one clobber the other
- [x] The portal loads the **artifact** `apps/widget` produced, not its source
- [x] Routing is path-based and bookmarkable; the nginx config serves
      `index.html` for any unmatched path
- [x] The portal appears in `CORS_ALLOWED_ORIGINS` like any other origin — it has
      no privileged standing with the API
- [x] `jsx-a11y` and `react-hooks` rules apply to the new app

**Additional definition of done**

- [x] `packages/oidc` carries the login flow's security tests, verified by
      deliberately breaking the `state` check and watching the CSRF test fail
- [x] No German copy duplicated between the widget and the portal —
      `germanDuration` moved to `@ds/domain` rather than being copied

**Amended by P5-11: the portal no longer has a catalogue of its own.**

It did, and that was the mistake this ticket's own context warns about, made in
the other direction. ADR-0007 says a host adapter mounts the widget and supplies
a token; the portal did that for the course screen and then hand-wrote a second
catalogue — a second React implementation of approved layout §4.1, calling the
same `GET /courses`, with its own delivery-type control, its own facet controls
and its own pagination. Two implementations of one design, and only the widget's
had tests. It had already drifted: chips where the layout specifies dropdowns
with removable tag chips, and no numbered pagination at all.

The widget already renders the catalogue when given no `course` attribute. What
was missing was a way for a host that owns URLs to hear the pick — now the
cancelable `ds-lms:course-open` event, Contract 3 in ADR-0007.

Deleted: `components/Catalogue.tsx`, `components/CourseMount.tsx` (replaced by
`WidgetMount.tsx`), `api.ts`, and two thirds of the portal's locale. The portal
now makes **no API call of its own** — it authenticates, routes, and mounts.
That is the whole of what a host adapter is, and it is a stronger test of
ADR-0007 than the version with a bespoke screen in it.

### P11-02 · Extension points

- **jira:** _(unassigned)_
- **Estimate:** 4 h · **Week:** post-plan · **Depends on:** P7-06
- **Review gate:** human — eiv

**Context**
Three things will genuinely differ between customers: which accreditation
interface receives a Punktemeldung, how a Teilnahmebescheinigung is rendered, and
how it reaches the physician. One thing must never differ: anything that decides
whether a physician earned a CME point.

There was already a seam — `EivSubmitterPort` — but a local interface documents
one extension and says nothing about which extensions must not exist. That is the
half carrying the compliance risk.

**Scope**

- `packages/plugin-api`: four capability contracts, a registry with exactly one
  implementation per capability, and the explicit list of what is **not**
  extensible.
- `EivAccreditationReporter` in `@ds/eiv-client`, implementing the contract
  without importing anything from `apps/api`.
- `apps/api/src/plugins.ts`: the one file naming what this deployment installs,
  and what it deliberately does not.
- ADR-0010.

**Acceptance criteria**

- [x] A capability receives a decision and never makes one — no contract is
      passed a watch percentage, a quiz score or a pass flag
- [x] The forbidden list is written in `capabilities.ts`, not only in the ADR
- [x] Registering a second implementation for one capability throws, naming the
      incumbent
- [x] The registry seals after wiring; registration afterwards throws
- [x] `find()` returning `undefined` is a supported state and does not crash
- [x] No runtime plugin loading: no directory scan, no manifest, no dynamic
      `import()` of a configured path
- [x] The EIV sweep is behaviourally unchanged — same tests, same refusals
- [x] Credentials travel in `ParticipationReport.credentials` and appear in no
      log, no audit record and no error message

**Additional definition of done**

- [x] The reporter lives outside `apps/api`, proving the seam is real rather
      than a rename
- [x] `installPlugins` is reachable from every path that boots the API,
      including the integration suites — verified by running them

## Not built, and why

- **`deliveryChannel` has no implementation.** Certificate email is P8-03 and
  remains unbuilt; declaring the contract is not building the feature. The
  absence is why nothing is sent.
- **`contentIngestor` has no implementation.** Storyblok is on the deferred list
  (roadmap §4) and this interface is not permission to build it. It exists so
  that when somebody does, the shape is already decided and the "read it live
  from the CMS" version is visibly not what was agreed.
- **`certificateRenderer` is declared but unregistered.** There is one renderer,
  injected directly into `CertificateService`. It moves behind the registry the
  day a second one exists; registering a capability with one implementation and
  no prospect of another is indirection for its own sake.
