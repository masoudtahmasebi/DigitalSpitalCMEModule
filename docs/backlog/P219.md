# P219 — the admin console redesign: baseline

Masoud's work order: the admin panel at `verwaltung.digitalspital.com` is
_"visually weak, difficult to scan, and not pleasant to use"_, and should be
rebuilt to the standard of TailAdmin / Mosaic / Admin One **as inspiration, not
as a template to clone**. Explicit rule in the order: _"Do not merge or deploy in
this session."_ This ticket is the baseline it asks for, written before any
visual change.

Everything below is `VERIFIED` from source unless labelled.

---

migrating to Next.js would add a server to a product whose deployment story is
four static sites plus one API.

## 2. Screens — `VERIFIED` from `routes.ts`

Fifteen addressable screens: `courses`, `new-course`, `course` (with a nested
tab), `organisation`, `branding`, `copy`, `media`, `punktemeldungen`,
`customers`, `platform-eiv`, `participants`, `learners`, `certificates`,
`staff`, `security`.

Navigation groups today: **ANGEBOT**, **TEILNAHME**, **EINSTELLUNGEN** — which is
already close to what the order proposes, and the order's own rule applies:
_do not add a screen to the sidebar unless the API and role matrix support it._

Capabilities gating the nav: `project` (×4), `learner_record` (×2),
`certificate` (×2), `customer`, `platform`, `staff_user`, and one row
deliberately ungated. `pnpm check:roles` derives 4 roles × 13 screens from the
capability matrix, the console's `NAV` and the API's `@Roles` decorators, and is
the gate any navigation change has to keep green.

## 3. The finding that shapes the work

**`App.tsx` is 1,929 lines** and holds the shell, the router, the nav table, the
view union and most screen composition. That is the single biggest obstacle to
this redesign and the reason the order's _"avoid one giant App.tsx rewrite"_ is
right — it cannot be rewritten in one reviewable diff.

So the first slice is **extraction, not decoration**: shell, sidebar, top bar,
breadcrumbs and page header out of `App.tsx` into composable pieces with tests,
leaving behaviour identical. A redesign applied on top of a 1,900-line component
would be a second layer over the same problem.

## 4. What must not change — `VERIFIED` against the order

Auth/TOTP/session, roles and grants, tenant isolation, server-side authorisation,
API routes and DTOs, course hierarchy and authoring rules, draft/publish/retract,
media upload including multipart resume/abort, participant support, EIV and
certificates, EFN protections, audit logging, write-only secrets.

The gates that enforce these and must stay green: `check:roles`,
`check:tenant-reads`, `check:content-lock`, `check:eiv-settings`,
`check:focus-ring`, `check:i18n`, `check:copy`, the 706 integration tests and
the browser journey.

## 5. License gate — `BLOCKED` until done

No reference code, SVG, font or asset is to be copied before its exact commit and
licence are recorded. **Nothing has been copied and nothing will be without that
record.** The intended approach is to implement the ideas with the existing
Tailwind preset, which makes the licence question moot for most of the work —
and the preset being _shared with the learner widget_ is itself a constraint the
order does not mention: a token changed for the console changes the physician's
screens too. Console-only tokens have to be namespaced or the widget re-verified.

## 6. Sequence

1. **Baseline** — this ticket.
2. Tokens + accessible primitives (console-scoped).
3. Shell extraction from `App.tsx`: sidebar, top bar, breadcrumbs, page header,
   responsive frame, role-derived nav.
4. Start page from real data — no invented KPIs.
5. Course list and course workspace.
6. Organisation/project screens.
7. Authoring and media flows.
8. Participants, certificates, EIV.
9. Settings, branding, copy, security.
10. Responsive/a11y/visual pass.

Slices 2–3 are PR A, 5+7 PR B, 6+8+9 PR C, per the order.
