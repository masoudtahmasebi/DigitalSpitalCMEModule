# P12 · Two identity planes and a complete admin panel

Implements ADR-0012. Splits staff authentication away from the customer's
Keycloak, makes learner authentication replaceable per project, and completes
the admin console so it moderates the whole hierarchy rather than the middle of
it.

**Review gate: human — auth.** Every ticket here touches authentication or
authorization.

## Why this exists

The admin console authenticated against MEDICE's Keycloak. Three consequences,
each of which alone would justify the change:

- A super administrator spans customers, so no customer's realm can own them.
- MEDICE's realm administrators could mint DigitalSpital super administrators.
- One missing audience mapper in one customer's client (S17) blocked every
  admin screen as well as every learner.

And the panel itself stops short of the hierarchy it is supposed to moderate:
**customers cannot be created at all** — the top of
`Customer → Department → Project → Course → Modul → Kapitel → Inhalt` has no
endpoint — and there is no user management and no certificate management.

## P12-01 · Staff identity: schema and rules — **done**

- **Estimate:** 4 h · **Depends on:** —

**Scope**

- `admin_users`, `admin_user_roles`, `admin_sessions`,
  `admin_credential_tokens`, `admin_audit_log` (migration 0017).
- The rules as pure functions in `@ds/domain/staff-identity`: password policy,
  lockout, session lifetime, second-factor requirement, who may grant what,
  invitation and reset validity.

**Acceptance criteria**

- [x] Password policy is a length floor plus a denylist, with no composition
      rules — NIST SP 800-63B, and because composition rules produce `Passwort1!`
- [x] Lockout clears on time, with no administrator needed, and measures from
      the _last_ failure so a slow attacker still trips it
- [x] Sessions expire on both an idle and an absolute limit, and report which
- [x] Revocation is distinguishable from a timeout, because only one of them
      means "try again"
- [x] `canGrant` refuses upward grants, cross-customer grants and
      self-escalation; every role pair is covered by an exhaustive sweep
- [x] Second factor required for `super_admin`; an unenrolled super admin is
      sent to enrolment rather than refused, which would be unrecoverable
- [x] `admin_audit_log` is append-only for `ds_app`, asserted inside the
      migration's own transaction
- [x] 42 tests; removing the escalation check fails two of them

**Notes.** The append-only `REVOKE` must name `ds_app`, not `PUBLIC` — the
default privileges grant is _to_ `ds_app`. The first draft got this wrong and
the in-migration assertion caught it.

## P12-01b · The fourth role, and the Mediathek's missing fields — **done**

- **Estimate:** 2 h · **Depends on:** P12-01

Scope and capability turned out to be different axes, and the first cut only
modelled the first. A `course_editor` and a `department_admin` can sit in the
same department and still differ on whether they may create a project in it —
ranking says who outranks whom, not who may create what.

**Acceptance criteria**

- [x] `course_editor` exists: courses and content, nothing else — "customer
      users who can create only courses, so they have limited access"
- [x] Only `super_admin` may create a customer, because a customer is the
      tenant boundary and nobody inside one may mint another
- [x] `department_admin` and `course_editor` manage no staff accounts — a
      department admin who could invite could invite themselves elsewhere
- [x] Capabilities never widen as the role narrows, asserted by a sweep
- [x] `contents.description` and `contents.thumbnail_url` added (0018), so the
      Mediathek card can render what the layout draws instead of a file size
- [x] `course_editor` may be customer-wide or department-scoped; a row with no
      customer is refused by the constraint

**Deliberately unchanged.** `canGrant` now checks capability _before_ rank, so a
department admin attempting to grant is refused with `not_permitted` rather than
`role_too_broad` — the more fundamental reason, and the one worth reporting.

## P12-02 · `IdentityProvider` port for learners

- **Estimate:** 5 h · **Depends on:** P12-01

**Scope**

- Extract `verifyToken` behind an `IdentityProvider` port with
  `KeycloakIdentityProvider` as the first implementation.
- `projects.identity_provider` names it; the existing `keycloak_*` columns
  become that implementation's configuration.
- `Principal.keycloakSub` → `subject`, plus `identity: "staff" | "learner"`.

**Acceptance criteria**

- [x] Adding a second provider is a new class and a row value — no change to
      `AuthGuard`, the schema shape or any endpoint
      — `IdentityProviderRegistry.forBinding` dispatches on
      `projects.identity_provider`; asserted with two providers in
      `identity-provider.test.ts`.
- [x] A project naming an unknown provider fails at boot, not at first request
      — `IdentityProviderBootCheck` compares the registry against the CHECK
      constraint's permitted set. Verified by widening the constraint to
      `azure_ad` on a real database: the process logged that
      `projects.identity_provider` permits a provider nothing implements, and
      exited 1 without opening the port.
- [x] The existing token-verifier tests pass unchanged through the port
      — 328 unit and 154 integration tests, including the auth pipeline suite,
      pass with no edits to their assertions.
- [x] `identity` reaches the audit log, so a submission records whether a
      physician or an operator triggered it
      — `audit_log.actor_identity` (migration 0020), fed from
      `Principal.identity`. `AuditEntry.actor` is a union, so an id without a
      population will not compile and `audit_log_actor_identity_agrees` refuses
      it at the database too.

**Notes**

- `Principal.keycloakSub` → `subject`, and the staff plane stopped synthesising
  `staff:<uuid>` to fill a field that named the wrong thing.
- Two defects were found by driving this rather than by reading it, both
  pre-existing and both fixed here:
  - `StaffAuthController` relied on `emitDecoratorMetadata` for its first
    constructor parameter. `pnpm dev` runs the API through `tsx`, which is
    esbuild and does not implement it, so the development server had not been
    able to start since P12-03. Every other controller already names its token
    with `@Inject`.
  - `main.ts` signalled a fatal bootstrap failure with `process.exitCode = 1`
    alone. The Postgres pool and Redis client keep the event loop alive, so the
    process logged the error and then hung — a crash that presents to an
    orchestrator as a slow start.
- Worker-written audit rows (`eiv.*`, `certificate.*`) are `system`: no human
  triggered that attempt. **P12-05's operator-triggered resubmit must pass a
  staff actor** — the union makes forgetting it a compile error rather than a
  silently wrong audit row.
- Admin writes currently audit as `learner`, which is accurate: the console
  still authenticates on the learner plane. They become `staff` when P12-06
  moves it over.

## P12-03 · Staff authentication API

- **Estimate:** 10 h · **Depends on:** P12-01, P12-02 · **Review gate:** human — auth

**Scope**

- `POST /admin/auth/login`, `/logout`, `/session`, `/totp/enrol`, `/totp/verify`,
  invitation acceptance and password reset.
- Argon2id hashing; opaque sessions in an httpOnly `SameSite=Lax` cookie scoped
  to the parent domain; double-submit CSRF for state-changing requests.
- `AuthGuard` accepts both planes and yields one `Principal`.

**Acceptance criteria**

- [ ] Login is constant-time with respect to whether the account exists
- [ ] Reset and invitation responses never reveal whether an address is known
- [ ] A disabled account's sessions are revoked by the same statement
- [ ] Every state-changing request without a valid CSRF token is refused
- [ ] The session cookie is unreachable from JavaScript, asserted in a browser
- [ ] No password, token or TOTP secret in any log or any response body

## P12-04 · Complete the hierarchy

- **Estimate:** 8 h · **Depends on:** P12-03

**Scope**

- Customer CRUD — currently absent entirely.
- Authoring coverage for every content kind down to video, text, quiz and the
  per-content detail (completion state, score).

**Acceptance criteria**

- [ ] Every level of `Customer → … → Inhalt` is creatable, editable, reorderable
      and deletable from the console
- [ ] Deleting a level with children is refused with a message naming what
      would be lost, never cascaded silently
- [ ] A customer administrator cannot see, or address by id, another customer

## P12-05 · User and certificate moderation

- **Estimate:** 8 h · **Depends on:** P12-03

**Scope**

- Staff account management: invite, edit scope, disable, sign out everywhere.
- Learner records: view, correct a name before EIV submission (S4), erase per
  GDPR using the existing `erase_subject`.
- Certificates: list, regenerate, resend, revoke.

**Acceptance criteria**

- [ ] Correcting a learner's name after an EIV submission is refused, not
      silently allowed — the submitted name is what was reported
- [ ] Erasure goes through `erase_subject` and is recorded in the audit log
- [ ] Regenerating a certificate does not re-report to EIV
- [ ] An EFN is never shown in full to any staff role

- **Estimate:** 6 h · **Depends on:** P12-03, P12-04, P12-05

**Scope**

- Replace the OIDC flow with the local login, including the TOTP step.
- Restructure navigation around the full hierarchy.

**Acceptance criteria**

- [ ] `@ds/oidc` is no longer imported by `apps/admin` — the portal keeps it
- [ ] The tree is navigable at the 360 px floor
- [ ] Session expiry surfaces as a re-login prompt that preserves unsaved work,
