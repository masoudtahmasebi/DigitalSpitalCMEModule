# P232 — the wait that waits for something already there

Found by CI on **PR #79**, which changes only the learner widget. The failure
was in the admin console's test suite, and the same commit passed in the other
workflow run on that PR — the shape that reads as a flake and is not one.

```
AssertionError: expected [ 'Kunde auswählen …' ] to include 'Medice'
  ❯ src/App.test.tsx:280
```

---

## P232-01 — the defect is in the array

That array has **one** element: the placeholder. The whole failure is visible in
it.

```ts
await waitFor(() => expect(screen.getByRole("combobox")).toBeTruthy());
const options = [...screen.getByRole("combobox").querySelectorAll("option")].map(
  (o) => o.textContent,
);
expect(options).toContain("Medice");
```

`Shell` renders the `<select>` **immediately**, carrying one option —
_"Kunde auswählen …"_. The customers arrive later, from `adminListCustomers`.
So the `waitFor` is satisfied by the **empty** picker: it waits for a thing that
was already there. The assertions after it are ordinary `expect`s and do not
retry.

That is deploy 131's shape (P221) in a component test — _a gate whose condition
is not the condition anybody cares about_ — and §9.1's second form: the check
covers less than it claims.

## Proved, at the condition that actually occurs

Not by repetition. 150 repeats unloaded and 150 more under 3× CPU
oversubscription were all green, so the window is narrower than load alone
opens. Recorded rather than glossed, because "I could not reproduce it" is part
of the finding.

Instead, by **creating the condition**: `adminListCustomers` resolving on a
60 ms timer rather than immediately.

| Code                                | Customers delayed 60 ms                                            |
| ----------------------------------- | ------------------------------------------------------------------ |
| the shipped `waitFor` for existence | **fails** — `expected [ 'Kunde auswählen …' ] to include 'Medice'` |
| `customerOptions()`                 | passes                                                             |

The failure is CI's, character for character. That is the proof the fix
addresses the thing that happened, rather than making the symptom less likely.

### And the sabotage was inert the first two times

The first attempt at the table above reported **both** rows passing, which would
have meant the fix was pointless. It did not mean that: prettier had reformatted
the mock into a different shape from the string being replaced, so **the delay
was never inserted** and both runs measured the undelayed case.

P227-01 taught this exact lesson with a zero-height sabotage element. Written
down again because it is two for two: **an inert sabotage is indistinguishable
from a fix that does nothing, and the only way to tell them apart is to measure
the sabotage itself.** `grep -c setTimeout` before the run is what caught it.

## P232-02 — the class, which is nine call sites wide

`fireEvent.change` on a `<select>` whose options have not arrived sets the value
to `""` — jsdom has nothing matching to select. So the console is told _"no
customer"_, and every assertion after it waits for something that will not
happen.

Nine call sites did this. **None has been seen to fail**, and that is stated
plainly rather than dressed up as nine defects: they are one render away from
the failure above, and the fix is the same two lines.

Both are now helpers, and both wait for **the data** rather than for the
element:

- `customerOptions()` — resolves once the picker holds more than its
  placeholder, and hands back the option text.
- `chooseCustomer(id)` — waits for that, then changes the value.

Its failure message says what is wrong rather than timing out silently:

> the customer picker still holds only its placeholder, so the registry's answer
> has not been rendered yet and anything asserted about it now is asserted about
> an empty list

## What this ticket does not do

- **It does not add a checker for the class.** "This `waitFor` guards a
  condition that was already true" is not derivable from source — it depends on
  what the component renders before its data arrives, which is exactly the
  thing a static scan cannot know. The rule is written at the helper instead,
  where somebody reaching for `getByRole("combobox")` will meet it.
- **It does not touch the other 20 existence-only `waitFor`s** in the admin and
  widget suites. Counted, not estimated: **32** in total across both, of which
  **12** are the picker and **20** are not. Each of the 20 was read, and every
  one waits for something that appears _because of_ the thing under test — an
  error notice, a progress bar, a file-too-large message, a toast's
  `role="alert"`, a course title, the EFN field. There the wait and the
  assertion are the same condition, which is what makes them sound. Only the
  picker is rendered **before** its own content, and that is the whole
  difference.
- **It is not PR #79's.** That branch changes `apps/widget` only
  (`git diff --stat origin/main...HEAD -- apps/admin packages` is empty), so
  this is a separate branch off `main` rather than a widening of it.
