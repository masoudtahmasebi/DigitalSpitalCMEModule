## P48-01 · `./run-on-local.sh` and `infra/docker-compose.apps.yml` — **done**

- **Estimate:** 3 h · **Review gate: none**

`pnpm dev` runs the applications from source with watchers. It is the right loop
for writing code, and it has **never once exercised the thing that has actually
broken on the client's server.** Every failure in P44 and P45 lived in the gap
between "the code works" and "the image starts":

| Failure                                                      | Reachable from `pnpm dev`?                          |
| ------------------------------------------------------------ | --------------------------------------------------- |
| `DS_PROJECT_SLUG` required by the entrypoint, set by nothing | No — Vite never runs `ds-runtime-config.sh`         |
| `S3_ENDPOINT` rejected at API boot                           | No — no image, no `NODE_ENV=production`             |
| `../postgres/init-roles.sql` read from `$PWD`                | No — that is `deploy.sh`'s path, not a dev server's |

`infra/docker-compose.apps.yml` adds the four application services over
`infra/docker-compose.yml`, using the **same Dockerfile targets, the same
entrypoints and the same runtime-config mechanism** as production. A container
that will not start here will not start there — and finding that out now costs a
minute instead of a failed deploy and three rounds of pasted logs.

It is a second file rather than a copy of `docker-compose.prod.yml`, because
that one is the _deployment_: Caddy, TLS, real hostnames, secrets from
`~/ds-education/`, `pull_policy: never`. Reproducing it locally would mean
certificates, a hosts file, and a second copy of every environment variable —
and the copy is what drifts.

### Why a script rather than "docker compose up"

`up` alone gives an API answering 500 on every route with an empty schema behind
it. The schema and the data arrive through **one-shot containers** — the
migrator and the three seeds — which have to run between the database becoming
healthy and the applications being useful. That ordering is the whole content of
`run-on-local.sh`, and a README step somebody has to remember is a README step
somebody skips.

It also does what P44-03 taught: when a container does not come up, it prints
that container's own log rather than compose's summary.

## P48-02 · One port block, and the check that keeps it honest — **done**

- **Estimate:** 1.5 h · **Review gate: none**

| Port  | Service        |     | Port  | Service      |
| ----- | -------------- | --- | ----- | ------------ |
| 55390 | API            |     | 55395 | PostgreSQL   |
| 55391 | admin console  |     | 55396 | Redis        |
| 55392 | learner portal |     | 55397 | Keycloak     |
| 55393 | widget         |     | 55398 | Mailpit SMTP |
| 55394 | Mailpit        |     |       |              |

3000, 5173 and 5432 are the most contended ports on a developer's laptop. A
five-digit block is not, so "port is already allocated" stops being the first
thing this stack says to you. The variables are named `DS_LOCAL_*` because
`.env` may already carry a `POSTGRES_PORT` for the base stack, and reusing that
name would move the block silently.

### The distinction that costs an afternoon

**Inside the network the services reach each other by service name** —
`postgres:5432`, `redis:6379` — and nothing in the stack uses a published port.
But `DS_API_BASE` is written into `/config.js` and fetched by the **browser**,
so it must be `localhost:55390` and not `api:3000`. `ALLOWED_ORIGINS` is the
mirror image: the API must allow the origins a browser actually sends.

Get either wrong and every request fails CORS — **a browser-side failure with no
server-side trace at all**. That is precisely how `CORS_ALLOWED_ORIGINS` came to
be misspelled in `docker-compose.prod.yml` and survived until somebody clicked.

`pnpm check:local-ports` asserts all three: every published port inside the
block, no port published twice, and every browser-facing URL naming a published
port rather than a service. Confirmed by breaking each of the three and watching
it name the right one.

### What the existing checks absorbed

- `check-runtime-config.mjs` now reads **both** compose files. The local one
  runs the same `admin` and `portal` images, so it is a second place a required
  variable can be missing from — and a check that looked at one of two would be
  green on the broken half (§9.1).
- `paths.test.sh` covers `run-on-local.sh`: a developer runs it as
  `./run-on-local.sh` and as `DigitalSpitalCMEModule/run-on-local.sh` from one
  directory up, and P45-02 is what happens when those differ.

## The two modes, and why both exist

| Want                                          | Use                      |
| --------------------------------------------- | ------------------------ |
| Write code, see it reload                     | `pnpm start && pnpm dev` |
| Check it will start the way the server starts | `./run-on-local.sh`      |
| No Node or pnpm installed                     | `./run-on-local.sh`      |

They share one compose project, so switching re-creates the four dependency
containers with the other port mapping. A few seconds, no data loss —
`postgres-data` is a named volume — but worth knowing before it looks like
something went wrong.
