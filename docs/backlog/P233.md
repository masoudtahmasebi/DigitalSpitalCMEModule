# P233 — the blank page, and the error nobody hears

Package C's remaining screen-level items, and one of them exists because a
claim I made in P231 was wrong.

---

## P233-01 — there was no error boundary anywhere

```
$ grep -rn "componentDidCatch\|getDerivedStateFromError\|ErrorBoundary" apps/admin/src apps/widget/src
(nothing)
```

React's behaviour without one is to unmount the **whole tree**. So any
render-time throw on any console screen left an operator looking at a blank
white page.

### Why that is worse than saying nothing

It says nothing **in the shape of something else**. A blank page is what a
failed deploy looks like, what a wrong URL looks like, and what an expired
session looked like before P40. So the first thing it costs is the hour
somebody spends checking the server — §9.9's _"which build and which data?"_ —
for a fault in the bundle they already have.

### Two boundaries, not one

**Per screen**, inside `Shell`'s `<main>`: one broken screen keeps the app bar,
the sidebar and the customer picker, so the operator can go somewhere else.
That is what the review meant by _route-level_ — a failure the size of the
thing that failed.

**At the root**, in `main.tsx`: `Shell` itself can throw, and a boundary inside
the thing that broke catches nothing. That one is deliberately plain — no `de`
lookup, no shared component, its German and English side by side inline —
because reaching the locale module is exactly the kind of thing that might have
been what threw. **A fallback that depends on the code that crashed is not a
fallback.**

### `resetKey`, which is the half that is easy to miss

A boundary's state outlives the children it wraps. Without a reset, a screen
that threw once stays broken for the rest of the session — _the fix producing
§9.8's defect, a place you cannot get back to._ `Shell` passes `encode(view)`,
so it resets per destination; `view.kind` would have been wrong, because two
course tabs are two screens and one failing must not condemn the other.

### Watched red, three ways

| Sabotage                                     | Result                                                                 |
| -------------------------------------------- | ---------------------------------------------------------------------- |
| the boundary renders its children regardless | all four tests fail                                                    |
| the `resetKey` reset removed                 | _"the boundary stayed tripped after navigating to a different screen"_ |
| the boundary taken back out of `Shell`       | _"a broken screen took the navigation with it"_                        |

### What it does not do

**It does not report anywhere.** There is no client-side error endpoint on this
platform, and inventing one is a decision with a GDPR shape — a stack trace
from an operator's browser is personal data about that operator's session — so
it is `docs/show-stoppers.md`'s kind of question rather than mine (§7). The
message therefore says the one thing a person can act on, which is reload, and
names the build so a report to DigitalSpital identifies the bundle. Nothing
else on a crashed screen can say that: the footer went down with the rest.

## P233-02 — the error beside a field was silent, and my account of why was wrong

P231 listed as not-done:

> **Accessible status announcements.** `Notice` is not a live region, so a
> screen reader is not told when an error appears.

**That was false**, and it is corrected in P231 rather than deleted. `ui.tsx`
spreads `role="alert"` onto every `Notice` tone but `info`:

```
{...(props.tone === "info" ? {} : { role: "alert" })}
```

and the `info` exclusion is deliberate and documented at the prop. So an error,
a warning and a success **are** announced. I asserted the opposite without
reading the component (§11.9, §11.13).

### The real gap, which is narrower

Five bare `<p className="text-xs font-medium text-red-700">` across four files —
`Field`'s own problem line, both of `Learners`', `Organisation`'s and
`QuizEditor`'s — in **no live region at all**.

A sighted operator sees red appear under the input they just used. A screen
reader user gets nothing: the focus is still in the field, and nothing
interrupts to say the save was refused. §9.4 — say what the thing is, to the
person holding it.

`FieldError` is now the one home, with `role="alert"`, and all five go through
it. `Field` uses it too, so its **109 call sites** get it without anybody
remembering.

`role="alert"` rather than `aria-live="polite"` on purpose: polite waits for a
pause, and the thing being announced is a refusal of the action just taken. By
the time a pause arrives the operator has moved on and the sentence has lost
its subject.

### Watched red

| Sabotage                                      | Result                                                       |
| --------------------------------------------- | ------------------------------------------------------------ |
| `FieldError` loses its role, keeps its colour | _"Unable to find an accessible element with the role alert"_ |
| `Field` renders its own paragraph again       | the 109-call-sites test fails                                |

The assertion is `getByRole("alert")` and not a class check on purpose:
`toHaveClass("text-red-700")` passes on a paragraph nothing announces, which is
precisely the property that was broken.

## What is still open in Package C

- **Unsaved-change protection.** Leaving a half-filled form still loses it.
- **Focus handling after errors and dialogs.** P227 recorded keyboard flow as
  needing its own instrument, and that is still true.
- **Retry that preserves input** for a refused _mutation_. `LoadFailure`'s
  retry re-runs a load; a refused save has no retry control. Honest today —
  the form still holds what was typed — but not the designed behaviour.
- **429 with a wait time.** The API sends no `Retry-After`, so a number would
  be invented (§11.4).
- **`useSaver`'s `validating` state**, which still has nothing that sets it.

## Acceptance criteria

- [x] The absence of any boundary established by command, not assumed
- [x] Per-screen and root boundaries, with the reason each exists separately
- [x] The root fallback free of every dependency that could have been the fault
- [x] `resetKey`, so the fix does not create a screen you cannot return to
- [x] Three sabotages, each red on the property it is for
- [x] The P231 claim corrected where it was made, with the command that disproves it
- [x] The real gap found, fixed at one home, and adopted at all five sites
- [x] Asserted by role rather than by class, so the test goes red on the real defect
