# P77 — the platform sender, provable rather than hopeful

Asked for as _"can you create a smtp server for the emails inside the server"_,
then narrowed by the client to:

> _"from @digitalspital.com but without port 25, i need this for the admin
> panel, not sending certificates and so on"_

with the question that decided the design: _"why can't we use ports 465 or
587?"_

---

## Why no SMTP server was built

The three ports do two different jobs, and only one of them is a choice:

| Port    | Job                                                                   |
| ------- | --------------------------------------------------------------------- |
| **25**  | server-to-server delivery — a sender connecting to the recipient's MX |
| **587** | submission: an authenticated client handing mail to **its own** relay |
| **465** | the same submission, with TLS from the first byte                     |

A recipient's mail server does not accept mail from strangers on 465 or 587. So
"no port 25" does not constrain which port our server _listens_ on — it means
our server cannot perform the final delivery leg at all, and something with
port-25 access has to. That is a relay, by definition.

Once mail is relayed, a local Postfix adds a container, a config mount, DKIM key
management and a queue, and changes nothing about whether the message arrives.
For admin-panel mail that is infrastructure with no payoff, and CLAUDE.md §3
makes scope discipline a correctness property with 140 h fixed. So the answer to
"build an SMTP server" was **no, and here is why** — the capability the client
actually needed already existed.

`platform_smtp` (P40-01) is already the sender for exactly this audience; its
own table comment says so:

> The sender for mail about platform accounts — operator password resets and
> invitations. A project's own SMTP settings are on `projects` and are used for
> anything belonging to a customer.

Host, port, username, an encrypted password, `from_address`, `from_name`, and a
`secure` flag whose console label is literally „Verschlüsselt ab
Verbindungsaufbau (Port 465)". Both ports the client asked about were already
supported. What was missing was not a server. It was any way to find out whether
the settings worked.

## P77-01 · „Test-E-Mail senden"

Until now the only way to test the platform sender was to trigger a real
password reset and wait. That flow is **deliberately** silent about its outcome
— it answers the same for an unknown address, a disabled account and a
successful send, because otherwise it is an account-enumeration oracle (§9.5).
So a mistyped host produced no error anywhere an operator could see, and the
first evidence was a colleague who never received their invitation.

`POST /admin/auth/platform-smtp/test` sends a message with the **stored**
settings and returns what happened.

### The four decisions worth recording

**It sends only to the caller.** The recipient is the authenticated operator's
own address and is not an argument. An endpoint that mails an address chosen by
the caller is an open relay wearing a console button — it would let any operator
send from this platform's domain and reputation to anybody. Their own inbox is
also the only address that answers the question they are asking.

**It uses the stored settings, not the form.** Testing an unsaved draft would
mean accepting a plaintext password in a request body, and would answer a
question about a configuration that may never be saved. "Green here, broken in
production" is the shape this feature exists to remove. Save, then test.

**It reports the SMTP server's own words.** `535 5.7.8 Authentication
credentials invalid` and `getaddrinfo ENOTFOUND` are two different afternoons. A
paraphrase drops the response code, which is the whole diagnostic value. The
console shows the server's text verbatim.

**It is rate limited.** A button that makes the server send mail is an outbound
channel; an unlimited one spends the relay's reputation, which is the entire
asset the sender depends on. Five a minute — far more than somebody fixing a
host name, useless as a cannon.

The permission rule was **extracted, not restated**: `requirePlatformSenderAdmin`
now governs both the write and the test, so what the console offers and what the
API refuses cannot drift. That is the P74-01 lesson applied on the way past
(§9.2). The button is disabled while the stored sender could not send anything,
for the same reason — a control whose only outcome is an error is worse than an
absent one.

### Two tests of my own that could not go red

Both found by breaking the product and watching, which is the only reason they
are not still in the file (§9.1).

1. **"does not submit the settings form"** — clicked the button and asserted
   `writePlatformSender` was never called. jsdom does not perform a browser's
   implicit form submission when a submit button is clicked, so it passed
   whether or not `type="button"` was present. It would have passed against the
   bug.
2. **Its replacement**, asserting `testButton().type === "button"` — also green
   with the attribute deleted, because `Button` in `ui.tsx` already renders
   `type={props.type ?? "button"}`. The hazard did not exist at this call site;
   the shared component had removed it years earlier.

So the prop was redundant, the comment justifying it was **wrong for this
codebase**, and the test pinned `ui.tsx`'s default rather than anything here.
All three deleted. Five tests remain and every one of them fails when the
behaviour it names is broken.

### Acceptance criteria

- [x] A test send from the Sicherheit screen, using the stored settings
- [x] The recipient is the caller's own address and cannot be chosen
- [x] The SMTP server's own failure text reaches the screen unparaphrased
- [x] "Not configured" and "the send failed" are distinguishable
- [x] Super administrators only, through the same function the write uses
- [x] Rate limited, and audited like every other outbound message
- [x] No credential in any response, log or audit row (invariant 7)
- [x] Red-checked — including deleting two of my own tests that could not fail

## What the client still has to do, and what nothing here can check

Three things, all outside this repository:

1. **A United Domains mailbox**, and its submission host, username and password
   in Sicherheit → E-Mail-Versand (SMTP). Port 587 leaves the checkbox
   unticked; port 465 ticks it.
2. **SPF and DMARC** on `digitalspital.com`.
3. **DKIM that aligns.** DMARC passes only if SPF _or_ DKIM aligns with
   `digitalspital.com`. Mail relayed through a provider that signs with its own
   domain produces a valid signature, no alignment, and a DMARC failure — so the
   provider's DKIM records must be published under `digitalspital.com` and the
   envelope sender must be on that domain. This is the step that is usually
   missed and it is usually the difference between inbox and spam.

## Still open

**Nothing verifies the DNS records exist.** They are applied by hand, and
§9.9's strongest form is that documentation instructing a human to apply a
setting is a setting that is not applied — the bucket's CORS rule sat in a
README from P23-04 until P70 and every video upload was refused for months. A
check that resolves SPF, DKIM and DMARC for the sender's domain, and reports
what is missing or unaligned, is the mechanism that would make this real. It is
its own ticket and it was offered.

**And a passing test is not a delivered message.** The test proves the relay
accepted the mail. It cannot prove the mail reached an inbox rather than a spam
folder, which is why the success message asks the operator to go and look.
