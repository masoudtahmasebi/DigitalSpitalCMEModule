## P188-01 — the default endpoint is `live`

Migration 0051 defaulted `eiv_endpoint` to `mock`, reasoning that an
installation gaining the table must not start submitting because a column
defaulted the friendly way. That reasoning is about **submitting**, and it is
answered by a different column.

Three things must be true before a Punktemeldung reaches the Ärztekammer:

|                         |                                |
| ----------------------- | ------------------------------ |
| `eiv_endpoint = 'live'` | what 0053 changes              |
| `eiv_worker_enabled`    | still defaults to **false**    |
| `eiv_live_confirmed_at` | a named person, in the console |

`platform_settings_live_needs_consent` makes (1) + (2) without (3)
**unrepresentable** — so `eiv_worker_enabled DEFAULT true` alongside this would
not have been a policy decision, it would not insert. The floor stays where
CLAUDE.md §3 puts it: a statutory report that cannot be unfiled needs a human to
say so. A new installation is **pointed at production and not yet armed**, which
is what "set to prod" can mean without deleting the consent gate.

### Why the existing row moves too, and only when nobody has chosen

`platform_settings` has one row, inserted by 0051 _before_ 0053 runs. Changing
the default alone would leave every installation — including brand new ones — on
`mock`: a default with no effect, which is worse than not changing it.

So the row is updated, guarded on `updated_by IS NULL`. An installation where an
operator **has** saved that screen keeps their choice, because a migration
overruling a decision somebody made in the console is the seed-overwrite defect
`check:seed-overwrites` exists to catch (§9.10b), one layer down.

### The consequence on the production host, stated plainly

Its row reads `endpoint=mock armed=false live-consent=false` (deploy 113's log)
and `updated_by` has never been set, so **this migration moves it to `live`**.
Nothing is armed and nothing files. The one visible change is that the
Verwaltung connection check would now talk to the real register — a read,
authenticating with the course's VNR — until the endpoint is set to `test`,
which the client has said they will do.

The post-deploy journey is unaffected: `ds_eiv_worker_will_file_live` requires
the worker **and** consent, so the guard still answers `no` and the journey
still runs. Asserted by name in `eiv-endpoint.test.sh`.

### One home for the value

The test harness's `resetDatabase` wrote `'mock'` under a comment claiming it
restored "the migration's own defaults". Both were true when written, and the
literal is what made them stop being true together. It now writes
`eiv_endpoint = DEFAULT` and has the column answer for itself; the safety
property it actually guards, `eiv_worker_enabled = false`, stays explicit.

`platform-settings.integration.test.ts` is the check that can go red on its own:
the row, the column default, the worker being off, and the database refusing to
arm without consent. All four watched red.

## P188-02 — the sender form threw away what you typed

**Found by the browser, not by reading the code.** P187's Act 0 filled the six
fields and clicked Speichern; the screen answered **"Gespeichert."** with
`Server` empty and the other five holding what had been typed.

The mount effect reads the stored sender and writes **every** field from the
response. Locally that lands in milliseconds; over the internet it is a few
hundred, and the fields are on screen and focusable the whole time. An operator
who clicks Sicherheit and types the server name loses exactly the characters
typed before the response arrives — and only those, so the form looks
half-filled by a person who filled it completely. The save then stores a `NULL`
host, `canSend` goes false, and the screen says the operation succeeded.

That is §9.13's fourth row — _"a form silently discarded: the order two controls
are used in, on one screen"_ — with P41-01's answer on top of it.

The form is not rendered until the read has finished. A `touched` flag would
also have worked and would have left a second defect standing: a blank form
during the load is indistinguishable from an installation with no sender
configured (§9.6), which is the reading a person takes from a blank Server box.
A field that does not exist yet cannot be misread or clobbered. A read that
comes back empty-handed now says so instead of drawing an empty form.

Two `Security.test.tsx` cases, the first watched red.

## P188-03 — the deploy says which sender will carry a certificate

"Which sender is this installation on?" needed a psql session, and it decides
whether a physician who finishes a Fortbildung receives their Bescheinigung.
§9.9's corollary: the repository's state is not the installation's, and both
halves of this fail silently.

A post-deploy step reports the same three answers `deliverySender` gives, over
the host's own rows: how many projects send as themselves, the platform's From
address, and how many the platform carries. When neither is configured for a
project it raises a **warning** naming the screen that fixes it — that is the
one state where a certificate is issued and silently never sent.

Counts and the From address only. No host, no username, no password: the address
is on every certificate that arrives anyway, and the credential is not on a CI
log. It never fails the job — a deployment whose customers have not set up mail
is a working deployment with a gap somebody should know about, and an exit there
would mark a successful swap as failed.

The parsing is guarded on being numeric before any arithmetic, and driven over
five shapes including an unreadable answer and an empty one: an unparseable
reply says so rather than aborting the step, which would read as "the deploy
broke" rather than "the question could not be answered" (§9.6).

## What CI found that `pnpm verify` could not

Both of these were green locally and red on the first CI run, which is the
§9.1 signature: two green runs is not proof.

### The test asserting shared mutable state

`platform-settings.integration.test.ts` originally read the installed row.
`platform_settings` is a **singleton every other suite can write** —
`hierarchy.integration.test.ts` drives `PATCH /admin/platform/eiv` through its
whole refusal table. Locally the file order put this suite first and it was
green; in CI it ran last and read `mock` with another suite's `updated_by` still
on the row.

Rewritten to **make** its state rather than find it, and to run 0053's own
`UPDATE` extracted from the shipped file against a row in each state. That
covers the two claims the column default cannot — 0051's row moving, and an
operator's choice surviving — and it is order-independent. Both watched red by
neutering the migration.

### A flake in a file this branch does not touch

`App.route.test.tsx` asserted `window.location.hash` **bare**, immediately after
a `waitFor` on the selected tab. The two do not settle together: the tab is
React state and the fragment is written by a following effect. On a loaded
runner it read `''` and reported "routing is broken".

Every other hash assertion in that file already sits in its own `waitFor`; this
one was the exception. Folding both into **one** `waitFor` is a different and
stricter claim — that they settle simultaneously — and fails; two sequential
waits is the right shape.

Fixing it surfaced a second thing at once. The extra tick let `CertificatePanel`
actually render, and the file's stub answered `/certificate` with a
`CourseDetail`, so `formatBerlinDate(undefined)` threw **inside render**. Vitest
reports that as an unhandled error outside any test — 387 passed and the run
still failed — which is precisely the trap the file's own comment about
`/evaluation` already records. `/certificate` now has a shape of its own.

## Acceptance criteria

- [x] A new installation's endpoint is the production register.
- [x] It is not armed, and the database refuses to arm it without consent.
- [x] An installation where an operator has chosen keeps their choice.
- [x] The post-deploy journey still runs.
- [x] The harness stops carrying its own copy of the default.
- [x] The platform sender form cannot discard what was typed into it.
- [x] The deploy reports which sender will carry a certificate, and warns when
      none will.
- [x] Every assertion watched red first.

## Not done, and deliberately

- **No bulk re-queue of certificates abandoned "no SMTP host configured"** on an
  installation that later configures a sender. The support panel's "Erneut
  senden" takes them one at a time, which is the right granularity, and a sweep
  that re-sent months of certificates in one batch is the EIV backlog hazard in
  a different queue.
