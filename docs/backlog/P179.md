**Raised by:** the client, 03.09.2026, looking at the Teilnehmende tab of DS

**Branch** `claude/education-platform-roadmap-3vgrqh`.

## What `undeliverable` meant, and what was actually wrong

`certificates.status = 'bounced'`. **The e-mail failed; the certificate did
not.** `delivery.service.ts` has said since P8-03 that a failed delivery must
never affect the entitlement — the document exists, is valid, and the physician
can still download it. An operator who does not know that will tell a physician
they have lost their Teilnahmebescheinigung.

Four gaps behind the one word, each verified rather than assumed:

| Gap                                            | Evidence                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The screen threw away everything it knew       | `certificates` stores `delivery_abandoned_reason`, `delivery_error`, `delivery_attempt_count`, `delivery_first_attempt_at`, `delivery_next_attempt_at`. `participantRowSchema` returned one enum.                                                                                                          |
| The retry existed on another screen            | `POST /admin/certificates/{id}/resend` and the Bescheinigungen screen have existed since P12-05. The person in the middle of a support call was on the course's Teilnehmende tab.                                                                                                                          |
| No admin download at all                       | `GET /courses/{slug}/certificate/pdf` reads `principal.userId`. The only document it can produce is the caller's own.                                                                                                                                                                                      |
| An EFN could not be corrected after completion | The learner's correction form lives on `CompletionScreen`, which the widget stops showing once a completion is recorded. There was no admin route. And the EIV worker sends `eiv_submissions.efn`, snapshotted at completion — so correcting the profile would not have reached the queued Meldung anyway. |

The last one is the serious one and the client did not ask about it. `queued`
was on the screenshot: if that EFN had a typo, the Punktemeldung would have been
filed against another physician's account and looked like success — which
ADR-0004 calls the worst failure available.

## P179-01 — The row says what happened, and can act on it

`certificateDeliverySchema` returns the id, the abandoned reason, the channel's
last error, the attempt count and both timestamps. A support panel opens under
the row with the diagnosis and three controls: **Bescheinigung herunterladen**,
**Erneut senden**, **Neu erstellen**.

Resending is **withheld** for `no_recipient` and `permanent_rejection` — it can
only produce the same error (§9.2, P118-02) — and the cause is printed in its
place saying what to do instead.

`lastError` is safe to show, and that is a property rather than a hope:
`DeliveryChannel` forbids a reason carrying the recipient or the transport
credentials, `classify` in `@ds/mail` produces only `SMTP <code>`, an errno,
`no SMTP host configured` or `unknown transport error`, and `smtp.test.ts`
asserts an address never reaches the outcome.

**Two silent holes closed on the way.** `certificateState` had no `revoked`,
which `certificates` has carried since migration 0023 — the cell rendered blank
for a certificate somebody had deliberately withdrawn. And
`delivery_abandoned_reason` is `text` with no CHECK, so a fourth value would
have reached the console as a label nobody wrote; it is narrowed in the service
and answers null, with the console falling back to a sentence.

The CSV export carries the cause and the attempt count too: "unzustellbar"
fifteen times in a column does not say whether that is fifteen wrong addresses
or one unconfigured SMTP host.

## P179-02 — An admin download

`GET /admin/certificates/{id}/pdf`, `customer_admin` and `super_admin`.

It **sends nothing** — resending is its own control, and keeping them apart
means a support download leaves no impression that the participant has been
contacted. It **re-issues nothing**: the render is idempotent, the download
token is minted only if absent, and `archiveOnce` keeps the first render as the
evidence. Asserted, not claimed — the integration test compares the token, the
status and the delivery schedule before and after.

Refused for a revoked certificate before rendering, because handing out a
withdrawn document is the outcome revocation exists to prevent. Audited as
`certificate.downloaded_by_staff`: what left the platform, in whose hands, and
no name.

## P179-03 — The EFN, on both sides

**The physician's side.** The Zertifizierung tab now carries their own EFN and
a correction control. P54-02 built that on the Punktemeldung form, which the
widget stops showing at completion — so from the moment the number starts to
matter, its owner could no longer see or change it. P54-02's own header is the
argument for fixing it: _"no way to notice a typo until the Kammer credits
somebody else's account, which is the failure ADR-0004 itself calls the worst
available because it looks like success."_

And a correction now **reaches the queued Meldung**. `efn_profiles` and
`eiv_submissions.efn` are two copies of one value; P118 taught the _requeue_
path to reconcile them with `efnRefresh` and left the moment of correction
alone. A physician who fixed a typo at 10:00 had the old number sent at 10:05
unless an operator happened to requeue in between, and it looked like it had
worked. `setEfn` now applies the same `efnRefresh` to every un-sent submission
of theirs.

**The operator's side**, and what it deliberately is not. `PATCH
/admin/learners/{enrolmentId}/eiv/efn` corrects **our own outbound report**. It
does not write `efn_profiles`, because that table's RLS `WITH CHECK` admits only
`user_id = app.user_id` — the subject and nobody else. That is a guarantee, not
an oversight: a platform on which a customer's administrator can assert a
doctor's national identifier is one that can credit points to anybody.
Changing it is a decision for the client and an amendment to ADR-0004, and it
is **raised rather than absorbed** (§7, §3) — see "Not done".

So the panel stops a wrong number reaching the Ärztekammer without letting
anybody rewrite whose number it is. `efnCorrection` in `@ds/domain` is the rule,
on `nameCorrection`'s and `efnRefresh`'s stages: refused once `submitted` or
`withdrawn` (S30), refused for a value that is already stored so a no-op cannot
be mistaken for a fix.

**And the divergence is visible.** The row carries `efnMasked` — the last four
digits, from the same `maskEfn` the Lernende and Punktemeldungen screens use —
and `efnDivergesFromReport`, a boolean saying whether the queued Meldung still
agrees with the profile. Before this, no screen anywhere could tell those apart.
`docs/gdpr.md` §2 is amended for the mask; it is the narrowest amendment that
answers the question, and the full number is in no response.

## Acceptance criteria

- [x] The row says what `unzustellbar` means, why, how often, and when next.
- [x] Retry, re-create and download, where the operator already is.
- [x] Retry withheld where it could only fail, with the reason in its place.
- [x] An admin can download a participant's certificate; it sends and re-issues
      nothing, and is refused for a revoked one.
- [x] A physician can correct their EFN after completing, and the correction
      reaches every un-sent Punktemeldung.
- [x] An operator can correct the EFN on a queued Meldung, and cannot touch the
      profile.
- [x] Refused once the Ärztekammer has accepted it, with no EFN in the message.
- [x] Rules watched red: the learner's refresh, the revoked-download refusal,
      the resend gate, each broken separately.

## Not done, and needing a decision

- **An admin cannot set a physician's EFN on their profile.** The database
  refuses it by design and the reason is a good one; the panel-side correction
  above covers the support case that matters, which is stopping a wrong number
  reaching the Kammer. If the client wants the profile write as well, it is a
  migration to `efn_profiles`'s policy, an amendment to ADR-0004 and its own
  ticket — not something to absorb while fixing a screen.
- **Two `maskEfn` implementations.** `@ds/domain`'s produces `•••••••••••1234`
  and `eiv-admin.repository.ts`'s produces `…1234`, so one physician's EFN looks
  different on two admin screens. Not a disclosure, but §4 invariant 6. Filed.
- **No e2e run.** `apps/e2e` needs a Docker daemon; this sandbox has none.
