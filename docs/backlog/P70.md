# P70 — the setting that was written down and never applied

Found on 13.08 by the post-deploy journey, on production, before anybody
clicked. The browser said:

```
Access to XMLHttpRequest at 'https://nbg1.your-objectstorage.com/dscme/…/video-….webm?X-Amz-…'
from origin 'https://verwaltung.digitalspital.com' has been blocked by CORS policy:
Response to preflight request doesn't pass access control check:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

This is the **third** distinct cause behind one client report — _"the video
upload to s3 does not even work!"_, 12.08 — and the three are worth reading
together, because they are the same shape three times:

|            | What was wrong                                         | What was green while it was                                             |
| ---------- | ------------------------------------------------------ | ----------------------------------------------------------------------- |
| P67-01     | The console's CSP did not name the bucket              | Every test: no test served a CSP                                        |
| P68-03     | `S3_ORIGIN` was derived, tested and never **exported** | `deploy-vars.test.sh`, which read the template rather than the value    |
| **P70-01** | The bucket had no CORS rule                            | Sixteen browser tests, against a harness bucket that allowed everything |

Each fix uncovered the next, because each was genuinely the blocker at the time.
The journey found all three, one per deploy, in about ninety minutes total.

---

## The finding

`infra/deploy/config.env.example` has carried this since P23-04:

> **Bucket configuration you have to do once, by hand** … **1. CORS.** The
> browser uploads straight to the bucket, so the bucket must allow it.

with the exact JSON to paste. It was correct, it was findable, and on every
installation the platform has ever had, **nobody did it.** Not through
negligence: it is a step in a provider's web console, months before the feature
that needs it was exercised, in a document read once during setup.

That is CLAUDE.md §9.9's corollary, stated as plainly as it gets: _the
repository's state is not the installation's state._ A seed, a migration, a
setting — it exists there only if somebody ran it. This one had the additional
property that its absence is **invisible from the server side**: the browser
asks the bucket for permission and the bucket refuses, in a conversation the API
is not part of. A clean API log is exactly what a broken bucket produces.

## The fix

`dist/bucket-cors.js`, in the API image alongside the migrator and the seeds,
run by `deploy.sh` on every deploy. It does two things, and the second is the
one that matters:

1. **Applies** the rule — `PUT` from `https://verwaltung.<BASE_DOMAIN>`,
   `content-type`, nothing else — with a presigned `PUT ?cors`.
2. **Probes** it, with an unsigned `OPTIONS` carrying `Origin` and
   `Access-Control-Request-Method`. That is the browser's own question, asked
   with no credentials, so it cannot pass for a reason the browser would not
   share.

The probe decides the exit code; a failed write is a warning. A `200` from
`PutBucketCors` proves the request was accepted, not that the effect is what a
browser needs — and if a provider ever refuses the write, the probe still goes
red and the deploy still prints the document to paste. An operator who applied
the rule by hand gets a passing deploy either way.

**A failing probe fails the deploy.** The containers are already running by
then, so the site stays up and the deploy reports failure — which is the honest
answer for an installation whose authors cannot upload a video.

## And the harness modelled the bug away

`apps/e2e/support/object-store.ts` answered every preflight with a fixed
permissive list. So the sixteen browser tests were green against a bucket that
had already been configured — a state no real bucket starts in and no
installation had reached.

It now starts with **no CORS configuration**, implements `PutBucketCors` and
`GetBucketCors`, and answers preflight from what has actually been written to
it. `stack.ts` then configures it by spawning the same compiled
`dist/bucket-cors.js` the deploy runs, with the same environment variables —
not by calling a TypeScript function, because the last three defects in this
area were all in the wiring and none in the logic.

**Red-checked**, twice:

- Remove the call in `stack.ts` → the journey fails at the upload with the
  browser's message, character for character the same as production's.
- Change `consoleUploadRule` to `["GET"]` → the probe refuses with _"the bucket
  allows GET, not PUT"_ before the journey even starts.

The second red-check found a defect of its own: the success line said
`Applied … PUT` while the document it had written said `GET`. A log that
restates its intention rather than what it did is exactly the green that cannot
go red, so it now prints `rule.methods`.

## Acceptance criteria

- [x] The deploy applies the bucket's CORS rule rather than a document asking
      somebody to remember
- [x] The deploy fails when the bucket would refuse an upload from the console,
      and prints the exact policy to paste
- [x] The check is an unsigned preflight — the browser's question, not ours
- [x] It is a no-op, exit 0, on an installation with no object storage
- [x] The harness bucket starts unconfigured, so the local journey can reach
      this defect (§9.1 — the check is run where the work happens)
- [x] The local rig configures it with the deploy's own artefact, as a
      subprocess, so the thing under test is the thing that runs there
- [x] Unit tests cover every way a bucket can answer and still refuse: no
      header, another origin, no methods, the wrong method
- [x] Red-checked in both directions

## Deliberately not done

**`GET` in the rule.** The console's length probe (`media-duration.ts`) uses
`crossOrigin = "anonymous"`, which is a CORS `GET` — and it does not need one
today only because `probeableSourceUrl` skips `s3://` references, so an uploaded
video is never probed. Adding `GET` now would widen the rule for a caller that
does not exist. The note is in `bucket-cors.ts`'s header, at the point whoever
implements the open P68 item will be reading.

**A `SKIP_BUCKET_CORS_CHECK` escape hatch.** An escape hatch for a check that
has already been missed once is a switch somebody sets during an incident and
nobody unsets. An installation that genuinely has no object storage is already
skipped, by the condition that names the real reason.
