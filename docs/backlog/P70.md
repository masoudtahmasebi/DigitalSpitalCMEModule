# P70 — the setting nobody applied, and the network nobody could leave

Two findings, one after the other, both surfaced by the post-deploy journey on
production before anybody clicked. They are the third and fourth distinct causes
behind a single client report — _"the video upload to s3 does not even work!"_,
12.08 — and the four are worth reading together, because they are one shape
repeated:

|            | What was wrong                                         | What was green while it was                                              |
| ---------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| P67-01     | The console's CSP did not name the bucket              | Every test — no test served a CSP                                        |
| P68-03     | `S3_ORIGIN` was derived, tested and never **exported** | `deploy-vars.test.sh`, which read the template rather than the value     |
| **P70-01** | The bucket had no CORS rule                            | Eighteen browser tests, against a harness bucket that allowed everything |
| **P70-02** | The API container has no route to the internet         | Everything — the paths that need it are all async, retried, or untried   |

Each fix uncovered the next, because each was genuinely the blocker at the time.

---

# P70-01 — the setting that was written down and never applied

The browser said:

```
Access to XMLHttpRequest at 'https://nbg1.your-objectstorage.com/dscme/…/video-….webm?X-Amz-…'
from origin 'https://verwaltung.digitalspital.com' has been blocked by CORS policy:
Response to preflight request doesn't pass access control check:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

`infra/deploy/config.env.example` has carried this since P23-04:

> **Bucket configuration you have to do once, by hand** … **1. CORS.** The
> browser uploads straight to the bucket, so the bucket must allow it.

with the exact JSON to paste. It was correct, it was findable, and on every
installation the platform has ever had, **nobody did it.** Not through
negligence: it is a step in a provider's web console, months before the feature
that needs it was exercised, in a document read once during setup.

That is CLAUDE.md §9.9's corollary in its strongest form, now written into the
file: _documentation instructing a human to apply a setting is a setting that is
not applied._ This one also has the property that its absence is **invisible
from the server side** — the browser asks the bucket and the bucket refuses, in
a conversation the API is not part of. A clean API log is exactly what a broken
bucket produces.

## The fix

`dist/bucket-cors.js`, in the API image beside the migrator and the seeds, run
by `deploy.sh` on every deploy. It does two things, and the second is the one
that matters:

1. **Applies** the rule — `PUT` from `https://verwaltung.<BASE_DOMAIN>`,
   `content-type`, nothing else — with a presigned `PUT ?cors`.
2. **Probes** it, with an unsigned `OPTIONS` carrying `Origin` and
   `Access-Control-Request-Method`. That is the browser's own question, asked
   with no credentials, so it cannot pass for a reason the browser would not
   share.

The probe decides the exit code; a failed write is a warning. **A failing probe
fails the deploy** — the containers are already running by then, so the site
stays up and the deploy reports failure, which is the honest answer for an
installation whose authors cannot upload a video.

## And the harness modelled the bug away

`apps/e2e/support/object-store.ts` answered every preflight permissively, so the
browser tests were green against a bucket that had already been configured — a
state no real bucket starts in and no installation had reached. It now starts
with **no CORS configuration**, implements `PutBucketCors`/`GetBucketCors`, and
`stack.ts` configures it by spawning the same compiled `dist/bucket-cors.js` the
deploy runs, over the same environment variables.

**Red-checked twice.** Removing the call in `stack.ts` fails the journey at the
upload with production's message character for character. Forcing the rule to
`["GET"]` makes the probe refuse with _"the bucket allows GET, not PUT"_ — and
that run found a defect of its own: the success line read `Applied … PUT` over a
document that said `GET`, so it now prints `rule.methods`.

# P70-02 — the API container could not reach the internet

The deploy then ran the new check against production, and it said:

```
Could not reach the bucket to write the CORS rule: fetch failed.
  https://verwaltung.digitalspital.com: the bucket could not be reached — fetch failed
```

Not a refusal. **No route at all.**

## The cause

```yaml
networks:
  edge:
  internal:
    internal: true
```

`internal: true` is usually read as "nothing outside can reach this", which is
true and is half of it. Docker gives an internal network **no gateway**, so a
container attached only to it cannot open an outbound connection either. The
comment above the block said _"Only Caddy is on both. Nothing else can be
reached from outside the host"_ — a sentence about ingress, on a setting that
also governs egress.

`api` was on `[internal]`. It is the service that:

- HEADs an uploaded object to verify it (`verifyUpload`)
- archives every issued certificate to the bucket (P60-01)
- delivers a certificate over SMTP (P8-03)
- fetches a customer's Keycloak JWKS to validate **every learner token**
  (ADR-0003) — MEDICE's realm is not on this host
- reports a Punktemeldung to EIV-FOBI

None of those has ever succeeded on this installation. None of them says so
where a person looks: each surfaces as a timeout, a retry, or Node's `fetch
failed` inside a background worker.

The JWKS one is the serious member of that list — it would have been discovered
at MEDICE go-live, as _every learner is refused_, with a 401 that names nothing.

## Why it survived so long

`backup` already carried `[internal, edge]`. Somebody traced an S3 failure once,
found the network, and fixed **the service in front of them**. The class was
never asked about. CLAUDE.md §9.11 is exactly this.

## The fix

`api` is on `[internal, edge]`. Being on `edge` publishes nothing: reachability
from outside the host is decided by `ports:`, which the API does not have and
must not — it is reached through Caddy.

`scripts/check-egress.mjs` holds the table against the file: every service is
named with whether it calls out and why, and the check fails both ways — a
service that needs egress and cannot, and a service that has egress and should
not. A service missing from the table is also a failure, because a new service
is exactly when the question has to be asked.

**Red-checked:** putting `api` back on `[internal]` fails with the sentence
naming the four things it can no longer reach.

## And the diagnostic that named nothing

The deploy's own message was `fetch failed`, which is what Node reports for a
DNS failure, a refused connection, an unreachable network and an untrusted
certificate alike. The real reason is in `error.cause`, sometimes two levels
down. `describeFetchFailure` now walks the chain, so the same failure would read

```
fetch failed — getaddrinfo EAI_AGAIN nbg1.your-objectstorage.com (EAI_AGAIN)
```

which points at the network in one line. This is §9.4 — say what the thing is —
inside a diagnostic written to satisfy §9.4, which is the honest reason it is
recorded here rather than quietly fixed.

## Acceptance criteria

- [x] The deploy applies the bucket's CORS rule rather than a document asking somebody to remember
- [x] The deploy fails when the bucket would refuse an upload, and prints the exact policy to paste
- [x] The check is an unsigned preflight — the browser's question, not ours
- [x] It is a no-op, exit 0, on an installation with no object storage
- [x] The harness bucket starts unconfigured, so the local journey can reach the defect
- [x] The local rig configures it with the deploy's own artefact, as a subprocess
- [x] The API container can reach the internet, and nothing else gains ingress
- [x] `check-egress.mjs` fails both ways, and on a service it has never been told about
- [x] A failed `fetch` reports its cause chain, not the word "failed"
- [x] Unit tests cover every way a bucket can answer and still refuse
- [x] Red-checked in every direction

## Deliberately not done

**`GET` in the CORS rule.** The console's length probe (`media-duration.ts`)
uses `crossOrigin = "anonymous"`, which is a CORS `GET` — and it does not need
one today only because `probeableSourceUrl` skips `s3://` references, so an
uploaded video is never probed. Adding `GET` now would widen the rule for a
caller that does not exist. The note is in `bucket-cors.ts`'s header, where
whoever implements the open P68 item will be reading.

**Auditing the other outbound paths now that egress exists.** SMTP delivery,
certificate archiving, JWKS validation against a real realm and EIV submission
have all been running against a network that could not carry them, so none has
ever been observed working end-to-end on this installation. They need a pass
each, and each is its own ticket — this one is not the place to discover four
more defects.

**An escape hatch on the bucket check.** An escape hatch for a check that has
already been missed once is a switch somebody sets during an incident and nobody
unsets. An installation with no object storage is already skipped, by the
condition that names the real reason.
