# P155 — Two holes in the release chain, found by reading a run rather than the workflow

Masoud asked for the post-merge deployment chain to be started. Most of it was
already there. What was missing were the two things that let "merged" and
"deployed" come apart — and both had been exercised in production, on this
repository, this week.

Branch `P155-release-guards`, from `origin/main` at `cc65b7a`.

|                                |                                                 |
| ------------------------------ | ----------------------------------------------- |
| `origin/main`                  | `cc65b7a` — merge of PR #43 (P154)              |
| `api.digitalspital.com/health` | `{"commit":"cc65b7a","version":"0.1.405"}`      |
| P148–P154                      | on `main`, and `cc65b7a` is what the API serves |

## What the workflow already got right

Worth stating, because the request asks for things that exist:

| Requirement                                | Where                                                         |
| ------------------------------------------ | ------------------------------------------------------------- |
| triggers after CI, on the default branch   | `on: workflow_run: workflows:["CI"], branches:[main]`         |
| only when CI **succeeded**                 | `github.event.workflow_run.conclusion == 'success'`           |
| deploys the **exact** SHA CI ran against   | `SHA: github.event.workflow_run.head_sha`                     |
| one deployment at a time, no overtaking    | `concurrency: deploy-production`, `cancel-in-progress: false` |
| production environment, approval preserved | `environment: name: production`                               |
| backup before migrations, rollback input   | `deploy.sh`, `workflow_dispatch.rollback_tag`                 |

None of that is changed here.

## P155-01 — `workflow_dispatch` walked around all of it

The job's condition read

```yaml
if: >-
  github.event_name == 'workflow_dispatch' ||
  github.event.workflow_run.conclusion == 'success'
```

so a manual run satisfied it **on any ref, with no CI at all**.

That is not hypothetical. Verified from the Actions API in a previous session of
this conversation:

```
run 33615653131   2026-09-02T09:43:19Z   event: workflow_dispatch
  head_branch: claude/education-platform-roadmap-3vgrqh
  head_sha:    010fea6a
  "Deploy to production" -> success
```

A feature branch, unmerged and unreviewed at the time, went to the production
host and the workflow reported success. Nobody misused anything: the dropdown
offered it.

**The fix is the narrowest one that keeps a manual deploy working**, because a
manual deploy is how a rollback runs and how an operator recovers when Actions
is having a bad day: a `workflow_dispatch` may deploy the **default branch
only**. `workflow_run` deploys are untouched — they are already filtered to
`main` and gated on CI success.

## P155-02 — the post-deploy step read the served commit and never compared it

The smoke step fetched `/health`, pulled `commit` out of it, printed it in the
job summary — and stopped. Its own comment, since P47-01, said why that number
is the one that matters:

> The version and commit the _running API_ reports, not the ones this workflow
> believes it deployed. Those are different claims, and only the first one is
> evidence: **a deploy that swapped nothing would still let this job report the
> commit it was triggered for.**

Correct, and then no line under it compared the two. So a deploy that swapped
nothing was **green**. §9.1 in the release pipeline itself: the right sentence
with no assertion beneath it, which is the same shape as P153's playback comment
and P154's seek-ceiling comment.

It is also precisely why "merged but not visible" is hard to answer: the
workflow was holding the answer and never looked at it.

The step now fails when the served commit is not the deployed one, and says
which is which.

## Why the logic is in a shell file rather than in the YAML

A line of YAML cannot be made to fail in a test. Both decisions live in
`infra/deploy/release-guards.sh` as pure functions and are driven by
`release-guards.test.sh`, which `pnpm verify` and CI already run through
`check:shell` (`for t in infra/deploy/*.test.sh`). That is the same arrangement
as `eiv-endpoint.sh` / `eiv-endpoint.test.sh`.

The deploy job now does a `sparse-checkout` of `infra/deploy` to read them. The
comment that said "No checkout: nothing from this runner reaches the server" has
been corrected rather than left to become false — what runs on the host still
comes from the host's own fetch of `$SHA`.

## Sabotage — real exit codes, no pipes

| Sabotage                                              | `release-guards.test.sh`                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------------- |
| dispatch allowed from any ref (today's behaviour)     | **exit 1** — 4 failed, incl. "a manual run from a feature branch is refused" |
| served-commit check always passes (today's behaviour) | **exit 1** — 5 failed, incl. "a stale commit is a mismatch"                  |
| restored                                              | **exit 0** — 15 passed                                                       |

The commit matcher is deliberately awkward to satisfy: an empty served commit
fails rather than passes, a one-character "commit" cannot prefix-match
everything, and a matching **tail** is not a match.

## Security and compliance impact

**This change only ever refuses more than before.** No new secret, no new
permission, no new network path, and no product behaviour.

| Concern             | Assessment                                                                                                                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blast radius        | Narrowed. An unreviewed branch can no longer be put on the production host from the Actions dropdown — which is what happened on 2026-09-02.                                                                              |
| Human review gate   | Untouched. `environment: production` and any approval configured on it still apply; nothing here weakens or bypasses an approval.                                                                                         |
| Secrets             | None added, none read by the new steps, none logged. The guard step's inputs are the event name, the ref and the default branch — all public metadata.                                                                    |
| Supply chain        | The new `actions/checkout@v4` is already used elsewhere in this workflow; it fetches `infra/deploy` from the same repository and copies nothing to the host.                                                              |
| Compliance surface  | None. No auth, assessment, EIV, certificate, GDPR or RLS code is touched, and no participant data is read, written or logged.                                                                                             |
| Failure mode        | Fails closed on both guards: a refused ref stops before any secret is read or any SSH session opens, and a served-SHA mismatch fails the run **without** rolling anything back, so an operator decides what happens next. |
| New risk introduced | One: a legitimate emergency deploy from a non-default branch is now refused. That is the intended trade, and the error message names the way through — merge it, and CI on the default branch deploys it.                 |

## What this does not do

- **It does not verify the frontend/widget build identity, or the MEDICE host.**
  The check added here compares the API's `/health` commit against `$SHA` on the
  domain the deploy derived. A widget bundle or CMS embed pinned to an older
  asset would still pass, and the MEDICE host is not part of the deploy's
  derived domains at all. Both are real gaps in §C4 and neither can be closed
  from here: this sandbox cannot reach either host. **Recorded as the next
  ticket rather than half-built.**
- **It does not add post-deploy smoke for deep links, progress retry or the EIV
  panel.** The existing journey suite runs against the deployed installation
  already; extending it is separate work with its own fixtures.
- **It does not change the environment approval.** If production requires one
  today, it still does, and a merge starts the workflow and then waits.
