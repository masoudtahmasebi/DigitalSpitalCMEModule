## P47-01 · The release number — **done**

- **Estimate:** 3 h · **Review gate: none**

`DS_COMMIT` answers "which build" exactly and "is this newer than yesterday's"
not at all: `0a177c7` and `e258c8d` are unordered. The footer now reads
`v1.0.482 · 0a177c7` — the version to compare, the commit to identify.

**Where the number comes from.** `major.minor` from the workspace's
`package.json`, hand-bumped for a release that means something to the client;
patch from `git rev-list --count HEAD`. So the next deploy of new work is
necessarily higher, and re-deploying a commit yields the same number, which is
correct — same code, same release.

Three alternatives were rejected for one reason each:

| Rejected               | Why                                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A counter in a file    | A merge conflict on every parallel branch, and a number that lies whenever somebody forgets to bump it                                                                                                        |
| A git tag pushed by CI | Needs push permission from the workflow and adds a failure mode to the deploy path                                                                                                                            |
| `github.run_number`    | **The important one.** It increments per workflow run, so `./deploy.sh` typed on the host could not produce a comparable value — and two sources for "the version" that cannot be compared is worse than none |

`version.sh` derives it, `deploy.sh` and `dsc` both source it, so a deploy from
GitHub Actions and one typed by hand agree.

### The failure it refuses instead of reporting quietly

`git rev-list --count` on a **shallow** clone returns the clone depth: a
plausible small number, silently wrong, and _lower_ than the last full-clone
deploy — so the version would appear to go backwards. `actions/checkout` is
shallow by default, which puts this one `fetch-depth` away at all times. A
shallow repository is therefore a hard refusal, and the message names
`git fetch --unshallow`.

`version.test.sh` builds real git repositories rather than stubbing git, because
the thing under test is what git reports. Confirmed by removing the guard and
watching the shallow cases go red.

### Where it surfaces

`/health` carries `version` beside `commit` — contract, schema, SDK, in that
order. The console and the portal render both. The widget bakes both at build
time and exposes them as `data-ds-build` / `data-ds-version`.

The deploy workflow's job summary reports the version **the running API
answers with**, not the one the workflow believes it deployed. Those are
different claims and only the first is evidence: a deploy that swapped nothing
would still let the job print the commit it was triggered for.

### What the existing checks caught

`deploy-vars.test.sh` failed the moment `${DS_VERSION}` appeared in
`docker-compose.prod.yml` — _"interpolates `${DS_VERSION}`, which nothing
exports"_ — because it did not know `version.sh` guarantees it. That is the
check working: a variable read by compose and exported by nothing is precisely
the class it was written for (P44-01 was the same shape one layer up). It now
reads `version.sh`'s exports the way it already read `domains.sh`'s, listed
explicitly so adding a third source is a deliberate act.

## On "build everything needed for production"

The honest answer is that the four rounds before this one were spent on
`deploy.sh` and the containers, because that is what was in front of the client
— and none of it was feature work. The engineering scope in `docs/roadmap.md`
§4 is built; what stands between this repository and a production launch is
mostly **not code**, and pretending otherwise by writing more of it would be the
wrong answer.

`docs/show-stoppers.md` is the list, and it is owned outside engineering. The
items with no engineering workaround at all:

- **S12 / S11** — two questions for the ÄKWL arising from the
  Anerkennungsbescheid. One email to `zertifizierung@aekwl.de`.
- **S15** — a live API key hardcoded in the WordPress plugin source MEDICE
  supplied. That wants rotating, not building.
- **S17 / S18** — MEDICE's Keycloak issues `aud: account`, which the API
  refuses by design, and the refresh token supplied is an _offline_ token that
  never expires. Both are decisions for MEDICE.
- **The MEDICE course content itself** — the seed carries placeholder prose and
  a 1×1 PNG where the stamp goes, deliberately (`PLACEHOLDER_IMAGE`: "seeding a
  convincing-looking fake stamp would be worse").

What is engineering's and is genuinely not built is listed in P46 and stays
listed rather than being quietly folded in: an **audit-log screen** in the
console — every row is written, retained and reachable only through `psql` —
and a **"Testmail senden"** control for SMTP. Both are real, both are small,
and both are behind the review gate or a ticket rather than being started
without one. Say which and they go next.
