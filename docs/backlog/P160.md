## Cause 1 — two sessions filed a ticket under the same number

`Format` failed on one file:

```
[warn] docs/backlog/P158.md
```

`docs/backlog/P158.md` is 463 lines holding **two unrelated work orders**. Two
sessions on 02.09.2026 each took the next free backlog number and both took
`P158`; git resolved the merge of PR #47 by concatenating the two documents, so
the second one begins mid-file with no blank line before its heading. Prettier
wanted the blank line. Prettier is the only thing that said anything at all.

The number cannot be given back. Both sets of commits already read `DEP-P158`
— `38ae52f` for the tail-and-gaps work and `d4fcd871`/`7cb7bb3` for the layout
work — and CLAUDE.md §10 is explicit that historic commits are not rewritten.
So the file keeps both tickets and now says so at the top, above the first
heading, instead of leaving the second discoverable at line 141.

The other session had already hit this an hour earlier: its ticket was filed as
`P156.md`, PR #45 took that name, and it was renamed to `P158.md` by hand. A
rename done by hand is a rename that can stop half way.

## Cause 2 — two advisories published against a dependency that had not moved

```
moderate  qs array-limit bypass via bracket-key comma parsing   >=6.14.2 <=6.15.3
moderate  qs: Denial of Service via Attacker Controlled isBuffer >=2.2.5 <6.16.0
          apps__api>express>qs
```

`qs` is express's query-string parser, so it is on the path of every request the
API serves. One resolved copy, `6.15.3`, patched at `6.16.0`. Both `express`
(`^6.14.0`) and `body-parser` (`^6.15.2`) already accept it, so the existing
`pnpm.overrides` entry widens rather than a dependency being forced:

```diff
-"qs@>=6.11.1 <=6.15.1": ">=6.15.2",
+"qs@>=6.11.1 <6.16.0": "^6.16.0",
```

**Verified:** `pnpm why qs -r` → `qs@6.16.0`, one version;
`pnpm audit --prod --audit-level=moderate` → `No known vulnerabilities found`,
exit 0 — the same command CI runs at `.github/workflows/ci.yml:506`.

This is the case CI's Monday 05:00 schedule exists for — an advisory against a
lockfile nobody has touched — and it landed on a Wednesday, so a merge caught it
first. The schedule is not at fault and is not changed.

## P160-01 — a ticket number means one file

Cause 1 is a shape, so it gets a check rather than a fix
(CLAUDE.md §9.11, §11 rule 11). `scripts/check-backlog-numbers.mjs`, in
`pnpm verify` and in CI:

1. every `docs/backlog/P<N>.md` carries at least one `# P<N> — ` heading —
   otherwise no commit message can point at it;
2. every such heading's number matches its filename.

Deliberately **not** a rule: one heading per file. `P158.md` genuinely holds two
tickets and always will. A check born with an exemption is CLAUDE.md §9.1, so
the rule is the one that is actually true — a number means one file, not a file
means one number.

**It went red on the first run, on four tickets nobody had noticed:**

```
P106.md:142: heading says P107, the file says P106
P106.md:234: heading says P108, the file says P106
P97.md:110:  heading says P98,  the file says P97
P97.md:235:  heading says P99,  the file says P97
```

There were no `P107.md`, `P108.md`, `P98.md` or `P99.md`. Those four tickets had
been reachable only by already knowing which other file had swallowed them —
the same defect as P158's, sitting in the repository since they were written.
Each is now its own file with a line saying where it came from; the text moved
verbatim, checked by sorting the before and after line sets, which differ by
zero lines.

The `# Epic P0 · …` form the original epic files use is matched too. Renaming
eleven historical headings to a convention invented later would change nothing
and prove nothing.

**Watched to go red** (§9.1) on all four of its failure modes: a heading
renumbered without the file (`P107.md:1: heading says P199`), a heading demoted
to `##` (`no "# P108 — …" heading`), a broken filename pattern
(`no backlog files found — wrong path?`), and a wrong directory, which throws
from `readdirSync` before reaching any of them.

## The same trap, one more time, on the check itself

The first full `pnpm verify` of this work failed:

```
[warn] scripts/check-backlog-numbers.mjs
```

The script written to stop a documentation file reddening `main` was itself
unformatted. That is the third time this week a Prettier failure has been the
whole content of a red build — P151-00 was `docs/backlog/P150.md`, cause 1 above
was `docs/backlog/P158.md`, and this was the fix for cause 1.

It is recorded rather than quietly corrected because the interesting part is
that nothing new is needed: `pnpm format` is already in `pnpm verify`, it went
red locally, and that is the whole mechanism working as designed. What keeps
failing is running `pnpm verify` before pushing rather than after — which is
§9.11's "a check that runs only in CI is a check the person writing the code
does not run", in the case where the check _is_ local and was skipped anyway.
No amount of further tooling fixes that; running it does.
