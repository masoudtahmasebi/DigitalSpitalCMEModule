# P45 · The two failures the deploy caused itself

> `Fatal error during bootstrap: Error: Invalid configuration: S3_ENDPOINT: must
start with https://`
>
> `deploy.sh: line 436: ../postgres/init-roles.sql: No such file or directory`

Both are `deploy.sh`'s, not the platform's, and both have the same shape as
P44-03: **the deploy knew something and did not act on it at the point where
acting was cheap.**

---

## P45-01 · Ask the image whether it can start, before changing anything — **done**

- **Estimate:** 2 h · **Review gate: none**

`S3_ENDPOINT` was a bare host. `config.ts` rejects that with a `refine` whose
message was written for exactly this mistake — a Hetzner console shows
`nbg1.your-objectstorage.com` and the API needs the scheme — so the _content_ of
the diagnosis was already perfect.

It arrived in the wrong place. The API validates at boot, so the refusal came
after four images were built, a backup was taken, migrations were applied and
the stack was swapped, as:

```
dependency failed to start: container ds-education-api-1 is unhealthy
```

The sentence naming the variable was reachable only by knowing to run
`docker logs`. The deploy's preflight validates a dozen variables by hand and
could not have caught this one, because the rule lives in the API's schema —
and copying it into `deploy.sh` would be a second implementation of a validator,
which is the mistake `@ds/migrator` exists to record.

So the image validates its own configuration through the same `loadConfig` the
server calls (`apps/api/src/check-config.js`), and `deploy.sh` runs it as a
one-shot container after the build and **before the backup**. One schema, two
callers; a bad value costs a build and stops, leaving the installation
byte-for-byte as it was.

It prints no values — `loadConfig` reports by path and message only, and the
environment it reads holds the database password and the KMS key (§9.5). A
rollback to an image predating the entrypoint is detected by `Cannot find
module` and skipped with a note rather than failing: turning a rollback into a
failed deploy would break the one command that exists for when everything else
has.

## P45-02 · No script may care which directory you ran it from — **done**

- **Estimate:** 1 h · **Review gate: none**

```
deploy@DS-CME:~$ ./Repositories/DigitalSpitalCMEModule/infra/deploy/deploy.sh
...
deploy.sh: line 436: ../postgres/init-roles.sql: No such file or directory
```

One line read a file relative to `$PWD` while every other path in the script was
built from `$SCRIPT_DIR`. It worked for everybody who had `cd`-ed into
`infra/deploy` first — which is what the runbook says to do — and failed the
first time somebody typed the full path from their home directory, two thirds of
the way through, after the build and the backup.

`infra/deploy/paths.test.sh` reads the five operator-invoked scripts, strips
comments, and fails on any path resolved against the working directory.

**Static, deliberately.** `--check` exits at line 336 and the offending line is
at 460, so a dry run from another directory would have been green — a check that
cannot go red (§9.1). The property wanted is textual and decidable by reading
the scripts. Confirmed by reintroducing the exact line and watching it name the
file and the line number.

---

## What this pair says

Three consecutive rounds have now ended the same way: the information needed was
present on the machine, and the tool that had it printed something else. P44-03
made the deploy print the logs of what actually broke; P45-01 moves the check
that would have prevented this one to before the first mutation; P45-02 makes
the class of "works only from the right directory" mechanical.

The remaining gap is named in P44 and is unchanged: nothing in this repository
can see the installation. Every one of these was diagnosable only from output
somebody pasted.
