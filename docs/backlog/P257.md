# P257 — MEDICE physicians arrived with no e-mail address

**Raised by:** the client, 15.10.2026, on the Teilnehmende tab: _"their email
is not shown from their medice login, as for medice login you actually have to
even enter your email so the data should be there"_.

## P257-01 — the SDK never sent the profile hint

**Review gate:** human · touches auth (how a learner's profile reaches the API)

**Context**

MEDICE's Keycloak puts no `email`, `given_name` or `family_name` in its tokens.
P105-01 (03.09.2026) built the workaround end to end, except for one link:

| Link                                                          | State before this ticket                   |
| ------------------------------------------------------------- | ------------------------------------------ |
| Plugin writes `learner-profile` (`class-ds-lms-renderer.php`) | working — the client's page carries it     |
| Widget reads it (`element.ts:359`) and passes `profileHint`   | working, and passed **twice** (`api.ts`)   |
| SDK sends it as `X-DS-Profile`                                | **missing** — `ClientOptions` had no field |
| API merges it where the token is silent (`auth.guard.ts`)     | working, never reached                     |

The widget passed the option in a conditional spread, which TypeScript does not
check for unknown keys, so the value was dropped without an error. The only test
was of the parser (`profile-hint.test.ts`), which nothing called — CLAUDE.md
§9.7. And the e2e rig could not have found it: `dev-keycloak` always put
`email` in its tokens, so the WordPress test never needed the hint (§9.13).

Verified: the client's page has `learner-profile` with keys `email`,
`firstName`, `lastName` (client, in the browser console); `grep` of
`packages/sdk/src/index.ts` at `4034b08` has no `profileHint` and no
`x-ds-profile`.

**Scope**

- SDK: `profileHint` option, sent as `x-ds-profile` from one `callerHeaders`
  helper that both `request` and `requestBlob` use (they were two copies).
- Widget: the duplicated spread removed.
- `dev-keycloak`: `profile_claims=omit` mints a MEDICE-shaped token.
- e2e: the WordPress harness writes `learner-profile` as the plugin does; the
  WordPress group shares one Keycloak stub (a second start re-keys under the
  same `kid` and every later token was 401).

**Acceptance criteria**

- [x] A MEDICE-shaped token plus a `learner-profile` stores the address —
      `wordpress.spec.ts` "übernimmt die E-Mail aus dem MEDICE-Profil": red on
      `4034b08` (`Received: null`), green after.
- [x] JSON and byte requests both carry `X-DS-Profile` — `profile-hint.test.ts`
      in the SDK: 2 red against the old `index.ts`, green after.
- [x] Full `pnpm test:e2e`: 41 passed. `pnpm verify` through `check:static`
      green; `check:shell` not run locally (shellcheck not installed; no shell
      changed).
- [ ] Seen on MEDICE: an existing physician's address appears after their next
      visit to the page.

**What happens to existing participants** — Assumed from the code, not
observed: the hint is sent on every request and `provision_learner` fills an
empty `email` with `coalesce`, so each MEDICE physician gets their address on
their next request. Nothing is backfilled for somebody who does not come back.
A certificate already marked "unzustellbar" (`no_recipient`) is not resent
automatically — an operator uses **Details und Support → Erneut senden** once
the address is there.

**Not in scope:** development mode and progress reset (P258).
