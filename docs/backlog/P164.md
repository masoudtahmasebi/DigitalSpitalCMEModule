# P164 — Four reports from one session with the running product

**Raised by:** the client, 03.09.2026, working through the deployed
`4943541` — a certificate carrying the wrong VNR, a progress card showing two
different things on one line, and an exam offered again to somebody who had
already passed it.

**Branch** `claude/education-platform-roadmap-3vgrqh`, from `origin/main` at
`4943541`.

## P164-01 — the certificate and the Punktemeldung named different events

The client configured the course with the number off their Anerkennungsbescheid,
`2760012024200354002`, and the Teilnahmebescheinigung came out carrying
`2760552025919300018`.

Traced, not guessed:

| Document                  | Column read                                 |
| ------------------------- | ------------------------------------------- |
| Teilnahmebescheinigung    | `enrolments.vnr` — snapshotted at enrolment |
| Punktemeldung to EIV-FOBI | `courses.vnr` — read live                   |

So one participation could produce a certificate whose two barcodes name one
event and a Punktemeldung filed under another. §4 invariant 6 on a document a
Kammer scans.

The snapshot was deliberate — `0001_init.sql:249`, _"pin the compliance settings
in force at enrolment, so a later threshold change cannot retroactively
invalidate work already done"_ — and that reasoning is right for
`required_watch_percent`, `pass_threshold_percent`, `cme_points` and the
attested identity. It is wrong for the VNR, and the difference is what the field
**is**: the others are what the learner was asked for or earned; the VNR is the
Ärztekammer's identifier for the event.

**Which one wins is an accreditation question, so it was put to the client
rather than decided here (§7).** Their answer: _"the certificate should be
generated with the real number from the course."_ `certificateSourceColumns`
now reads `courses.vnr`; the snapshot column is untouched and still written.

**Watched red first**, and the reason it could never have gone red before: every
fixture set the course VNR and the enrolment VNR to the _same_ value, so no test
could tell which was being read (§9.1). The new case makes them differ.

## P164-02 — attempted, wrong, and reverted

**This section records a fix that was written, tested, committed, and taken back
out. It is here because the reasoning that produced it is the interesting part.**

The certificate had carried `2760552025919300018`, which is
`packages/seed/src/medice-adhs.ts:133`. Reading the client's first sentence —
_"that number should not be there in real system anywhere, that is only for the
seeder"_ — this added it to `isPlaceholderVnr` beside the nineteen zeros, so
every gate would refuse it. Eleven fixtures that used it as their _real_ VNR
moved to a neutral number, and the e2e harness gained a VNR of its own.

The client's answer on seeing it:

> _"2760552025919300018 can be a real number, everywhere the actual number given
> in the course should be used, that is the correct structure, why would the
> certificate even use a number from seeder when i have given another number in
> the course, it can be the case that i want a certificate with vnr all as 1s,
> it should just print what has been given!"_

They are right, on two counts.

**The blacklist is not a fix, it is a second guess at the same question.** The
certificate printed the wrong number because it read the wrong _column_
(P164-01). Once it reads the course, a course carrying `2760552025919300018`
prints `2760552025919300018` — which is correct, because that is what somebody
put there. Refusing the string treats the symptom of a bug that is already
fixed, and would have gone on refusing it after the cause was gone.

**And no nineteen-digit string is ours to refuse.** `PLACEHOLDER_VNR` is
defensible because nineteen zeros is not a number any Kammer issues. A
plausible one is different: the platform cannot know that no Ärztekammer will
ever issue `2760552025919300018`, and a course whose VNR is refused cannot
publish or certify — so the cost of being wrong is an operator locked out of
their own accreditation at the one moment it matters. That is the reasoning
`isPlaceholderVnr`'s own header already gives for refusing to validate the VNR's
_format_, and it applies unchanged here. I added the exception the comment three
lines above argues against, which is §11 rule 9 in the writing direction rather
than the reading one.

**The rule, in the client's words:** it should just print what has been given.

Reverted in full — `eiv.ts`, `index.ts`, `eiv.test.ts`, the eleven fixtures and
`apps/e2e/support/world.ts` are back to their state before it. Nothing of it
survives except this section.

### What the seed's default is still worth asking about

Unchanged, and now the only live question: `medice-adhs.ts` seeds a VNR at all.
With P164-01 that number reaches a certificate only on a course nobody has
configured — but a seeded accreditation number is a fact about MEDICE's course
that the platform invented. Whether the seed should write one, refuse to publish
without one, or leave it null is a question for the client and it is **not**
answered by refusing a string. Listed under "Not done" with the related
seed-publish item.

## P164-03 — one card, two scopes, neither named

`41:23 / 41:30` beside `33 % der Fortbildung absolviert`, on a module holding a
41:30 and a 24:49 video. The pair was `status.position` — the **current video's**
head against **that video's** length — and the percentage beside it was the
**course** rollup. The client read them as one quantity, which is the only
reasonable way to read two numbers on one line.

The numbers wanted already existed: `courseWatchCoverage` returns `watchedSec`
and `totalSec` across every video in the course, and they are the numerator and
denominator `achievedWatchPercent` is floored from. They were simply never
exposed. Contract first, then the SDK, then the card — so the pair, the
percentage and the bar are three readings of one number.

Two existing tests encoded the old model and were **migrated rather than
deleted**: one asserted the lesson's own timeline, the other asserted that a
text lesson has none. The second inverts on purpose — the course's total does
not stop existing because the learner opened a text section, and a counter that
vanishes on navigation is the same confusion in another form. A course with no
scorable video draws no counter at all, because `0:00 / 0:00` is a number
pretending to be information.

## P164-04 — an exam offered again, with nothing saying it was passed

_"When the doctor finished the course, cleared the exam and got the certificate
— I can still see the option to take the exam again."_

**Checked before changing anything: a retake cannot cost the physician
anything.** `assessment.repository.ts` stores `Math.max` across attempts and
`hasPassedQuiz` reads that stored best, so a failed repeat cannot lower a passed
score, flip `courseComplete`, or invalidate an issued certificate. Nothing in
`submit` refuses an attempt after completion, and after this it still does not —
reviewing an exam is a legitimate thing to want.

So the defect is entirely what the screen says, which is §9.4: the intro offered
a bare **Lernerfolgskontrolle beginnen** whatever had happened before. It now
names the score already on file, states the rule that makes a repeat safe — the
platform's own rule, not a reassurance invented for the screen — and demotes the
button from the primary call to action to **Zur Wiederholung erneut bearbeiten**.

`recordedQuizScore` reads `ProgressSummary.scorePercent`, which is already the
server's best attempt, rather than adding a second answer to "what did they get".

## Not done, and named rather than absorbed

**Whether the seed should invent a VNR at all** (P164-02), and — depending on
that answer — **what the seed's re-run should do about publishing.** The
The `status = CASE WHEN courses.vnr = $18 …` repair is conditioned on the
sentinel and carries P108-01's and P117-01's rules about what a re-run may
republish. Any change to what the seed writes has to account for it, which is
its own ticket rather than a fourth edit to that statement in one sitting.

sandbox does not have, so the journey is unexecuted here; the deploy runs it.
The VNR change in particular is asserted at the API and not on a rendered PDF.
