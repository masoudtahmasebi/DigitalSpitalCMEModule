**Raised by:** the client, 03.09.2026:

> i don't want to have eiv-worker enabled or disable in config.env i want to be
> able to sweitch that from the admin panel, and i want to be able to change the
> sending to domain, please bring all of those from config.env and put them to
> ui and db, so i can easilty test this, also with sample certificate
> generation, if we use test server, i should easily test this, and having this
> eiv-worker when we have test env does not make sense.

**Branch** `claude/education-platform-roadmap-3vgrqh`.

---

## The complaint is right, and it is a §9.9 complaint

`EIV_WORKER_ENABLED`, `EIV_BASE_URL` and `EIV_ALLOW_LIVE` were three lines in
`config.env`. Between them they decided **whether statutory Punktemeldungen
leave this installation and who receives them** — and changing either meant
editing a file on the host and redeploying. Switching to EIV's test system to
try something out was a deploy; switching back was another.

So in practice nobody switched, which is CLAUDE.md §9.9's corollary in its
purest form: a setting that needs a human to apply it by hand stays as it was.

## P180-01 — `platform_settings`

Migration `0051`. One row, no `customer_id`, no RLS policy, `super_admin` only —
there is one EIV worker per installation and one register it talks to. A
customer administrator's authority is over their own courses and participants;
pointing the platform at the live Ärztekammer endpoint would file statutory
reports for every tenant at once, including customers they have never heard of.
That is a new `ManagedEntity`, `platform`, rather than a reuse of `customer`:
the two are different authorities that one role happens to hold today.

**The endpoint is a word, never a URL.** Three choices — `mock`, `test`, `live`
— and `eivEndpointUrl` in `@ds/eiv-client` owns what each resolves to. A text
field would have moved the _address_ into the browser with the setting, and an
address a person can type is an address that can be the production register by
accident or somebody else's host on purpose. Same argument P157-01 made about
the diagnostic's environment, applied to the setting that decides where **real**
Punktemeldungen go. A test asserts no branch returns its caller's input.

**The worker reads it on every tick.** Not at boot, which would have moved the
problem behind a screen rather than solving it. `EivService.sweep` takes the
target as an argument now instead of capturing it, so there is no copy to go
stale.

**The consent that replaces `EIV_ALLOW_LIVE`.** Arming against the live register
still requires an explicit confirmation — a Punktemeldung cannot be unfiled,
only withdrawn, and the withdrawal stays visible on the physician's own record.
What changed is that the consent now records **who** and **when** instead of
being the string `yes` in a file nobody signed. Changing the endpoint clears it,
because consent is to one register and not to the idea of registers: an operator
who confirms live, detours through the test system and comes back would
otherwise still be armed on a decision taken before the detour.

The rule is a database CHECK as well as a service rule, so it holds against a
migration, a `psql` session and every future code path.

### What kept the safety while the switch moved

The deploy and the post-deploy smoke both refuse to run a browser journey
against an installation that files for real. They used to read `config.env`;
they now read `platform_settings` through **one** query, `ds_eiv_settings_sql`,
because two readings of "is the worker armed" is exactly the shape that lets a
smoke run against a host that reports to the Ärztekammer. The smoke fails
**closed**: an unreadable answer stops the run.

`ds_eiv_worker_will_file_live` gained a third argument for a state `config.env`
could not express — armed, pointed at live, and _not_ consented, in which the
application refuses every submission. Warning there would cry wolf on every
deploy of a half-configured host.

### `scripts/check-eiv-settings.mjs`

The failure mode of this move is quiet: somebody adds `EIV_BASE_URL` back to a
config file for a good local reason, a reader picks it up, and the console's
switch stops being the thing that decides. Nothing fails; the screen says one
thing and the worker does another (§9.10b).

So the three names are refused in every config file and every source file,
except the prose that explains where they went. In `pnpm verify` and CI, and
watched red three ways — the variable back in compose, the variable read in the
scheduler, and a glob that stopped matching.

**That third sabotage was not hypothetical.** The check's first run reported "1
config file scanned" and passed with `EIV_BASE_URL` still assigned two files
away: git's pathspec `**` matches whole directory levels, so `infra/**/*.yml`
found `infra/deploy/docker-compose.prod.yml` and missed the two beside it. The
source globs had the identical hole and missed the one file in the repository
that still read the variable. Both lists now carry a floor that fails if the
match count ever collapses again — §9.1's third form, found by looking at the
number the check printed.

### `EIV_HARNESS_*`

`apps/eiv-harness` legitimately reads its own base URL: it is a contract-test
CLI a developer runs by hand against EIV's test system. It used to read
`EIV_BASE_URL` — the same name the API read — which was fine while both meant
"where this process talks to EIV" and stopped being fine the moment the API's
moved into a table. One name, one meaning.

## P180-02 — A sample certificate

> also with sample certificate generation, if we use test server, i should
> easily test this

`GET /admin/courses/{slug}/certificate/sample`. Configuring a certificate means
uploading a stamp and a signature, typing a VNR, a Veranstalter and a
wissenschaftliche Leitung — and then having no way to see the result until a
physician finishes the course. Until this route, the first person to find out
whether the stamp was the right way up was a doctor holding their own CME
record.

**Everything about the event is real; everything about the person is synthetic
and says so.** The name printed on the page is `MUSTER — keine gültige
Bescheinigung`, the address line repeats it, and no EFN is printed at all — a
plausible one would be the single field most likely to make a sample pass for
real. `findCourseForSample` selects from `courses` alone, so there is no join
through which a participant's name, address or EFN could reach the document.

It issues nothing: no `certificates` row, no download token, nothing archived. A
sample is a rendering, not a document the platform stands behind.

It applies the same completeness check the real document gets and refuses with
the same list of missing fields — which is the answer an operator pressing the
button came for.

## The "other EFN settings"

There were none in `config.env` to move. `EIV_VNR` and `EIV_VNR_PASSWORD` exist
only in `.env.example` for the harness, `deploy.sh` has refused them in
`config.env` since P30, and the VNR and its password belong to a **course** —
they are set on the Zertifizierung tab, the password write-only and encrypted at
rest. That is stated here rather than left as a silent non-answer.

## Acceptance criteria

- [x] The worker is switched on and off from the console, and takes effect
      within a sweep rather than at the next deploy.
- [x] The register is chosen in the console, from three words, and the resolved
      address is shown.
- [x] The live register still requires explicit consent, now with a name and a
      timestamp on it.
- [x] Changing the register clears the consent.
- [x] A customer administrator can reach none of it.
- [x] The three variables are gone from every config file, and cannot come back.
- [x] The deploy and the smoke read the new source, through one query, and fail
      closed.
- [x] A sample certificate an operator can render before anybody takes the
      course, marked as a sample on the page.
- [x] Rules watched red: the consent requirement, the consent clearing, the
      shell guard's consent argument, the endpoint resolver's unknown word, and
      the settings check three ways.

## Not done

- **No e2e run.** `apps/e2e` needs a Docker daemon; this sandbox has none.
- **The first deploy after this needs one manual step, and refuses without
  it.** `platform_settings` defaults the worker **off**, so an installation that
  had `EIV_WORKER_ENABLED=yes` stops filing until somebody arms it in the
  console. A migration cannot read `config.env`, so nothing carries the old
  value across — anything that appeared to would be guessing.

  Rather than let that be silent, `deploy.sh` **refuses to start** while any of
  the three variables is still in `config.env`, with a message that says the
  installation is no longer reporting and names the switch to set. Queued
  Meldungen are not lost: they are filed on the first sweep after the worker is
  armed.

  That is the §9.9a shape handled deliberately — a change that needs a human is
  a change a machine has to insist on.
