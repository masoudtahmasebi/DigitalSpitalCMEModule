# P138 — The API was fine; the healthcheck could not go red for anything real

**Status:** three fixes, all in the deployment. The cause of the current
unhealthy state is **not yet established** — the diagnosis commands are at the
bottom and nothing here claims to have fixed it.

---

## What was reported

> _"why isn't the api responding?"_

It is. The API log shows uninterrupted traffic to 10:51 today — logins `201`,
`/admin/courses` `200`, `/courses` `200`/`304`, media views `201`. Disk 13 %,
memory 38 %, Postgres healthy, Redis up. Nothing in twelve hours of log is an
error the platform caused.

What is true is this, from `docker ps`:

```
ds-education-api-1   ds-education/api:16c8852   Up 22 hours (unhealthy)
```

The container has reported **unhealthy since the 16c8852 deploy**, while serving
every request put to it.

## P138-01a — The probe could only fail spuriously

The healthcheck fetched **`/health`**, which returns `200` whether or not it says
`degraded`. `health.service.ts` had already written down why that is wrong, about
a different reader, two phases before:

> _"a 200 saying 'degraded' in the body is a 200 to every load balancer ever
> written"_

A container healthcheck is exactly such a reader, and this one parsed no body. So
a dead database or a dead Redis left the container **healthy**, and the only
thing that could ever turn it red was the fetch itself failing or timing out.
CLAUDE.md §9.1 in the deployment: a gate that cannot go red for the conditions it
exists to detect — and, being unable to fail for a real reason, the one time it
did fail it was for an unreal one.

It probes `/health/ready` now, which answers `503`, and it **prints the body** on
failure. Docker keeps the last probe outputs in `State.Health.Log`; an exit code
alone sends whoever reads `docker inspect` at 22:00 back to guessing, where the
body names the dependency (§9.4).

## P138-01b — Redis had no healthcheck at all

`docker ps` showed `Up 3 weeks` for Redis whether or not it was answering, and
the API waited only on `condition: service_started`. So "Redis is running and
wedged" was invisible from every direction at once: `depends_on` did not check
it, `docker ps` did not show it, and the API's own probe could not go red for it.

That matters here specifically, because `/health` is the **only** endpoint that
touches both Postgres and Redis on every call — which makes a wedged Redis a
candidate for the current state while ordinary routes keep working.

Redis has `redis-cli ping` as a healthcheck now, and the API depends on
`service_healthy`, matching Postgres.

## P138-01c — Caddy would not have come back from a reboot

The one that turns this from cosmetic into urgent. `caddy` had:

```yaml
depends_on:
  api:
    condition: service_healthy
```

`depends_on` is evaluated when a container is **created**, so Caddy kept running
through 22 hours of unhealthy API. The bill was deferred, not waived: the host
prints `*** System restart required ***`, and on that reboot Caddy would have
waited for a health state the API cannot currently reach — leaving **every
hostname dark**, not just the API.

Caddy terminates TLS and serves the console, the portal and the widget: three
static bundles that need the API for nothing. It is `service_started` now. An API
that is down costs 502s on `api.…` and nothing else — the sign-in page still
loads and says so, which is a better answer than a refused connection everywhere.

The same argument is already in `health.service.ts` about liveness: _"a database
outage that made liveness fail would restart every API container in a loop,
turning a recoverable dependency failure into a self-inflicted outage."_ An edge
that will not start is that trade one layer out.

## What is NOT established

**Why the probe is failing right now.** The fix changes what is probed and makes
it explain itself; it is not known to be the cause. If the cause is a wedged
Redis or a dependency genuinely down, `/health/ready` will fail too — correctly,
and this time with the reason printed.

Three commands answer it, in order:

```bash
# 1. What did the probe actually say? Docker kept it.
docker inspect --format '{{json .State.Health}}' ds-education-api-1

# 2. Reproduce it from inside the container — the exact call the probe makes.
docker exec ds-education-api-1 node -e \
  "fetch('http://127.0.0.1:3000/health').then(async r=>console.log(r.status, await r.text())).catch(e=>console.log('THREW', e.message))"

# 3. Is Redis answering?
docker exec ds-education-redis-1 redis-cli ping
```

`(2)` splits the two shapes: a status and a body means the endpoint works and the
probe's own reading was at fault; `THREW` means nothing is listening on loopback
inside that container, which is a different bug entirely.
