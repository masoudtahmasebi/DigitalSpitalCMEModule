# P236 — the Mediathek said it was loading, for ever, over the error that said it had failed

Reported from production on `c2df963`, as a screenshot of
`verwaltung.digitalspital.com` → **Mediathek**:

> Zu viele Anfragen. Bitte versuchen Sie es in Kürze erneut.
> (Referenz: 03121f5b-c6cd-4632-b966-8152151dd85e)
>
> Wird geladen …

Both at once. And the second is the one an operator believes, because a spinner
is a promise that waiting will work.

---

## P236-01 — a failed load is not a load in flight

`useMediaLibrary`'s rejection handler set `problem` and **never touched
`assets`**:

```ts
(error: unknown) => {
  if (live.current) setProblem(describeError(error, de.error.generic));
},
```

`assets` therefore stayed `undefined`, and both screens render
`assets === undefined` as _"Wird geladen …"_. So **every** failure of the first
load ends in an eternal spinner — the 429 above is only the one that was
reported. There is no way off that screen but a full page reload.

### Why `assets = []` would have been worse

An empty array is a claim about the customer's files. Rendering _"Sie haben noch
nichts hochgeladen"_ over a refusal is the one answer worse than the spinner,
because it looks like data and an operator would act on it. So the fix is a
**third state** — `loadFailed` — not a substitute value. That is §9.6's shape
one layer up: a refusal must not be indistinguishable from a legitimate empty.

### The fix, and why `LoadFailure` already existed

Seven screens render `LoadFailure`, and P231-02 gave it a **required**
`retryable` prop precisely so every screen had to answer _"could trying again
ever work?"_. `useMediaLibrary` is a hook rather than a screen and was never
asked. Now:

- a failed **load** replaces the list — nothing on screen is true, so nothing
  stays;
- a failed **write** still sits above the list, which is still true;
- the retry is present for a 429 and **absent** for a 404, via `isRetryable`;
- a successful reload clears the failure, or a retry that works leaves the
  failure screen up and the operator stuck on it.

### Two instances, because the hook has two callers (§9.11)

|                |                                                       |
| -------------- | ----------------------------------------------------- |
| `MediaLibrary` | the Mediathek screen — the one reported               |
| `MediaDialog`  | the picker, **found by looking rather than reported** |

The picker is the worse of the two. It is opened _during_ something — an author
adding a video to a course — so the stall is a step of their work that appears
to still be going, in a box they opened on purpose.

### Watched red

| Sabotage                                                 | Result                                                                                                                      |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| restore the shipped handler (`problem` only)             | **2 failed** — _"the screen still says 'Wird geladen …' after the load was refused"_                                        |
| `setLoadRetryable(true)` instead of `isRetryable(error)` | **1 failed** — the 404 case offers a retry that cannot work (§9.2)                                                          |
| revert the picker's render                               | **1 failed** — _"the picker still says 'Wird geladen …' … in a dialog an author opened in the middle of building a course"_ |

And one caught by the compiler rather than the suite, which is worth recording:
the first version of the picker test passed `purpose="course_video"`. All five
tests were green and `pnpm typecheck` was red — vitest does not typecheck. A
green suite is not a green gate (§9.1).

## What is NOT established: where the 429 came from

Stated plainly because the fix above does not depend on it and must not be read
as having addressed it.

**Measured**, on the component in isolation:

|                                       |       |
| ------------------------------------- | ----- |
| requests from one mount               | **1** |
| requests after five parent re-renders | **6** |

So one mount is not a loop — my first hypothesis, that an infinite render loop
was hammering the API, is **wrong** and is recorded here as wrong. What is true
is the amplifier: **each re-render of the component that owns the client costs
one extra `adminListMedia`**, because `App` passes `onExpired={() => …}` as an
inline arrow, which gives `client` a new identity, which invalidates `reload`,
which refires its effect.

The budget is `mediaUpload: { limit: 60, windowSec: 60 }` — and every media
route shares it, list and upload alike.

**Not established:** what actually spent 60 requests in a minute on that host.
Candidates, none confirmed — a burst of parent re-renders, an upload session
sharing the same budget, repeated manual reloads while the screen was stuck
(which the eternal spinner actively encourages). The correlation id in the
report, `03121f5b-c6cd-4632-b966-8152151dd85e`, locates the refused request in
the API log and is where the answer is; I could not reach the host from the
sandbox to look.

### P236-02 — the stable-identity fix, deliberately not done here

Making `onExpired` a `useCallback` removes the amplifier and is two lines. It is
**not** in this ticket, because it changes how every screen's client is created
and every screen's load effect fires, on the day of a production incident, for a
cause that has not been established. It is worth doing on its own evidence, with
the request counts measured per screen before and after.

Until then the guard against a stuck client is the one added above: the screen
now says the request failed and offers the retry, instead of spinning and
inviting the reload that spends more budget.
