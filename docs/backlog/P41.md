# P41 · Checking for this class instead of waiting to be told

> can you please check all of the system for this bad experiences that i am
> finding one by one? how can you check this yourself?

Fair question, and the honest answer is that every defect reported this week was
findable from source and nobody was looking. They share one shape:

**The system states a rule, or offers an affordance, that some other part of it
does not honour.**

| Reported                                    | The disagreement                                                      |
| ------------------------------------------- | --------------------------------------------------------------------- |
| `course_editor` met "keine Berechtigung"    | domain granted capabilities; no route accepted the role               |
| A reset button that only 403'd              | the comment said "never for your own"; the code had no such condition |
| An invitation that was a string, not a link | copy said "Dieser Link"; the component rendered a token               |
| A link that never expired                   | `INVITE_VALID_DAYS` written, exported, unit-tested, never called      |

None needed a browser to find. Two scripts now look for them.

---

## P41-01 · `scripts/unused-rules.mjs` — rules nothing enforces — **done**

- **Estimate:** 2 h · **Review gate: none**

Every value `@ds/domain` exports, against every caller outside the domain and
its own tests. A hit is not automatically a bug — a helper used only internally,
or a constant held for a feature not yet built, is legitimate — but somebody has
to look, which is more than was happening.

It would have found **P39-01** the day it was written: `inviteStatus` and
`resetStatus`, exported and exhaustively unit-tested, called from nowhere, while
an invitation link was a permanent replayable key to a console account.

### What it found on its first run

**`invalidBrandingFields`**, whose own comment says _"`parseBranding` drops
silently because a learner's screen must render whatever is stored. An admin
saving a value deserves to be told it was rejected, which is a different
question and gets a different function."_ Nothing called it.

So `PATCH /admin/projects` ran the _read-path_ parser over an operator's input:
an unparseable hero image URL was dropped, the request answered 200, and the
console said **"Gespeichert."** The operator found the field empty later, with
nothing to act on and no reason to suspect the save.

Now refused, whole, naming the invalid fields — **their names, never their
values**: the case that exercises this is a CSS injection, and echoing the
payload into a message a browser renders would turn the refusal into the vector.

## P41-02 · `scripts/role-matrix.mjs` — screens a role cannot open — **done**

- **Estimate:** 3 h · **Review gate: human — auth**

Four roles × nine screens = thirty-six answers, every one derivable from three
files: the capability matrix in `@ds/domain`, the `NAV` array in the console,
and the `@Roles` decorators on the controllers. It reads all three rather than a
hand-written table, so a role added to any of them is covered on the next run.

It checks **loads**, not writes. A screen an operator may see and not change is
a legitimate design here — a department administrator reads a Keycloak binding
they may not edit — and the refusal on the button is the boundary working. What
is never legitimate is a screen that cannot finish loading.

Runs in `pnpm verify` and in CI.

### What it found

Three screens a **`department_admin`** is drawn and could not load:

- **Organisation** — `GET /admin/departments` accepted them, `GET /admin/projects`
  did not, so the screen errored on the read it needed rather than the one it
  was refused.
- **Teilnehmende** and **Bescheinigungen** — the moderation controller's own
  header said `learner_record` "is not in their set", which was simply false.
  The matrix grants them `learner_record` and `certificate` on the reasoning
  that they run a department _"and the people who take them"_. The console
  believed the matrix; the API believed the comment.

The reads now accept them. The **corrections do not**: changing a physician's
name, erasing a subject and withdrawing a Teilnahmebescheinigung are acts
against a CME record with a chamber on the other end, and the header's reasoning
holds for those even though it was wrong about the matrix. Five integration
tests state both halves.

### Two bugs in the checker itself, both worth recording

1. It resolved only `const …ROLES` aliases, so `RECORD_READERS` came out empty
   and it reported that a super administrator cannot open a screen they have
   always been able to open. **A checker that cries wolf gets switched off.**
2. It parsed five of the nine navigation entries and still printed _"every drawn
   screen loads"_ — green because of what it did not look at, which is the exact
   failure it exists to catch, one level up. It now asserts that the screens it
   knows and the screens the console draws are the same set, and fails if they
   diverge.

## P41-03 · The check that was only in CI — **done**

- **Estimate:** 1 h · **Review gate: none**

Two commits went red on **"Verify generated SDK matches the contract"**, a check
that has been right since P2-06 and that I could not run.

`contracts/openapi.yaml` gained two paths; `packages/sdk/src/generated/schema.ts`
did not. I ran `pnpm --filter @ds/sdk build`, which runs `tsc` and compiles the
_existing_ generated file perfectly happily. Only `generate` re-derives it. Two
verbs, one easy to mistake for the other, and nothing local said so — every gate
I had was green and the tree was 195 lines stale.

So the loop was: edit the contract, run every local gate green, push, wait ten
minutes, read a diff. `scripts/check-sdk.mjs` closes it, and `pnpm verify` now
runs it.

### It compares before against after, not against `HEAD`

The first version asked `git status --porcelain -- packages/sdk`. Exact in CI,
where the tree is clean; locally it answers a different question — "do you have
uncommitted SDK changes" — which is true and harmless every time somebody is
mid-edit. **A gate that fires when nothing is wrong is a gate people learn to
ignore**, which is the mechanism that put this check in CI only to begin with.

### The general lesson, which is the same one twice

A check that exists only in CI is a check the person writing the code does not
run. `pnpm verify` is now the full set: lint, format, typecheck, unit tests,
`check:roles`, `check:sdk`, audit. `env-audit` and the integration suite are
still CI-side and want the same treatment.

## What these do not cover

Stated because a check whose limits are unwritten gets trusted past them.

- **Copy against behaviour.** "Dieser Link" over a bare token was found by a
  person, and would still be. Comparing a German sentence to what a component
  renders is not mechanical.
- **Writes.** Deliberate, see above.
- **The learner plane.** The portal has no role matrix — every participant is a
  learner — so there is nothing analogous to check there.
- **Screens whose mount-time reads change.** `SCREEN_LOADS` is hand-kept. The
  set-equality assertion catches a _new_ screen; it does not catch a screen that
  starts loading a _new route_.
