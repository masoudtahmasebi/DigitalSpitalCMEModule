# P208 — the band above the hero, and the half-answer that left it there

The client, twice. First, with the embed open on their own page:

> there is a not needed `mb-4` and `space-y-6 py-4` which makes this different
> than the design

and then, after the fix shipped and deployed, with DevTools open:

> why is `space-y-6` back on the div with parent of `class="ds-lms-root"`?

---

## P208-01 — it was never back

It was never removed. P204-01 read that first sentence as three classes on two
elements, took `mb-4` and `py-4`, and **kept** `space-y-6` — with a comment and
a line in the pull request saying so:

> `space-y-6` **stays**: that's the gap between logo, hero and content, which
> the drawing does have.

The same pull request said, under "Not verified": _"That the layout changes
match the design — these are pixel judgements against an export I don't have."_
Those two sentences cannot both be load-bearing. One asserts what the drawing
has; the other says the drawing has not been seen. The assertion should have
been the question.

That is §11 rather than §9: not a defect found by clicking, but **a confident
sentence about something unverified**, which then justified overriding half of
what the person holding the design had asked for.

## What is actually wrong, and it needs no drawing

`BrandLogo` returns **null** when the customer has set no logo. The course
detail wrapped it unconditionally:

```tsx
<div className="space-y-6">
  <div className={CONTENT}><BrandLogo … /></div>
  <StickyMetaBar … />
```

So on a project with no logo the first child is an **empty div**, and
`space-y-6` still reserves 24 px above the hero — a band of the host page's
background in exactly the place the `py-4` report was about. The client's two
messages are one defect, and the second one is the first one still there.

## The lesson was already written down, one screen over

`Catalogue` had met this and guarded it, and left the reason in its own comment:

> `BrandLogo` returns null when the customer has set no logo, but `px-4 pt-4`
> inside a `space-y-6` does not — it left 40 px of nothing above the hero, which
> the layout draws flush to the host page's header. Visible the moment the
> catalogue was screenshotted at 430 px against the mobile design, and just as
> wrong at 1440 px.

Its sibling screen never got the guard. One component learned the lesson and the
one beside it did not — CLAUDE.md §9.11 inside a single file, and the reason a
fix that was "the same thing, on the catalogue" did not generalise on its own.

**The sweep** (§11.11), stated in full because the question must not depend on
somebody thinking to ask it. Three `BrandLogo` call sites:

| call site                    | state                                                                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `App.tsx` `Catalogue`        | already guarded — the wrapper renders only when there is a logo                                                           |
| `components/CourseShell.tsx` | safe — the wrapper always holds the back button, so it is never empty, and its comment already records the null-logo case |
| `App.tsx` `Loaded`           | **the defect** — fixed here                                                                                               |

## The fix

The gap now belongs to the elements that want one rather than to the container:

- the logo wrapper renders only when `branding.logoUrl` is defined, and carries
  its own `mb-6`;
- the tab panel carries `mt-6` — the same gap the container used to give between
  the meta strip and the tab row, unchanged, so removing the band above the hero
  could not take it with it;
- `space-y-6` is gone from the root div, which is what was asked for.

With no logo the hero meets the page header. With a logo, the rendering is
identical to before.

## Watched red

The failing case first (§11.6). `App.route.test.tsx` renders the course detail
with the file's default stub — which answers `/branding` with a `CourseDetail`,
so `parseBranding` finds no logo, which is the state under test — and asserts
that no **empty element** sits between the root and the hero:

```
× puts no empty element above the hero when the customer has no logo
  AssertionError: an empty element above the hero is a band of the host page's
  background: expected [ Array(1) ] to deeply equal []
```

Green after the fix; 418 widget tests pass.

It asserts the empty element rather than the absence of the string
`space-y-6`, deliberately. A class-name assertion would pass on any rewrite that
reintroduced the same gap under another name, which is §9.7 — the test would be
about the class rather than about what a physician sees.

## Not verified

Whether the design wants a gap between the logo and the hero **when a logo is
set**. It is unchanged at 24 px, because changing it would be a second guess
against an export I still do not have. If it should be flush there too, that is
one class on the logo wrapper — and this time it is a question rather than a
claim.
