# P59 — What the QA pass through the Teilnahmebescheinigung found

Raised 12.08 by the QA agent's Section 8 (certificate generation and e-mail
delivery), run against a local STARTTLS test SMTP sink and the `@ds/eiv-client`
mock on `127.0.0.1` — never a live mail relay and never a live Ärztekammer.

The PDF itself was correct in every field the Bescheid names. The **pipeline
around it was not connected at either end**: nothing created the row the
delivery sweep claims, and nothing attached the document the e-mail is about.

Both are the same shape, and it is the one CLAUDE.md §9.3 and §9.7 name from
opposite sides: **a capability that was built, tested and never called.**

---

## P59-01 · Completing a course issued no certificate · 1 h

**Status: done.** Touches certificates — human review.

### What was wrong

`certificates` rows were created lazily, by the first request that _fetched_
the certificate — the preview or the PDF download.

Everything downstream keys on that row. The delivery sweep claims
`status IN ('issued','pending')`, so a physician who finished a course and
closed the tab was never sent anything. The durable delivery pipeline built in
P8-03 — the lease, the backoff, the bounce handling, the audit record — could
only ever run for people who had **already downloaded the certificate
themselves**, which is exactly the population that did not need the e-mail.

QA saw it end to end: complete a course, then

```
certificates rows immediately after completion: 0 []
after two delivery sweeps:                      0 []
messages in the test mailbox:                   0
```

### What changed

`CompletionService.complete()` calls `issueForEnrolment` after
`markCompleted`, one line below the existing `queueSubmission`. The
certificate is minted when it is earned.

`issueForEnrolment` **never throws.** A course whose stamp was never uploaded,
or a name that cannot be composed, answers `undefined` — the same trade
`queueSubmission` makes for a missing VNR. The physician has met every
condition and the Punktemeldung is already queued; failing their completion
because somebody forgot to upload an image would be the wrong way round. The
download route still explains the gap properly to a person looking at a screen.

The issue is idempotent, and was already: whichever of completion and download
happens first mints the token and the other finds it.

### The test that was green on the broken system

`completion-flow.integration.test.ts` had **"records the issue exactly once,
with a high-entropy token"** — a correct assertion, in the wrong place. It sits
in the `Teilnahmebescheinigung` block, which runs _after_ the preview and the
download, so lazy creation satisfied it completely.

The new case is in the completion block, where no certificate endpoint has been
called yet, and its name says what it is for: _"issues the certificate at
completion, before anybody asks for it"_. CLAUDE.md §9.7 — for anything tested
separately, name the caller; if the test would pass with the call site deleted,
the call site is untested.

### Acceptance criteria

- [x] Completing a course creates the `certificates` row, `status = 'issued'`
- [x] The row is created before any certificate endpoint is called
- [x] A course missing its stamp still completes, and still queues the
      Punktemeldung
- [x] Verified red: deleting the `issueCertificate` call turns the new
      integration case red and leaves the old one green — which is the point
- [x] Verified live: completion → issued row → EIV submitted → e-mail delivered
- [ ] **Human review** — certificates. The reviewer's question is **whether a
      certificate that cannot be rendered should still let the completion
      stand.** It does: the physician met every condition and a missing stamp
      image is the organiser's problem, not theirs. Deciding the other way
      refuses an earned CME point over an unuploaded PNG while the 8-day
      reporting window runs. Packet §7.

## P59-02 · The e-mail promised an attachment and carried none · 1.5 h

**Status: done.** Touches certificates — human review.

### What was wrong

The delivery copy has said

> Ihre Teilnahmebescheinigung finden Sie im Anhang dieser E-Mail.

since P8-03. `compose()` built `to`, `from`, `subject`, `body` and a transport.
`OutboundMessage.attachments` — which the SMTP channel has forwarded to
nodemailer all along — was never set. QA read the sent message and found one
`text/plain` part.

So the one thing the e-mail is about was the one thing missing from it, and the
sentence saying so made it worse: a recipient who trusts it stops looking.

### What changed

A port, `CertificateAttachmentPort`, and one adapter, `CertificateAttachments`.
The sweep asks for the PDF per attempt and passes it to `compose`; the "im
Anhang" sentence is now conditional on whether one arrived, so the copy cannot
claim an enclosure that is not there.

Three decisions worth stating:

- **Rendered per attempt, not stored.** The row records what was earned and the
  PDF is a view of it, so a retry a day later carries a document that agrees
  with the record as it stands. It is also why there is no `pdf_path` column
  and no blob to erase — see §"Differences from the section's wording".
- **Through `CertificateService`, not a second assembly.** Teaching the
  delivery repository to return bytes would have put rendering in a repository
  and produced a second assembly of the certificate's fields beside the one
  `download` uses. Two assemblies is how a physician ends up with an e-mailed
  document that differs from the one on their screen — CLAUDE.md §4 invariant 6,
  one table across. QA confirmed the two agree: the emailed PDF and the
  downloaded PDF carry the same VNR, the same name and the same date.
- **A render failure does not stop the message.** The learner can download the
  document from their account either way. An unexpected error is logged with
  the certificate id and the error _class_ — never the physician, never the
  document — and the message goes without the sentence.

### The tenant scope is the part a unit test cannot check

`CertificateAttachments` opens `runInTenant(pool, { customerId, role: "system" })`
before reading. Without it, `certificates` and `enrolments` are under FORCE ROW
LEVEL SECURITY, the read matches zero rows, and the adapter answers `undefined`
— which is indistinguishable from "this course has no certificate". CLAUDE.md
§9.6, exactly. So the assertion lives in the integration suite with the real
adapter wired in, and the red check is pointing it at the wrong customer id.

`"system"` rather than a borrowed `super_admin`, so the audit trail can tell the
delivery worker apart from a person.

### The fixture that was not testing what it looked like

The delivery integration suite's course carried no VNR, no points and no stamp,
and its enrolment carried none of the **snapshotted** `vnr` / `cme_points` /
`cme_category` the certificate is actually rendered from (P3-01 — the snapshot,
never the course, so re-pricing a course cannot rewrite a certificate already
earned). Every assertion would have been describing the no-attachment fallback
while reading as though it described the ordinary case. Furnishing the fixture
came first; the assertions came after.

### Acceptance criteria

- [x] The message carries the PDF, `application/pdf`, filename beginning
      `Teilnahmebescheinigung`
- [x] The "im Anhang" sentence appears if and only if something is attached
- [x] A course with no stamp still gets its e-mail, without the sentence
- [x] Rendered once per attempt, inside the claimed row's tenant scope
- [x] Verified red at both layers: dropping the `renderFor` call turns three
      unit cases red; pointing `runInTenant` at another customer turns the
      integration case red
- [x] `pnpm verify` green; 479 integration tests green
- [ ] **Human review** — certificates, and held with P59-01 rather than for a
      decision of its own: the copy promised an enclosure and the message
      carried none. There is no judgement call, only a correction. Packet
      §"held with their siblings".

## What Section 8 confirmed as already correct

Run against a test SMTP sink on `127.0.0.1:1025` with the mailbox on disk. The
project's own SMTP settings pointed at it: `medice-adhs` →
`127.0.0.1:1025`, sender `MEDICE Fortbildung <fortbildung@medice.example>`.

- **8.1 — nothing before the course is finished.** `GET …/certificate` → 404,
  `GET …/certificate/pdf` → 409 _"Die Teilnahmebescheinigung steht erst nach
  Abschluss der Fortbildung zur Verfügung."_, and zero rows in `certificates`.
- **8.2 — the whole chain, in one completion.** `issued` row at the moment of
  completion → Punktemeldung `submitted` at attempt 1 → e-mail `delivered`,
  three seconds later.
- **8.3 — every field the Bescheid names, and no placeholder.** Veranstalter,
  the participant's composed name, the course title, the VNR as **both**
  barcodes (Code 39 and Datamatrix) plus the digits and _"Felder bitte nicht
  überkleben"_, the participation date and time, `als on-demand-Webinar`, the
  creditability sentence templated from the course's own values (_"mit 4
  Punkten (Kategorie D)"_, _"Ärztekammer Westfalen-Lippe"_), the Originalstempel
  clause, and the signature block with the Wissenschaftliche Leitung's name.
  Scanned for `undefined`, `null`, `NaN`, `[object`, `{{`: none present.
- **8.4 — from the project, not from DigitalSpital.** `From: MEDICE Fortbildung
<fortbildung@medice.example>`, subject _"Ihre Teilnahmebescheinigung: ADHS
  Akademie adult"_, `multipart/mixed` with the PDF attached.
- **8.5 — a 451 retries and then succeeds.** Attempt 1 `SMTP 451`,
  `delivery_next_attempt_at` set, row still claimable; attempt 2 delivered,
  `delivered_at` stamped. Both attempts audited with a count and a channel id —
  no name, no address, no token. The rejected attempt carried the PDF too.
- **8.6 — the download belongs to one person.** The owner gets 200,
  `application/pdf`, `content-disposition: attachment`, `cache-control:
no-store`. Another learner in the same tenant gets 404 on both the preview and
  the PDF; an unauthenticated request gets 401. There is no route that trades
  the download token, or the certificate id, for a document.

### The one thing that failed for a good reason

The first delivery attempt against the sink came back `SMTP 500` and abandoned.
That was the **product being right**: `SmtpDeliveryChannel` sets
`requireTLS: true`, so it refuses to hand a physician's Teilnahmebescheinigung
to a server that will not do STARTTLS. The test sink was replaced with a
STARTTLS-capable one and the API told to trust its certificate — the code was
not touched, and it should not be.

### Differences from the section's wording, not defects

Three, and each is a decision rather than a gap.

- **The certificate is gated on completion, not on a successful EIV
  submission.** Section 8.1 expects a 400/403 until the Punktemeldung lands.
  Gating there would deny a certificate for every point-free course — where
  there is no Meldung to wait for — and would withhold earned documents for the
  length of any Kammer outage. The two are deliberately independent: the
  physician earned the document by finishing the course, and the Meldung is the
  platform's obligation, not a condition on theirs. This is worth a decision
  from MEDICE if they read it differently.
- **There is no `pdf_path`.** No PDF is stored. The `certificates` row records
  what was earned; the document is rendered from it on demand, for the download
  and for each delivery attempt alike. That is what keeps the emailed copy and
  the downloaded copy the same document, and it means an erasure has no blob to
  chase.
- **The EFN is not printed on the certificate.** The ÄKWL Muster has no field
  for it — the EFN goes to EIV-FOBI, which is what identifies the physician to
  the Kammer. Putting a permanent physician identifier into a PDF that travels
  by e-mail would widen the footprint ADR-0004 exists to keep narrow.

### And one field that is genuinely blank

`Anschrift:` renders as an empty line, because the platform holds no postal
address. That is **S12 / requirements §6.8**, still open with the ÄKWL: collect
it (+2 h across P1, P5 and P8, plus a lawful-basis and retention decision), or
confirm a blank address is acceptable for an online on-demand format. The line
is drawn rather than omitted because a Muster missing a line it should have
looks altered.

`Originalstempel` (S11) remains the larger open question above it, and the
answer to that one decides whether any of this produces a valid document.
