# P215 — the widget suite went red in CI on a commit that touched none of it

Found while merging P214: `@ds/widget#test` failed in CI and passed locally six
runs in a row.

**It predates P214.** It reproduces on `6717a94` — already merged, already
deployed — with `--sequence.shuffle`, twice in four runs. What P214 changed was
the _file ordering_ vitest picks (a heuristic over file size and previous
durations), and adding one test file was enough to expose it on a CI runner.

## The cause

`element.test.ts` waited a fixed number of React commits for the catalogue to
appear, then looked for a button. How many commits that needs depends on whether
`useBranding`'s **module-scoped cache** already holds an entry for the test's
`(apiBase, projectSlug)` — a cached branding resolves in fewer turns than a
fetched one. That cache is keyed on two values every widget test uses, and
nothing emptied it between cases.

So the suite's result depended on which case ran before, which depended on the
file order, which differs between a laptop and a CI runner. §9.8: _state that
outlives a test is a failure attributed to the wrong code._

## The fix, at the class rather than the instance

§9.8's own words are _"reset every ambient store in `afterEach`, not only the
one that broke"_ — and it has been learned twice here already (`localStorage` in
P22-08, the jsdom URL in P42-01), both times by fixing the one store that broke.

`apps/widget/vitest.setup.ts` now runs for **every case in the package** and
clears all of them: `clearBrandingCache()`, `clearCopyCache()`, the jsdom hash,
`localStorage` and `sessionStorage`. A test that has to remember is a test that
will forget; a cache added later joins by being listed there once.

The second half is the fixed-turn wait itself. `element.test.ts`'s own header
already said _"for an assertion that something appears, prefer `waitForText`,
which waits for the fact instead of for a duration"_ — a rule written three
lines above a helper that did not follow it. It does now, and the disappearance
case uses `waitForAbsence`.

**Watched red, then green:** `--sequence.shuffle` failed 2 of 4 runs before and
**0 of 12** after.

One assertion of mine had to become more honest as a result: a preview case
asserted "no request reached `api.example.test`", which passed only because the
branding cache happened to be warm. With the cache cleared the public
`/branding` fetch is deterministic, so the case now names what it actually
defends — no `/courses` and no `/enrolment`, the two that need a token.
