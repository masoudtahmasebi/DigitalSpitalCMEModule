## P176-01 — Two components, one exam, two answers

P170-01 closed the sitting of a passed exam and took the button off the exam's
own intro. **`PlayerScreen` draws a different control**, under the module list,
and went on offering `Lernerfolgskontrolle beginnen` for an exam that cannot be
begun — so both sentences were on screen at once, which is what the client met.

The control stays and the verb changes: `Lernerfolgskontrolle ansehen` once the
recorded best score clears the course's threshold. The screen behind it is worth
reaching — it carries the score and the way on to the Punktemeldung or the next
section — and hiding it would take that away to fix a label.

`quizPassed` is derived the same way the gate derives it: the stored
`scorePercent` against `state.passThresholdPercent`, which since P174-01 is the
course's live value. A failed attempt leaves a score behind and still says
"beginnen", because the exam is still open — there is a case for that.

## P176-02 — A document named with no way to it

P168-04 gave a certified course its own line on the catalogue card,
"Abgeschlossen – Teilnahmebescheinigung verfügbar", and stopped there. The
client asked the question the line invites, and it is §9.4 with the sentence
already written: naming a document without a route to it.

**Zur Teilnahmebescheinigung** now sits under that line and opens the course on
its Zertifizierung tab, through a fourth `OpenIntent`, `certificate`, accepted
as `open-at="certificate"` like the other three.

The tab rather than the file: the download lives there beside the accreditation,
the conditions and the VNR it belongs to, and a PDF that arrives with no page
around it is a document nobody can check. Granted only on the server's own
`completedAt` — before a completion is recorded there is no Bescheid, and the
tab would draw "noch nicht verfügbar" under a promise the card had just made.

## P176-03 — P162 was fixed; its third foreign key was not

**The 500 the client asked me to fix is already fixed and live.** `cc0cca6`
(deploy run 100, 09:17 today) added a children census to all six levels —
Abteilung, Projekt, Kurs, Modul, Kapitel, Inhalt — plus the quiz-questions case,
each refusing with a 409 that names what is in the way. `Verified:`
`authoring.integration.test.ts` "a level that still has something inside it
refuses, rather than failing", 55 cases green.

I have been carrying "P162 — tests written, product fix not" in every summary
since; that note was stale and I should have re-read the code before repeating
it. It is withdrawn.

**What was genuinely still open** is one foreign key. `contents` is referenced
with `ON DELETE RESTRICT` by three tables:

| table              | counted before | now |
| ------------------ | -------------- | --- |
| `content_progress` | yes (P162-01)  | yes |
| `quiz_questions`   | yes (P162-01)  | yes |
| `quiz_attempts`    | **no**         | yes |

The only reason that was not a 500 is an invariant nothing enforces: `submit`
writes an attempt and a progress row in one transaction, so an attempt has
always had a progress row beside it, and the progress row is what the census
saw. Nothing deletes either table — erasure anonymises rather than removes,
because an assessment record behind an issued Bescheid has to stay — so the gap
is not reachable through the API today.

Closed anyway. A guard that matches two of three foreign keys is right by luck,
and the next `RESTRICT` added to `contents` would be a 500 nobody predicted. The
module and chapter censuses count attempts beneath them too, on the same
reasoning.

The test builds the state in SQL, because the API cannot produce it — which is
the point: the guard has to hold on the schema's terms rather than on the happy
path's. Watched red, and the failure is exactly the client's original report:

```
update or delete on table "contents" violates foreign key constraint
  "quiz_attempts_content_id_fkey" on table "quiz_attempts"   → 500
```
