## The blocker, stated plainly

`eiv.service.ts` sends the learner's completion instant as `teilnahmedatum`, and
EIV refuses a date outside the accredited period with **406** — the comment
above that field has said so since P31-01. The period ends **19.01.2024**.

**So every Punktemeldung this platform files for that VNR today is refused**,
whatever the EFN. Not a defect in the code; the register is describing a
five-day event in the past and we would be reporting a completion in 2026.

That is a decision for the client and the Ärztekammer, and CLAUDE.md §7 refuses
to guess at it. What this ticket does is make the platform _say so before
sending_ instead of collecting one 406 per physician.

## P184-01 — the platform compares the window before anything is filed

`reportableOn` in `@ds/domain`: given a completion instant and the accredited
period the register itself returned, does EIV accept it?

Surfaced in `checkConnection`, which already reads the event — so the Verwaltung
screen that says "the register answered" also says **how many queued
Punktemeldungen it will refuse, and why**. Today it prints the period and leaves
an operator to compare two dates in different formats and time zones, which is
§9.2 with the arithmetic left to a person.

It **reports rather than holds.** Refusing to send would silently miss the
statutory 8-day deadline in the case where our copy of the period is stale, and
EIV is the authority on its own accreditation. A warning an operator can act on
is the honest instrument; a queue that quietly stops is not.

## P184-02 — deferred, and why it is not needed yet

**`courses.eiv_test_event` is not built.** It was in this ticket to make seeding
the test VNR safe, and nothing is seeded (P184-03), so the hazard it guards
against does not exist: the test event is configured by an operator in
Verwaltung, on one course, on one installation, deliberately.

What already stands between that course and the live register is stronger than a
column: the register is a console setting the live tier of which requires a
named consent (P180-01), and the deploy refuses a config that names the live
host without one. Adding a third guard for a course nobody has created would be
a rule with no caller, which is §9.3 in the direction people forget.

It becomes necessary the moment anything seeds a real VNR. Recorded here so the
next person reaches for it rather than inventing it.

## P184-02 (original) — a course whose VNR belongs to a test register cannot file live

`courses.eiv_test_event`. The four EFNs above and VNR `2760012024200354002` are
EIV's own test fixtures. The moment either is configured on a course, the
sentence `docs/deployment.md` has carried since P20 — _"nothing here can reach
the live EIV endpoint"_ — stops being true by construction: a real VNR on a real
course files wherever the installation points.

So the course carries the fact, and the worker refuses to submit a test event to
the live register. Enforced in `@ds/domain` beside the existing live-consent
rule, so it holds for the worker, the admin requeue and the harness alike rather
than at one call site.

This is what makes the rest of the ticket safe to do at all.

## P184-03 — the test EFNs, where somebody testing will find them

`docs/eiv-test-system.md`, beside the VNR that is already there. They are
EIV-issued test identifiers, they belong to no physician, and the document
already carries the test VNR — which is the same class of value.

**Not seeded.** A seed runs on every deploy (§9.10b) and would put a real VNR on
a course on every installation, including one pointed at the live register.
Configuring the test event is an operator's deliberate act in Verwaltung, and
P184-02 is what stops it reaching the wrong register.

**And the VNR password is not committed anywhere**, `1234` included. The client
has said it is public and it plainly is a placeholder, but §4 invariant 7 is
about the shape of the system rather than the sensitivity of one value: the
moment a plaintext VNR password is normal in this repository, the next one is
somebody's real one. It is supplied per command, as `./dsc eiv` already takes
it.

## What P184-03 turned out to be

Nothing to add. The four EFNs the client sent are **already** in
`docs/eiv-test-system.md` — the first four of a 40-odd EIV-issued list that has
been there since P130, under a paragraph explaining why synthetic identifiers
may be written down at all.

What _was_ false in that document is the line beneath them: _"Not verified:
anything against the real EIV test server."_ It is now, and the client's own
output is the record — so the section carries the run, the answers to S11 and
S25, and the one step still unproven: a `push_teilnahme`, which the accredited
period currently prevents.

`docs/show-stoppers.md` is updated with the same evidence. S25 closes for the
test VNR; S25b opens for MEDICE's live one, which is the same question nobody
has been able to ask yet.
