# P231 — "Bitte versuchen Sie es später erneut" for forty-two things that are gone

The review's **Package C**, first half:

> **The full centralized error layer** — `409` conflict/reload, `422` field
> validation, `429` rate limiting, retry that preserves input.

P225 fixed two instances of one shape and wrote each as the single case in
front of it. This is the class.

---

## P231-01 — the fallback is status-blind

`describeError` answers with the API's `detail` where there is one, and with
the call site's `generic` where there is not. **Every call site in the console
passes a sentence ending "Bitte versuchen Sie es später erneut"** — most of
them the literal `de.error.generic`, which is only that sentence.

So the console's answer to a failure the API chose not to explain is **advice
to retry**, whatever the status was.

For `429`, `500`, `502` and a dropped connection that is right, and it is the
one genuinely useful thing the console can say. For three statuses it is the
same §9.4 defect as the font toast (P225-01) and the 403 (P225-05) — _the
sentence is advice, and the advice is wrong_:

| Status | Retrying the identical request will                            |
| ------ | -------------------------------------------------------------- |
| `404`  | not find it again — the thing is gone                          |
| `409`  | meet the same conflict — somebody else's change is still there |
| `422`  | be rejected identically — the input is what was refused        |

### 404 is not a corner case, and this is the number that says so

`AppError.notFound(reason, clientDetail?)` sends no `detail` unless the second
argument is given — `reason` is internal by design and never serialised. Counted
across `apps/api/src`, excluding tests:

| Constructor       | no client detail | with |
| ----------------- | ---------------- | ---- |
| `notFound`        | **42**           | 3    |
| `unauthenticated` | 21               | 1    |
| `badRequest`      | 8                | 2    |
| `new AppError(…)` | 14               | 117  |

**Forty-two distinct 404s in this API reached an operator as "please try again
later."** One of them is the second click of a GDPR erasure (P230-01), where the
honest reading is "it already worked".

`badRequest` is the reassuring half of the table: it sets `clientDetail` to the
same string as `reason` on purpose, because a bad-request reason is about what
the caller sent rather than about what exists on the server. And the 117 is why
this change is a **fallback** and never a replacement — a 409 explaining that
the Punktemeldung has gone and what to do instead must still win.

### The fix

A three-entry table in `api.ts`, and `fallbackFor(status, generic)` consulted
only when the API wrote no `detail`. Everything not in the table keeps the call
site's own words, so a screen with better sentences than "try again later" for
a timeout still gets to use them.

New copy, in both locales, each saying what happened **and what to do instead**,
and none naming a field's value or an identifier (§9.5):

| Key        | German                                                                                                                       |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `gone`     | Dieser Eintrag existiert nicht mehr. Bitte laden Sie die Seite neu.                                                          |
| `conflict` | Diese Daten wurden zwischenzeitlich von jemand anderem geändert. Bitte laden Sie die Seite neu und prüfen Sie Ihre Eingaben. |
| `rejected` | Die Eingaben wurden nicht akzeptiert. Bitte prüfen Sie die Angaben.                                                          |

Written red first. On the shipped code all three reported the same thing:

```
AssertionError: a 404 answered with retry advice — the thing is gone and
asking again will not bring it back: expected 'Bitte versuchen Sie es später
erneut.' not to contain 'später erneut'
```

Two guarantees are asserted as well as the three cases, because a table like
this is one careless commit from becoming a gag:

- **429, 500, 502, a dropped connection and a timeout keep their retry
  advice.** A rule that suppressed it everywhere would remove the only honest
  advice the console has.
- **A `detail` the API wrote is never replaced**, at any of those statuses.

## P231-02 — and the affordance, because a rule with no caller is not a rule

`isRetryable(error)` is the other half, and it is the piece P230 deferred here:
deciding what an error _is_ belongs with the error layer, not with a form's
state machine.

Shipping it alone would have been §9.3 exactly — `inviteStatus`, `resetStatus`
and `invalidBrandingFields` were each exported, exhaustively unit-tested, and
called from nowhere. A perfect `isRetryable` with eleven screens still drawing
the button, and a green suite.

So `LoadFailure` — the retry affordance, used by **eleven** screens — takes a
**required** `retryable: boolean`.

**Required, with no default.** An optional prop defaulting to `true` would have
left all eleven unchanged and the rule unapplied: the same outcome in a
different shape. A required prop makes the compiler ask every call site, and it
named all eleven:

```
Certificates.tsx(110,8): error TS2741: Property 'retryable' is missing …
CourseStructure.tsx(167,8) … Customers.tsx(128,8) … EivQueue.tsx(139,8) …
EvaluationEditor.tsx(86,8) … ExpertsEditor.tsx(62,8) … Learners.tsx(188,8) …
ParticipantAccounts.tsx(90,8) … PlatformEiv.tsx(93,8) … QuizEditor.tsx(122,8) …
StaffAccounts.tsx(214,8)
```

`useLoaded` now reports it as a fifth element, set **from the same error as the
sentence, in the same place** — §4 invariant 6, and the failure mode here is
specific: a screen deriving the words from the error and the button from
something else would eventually say "this no longer exists" over a control
offering to look for it again.

When it is `false` the button is **absent, not disabled**. A disabled control
still says "this is the thing to do here, but not now", and for a 404 there is
no later when it works. Removing an affordance is only an improvement if
something else says what to do instead, which is why `de.error.gone` ends
"Bitte laden Sie die Seite neu" — and a test asserts that it does (§9.2, §9.4,
§9.10).

### Watched red

| Sabotage                                       | Reported                                                                        |
| ---------------------------------------------- | ------------------------------------------------------------------------------- |
| `LoadFailure` draws the button unconditionally | "a retry control was drawn beside a sentence saying the entry no longer exists" |
| the three status entries removed               | all three sentences back to `Bitte versuchen Sie es später erneut.`             |

## What this ticket does not do

Package C is larger than this, and the rest is **named rather than quietly
counted as done**:

- **Route-level error boundaries.** A thrown render error still takes the
  console down to a blank page.
- **Unsaved-change protection.** Leaving a half-filled form loses it silently.
- **Focus handling after errors and dialogs.** Not addressed; P227 already
  recorded keyboard flow as out of scope and needing its own instrument.
- **Accessible status announcements — and this line was wrong when first
  written here.** It said _"`Notice` is not a live region, so a screen reader
  is not told when an error appears."_ **It is one.** `ui.tsx` spreads
  `role="alert"` onto every tone except `info`, and that exclusion is
  deliberate and documented at the prop: _"info is not a quieter warning … a
  screen reader is not interrupted to be told something that is merely true."_
  So an error, a warning and a success **are** announced.

  Corrected here rather than quietly deleted, because it shipped in this
  ticket and in PR #78's body, and §11.13 applies to a correction as much as
  to the original claim: the command is
  `grep -n "export function Notice" -A 30 apps/admin/src/components/ui.tsx`,
  and the line is `{...(props.tone === "info" ? {} : { role: "alert" })}`.

  What is **not** done, and is the real remainder: an error rendered _inline_
  next to a field — `<p className="text-xs font-medium text-red-700">` — is
  not in any live region, so a validation failure beside an input announces
  nothing. That is a different and smaller gap than the one claimed.

- **Retry that preserves input.** `LoadFailure`'s retry re-runs a _load_; a
  refused _mutation_ has no retry affordance at all, which is honest today —
  the form still holds what was typed — but is not the designed behaviour the
  review asked for.
- **429 specifically.** It keeps the generic retry sentence, which is correct
  but says nothing about waiting. The API sends no `Retry-After` today, so a
  better sentence would be inventing a number (§11.4).
- **`useSaver`'s six states.** `validating` still has nothing that sets it.
  `isRetryable` now exists for the retryable/permanent split, but no form
  offers a retry control yet, so adding the enum members would be §9.3 again.
