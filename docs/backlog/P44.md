# P44 · The deploy that would not start, and the reason nobody could tell why

> `✘ Container ds-education-api-1 Error` … `dependency failed to start:
container ds-education-api-1 is unhealthy` … `xx failed at line 316. The
previous version is still running.`
>
> why is everything so hard with implementation and i have to repeat everything
> multiple times? why are you silently failing and not telling stuff
>
> please prepare everything for local development as well.

`docker ps` carried the answer the deploy did not print:

```
ds-education-admin-1    Restarting (1) 11 seconds ago
ds-education-portal-1   Restarting (1) 11 seconds ago
ds-education-api-1      Restarting (1) 59 seconds ago
```

Two containers in a restart loop with exit code 1, and the deploy naming a
third — because `caddy` `depends_on` all of them and the API is the one with a
healthcheck. The error pointed at the service that was not the cause, and there
was no way from that message to the two that were.

---

## P44-01 · `DS_PROJECT_SLUG`: required by the entrypoint, supplied by nothing, read by nobody — **done**

- **Estimate:** 1 h · **Review gate: none**

`infra/nginx/ds-runtime-config.sh` runs at container start for the console and
the portal and writes `/config.js` from the environment. It required
`DS_PROJECT_SLUG`, and exited 1 when it was empty — correctly, by its own
design: a frontend that loads and then fails every request is worse than a
container that will not start.

**Nothing ever set it.** Not `docker-compose.prod.yml`, which gives those two
services exactly one variable each (`DS_API_BASE`); not `config.env.example`;
not `domains.sh`. And nothing read it either — `readConfig` in both apps returns
`{ apiBase }` and nothing else. The console picks its customer from what the
operator can reach (P22-03) and the portal takes its tenant from the first path
segment (P21-03); `apps/admin/src/config.ts` carries the comment saying so.

So it is a value no deployment supplied and no code consumed, in the one
position where that is fatal: CLAUDE.md §9.3 — a rule written and never
enforced — with the enforcement being a container that would not boot. It is now
`optional`, written when present and absent otherwise.

## P44-02 · `pnpm check:runtime-config` — the class, not the instance — **done**

- **Estimate:** 1.5 h · **Review gate: none**

The two facts live in different languages: a `required` marker in a POSIX shell
script, and an `environment:` block in YAML. Nothing in either could see the
other, which is exactly what CLAUDE.md §9.11 says belongs in `scripts/`.

`scripts/check-runtime-config.mjs` parses the `emit … required` lines out of the
entrypoint — parsed, not listed, because a list is a second place to go stale
the same way — and asserts every service that runs that image provides them. It
refuses to pass when it finds _no_ required lines at all, because a check that
silently stops checking is §9.1's whole subject.

Confirmed by restoring `required` and watching it name both services.

## P44-03 · The deploy prints why, for every container that is not running — **done**

- **Estimate:** 1 h · **Review gate: none**

`deploy.sh` already had `compose logs --tail 50 api` — and it could not run. It
sits after the health-wait loop, and `compose up -d` had already exited
non-zero, so the `ERR` trap fired first and the script died at line 316 with no
diagnosis. **A diagnostic behind a failing command only prints when it is not
needed.**

`ds_dump_broken_services` now runs at the failure itself, for `api`, `admin`,
`portal`, `widget` and `caddy` alike: status, exit code, and the last forty log
lines of anything not `running`. The health-timeout path calls it too, because
the container that explains an API timeout is frequently a different one.

Had this existed, the first failed deploy would have printed
`ds-runtime-config: DS_PROJECT_SLUG is empty and is required.` and P44-01 would
have been a five-minute fix instead of three rounds.

## P44-04 · One command for local development — **done**

- **Estimate:** 2.5 h · **Review gate: none**

`pnpm start` takes a clean checkout to a running, seeded, signable-in stack and
then says what to open. It was five commands and one **undocumented** step: the
README never mentioned `cp .env.example .env`, without which the API reads no
database URL at all.

It checks each tool separately and names the one that is missing — including
`docker info`, because `docker --version` answers from the client alone and
succeeds while the daemon is stopped, which is the state of every laptop that
has just booted. It writes `.env`, generates a local `SECRETS_KMS_KEY` so the
encrypted-at-rest path behaves here as it does in production, brings up the
containers, migrates, seeds all three tenants, creates a console super
administrator, and prints the URL table — including Mailpit on `:8025`, where
every password-reset and certificate email lands.

`scripts/devdb.mjs` no longer needs a `psql` on the host. It did, and
`postgresql-client` is not something Node, pnpm or Docker pull in — so a
developer with a working Postgres container met `cannot reach PostgreSQL`, a
message that diagnoses the server and names the client's absence not at all. It
now falls back to the container's own `psql`, piping SQL over stdin rather than
passing a host path a container cannot see.

## What is still not known, and what will answer it

**Why the API container exits.** `admin` and `portal` are fully explained above.
The API is a third failure and its cause is in its own logs, which no deploy has
yet printed — P44-03 is what makes the next one print them. Everything about it
here would be a guess, and CLAUDE.md §7 says not to guess.

**Whether P43-02's diagnosis was right.** That ticket read the
`projects_identity_provider_check` failure as a schema behind the code. The
deploy log since shows `Already up to date`, so if migrations were current at
the time then the cause is something else and has not been found. The guard
added there is still correct and still worth having — it just may not have been
this. `SELECT pg_get_constraintdef(oid) FROM pg_constraint WHERE conname =
'projects_identity_provider_check';` settles it in one line.
