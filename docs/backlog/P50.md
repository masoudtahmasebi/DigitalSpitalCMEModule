## The journey, run against a real database

No Docker in the sandbox, but Postgres 16 and Redis are installed natively, so
the whole stack ran from source and every step below is an actual HTTP response,
not a reading of the code.

| Step                 | Result                                                                     |
| -------------------- | -------------------------------------------------------------------------- |
| Sign in at `/medice` | 200, session cookie                                                        |
| Catalogue            | the ADHS course, with facets                                               |
| Enrol (`PUT`)        | settings snapshotted onto the enrolment                                    |
| Watch all videos     | 100 %, 0 segments rejected                                                 |
| Lernerfolgskontrolle | 100 %, passed, threshold 70                                                |
| Evaluation           | accepted                                                                   |
| Before EFN           | `outstanding: ["efn"]` — because the course awards 4 points                |
| EFN                  | 204                                                                        |
| `POST /completion`   | `completedAt` stamped                                                      |
| Certificate PDF      | **200, 5 405 bytes, real PDF 1.7**                                         |
| EIV submission       | queued, `event_end_at` = the completion instant, `report_due_at` = +8 days |

The EIV row is worth naming: `event_end_at` is **the learner's own completion**,
and the deadline is eight days from it. That is exactly the reading of
`Veranstaltungsende` that Q1 asks the ÄKWL to confirm — the code already
behaves as if the answer is yes.

The same journey on `DSCourse` (no VNR, no points) ends at a **409 on the
certificate**, correctly: `missingCertificateFields` refuses to issue one whose
required fields are absent. Worth knowing, because that seed's own header says
"the certificate simply carries no points", which reads as though a certificate
would still be issued. It is not, and that is the safer behaviour.

## P50-01 · The validity window, enforced — **done**

- **Estimate:** 3 h · **Review gate: none**

`valid_from` and `valid_to` were **stored, editable in the console and returned
by the catalogue DTO — and enforced nowhere.** An expired course was listed,
openable and enrollable. CLAUDE.md §9.3 exactly: a rule written is not a rule
enforced, and this one had a column, a form field and an API field to make it
look done.

`courseAvailability` in `@ds/domain` is the rule — pure, time as an argument,
and returning a _state_ rather than a boolean because "not yet" and "no longer"
need different words on screen (§9.10). It is called in three places, because
three different doors reach a course:

| Door                  | Behaviour outside the window                           |
| --------------------- | ------------------------------------------------------ |
| `GET /courses`        | not listed, and the total agrees with the page         |
| `GET /courses/{slug}` | 404 — a bookmark or an old email reaches this directly |
| `PUT /…/enrolment`    | 404 for a **new** learner                              |

404 and not 403 throughout: a retired course must not be distinguishable from
one that never existed, or the status code enumerates which VNRs an
installation has retired (§9.5).

**Optional, as asked.** Both ends independently nullable; a course with neither
is offered indefinitely, which is what almost every course will be. The
`IS NULL OR …` in the SQL is the part that would have emptied the catalogue if
it were wrong.

`invalidAvailabilityWindow` refuses a backwards window at the one place a
window can be written, validating the **merged** result — a request that moves
only `validTo` can invert a window whose `validFrom` it never mentions.

### The deliberate half, which needs your decision

**A physician who started while the course was open keeps their access.** Their
compliance settings are already snapshotted onto the enrolment (P3-01), and
revoking a half-finished course seemed the worse outcome — a late completion is
refused by EIV's own `beginn`/`ende` check at submission time, loudly, inside
the correction window.

If the accreditation rule requires a hard cut-off, it is one condition in
`enrol` and the test that pins the current behaviour is named for it.

### Tested twice, deliberately

`availability.test.ts` covers the rule at every boundary — including that
`12.10.2026` means the whole of that day — and **every one of those tests would
stay green on a platform that never called it** (§9.7). So the wiring has six
tests of its own in `learning-flow.integration.test.ts`, driving real HTTP.
Confirmed by disabling the detail check and watching one go red.

## What the journey found that is still open

**The completion rule does not match your sentence.** You wrote that a course is
complete when the physician finishes the videos and the quiz. The platform also
requires the **Evaluationsbogen** — `outstanding: ["evaluation"]` after a
perfect quiz — and requires an **EFN** when the course awards points.

That is not a defect: the evaluation is in `docs/roadmap.md`, in the README's
first paragraph, and is a normal condition of German CME accreditation.
Removing it is a compliance change, and CLAUDE.md §7 says not to guess at
those. **Unchanged, pending your answer** — see the question in the reply.

**No wall-clock check on watch reporting.** A single POST claiming 900 seconds
of playback the instant after enrolling is accepted. `validateSegments` rejects
segments claiming more playback than elapsed _between reports_, so a client
that reports once is not caught by it. Whether that matters is a policy
question about how hard the watch gate is meant to be; it is not something to
tighten without saying so, because it would reject a legitimate client that
buffers a whole chapter before reporting.
