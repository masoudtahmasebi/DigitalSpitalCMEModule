# P68 — A test that fails when the product does

Raised 12.08 by the client, after five defects in one day that every gate was
green for:

> _"why do i have to find all of these issues myself? why aren't you testing
> these basic functionalities?"_

The answer is structural and is worth stating before the plan, because the plan
follows from it.

---

## What actually went wrong, as a class

**The tests call the API. The client uses the product.**

512 integration tests drive HTTP against the API with a real Postgres and real
RLS. They are good tests. They cannot see four things, and every defect on 12.08
lived in one of them:

| Defect                    | Lived in                                                       |
| ------------------------- | -------------------------------------------------------------- |
| Enrolment answered 403    | Two cookies on one request. Every suite sends exactly one.     |
| Video upload blocked      | A CSP header set by Caddy. No suite reads a header from Caddy. |
| `/medice` empty           | The deploy's seed step. No suite runs a deploy.                |
| Seeds could not run       | Nothing ran the seeds — until P63-03.                          |
| Second factor unremovable | A screen offering a control the API refuses.                   |

A Playwright suite existed (`apps/e2e`, five specs) and stopped at course
creation. It ran against a local rig with **no Caddy** and **no bucket**, so it
had no CSP and no upload — which is exactly why it was green while every upload
was blocked.

So there were two gaps, not one:

1. **Coverage** — the journey stopped less than half way. No upload, no
   watching, no quiz, no completion, no certificate.
2. **Fidelity** — it ran against a rig that is not shaped like the deployment.
   A test that cannot see a CSP cannot catch a CSP bug.

Both are closed.

## P68-01 · The DS Test tenant · 1 h

**Status: done.**

A tenant that exists to be **written to**, which `ds` does not: `ds` is the demo,
and a suite that authors inside it means the demo is whatever the last run left.

`packages/seed/src/ds-test.ts` seeds a customer `dstest`, a department, a portal
project at `/dstest` with a privacy notice, and one `customer_admin` with a
predictable password.

**No course.** That is the point — building one is what the suite is for, and a
seeded course would mean asserting against a fixture rather than against what an
operator actually produces. Every defect this suite exists to catch lives in the
authoring path.

`customer_admin` rather than `super_admin` deliberately: it is the role a real
customer's administrator holds, and the role whose refusals are easiest to get
wrong. Anything the suite cannot do as one is a finding, not a reason to widen
the account.

The privacy notice is on the project because `CompletionScreen` draws the
Einwilligung only when the project has one — and the Punktemeldung is an
Art. 6(1)(a) transmission of a named physician's data whose proof is on us. A
tenant without a notice would never exercise the consent path at all.

The tenant's data is expected to accumulate — the client asked for that — and
each run names its objects with a fresh suffix, so runs never collide and an old
run's course is still there to look at when something goes wrong.

Wired into `deploy.sh` (with the other two, under `--if-missing`), `./dsc seed
ds-test`, `pnpm db:seed:ds-test`, and `seeds.integration.test.ts`, which runs
every shipped seed twice against a real migrated database.

### Acceptance criteria

- [x] `dstest` customer, department and a **local** portal project at `/dstest`
- [x] One `customer_admin` whose password the suite can predict
- [x] A privacy notice, so the consent the Punktemeldung needs is reachable
- [x] No course, no accreditation, no CME points on anything **seeded**
- [x] Runs twice without error, and is covered by the seeds suite
- [x] Reachable as `./dsc seed ds-test` and run by the deploy

## P68-02 · The full journey, in a browser · 6 h

**Status: done.** `apps/e2e/tests/journey.spec.ts`, one test, fifteen acts, about
twenty seconds.

1. the operator signs in to Verwaltung as a `customer_admin`
2. creates a participant and **reads back the password the console issues once**
3. creates a course, a module, a chapter
4. **uploads the video** — the presigned PUT, straight to object storage
5. writes a Lernerfolgskontrolle with a question and two options
6. writes an Evaluationsbogen
7. sets CME points and Kategorie
8. fills in Veranstalter, Ort, Ärztekammer, wissenschaftliche Leitung, VNR and
   VNR-Passwort, **uploads the Stempel and the Unterschrift**, and publishes
9. the participant signs in at `/dstest` and is made to choose her own password
10. the course is in her catalogue; she opens it and **enrols**
11. **plays the video, pauses**, and the watched seconds reach the API
12. **reloads** — the progress is still there — then plays to the end and the
    watch gate opens
13. passes the Abschlussprüfung
14. submits the Evaluation, consents, supplies an EFN, submits the Punktemeldung
15. **downloads the Teilnahmebescheinigung, and it is a real PDF**

### The three things that had to exist first

**An object store in the harness** (`support/object-store.ts`). Not a stub: it
verifies the SigV4 query signature, enforces the signed content type and length,
enforces the expiry, answers CORS preflight and serves `Range` with 206. An
upload that would 403 against Hetzner 403s here. The verifier is written out
rather than imported from `S3Presigner`, on the same reasoning `support/staff.ts`
gives about RFC 6238: a bug present on both sides would cancel out.

It is served over **TLS**, on a certificate generated per run, because the
portal's deployed policy is `media-src 'self' https:` — the honest way to run
under a policy is to satisfy it rather than to edit it for the test.

**The deployed CSP** (`support/csp.ts`), parsed out of `infra/deploy/Caddyfile`
and served by the harness with the rig's own addresses substituted. Sixteen
browser tests were green while every upload in production was CSP-blocked,
because this rig sent no policy at all. Deleting `{$S3_ORIGIN}` from the
Caddyfile now turns this suite red.

**An eight-second WebM** (`fixtures/kurzvideo.webm`). The anti-skip rule measures
watched time against elapsed real time, which is what makes a real-time run of a
real course impossible. The fixture is the answer, **not a weakened rule**:
`requiredWatchPercent` keeps its real value of 100, and watching the whole thing
costs eight seconds of wall clock.

### Reaching inside the widget

`<ds-lms>` attaches its shadow root with `mode: "closed"`, so Playwright cannot
see the player, the quiz or the certificate button. `support/shadow.ts` installs
a page init script that opens it **for this browser only**. The product is
unchanged — `element.ts` still says `closed`, and the shipped bundle is
identical — and `learner.spec.ts` now has a test that loads the portal **without**
the script and requires `shadowRoot === null`. Without that assertion this would
have been the §9.1 failure it exists to fix.

### Acceptance criteria

- [x] One spec walks operator and physician from an empty tenant to a PDF
- [x] The video is uploaded through the console, over a verified signature
- [x] The player plays in real time; no `timeupdate` or segment is fabricated
- [x] Progress is asserted after a reload, from the server's own figure
- [x] The watch gate opens at its real threshold
- [x] The certificate is asserted as bytes (`%PDF-`), not as a click
- [x] The suite runs on `pnpm test:e2e`, where the work happens

## P68-03 · Post-deploy smoke, against the deployed installation · 2 h

**Status: done.**

`playwright.smoke.config.ts` runs the same spec with nothing started;
`support/target.ts` chooses between the local rig and a deployment from
`E2E_PORTAL_URL` / `E2E_ADMIN_URL` / `E2E_API_URL`. `pnpm test:smoke` refuses to
run unless all three and `SEED_TEST_STAFF_PASSWORD` are set — a smoke test that
fell back to `localhost` would report a healthy deployment while looking at
nothing.

The deploy workflow gained a `journey` job that runs after `deploy`, from a
GitHub runner rather than on the host — the point is to see the deployment the
way the internet sees it. The hostnames come from the host's own
`ds_derive_domains`, so the test cannot disagree with the server about where the
server is. Before asserting anything it records the commit behind `/metrics`
(§9.9), so a failure names the build.

A failure fails the workflow run. A green deploy that cannot enrol a learner is
not a green deploy; the previous images are still on disk and
`deploy.sh --rollback <tag>` is the way back.

### The one refusal

The journey publishes an **accredited** course, because a Teilnahmebescheinigung
requires CME points and a VNR (`courses_published_cme_is_complete`) and
generating one is half of what this proves. Completing it queues a Punktemeldung.
The VNR is a reserved number the Ärztekammer has issued to nobody.

`run-smoke.mjs` therefore **refuses to run when `EIV_ALLOW_LIVE` is set**, and
says why rather than skipping quietly. If the smoke ever has to run on a
live-reporting installation, the thing to build is a per-course "meldet nicht"
switch — which is also the honest home for the Bescheid's own paper fallback,
where a Veranstalter reports by hand. It is not in this budget and is recorded
here rather than assumed.

## What the journey found on its way through

Nine defects, all fixed in this phase, none of which any existing gate could see.
Each one is the product being wrong on a screen, in an order a person uses it.

| #   | Defect                                                                                                                                                                                                                                                                                                                                                  | Why nothing caught it                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `TextInput`, `Select` and `TextArea` **silently dropped `aria-label`**. The video sources row passes one to each of its three controls, so a screen reader announced three unnamed fields per rendition.                                                                                                                                                | TypeScript cannot object: a **hyphenated** JSX attribute is never checked against a component's props. No test had ever asked for a control by its accessible name. |
| 2   | **"Inhalte & Darstellung" never confirmed a save.** It set the flag, handed the updated course up, and the reset effect — keyed on the object — cleared the confirmation in the same commit.                                                                                                                                                            | Nothing rendered the screen and pressed the button.                                                                                                                 |
| 3   | **"Einstellungen" discarded the whole form when the Stempel was uploaded.** Fill in VNR, Veranstalter, Ort and Leitung, attach the stamp, press Speichern — and a blank form was saved over the work, reporting success.                                                                                                                                | Each piece works. It is the _order a person uses them in_ that breaks, and only a journey does them in that order.                                                  |
| 4   | **A staff session authenticated the learner portal.** `GET /auth/participant/me` succeeded on a staff cookie, so the portal drew a signed-in catalogue for an operator who could not enrol in anything on it.                                                                                                                                           | API suites send one credential per request. P66-01 fixed the unsafe half of this collision; this was the safe half, and it fails more misleadingly.                 |
| 5   | **A staff cookie riding along displaced the learner** on every non-`/admin` read. A physician using the portal with a console open in another tab got "Diese Fortbildung wurde nicht gefunden" mid-Fortbildung.                                                                                                                                         | Same reason. Found by running both people in one browser context, which is what the client's browser actually is.                                                   |
| 6   | **The course rollup disagreed with itself about "started."** Modules and chapters asked whether any content had left `not_started`; the course asked whether any had been _completed_. One response carried `course: not_started` above `module: in_progress`.                                                                                          | CLAUDE.md §4 invariant 6 being false _inside a single function_. Visible only as a button reading "Fortbildung starten" beside "50 % angesehen".                    |
| 7   | **A finished video was 100 % on the player and 99 % at the gate.** `watchedPercent` applied the endpoint tolerance; `courseWatchCoverage` did not. `requiredWatchPercent` defaults to 100, so a physician who watched every frame was told "Es fehlt noch: die vollständige Videowiedergabe" with nothing left to watch — and no way out of that state. | Two implementations of one number. Both had tests; neither had a test that they agree.                                                                              |
| 8   | **The length probe is absent for an uploaded video**, because an `s3://` reference is not an address a browser can fetch — and it disappears exactly when the author used the console's own uploader.                                                                                                                                                   | An absent control reads as an unfinished feature (§9.4).                                                                                                            |
| 9   | `prepareDatabase` refused any Postgres not on **port 5432**, with a message about "local clusters" while looking at a loopback cluster.                                                                                                                                                                                                                 | A guard narrower than the thing it guards gets deleted by whoever hits it.                                                                                          |

Fixed as follows. 1 → the three components declare and forward `aria-label`, with
`ui.test.tsx` asserting the accessible **name** (not the attribute). 2 and 3 →
both effects key on `course.slug` rather than on the object. 4 → the guard never
serves `/auth/participant/**` from the staff plane, and
`ParticipantAuthController` checks `principal.identity` as a second layer. 5 →
outside `/admin/**`, a request carrying a learner credential is a learner's; the
route namespace is the discriminator, because **both planes legitimately use
`X-DS-Project`** and keying on the header would have signed every department
administrator out. 6 → one `anyStartedIn` predicate for all three levels. 7 → one
`watchedSecondsWithin`, which both the per-content percentage and the course
coverage are built on. 8 → the screen now says why, and the real fix (the API
handing back a readable URL for an object it has just accepted) is below. 9 →
the guard checks the hostname is loopback, which is what it is actually about.

Every one of them was red-checked: broken deliberately, watched to fail, restored.

## Still open, deliberately

- **The length probe for an uploaded video.** The fix is for
  `adminCompleteUpload` to return a short-lived readable URL alongside the
  reference, so `DurationProbe` can read the header of the file the author has
  just uploaded. It is an additive field on an existing response plus an SDK
  regeneration — small, but it is contract surface and it is not what this phase
  was asked for. The screen says why in the meantime.
- **A per-course "meldet nicht" switch**, described under P68-03.
- **The upload's English failure message.** `uploadToTicket` throws
  `new Error("the connection to object storage failed")` and the console renders
  `error.message`, so an English sentence appears on a German screen — which is
  what the client saw on 12.08. The fix is a typed error in the SDK and a German
  mapping in the console; it is cosmetic next to the nine above and is the next
  thing to pick up.

## The refactor the client also asked for

Three times, in the same message: _"refactor the whole project"_ for best
practices, for security, and for scalability.

This phase is the prerequisite rather than a substitute, and the reason is the
nine defects above: **a refactor of a system whose end-to-end behaviour is
untested is how 12.08 happened.** Until this week, "the platform still works"
could only be established by a person clicking, and no reviewer of a large diff
could have said whether it still did.

Now one command can. `pnpm test:e2e` walks the entire product in twenty seconds
and `pnpm test:smoke` walks the deployed one — so a security or scalability pass
finally has something to fail against, and every change in it can be shown not to
have broken the physician's journey.

That pass is the next phase, and it starts from the instrument this one built.
