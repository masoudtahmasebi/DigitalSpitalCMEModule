# P68 — A test that fails when the product does

Raised 12.08 by the client, after five defects in one day that every gate was
green for:

> _"why do i have to find all of these issues myself? why aren't you testing
> these basic functionalities?"_

The answer is structural and is worth stating before the plan, because the plan
follows from it.

---

## What actually went wrong, as a class

**The tests call the API. The client uses the product.**

512 integration tests drive HTTP against the API with a real Postgres and real
RLS. They are good tests. They cannot see four things, and every defect on 12.08
lived in one of them:

| Defect                    | Lived in                                                       |
| ------------------------- | -------------------------------------------------------------- |
| Enrolment answered 403    | Two cookies on one request. Every suite sends exactly one.     |
| Video upload blocked      | A CSP header set by Caddy. No suite reads a header from Caddy. |
| `/medice` empty           | The deploy's seed step. No suite runs a deploy.                |
| Seeds could not run       | Nothing ran the seeds — until P63-03.                          |
| Second factor unremovable | A screen offering a control the API refuses.                   |

A Playwright suite exists (`apps/e2e`, five specs) and stops at course
creation. It runs against a local rig with **no Caddy**, so it has no CSP — which
is exactly why it was green while every upload was blocked.

So there are two gaps, not one:

1. **Coverage** — the journey stops less than half way. No upload, no watching,
   no quiz, no completion, no certificate.
2. **Fidelity** — it runs against a rig that is not shaped like the deployment.
   A test that cannot see a CSP cannot catch a CSP bug.

## P68-01 · The DS Test tenant · 1 h

**Status: done.**

A tenant that exists to be **written to**, which `ds` does not: `ds` is the demo,
and a suite that authors inside it means the demo is whatever the last run left.

`packages/seed/src/ds-test.ts` seeds a customer `dstest`, a department, a portal
project at `/dstest`, and one `customer_admin` with a predictable password.

**No course.** That is the point — building one is what the suite is for, and a
seeded course would mean asserting against a fixture rather than against what an
operator actually produces. Every defect this suite exists to catch lives in the
authoring path.

`customer_admin` rather than `super_admin` deliberately: it is the role a real
customer's administrator holds, and the role whose refusals are easiest to get
wrong. Anything the suite cannot do as one is a finding, not a reason to widen
the account.

The tenant's data is expected to accumulate — the client asked for that — and
each run names its objects with a fresh suffix, so runs never collide and an old
run's course is still there to look at when something goes wrong.

Wired into `deploy.sh` (with the other two, under `--if-missing`), `./dsc seed
ds-test`, and `seeds.integration.test.ts`, which runs every shipped seed twice
against a real migrated database.

### Acceptance criteria

- [x] `dstest` customer, department and a **local** portal project at `/dstest`
- [x] One `customer_admin` whose password the suite can predict
- [x] No course, no accreditation, no CME points — nothing that can reach EIV
- [x] Runs twice without error, and is covered by the seeds suite
- [x] Reachable as `./dsc seed ds-test` and run by the deploy

## P68-02 · The full journey, in a browser · 6 h

**Status: not started. This is the substance of the request and it is not done.**

One spec, one run, in order, each step failing loudly where it breaks:

1. operator signs in to the console
2. creates a participant account **with a password**
3. creates a course, a module, a chapter
4. **uploads a video** — the presigned PUT, straight to object storage
5. adds a quiz with questions
6. sets the accreditation fields and **publishes**
7. participant signs in at `/dstest`
8. sees the course, opens it, **enrols**
9. **starts the video, watches, pauses**
10. progress is saved — assert it survives a reload
11. finishes the module, the gate opens on the next one
12. passes the quiz, submits the evaluation, supplies an EFN
13. **certificate is issued and downloads as a real PDF**

### The one design problem, and how it is solved

The anti-skip rule measures watched time against elapsed real time since the
learner's last activity — a physician cannot watch ten minutes in one second, and
the API refuses a report that claims they did. **That makes a real-time E2E of a
real course impossible**, which is presumably why the existing suite stops before
it.

The fixture is the answer, not a weakened rule: the course the suite builds uses
an **8-second video** with `requiredWatchPercent` at its real value. Watching 80%
of 8 seconds takes 7 seconds of wall clock, and every rule stays exactly as it is
in production.

### What is needed and does not exist yet

- A short WebM the browser can actually play. Playwright's bundled Chromium has
  no H.264, so an MP4 fixture would silently never load — learned in QA §9.
- The upload step needs object storage. Locally there is none, so that step
  must **skip with a stated reason** rather than pass quietly, and run for real
  against the deployed installation.

## P68-03 · Post-deploy smoke, against the deployed installation · 2 h

**Status: not started.**

The suite takes a base URL. After `deploy.sh` succeeds, the workflow runs it
against the real hostnames — real Caddy, real CSP, real cookies, real object
storage. That is the run that would have caught the upload and the enrolment
403, on the machine the client actually looks at, before they did.

Failure fails the deploy job. A green deploy that cannot enrol a learner is not a
green deploy.

---

## Deliberately not attempted

The client also asked, three times, to _"refactor the whole project"_ for best
practices, security and scalability.

I am not doing that in the same pass, and the reason is the finding above rather
than reluctance: **a refactor of a system whose end-to-end behaviour is untested
is how today happened.** P68-02 and P68-03 are the instrument that makes a
refactor safe to attempt, and they come first. Once a single command can prove
the whole journey works, a security and scalability pass has something to fail
against — and each change can be shown not to have broken the product.

Recorded here so it is a sequence and not a silence.
