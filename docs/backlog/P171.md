# P171 — The course's values are the course's, everywhere

**Raised by:** the client, 03.09.2026, with a screenshot of one Zertifizierung
tab contradicting itself:

> _"For test course I have set the number of points to 10, but in this
> certificate document and certificate tab, I am seeing only 4 punkt and I see
> the same number in the pdf as well. […] why have you coupled things from the
> course to the seeder, this is unacceptable. you must, must, must check if
> there are any other cases like the vnr and points and maybe category that you
> have done wrong. […] how can you set these hard coded when there are values in
> course! […] why would I have a form and have a course custom, and then load
> the defaults inside it?"_

**Branch** `claude/education-platform-roadmap-3vgrqh`, from `3029381`.

---

## What the screenshot proves

Three lines apart, on one tab, about one course:

> Diese Fortbildung ist von der Ärztekammer Westfalen-Lippe zertifiziert und
> wurde mit **10** CME-Punkten akkreditiert.

> Die Veranstaltung ist … mit **4** Punkten (Kategorie D) anrechenbar.

The accreditation paragraph renders `courses.cme_points`. The
Teilnahmebescheinigung rendered `enrolments.cme_points`. §4 invariant 6 on a
legal document, and the identical shape the VNR had in P164-01.

## The diagnosis, which is not the one in the report

**It is not the seeder** — not for this course. `Verified:`
`learning.repository.ts` `createEnrolment` writes
`cmePoints: input.course.cmePoints`, so the enrolment holds whatever the course
was worth **at the moment that physician enrolled**. Test Course was worth 4
then; it is worth 10 now; the certificate read the copy. Nothing was hard-coded
and no seed touches a course whose slug it does not own.

**And there is a seeder defect, in the same family, which the report did not
name.** `medice-adhs.ts` assigned `title`, `cme_points` and `cme_category`
unconditionally in its `ON CONFLICT DO UPDATE` clause, so every deploy wrote the
MEDICE course's points back to the seed's 4 — silently, because an UPDATE
writing a different valid value is not an error anywhere. That one **is** the
coupling the client described, on a different course.

Both are the same class, and the class is the point.

---

## P171-01 — Points and category follow the course, like the VNR

`certificate.repository.ts` reads `courses.cme_points` and
`courses.cme_category`. The comment that used to defend the snapshot said:

> `cmePoints`, `cmeCategory` and the attested identity are things the learner
> earned or stated.

Two thirds of that is wrong, and it is wrong in a way worth writing down: **a
physician does not earn a number of points.** The _event_ is worth a number of
points, the Ärztekammer decided it, the VNR identifies it and the Bescheid
states it. Points and category are attributes of the event in exactly the way
the VNR is — so correcting what a course is worth must correct every
certificate for it, or the platform issues documents that disagree with the
register they name.

What stays snapshotted is what the **learner** did or stated: `attestedName`,
`attestedAddress`, the completion date. Those are theirs.

The same reasoning applied to every other reader of that column:

| Reader                                           | Was              | Is now     | Why it mattered                                                                     |
| ------------------------------------------------ | ---------------- | ---------- | ----------------------------------------------------------------------------------- |
| `certificate.repository` (PDF + preview)         | enrolment        | **course** | the document contradicted the tab above it                                          |
| `learning.repository.findEnrolment`              | enrolment        | **course** | drives `awardsCmePoints` — whether an EFN is asked for at all                       |
| `completion.repository.hasPointBearingEnrolment` | enrolment        | **course** | same question, asked across a learner's courses                                     |
| `admin.repository.listEnrolments`                | enrolment        | **course** | the console showed an operator a different number from the course they were editing |
| EIV (`eiv.repository`, `eiv-admin.repository`)   | course (already) | course     | correct before this ticket — which is _why_ the two disagreed                       |

The direction that matters most is the quiet one: a course accredited **after**
somebody enrolled would never have asked them for an EFN, so no Punktemeldung
would ever be filed for a physician who finished an accredited Fortbildung —
and nothing on any screen would have said a question had been skipped.

The snapshot columns are still written and are untouched by this. They remain
the record of what was in force at enrolment; they are simply no longer what any
decision is made on.

## P171-02 — A seed may not overwrite what an operator typed

Two seeds did:

- `medice-adhs.ts` — `title`, `cme_points`, `cme_category`, on a **real
  customer's** course, on every deploy.
- `ds-default.ts` — `title`, `description`, `learning_objectives`,
  `target_audience`, on the starter course an operator is _meant_ to find and
  edit. Its own header says it is "idempotent on its slugs … so the first deploy
  and the fiftieth produce the same rows", which is true and is the defect:
  identical rows are what a fixture wants and the opposite of what a starting
  point wants.

Both now follow the rule the file already claimed: **a starting value where
there is nothing, never a replacement.** `ds-demo.ts` is left alone — that
tenant is a fixture whose purpose is to be restored, which is the client's own
rule from P165-01 (_"seed should be only on ds tenant, not medice"_).

### The check, because a list maintained by hand cannot guard a list

There **was** an assertion covering this, since P108-01, under a comment
claiming _"every field an operator can edit in Verwaltung is asserted here
together, so a field added to the DO UPDATE later has to delete a named case to
pass"_. That claim was false for three fields for four months, and the claim is
exactly what stopped anybody looking — §9.1's second form.

`scripts/check-seed-overwrites.mjs` derives both sides instead:

- what an operator can edit — the keys of `adminCourseUpdateSchema`;
- what the seeds assign unconditionally — every `column = EXCLUDED.…` in an
  `ON CONFLICT … DO UPDATE SET` with no reference to the existing row.

An overlap is the defect. It is in `pnpm verify` and in CI, and it found the
`ds-default.ts` instance on its first run — which is the argument for writing
the check rather than another list.

**It did not go red the first two times it was sabotaged.** The parser matched
up to the next backtick, and every clause in these files sits under a long
comment that quotes identifiers `like this`, so the capture ended inside the
comment and the check reported "0 unconditional assignments" on a seed that had
three. That is the thing this file exists to prevent, inside the file itself. It
now strips comments first, splits assignments on depth-zero commas, and
**throws** on a clause whose assignments it cannot parse — a check that cannot
read its input must not print a reassuring number.

Watched red afterwards on three separate sabotages: the points assignment
restored, a new editable field (`organizer`) added unguarded, and the
`ds-default` description reverted.

## What I did not change, and the one question it leaves

Three columns are still read from the enrolment's snapshot:
`required_watch_percent`, `pass_threshold_percent`, `max_quiz_attempts`.

They are a different class from points and category: they are not _what the
event is_, they are **the rules a physician studied under**, and changing them
live is retroactive in a way that can take something away.

- Raising `pass_threshold_percent` from 70 to 90 would reopen an exam somebody
  passed at 80 and un-finish their course.
- Raising `required_watch_percent` would put an in-progress learner back below
  the line on videos they have already watched.

There is a real inconsistency today, and it is the same shape as this ticket:
the Zertifizierung tab renders the **course's** thresholds while the progress
card renders the **enrolment's**, so the two disagree the moment an operator
edits a published course.

**This needs a decision rather than a commit (§7).** My recommendation: read
them live like everything else, keeping the two protections that already exist —
`alreadyCompleted` never un-finishes a completed enrolment (P167-01), and a
passed exam stays passed. It is the client's call because the alternative
reading — an enrolment is a contract at the moment it is taken — is also
defensible and is what the schema was built for.
