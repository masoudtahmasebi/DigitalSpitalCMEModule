# P202 — A refused action was written into the channel that clears it

**Raised by:** the client, 07.09.2026 — _"deleting a course causes [a 409] error
and a detailed error in the network page, but nothing was reported to the user
… why isn't the error communicated? is that the same case for other entities?"_

```json
{
  "status": 409,
  "detail": "Dieses Kurs enthält noch 1 Module. Diese müssen zuerst gelöscht werden.",
  "correlationId": "d61f7fc2-8332-4d84-b063-7fe360279a14"
}
```

---

## Two defects, and the client saw their sum

```ts
setProblem(undefined);
try {
  await client.adminDeleteCourse(slug);
} catch (error) {
  setProblem(describeError(error, de.error.generic));
}
await loadCourses(); // <- and this is `setProblem(undefined)` on success
```

1. **The message was erased before it could render.** `loadCourses()` clears
   `problem` as its first act on success, and it runs immediately after the
   catch. Every refusal, every time.
2. **`problem` is the screen's _load_ channel.** Rendering it returns early and
   replaces the whole table with an error and a retry button. Right when the
   list could not be fetched; wrong when the list is fine and one action was
   refused — it would have hidden the very rows the message is about.

Neither is a missing message: `describeError` already reads the API's own
`detail` and appends the correlation id, so the sentence the client wanted was
built and thrown away.

## The answer to "is that the same case for other entities?"

Audited across 39 catch blocks in 53 files of `apps/admin/src`: **this is the
only set-then-reload**, and there are no empty catches. So the _erasure_ is
unique to course deletion.

What is **not** unique is the shape behind it: the console has one error channel
per screen, and it is a full-screen replacement. That is correct for a load and
wrong for an action, and course deletion is where the two first collided
because it is the screen with a destructive action on a list.

## The change

A second channel — `actionProblem` — which the reload does not touch, rendered
above the table with the rows still on screen, dismissible, and `role="alert"`
so it is announced to somebody whose focus is on the button that produced it.

Cleared by the next attempt rather than left standing: it describes one act, and
an error that outlives what caused it is an error people learn to ignore.

## Not done, and named rather than skipped

The client asked for **a toast, and the same treatment everywhere**. This gives
the correct behaviour on the screen that reported it, and does not yet give a
shared notification host for the whole console. That is a bigger change — every
screen's failure paths rerouted through one component — and it should not ride
along unreviewed at the end of a batch. It is the next ticket.

## Watched red

Restoring the original `setProblem` write fails
`keeps the API's own sentence on screen after the list reloads` — which is the
defect exactly, including the reload that erases it.

The test uses a real `ApiError`, not a look-alike: `problemDetail` narrows with
`instanceof`, so an object carrying the same fields falls through to the generic
sentence and the case would pass while proving the opposite.
