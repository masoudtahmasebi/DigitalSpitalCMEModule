## First, two corrections to the audit's own premises

Both matter, because a check written against the wrong name tests nothing.

- **The tenant header is `X-DS-Project`, not `X-DS-Customer`** on the learner
  plane. `X-DS-Customer` does exist, on the **staff** plane only, and both land
  at `resolveStaffTenant` — so they cannot drift apart on authorization, only on
  how the customer id was arrived at.
- **The roles are `super_admin`, `customer_admin`, `department_admin`,
  `course_editor`** — not the `tenant_admin` / `operator` / `viewer` the audit
  lists. There is no viewer role.

## 1.1 — Tenant guard: the one real gap, now a sweep

The invariant was proven at the database and not at the door.
`tenant-isolation.integration.test.ts` shows RLS matching nothing without
`app.customer_id` and refusing a cross-tenant insert by policy rather than by
application code. That holds. It is a different question from _"does every route
reach that invariant"_, and §9.2's whole shape is a guard that covers a subset —
made worse here by §9.6, because a missing tenant context returns **zero rows**,
which a repository can render as "nothing configured" with a 200.

`tenant-header.integration.test.ts` sweeps the contract instead: every operation
the contract marks tenant-scoped, called with a **real signed-in staff session**
and a wrong tenant claim, twice —

- **naming no tenant at all**, and
- **naming a customer the operator holds no grant for**, well-formed and really
  existing, so nothing is a validation failure and only the grant check stands
  between this operator and another company's data.

Each must answer `4xx`, never `2xx`, never `5xx`, and in problem-details with a
`detail` or `title` a person could read — because the failure the client reported
this year was _"this route is tenant-scoped and no X-DS-Project header was sent
(Referenz: e06b7eb6-…)"_ on an operator's screen (§9.4).

All pass today. Two things keep that meaningful:

- **A control**: the same session naming its **own** customer must still get a 200. Without it every route could be refusing for the wrong reason and the
  sweep would be green (§9.1).
- **A floor**: the sweep asserts it found more than fifteen operations, so a
  reformat that broke the contract parser turns the file red rather than
  vacuously green — the P41-02 failure exactly.

**Watched to go red.** With `staffTenantContext` neutered to accept any customer
the caller names, the sweep failed and listed them:
`GET /admin/courses → 200`, `GET /admin/learners → 200`,
`GET /admin/participants → 200`, and six more.

## 1.2 — Every gate in the domain has an API caller

`contentGates`, `evaluateSequence`, `hasPassedQuiz` and `assertReachable` are all
called from `learning.service.ts`. `assertReachable` is the one worth naming: it
enforces the same rule the screen renders, so a direct POST to a locked quiz gets

## 1.3–1.6 — The bypasses are refused, and were already tested

The audit's request shape (`POST /api/progress { status: "completed" }`) does not
exist, and that is the strongest answer available: **there is no endpoint that
marks anything complete.** Progress is submitted as watched _intervals_ and the
server derives everything from them; completion is `POST /courses/{slug}/completion`
and it re-derives every gate rather than trusting a claim.

Covered in `completion-flow.integration.test.ts`:

| Audit case               | Test                                                                      |
| ------------------------ | ------------------------------------------------------------------------- |
| 1.3 quiz bypass          | `cannot be passed by asserting a score in the request`                    |
| 1.3 gate before the quiz | `refuses this module's Lernerfolgskontrolle while its video is unwatched` |
| 1.4 video bypass         | `refuses completion at the very start` + `accepts the watched video`      |
| 1.5 evaluation gate      | `refuses completion with only the evaluation and EFN outstanding`         |
| 1.6 EFN gate             | same, plus `says an EFN is required, because this course awards points`   |

## 1.7 — Draft courses

Enforced in `learning.service.enrol`, and the comment is the reason: the
catalogue hides a draft, and _"a bookmark, a WordPress embed or a link in an old
email reaches this method without ever having gone through the list"_. It answers
404 for a draft and for a closed validity window alike — neither being a
distinction a stranger is entitled to. Asserted from the learner plane in
`learning-flow.integration.test.ts`.
