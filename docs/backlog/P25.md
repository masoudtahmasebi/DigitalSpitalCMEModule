## P25-02 · Participants who sign in here — **done**

- **Estimate:** 8 h · **Review gate: human — auth**

### The problem, stated exactly

`fortbildung.digitalspital.com/medice` was an empty page, and it could not have
been anything else. Three separate things each guaranteed it:

1. **No project was slugged `medice`.** The portal takes its tenant from the
   first path segment and sends it as `X-DS-Project`; the only MEDICE project
   was `medice-adhs`. Hence "Dieses Projekt existiert nicht."
2. **Every learner route is behind the guard**, and the only credential the
   guard accepted was a JWT from a customer's own Keycloak realm.
3. **Nobody had one**, and there was no way to get one without MEDICE running
   an authorization-code flow they never asked us to run.

So the catalogue was unreachable by construction, and the page had nothing to
say about why.

### Why this is a gap, not a testing convenience

A customer without an identity provider cannot use this platform at all. "You
must run a Keycloak realm" is not a sentence anybody wants in a sales
conversation, and `user_identities.provider` has permitted `'local'` since
migration 0025 — this is the rest of it.

### The shape

| Piece | Where | Note |
| --- | --- | --- |
| `learner_credentials` | migration 0030 | Argon2id, keyed on the **credential** not the person |
| `learner_sessions` | migration 0030 | opaque token, SHA-256 stored, `project_id` scoped |
| `LocalIdentityProvider` | `apps/api/src/auth/` | the second `IdentityProvider`, first real use of P12-02's seam |
| `POST /auth/participant/sign-in` | `modules/participant-auth/` | the only unauthenticated write on the learner plane |
| `ParticipantSignIn` | `apps/portal/src/components/` | a form, for tenants whose `kind` is `portal` |
| a second project per customer | `packages/seed/src/lib.ts` | `medice` and `ds`, `identity_provider = 'local'` |

**A second project rather than flipping the first one.** A project binds one
*channel*, not one customer. MEDICE's physicians reach the course through the
WordPress plugin carrying a token from MEDICE's Keycloak, and that binding is
correct. The standalone portal is a different channel. Both projects belong to
the same customer and the catalogue is scoped by *customer* under RLS, so the
two show the same courses without seeding content twice.

**No self-service registration.** `CLAUDE.md` §3 defers it and it stays
deferred: a participant record is created by an administrator or by a seed.
Anyone who can create an account on a CME platform can create a CME record.

### Acceptance criteria

- [x] A participant signs in at `/{tenant}` with an e-mail and a password and
      sees that customer's courses.
- [x] The session is an httpOnly cookie; the token never appears in a response
      body and is stored only as a SHA-256.
- [x] A session minted at one tenant is refused against another — asserted in a
      unit test *and* over real HTTP, because the first proves the check is
      written and only the second proves it is reached.
- [x] Every refusal is one 401 with one German message: wrong address, wrong
      password, locked account, a Keycloak project, a malformed body.
- [x] Sign-out revokes the row, not merely the cookie.
- [x] The Keycloak path is untouched — 298 integration tests, including the
      whole existing auth pipeline, still pass.
- [x] The seed prints credentials it generated from the CSPRNG; no password is
      ever a literal in this repository.

### Five bugs that only running it found

Worth listing, because each one passed every unit test in the repository.

1. **`findProject` read `projects` directly.** That table has `FORCE ROW LEVEL
   SECURITY` and sign-in runs before any tenant context exists, so it matched
   zero rows and refused every correct password with the same message as a
   wrong one. Fixed by going through `resolve_project_binding`, which exists
   for exactly this chicken-and-egg.
2. **`findParticipant` joined `user_customers` on the bare pool.** Same class,
   same symptom. Fixed by running it inside `runInTenant` for the customer the
   binding already named.
3. **The guard read `request.cookies`.** This API deliberately does not run
   `cookie-parser` (`staff-session.ts` says why), so that property is always
   undefined — every cookie-authenticated request 401'd with "no bearer token
   presented" while carrying a perfectly valid cookie.
4. **`GET /auth/participant/me` declared no `@Roles`.** `RolesGuard` fails
   closed, so the one route the portal asks "am I signed in?" answered **403**
   after a successful sign-in. The page showed the login form for ever.
5. **The portal handed the widget the Keycloak token provider.** With no
   session it calls `beginLogin()` — an OIDC redirect to a realm that has never
   heard of this participant — so `GET /courses` was never sent at all. The
   page said "Abmelden" above an empty catalogue and no error anywhere.

Numbers 1–2 were found by an integration test written before the code was
believed to work. Numbers 3–5 were found by driving a real browser, and none of
them could have been found any other way: 3 and 4 need the whole guard chain and
5 needs a widget mounted in a page.

### Deliberately not done

- **No password change or reset flow.** `must_change` exists on the column and
  the sign-in reports it, but the screen is P21-04. A seeded demo account
  therefore sets `must_change = false` rather than raising a flag the portal
  cannot act on.
- **No "remember me".** A twelve-hour session with no refresh, because a shared
  clinic computer is the normal case rather than the edge one.
- **No account lockout notification.** The lockout is real
  (`learner_credentials.locked_until`, 8 attempts, 15 minutes) and silent —
  telling somebody their account is locked tells an attacker they found a real
  address.
