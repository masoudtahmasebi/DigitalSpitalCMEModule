# P63 — Neither client seed can run against the current schema

Raised 12.08, during P62's verification. Not reported from a browser and not
reported by CI: found by running `seedDsDemo` and `seedMediceAdhs` against a
**freshly migrated, empty database**, which is the one thing nothing had done
since migration 0039 landed.

```
SEED ds:     FAILED — new row for relation "courses" violates check constraint
                      "courses_no_answer_key_for_points"
SEED medice: FAILED — new row for relation "courses" violates check constraint
                      "courses_published_cme_is_complete"
```

Both seeds abort in their opening transaction. Neither tenant can be created on
a new installation. `dscustomer` — the only seed any test exercises — is
unaffected, because its course awards no CME points and is exempt from both
constraints.

This is CLAUDE.md §9.9's corollary in its sharpest form. The QA database has
`ds-cme-demo` and `adhs-akademie-adult` in it, so the seeds _look_ fine from
every screen. They are rows written by an **older schema**, by a seed that has
not been able to run since. The repository's state is not the installation's
state, and here the installation is the one that is out of date in our favour —
it is hiding the break.

## P63-01 · `./dsc seed ds` writes an answer key onto a course awarding points · 0.5 h

**Pre-existing. Broken since migration 0039 (P56-01), five phases ago.**

### What is wrong

`seedCourse` in `packages/seed/src/ds-demo.ts` passes `reveal_correct_answers`
as a literal `true` for every course it writes:

```sql
       100, 70, NULL,
       true, $12, $13,
```

`courses_no_answer_key_for_points` forbids that on a course awarding CME points:
with unlimited retries, per-question feedback **is** the answer key, and the
Lernerfolgskontrolle is a condition of the Anerkennung.

The seed was written before the constraint and never re-run after it. Nothing
caught it because nothing runs this seed — see P63-03.

### The fix

Derive it from the accreditation rather than hard-coding it. The seed already
computes `const accredited = course.cmePoints !== null` one line above; the
answer key is exactly the thing an accredited course may not show. So
`reveal_correct_answers = NOT accredited`, which makes the point-free demo
course keep its feedback — that course exists to show the non-CME path, and
showing answers there is correct and useful.

### Acceptance criteria

- [x] `seedDsDemo` completes against a freshly migrated database
- [x] `ds-cme-demo` has `reveal_correct_answers = false`
- [x] `ds-ohne-punkte` has `reveal_correct_answers = true`
- [x] The seed is re-runnable: the `ON CONFLICT DO UPDATE` sets it too, or a
      second run against the old row leaves the violation in place

## P63-02 · Both seeds publish a CME course they cannot furnish a VNR password for · 1 h

**Caused by P62-02.** Touches eiv — human review.

### What is wrong

Both seeds insert `status = 'published'` on a course awarding CME points, and
neither writes `vnr_password_enc`. The MEDICE seed says so, in its own printed
output:

> `No VNR password is seeded. Set courses.vnr_password_enc via the admin path`
> `before the EIV worker can authenticate.`

That sentence has been true and harmless for months, because the course was
published anyway and the failure only appeared later as a `failed_permanent /
missing_vnr_password` row. P62-02 turned that latent misconfiguration into an
immediate refusal, which is what it is for — and the seed is one of the writers
it refuses.

### Why the fix is not "seed a password"

The obvious repair is to generate a random VNR password, encrypt it, and
publish. It is wrong, and the reason is worth writing down.

A VNR password authenticates DigitalSpital to a legally binding accreditation
interface. A generated one authenticates to **nothing**. Seeding it would take a
course that currently refuses to be published for a stated reason and make it a
published course whose Punktemeldung fails at the Ärztekammer with an
authentication error instead — trading a clear refusal naming a field for an
opaque one naming a remote system. That is the §9.2 failure ("never offer what
the system will refuse") one layer down.

It also puts a credential-shaped constant in the repository, and requires the
seed to carry the cipher, which lives behind invariant 7 in `apps/api/src/
shared` and has no business being reachable from a seed package.

### The fix

**Seed the CME course as `draft`.** It is the truthful state: the course is
authored, accredited on paper, and cannot yet report. Publishing it is one
console action — set the VNR password, press Veröffentlichen — and that action
is now exactly the operator step the journey suite walks in act 3.

Both seeds' printed output names the action, at the point somebody looks for it
(§9.4), rather than describing the column.

Point-free courses (`ds-ohne-punkte`, `dscourse`) stay published: they have no
Punktemeldung to be incomplete for, so nothing about them is provisional.

### Acceptance criteria

- [x] `seedMediceAdhs` and `seedDsDemo` complete against a freshly migrated
      database
- [x] `adhs-akademie-adult` and `ds-cme-demo` are seeded `draft`
- [x] `ds-ohne-punkte` is seeded `published`
- [x] Each seed's summary names the two steps needed to publish, in the order
      they are done, and does not name a column
- [x] Setting the VNR password and publishing through the API succeeds with no
      other change
- [ ] **Human review** — eiv. The reviewer's question is **whether MEDICE's
      course arriving as a draft is acceptable at launch**, given that it means
      the tenant is not learner-visible until somebody sets the VNR password.
      The alternative is that DigitalSpital sets it as part of the deploy, and
      the seed keeps publishing.

## P63-03 · Nothing runs these seeds · 1 h

### What is wrong

The class, and the only part of this ticket that stops the next one.

`packages/seed` exports three seeds. **One** of them is executed by a test —
`seedDsDefault`, in `seed-default.integration.test.ts` — and it is the only one
of the three whose course awards no CME points, so it is exempt from every
constraint the other two hit. The two seeds that build the tenants we actually
demonstrate and ship have never been run by CI.

`scripts/check-seed-structure.mjs` exists and is in `pnpm verify`. It reads the
seed **source** and checks its shape. It cannot fail on a constraint, because it
never talks to a database — a check that silently covers less than its name
suggests (§9.1, second form).

Both defects above are the same sentence: a seed that has not been run since the
schema changed under it. That will happen again on the next constraint, and the
next one might be found by a client on launch day rather than by me the week
before.

### The fix

`apps/api/test/integration/seeds.integration.test.ts`: for **each** exported
seed, run it against the migrated test database and assert it completes. Then
run it a second time and assert it completes again — these seeds are `ON
CONFLICT DO UPDATE` upserts, and re-runnability is the property `deploy.sh`
depends on.

Derived from the export list rather than written as three cases, so a fourth
seed is covered on the day it is added rather than on the day somebody
remembers.

### Red check

database.

## P63-04 · P62-03's media check is reachable by nobody · 1.5 h

**Found by applying the client's own rule to my own work.**

### What is wrong

P62-03 built `MediaCheckService`, unit-tested it, and mounted
`GET /admin/courses/:slug/media-check`. Asked "name the caller", the honest
answers are:

| Symbol              | Called by                                                                         |
| ------------------- | --------------------------------------------------------------------------------- |
| `MediaCheckService` | the controller                                                                    |
| the endpoint        | **nothing** — not in `contracts/openapi.yaml`, not in the SDK, not in the console |
| `allSeekable`       | **nothing but its own test**                                                      |

So the deliverable of 0.4 — "an admin-side check that a configured media URL
answers a Range request" — exists as something an operator can reach only with
`curl` and a hand-made session cookie. That is CLAUDE.md §9.3 in the ticket that
cites §9.3, and §9.2 upside down: not an affordance that cannot work, but a
working thing with no affordance.

`scripts/unused-rules.mjs` did not catch `allSeekable` and could not: it reads
`packages/domain/src/index.ts` and nothing else. It is right about its own
scope; the scope is narrower than the failure class it is named for. Noted
rather than widened — scanning every export of every app would bury the signal
that makes it useful.

### What changed

- The endpoint answers `{ seekable, sources }`. `allSeekable` now has a
  production caller, and an operator gets a verdict rather than a table to read.
- `contracts/openapi.yaml` describes it and the SDK is regenerated from the
  contract, so `pnpm check:sdk` covers it from here on.
- The console's course structure screen gets **Medien prüfen**: one button, a
  German sentence per source, and the three outcomes named in the words the
  problem has — the host will not seek, the host cannot be reached, the file is
  ours and is signed at playback.

### Acceptance criteria

- [ ] `allSeekable` has a caller outside its test
- [ ] The endpoint is in the contract and in the generated SDK
- [ ] An operator can run the check from the console without leaving the course
- [ ] Each verdict is a sentence naming what to do, not a status code
- [ ] A component test drives the button and asserts the German for a host that
      answers `200` to a Range request — the case that looks healthy
