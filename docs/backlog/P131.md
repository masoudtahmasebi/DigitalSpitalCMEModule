# P131 — The Mediathek can add media

**Status:** built. One follow-up named at the bottom, not absorbed.

---

## The gap

> _"in mediathek there is no option to upload"_

True since the screen existed. P88-01 built the library as a place to **manage**
files — rename, describe, remove, find out what is taking four hundred megabytes
— and every way of getting a file _in_ stayed inside a course form. So the one
screen called "Mediathek" was the one place you could not add media.

## Why it asks which course

Every key is `<customerId>/courses/<courseId>/<filename>` (`storage-key.ts`).
There is no customer-level keyspace. The library _lists_ across courses; the
bucket still files everything under one.

Asking is the honest rendering of that. The alternative — inventing a second key
shape days before a launch — gives one file two ways to be addressed, and
`keyBelongsToCustomer`, `media-url.ts`, the audit log and the backup would each
have to learn both. Named as a follow-up below rather than absorbed while doing
something else (§3).

## What was built

- **`media-upload.ts`** — pure. `purposeFor` derives the purpose from the file's
  own MIME type, so the operator is never asked: a purpose decides the accepted
  types and the size ceiling, and the server derives the same answer from the
  same table. A dropdown would be a second opinion that can only disagree.
  `planFile` refuses an unsupported type, an empty file or an oversized one
  **before a byte is sent** — the server refuses too, but for a 6 GiB file that
  is twenty minutes later.
- **`MediaUpload.tsx`** — a drop target that is also a real `<input>`, so an
  author who cannot drag is not a special case. Per-file progress rows, and
  whatever landed is in the library even when part of a batch failed.
- Past the multipart threshold it uses `uploadInParts` (P129-05), so a 3 GB
  lecture is 96 retryable parts. Below it, the single-ticket path, which is
  cheaper for a 2 MB poster. `planFile` decides, from the server's constants.

## The bug the tests found, which was mine

The course list is loaded by the library and handed down, so a failure to list
courses degrades the upload panel rather than taking the screen with it. The
comment said exactly that, and it was **false**: `.catch()` sees a rejected
promise, and a client without the method at all throws _synchronously_. Seven
existing tests went red the moment the effect landed, all of them for that
reason, and an operator who came to rename a file would have lost the whole
Mediathek.

A claim in a comment the code does not keep is worse than no comment. The call is
inside `try` now, and `survives a client that cannot list courses at all` was
watched to go red without it.

## Not built, and named

**A customer-level keyspace**, so the Mediathek could accept a file that belongs
to no course. That is the right shape — the library outlives any course, and the
audit log has allowed a null `courseId` since P88-01 in anticipation. It is a
migration, a key builder, a route and four call sites that check prefixes, and
that is not work to start ten days before a launch.

**Resume across a page reload** for large uploads (P129-05). The server half is
real; the browser does not yet remember the `uploadId`.
