### What changed, and why it is recorded here

P9-02, P9-04 and P9-05 were previously dropped — the trade lever, taken
deliberately. They have since been built on an explicit instruction, and the
earlier reasoning is worth keeping because it was not wrong:

Seeding content programmatically (`db/seed/adhs.ts`) meant every change to a
course was a reviewed change, which for a course whose pass threshold is a
condition of an Anerkennungsbescheid is arguably a _better_ control than a form
somebody can change on a Friday afternoon. That argument still holds, and the
console answers it rather than ignoring it:

- **The compliance rules are still server-side and still refuse.** A pass
  threshold below the accredited minimum is refused with the reason. A video
  without a duration is refused, naming the field. A question with no correct
  answer — or a single-choice question with two — is refused, because it would
  produce a quiz nobody can pass.
- **Nothing a learner has touched can be deleted.** Content with recorded
  progress, a question with recorded answers, an evaluation question with
  responses: all refused with the count, and the console says so before the
  click rather than turning a 409 into a surprise.
- **Every mutation is audited** — actor, action, subject, field names and
  counts. Never a prompt, never an answer key.
- **Reordering is validated as a permutation** before anything is written, so a
  client that lost an item during a re-render is rejected rather than obeyed.
  Obeying it would delete a chapter from a course learners are part-way through.

`db/seed/adhs.ts` remains, and remains the way the ADHS course is created. The
console is how it is _changed_ after launch.

### P9-01 · Admin console shell and authentication

- **jira:** _(unassigned)_
- **Estimate:** 2.5 h · **Week:** 5 · **Depends on:** P1-04
- **Review gate:** human — auth

**Context**
The console has its own login — unlike the learner widget, there is no WordPress
session to bridge from. It is also where `super_admin` and `customer_admin`
operate, so the role model from P1-04 is enforced at its most consequential.

**Scope**

- Vite SPA with Keycloak login, navigation and the role-aware shell.
- Super admin "act as customer" selector, audited per ADR-0002.

**Acceptance criteria**

- [ ] Login uses the same validated-token path as the API; no separate trust
      mechanism exists
- [ ] Navigation shows only what the role may reach — a hidden route is also
      refused by the API
- [ ] "Act as customer" is explicit, one customer at a time, and audited
- [ ] Session expiry returns to login without data loss in an open form

### P9-03 · Course authoring with compliance fields

- **jira:** _(unassigned)_
- **Estimate:** 3.5 h · **Week:** 6 · **Depends on:** P9-02, P2-02
- **Review gate:** human — assessment

**Context**
This is where a customer admin sets `required_watch_percent` and
`pass_threshold_percent`. Those two fields decide whether a physician's CME points
are valid, so the UI must make their effect unambiguous rather than presenting
them as two numbers in a form.

`pass_threshold_percent` in particular is a **condition of the
Anerkennungsbescheid** for an accredited course, not a preference — the ÄKWL
requires at least 70 % for this one. An admin lowering it is not tuning
difficulty, they are voiding the accreditation, and the form has to say that.

**Scope**

- Course create/edit with all compliance fields from P2-02.
- VNR password entry, write-only.
- Explicit warning that changing a threshold does not affect existing enrolments.

**Acceptance criteria**

- [ ] Every compliance field from P2-02 is editable and validated in the UI
- [ ] The VNR password is write-only and never rendered after saving
- [ ] The form states plainly that threshold changes do not apply retroactively
- [ ] Lowering `pass_threshold_percent` below the course's accredited minimum
      warns explicitly that it voids the Anerkennung — not a silent save
- [ ] Percentages accept only integers 0–100, with the effect of the value
      explained in plain German

### P9-04 · Module, Chapter and Content authoring

- **jira:** _(unassigned)_
- **Estimate:** 4 h · **Week:** 6 · **Depends on:** P9-03, P2-03
- **Review gate:** none

**Context**
Ordering here defines sequential gating (P3-03), so the reorder UI is a
compliance-adjacent control, not a convenience.

**Scope**

- Create, edit, reorder and delete modules, chapters and content items.
- Video (URL + duration), text, quiz and details content types.
- Plain text/markdown editing only — **rich WYSIWYG is deferred scope**
  (roadmap §4).

**Acceptance criteria**

- [ ] Reordering is atomic and immediately reflected in learner gating
- [ ] Video content cannot be saved without a duration, since the watch gate
      requires it
- [ ] Deleting content with recorded learner progress is refused with a clear
      explanation
- [ ] No WYSIWYG editor and no media upload/transcoding is introduced

### P9-06 · Participant status list

- **jira:** _(unassigned)_
- **Estimate:** 2.5 h · **Week:** 6 · **Depends on:** P9-05, P3-04
- **Review gate:** none

**Context**
Must read the same rollup as the learner view (`CLAUDE.md` §4 invariant 6). This
is the screen where a divergence would be noticed by the customer — and by then it
would already have been wrong in a CME record.

**Scope**

- Per-course participant list: completion status, score, watched %, EIV submission
  state, certificate delivery state.
- Filter by status; a list, not a dashboard.
- **Surface EIV submissions that failed the fast retries** (P7-06): a submission
  still unresolved after 3 attempts at 10-minute intervals must be visible here,
  distinctly from healthy ones, so an admin can act before the correction window
  closes and the paper fallback (P7-07) is still open.

**Acceptance criteria**

- [ ] Numbers match the learner's own view exactly, asserted by test
- [ ] EIV state distinguishes queued, submitted, failed and overdue
- [ ] A submission unresolved after the fast retries is called out for admin
      attention, not buried in a generic "failed" count
- [ ] Certificate state distinguishes issued, delivered and bounced
- [ ] The list is tenant- and department-scoped by role
- [ ] No chart is built
