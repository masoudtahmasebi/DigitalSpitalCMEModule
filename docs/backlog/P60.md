# P60 — What the client changed after Section 8

Four instructions from MEDICE on 12.08, in response to the Section 8 report.
Three change what the platform does; the fourth asks for a test of something it
already did. Two of them reverse a position taken earlier in the project, and
both reversals are recorded here rather than silently applied.

---

## P60-01 · Archive every issued certificate in object storage · 3 h

**Status: done.** Touches certificates — human review.

### What was asked

> "what is pdf_path? we should store those also in s3 for later verification
> for each course and customer."

Section 8 reported that there is no `pdf_path` because nothing is stored — the
PDF is rendered from the record on demand. That remains true of the **serving**
path, and it is what keeps the emailed document and the downloaded one the same
document. What changes is that the bytes as issued are now also kept.

### Why the two are not the same thing

They answer different questions, and only one of them survives time:

| Question                              | Answered by            |
| ------------------------------------- | ---------------------- |
| "show me my certificate"              | the render, current    |
| "prove what was issued on 12.08.2026" | the archive, as it was |

A re-render years later cannot answer the second. Fonts change, the layout
changes, a course's stamp is replaced, an accreditation lapses. The Kammer, an
audit or a dispute asks the second question, which is exactly the "later
verification" the instruction names.

`pdf_sha256` is what makes it evidence rather than a copy: an object whose bytes
do not hash to the stored value has been altered, and that is answerable without
having to trust the bucket.

### The shape

`<customer>/certificates/<course>/<certificate>.pdf` — per customer and per
course, as asked. Customer-first, so `keyBelongsToCustomer` and
`customerPrefix` cover it without knowing it exists, and a bucket policy or a
lifecycle rule written for course media covers this too. A CHECK constraint
holds the key to the row's own `customer_id`: a bucket has no RLS, so the
isolation has to be the key (ADR-0002, carried across).

Written at issue, once. A retry that renders again finds `pdf_object_key`
already set and leaves it — overwriting would replace the evidence with a
reconstruction. A bucket that is down leaves the row unarchived, which is a
state the schema can express and `certificates_unarchived_idx` can find; it
never fails a completion, because the physician earned the document either way.

### The part that is not optional, and nearly was

**This is the first personal data the platform puts somewhere Postgres cannot
reach.** The archived PDF carries the name, the Anschrift and the EFN on its
face. `erase_subject` can redact every column that names a physician; it cannot
delete an object in a bucket.

Shipping the archive without an answer to that would have made erasure quietly
incomplete — the request returns 200, `audit_log` records it, every table looks
right, and the document is still in storage. Migration 0024 wrote down this
exact shape one table over ("an erasure routine that misses a column added after
it was written … fails silently"); this is the same failure at one remove.

So `erase_subject` now writes the key to `object_erasures` **before** clearing
the row that names it, and the API drains that queue — in the erasure request
itself, and again on boot for whatever a storage outage left behind. `deleted_at`
is stamped only after the bucket confirms, and a 404 counts as gone. An
obligation cannot be discharged by being forgotten.

### Acceptance criteria

- [x] Every issued certificate is written to `<customer>/certificates/<course>/`
- [x] The row records the key, a SHA-256 and a time — all three or none
- [x] A constraint refuses a key under another customer's prefix
- [x] Archived once: a re-render does not overwrite the issued bytes
- [x] A bucket failure never fails a completion or a delivery
- [x] **An erasure deletes the object**, and a failed delete stays owed
- [x] Verified against a SigV4-verifying bucket, not a stub that answers 200
- [x] `pnpm verify` green; 488 integration tests green
- [ ] **Human review** — certificates, and a new personal-data location. Two
      separable questions: **should the platform keep the issued bytes at
      all**, and **is the erasure mechanism sufficient?** The second is the new
      risk — `erase_subject` cannot delete an object in a bucket, so it queues
      the key and the API drains it on the erasure request and on boot, **not
      on a timer**. An installation that never restarts and never erases again
      keeps a failed deletion outstanding; it is queryable
      (`object_erasures WHERE deleted_at IS NULL`) but nobody is told. Packet §6.

## P60-02 · Print the EFN on the Teilnahmebescheinigung · 0.5 h

**Status: done.** Touches certificates — human review.

### The reversal, stated plainly

Section 8 reported the EFN as deliberately absent: the ÄKWL Muster has no field
for it, and ADR-0004 keeps the platform's personal-data footprint narrow. MEDICE
asked for it on the document. **That is their call and it is applied** — they
are the controller, and the certificate is their document.

What does not change: the EFN still never reaches a log, an audit `detail`, an
error message or any other person's response. Only its own subject can read it
through the API, and only their own certificate carries it.

### Where it comes from, and why that is not the enrolment

Read live from `efn_profiles`, not snapshotted onto the enrolment like the VNR
and the points. That is the right way round for this one field: an EFN is
permanent and unique per physician, so a _correction_ means the earlier value
was wrong — including on a certificate already issued. Snapshotting would keep
the typo on the paper while the Punktemeldung went to the corrected number.

### Drawn only when there is one

A point-free course reports nothing to EIV-FOBI and never asks for an EFN, and
erasure deletes the row. In both cases the line is omitted rather than drawn
empty: an "EFN:" with nothing after it on a legal document reads as a field
somebody failed to complete (CLAUDE.md §9.4). `missingCertificateFields`
excludes it for the same reason — its absence must not refuse a document that
has been earned.

### Acceptance criteria

- [x] The EFN is printed as a labelled line when the course awards points
- [x] The line is omitted, not drawn empty, when there is no EFN
- [x] Read live, so a corrected EFN corrects the certificate
- [x] Verified red: dropping the field turns one renderer case red
- [ ] **Human review** — certificates. The reviewer's question is **whether the
      client's instruction overrides ADR-0004's minimal-footprint reading for
      the printed document.** The ÄKWL Muster has no EFN field; printing it
      widens a permanent physician identifier's exposure from "our database and
      the Kammer" to wherever the PDF ends up. MEDICE are the controller and
      asked for it. Record which way, and why — ADR-0004 will be read again.
      Packet §8.

## P60-03 · The Anschrift, filled when the data exists · 1.5 h

**Status: done.**

> "Anschrift: would be filled if the data is available, not filled if the data
> is not available."

Which is what the renderer already did — `data.participantAddress ?? ""` has
been there since P8 — and nothing ever supplied a value. CLAUDE.md §9.3: a rule
written is not a rule enforced.

`enrolments.attested_address` now holds it, supplied with the rest of the
Punktemeldung form. On the enrolment beside the attested name, for the same
reason: it is what the learner attested to for _this_ participation, and a
physician who moves does not thereby change the address on a certificate already
issued.

Optional and staying optional. The Bescheid's minimum field list does not
include it (**S12 is still open with the ÄKWL** — whether a blank Anschrift is
acceptable for an online on-demand format), so a learner who leaves it empty
must still be able to finish. The line is drawn either way, because the Muster
has it and a form missing a line it should have looks altered.

Bounded at 200 characters in the DTO and in the column, because it is free text
that goes onto a printed document.

### The visible half, added in P61-01

**Done.** The field was missing from the widget's Punktemeldung form when this
ticket was written, and stating that here is what made Section 9 look for it —
which it did, and which is now **P61-01**. Typed into the form, it reaches the
enrolment and prints on the PDF; left empty, the line is drawn blank.

## P60-04 · Pin the gate that is already right · 0.25 h

**Status: done.**

> "The certificate is gated on completion is correct, but we should be able to
> test it."

It is now its own integration case, asserting the property rather than the
implementation: with the Punktemeldung still `queued` — the worker has not run
— the certificate is already `issued`.

The case exists because the reading QA applied is a reasonable one and the
consequences of the other reading are not obvious until stated: gating on EIV
would deny certificates for every point-free course, where there is no Meldung
to wait for, and would withhold earned documents for the length of any Kammer
outage. The physician earns the document by finishing the course; the
Punktemeldung is the platform's obligation to the Kammer, not a condition on
theirs.

A test whose name says which of two defensible designs was chosen is worth more
than one that only checks a status code.
