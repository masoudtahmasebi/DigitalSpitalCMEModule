# P214 — an expired session was reported as a fault in the site

The client, with a screenshot of `gemeinsamadhsbegegnen-medice-kunden.digitalspital.de/dscme/`
at 12:16 on 11.09.2026:

> why would this happen at 12:16? was it a deployment?

The screen said:

> **Es ist ein Fehler aufgetreten** — Diese Seite konnte keine Anmeldedaten für
> das Lernmodul abrufen. Das liegt nicht an Ihrem Konto — bitte versuchen Sie es
> später erneut oder wenden Sie sich an den Betreiber der Seite. Technische
> Angabe: Token-Endpunkt — endpoint_403.

---

## First: it was not a deployment

The standing list's question one (§9.12) — **which build, which data?**

```
$ gh api .../actions/workflows/deploy.yml/runs
127  Deploy  success  2026-09-08T08:39:30Z
```

127 runs, the most recent three days earlier. The only workflow runs on 11.09
were CI on a feature branch, and CI does not deploy — `deploy.yml` fires on
`workflow_run` filtered to `branches: [main]` (§9.9b). The screenshot's 12:16
CEST is 10:16 UTC; that day's CI runs were 09:15 and 10:17 UTC, one of them
_after_ the error.

Nothing changed under the client. This had been true for as long as the code had
been there, and it took a person clicking to find it — §9 in one line.

---

## What the screen actually meant

Three layers, each individually correct, each tested, and the seam between them
tested by nothing. A physician's Keycloak session expired — which is ordinary,
happens every day, and needs one sentence and a link.

### Layer 1 — the plugin turned "signed out" into "forbidden"

`DS_LMS_Token_Endpoint::permitted()` ended:

```php
return DS_LMS_Token_Source::available();   // "does this session hold a token?"
```

That reads like the endpoint's strongest gate. It was not a gate at all:
`handle()` asks the very same function one line later and answers
`404 {"token":null,"reason":"no_token_held"}` when there is nothing. The set of
requests that walk away with a token is identical either way. All the check
decided was **which refusal the caller sees** — and WordPress turns a false
permission callback into `rest_forbidden`.

So the 404 path — written for P97-01 _because the ambiguity had already cost a
day_ — was **unreachable in production**.

### Layer 2 — the widget threw the reason away

Even when the plugin sent it, the widget could not read it:

```ts
if (!response.ok) {
  // The status, not the body: an error page from a proxy or a WAF is not
  // this endpoint's JSON …
  throw new TokenUnavailableError(`endpoint_${response.status}`);
}
const body: unknown = await response.json(); // never reached for a 404
```

The comment's concern is real and is kept. What it missed is that the endpoint's
_designed_ answer for a signed-out visitor is a **404 with a body**, so
`no_token_held` — the one reason the widget has different words for — could only
ever have arrived through the 200 path, which the plugin does not use.

Found by running it, not by reading it. The first version of this ticket fixed
layer 1, and the widget test still failed with `endpoint_404` on screen.

### Layer 3 — and the screen had no way forward anyway

`describeError` maps `no_token_held` to a sensible sentence, and every screen
wrapped that sentence in a red `ErrorNotice` headed _"Es ist ein Fehler
aufgetreten"_, with a **Erneut versuchen** button and no sign-in link. Retrying
cannot fix an expired session.

`de.signedOut.expiredTitle` and `expiredMessage` — _"Ihre Anmeldung ist
abgelaufen / Ihr Fortschritt ist gespeichert…"_ — have existed since P99-02 and
were rendered by **nothing**. They sat in `copy-coverage.mjs`'s dead baseline
with the note `raise — no screen tells a mid-course expiry from a missing token`.
That note was correct, was carried forward for eleven phases, and described this
defect exactly (§9.3).

## P214-01 — the fix, in three places because the defect was in three

| Layer  | Change                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------ |
| Plugin | `permitted()` decides origin and nonce only; `handle()` answers `404 no_token_held`                    |
| Widget | a failed response's `reason` is read when it has a usable one, status otherwise                        |
| Widget | `FailureNotice` renders an ended session as `SignedOutNotice` with the expired copy and a sign-in link |

**The security posture is unchanged, and this is the claim that matters most.**
`DS_LMS_Token_Source::current()` takes no argument, so no token is reachable from
this endpoint except the calling session's own — that is the property that makes
it safe, and it is not a check. Same-origin and nonce stay exactly where they
were. Only the status and body for the no-token case changed.

One quieter consequence: `available()` calls `current()`, which **refreshes an
expiring token against Keycloak**. Asking in the callback and again in the
handler was two refresh attempts per request. It is one now.

And the fallback is preserved deliberately: a token endpoint that is down,
misconfigured or behind a broken proxy still says so and still offers a retry.
Telling _that_ physician "please sign in again" sends them round a loop that
cannot end, which is P101-03's lesson and has its own test.

## P214-02 — `pnpm build:wp-plugin`

The plugin is the one artefact of this project a **human carries by hand** to a
server we do not control, months after the commit that produced it. So the zip
is built by a script that refuses to produce one whose three version strings
disagree, runs the PHP suite first, excludes `tests/` (a harness that redefines
`wp_verify_nonce` has no business on a customer's server), and zips from
`wordpress/` so every path begins `ds-lms/` — a zip made from inside the folder
unpacks as loose files and installs as a broken plugin, which looks like a
corrupt download rather than a packaging mistake.

Watched red: with `DS_LMS_VERSION` set to `2.0.9` it prints all three numbers
and exits 1.

Plugin **2.1.0**. It requires the platform side released the same day — before
it, layer 2 discards the body.

---

## What would have caught it, and now does

**Nothing could have, and that is the finding.** Every layer had tests and all
of them were green:

- `security-test.php` asserted the 404 and the reason by calling
  `DS_LMS_Token_Endpoint::handle()` **directly**, so it proved the handler's
  behaviour on an input WordPress would never deliver to it. §9.7 verbatim: _a
  test can cover a function exhaustively and prove nothing about the product,
  because nothing checks that the function is called._ There is now a
  `dispatch()` helper that runs the permission callback first and the handler
  only if it passed, and nothing asserts a status without going through it.
- The widget's token tests stubbed providers, so no test ever took an HTTP
  status through `endpointProvider` to a screen. `session-expired.test.tsx`
  drives `App` with the **real** provider built by `resolveTokenProvider`, over
  a `fetch` answering the way WordPress answers.

Each of the three fixes was sabotaged separately and each takes the suite red on
its own — 5 PHP checks, 5 widget cases, 5 widget cases. That mattered here more
than usual: a defect with three layers can be "fixed" by one change that makes
the symptom go away while two of the three remain.

---

## The number I could not establish, and did not guess

**Why the refresh failed at that moment.** `available()` → `current()` → if the
token expires within 60 s, `refresh()`; if that returns null, `available()` is
false. The page rendered with a `token-endpoint` attribute, which
`token_attributes()` only writes when `available()` was true — so it was true at
render and false at fetch, meaning `refresh()` failed in between.

Why is not derivable from a screenshot. Candidates, none chosen: Keycloak's SSO
session max or idle reached, a refresh token already rotated by a concurrent
request, or Keycloak unreachable from the WordPress host.

**What answers it** is the plugin's own diagnostics screen (`manage_options`,
which Philipp has). It reports whether a token is present for the current
session and whether renewal is configured at all — _"KEINE Erneuerung möglich —
nach Ablauf muss sich die Person neu anmelden"_. If it says that, every session
on the site hits this wall on expiry and the fix above changes the message
rather than the frequency.

That is the honest scope of this ticket: **the screen now tells the truth.**
Whether the underlying session should have survived is a separate question, it
belongs to whoever owns the Keycloak realm's session settings, and it is not
answered here.
