# P237 — the course masthead: no strip above it, and its two controls together

Closes **DEP-45** (_Fix · Course detail page — fill gap between navigation
header and hero banner_) and **DEP-46** (_Improve · content pages — establish
consistent CTA placement for progress and back navigation_), both filed by
Philipp on 15.09.2026.

Raises a question on **DEP-44** rather than building it — see the last section.

---

## They were filed as two tickets and they are one defect

`apps/portal/src/App.tsx` wrapped the widget in a `space-y-4` div and, on the
course route only, put a standalone **Zurück zur Übersicht** button in it above
the hero. Measured in the rig at 1280 px before the change:

```
GEOMETRY {"headerBottom":79,"widgetTop":157,"band":78,
          "lightDomButtons":[{"text":"Zurück zur Übersicht","top":103,"height":38}]}
```

78 px decomposes exactly: 24 px of the header's `mb-6`, a 38 px button, 16 px of
`space-y-4`. That band **is** DEP-45. The button in it **is** DEP-46 — it sat at
the top-left of the page while the CTA it belongs beside sat mid-right, inside
the widget's meta strip.

So one change answers both: delete the band, and give the widget a back control
of its own in the strip beside **Fortbildung starten**.

## Why the widget could not simply draw one

`App.tsx` has offered `onBackToCatalogue` since P156-02 — but only when
`courseSlug === ""`, i.e. when the widget drew the catalogue itself. Its comment
says why, and the rule is still right:

> The attribute wins for the whole lifetime of the element: a page that names a
> course is showing that course, and there is no back link to a catalogue the
> host page never asked for.

On a customer's WordPress course page there is no catalogue behind the widget.
A back control there could only ever do nothing, which is §9.2. The portal is
different — it has a catalogue and a URL for it — but the widget cannot tell the
two hosts apart from inside.

`ds-lms:course-open` solves its version of this without configuration, because
the widget has a working answer either way: a routing host cancels, a WordPress
host gets the widget's own navigation. Leaving a course has no such pair, so the
host has to say. `back-to-catalogue="yes"` is that declaration, and it is the
only thing that puts the control on the screen. `ds-lms:course-back` is not
cancelable, because there is no fallback for a host to suppress.

## Two things found while doing it, both by looking rather than by reasoning

**The label acquired a second meaning in its new position.** "Zurück zur
Übersicht" was unambiguous 16 px under the strip. Four rows below the strip is a
tab called **Übersicht**, and in the new position the nearer reading is the
wrong one — §9.4. `player.back` keeps the old words and is left alone: on the
player screen "Übersicht" is the course overview and there is no tab of that
name in view.

**And the first replacement broke the layout.** "Zurück zum
Fortbildungsbereich" — which names `catalog.title` exactly — pushed the pair
onto a second row at 1280 px and made the 86 px strip half as tall again. Seen
in the screenshot, not predicted. The shipped label is **"Alle Fortbildungen"**
at `md` rather than `lg`, which is also the better hierarchy: the two are a pair
and not equals.

`portal/locale/de.ts`'s own `nav.back` held a second copy of the same sentence
and has gone with the button — §9.10b, one value, one home. `catalog.back` is
the survivor and is the one an operator can override in Verwaltung → Texte.

## What tests this, and what each one would miss alone

Three layers, because the contract crosses a package boundary as an attribute
and a CustomEvent, and **each side's own tests pass with the other side
deleted** (§9.7):

- `widget/element.test.ts` — no control without the attribute (the WordPress
  case), the event reaches a listener outside the closed shadow root carrying
  the slug, and the widget stays on the course after reporting.
- `portal/WidgetMount.test.tsx` — the attribute goes on a course mount and not
  on the catalogue, the event reaches the navigation, and the listener is
  removed on unmount.
- `e2e/kurs-kopfleiste.spec.ts` — the band is gone, the two controls are on one
  row with back reading first, and pressing it returns the address to the
  catalogue. This is the only test in the repository that fails if the three
  pieces are not connected (§9.13).

All three were watched to go red, one sabotage each:

| Sabotage                                          | Red                                              |
| ------------------------------------------------- | ------------------------------------------------ |
| `routesBack = true`                               | "draws no back control when the host has not…"   |
| `onCourseBack` wired to a no-op                   | "draws it, and reaches a listener outside…"      |
| the `back-to-catalogue` attribute removed         | "says it handles back navigation on a course…"   |
| `WidgetMount`'s listener removed                  | "navigates when the widget reports…"             |
| `flushContent={false}`                            | "a strip of page sits above the hero"            |
| the control returned to its own line              | "the two controls are not on one row"            |
| `onBackToCatalogue` wired to a no-op              | the URL does not return to the catalogue         |
| `catalog.back` reverted to "Zurück zur Übersicht" | "names where the back control goes, not the tab" |

### And one of those sabotages was green before it was red (§9.1)

Reverting the copy and re-running the widget suite **passed**. `@ds/copy`
resolves to `dist/`, so editing `src/de.ts` changes nothing until the package is
rebuilt. The check was green because of what it was not reading. With
`pnpm --filter @ds/copy build` in between it goes red as it should — worth
recording, because every future copy-level sabotage in this repository has the
same trap and nothing about it is visible from the test run.

## Not done: DEP-44, and why

DEP-44 asks for a state-based CTA in the progress overview with three labels.
Two of them already ship (`de.overview.start`, `de.overview.resume`, chosen in
`CourseHeader.tsx:232` from `progress.status`). The third is state 2, "Course
paused → Fortsetzung pausieren", and **there is no paused state**:
`packages/domain/src/types.ts:12` is `"not_started" | "in_progress" |
"completed"`, and `grep -rn "paused" packages/domain/src/` returns nothing.

The two existing "Fortbildung pausieren" controls are neither of them a course
state — `PlayerScreen.tsx:234` pauses the playing video in React-local state
that never reaches the server, and `QuizScreen.tsx:706` is `onBack` off the exam
result screen.

So the ticket reads two ways: the labels for states 2 and 3 are crossed and
there are really two states, or a persisted paused flag on the enrolment is
genuinely wanted — a migration, a new `ContentStatus` value (compliance logic,
§2 human review), the rule for what clears it, and an answer about whether a CME
deadline runs while paused. Asked on the ticket on 16.09.2026 rather than
guessed (§7). Building it is its own work order.
