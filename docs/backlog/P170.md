# P170 — A passed Lernerfolgskontrolle is finished, and says what to do next

**Raised by:** the client, 03.09.2026, widening P169-01 the day it shipped:

> _"there is a new requirement, if someone has passed a lernerfolgskontrolle, we
> shouldn't let that user fill the lernerfolgskontrolle again, when he has
> cleared the exam already. — afterwards, although the user is not able to do the
> exam, if they match the criteria to do the point declaration, they can see the
> button of `CME-Punkte geltend machen`. For the users, who have done the
> lernerfolgskontrolle, we can show either the next steps or if done button of
> CME-Punkte geltend machen"_

**Branch** `claude/education-platform-roadmap-3vgrqh`, from `15d0c18`.

---

## P170-01 — The line is the pass, not the certificate

P169-01 refused a further attempt once the certificate was issued. The client
moved the line one step earlier, and the earlier line is the more defensible of
the two: **between passing and certifying there is no question a further attempt
could answer.** The score is not a grade a physician is marked on, it is a
threshold they are over; `bestScorePercent` is best-of, so a retry cannot change
the outcome, and all it can do is add rows to the assessment record behind a
result that is already decided.

- **API.** `submit` refuses with `conflict` when the stored best score for this
  content is at or above the **enrolment's** `passThresholdPercent`. Checked
  before the attempt counter, so a refused attempt never consumes one of a
  course's allowance, and asserted to record nothing — a refusal that still
  writes the attempt is the defect with an error message on top.

  Three details, each with its own test:

  - **At the threshold, not above it.** 70 % against 70 % is a pass, and
    `upsertQuizProgress` uses the same `>=`. An exam that reopened at exactly
    the pass mark would be open for everybody who scraped through.
  - **The enrolment's threshold, not the course's.** A course later tightened to
    90 % must not reopen an exam somebody passed at 80 under the rule they
    enrolled on. That is what the enrolment's snapshot columns are for.
  - **Derived, not read from a flag.** `upsertQuizProgress` writes
    `passed` from exactly this comparison, so re-deriving it here keeps one rule
    rather than two that could drift (§4 invariant 6).

  The certified branch from P169-01 stays above it, and now earns its place
  only by its **message**: a physician holding a Bescheid is told about that
  rather than about their score.

- **Widget.** The intro screen drops from three states to two — unsat, and done.
  No sitting button once passed, because `submit` would refuse it (§9.2).

  The copy had to change with it. `alreadyPassed` used to end _"gewertet wird
  immer Ihr bestes Ergebnis, ein weiterer Versuch kann Ihr Bestehen also nicht
  aufheben"_ — true, useful, and obsolete the moment the retake closed: beside a
  button that no longer exists, a reassurance about repeating reads as an
  instruction to go and find it. `de.quiz.repeat` is gone entirely.

## P170-02 — And it is not a dead end

The second half of the request, and the half that keeps the first from being a
worse screen than before it. The passed **result** screen already offered
_CME-Punkte geltend machen_ or the next section; the **intro** — where a learner
lands when they come back to an exam they finished last week — explained itself
and offered nothing to do.

It now carries the same two controls in the same order:

- **CME-Punkte geltend machen** when the course is finished and the point is
  unclaimed, through the Evaluationsbogen first if that is outstanding;
- otherwise **Weiter: «next section»**;
- and **Zurück** always, so the screen is never a dead end.

Never both at once: two primary buttons proposing different directions is a
screen asking the learner to decide something the server has already decided.

`App` now gates `onClaimPoints` on `courseComplete && completedAt === null`
rather than on `courseComplete` alone. It was enough while the button only
appeared straight after a pass; now that it also appears on a screen a certified
physician can return to, "geltend machen" would be describing something already
done. It is the same condition the course page's own button uses (P168-02), so
the two cannot disagree about whether a point is left to claim.

## Acceptance criteria

- [x] A passed exam accepts no further attempt, at the service and over HTTP.
- [x] The refusal records nothing.
- [x] It bites at the threshold exactly, and against the enrolment's snapshot.
- [x] A failed attempt still leaves the exam open.
- [x] The intro offers no sitting once passed, and says why.
- [x] It offers the Punktemeldung when the criteria are met, the next section
      otherwise, never both, and always the way back.
- [x] Rules watched red: the API refusal (3 service cases + the integration
      case), the intro's missing sitting button (4), the next-step controls (1).

## Notes on what this changed underneath

Two existing tests asserted the behaviour the client removed, and both are
rewritten rather than deleted — the surviving property is worth keeping:

- `keeps the best score, so a curious retry cannot lose an earned pass` →
  **`keeps the best of several failing attempts`**. The best-of rule still
  governs repeated _failures_; it is only unreachable after a pass.
- the integration suite's `keeps the best score after a later failed attempt` →
  **`refuses a further attempt once the exam is passed`**, which asserts the
  same thing more strongly and through the controller, the DTO and the
  transaction.
