## P38-01 · Console operators for a seeded tenant — **done**

- **Estimate:** 6 h · **Review gate: human — auth**

### What was actually missing

Three seeds populated a tenant down to its quiz options and **none of them
created an account that could open the console for it**. The only staff account
any installation had was the one `bootstrap-admin` mints — a `super_admin`,
whose password is printed once and never again. "Sign in to Verwaltung and look
at the demo customer" meant using the account that can do everything to every
customer.

`seedDemoStaff` now creates two per tenant, one per customer role:

| Account                     | Role             | May                                                    |
| --------------------------- | ---------------- | ------------------------------------------------------ |
| `verwaltung@<slug>.example` | `customer_admin` | departments, projects, courses, participants, branding |
| `redaktion@<slug>.example`  | `course_editor`  | courses and their content — nothing above a course     |

`.example` is reserved by RFC 2606, so neither address can ever receive mail. A
demo account on a real domain is one somebody eventually sends a password reset
to.

Neither is exempt from anything. They hold no TOTP secret, so the first sign-in
follows whatever policy applies. Seeding a factor would mean a shared TOTP
secret in the repository.

## P38-02 · `course_editor` granted access to nothing — **done**

- **Estimate:** 5 h · **Review gate: human — auth**

### The defect

Signing in as the new `redaktion@` account produced:

> Ihr Konto hat keine Berechtigung für die Verwaltung.

The role the client asked for in as many words — _"customer users who can create
only courses, so they have limited access"_ — was **declared in `@ds/domain`,
granted `course` and `content` by the capability matrix, offered on the Konten
screen as something to assign, and accepted by no route in the platform.**
`ADMIN_ROLES` and `AUTHOR_ROLES` both omitted it, so the console's very first
request, `GET /admin/courses`, answered 403 and the console rendered nothing but
that error.

A role that grants access to nothing is worse than an absent one: it can be
handed out, it looks like a decision, and the person holding it cannot work.

### The boundary, drawn where the capability matrix already drew it

**May** — `GET/PATCH /admin/courses`, `GET /admin/projects` (read-only: creating
a course means choosing a project), and everything from `POST /admin/courses`
downwards — modules, chapters, contents, ordering, experts, the quiz, the
evaluation.

**May not** — departments, projects (any write), participants, certificate
assets, branding, staff accounts, the customer registry.

`PATCH /admin/courses/:slug` is included deliberately. It carries the VNR, the
points and the pass threshold, and a role that can create a course but not make
it certifiable is not "limited access", it is a dead end. The compliance floor
is enforced in the service for every caller alike: the pass threshold cannot go
below the accredited minimum whoever is asking.

The console stops drawing **Organisation** and **Erscheinungsbild** for this
role. That is not the enforcement — the API refuses regardless, and thirteen
integration tests say so — it is that both screens read projects, so leaving
them drawn would offer a menu entry that can only produce an error.

### Covered in both directions

`hierarchy.integration.test.ts` gained a block that signs in a real
`course_editor` staff session and asserts the "may" half (opens the console,
lists projects, creates a course, adds a module/chapter/content, edits course
settings) and the "may not" half (departments, projects, project edits,
participants, certificate assets, branding, the registry, staff accounts) — plus
one test that reads the database directly to confirm a refused write left no row
behind. Widening a permission is one line; a test that fails when the next line
widens it further is the only thing that stops it.

## P38-03 · `bootstrap-admin` refused a fresh installation — **done**

- **Estimate:** 1 h · **Review gate: human — auth**

Seeding staff broke the first-deploy ordering immediately, and the browser
suite's `global-setup` caught it because it performs the same two steps a real
host does:

> refusing: 2 staff account(s) already exist.

The refusal was on _any_ row in `admin_users`, on the reasoning that with a staff
account present the ordinary invitation path works. That reasoning assumed every
account can reach the flow that mints a super administrator. It cannot —
`canGrant` refuses a grant outranking the actor's own, which is correct, and
which makes an installation holding only a `customer_admin` an installation with
**no path to a super administrator at all** and no way to bootstrap one.

The condition is now the one the security property actually needs: refuse when
an **active super administrator** exists, because then there is another way in.
`disabled_at IS NULL` draws the same line the sign-in draws.

## P38-04 · Two harness findings, both the product being right — **done**

- **Estimate:** 1 h · **Review gate: none**

**A second factor cannot be presented twice in the same step.** The run's second
console sign-in was refused as `replayed` — RFC 6238 §5.2, and
`packages/domain/src/totp.ts` implementing it. `freshTotpCode` now waits for the
next code exactly as a person with a phone has to.

**Not every operator meets a second factor.** `super_admin` is governed by the
_platform_ policy, fixed at `required` by ADR-0012. A customer-scoped operator
is governed by their _customer's_, which defaults to `optional` — so the two
seeded accounts go straight in. The first sign-in helper assumed the super
administrator's path was the only one and threw "no second factor is enrolled
and none was offered" at a screen showing the fully signed-in console. It now
races all three outcomes.

Neither was a product defect. Both were the harness being narrower than the
system, which is the same shape as every finding in P32.

## P38-05 · The mock-data register — **done**

- **Estimate:** 2 h · **Review gate: none**

`docs/mock-data.md`: every placeholder value in the platform, with what it is,
where it lives, what replaces it and who owns that. Structured so that "work
down the Before go-live column" is a complete pre-launch pass.

The part worth reading twice is §2. Where a mock value could reach a third party
— the Ärztekammer, a physician's inbox — it is not merely marked, it is built so
it cannot: no seed writes a VNR password, so nothing seeded can authenticate a
Punktemeldung even with a plausible VNR; the demo addresses are on a reserved
domain that cannot receive mail; and the default customer's course carries no
points at all, so it produces no submission to begin with.

## Deliberately not done

**The live environment was not touched, and could not be.** This sandbox's
egress gateway answers 403 to `CONNECT` for `digitalspital.com` and
`fortbildung.digitalspital.com` — the same policy that blocks `example.com`, so
it is a general allowlist and not a block on that domain. Everything above was
built and verified against a local stack. Verifying it on `78.47.178.65` needs
somebody with access to run the three seed commands and `bootstrap-admin`, and
the exact commands are in `docs/mock-data.md` §6.

**The customer's name in a single-customer operator's app bar** stays wrong, and
is now honest about it: it shows the platform's name. The console fetches the
customer registry only for operators holding the `customer` capability, which is
the one a `customer_admin` lacks. Fixing it means putting the customer's name on
the _session_, which is a registry read from a pool that is not tenant-scoped,
under a `customers` policy checking `id = app.customer_id`. Filed rather than
bodged, and recorded in `docs/mock-data.md` §5.

**A mock course carrying mock points was not seeded for the MEDICE tenant.** The
DS demo tenant already has one, with a dummy VNR and a fictional chamber, and it
exercises the whole path through to a certificate. A second one under a
customer's real accreditation would be a course that looks reportable next to a
course that is.
