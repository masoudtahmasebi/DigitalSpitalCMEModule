# P195 — The Punktemeldung step's third state is the certificate, not a dead label

**Raised by:** the client, 04.09.2026, answering a question about two controls
sharing one name:

> _"CME-Punkte geltend machen button only appears when all of the steps in one
> course are done and the efn entry and getting the certificate is remaining, if
> that is done, the option should appear to only download the created
> certificate"_

---

## What is already right

The first half is implemented and correct. `App.tsx` defines the action once:

```ts
const claimPoints =
  state.courseComplete && state.completedAt === null ? () => { … } : undefined;
```

`courseComplete` is the server's verdict that every step is done;
`completedAt === null` is "the EFN entry and the certificate are still
outstanding". All four places that draw the control — the course overview's
progress card, the module sidebar, the passed-exam screen and the floating
mobile module — render it only when that callback is defined. So the button
never appears early and never appears twice in time.

That is §9.2 working: `POST /completion` accepts exactly this pair, so the
control cannot be offered where the API would refuse it.

## What is wrong

**Once it is done, three of the four sites render nothing, and the fourth
renders a dead label.**

`ModuleSidebar`'s `ClaimRow` has three states, and its `done` branch is:

```tsx
<p …>
  <StateIcon state="completed" … />
  {de.quiz.claim}          // "CME-Punkte geltend machen"
</p>
```

A completed step labelled with the imperative for the act that is finished, and
no route to the thing the act produced. The physician has done the work, the
Teilnahmebescheinigung exists, and the screen they are on says only that they
already claimed. The certificate is reachable — on the Zertifizierung tab — but
nothing on the page they are looking at says so. §9.4: what does the person do
next, and does the screen say so?

## The rule this settles

The Punktemeldung step has three states and the third one is the certificate:

| state  | condition                                | affordance                                     |
| ------ | ---------------------------------------- | ---------------------------------------------- |
| locked | `!courseComplete`                        | padlock, and the sentence naming what opens it |
| open   | `courseComplete && completedAt === null` | **CME-Punkte geltend machen**                  |
| done   | `completedAt !== null`                   | **Teilnahmebescheinigung herunterladen**       |

`completedAt !== null` is the same condition the Zertifizierung tab already uses
to decide between "noch nicht verfügbar" and the certificate panel, so this adds
no second reading of when a certificate exists (§9.10b).

## Where it downloads, and where it points

Not everywhere. The affordance has two forms, and the split is P176-02's own
settled answer rather than a new one:

| screen                                                | affordance                                                    | why                                                                                             |
| ----------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| module sidebar, passed-exam panel                     | **Teilnahmebescheinigung herunterladen** — a real download    | no tab is in reach; the physician is inside the player                                          |
| course-detail progress card, its floating counterpart | **Zur Teilnahmebescheinigung** — opens the Zertifizierung tab | the tab is one click away and already holds the download beside the accreditation it belongs to |

P176-02 wrote the rule for the second row and the reason for it: _"a label
promising a file would be a second promise to keep."_

It is also what stops this ticket re-creating the defect it fixes. The progress
card is a **sibling** of the tab panel, not a child, so it renders _on_
Zertifizierung — a download button there would sit beside `CertificatePanel`'s
own, with the same accessible name. That is the deploy-120 collision again, one
screen over. `App.route.test.tsx` asserts exactly one such control on that tab,
and the assertion goes red at `expected 2 to be 1` when the card is made to
promise the file.

## Why the download is a download

A control labelled _herunterladen_ that navigates to a tab holding a download
button is the false promise §9.4 exists to prevent. So the download itself is
extracted from `CertificatePanel` into one hook and called from both — one
implementation, two call sites, rather than a second copy of the blob handling
that revokes the object URL immediately because a live `blob:` URL is a readable
copy of a named physician's participation record.

## The defect this was found through

The post-deploy journey ran against production for the first time in deploy 120
— the run P194 unblocked — and both specs failed at the same line:

```
strict mode violation: getByRole('button', { name: 'CME-Punkte geltend machen' })
resolved to 2 elements
```

P190-01 added the Punktemeldung as the last sidebar row on every player and exam
page. On the passed-exam screen that sits beside the in-flow CTA: two buttons,
one accessible name, one screen. A screen-reader user hears it twice with
nothing to tell them apart.

This is the second thing §9.13 has caught that no API test could: it is not a
wrong answer, it is two controls on one screen.

## Not in scope, and why

A course that awards no CME points has no Punktemeldung row at all
(`cmePoints === null` ⇒ `claim` is `undefined`), so it gains no download row
either. Its Teilnahmebescheinigung stays on the Zertifizierung tab. That is
consistent — the row is the _Punktemeldung_ step — but it is a deliberate gap
rather than an oversight, so it is written down here.

## Three checks that could not go red, found while writing this

All three are §9.1, and each was found by breaking the product on purpose rather
than by reading the code:

1. **A rule with no caller, in the commit that added the rule (§9.3).** The
   card's download block went _inside_ `completedAt === null ? (…)`, under a
   comment of mine claiming the two states were "mutually exclusive by
   construction". That was true, and is precisely why nesting it there made it
   unreachable. The App-level test caught it on its first run — which is the
   entire argument of §9.7 for writing one.

2. **A test proving the wrong component's rule.** With the block moved to the
   sibling branch, it re-read `completedAt` to decide something `App` had
   already decided. Breaking `App`'s rule left the screen correct anyway, so the
   test that names the caller was really testing the component's own copy.
   Fixed by making the prop the single gate (§9.10b), after which sabotaging
   `App` in either direction fails the matching case.

3. **An assertion that passed on a transient state.** The collision test was
   `waitFor(() => expect(count).toBe(1))`. `waitFor` succeeds the moment its
   callback stops throwing, and there is a window before `CertificateGate`'s
   fetch resolves in which the card's control is the only one on the page — so a
   second control appearing afterwards was never observed. Restoring the
   collision on purpose left it **green**. It now waits for the panel itself (by
   the VNR, which is unique to it) and then counts.
