## P249-01 — framework errors become problem documents

**Review gate:** none · closes RUN-1

**Context**

`problem-details.filter.ts:167` sends anything that is not an `AppError`, Zod
error or `HttpException` to the 500 branch. Body-parser's 413 and 415 arrive
as plain http-errors objects, and Nest's 404 message echoes the full URL.

**Scope**

- The filter maps any error carrying a 4xx `status`/`statusCode` and
  `expose: true` to a problem document with a fixed title per status and no
  echoed message. The 404 detail names the method and path, without the query.

      contain `secret`.

## P249-03 — Redis failure is a decision, not a 500

**Review gate:** human (auth: sign-in behaviour changes) · closes RUN-3

**Scope**

- `commandTimeout` on the Redis client.
- Each rate-limit rule declares `onStoreFailure: "open" | "closed"`. Open:
  progress, quiz submit, completion and other learning routes. Closed (503
  problem document, `Retry-After`): sign-in, password reset, invitations, staff
  login. Every store failure logs once per minute and increments
  `ds_rate_limit_store_failures_total{rule,policy}`.
- `/health/ready`'s Redis ping is bounded by the same timeout.

**Acceptance criteria**

- [ ] Unit: with a store that throws, an open rule passes and a closed rule
      answers 503; the metric increments for both.
- [ ] Unit: a test fails if any `@RateLimit` rule name has no declared policy.

## P249-04 — shut down in the right order

**Review gate:** none · closes RUN-4

**Scope**

- The HTTP server stops accepting (503 while closing) before pools and Redis
  close; pools close in `onApplicationShutdown`.
- Each scheduler tracks its in-flight tick and awaits it on shutdown.
- Settles the needs-verification item on duplicate EIV filing across a
  shutdown: the plan reads `eiv.service.ts` and records whether "already
  reported" is treated as success.

**Acceptance criteria**

- [x] Integration: a request arriving after shutdown begins answers 503, not
      500; no "Cannot use a pool after calling end" is logged.
- [x] Unit: shutdown waits for a tick that is mid-run.

### The EIV question: is "already reported" treated as success after a re-claim?

**Yes — and there is no separate "already reported" answer to treat.**
Verified by reading:

- `packages/eiv-client/src/client.ts:27–30` — the specification's guarantee:
  "Idempotency is per `(EFN, VNR)`. A repeat with an unchanged payload updates
  the same record rather than double-booking, and is explicitly safe after a
  5xx whose outcome is unknown."
- `packages/eiv-client/src/client.ts:261` — `pushTeilnahme` returns
  `accepted: exchange.status >= 200 && exchange.status < 300`; a repeat is a
  200 like the first write (`packages/eiv-client/src/mock/server.ts:256–264`
  answers it `200 { affectedRows: 1, messages: ["aktualisiert"] }`; the mock
  README records that the old `BEREITS_GEMELDET` was our invention).
- `packages/eiv-client/src/reporter.ts:71` hands `push.accepted` on unchanged;
  `apps/api/src/modules/eiv/eiv.service.ts:227` throws only when
  `!push.accepted`, otherwise `recordSuccess` (`:256`).

So a submission accepted by EIV whose success row was lost at shutdown is
re-pushed after its lease and recorded as `submitted`, with one record at the
Ärztekammer. Assumed (not traced): the re-push carries the same payload, which
holds unless the course's credit flags or the completion date change between
the two attempts — in which case EIV updates the record to the new values,
which is the spec's stated behaviour. No eiv logic is changed by P249-04; the
scheduler now awaits the sweep, so the case no longer arises on an orderly
shutdown.

### Plan

**Interfaces**

- Produces: `ShutdownGate` (`apps/api/src/shared/shutdown-gate.ts`, provided
  and exported by `DbModule`) with `isClosing`, set in `onModuleDestroy`;

### Review focus

- A keep-alive connection that is mid-request when `close` is called finishes
  on open pools; whether Node then closes that socket promptly or after
  `keepAliveTimeout` is not tested here.
- `local-identity-provider.ts:118` fires `sessions.touch` without awaiting it
  and swallows its error; one started by the last in-flight request can race

  carries no body anybody renders as HTML; judged acceptable, not tested.

  with a slow but healthy bucket defers more objects to the boot drain.
