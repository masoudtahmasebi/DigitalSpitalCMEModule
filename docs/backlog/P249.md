## P249-01 — framework errors become problem documents

**Review gate:** none · closes RUN-1

**Context**

`problem-details.filter.ts:167` sends anything that is not an `AppError`, Zod
error or `HttpException` to the 500 branch. Body-parser's 413 and 415 arrive
as plain http-errors objects, and Nest's 404 message echoes the full URL.

**Scope**

- The filter maps any error carrying a 4xx `status`/`statusCode` and
  `expose: true` to a problem document with a fixed title per status and no
  echoed message. The 404 detail names the method and path, without the query.

**Acceptance criteria**

- [x] Integration: a body over `MAX_REQUEST_BODY_SIZE` answers 413
      `application/problem+json`. Red on `0208b64` (500).
- [x] Integration: `GET /no-such?token=secret` answers 404 whose body does not
      contain `secret`.

## P249-02 — an erasure is not held hostage by the bucket

**Review gate:** none (GDPR erasure; touches no certificate logic) · closes RUN-2

**Context**

`DELETE …/learners/:enrolmentId` runs inside the request's ambient transaction
while `object-erasure.service.ts:79` deletes up to 50 queued objects one by
one at 15 s each. Nine slow deletes exceed `idle_in_transaction_session_timeout`
(120 s, `db.module.ts:107`), the session is killed, and the operator gets a 500
for an erasure already committed on the side pool.

**Scope**

- The route is `@NoAmbientTransaction()`; the request drains only this
  subject's objects under one overall deadline; the backlog stays with the
  scheduler.
- `db.module.ts:99`'s comment is corrected (the false "2 GB upload" claim,
  CLAUDE.md §11).

**Acceptance criteria**

- [ ] Integration: ten queued objects with the bucket blackholed; the erase
      answers 2xx within the deadline and the erasure is recorded. Red on
      `0208b64`.

## P249-03 — Redis failure is a decision, not a 500

**Review gate:** human (auth: sign-in behaviour changes) · closes RUN-3

**Scope**

- `commandTimeout` on the Redis client.
- Each rate-limit rule declares `onStoreFailure: "open" | "closed"`. Open:
  progress, quiz submit, completion and other learning routes. Closed (503
  problem document, `Retry-After`): sign-in, password reset, invitations, staff
  login. Every store failure logs once per minute and increments
  `ds_rate_limit_store_failures_total{rule,policy}`.
- `/health/ready`'s Redis ping is bounded by the same timeout.

**Acceptance criteria**

- [ ] Unit: with a store that throws, an open rule passes and a closed rule
      answers 503; the metric increments for both.
- [ ] Unit: a test fails if any `@RateLimit` rule name has no declared policy.

## P249-04 — shut down in the right order

**Review gate:** none · closes RUN-4

**Scope**

- The HTTP server stops accepting (503 while closing) before pools and Redis
  close; pools close in `onApplicationShutdown`.
- Each scheduler tracks its in-flight tick and awaits it on shutdown.
- Settles the needs-verification item on duplicate EIV filing across a
  shutdown: the plan reads `eiv.service.ts` and records whether "already
  reported" is treated as success.

**Acceptance criteria**

- [ ] Integration: a request arriving after shutdown begins answers 503, not
      500; no "Cannot use a pool after calling end" is logged.
- [ ] Unit: shutdown waits for a tick that is mid-run.
