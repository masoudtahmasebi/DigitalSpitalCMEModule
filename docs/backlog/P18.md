# P18 · Build on the host, and stop naming a customer in platform config

Two things surfaced the moment the first real deploy was attempted: the pipeline
had never run, and the configuration it would have used still had a customer's
name in it.

---

## P18-01 · One Dockerfile, four targets, built on the host — **done**

- **Estimate:** 4 h · **Depends on:** P17-01

**Why**

The deploy pulled four images from `ghcr.io`. That is the right shape for a
fleet. For one small host it added a registry account, a token on the server, a
login step in the workflow, and a build artefact that the person debugging at
22:00 could not reproduce because it was made somewhere else.

And there were four Dockerfiles, each beginning with the same seven lines:
pull Node, enable corepack, `pnpm fetch`, copy the workspace, `pnpm install`.
Fine on a CI runner with four parallel jobs; on a 4-vCPU deployment host it is
the monorepo installed up to four times.

**Scope**

- One root `Dockerfile`: `deps` → `build-api` / `build-web` → four runtime
  targets. The four per-app Dockerfiles are deleted.
- `docker-compose.prod.yml` gains `build:` and tags each image
  `ds-education/<service>:${DS_COMMIT}`.
- `deploy.sh` builds instead of pulling; `--no-build` restarts without one.
- The deploy workflow loses its build-and-push job and the registry login.

**Acceptance criteria**

- [x] The workspace is installed **once** for all four images, not four times
- [x] The three frontends build in **one** turbo invocation, which matters
      because `@ds/portal` depends on `@ds/widget`: built separately the widget
      is compiled twice and the second copy has to be byte-identical to the
      first (`scripts/bundle-widget.mjs`)
- [x] The image tag is the commit, so `docker images` is a deployment history
- [x] `--rollback <sha>` runs images already on the disk — no rebuild, no
      registry, and one variable instead of four (the old form set four and
      forgot the portal for a while, which is a version skew between a frontend
      and the API it calls)
- [x] `--no-build` refuses when the tagged images do not exist, rather than
      failing on a missing image after the backup and migration have run
- [x] A failed build cannot take the site down: nothing is swapped until it has
      succeeded, and the script exits non-zero long before then
- [x] Build cache is pruned with the images — a host that builds fills a disk,
      and a full disk is its own outage
- [x] CI builds all four targets on every branch, so the file that the
      production host runs is verified before it ever runs it

**Three things the first real build found**, none of which could be seen from
here — there is no Docker daemon in the environment this was written in, and
the honest cost of that is that they were found on the server:

- **`ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`.** `pnpm fetch` populates
  `node_modules/.pnpm` before `COPY . .` lands the workspace on top of it; pnpm
  10 then wants to purge a modules directory whose `.modules.yaml` does not
  describe the install it is about to do, finds no TTY to ask on, and aborts.
  `ENV CI=true` is pnpm's own documented answer and is true by construction in
  a container build.
- **buildx was not installed**, so compose warned once and silently used the
  legacy builder — which cannot share the `deps` stage between targets, making
  the consolidation above worth nothing. `deploy.sh` now detects it, says what
  to install, and sets `COMPOSE_BAKE` explicitly rather than leaving the
  fallback implicit.
- **`pnpm fetch` was fetching nothing.** With only `pnpm-lock.yaml` copied, it
  printed "Already up to date", exited 0, and left a 2 MB store instead of a
  339 MB one — because the lockfile's packages hang off its `importers`, and
  `pnpm-workspace.yaml` is what tells pnpm this is a workspace root with
  importers to resolve. The build ran on for another layer and failed with
  `ERR_PNPM_NO_OFFLINE_TARBALL … helmet-8.3.0.tgz`, which reads as a broken
  lockfile or a network problem and is neither.

  Measured rather than guessed: fetching with the lockfile alone produced **0**
  packages, and with `pnpm-workspace.yaml` beside it **597**. The fix is one
  more file on the `COPY`, plus a guard that fails _at the fetch_ if the store
  comes out empty — the whole cost of this one was that a silent no-op was
  reported as success.

  **This bug predates the consolidation.** All four old Dockerfiles copied the
  lockfile alone, so none of them could ever have built. CI's `images` job runs
  unconditionally on every push and would have said so; it has presumably been
  red and unread.

- **A stale `config.env`.** `PROJECT_SLUG` had become `PORTAL_PROJECT_SLUG` and
  `ADMIN_DEFAULT_PROJECT_SLUG`, and the failure named the new spellings without
  saying that the file predated them. The preflight now lists the **required**
  keys the template has and the file does not — required only, because listing
  the optional ones buries the two that matter under a dozen that do not.

**Not done: a smaller base image.** `node:22-bookworm-slim` stays. The obvious
move is Alpine, and `@node-rs/argon2` is a native module whose musl build would
have to be in the pnpm store for `--offline` to find it. That is a change that
fails at _build_ time on the deployment host, which is exactly where a failure
is most expensive, and it cannot be verified from here. The runtime stage
already carries production dependencies only; the frontends are already
`nginx:alpine`.

## P18-02 · Why the pipeline had never deployed — **explained**

Not a defect. `deploy.yml` triggers on `workflow_run` of CI **on `main`**, and
everything so far has lived on a feature branch. A green CI run on
`claude/education-platform-roadmap-…` deliberately does not reach production.

Two things were still worth changing:

- the workflow header now says this first, because "why has it not deployed" is
  the question somebody actually arrives with;
- `docs/deployment.md` §5 gained an _If the deploy never runs_ section pointing
  at manual dispatch, which works from any branch and is what a first
  deployment needs.

## P18-03 · The console should choose its project — **open**

`ADMIN_DEFAULT_PROJECT_SLUG` is a customer's name in a file that describes an
installation meant to serve many.

It is a _default_ rather than an identity — a super administrator spans
customers, and their first screen is the customer registry, which sends no
project header at all (`createPlatformClient`). But every tenant-scoped screen
after that uses this one value, so a second customer on this installation cannot
be administered from this console at all.

**What it should be:** the operator picks a customer, then a project, and the
console sends that as `X-DS-Project`. The registry endpoint that lists
customers already exists (migration 0021, `list_customer_registry`); what is
missing is the project list under a customer, a picker in the console's chrome,
and persistence of the choice across a reload.

**Estimate:** 6 h. Touches the console's navigation, not the compliance core.

## P18-04 · CORS should be per project — **open**

`EXTRA_CORS_ORIGINS` is the union of every customer's origins across the whole
installation. MEDICE's WordPress origin is allowed to call the API on behalf of
_any_ project, not only theirs.

Which origins may embed a project's widget is a fact about that project and
belongs on the project row, beside its Keycloak binding. The obstacle is not
storage.

**The obstacle is the preflight.** A browser sends `OPTIONS` before a
cross-origin request and that preflight carries **no custom headers** — no
`X-DS-Project`. So at the moment the API must decide whether an origin is
allowed, it does not know which project is being asked about. Reading the
project from the header works for the real request and fails for the preflight,
which is worse than not doing it: the preflight is what the browser believes.

**What it should be:** an origin → project lookup, resolved the same way the
project binding already is — a `SECURITY DEFINER` function over a table of
`(customer_id, origin)`, consulted by the CORS callback. An origin allowed by
_any_ project passes the preflight; the real request still carries
`X-DS-Project` and is still scoped by RLS, so the preflight decision is about
whether the browser may speak at all, not about what it may see.

That is the correct shape and it is a migration plus a change on the request
path that decides who may call the API — **human review gate**. Written down
here rather than bolted onto a deployment fix.

**Estimate:** 5 h.

## P18-05 · A pin nothing refreshes — **done**

- **Estimate:** 2 h · **Depends on:** —

**Why**

Raised directly: _"if you pin packages to a certain version, they will not
receive the needed security updates."_

Half right, and the half that is wrong is the important half — so both are
written down here rather than settled in a chat message.

**The lockfile pin stays.** Removing it does not make the platform safer, it
makes it unknowable: the build on a laptop, the build in CI and the build on
the Hetzner box become three different programs, and "CI was green" stops being
a statement about what is running. It is also the only thing that makes a
compromised release _visible_ — a new version cannot arrive without a diff
somebody has to approve. Unpinning is how a typosquat reaches production
unreviewed.

**What was actually missing is the refresh.** Nothing in this repository ever
opened the pull request. Three specific gaps, each with its own fix:

| Gap                                                                                                            | Fix                                         |
| -------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| No mechanism proposed new versions at all                                                                      | `.github/dependabot.yml`                    |
| `pnpm audit` only ran on a push, so a CVE against an unchanged lockfile was invisible until somebody committed | CI's `schedule:` trigger, Mondays 05:00 UTC |
| A running container kept its base image forever, because `--pull` only helps when a deploy happens             | `docs/deployment.md` §6, a monthly redeploy |

**Scope**

- `.github/dependabot.yml` — three ecosystems: the pnpm workspace (one entry,
  because the lockfile is one file), Docker base images, and the workflows'
  own actions.
- `.github/workflows/ci.yml` — a weekly `schedule:`, an hour before
  Dependabot's window so the audit's verdict is on `main` when the update pull
  requests arrive. The `concurrency:` group gains `github.event_name`, so a
  scheduled run and a push to the same ref no longer cancel each other.
- `docs/deployment.md` §6 — the monthly base-image redeploy, with the table
  that says which of the four patch paths covers what.

**Acceptance criteria**

- [x] Security advisories are their own Dependabot group, ahead of version
      updates — a fix must never queue behind a major bump somebody is nervous
      about
- [x] Production and development dependencies are separate groups, because a
      vulnerable linter is a real finding and not a production exposure, and
      the queue should keep saying so
- [x] Majors are ignored by the automatic queue and read by a person. A grouped
      pull request that silently contains a NestJS major is a grouped pull
      request nobody can review
- [x] **Nothing auto-merges.** Every update runs the full suite — 485 domain
      tests, the integration suite against a real Postgres, the
      tenant-isolation suite — and a human presses the button. On a platform
      where a wrong number is a compliance incident, an auto-merged transitive
      bump is not a saving
- [x] The scheduled audit run cannot be cancelled by an unrelated push
- [x] The one path that **cannot** be automated is named as such, with the
      command and the reason: an unattended production restart on a timer is an
      unattended production outage

**Not SHA-pinning the actions, and why.** Pinning `actions/checkout` to a
commit defends against a tag being moved under us — a real attack. It also
freezes every action at whatever commit was pasted, and makes this file the
thing that has to unfreeze them. For four services on one host, a floating
major tag plus GitHub's own tag protection is the better trade. Recorded in
`dependabot.yml` itself so it reads as a decision rather than an oversight.

## P18-06 · The deploy's second job was the thing stopping the deploy — **done**

- **Estimate:** 1 h · **Depends on:** P18-02

**Why**

Bringing the first deployment up failed three times in a row without a single
byte reaching the server, and every failure was in the same place: the
`preflight` job, which existed to make failures cheap.

| Attempt | What happened                                                                |
| ------- | ---------------------------------------------------------------------------- |
| 1       | GitHub could not resolve action download info; the job never started         |
| 2       | Every step reported `success`; the job was killed at its 5-minute cap        |
| 3       | The job sat in `Set up job` for the full 15 minutes without executing a step |

Attempt 2 is the instructive one. GitHub reports a timeout as **`cancelled`**,
not `failure` — so `needs: preflight` **skipped** the deploy job, and a run in
which every check passed produced no deployment and no error anybody would
read as one.

**The split was costing a second runner acquisition** for a check that is one
SSH round trip. Two jobs is two chances to lose that lottery.

**Scope**

- The `preflight` job is folded into `deploy` as its first steps. Same code
  path, same ordering guarantee: nothing is checked out, built or migrated
  until `deploy.sh --check` has passed.
- `timeout-minutes` 45 for the whole thing. The first build on a host has no
  layer cache at all — four images from a cold `deps` stage — and without
  buildx compose cannot share that stage between them.
- Every `ssh` gains `BatchMode`, `ConnectTimeout` and keepalives. `BatchMode`
  turns a prompt into an error rather than a hang, and a hang burns the whole
  budget while looking exactly like slow work; the keepalives matter for the
  build step, which holds a connection open for minutes with nothing to say.

**Acceptance criteria**

- [x] One runner acquisition, not two
- [x] The check still runs **first** — the point of the split is preserved, only
      its cost is not
- [x] The API hostname still comes from the **host**, so the smoke test cannot
      disagree with the server about where the server is. It moves from a job
      output to a step output
- [x] The `production` environment gate now covers the check too. Arguably more
      correct: the check opens an SSH session to production either way
- [x] The reasoning is in the workflow, next to the code, because the next
      person to see a long deploy will be tempted to split it again

**What is lost, honestly.** The `environment.url` — a job cannot reference its
own steps there, and the value came from the preflight job's output. The API
hostname is printed by the step that asks the host for it, which is where
somebody debugging would look anyway.
