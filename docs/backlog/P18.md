# P18 · Build on the host, and stop naming a customer in platform config

Two things surfaced the moment the first real deploy was attempted: the pipeline
had never run, and the configuration it would have used still had a customer's
name in it.

---

## P18-01 · One Dockerfile, four targets, built on the host — **done**

- **Estimate:** 4 h · **Depends on:** P17-01

**Why**

The deploy pulled four images from `ghcr.io`. That is the right shape for a
fleet. For one small host it added a registry account, a token on the server, a
login step in the workflow, and a build artefact that the person debugging at
22:00 could not reproduce because it was made somewhere else.

And there were four Dockerfiles, each beginning with the same seven lines:
pull Node, enable corepack, `pnpm fetch`, copy the workspace, `pnpm install`.
Fine on a CI runner with four parallel jobs; on a 4-vCPU deployment host it is
the monorepo installed up to four times.

**Scope**

- One root `Dockerfile`: `deps` → `build-api` / `build-web` → four runtime
  targets. The four per-app Dockerfiles are deleted.
- `docker-compose.prod.yml` gains `build:` and tags each image
  `ds-education/<service>:${DS_COMMIT}`.
- `deploy.sh` builds instead of pulling; `--no-build` restarts without one.
- The deploy workflow loses its build-and-push job and the registry login.

**Acceptance criteria**

- [x] The workspace is installed **once** for all four images, not four times
- [x] The three frontends build in **one** turbo invocation, which matters
      because `@ds/portal` depends on `@ds/widget`: built separately the widget
      is compiled twice and the second copy has to be byte-identical to the
      first (`scripts/bundle-widget.mjs`)
- [x] The image tag is the commit, so `docker images` is a deployment history
- [x] `--rollback <sha>` runs images already on the disk — no rebuild, no
      registry, and one variable instead of four (the old form set four and
      forgot the portal for a while, which is a version skew between a frontend
      and the API it calls)
- [x] `--no-build` refuses when the tagged images do not exist, rather than
      failing on a missing image after the backup and migration have run
- [x] A failed build cannot take the site down: nothing is swapped until it has
      succeeded, and the script exits non-zero long before then
- [x] Build cache is pruned with the images — a host that builds fills a disk,
      and a full disk is its own outage
- [x] CI builds all four targets on every branch, so the file that the
      production host runs is verified before it ever runs it

**Not done: a smaller base image.** `node:22-bookworm-slim` stays. The obvious
move is Alpine, and `@node-rs/argon2` is a native module whose musl build would
have to be in the pnpm store for `--offline` to find it. That is a change that
fails at _build_ time on the deployment host, which is exactly where a failure
is most expensive, and it cannot be verified from here. The runtime stage
already carries production dependencies only; the frontends are already
`nginx:alpine`.

## P18-02 · Why the pipeline had never deployed — **explained**

Not a defect. `deploy.yml` triggers on `workflow_run` of CI **on `main`**, and
everything so far has lived on a feature branch. A green CI run on
`claude/education-platform-roadmap-…` deliberately does not reach production.

Two things were still worth changing:

- the workflow header now says this first, because "why has it not deployed" is
  the question somebody actually arrives with;
- `docs/deployment.md` §5 gained an _If the deploy never runs_ section pointing
  at manual dispatch, which works from any branch and is what a first
  deployment needs.

## P18-03 · The console should choose its project — **open**

`ADMIN_DEFAULT_PROJECT_SLUG` is a customer's name in a file that describes an
installation meant to serve many.

It is a _default_ rather than an identity — a super administrator spans
customers, and their first screen is the customer registry, which sends no
project header at all (`createPlatformClient`). But every tenant-scoped screen
after that uses this one value, so a second customer on this installation cannot
be administered from this console at all.

**What it should be:** the operator picks a customer, then a project, and the
console sends that as `X-DS-Project`. The registry endpoint that lists
customers already exists (migration 0021, `list_customer_registry`); what is
missing is the project list under a customer, a picker in the console's chrome,
and persistence of the choice across a reload.

**Estimate:** 6 h. Touches the console's navigation, not the compliance core.

## P18-04 · CORS should be per project — **open**

`EXTRA_CORS_ORIGINS` is the union of every customer's origins across the whole
installation. MEDICE's WordPress origin is allowed to call the API on behalf of
_any_ project, not only theirs.

Which origins may embed a project's widget is a fact about that project and
belongs on the project row, beside its Keycloak binding. The obstacle is not
storage.

**The obstacle is the preflight.** A browser sends `OPTIONS` before a
cross-origin request and that preflight carries **no custom headers** — no
`X-DS-Project`. So at the moment the API must decide whether an origin is
allowed, it does not know which project is being asked about. Reading the
project from the header works for the real request and fails for the preflight,
which is worse than not doing it: the preflight is what the browser believes.

**What it should be:** an origin → project lookup, resolved the same way the
project binding already is — a `SECURITY DEFINER` function over a table of
`(customer_id, origin)`, consulted by the CORS callback. An origin allowed by
_any_ project passes the preflight; the real request still carries
`X-DS-Project` and is still scoped by RLS, so the preflight decision is about
whether the browser may speak at all, not about what it may see.

That is the correct shape and it is a migration plus a change on the request
path that decides who may call the API — **human review gate**. Written down
here rather than bolted onto a deployment fix.

**Estimate:** 5 h.
