# P36 · Seed, test, and clean up whatever happened

> let's run a test that first seeds its test data, gets tested the whole flow,
> and then at the end, no matter success or fail, the seeded test data is
> removed … until you are sure all of the routes, all of the functionalities
> work correctly

---

## P36-01 · A run that leaves nothing behind — **done**

- **Estimate:** 3 h · **Review gate: none**

The browser suite already built its own database and seeded it. What it did not
do was remove it — `ds_education_e2e` survived every run, which is the beginning
of exactly the drift P32 spent a phase undoing.

`globalTeardown` now stops the stack and **drops the database**, and Playwright
runs it whether the suite passed or failed.

### Dropping, not deleting

The suite's data is a whole tenant: a customer, a department, a project, two
courses with their module/chapter/content trees, a participant, an enrolment,
progress, a certificate and an EIV submission. Deleting that by hand is a
`DELETE` per table in dependency order —
`seed-default.integration.test.ts` has exactly that list, twenty statements
long — and it rots silently the day somebody adds a table.

One `DROP DATABASE` cannot fall out of date.

### The failure case is the one that matters

A teardown that only runs on success leaves its worst state behind, which is how
a development database reaches 1096 customers. So this was verified the only way
worth trusting: **a deliberately failing test was added, the run went red, and
the database was gone afterwards.** Then removed again.

Every step is individually guarded, because a teardown that throws half-way
leaves the rest undone — and unpredictable cleanup is worse than none.
`E2E_KEEP_DATABASE=1` keeps it, for the case this is written for: something
failed and the state is the evidence.

### Verified

| Run                    | Result       | Database afterwards |
| ---------------------- | ------------ | ------------------- |
| Full suite             | 12 passed    | gone                |
| Deliberate failure     | 1 failed     | **gone**            |
| Full suite, twice more | 12 passed ×2 | gone, gone          |

## P36-02 · All the routes, from the contract — **done**

- **Estimate:** 2 h · **Review gate: none**

"All of the routes work" needs a list of all the routes, and a hand-written one
is a list somebody has to remember to extend — where the route that gets
forgotten is the new one, the one most likely to be wrong.

So the check reads `contracts/openapi.yaml` and probes **every operation it
documents**: 66 paths, 90 operations. Add a path to the contract and it is
probed on the next run, with no second place to update. The contract is already
the source for the SDK and the DTO parity test; this makes it the source for
reachability too.

Anonymously, each operation must:

- **exist** — a path documented but implemented nowhere is a real failure mode
  of a contract-first repository, where the contract is written first and
  nothing checks that the second half happened;
- **not answer 5xx** — an unauthenticated request reaching a stack trace is an
  availability bug and an information leak at once;
- **refuse, if it is under `/admin`** — no admin route may serve an anonymous
  caller.

### The negative control, which is not optional

"Documented but not implemented" is decided from the _shape_ of the 404 body.
If the problem-details filter ever rewrites unrouted 404s into the same shape as
a handler's own, that check keeps passing while detecting nothing — a check that
cannot fail, which is worth less than no check because it is believed.

So a companion test probes a path that certainly does not exist and asserts the
**same predicate** flags it. If that goes red, the route sweep has stopped
meaning anything whatever it reports. There is a second one guarding the parser:
if it silently found no operations, every assertion would be vacuous, so the
count is asserted too.

That pattern is the lesson of P32-02 applied before the fact rather than after:
a green check is only evidence if it could have been red.

### What it deliberately does not assert

What a route returns _with_ credentials. That is the API suites' job, against a
real Postgres, where fixtures exist to make the answer meaningful — 379
integration tests already do it. Duplicating it here in a browser would be a
second, weaker implementation of the same claim.

### Acceptance criteria

- [x] Every documented operation probed, generated from the contract
- [x] The missing-route detector proven able to detect a missing route
- [x] The parser proven non-vacuous
- [x] No documented route is unimplemented; none 5xxs; no `/admin` route serves
      an anonymous caller
- [x] 12 specs green, three consecutive runs, no leftover database after any
