# P36 · Seed, test, and clean up whatever happened

> let's run a test that first seeds its test data, gets tested the whole flow,
> and then at the end, no matter success or fail, the seeded test data is
> removed … until you are sure all of the routes, all of the functionalities
> work correctly

---

## P36-01 · A run that leaves nothing behind — **done**

- **Estimate:** 3 h · **Review gate: none**

The browser suite already built its own database and seeded it. What it did not
do was remove it — `ds_education_e2e` survived every run, which is the beginning
of exactly the drift P32 spent a phase undoing.

`globalTeardown` now stops the stack and **drops the database**, and Playwright
runs it whether the suite passed or failed.

### Dropping, not deleting

The suite's data is a whole tenant: a customer, a department, a project, two
courses with their module/chapter/content trees, a participant, an enrolment,
progress, a certificate and an EIV submission. Deleting that by hand is a
`DELETE` per table in dependency order —
`seed-default.integration.test.ts` has exactly that list, twenty statements
long — and it rots silently the day somebody adds a table.

One `DROP DATABASE` cannot fall out of date.

### The failure case is the one that matters

A teardown that only runs on success leaves its worst state behind, which is how
a development database reaches 1096 customers. So this was verified the only way
worth trusting: **a deliberately failing test was added, the run went red, and
the database was gone afterwards.** Then removed again.

Every step is individually guarded, because a teardown that throws half-way
leaves the rest undone — and unpredictable cleanup is worse than none.
`E2E_KEEP_DATABASE=1` keeps it, for the case this is written for: something
failed and the state is the evidence.

### Verified

| Run                    | Result       | Database afterwards |
| ---------------------- | ------------ | ------------------- |
| Full suite             | 12 passed    | gone                |
| Deliberate failure     | 1 failed     | **gone**            |
| Full suite, twice more | 12 passed ×2 | gone, gone          |

## P36-02 · All the routes, from the contract — **done**

- **Estimate:** 2 h · **Review gate: none**

"All of the routes work" needs a list of all the routes, and a hand-written one
is a list somebody has to remember to extend — where the route that gets
forgotten is the new one, the one most likely to be wrong.

So the check reads `contracts/openapi.yaml` and probes **every operation it
documents**: 66 paths, 90 operations. Add a path to the contract and it is
probed on the next run, with no second place to update. The contract is already
the source for the SDK and the DTO parity test; this makes it the source for
reachability too.

Anonymously, each operation must:

- **exist** — a path documented but implemented nowhere is a real failure mode
  of a contract-first repository, where the contract is written first and
  nothing checks that the second half happened;
- **not answer 5xx** — an unauthenticated request reaching a stack trace is an
  availability bug and an information leak at once;
- **refuse, if it is under `/admin`** — no admin route may serve an anonymous
  caller.

### The negative control, which is not optional

"Documented but not implemented" is decided from the _shape_ of the 404 body.
If the problem-details filter ever rewrites unrouted 404s into the same shape as
a handler's own, that check keeps passing while detecting nothing — a check that
cannot fail, which is worth less than no check because it is believed.

So a companion test probes a path that certainly does not exist and asserts the
**same predicate** flags it. If that goes red, the route sweep has stopped
meaning anything whatever it reports. There is a second one guarding the parser:
if it silently found no operations, every assertion would be vacuous, so the
count is asserted too.

That pattern is the lesson of P32-02 applied before the fact rather than after:
a green check is only evidence if it could have been red.

### What it deliberately does not assert

What a route returns _with_ credentials. That is the API suites' job, against a
real Postgres, where fixtures exist to make the answer meaningful — 379
integration tests already do it. Duplicating it here in a browser would be a
second, weaker implementation of the same claim.

### Acceptance criteria

- [x] Every documented operation probed, generated from the contract
- [x] The missing-route detector proven able to detect a missing route
- [x] The parser proven non-vacuous
- [x] No documented route is unimplemented; none 5xxs; no `/admin` route serves
      an anonymous caller
- [x] 12 specs green, three consecutive runs, no leftover database after any

## P37-01 · Verwaltung, in a browser, with a real second factor — **done**

- **Estimate:** 4 h · **Review gate: human — auth**

> so now if i as a user go to verwaltung and then create all entities all work?

The honest answer before this was **I did not know**. The admin _API_ was
covered thoroughly — the journey suite builds the whole hierarchy over HTTP, and
`authoring`, `hierarchy` and `moderation` cover it against a real Postgres — but
nothing had ever clicked the console's own buttons. P35 listed admin specs as
deliberately not done; this is that gap closed as far as it now goes.

### The second factor is real

ADR-0012 makes the platform policy `required`, and `super_admin` is the account
it matters most for. Setting the e2e database to `disabled` would have made this
easy to write and would have meant the browser suite never touches the control
standing between a stolen password and every customer's data.

So the harness signs in the way a person does: `bootstrap-admin` is run and its
**printed password is parsed out of stdout** — there is no flag to choose one,
deliberately, and adding one would be a way to put a known administrator
password into an installation. Then the enrolment screen's base32 key is read
off the page exactly as somebody would copy it, and codes are computed from it
per RFC 6238.

The TOTP is re-implemented in the harness rather than imported from `apps/api`,
on P32-02's reasoning: an independent statement of the same rule is the only
version worth asserting against. If the two ever disagree, that is the finding.

### What it proves

| Step                                  | Asserted                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------ |
| Sign in with password + enrolled TOTP | reaches the console, not a loop                                                            |
| The navigation                        | Kunden, Organisation, Fortbildungen, Teilnehmende present                                  |
| Create a customer                     | submit is **disabled** until name _and_ slug are given, then the row appears with its slug |

That disabled-submit assertion is not decoration: it pins down that the slug is
genuinely required rather than quietly derived from the name — and a slug
reaches a URL and cannot be changed afterwards.

### A bug in the test, worth recording

The first version used `locator.isVisible({ timeout })` to decide whether the
enrolment screen had appeared. **`isVisible()` does not wait** — it is a
question asked immediately, and the `timeout` option does not change that. It
was asked while the page still said "Anmeldung läuft …", concluded no enrolment
was offered, and failed complaining about a secret that appeared two seconds
later. `waitFor` is the waiting one.

### How far this goes, and what it does not claim

Sign-in, navigation and **the customer**. The department, project and course
below it are not clicked yet — they are covered over HTTP by the journey suite's
act 3, through the same admin endpoints these screens call.

That is a real difference and it is stated rather than implied. Extending this
file downwards is the obvious next step, and the harness it needs — a signed-in
super administrator with a working second factor — now exists.

> **Superseded by P37-02**, below: the chain now runs to the course. This
> paragraph is left standing because the limit was real when it was written, and
> a ticket that quietly grows to cover what it did not do is a ticket nobody can
> use to tell what was true when.

### Acceptance criteria

- [x] A super administrator created by the real `bootstrap-admin`
- [x] Signed in through the console with a genuinely enrolled second factor,
      with no policy relaxed anywhere
- [x] A customer created through the console's own form, and verified in the
      list it appears in
- [x] 14 specs green; the database still dropped afterwards, pass or fail

## P37-02 · The rest of the chain, clicked

**Estimate** 3 h · **Review gate: human** (auth — the sign-in helper changes) ·
`jira:` _unassigned_

### Context

P37-01 stopped at the customer and said so. The question behind it — _"if I go
to Verwaltung and create all the entities, does it all work?"_ — was still only
half answered: the customer was clicked, the three levels below it were covered
over HTTP by the journey suite and by nothing a browser had ever touched.

This walks the rest: customer → picking it in the app bar → department →
project → course, and then back up to check the course is counted against the
project it was put into.

### One test, not five

Each link needs the one above it, and the console keeps that dependency in
places a page load does not restore — the chosen customer is app state, and
every tenant screen is inert without it. Five tests would either repeat the
sign-in four times or share state through test ordering, which is the
arrangement where a retry of the second test leaves the third looking for a
customer that was never created.

It is also closer to the question. Nobody asked whether a department can be
created; they asked whether an operator gets from an empty console to a course.

### Three findings, all of them the harness being naive

**1 · A second factor cannot be presented twice in the same step.** The run's
second sign-in failed with "Der Code ist nicht korrekt oder nicht mehr gültig."
Two tests signing in within thirty seconds compute the _same_ code, and the API
refuses a counter it has already accepted (`packages/domain/src/totp.ts`,
rejection `replayed`).

That is the product being right — RFC 6238 §5.2 — and without it a code
shoulder-surfed or read out of a log stays usable for the rest of its window.
The fix is `freshTotpCode`, which waits for the next step exactly as a person
with a phone has to. It costs up to thirty seconds, which is why the chain test
carries a raised timeout rather than a shortened window.

**2 · "Fortbildungen" names two buttons on the course editor.** The sidebar
entry and the breadcrumb's first crumb share an accessible name, so a page-level
`getByRole("button", …)` matches both and fails strict mode. Playwright was
telling the truth: "click Fortbildungen" is ambiguous on that screen for a
screen-reader user too. Every navigation click now goes through the `Menü`
landmark, which says which one and leaves the crumb free to be asserted on
separately.

**3 · A panel title is not a heading.** `Panel` renders its title as a `div`,
and a project's name sits in it as a bare text node beside the Kürzel — so there
is no element whose text is the name. The assertion goes through the element
that _is_ addressable (the slug) and reads the name off its parent. Worth
recording as a small a11y debt rather than fixing under a test ticket: panel
titles should be headings, and that is a change across every screen.

### What it proves

| Step                         | Asserted                                                                   |
| ---------------------------- | -------------------------------------------------------------------------- |
| Pick the new customer        | it is offered in the app-bar picker seconds after being created (P22-05)   |
| Department                   | the Kürzel the console derived, read back — `slugify` expands ä→ae         |
| "Neues Projekt" is reachable | which only happens once a department exists                                |
| Project                      | created on **Zugangsdaten dieser Plattform**, the value P28-02 added       |
| Course                       | the project is preselected; creation opens the editor on the structure tab |
| Back on the list             | the new course reads **unvollständig** — a fresh course cannot certify     |
| Back on Organisation         | the project counts exactly 1 Fortbildung                                   |

The last two are the ones worth having. A course claiming "bereit" on creation
would issue a Teilnahmebescheinigung missing fields the Ärztekammer requires
(P28-03), and a project showing 0 next to a course claiming that project would
mean the hierarchy the console displays is not the hierarchy it wrote.

The count assertion is anchored — `/^Fortbildungen\s*1$/` — because
`toContainText("1")` would have passed on 21 and on "0 von 1".

### Slugs are read, never recomputed

The test could `slugify` each name itself and compare. Then both sides of the
assertion would come from the test, and a console that derived nothing at all
would still pass. It reads the Kürzel field back instead.

### Acceptance criteria

- [x] Customer, department, project and course all created through the console's
      own buttons, in one browser session
- [x] The customer picker offers a customer created moments earlier
- [x] Derived slugs read off the screen rather than recomputed in the test
- [x] The new course is asserted to be **not** certificate-ready
- [x] The project's course count agrees with the course list
- [x] No policy relaxed and no product code weakened to make any of it possible
- [x] 14 specs green; the database still dropped afterwards, pass or fail

### Deliberately not done

Module, chapter and content creation inside the course editor, and the quiz
editor below them. Those are the structure tab's drag-ordered tree — a different
kind of interaction from a form with two fields, and worth its own ticket rather
than a tail on this one. They are covered over HTTP by `authoring`.

Panel titles as real headings (finding 3) is filed as debt here, not fixed:
it touches every screen and belongs in a change reviewed for what it does to the
document outline, not in a test ticket.
