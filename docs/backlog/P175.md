# P175 — The deploy branch is a literal, because the default branch is not `main`

**Raised by:** the deploy this repository's own guard refused — run 106,
2026-09-03T15:04, the first execution of P173's `workflow_run` arm.

**Branch** `claude/education-platform-roadmap-3vgrqh`, from `a81c558`.

---

## What the run printed

```
EVENT_NAME:        workflow_run
REF:               refs/heads/claude/education-platform-roadmap-3vgrqh
DEFAULT_BRANCH:    claude/education-platform-roadmap-3vgrqh
TRIGGERING_BRANCH: main
SHA:               8cc65028…            (main's merge commit)
```

**This repository's default branch is the feature branch, not `main`.**

Everything else follows from that one setting, including two of my own wrong
reports:

- `github.ref` on a `workflow_run` event is the **default** branch, so every
  deploy run is labelled `claude/education-platform-roadmap-3vgrqh` in the API
  and in the UI. That labelling is what I read as "deploys are firing from the
  feature branch" (P173's opening claim). They were not: `TRIGGERING_BRANCH` is
  `main`, and `SHA` is main's merge commit, on every run.
- P173's correction — that the `branches: [main]` filter holds — is right, and
  now has direct evidence rather than timing correlation: CI runs 562 and 563 on
  the feature branch completed at 14:50:51 and 14:59:33 and produced **no**
  deploy run at all.

## The defect

P173's guard compared the triggering branch (`main`) against
`github.event.repository.default_branch` (the feature branch), so it refused a
deploy of `main`. Correct logic, wrong constant.

And the same expression was already in P155-01's manual arm, where it is
inverted in the dangerous direction: a `workflow_dispatch` of the **feature
branch** would have been _allowed_ — it is the default branch — and a manual
deploy of `main` refused. P155-01 exists because a manual run put a feature
branch on the host; on this repository its fix would have permitted exactly
that again.

`Verified:` the run log above; `release-guards.test.sh` now covers both.

## The fix

`DEPLOY_BRANCH: main`, a literal in the workflow, next to the `branches: [main]`
filter that already names it as one. The two halves of "only main reaches
production" now say the same word, and neither depends on a repository setting
that can be changed in a dropdown by somebody not thinking about deployment.

Three cases added, and the middle one is the one that matters: the feature
branch is refused _even when it is the repository default_. Watched red by
feeding the function the default branch again.

## What this does not fix

**The default branch setting itself.** `claude/education-platform-roadmap-3vgrqh`
being the default is almost certainly not intended — it decides what a clone
checks out, what a PR opens against, and what the repository shows first. It is
a repository setting, not code, so it is the client's to change; the deploy no
longer depends on it either way.

## Acceptance criteria

- [x] A deploy triggered by CI on `main` is allowed, whatever the repository
      default is.
- [x] One triggered by CI on any other branch is refused, including when that
      branch is the repository default.
- [x] A manual run may name `main` and nothing else, again including when the
      default is something else.
- [x] Watched red.

## Not done
