# P31 · The specification arrived, and five of six assumptions were wrong

> what is remaining for eiv?
>
> _[followed by the EIV-FOBI Veranstalter Swagger, the organiser page and the
> integration ticket]_

The question was answered by the person who asked it. The top item on the list
was **S24 — get the Swagger**, and the Swagger came back in the same breath.

This phase is what it cost to be wrong, and it is worth stating plainly at the
top: **the client, the mock, the tests and the audit log had all been agreeing
with each other about an interface that does not exist.** Eighteen tests were
green. The retry policy classified failures that could not occur. P30-03 — one
commit earlier — had carefully threaded a response field through the port, the
worker and the audit log so a compliance question would be answerable later.
That field is not in the real response.

## P31-01 · Reconcile the client with the published contract — **done**

- **Estimate:** 6 h · **Review gate: human — eiv**

### What was wrong

| We assumed                              | It is                                             |
| --------------------------------------- | ------------------------------------------------- |
| `POST /auth/login` with a JSON body     | `GET /fobi/veranstalter-auth/jwt` with HTTP Basic |
| the token field is `token`              | `jwt`                                             |
| the push body carries `vnr` and `rolle` | neither — the VNR is carried by the token         |
| `422` is the business rejection         | `406` is; `422` is a _format_ error               |
| success returns `{ referenz, status }`  | no reference and no status word exist             |
| a repeat answers `BEREITS_GEMELDET`     | a repeat is indistinguishable from a first write  |

Only "the JWT is presented as a Bearer token" survived.

The specification is also explicit about something we had been doing wrong in
principle: _"Maßgeblich für die technische Bewertung einer Antwort ist immer der
HTTP-Statuscode, nicht einzelne interne Response-Felder wie `affectedRows` oder
`messages`."_ The client now decides on the status code and records the body
verbatim for a human. It branches on no response field at all.

### Three capabilities the specification gave us that we had not asked for

1. **A withdrawal.** Re-send with both point flags false and
   `punkte_referent: 0`; the record survives and stays auditable. `@ds/domain`
   has computed a 7-day correction window since week 1 and **nothing could
   perform a correction** — the mechanism was listed as unknown in the mock's
   README. `retractTeilnahme` closes that.
2. **`GET /fobi/veranstalter/veranstaltung`** — the accredited period and the
   per-event point values. This turns S11 and S25 from letters to the
   Ärztekammer into `pnpm --filter @ds/eiv-harness veranstaltung`.
3. **`GET /fobi/veranstalter/gemeldetepunkte`** — what the Kammer _holds_, as
   against what we believe we sent. Our append-only log records our own
   attempts; a disagreement between the two is the one failure it structurally
   cannot see.

### And one new hazard

**A `teilnahmedatum` outside the accredited period is refused 406.** For an
on-demand Fortbildung whose Bescheid says _am 13.10.2025_, valid until
12.10.2026, that is potentially the difference between every completion being
reported and none of them being. It is why S11 is now more urgent, not less, and
why it moved from "which date do we pass to our own deadline function" to
"is the Punktemeldung possible at all".

It is reproducible locally:

```bash
pnpm --filter @ds/eiv-harness start:mock -- --beginn 2026-01-01 --ende 2026-12-31
pnpm --filter @ds/eiv-harness push -- --efn … --datum 2027-05-05   # 406, permanent
```

### Two corrections that are compliance decisions, not refactors

**`teilnahmedatum` is a German calendar date.** `formatBerlinIsoDate` is a new
pure function in `@ds/domain`, because 22:30 UTC on 9 August is already the 10th
in Berlin — and the 10th may be outside the accredited period when the 9th was
inside it. A physician completing on the last evening of the window would have
been reported against the following day and refused. One function, so the
deadline clock and the reported date can never disagree.

**`business` is not `validation`.** Both are permanent and neither may be
retried, but 406 means _the event_ is wrong — unknown VNR, locked VNR, date
outside the period — and 422 means _the payload_ is wrong: a failed EFN check
digit. They send an operator to different places, so the retry policy names them
separately and `alertAdmin` fires for both. `rate_limited` (429) joined as
**retryable**: the specification asks for backoff by name, and treating it as
permanent would abandon a Meldung the Kammer was willing to accept.

### Acceptance criteria

- [x] Auth is `GET` + Basic and reads `jwt`; the credential never reaches a body
- [x] The push body carries the four documented fields and neither `vnr` nor `rolle`
- [x] 406 → `business`, 422 → `validation`, 429 → `rate_limited`, all classified
      correctly by the retry policy
- [x] Nothing branches on `affectedRows` or `messages`
- [x] A repeat updates rather than inserts, per `(EFN, VNR)`
- [x] A withdrawal zeroes the points and keeps the record
- [x] `veranstaltung` and `gemeldetepunkte` reachable from the harness
- [x] `teilnahmedatum` is the Berlin calendar date
- [x] The mock refuses a date outside the configured period with a 406
- [x] Every gate green: 1 189 unit tests, 363 integration tests, lint, format,
      typecheck, env audit

### What this does **not** prove

Nothing in this repository has spoken to a real EIV server. We now match the
published contract field for field, which is a much better place to be wrong
from — but the remaining unknowns are the ones only a real response answers, and
they are **S25**, **S26** and **S27**.

### The lesson, recorded rather than absorbed

The mock was written from the same guesses as the client, so CI asserted the
guesses. That is not a testing gap that more tests would have closed; a contract
test is worth exactly what its fixture is worth. The mock's README now leads with
what the contract _is_ and keeps the wrong assumptions in a table at the bottom,
because the failure mode is invisible from inside and the record is the only
defence against repeating it.

`CLAUDE.md` §7 says do not guess on compliance semantics. Week 1 guessed —
under the pressure of a build with no specification available, and honestly
labelled as guesses in ADR-0005 and the mock's README. The labelling is what made
this a six-hour reconciliation instead of a rewrite.

## P31-02 · The methods existed and nothing could reach them — **done**

- **Estimate:** 8 h · **Review gate: human — auth, eiv**

P31-01 gave the client a withdrawal, an event lookup and a reconciliation. The
platform could reach none of them. That is the ninth instance of the class P28
named — **a mechanism fully built and reachable through no supported
interface** — and it arrived one commit after naming it.

### What is now reachable, and why each one earns its place

| Endpoint                                 | The failure it prevents                                                                                                                           |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /admin/courses/{slug}/eiv/event`    | A course whose accredited period has closed reports **nothing**, and nobody finds out until a physician has been shown a completed Zertifizierung |
| `GET /admin/courses/{slug}/eiv/reported` | Our log and the Kammer's disagree, and only ours is visible                                                                                       |
| `POST /admin/learners/{id}/eiv`          | A 406 an operator has since fixed stays abandoned forever                                                                                         |
| `DELETE /admin/learners/{id}/eiv`        | The 7-day correction window existed with nothing able to correct anything                                                                         |

The event lookup is the one that matters most. EIV refuses a `teilnahmedatum`
outside the accredited period, and for an on-demand Fortbildung taken across a
year that is potentially every completion — so the console now shows the period,
the point values and whether the Kammer has locked the event, on the settings
screen, before a physician is ever promised a point. It warns outright when the
event carries zero Lernerfolg points and the course claims them anyway, which is
**S25** made visible instead of documented.

### Five decisions worth defending

1. **The port's new methods are optional.** Reporting is the only thing every
   accreditation interface must do; withdrawing, describing and listing are
   things EIV happens to offer. Requiring them would make a second Ärztekammer's
   reporter impossible to write until its interface matched this one's, which is
   the opposite of what a port is for. The console degrades — no capability, no
   button.
2. **Requeue does not submit.** It resets the row and lets the ordinary worker
   take it. Submitting inline would put the retry budget, the deadline
   arithmetic and the failure classification on a second code path, and the
   whole design of P7 is that there is exactly one.
3. **Withdraw does submit, inline.** A withdrawal is a decision a named human
   took at a moment they are accountable for, and the correction window may be
   hours from closing. A scheduler between the decision and the effect would be
   the wrong trade in the other direction.
4. **The point flags are a course setting** (migration 0034), not a constant.
   Only the Ärztekammer knows what an event is accredited for and it differs per
   VNR. Both default true — see `reporter.ts` for why claiming too much is the
   safer of the two wrong answers.
5. **`withdrawn` is a status, not a deletion.** "Reported and taken back" is a
   different history from "never reported", and it refuses a name correction
   just as `submitted` does: the withdrawal zeroed the points, it did not unsay
   the name, and EIV keeps the record either way.

### A new error kind

`upstream_unavailable` → **502**. Distinct from `internal` on purpose: nothing
of ours is broken, the operator's next step is different, and a 500 would page
whoever watches our error rate for somebody else's outage. The authority's own
words go to the log; the browser gets a sentence written by hand, because
`EivError.message` is the one place an authority's response text could reach a
screen.

### Acceptance criteria

- [x] All four endpoints contract-first, SDK regenerated, DTO/SDK parity holds
- [x] The worker sends the course's flags rather than a constant
- [x] A withdrawal outside the correction window is refused with 409, not 502
- [x] A requeue clears `last_error` — leaving it would make the worker abandon
      the row again on its next pass, so the button would appear to work and do
      nothing
- [x] Reconciliation reports both directions separately and masks the EFN
- [x] No EFN and no VNR password in any response, audit row or log line
- [x] 9 integration tests against a real Postgres and the real mock; 372 in the
      suite overall
- [x] The correction-window guard verified by reverting it and watching the
      test fail
