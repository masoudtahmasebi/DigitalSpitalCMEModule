## P31-01 · Reconcile the client with the published contract — **done**

- **Estimate:** 6 h · **Review gate: human — eiv**

### What was wrong

| We assumed                              | It is                                             |
| --------------------------------------- | ------------------------------------------------- |
| `POST /auth/login` with a JSON body     | `GET /fobi/veranstalter-auth/jwt` with HTTP Basic |
| the token field is `token`              | `jwt`                                             |
| the push body carries `vnr` and `rolle` | neither — the VNR is carried by the token         |
| `422` is the business rejection         | `406` is; `422` is a _format_ error               |
| success returns `{ referenz, status }`  | no reference and no status word exist             |
| a repeat answers `BEREITS_GEMELDET`     | a repeat is indistinguishable from a first write  |

Only "the JWT is presented as a Bearer token" survived.

The specification is also explicit about something we had been doing wrong in
principle: _"Maßgeblich für die technische Bewertung einer Antwort ist immer der
HTTP-Statuscode, nicht einzelne interne Response-Felder wie `affectedRows` oder
`messages`."_ The client now decides on the status code and records the body
verbatim for a human. It branches on no response field at all.

### Three capabilities the specification gave us that we had not asked for

1. **A withdrawal.** Re-send with both point flags false and
   `punkte_referent: 0`; the record survives and stays auditable. `@ds/domain`
   has computed a 7-day correction window since week 1 and **nothing could
   perform a correction** — the mechanism was listed as unknown in the mock's
   README. `retractTeilnahme` closes that.
2. **`GET /fobi/veranstalter/veranstaltung`** — the accredited period and the
   per-event point values. This turns S11 and S25 from letters to the
   Ärztekammer into `pnpm --filter @ds/eiv-harness veranstaltung`.
3. **`GET /fobi/veranstalter/gemeldetepunkte`** — what the Kammer _holds_, as
   against what we believe we sent. Our append-only log records our own
   attempts; a disagreement between the two is the one failure it structurally
   cannot see.

### And one new hazard

**A `teilnahmedatum` outside the accredited period is refused 406.** For an
on-demand Fortbildung whose Bescheid says _am 13.10.2025_, valid until
12.10.2026, that is potentially the difference between every completion being
reported and none of them being. It is why S11 is now more urgent, not less, and
why it moved from "which date do we pass to our own deadline function" to
"is the Punktemeldung possible at all".

It is reproducible locally:

```bash
pnpm --filter @ds/eiv-harness start:mock -- --beginn 2026-01-01 --ende 2026-12-31
pnpm --filter @ds/eiv-harness push -- --efn … --datum 2027-05-05   # 406, permanent
```

### Two corrections that are compliance decisions, not refactors

**`teilnahmedatum` is a German calendar date.** `formatBerlinIsoDate` is a new
pure function in `@ds/domain`, because 22:30 UTC on 9 August is already the 10th
in Berlin — and the 10th may be outside the accredited period when the 9th was
inside it. A physician completing on the last evening of the window would have
been reported against the following day and refused. One function, so the
deadline clock and the reported date can never disagree.

**`business` is not `validation`.** Both are permanent and neither may be
retried, but 406 means _the event_ is wrong — unknown VNR, locked VNR, date
outside the period — and 422 means _the payload_ is wrong: a failed EFN check
digit. They send an operator to different places, so the retry policy names them
separately and `alertAdmin` fires for both. `rate_limited` (429) joined as
**retryable**: the specification asks for backoff by name, and treating it as
permanent would abandon a Meldung the Kammer was willing to accept.

### Acceptance criteria

- [x] Auth is `GET` + Basic and reads `jwt`; the credential never reaches a body
- [x] The push body carries the four documented fields and neither `vnr` nor `rolle`
- [x] 406 → `business`, 422 → `validation`, 429 → `rate_limited`, all classified
      correctly by the retry policy
- [x] Nothing branches on `affectedRows` or `messages`
- [x] A repeat updates rather than inserts, per `(EFN, VNR)`
- [x] A withdrawal zeroes the points and keeps the record
- [x] `veranstaltung` and `gemeldetepunkte` reachable from the harness
- [x] `teilnahmedatum` is the Berlin calendar date
- [x] The mock refuses a date outside the configured period with a 406
- [x] Every gate green: 1 189 unit tests, 363 integration tests, lint, format,
      typecheck, env audit

### What this does **not** prove

Nothing in this repository has spoken to a real EIV server. We now match the
published contract field for field, which is a much better place to be wrong
from — but the remaining unknowns are the ones only a real response answers, and
they are **S25**, **S26** and **S27**.

### The lesson, recorded rather than absorbed

The mock was written from the same guesses as the client, so CI asserted the
guesses. That is not a testing gap that more tests would have closed; a contract
test is worth exactly what its fixture is worth. The mock's README now leads with
what the contract _is_ and keeps the wrong assumptions in a table at the bottom,
because the failure mode is invisible from inside and the record is the only
defence against repeating it.

`CLAUDE.md` §7 says do not guess on compliance semantics. Week 1 guessed —
under the pressure of a build with no specification available, and honestly
labelled as guesses in ADR-0005 and the mock's README. The labelling is what made
this a six-hour reconciliation instead of a rewrite.
