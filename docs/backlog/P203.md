# P203 — The widget wrote no address until the learner navigated

**Raised by:** the client, 07.09.2026, with the address bar in the screenshot —
_"i just clicked on a course in the frontend, and you can see the url is still
`…/dscme/` which is the url for the base of the module in wordpress."_

---

## I looked in the wrong place first

They had reported this once before and I checked the **admin console**, found
its routing complete and correct, and said I could not reproduce it. That was
true and useless: the report is about the **widget**, on a customer's WordPress
page. Their second message named it, and the defect was there.

## The cause

The widget has two effects. One **reads** the fragment on load and sets
`addressApplied.current = true`; the other **writes** the address whenever the
screen changes, and returns early while that flag is false.

`addressApplied` is a `useRef`. A ref does not re-render and is not a
dependency — so the moment the read effect flips it, the write effect has no
reason to run again: `screen`, `tab` and `addressCourseSlug` are all unchanged
since mount.

A learner who opens a course and stays on Übersicht therefore never gets an
address. One who clicks a tab does, because `tab` changes and the effect finally
runs. **That is why every earlier sighting of this looked like it worked** — the
reporter had navigated before looking at the URL.

Reproduced before changing anything, as a catalogue embed with no fragment:

```
expected '' to be '#ds/kurs/adhs-akademie-adult'
```

The empty string is the client's screenshot.

## The fix, and the rule it made explicit

`course.data` joins the write effect's dependencies, so it runs in the same
commit as the read — declaration order puts the read first, which sets the flag.

That exposed a rule the old behaviour was keeping **by accident**. The widget
must not rewrite a fragment belonging to the host page: `<ds-lms>` mounts inside
a customer's WordPress site beside anchors that were there first. Before this,
`#kontakt` survived because the flag simply had not been set when the effect
last ran. Now that the effect runs on load, the rule has to be stated — an empty
hash or one of ours may be replaced, anything else may not.

`decode` decides what "ours" means, which is the same reader the load effect
uses.

## Watched red

| sabotage                        | result                                                   |
| ------------------------------- | -------------------------------------------------------- |
| revert the dependency           | the new case fails — the reported defect                 |
| drop the foreign-fragment guard | `ignores a fragment that belongs to the host page` fails |

The second is the more valuable of the two: it is a rule that was true by
coincidence and is now true on purpose.
