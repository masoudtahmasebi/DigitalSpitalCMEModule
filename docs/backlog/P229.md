# P229 — fifteen gates that could not stop a merge

Found while confirming where a new check would run (P228-03). It is not about
the admin redesign and is not in that stack.

---

## P229-01 — the defect

CLAUDE.md §9.11 states the rule in one direction:

> `pnpm verify` is the local equivalent of CI and must stay that way. A check
> that runs only in CI is a check the person writing the code does not run.

That sentence was earned by **P41-03** and fixed by adding `check:sdk` to
`verify`. Nobody then looked the other way.

Derived mechanically rather than by eye — matching each `verify` step against
the text of every workflow — **16 of the 32 steps in `pnpm verify` were named
in no workflow at all.** One of those, `check:sdk`, is covered by a CI step
spelled differently (_"Verify generated SDK matches the contract"_ regenerates
and diffs; `check-sdk.mjs`'s own header says so). `check:runtime-config` is
**not**: CI's _"The console's runtime config is generated, and refuses bad
input"_ runs the entrypoint with explicit `-e` flags and tests the script's
behaviour, while the script asserts that `docker-compose.prod.yml` **supplies**
every value the entrypoint requires — the property P44-02 was written for, and
a different one.

So **fifteen checks could not stop a merge:**

```
check:i18n            check:copy             check:runtime-config
check:egress          check:local-ports      check:focus-ring
check:backlog         check:csp              check:seed-overwrites
check:content-lock    check:eiv-settings     check:docs-commands
check:aria-props      check:screen-intros    check:design-tokens
```

(The last three exist on the admin-redesign branches, not yet on `main`.)

They ran when somebody happened to type `pnpm verify`, and nowhere else.
`main` is protected by CI, not by anyone's habits.

### Why this is worse than it sounds

Each entry in CLAUDE.md §9 became a script _because a defect reached the
client_, and §9.11 says so explicitly: _"Three of the entries above became
scripts in `scripts/` and steps in `pnpm verify`."_ Every one of those is on
the list above.

| Check                   | The class it guards                                                                      |
| ----------------------- | ---------------------------------------------------------------------------------------- |
| `check:seed-overwrites` | a seed silently replacing an operator's typed course values on **every deploy** (§9.10b) |
| `check:csp`             | the CSP header class that blocked **every video upload** for months (§9.13)              |
| `check:eiv-settings`    | a §2 human-review area — EIV                                                             |
| `check:docs-commands`   | §11's _"Run once: `sudo deploy.sh --install-timers`"_, which answered `unknown option`   |
| `check:focus-ring`      | the accessibility floor §3 calls non-negotiable                                          |

This is §9.1's first form — _"the check is not run where the work happens"_ —
except that the work that matters here is the **merge**, and the checks were on
the wrong side of it.

### It is also the answer to a review point

> **CI green output must be trustworthy.**

A green CI was being read as _"the repository's checks passed"_ when fifteen of
them had not run.

## P229-02 — the fix: one home, two callers

A list of twenty checks written into `ci.yml` by hand would reproduce the
defect `check-shell.mjs` exists for:

> This step used to name fourteen files for shellcheck by hand and then run the
> tests, while `pnpm check:shell` ran only the tests. … six scripts and six test
> files had never been linted, two of them written the same day.

So the checks get **one home** — `pnpm check:static`, twenty-one steps in
`package.json` — and two callers:

- `pnpm verify` runs `pnpm check:static`;
- `ci.yml`'s `verify` job runs `pnpm check:static`, in a new **Repository
  checks** step.

§9.10b at the level of a script list. `verify` drops from 29 hand-listed steps
to 10.

`check:shell` stays outside `check:static` because it needs shellcheck
installed, which `check:static` must not assume — it has to run anywhere node
does. CI runs it in its own step, as before.

**Ordering matters and is documented in the workflow:** the step comes after
`Build`, because `check:copy` imports `packages/copy/dist` and `check:sdk`
regenerates against the contract.

## P229-03 — `scripts/check-ci-parity.mjs`

One home and two callers is an arrangement, not a guarantee. This makes it
enforced, in **both** directions:

1. every step of `pnpm verify` is reached by a workflow — directly, or via
   `check:static`, or by an exemption naming the CI step that covers it;
2. every `pnpm check:*` a workflow runs is reachable from `pnpm verify` — which
   is §9.11's original wording, still enforced.

It is inside `check:static`, so it runs on both sides of the gate it describes.

### Five rules, five sabotages, all red

| Sabotage                                                    | Reported                                                                                                            |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| move `check:roles` out of `check:static`, blank its CI step | "`pnpm check:roles` … no workflow runs, so it cannot stop a merge"                                                  |
| delete the whole `Repository checks` step                   | "`pnpm check:static` is in `verify` and in no workflow, so all 21 checks inside it can be pushed past"              |
| add `check:csp` to CI and remove it from `check:static`     | "runs in a workflow and is not reachable from `pnpm verify`, so it fails ten minutes after a push"                  |
| gut `check:static` to one step                              | "parsed fewer than five steps … would cover almost nothing and this check would still pass. Refusing to agree."     |
| leave an exemption nobody needs                             | "a workflow runs it under its own name, so the exemption is unused. Remove it, or the list stops meaning anything." |

The fourth is the §9.1 guard on the checker itself: a `check:static` reduced to
nothing would leave a workflow "running the checks" and covering none of them.
The fifth is the `ANSWERS_WITH_NOT_FOUND` guarantee from P225 in another place —
an exemption list must not be able to become a mute button.

### And the checker's own defect, found by its first run

**It went green for the wrong reason.** `pnpm test:integration` is covered in CI
as `pnpm test:integration:ci`, and the boundary test is written to tell those
apart — but `ci.yml` line 262 is a **comment** reading

> `pnpm test:integration` is the developer's command

and a backtick is not a name character, so the step looked directly named and
the exemption was never consulted. The output said _"0 covered under another
name"_ where 1 was correct.

That is `check-deadlines`' defect from CLAUDE.md §11 — _"It was matching prose
in doc comments"_ — and the **third** time in one lineage of checks
(`aria-props.mjs`, `screen-intros.mjs`, here). Whole-line comments are stripped
from the workflow before scanning; only whole-line, so a `#` inside a command
can never truncate it.

The shape, since it apparently needs writing down a third time: **a checker that
greps a file is reading the explanation as well as the instructions, and the
explanation is where the thing being looked for is most likely to be named.**

## Does turning fifteen gates on break `main`?

No. Every one was run against `origin/main` at `31e8db2` before the change, and
then `pnpm check:static` was run end to end on this branch after a cold build:

```
$ pnpm check:static
… 21 lines, every one green …
check-ci-parity: 10 verify step(s), of which 21 are inside `check:static` and
run by 2 workflow(s); 1 covered under another name, none unreachable from a
merge gate.
exit 0
```

Two of the fifteen reported errors on a first attempt and both were artefacts of
the throwaway worktree rather than findings: `check:copy` needs
`packages/copy/dist`, which an unbuilt checkout does not have, and `check:sdk`
needs the sdk workspace's own `node_modules`. Both are green in a real
checkout, and the CI step is placed after `Build` for exactly that reason.

## What this ticket does not do

- **It does not add a new check to the repository.** Fifteen existing ones start
  being enforced; one new script enforces the arrangement.
- **It does not change any check's rules**, so nothing that passes today starts
  failing.
- **It does not touch the `integration`, `images`, `security`, `codeql` or
  `dependency-review` jobs.**
- **It does not update CLAUDE.md §9.11**, whose wording is now half a rule. That
  is a documentation change the client should see rather than one absorbed in a
  commit, and it is named here instead.

## Acceptance criteria

- [x] The gap derived mechanically, not by eye, with the two false positives adjudicated individually
- [x] The checks given one home and two callers, rather than a hand-copied list
- [x] The CI step placed where its dependencies are satisfied, with the reason in the file
- [x] Parity enforced in both directions by a check that runs on both sides
- [x] Five rules, five sabotages, each watched red
- [x] The checker's own prose-matching defect found and fixed before shipping
- [x] Every newly-enforced check verified green against `main` first
