# P89 — the deployment that did not happen, and the library that does not know

**Status:** P89-03 built; P89-01 and P89-02 specified, not started.
**Raised by:** three things found on 17.08.2026 while releasing P87/P88 — one by
watching a deploy fail to start, one by the client asking a question, and one by
the post-deploy journey failing on the installation while passing on the rig.

---

## P89-01 — a re-run does not re-fire the deploy (1 h)

### What happened

CI on `main` failed on `1c8df78`. The failure was GitHub's own CDN answering
429/503 while a runner downloaded `docker/setup-buildx-action` — three times
running, on a job that had passed twice on the identical tree twenty minutes
earlier. Re-running the failed job turned CI green.

**And the deployment never started.** No `Deploy` run appeared at all.

`deploy.yml` triggers on:

```yaml
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
    branches: [main]
```

The `workflow_run` event fired once, when CI first completed — as a **failure**,
which the job's `if` correctly skipped. Re-running the failed job did not
produce a second `completed` event the Deploy workflow acted on. CI's badge says
success, `main` is green, and nothing is deployed.

### Why it matters more than it looks

The symptom is **nothing happening**, which is the worst symptom a pipeline can
have. A failed deploy is loud; an absent one is silent, and looks exactly like a
deploy that succeeded to anybody not watching the Actions tab. On this project
that is §9.9's territory: _"a report about a running system is a report about a
commit"_ — and here the commit everybody believes is live is not.

It also means **any transient CI failure on main costs a release**, permanently,
until somebody notices. GitHub's CDN had a bad half-hour; the platform silently
stopped deploying.

### The work

`workflow_dispatch` already exists on `deploy.yml` and is what was used to get
this release out. That is the workaround, not the fix — it depends on somebody
knowing to do it.

Options, in preference order:

1. **Key the deploy off the run's final conclusion**, not the first completion.
   A scheduled or `check_suite`-driven reconciler that asks "is the newest green
   CI run on main deployed?" and acts if not. Costs a cron; makes the pipeline
   self-healing.
2. **Fail loudly instead of silently.** A step that compares
   `ds_build_info{commit=…}` on `/metrics` against `main`'s tip and alerts when
   they diverge for more than N minutes. Does not fix it, but converts silence
   into a message.
3. **At minimum**, document the dispatch in the runbook — and note that a README
   sentence is a mechanism nobody runs (§9.9's strongest form), so this is the
   floor rather than the answer.

Option 1 is the only one that makes the deployment a property of the repository
rather than of somebody's attention.

### The related irritant, worth fixing at the same time

Five pushes in twenty minutes spawned ten workflow runs (`push` **and**
`pull_request` for each), and they compete for the same action downloads —
which is what tipped GitHub into rate-limiting us in the first place.

CI **already has** a `concurrency` group with `cancel-in-progress: true`, so
this is not the missing-cancellation case it looks like. The group is keyed on
`${{ github.event_name }}` as well as the ref, deliberately — a scheduled run
and a push must not cancel each other — and the side effect is that a branch
with an open pull request runs the whole suite twice per push, in parallel, for
identical trees.

The fix is to stop triggering on `push` for branches that a pull request
already covers, keeping `push` for `main` (which is what the deploy hangs off).
That is a change to when the gates run, so it belongs in a ticket rather than in
a release commit.

## P89-02 — the Mediathek does not know about files uploaded before it existed (2 h)

### What the client asked

> _"should we clean the db from content and re seed it with real content from
> the s3 so there are also no placeholders, and the mediatheck is also correct?"_

The second half is a real defect. The first half should not be done — see below.

### The defect

`media_assets` rows are written by exactly one path: `rememberAsset`, called
from `adminCompleteUpload`. Nothing backfills.

So every object uploaded **before migration `0043`** is in the bucket, is
referenced by a live course, and is **invisible in the Mediathek**. The library
screen honestly reports what it knows; what it knows is "files uploaded since
the library was built". An operator looking for the intro video they uploaded in
July finds an empty shelf and concludes the feature is broken.

Same shape as §9.3 in a new place: the mechanism exists and the data it is
supposed to describe was never handed to it.

### The work

A backfill that inserts the missing rows, from two sources:

1. **What the courses reference** — `contents.file_url`, `poster_url`,
   `captions_url` and every `media_sources[].url` that is an `s3://` reference.
   These are certainly in use and certainly this customer's.
2. **What the bucket holds** under the customer prefix, for objects referenced
   by nothing — orphans from a cancelled upload. Listing them is the only way
   the Mediathek can offer to tidy them up, which is half its purpose.

Idempotent on `(customer_id, storage_key)`, which `rememberAsset` already is, so
running it twice is safe and running it after every deploy is an option.

`file_name` and `mime_type` come from the object's own metadata where the bucket
has it, and from the key's extension where it does not. `byte_size` from the
listing. `title` and `alt_text` stay null — those are somebody's words, not
something to invent.

**Run it as a migration step or as `dsc` command?** As a command the deploy
calls, not a SQL migration: it has to talk to object storage, and a migration
that needs S3 credentials is a migration that fails on a machine that has none.

### Watch it go red

Seed a course whose content references an `s3://` key with no `media_assets`
row — which is exactly the production state — assert the Mediathek lists
nothing, run the backfill, assert it lists one. Without the first assertion the
test passes on a library that was never broken.

## P89-03 — the journey found its course by luck, and the luck ran out — **done**

### What happened

The manual deploy of `1c8df78` succeeded. `journey.spec.ts` passed against the
installation. `zwei-module.spec.ts` — running for the first time post-deploy —
failed one line into the physician's half:

```
Locator: locator('li').filter({ hasText: 'E2E Zwei Module xea41g' }).first()
Expected: visible — element(s) not found
```

Everything before it passed on the same installation in the same minute: the
course was built with two modules, both exams, an Evaluationsbogen, points, a
stamp and a signature, and the console confirmed **„Diese Fortbildung ist
veröffentlicht und für Teilnehmende sichtbar."**

### Why the two specs disagreed

The catalogue is `ORDER BY title` (`catalog.repository.ts`) at **ten per page**
(`PER_PAGE` in `CourseList.tsx`), with no text search. The DS Test tenant keeps
its data on purpose (P71-04), so it holds one more course after every run this
suite has ever made.

_"E2E **Z**wei Module …"_ sorts after every _"E2E **F**ortbildung …"_ and after
almost anything else a course is likely to be called. Once ten titles sort
before it, it is on page two — and a locator that only looks at page one reports
it as absent, which is indistinguishable from the course never having been
published.

The difference between the passing spec and the failing one is a letter. That is
the tell that neither was ever testing what it looked like it was testing:
`journey.spec.ts` has been finding its own course **because F is early in the
alphabet**, and would have started failing on its own the moment the tenant grew
past its position.

### Which makes it §9.13's rule about the rig, applied to data

> _The rig must be shaped like the deployment — including what the deployment
> has not been given yet._

The local rig's tenant holds one or two courses, so the catalogue there has no
second page at all and the assumption is invisible. This is the same shape as
the harness bucket that answered every CORS preflight permissively (P70-01): a
fixture whose convenient state is precisely the state production is not in.

### What was built

`apps/e2e/support/catalogue.ts` — `openCourseFromCatalogue(page, title)`, used
by both journeys. It walks the catalogue's own pagination until it finds the
card, opens it through the card rather than through a page-level `.first()`, and
fails with the four causes named in the order to check them.

**It pages rather than deep-linking, deliberately.** Opening `#/kurs/<slug>`
would be one line and would delete the property the assertion exists for — _the
published Fortbildung is in the physician's catalogue_ is what fails when
publishing does not take, when the delivery-type tab is wrong, and when the
validity window excludes today.

### Watch it go red

`apps/e2e/tests/katalog-seiten.spec.ts` builds a two-page catalogue in the
browser with `setContent` and walks it, because **the paging branch cannot
execute on the local rig** — one or two courses is never a second page. A branch
no local run can take is a branch first exercised on the server, which is the
position the helper exists to get out of (§9.1).

Verified by neutering the loop to a single page: two of the three tests fail,
including the message assertion. Restored, all three pass.

The other half of the evidence is the installation itself: this is a check that
is currently **red on production data and green on the rig**, so the next
post-deploy run is the red-to-green that matters.

### What is not fixed, and is a product question rather than a test one

A physician on a tenant with two hundred courses has the same problem the helper
has, and the same tools: ten at a time, alphabetical, filters for Thema and
Altersgruppe, and no search. MEDICE launches with one course, so this is not on
the critical path — but it is the shape of a report that will arrive from the
second customer, and it is worth naming here rather than being surprised by it.

## What was explicitly **not** done, and why

**Cleaning the database and re-seeding.** Asked for, and refused with reasons:

`enrolments`, `content_progress`, `quiz_attempts`, `evaluation_responses`,
`certificates` and `eiv_submissions` all hang off content. They are the evidence
for CME points already awarded. ADR-0004 and the append-only audit rule exist so
that evidence cannot be casually destroyed, and `deleteContent` already refuses
while participations exist — a wipe would be bypassing a refusal the product
enforces on purpose.

It is also unnecessary for the stated goal. A course is replaceable in place:
retract to draft, replace the content, republish. The audit trail survives and
it is the path an operator would take anyway.

**And a trap worth naming:** the MEDICE seed ships a **placeholder VNR and VNR
password**. Replacing the videos without replacing those produces a course that
looks finished and whose Punktemeldung the Ärztekammer will refuse. Content and
accreditation data are two separate jobs, and the second one needs the
Anerkennungsbescheid rather than a guess (§7).

### What is needed before real content can go in

Open questions for the client, none of which are ours to answer:

- which files, in which bucket and prefix;
- the course structure — how many modules, which video where, and a
  Lernerfolgskontrolle on each or only the last;
- the real VNR, VNR password, points, category and validity window from the
  Bescheid;
- **whether anybody has real participation on `/medice` yet** — replacing
  published content changes a course under people who are part-way through it.
