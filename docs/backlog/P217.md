## P217-01 — the progress ring, measured

The client (DEP-39): _"the progress circle is too small relative to the widget"_.

Measured from `screens/page-02.png`, which is **1400 × 1834** against a 1920
frame, so every figure is the measured pixel × 1.3714:

|                 | design                    | built            | verdict       |
| --------------- | ------------------------- | ---------------- | ------------- |
| card width      | 283 px                    | 288 px (`18rem`) | matches       |
| card padding    | ~22 px                    | 20 px (`p-5`)    | matches       |
| **ring outer**  | **145 px**                | **96 px**        | **too small** |
| **ring stroke** | **16 px** (11.0 % of box) | **6 px** (6.3 %) | **too thin**  |

So the ticket is right about the ring and the card is already the drawn width —
"too wide" is a proportion, and the ring was what made it read that way.

Two changes, not one: scaling the box alone would have produced a correctly
sized ring that still reads as a thin hoop. The box is `h-36 w-36` (144 px), the
viewBox stays 80 so one unit is 1.8 px, the stroke is 8.9 units (16.0 px) and
the radius 35.5 units — outer edge at 143.8 px, within a pixel of the drawing.
The centre numeral goes `text-2xl` → `text-4xl` with it.

### The test that broke, and why it was right to

`CourseHeader.test.tsx` held `const RING_RADIUS = 34` — a second copy of a
number that lives in `ProgressRing` — and failed with
`expected 89.2 to be close to 85.5`. That says nothing about the property under
test: the arc is still exactly 40 % of the circle. It now reads the
circumference out of the rendered `stroke-dasharray`, so the assertion is "the
arc is 40 % of _this_ ring" and cannot go stale.

Checked both ways: with the old ring restored it still passes (it no longer
depends on the size), and with the arc fed the content percentage instead of the
module fraction it still fails. The property survived; only the duplicated
constant went.

## P217-02 — DEP-38's second half, now answerable

> Tab border should be this - #007f95

Measured from the same render:

|                          | measured             | as hex    |
| ------------------------ | -------------------- | --------- |
| tab panel's outline      | `rgb(163, 208, 216)` | `#a3d0d8` |
| active tab's outline     | `rgb(220, 236, 239)` | `#dcecef` |
| the teal everywhere else | `rgb(0, 127, 149)`   | `#007f95` |

`#007f95` is confirmed as the brand teal — it is the dominant saturated colour
on the page by a wide margin (66,262 samples), which is why P216 changed the
palette to it.

**But the outline the ticket names is not that colour in the drawing.** It is a
light teal, and the panel's is a shade darker than the tab's — two values where
we use one token (`border-brand-100`). This is also the outline DEP-28 was filed
about.

So the ticket and the authority disagree, and it is not mine to settle (§7):

- **If the render wins**, the outline stays light and `brand-100` could be split
  into the two measured values.
- **If the ticket wins**, panel and tab both become `#007f95` — a strong teal
  outline the drawing does not have, and DEP-28's "one outline" property still
  holds because both sides move together.

Raised with the numbers rather than guessed. Guessing is how P204, P208 and
P209 each became the next report.
