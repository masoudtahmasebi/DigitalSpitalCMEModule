# P224 — the admin console redesign, PR B: the authoring tree stops being button soup

The second of the three pull requests `docs/backlog/P219.md` sequences, and like
PR A it is **not to be merged or deployed by this session**.

It is the first PR in the series that changes what a screen looks like. Where
PR A moved code, this one is the work order's actual complaint — _"visually
weak, difficult to scan, and not pleasant to use"_ — answered on the two screens
an operator spends their day in.

---

## How the decisions were made, which is the part worth reading first

**By looking at the console.** The e2e rig renders it in Chromium, so a
throwaway spec signed in as `verwaltung@ds.example`, walked the screens at
1440 px and photographed them. Every change below is against something visible
in those screenshots, and every one was re-photographed afterwards.

That is worth stating because the alternative was available and tempting:
reasoning about a screen from its source. The authoring tree's source does not
look like button soup. The screenshot does — the controls outweigh the titles
they belong to by area, and the eye lands on a grid of bordered boxes and has to
hunt for the course.

Nothing has been copied from TailAdmin, Mosaic or Admin One. P219 §5's licence
gate is still unreached, because nothing here needed it.

---

## P224-01 — a fourth button weight, and why the console only had three

`Button` had `primary`, `secondary` and `danger`, and used `secondary` for
everything that was not _the_ action of a screen. On the authoring tree that is
every control on every row: a module carries **Bearbeiten**, **Löschen** and two
reorder buttons; a chapter adds a `<select>`; a content row two more. Ten
modules is upward of sixty bordered boxes.

`quiet` is the missing weight — a real button, focusable and labelled exactly as
before, that draws its border only on hover or focus. It is what Linear, Stripe
and Vercel use for per-row actions, and the reasoning is the one `Row`'s own
header already gives for preferring hairlines to cards: **a repeated control is
not information, and spending a border on each repetition buys nothing.**

Applied to: the three **Bearbeiten** toggles, the quiz editor's open button,
every `IconButton`, and `ConfirmButton`'s **unarmed** state. That last one is
one change at twelve call sites, and all twelve are a destructive action on a
row — delete this course, revoke this account, discard this submission. Arming
it is what makes it loud; the armed state is untouched, `danger` and filled.

`secondary` keeps its job: a real alternative beside a primary action. `quiet` is
never _the_ action of a screen.

### Two things found while doing it

**`IconButton` had no `CONTROL_FOCUS`.** That is not "the focus ring was
invisible" — `CONTROL_FOCUS` begins with `outline-none`, so without it the
button kept the browser's own default outline and a keyboard user could see it.
What was true is that it was the one control in the console focusing in a
different colour from every other, and that matters more now the resting border
has gone: the hover border and the focus ring are the only two things left that
say this is a control. (I wrote the stronger claim first and corrected it after
reading `CONTROL_FOCUS` — §11.9, a comment is a claim.)

**The `<select>` is already right.** "In anderes Modul verschieben" looked like a
§9.2 candidate — a control offering to move a chapter to another module when
there may be only one. It is guarded: `modules.length > 1`. Checked before
asserting; it is only visual weight, and it is quiet now like the buttons beside
it.

## P224-02 — three levels of tree, three weights of title

Every row drew its title at `text-sm font-semibold text-gray-900` — module,
chapter and content alike. The only thing distinguishing three levels of
hierarchy was an eleven-pixel uppercase eyebrow and a left rule, and on a real
course that is forty rows of identical-looking text against the question a
person actually has on this screen: _where does this module end?_

Indentation alone does not answer it — `RowList`'s `flush` already indents, and
by the third level that indent is a few pixels against a row 1,100 px wide.

So `Row` takes a `level`, and it is three steps and no more: a fourth would be a
size nobody can tell from its neighbour, and the tree is only ever three deep.

| level     | used for                    | title                                      |
| --------- | --------------------------- | ------------------------------------------ |
| `section` | a module                    | `text-[0.9375rem] font-bold text-gray-900` |
| `group`   | a chapter                   | `text-sm font-semibold text-gray-900`      |
| `item`    | a content — **the default** | `text-sm font-medium text-gray-800`        |

`item` is the default because most rows in the console are flat lists with no
hierarchy to express, so every other screen is unchanged.

## P224-03 — the course list, and a check that can go red

Three things in the courses table, all visible in the before screenshot:

- **The title was permanently underlined.** In a table of two columns of prose
  that reads as raw hypertext and competes with the data beside it, and a long
  German course name wrapped to two underlined lines — the widest thing on the
  screen. The underline is on hover and focus now, where it is doing the work of
  saying "this is clickable"; at rest the colour and weight already do.
- **`0 von 0 abgeschlossen` wrapped** after the numbers, so a row carrying it was
  two lines tall while its neighbours were one. That is the jagged-list defect
  the client reported as DEP-42 on the learner's catalogue, in the console.
- **CME points and the VNR were proportional figures.** A VNR is seventeen
  digits compared against a Bescheid; points are compared down the page.
  `tabular-nums` on both.

### The check

`apps/e2e/tests/konsole-layout.spec.ts`. Everything in this PR is visual, and a
visual change has the §9.1 problem in its purest form: **the 348 admin tests
pass identically before and after it**, so nothing in the repository would
notice it being reverted. jsdom has no layout, so a component test could only
assert that `whitespace-nowrap` is in a class string — a test about Tailwind
that would stay green if the cell were given a width that made it wrap anyway.

Sabotaged by removing `whitespace-nowrap`:

```
Error: a completion count wrapped: the cell is 36.0 px tall against a 20.0 px
       line, so it is on two lines and its row is taller than its neighbours
```

and 20.0 px with it.

**Two things about that check are deliberate.**

It measures the **text's** box through a `Range`, not the cell's. The first
version measured `cell.getBoundingClientRect()` and reported 65 px against a
20 px line — "this wrapped" — on a cell that does not wrap: a `<td>` stretches to
the tallest cell in its row, and the title column wraps. A measurement of the
wrong box is a check that goes red for a reason unrelated to what it claims,
which is deploy 131's class from the other side.

And it does **not** assert that the rows are equal to each other, which is the
property somebody would reach for first. On the rig's two courses both counts
wrap identically, so that comparison is two equal numbers before the fix as well
as after. A check that cannot go red is not evidence, and saying so is cheaper
than shipping one.

  they are untouched here and that is stated rather than implied.

## P224-07 — the two questions the review asked, measured at 390 px

The review of PR B asked two things that a 1440 px screenshot cannot answer:

> The quiet destructive controls need a touch/mobile discoverability check at
> 390 px … `whitespace-nowrap` needs responsive overflow evidence.

Both are now in `apps/e2e/tests/konsole-layout.spec.ts`, and answering them
found more than they asked for.

### What holds, and is asserted

| Property                                                  | Measured at 390 px                                               | Assertion                                                                                                                                                      |
| --------------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The **page** does not scroll sideways on the courses list | `scrollWidth` 390 = `clientWidth` 390                            | red when `Table`'s `overflow-x-auto` wrapper is removed: _"the page scrolls sideways at 390 px: 1011 px of content in a 390 px viewport"_                      |
| The table scrolls **inside its own box**                  | table 1,011 px inside a 358 px container with `overflow-x: auto` | asserted directly, because the page-level pass depends on a container nothing else named                                                                       |
| The quiet delete is a tappable target                     | **94.6 × 38 px**, padding 14/8, border 1 px                      | red at `py-0`: _"95 × 22 px … below the 24 × 24 CSS px of WCAG 2.5.8"_                                                                                         |
| `quiet` keeps a border box at rest                        | `border-top-width` **1 px**                                      | red at `border-0`: _"has no border box at rest (0 px)"_ — the failure mode is somebody reimplementing `quiet` as bare text, which shrinks the target invisibly |
| The reorder controls on the authoring tree are on screen  | right edge 65–116 px in a 390 px viewport                        | red with `ml-[400px]`: _"ends at 465 px in a 390 px viewport"_                                                                                                 |
| …and are tappable                                         | **32 × 32 px**                                                   | red at `h-5 w-5`: _"20 × 20 px, below the 24 × 24"_                                                                                                            |

**32 × 32 passes WCAG 2.5.8 Target Size (Minimum) and does not reach the
44 × 44 of 2.5.5 (Enhanced, AAA).** Stated rather than quietly asserted at the
lower bar.

On the discoverability question itself: at rest `quiet` is `text-gray-700`,
`font-semibold`, `text-sm` in a `px-3.5 py-2` box — a weighted label in a
button-sized box, not a hyperlink, and the same box as the bordered variant it
replaced, which is why `border-transparent` was chosen over `border-0`. Whether
that _reads_ as tappable is a judgement a number cannot settle, so it is a
manual acceptance step with a screenshot rather than a green check.

### What does not hold — two responsive defects, measured

Neither is caused by `quiet`, and both were found by looking at 390 px rather
than by any check:

1. **The courses list's per-row delete is off the screen at 390 px.** Measured
   `left: 901, right: 995` in a 390 px viewport — **511 px past the right
   edge**, reachable only by dragging the table sideways. A bordered button at
   x = 901 is equally unreachable, so this is the table's column layout, not
   the button's weight. This is the "remaining responsive action-cell problem"
   already on the open list.

2. **Twelve buttons on the course workspace end beyond 390 px**, including four
   of the tab bar's own entries — `Einstellungen` (282 → 405), `Referenten`
   (409 → 514), `Evaluationsbogen` (518 → 671), `Teilnehmende` (675 → 800) —
   and the chapter rows' `Bearbeiten` (294 → 411), which the module-select
   pushes out. The page itself does not overflow (`scrollWidth` 390), so each
   sits inside a horizontally scrolling strip and there is no indication that
   more exists to the right.

Both are **recorded rather than asserted**: a red gate on a known defect stops
the build without fixing anything. They need a ticket that decides what a row of
actions becomes below `md` — a stacked cell, an overflow menu, or a screen of
its own — and that is a design decision, not a rider on a PR about button
weights.

### A harness defect found on the way, which is the §9.13 shape on the rig

The first 390 px test failed with

```
signing in as verwaltung@ds.example reached neither enrolment, nor a code
prompt, nor the console. The page says: Menü DS Education ds · Verwaltung
(Demo) EN Abmelden Fortbildungen Alle Fortbildungen dieses Kunden …
```

on a page whose own text, quoted in its own error, **was the console**.
`signInToConsole` waited for a sidebar entry, and `Shell` renders the `<aside>`
as `hidden md:block` — so below 768 px the sidebar does not exist until the top
bar's **Menü** button is tapped. Every browser test until now ran at 1440 px,
where that is never true.

So the harness was shaped like one deployment and no browser test had ever
signed into the console at phone width. `signInToConsole` now races the
hamburger alongside the sidebar entry, and `openMenu()` opens the drawer when a
test sets a narrow viewport (a no-op at desktop widths, because the toggle is
`md:hidden`).

**And the fix's own second half** (§9.1): the race was fixed, the helper got
past it, and the _final_ `await expect(console_).toBeVisible()` twenty lines
down threw twenty seconds later on exactly the same cause. A fix is not
verified until the thing it fixes is observed — one green run of the failing
case, not one reading of the patch.
