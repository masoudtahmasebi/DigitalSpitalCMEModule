# P97 — the WordPress integration, from a browser on the real site

**Raised by:** the client, 19.08.2026, from the MEDICE staging install, with two
rounds of browser console output and this decisive sentence:

> _"i enabled the checkbox for Token-Endpunkt aktivieren and deactivated the
> checkbox for Token-Endpunkt aktivieren and both produce the same set of
> errors"_

That sentence is the whole ticket. A setting that changes the system and changes
nothing an observer can see is not a setting anybody can reason about.

**Estimate:** 2 h. **Actual:** 2 h.

---

## What was actually working, and it matters

Both rounds are evidence that P96 landed:

- `ds-lms.js` was fetched from `widget.digitalspital.com`, executed, and
  `connectedCallback` ran. No CSP refusal, no 404, no plugin update needed.
- The token request came from **inside the bundle** (`ds-lms.js:12751`), which
  only happens when the element carries `token-endpoint` — so plugin 1.0.0 was
  installed and P96-03's attribute path was live.
- Between round one and round two the CORS failures became `401`s, so adding the
  origin to the project took effect exactly as P94-04 intended.

## P97-01 — two 404s a browser cannot tell apart

`GET /wp-json/ds-lms/v1/token` answers 404 in two unrelated situations:

| Condition                          | Status | Body                       |
| ---------------------------------- | ------ | -------------------------- |
| Feature flag off — no route at all | 404    | `{"code":"rest_no_route"}` |
| Route ran, nothing holds a token   | 404    | `{"token":null}`           |

A console prints `404 (Not Found)` for both. So toggling the checkbox produced
identical output, the natural reading — "the endpoint is missing" — was the
wrong one, and a day went into the wrong hypothesis.

Each half was defensible alone. The flag-off 404 is deliberate and correct: a
403 would confirm the route exists (§9.5). The no-token 404 carried no
explanation on the stated grounds that "whether the Keycloak plugin holds one is
not the caller's business". **That reasoning does not survive contact with who
the caller is.** This caller has presented their own session cookie and a valid
`wp_rest` nonce. They are the subject. "WordPress is holding no Keycloak token
for you" is a fact about their own session and discloses nothing about anybody
else's — §9.5 is about not being an oracle to a _stranger_, and I applied it to
the one person entitled to the answer. That is §9.10 in its exact form: a
refusal that was correct and useless.

So: `{"token":null,"reason":"no_token_held"}`, and — because a person debugging
this is looking at a settings screen, not a JSON body — a third line in
**Verbindung prüfen**:

| State                              | What it says                                          |
| ---------------------------------- | ----------------------------------------------------- |
| Flag off                           | switch it on, in those words                          |
| Flag on, no token for this session | names the `ds_lms_access_token` filter and the README |
| Flag on, token present             | the module can sign in                                |

It reports on the **administrator's own** session, because `current()` takes no
user and must not — and the message says so rather than implying it speaks for
the physicians. That limit does not matter for the question that was actually
unanswerable, which was _which of the two 404s is this_.

Watched go red: removing `reason` fails 1 check; the three diagnostics states
have their own checks and each names a different failure.

## What the report was really about, and it is not ours

`DS_LMS_Token_Source::current()` returns null because there is nothing to read.
`class-ds-lms-token-source.php` has said so in its own header since 28.07, after
we read MEDICE's plugin:

> There is **no login handler, no session write, no cookie write, no user meta
> write and no refresh-token handling anywhere in it.** … **So there is nothing
> for this file to read.**

`keycloakwordpressplugin` obtains an access token by password grant, uses it for
a userinfo lookup, and drops it. Every symptom in the report follows from that
one fact: no stored token → our 404 → no bearer → the API's 401 on `/courses`
and `/enrolment`.

**This is S2, arriving.** It is now recorded in `docs/show-stoppers.md` as
observed rather than predicted, and it is on the critical path: until MEDICE add
one `add_filter( 'ds_lms_access_token', … )` — and persist the token at login if
their handler does not already — no physician can start a Fortbildung from
WordPress. Nothing on our side is broken and nothing on our side can fix it,
which is precisely why it needs to be stated plainly rather than absorbed.

The second half of S2 applies the moment the token does flow: at Keycloak's
default five-minute lifespan a 25-minute module outlives it several times and
progress stops being credited mid-video (measured, P62-04). The realm needs
**30 minutes minimum**.

## Still to do in this ticket

**P97-02 — a refused origin is invisible to us.** When the API refuses an
origin, nothing is logged and no metric moves; the only evidence is a line in a
browser console on somebody else's site. Worse, `EmbedOriginRegistry#load()`
catches every error silently, so "no customer has configured an origin" and "the
query failed" are the same observable state — with every widget on the platform
refused either way. That is §9.1's third form and it is not acceptable in the
component that decides whether a customer's site works.

# P98 — the MEDICE login, read correctly at last

**Raised by:** the client, 19.08.2026, by supplying `keycloakwordpressplugin`
**and** the theme, with the sentence that settles the design:

> _"there is no wordpress login for any physician at all, there is a doccheck
> login and medice login that we have build on top … you should not use anything
> from wordpress, you should only use the medice keycloak login"_

**Estimate:** 3 h. **Actual:** 3 h. **Touches auth — `needs-human-review`.**

---

## The correction, which is mine

`docs/show-stoppers.md` S2 has said since 28.07 that MEDICE's plugin persists no
token, so there was nothing for us to read and the integration was blocked on
their developer. **That was wrong, and wrong in a way this repository has a
standing check against.** I read `keycloakwordpressplugin`, found no session
write in it, and concluded about the system. The login is in the _theme_:

```php
// theme/functions/login-class.php
$tokenResponse = Keycloak::getAccessTokenByUnamePass($username, $password);
$token         = $tokenResponse['data']['access_token'];
$userInfo      = Keycloak::getUserInfoByToken($token);
$data          = array_merge($tokenResponse['data'], ['userinfo' => $userInfo['data']]);
self::storeIntoSession($data);              // → $_SESSION['LOGIN_SESSION']
```

`$tokenResponse['data']` is the whole token endpoint response, so the session
holds `access_token`, `refresh_token`, `expires_in` and `refresh_expires_in`.
The grant's scope includes **`offline_access`**, so the refresh token is an
offline one — which also softens S2's other half: the 30-minute realm lifespan I
raised the same morning is a comfort rather than a blocker, because a refresh
path exists.

**Nothing was needed from MEDICE. Three weeks of "blocked on the client" was our
own reading error.**

## The defect that was actually in the way

**No physician is a WordPress user.** Across the theme and the plugin there is
no `wp_signon`, no `wp_set_auth_cookie`, no `wp_insert_user`.
`Profile::isLogedIn()` is `isset($_SESSION['LOGIN_SESSION'])`.

Our plugin gated three separate things on `is_user_logged_in()`, and every one
of them was false for every physician:

| Where                          | What a physician got                   |
| ------------------------------ | -------------------------------------- |
| `Renderer::token_attributes()` | an element with no way to authenticate |
| `Token_Endpoint::permitted()`  | refused                                |
| `Token_Source::current()`      | null                                   |

It also explains the one thing in the client's report that did not fit: the
token endpoint was called at all, which needs `is_user_logged_in()` to be true —
they were signed in as a WordPress administrator as well. A physician would not
have reached even that.

All three now ask the only question with meaning on that site: **is there an
access token in this request's session?** The key is a setting, defaulting to
`LOGIN_SESSION`, because it belongs to the host's login code and not to us.

The user-meta strategies are deleted rather than left. `get_user_meta` needs a
user id, there is never one, so they were §9.2 and §9.3 at once — an affordance
the system can only refuse, and a rule nothing calls. A test now asserts that a
WordPress user carrying a token in user meta is _not_ a source.

## The security change, stated rather than absorbed

The endpoint used to answer WordPress users; it now answers browsers on this
origin holding a MEDICE session. That is a widening, and three things follow:

- **Same origin is now the boundary, so it is checked here** rather than
  inherited from WordPress's CORS defaults. A present-and-foreign `Origin` is
  refused by us, where a test can see it; absent is allowed, because browsers
  omit it on same-origin GETs.
- **The nonce is not a defence for this endpoint any more, and the code says
  so.** WordPress binds a nonce to a user id; with no user, every anonymous
  visitor shares one value within a tick, and the page carrying it is public. It
  is kept because it stops accidents, not attackers. A comment claiming
  otherwise would be §9.10a — a comment naming one consequence of two.
- The endpoint still cannot return a token the caller's own session did not
  already contain. There is no user parameter, no lookup by id, and nothing
  minted.

## The next failure, defused before it happened

Our API validates every bearer against the realm's JWKS with the project's
`keycloak_issuer` **and `keycloak_audience`** as required claims. A perfectly
valid MEDICE token whose `aud` does not match — the default for a Keycloak
client with no audience mapper — is refused, and reaches the browser as a 401
that looks exactly like "not signed in". That is the same shape as everything
else in P96–P98: a correct refusal that is unreadable from where the person is
standing.

So **Verbindung prüfen** decodes the token this site actually produces and
prints its `iss` and `aud` for copying into the project. Two public registered
claims, and nothing else: the subject, the email and the token itself are
dropped, with tests asserting each absence.

## Verification

106 → **128 plugin checks**. Four guards broken and watched go red:

| Broken                                          | Red |
| ----------------------------------------------- | --- |
| same-origin check neutered                      | 7   |
| session gate removed from `permitted()`         | 8   |
| whole JWT payload printed instead of two claims | 8   |
| session key hard-coded, setting ignored         | 7   |

The suite starts a real PHP session before its first byte of output, because on
this site identity _is_ the session — a suite that cannot start one cannot test
the plugin, and `session_start()` after output fails silently.

## Still open

**P97-02**, unchanged: a refused origin is invisible to us, and
`EmbedOriginRegistry` swallows load errors so "nobody configured an origin" and
"the query failed" are one observable state.

# P99-02 — the session outlives the token, and nothing renewed it

**Raised by:** the client, 19.08.2026, from the live site:

> _"my user was still logged in on the wordpress website for medice keycloak,
> but our system said your session is done, please try again, and it had the try
> again button, and that did not work"_

**Estimate:** 2 h. **Actual:** 2 h. **Touches auth — `needs-human-review`.**

## The mechanism

`theme/functions/login-class.php` writes the Keycloak token response into
`$_SESSION['LOGIN_SESSION']` **once, at login**. `grep -r refresh_token` across
the theme and `keycloakwordpressplugin` returns nothing but unrelated Alpine.js
variables. Nothing renews it, ever.

A Keycloak access token lives five minutes by default. A MEDICE session lives as
long as the browser does. So the **normal** state of that site an hour after
anybody signed in is a live session holding a dead token:

|                      | says                                       |
| -------------------- | ------------------------------------------ |
| The website          | signed in — menus, headers, everything     |
| Our widget           | _Ihre Sitzung ist abgelaufen_              |
| **Erneut versuchen** | re-reads the same dead token, 401, forever |

That retry is §9.2 with the widget on the wrong side of the rule: a control that
could not ever succeed. And this is the same defect P62-04 measured in August at
a 60-second lifespan — recorded then as "a lifespan to negotiate with MEDICE"
when it was actually a missing refresh on a token we could already see.

## The fix, and why nothing was needed from MEDICE

The `refresh_token` has been in the same array all along, and the login grant
requests **`offline_access`**, so it is designed to outlive the access token.

- A token expired — or within `RENEW_MARGIN_SEC = 60` of it — is refreshed
  before it is handed over. Not zero: a token with four seconds left passes
  every check here and is refused by the API by the time it arrives, which
  presents as an intermittent, unreproducible sign-out.
- The new pair is **written back into the session**. That is what the login
  wrote, so every other part of the site reading the token gets the fresh one; a
  refresh kept privately in the plugin would leave the rest of the site holding
  a corpse.
- The client id, secret and realm come from `Keycloak::getSettings()` — MEDICE's
  own plugin — so there is exactly one client secret on the site and nothing to
  keep in step. No plugin means no refresh, reported as such.
- A refusal from the realm (a revoked offline token) yields no token. That
  person must genuinely sign in again, and the realm's error text reaches
  neither a screen nor a log: it is about their credential.

## What made it invisible, now fixed

Nothing on any screen mentioned a clock. **Verbindung prüfen** now shows the
minutes remaining on the current token and whether renewal is possible at all —
`KEINE Erneuerung möglich` in those words when the Keycloak plugin is absent.

## Verification

128 → **147 checks**. Broken four ways and watched go red:

| Broken                                          | Red |
| ----------------------------------------------- | --- |
| hand the expired token over (the defect itself) | 10  |
| refresh but never write back to the session     | 2   |
| renewal margin of zero (the four-second race)   | 1   |
| refresh on every call, healthy token or not     | 19  |
| diagnostics without the renewal line            | 2   |

The fixture is now a real-shaped JWT with an `exp`, because a token that cannot
be parsed is correctly treated as expired — and a fixture that was not a JWT
would have exercised the expiry path in every unrelated check by accident.

## Still open, and it is the widget's half

`Erneut versuchen` is now usually right, because the refresh usually works. When
it cannot — a revoked offline token — the widget still offers a retry that
cannot help, and its message still says "laden Sie die Seite neu", which does
not help either: the reload reads the same session. That needs the endpoint's
`reason` (P97-01) to reach the copy, and it is a widget change and therefore a
deploy. Raised as **P99-03** rather than folded in silently.
