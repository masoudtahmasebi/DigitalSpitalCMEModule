## P181-01 — A command a document promises must exist

`pnpm check:docs-commands`, in `pnpm verify` and in CI.

CLAUDE.md §11's own table records the failure:

> **"Run once: `sudo deploy.sh --install-timers`"** — the script's `case` had no
> such option and answered `unknown option`.

Nothing caught it and nothing could have: `pnpm verify` runs code, and **prose is
not executed.** The sentence was read by a person at the moment they needed it
to work, which is the worst possible time to find out it never did. It is §9.9's
corollary pointed at ourselves — there, a setting a document tells a human to
apply is a setting that is not applied; here, a command a document tells a human
to run may not be a command.

The check reads fenced code blocks and inline code, in the documents somebody
reads in order to _do_ something, and resolves:

- `pnpm <script>` and `pnpm --filter <package> <script>` against the root and
  workspace `package.json` files (pnpm's own verbs are excluded by name);
- `node scripts/<file>.mjs` and bare `<file>.mjs` against the filesystem;
- `<file>.sh --option` against the script, requiring the literal option to be
  **handled**, not merely mentioned in a usage block.

It deliberately does not read `docs/backlog/`, `docs/adr/` or the changelogs.
Those record what happened, and a correct entry there may name a command that
was rightly removed afterwards — P96 explains a defect whose cause was
`pnpm wp:bundle`. Requiring history to stay runnable would either break the
check or, far worse, pressure somebody into editing the history so it passes.

That exclusion is this script's own §9.1 exposure, so:

- `MINIMUM_DOCUMENTS` and `MINIMUM_COMMANDS` fail the check if the scan
  collapses — `check-eiv-settings.mjs` earned those the hard way, reporting
  success while reading one config file;
- the one historic exemption carries its reason in the source, and a **stale**
  exemption is itself a failure. An exemption nobody can see is how a check
  quietly stops covering the thing it was written for.

_Verified:_ broken four ways and watched to go red — a `pnpm` script that does
not exist, `./deploy.sh --install-timerz`, an exemption whose sentence was
removed, and the extraction neutered so the floor fires. Green again after each.
It reads 168 commands across 51 documents.

## P181-02 — `pnpm db:snapshot` / `db:restore` / `db:snapshots`

`pnpm db:dev:reset` gets you back to _seeded_. There was nothing that got you
back to **the state you were in** — the course built by hand, the enrolment
half-way through a video, the twenty minutes of clicking that reproduce a bug.

`scripts/devbackup.mjs` is a `pg_dump --format=custom` into a git-ignored
`db/snapshots/`, restored by dropping and recreating the database rather than
loading over it, because the one thing the command exists to give is a _known_
state. It uses libpq's environment variables so no password reaches a command
line, validates the snapshot name because it becomes a filename, and falls back
to the postgres container's own client where the host has none — the same
fallback `devdb.mjs` documents, for the same reason.

**It is not the production backup system and must never become it.** That one
encrypts with the deployment's key, uploads off-host, prunes on a retention
policy and is restorable by `dsc run --rm backup restore`; it is built around
the data being a hundred physicians' CME records. This one is built around the
data being `Anna Mueller`. Keeping them apart is the point: the production tool
must not grow a "local mode" that skips encryption, because that flag would then
exist on the machine that holds real records.

_Verified:_ against a real database — created a table, took a snapshot, dropped
the table, restored, and read the row back. The traversal guard, the missing
snapshot and the missing argument were each driven and each refused.
