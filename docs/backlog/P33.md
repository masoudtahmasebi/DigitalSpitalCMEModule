# P33 · The alarm was watching the clock and not the queue

> so this is not yet ready for production? can you please complete the complete
> cme for production release?

The question was worth asking, and answering it properly meant re-reading the
one mechanism whose failure is invisible by construction: the thing that is
supposed to shout when a Punktemeldung is not going to happen.

It had two defects. Neither is a crash, neither shows in a test that was
passing, and both would first have been noticed in production — one as silence,
the other as noise.

---

## P33-01 · A submission that has stopped is not a submission running late — **done**

- **Estimate:** 4 h · **Review gate: human — eiv**

### Defect 1 · Six days of silence on a submission that will never retry

`alertLevelFor` decides on one input: hours until `report_due_at`. `warning` at
48 h, `urgent` at 12 h, `overdue` after. That is exactly right for a row the
worker is still retrying — it may yet succeed, and time is the only thing that
decides when a human needs to care.

It is wrong for a row the worker has **abandoned**. `EivService.abandon` writes
`failed_permanent`, and there is no path back to `queued` except an operator
pressing requeue. The reasons are ordinary configuration mistakes:

| `last_error`                  | What happened                                    |
| ----------------------------- | ------------------------------------------------ |
| `missing_vnr_password`        | nobody set the VNR password on the course        |
| `live_submission_not_allowed` | `EIV_ALLOW_LIVE` unset with a non-local endpoint |
| a 406 from the Kammer         | unknown VNR, locked VNR, date outside the period |

Such a row was **silent for six of its eight days**, then arrived as `warning`
with 48 hours left — indistinguishable from a retry running late, when in fact
it had stopped on day one and had been waiting for a person the whole time.

Six days is the difference between setting a password and invoking the
Bescheid's paper fallback.

`eiv-alert.service.ts` had already written the argument against itself: the
console shows `needs_attention`, "that is a **pull** signal: it works exactly as
long as somebody opens the console." A dead row is precisely the case where
nobody does, because nothing is moving to draw attention to it.

**The fix.** A fourth level, `blocked`, raised the moment the queue stops
working on a submission, at any distance from the deadline. The clock levels
still follow if nobody acts — "this stopped" and "this stopped and there are
twelve hours left" are different messages, and the second is not implied by the
first.

The domain takes the fact as a boolean (`willNotRetry`), not the status string:
`failed_permanent` and `window_closed` are spellings this schema chose, and a
second Ärztekammer's reporter would choose others. `@ds/domain` stays free of
the database's vocabulary, which is what `CLAUDE.md` §4 invariant 4 is for.

### Defect 2 · Every withdrawal would have raised three false alarms

`unreported_eiv_submissions` has selected `status <> 'submitted'` since
migration 0011, when reported and unreported were the only two outcomes.

P31-02 added `withdrawn` — a Meldung a named human deliberately retracted inside
the 7-day correction window, which EIV keeps as a record with its points zeroed.
It is the _opposite_ of unreported: it was reported, then taken back on purpose.

Under that predicate a withdrawal is permanently a candidate. Nothing ever moves
it to `submitted`, so it would escalate `warning`, `urgent` and `overdue` at
whoever is on call, about a decision somebody made deliberately and recorded in
the audit log.

The first alarms this platform raised in production would have been three false
ones per withdrawal — against a service whose own header says an alerting path
that cries wolf is one somebody mutes, "and a muted alert is worse than none
because it is believed to be working."

Migration 0035 replaces the predicate with a **positive list** of the statuses
that genuinely await reporting. Deliberately positive: the next status added to
the enum should have to think about this query, rather than a `<>` chain
silently including it.

### What this says about the class of bug

Both defects were introduced by work that was itself correct. `withdrawn` was
right to add. The clock-based ladder was right when every row in it was
retrying. What neither change did was revisit the query and the rule that
consumed the thing they changed — and because an alarm's failure mode is that
nothing happens, no test noticed.

The pattern is worth naming, because P28 named its cousin: **a mechanism whose
correctness is only observable when it fires**. It needs tests written from the
outside — "given a row in this state, does anybody find out?" — not from the
inside of the function that happens to exist.

### Acceptance criteria

- [x] A submission abandoned with days of window left raises immediately
- [x] It raises **once**, and the clock levels still escalate afterwards
- [x] A retrying submission at the same distance still raises nothing
- [x] A withdrawn Meldung raises nothing, ever — asserted against real Postgres,
      because the predicate is SQL
- [x] The alert carries no EFN, no name, no course title (ADR-0004) — the
      existing payload test still holds
- [x] The log line for `blocked` does not read as a deadline
- [x] 565 domain tests, 495 API unit tests, 374 integration tests

### Not done, deliberately

**The console does not show the alert level.** It shows the submission's status,
which is the fact; the level is the escalation history, and it lives in the
append-only audit log where it cannot be reset. Adding a fifth badge to the
participant list would be a second place to read the same thing, and P28 is the
record of what two implementations of one fact cost here.
