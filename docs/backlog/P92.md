## Why this needed a new rig rather than a re-read

Every browser test this suite had drives `apps/portal`. The portal is **not**
how MEDICE's physicians reach the course, and it differs in all three of the
ways that matter:

|            | portal (tested since P68)            | WordPress (untested until now)      |
| ---------- | ------------------------------------ | ----------------------------------- |
| credential | `ds_participant` cookie, same origin | **bearer token** from a provider    |
| identity   | `local` — our own password           | **`keycloak`** — MEDICE's realm     |
| origin     | the API's own host                   | **a different origin** — CORS rules |

That is CLAUDE.md §9.13 with the names changed: the tests called one channel
and the customer uses the other. The PHP had tests (53 checks, all passing),
and they run the plugin's logic against a WordPress stand-in — they cannot see
what a browser does with the markup it emits.

## P92-01 — a WordPress-shaped page, and a Keycloak to sign into it — **done**

`apps/e2e/support/wordpress.ts` serves the page the plugin renders, in the
plugin's own tag order, from `127.0.0.1:4182` — a different origin from the API
on `:3100`. `apps/api/dist/dev-keycloak.js` (P52-02) mints **really signed**
tokens the API verifies against a real JWKS; nothing is bypassed.

What is faithful, because each is a failure mode:

- **the tag order** — an inline classic script assigns `element.tokenProvider`
  _before_ the deferred module defines the element. That is what
  `#upgradeProperty` exists for, and getting it wrong renders "nicht korrekt
  eingebunden" inside a **closed** shadow root: invisible, with no failed
  request to notice.
- **a separate origin**, so `ALLOWED_ORIGINS` genuinely decides.
- **the token endpoint's shape** — same-origin `fetch`, `X-WP-Nonce`, a `token`
  field — so a change on either side shows up here.
- **the shipped bundle** — `apps/widget/dist/ds-lms.js`, the same file
  `pnpm wp:bundle` copies into the plugin.

### What the browser proved works

1. The element upgrades, keeps the pre-upgrade `tokenProvider`, and calls the
   API. 2. `GET /branding` answers **200 cross-origin**. 3. With a role granted,
   the catalogue renders the seeded course. 4. A visitor whose WordPress session
   has ended is told _"Ihre Sitzung ist abgelaufen…"_ — and specifically **not**
   "nicht korrekt eingebunden", which would send them to the wrong person.

Two of my own assertions were the §9.1 trap and were corrected before commit:
`toContain("Fortbildung")` passed against the 403 (the hero says
"Fortbildungsbereich"), and reading the text once instead of polling caught a
spinner one run in three.

## P92-02 — nobody can be a WordPress learner yet — **the finding**

With a valid, verified Keycloak token for a physician the platform has not seen
before:

```
200 /branding
403 /courses?deliveryType=on_demand&page=1&perPage=10
```

and the widget renders _"Es ist ein Fehler aufgetreten — Bitte versuchen Sie es
später erneut."_

**Why.** The guard provisions the _person_ on first sight — `provision_learner`
writes `users` and `user_identities` — and then asks `resolveTenantContext` for
a grant. Nothing writes one. `user_roles` for a learner is inserted in exactly
one place, `participant.repository.ts`, which is the console's **"Zugang
anlegen"** and creates a **`local`** credential. By ADR-0013 a credential is
never matched to an existing person by email, so the same physician arriving
through MEDICE's Keycloak is a _different_ person with no grant.

P1-02 specified "provision just-in-time on first sight" and its acceptance
criteria cover the user row, the concurrency and the realm key — none of them
mentions authorisation. The identity half was built; the authorisation half was
never specified.

**This is not something to guess at.** It is the auth plane (CLAUDE.md §2 human
review) and it is a policy question, not a coding one:

- **Auto-grant on first sight** — any physician whose token verifies against the
  project's realm becomes a `learner` of that project's customer, audited. That
  is what "MEDICE's Keycloak is the gate" implies, and it is how a launch with
  unknown physicians can work at all. It also means MEDICE's realm membership
  _is_ the entitlement, which somebody has to agree to in writing.
- **Explicit provisioning** — an import, or the console listing pending
  first-sights for approval. Safer, and it needs an operator in the loop before
  each physician can start.

The test records today's behaviour and says so, so the day this is decided the
assertion fails in the file whose subject is this channel.

## P92-03 — `ALLOWED_ORIGINS` must name MEDICE's site

The rig allows the WordPress origin, which models a correctly configured
installation. Whether the **installation** lists MEDICE's origin cannot be
checked from here — and getting it wrong is the worst-shaped failure this
platform has: the browser refuses, the API logs nothing, and the widget shows a
generic error.

Recommend: the deploy prints the configured origins, the way it already prints
the tenant paths (§9.10 — put the answer where an operator who is already
trusted can see it).

## P92-04 — the bundle is a build artefact the plugin folder does not carry

`assets/ds-lms.js` is gitignored and written by `pnpm wp:bundle`. A plugin folder
copied to the site without that step ships **no widget**; one copied without
re-running it after a platform release ships an **old** widget against a new
API. The element already writes `data-ds-build` on itself — the plugin should
surface it, and the release checklist should name the step.

## Still open from before, and the one most likely to bite

**S2, the token's lifespan.** The provider supports `{ refresh: true }` and the
SDK calls it once per 401; whether MEDICE's WordPress session actually holds a
refresh token is still unconfirmed. At Keycloak's default five-minute access
token, a 25-minute lecture outlives it several times. The widget degrades
honestly — _"Ihre Sitzung ist abgelaufen — Ihr Fortschritt wird derzeit nicht
gespeichert"_ — which is the right message and still a physician losing the
watch time that decides their CME points.
