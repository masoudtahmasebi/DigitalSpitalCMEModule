## P106-03 — three levels that did not say which one you were in

## P106-04 — every module row printed its number twice

Not reported. It is in the P106-03 screenshot, on every row:

```
Modul 2 – Modul 3 – Pharmako…
Modul 3 – Modul 2 – Diagnostik
Modul 4 – Modul 5 – Komorbidi…
Modul 5 – Modul 4 – Psychoth…
```

`moduleHeading` prefixes the position unless the title already carries **that
same number**. These modules were reordered in the console without their titles
being retyped, so every title carried a _different_ number, was judged
unnumbered, and got a second one.

The position now wins and the title's number is dropped: the position is what
orders the list, gates it and counts it. `moduleTopic` loses its ordinal
parameter — it existed only to insist the number matched, which is the opposite
of what its one caller wants.

**The test asserted the defect.** `does not treat another module's number as
this one's` expected `"Modul 2 – Modul 1 – Grundlagen"`. It was derived from the
code rather than from a screen, so no gate could have gone red — §9.7 in the
form where the caller _is_ tested and the expectation is simply wrong. Replaced,
with the reasoning kept in the file.

### The half not fixed here

Rendering hides an authoring mistake: those titles disagree with their positions
and somebody should retype them. The place to say so is the **console's course
structure screen**, to the person who can act on it — not the learner's sidebar
(§9.10). Not built in this ticket; the client's own data is the first instance.

# P107 — the screen showed an address where the question was "which register"

**Raised by:** the client, 24.08.2026, from `config.env` and the console:

> _"i updated this, still shows with test in verwaltung"_

**Estimate:** 1.5 h. **Actual:** 1.5 h.

## What was actually wrong, in two parts

**The report was true.** `EIV_BASE_URL` had been changed in `config.env` on the
host and nothing had re-read it. `docker-compose.prod.yml` interpolates
`${EIV_BASE_URL}` at `docker compose up` time, so the running API still held the
value it was created with, and the console faithfully reported it. §9.9a, one
layer over from the Caddyfile: the file was right, nothing failed, and the
process was serving what it read at startup. The remedy is a deploy.

**And the screen could not have helped.** It printed `report.endpoint` and
nothing else. EIV name their sandbox `backend-test.eiv-fobi.de` and the live
register `backend.eiv-fobi.de` — one word between a rehearsal and a statutory
filing, and no reason for an operator to know which is which. The client read
the two as the same kind of thing, which is the correct reading of a URL by
anybody who has not memorised EIV's naming (§9.4).

## P107-01 — say which register, and whether it is armed

`EivConnectionReport` gains two fields:

| Field                | From                                                                     |
| -------------------- | ------------------------------------------------------------------------ |
| `tier`               | `eivEndpointTier`, the same function the deploy guard and the worker use |
| `submissionsEnabled` | `EIV_WORKER_ENABLED`                                                     |

Rendered as sentences beside the address, not instead of it — an operator
reconciling against `config.env` needs the literal string, and one deciding
whether to go live needs the words.

`submissionsEnabled` is the more important of the two and had been **visible
nowhere in the product**: the flag that decides whether a completed Fortbildung
files a real Punktemeldung was readable only by opening `config.env` over SSH.
So the one person entitled to make that decision could not see its current
state. That is §9.2's mirror — a control that can only fail must not be offered,
and a consequence the system _will_ produce must not be hidden.

One warning, on one combination: live (or unrecognised) endpoint **and** worker
armed. Not on the live endpoint alone, because that is exactly the state of the
credential test the operator is supposed to run first, and a warning nobody can
avoid is a warning nobody reads. `unknown` is included because every other guard
in the platform treats it as live.

Five console tests, all watched red — the warning made unconditional fails the
one that enumerates the four states; the two rows deleted fails the other four.
Three integration tests name the API-side caller (§9.7): that the tier comes
from the endpoint the API is _actually_ configured with, that the flag is the
worker's own rather than a constant, and that the field added beside the
password-free report did not loosen it.

**Not verified locally:** the three integration tests need Postgres and the EIV
mock from docker-compose and were not run in this sandbox. They run in CI.
