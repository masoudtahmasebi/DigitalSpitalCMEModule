# P46 · Which build is this, and which SMTP sent that

> please add versioning to be shown when all of the services load in the footer,
> so that we can check which version is deployed.
>
> now i decided to send a password forget to masoud.tahmasebi@digitalspital.de
> and it did not receive, how can i check which smtp was used? how can i set an
> smtp for the admin panel?

Two questions with the same shape, and it is the shape of the last four
tickets: **the system knows and does not say.** The commit is in an environment
variable and on `/metrics`, which the edge does not route. The SMTP outcome is
in the audit log, minus the two fields that would make it actionable.

---

## P46-01 · Every frontend shows its build, beside the API's — **done**

- **Estimate:** 4 h · **Review gate: none**

`/health` gains a `commit` field — contract first, then the schema, then the
SDK. **Not a new endpoint:** `/health` is already public, already routed by the
edge, and already what `deploy.sh` curls to decide a deploy worked; a second
public route would be another thing to expose, review and route for a field
this one can carry.

`@ds/build-info` is the shared half — `shortCommit`, `compareBuilds`,
`fetchApiCommit`. A package rather than a copy in each app for the same reason
`@ds/oidc` is one, and because the interesting function is `compareBuilds`: two
copies would eventually disagree about what counts as skew.

**Both numbers, not one.** The frontend's own commit answers "is this the
bundle I deployed". The API's answers "is the thing it talks to the same
build". A deploy that rebuilt one and not the other is the single most
confusing class of bug report on this project, and it is invisible unless both
numbers are on screen together. When they differ the footer says
_Unterschiedliche Stände — bitte erneut deployen_ rather than leaving somebody
to compare two seven-character hex strings by eye.

`unknown` on either side is **not** skew. A developer running `pnpm dev` has no
image and no `DS_COMMIT`, and a footer that cried version-mismatch at them daily
is a footer nobody reads by Friday — and then does not read on the day it is
right.

| Surface | How it learns its commit        | Where it shows                 |
| ------- | ------------------------------- | ------------------------------ |
| API     | `DS_COMMIT` env                 | `/health`, and `ds_build_info` |
| Console | `/config.js` at container start | footer, every screen           |
| Portal  | `/config.js` at container start | footer, every screen           |
| Widget  | baked at build time             | `data-ds-build` on the element |

The widget is the one that differs, twice. It has no `/config.js` — it is a
single script loaded into a customer's page — so the commit is a Vite `define`,
fed by a Docker build arg. That does not reintroduce the environment-specific
image P16-02 removed: a commit is a property of the _build_, and two deploys of
one commit still produce identical bundles. And it is an attribute rather than
visible chrome, because that element renders inside **MEDICE's** site and a
version line under their course is our diagnostic printed on their layout
(§9.10 — the answer belongs where the entitled audience is, and
`document.querySelector("ds-lms").dataset.dsBuild` is exactly as reachable for
the person who needs it).

Both footers are rendered by `Shell`, not passed in at each call site. The
portal's `Shell` has nine of them, and a prop threaded through nine is a prop
that will be missing from the tenth. It appears on the misconfigured and
signed-out branches too — those are where the question actually gets asked.

**Tested in two places, deliberately** (§9.7). `@ds/build-info` has thirteen
unit tests that would all stay green on a console that never rendered the
component, so the wiring gets its own tests in `App.test.tsx`. Confirmed by
deleting the `<BuildFooter/>` line and watching all three fail.

## P46-02 · An unarrived mail must say which sender and why — **done**

- **Estimate:** 1 h · **Review gate: `needs-human-review`** (staff auth)

The reset endpoint answers 202 for every input by design — unknown address,
disabled account, successful send alike (§9.5) — so `admin_audit_log` is the
_only_ record that an attempt happened. It recorded `{ delivered, status }`,
which is enough to know a mail did not arrive and not enough to act:

- **`host`** was missing, and "which SMTP was used?" has two answers on this
  platform: the platform sender for console accounts, the project's for
  participants. From a missing mail an operator cannot tell which path it took.
- **`reason`** was missing, and `sendNow` had already classified the failure
  and had nowhere to put it. `535 authentication failed` and `connection
refused` are different jobs; both were recorded as `transient`.

Still never the token, never the password, and no recipient field — the row is
keyed to the account, so an address would add nothing and an audit log full of
e-mail addresses is a different disclosure.

## What was not built, and the honest gap

**A "Testmail senden" button.** The right fix for "did my SMTP work" is a
control on the Sicherheit screen that sends one and reports the real outcome to
the operator's face — the audience already entitled to the answer. It is a new
authenticated endpoint in the staff module, so it needs the review gate and a
ticket of its own rather than being folded into a version-footer change.

Until then the audit log answers it, and only through `psql` — **there is no
audit screen in the console.** That is worth naming as a gap rather than
leaving to be discovered: every one of these rows is written, retained and
unreachable from any UI.
