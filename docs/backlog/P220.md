## P220-02 — the column is 1430 px and the customer's page is wider

> the layout stretches the width and aligns from the logo till the logout
> button. We need to have the entire CME module screens be in this structure.

Measured from `screens/page-01.png`, which is the one render containing **both**
the theme's chrome and the widget:

|                                   | design px  |
| --------------------------------- | ---------- |
| theme's logo, left edge           | 254        |
| theme's Logout button, right edge | 1713       |
| widget's panel                    | 261 … 1658 |

The widget's panel is exactly `max-w-[1430px]` minus its `px-4` gutters,
centred at 1920 — it is doing precisely what it was told. And it is **narrower
than the page around it even in the drawing**, which is the client's report.

### Why this is a setting and not a new constant

The number belongs to MEDICE's theme. It is not in this repository, it is not in
the design renders (which draw a mock of that header), and production is not
reachable from here — so any figure I picked would be the same guess the current
1430 already is, made twice.

The cap is therefore a CSS custom property with `1430px` as its default:

```
CONTENT_WIDTH = "w-full max-w-[var(--ds-content-max,1430px)]"
```

`brandingCssVariables` writes `--ds-content-max` from a new project setting,
**Maximale Breite der Lernoberfläche**, beside the colours added in P218-03. A
deployment that sets nothing renders exactly as it does today; Masoud can dial
it against the live theme, see the result, and change it again — without a
release, and without anybody guessing.

This also keeps ADR-0007's line intact. The widget still owns its column, which
it must: the hero, the course artwork and the player's teal band all bleed past
it, and inheriting a WordPress container would clip them. What changes is that
the _number_ is the host's to state rather than ours to assume.

### What the validator refuses, and why that is the interesting half

The value is interpolated into a custom property that ends up in a `max-width`,
so an unbounded string here is a way to write CSS into a physician's page.
Accepted: digits, at most one decimal point with two places, and a unit from
`px | rem | em | vw | ch`. Refused: `calc()`, `var()`, `min()`, a bare number, a
percentage, and anything with a `;` in it.

**Written without a regular expression at all**, and that was not a preference —
two of this repository's own lint rules refused the obvious patterns and both
were right to:

- `security/detect-unsafe-regex` on digits-then-optional-decimal-then-unit;
- the local `no-restricted-syntax` on `/[a-z]+$/` and `/^[0-9]+$/`, because a
  repetition anchored at the end backtracks quadratically — the rule P212 was
  caught by.

So it is a suffix match against a closed list and a character-class scan of each
half, where the question cannot arise. Sabotaged — `if (value.length > 0) return
true` — two cases go red, including the one that feeds `invalidBrandingFields`
so the console names the field rather than dropping the value silently (P41-01).
