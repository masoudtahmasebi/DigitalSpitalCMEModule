# P142 — The API stops answering: one pool, two connections per request

**Reported by the client, twice, four days apart.**

> "why isn't the api responding?"
> — and, after restarting the server themselves — "this is a very critical
> issue! this is really bad."

And on the second occasion, with a network panel attached:

> "this again happened, i just browsed through the menus one by one, and then
> as you can see the networks are pending for answers … it seems to be on
> departments api call, and projects"

---

## P142-01 — A handler holding the request transaction asks the same pool for a second connection

**Status:** done. **Needs human review** — it touches `auth` (participant
sign-in and credential routes move pool).

### What was actually wrong

`TenantTransactionInterceptor` opens the RLS transaction around the **whole**
request, so every handler runs holding one pooled connection for its duration.
Several handlers then ask the _same_ pool for a **second** one:

| Caller                           | Why it needs its own connection                                           |
| -------------------------------- | ------------------------------------------------------------------------- |
| `AuditService.recordForCustomer` | the row must survive the rollback of what it audits (§4 invariant 8)      |
| `StorageAuditRecorder`           | same, for upload events                                                   |
| `ParticipantRepository`          | `users` / `user_identities` / `learner_credentials` are not tenant-scoped |
| `ParticipantAuthRepository`      | resolves a credential before any tenant context exists                    |
| `CustomerRepository`             | acts on a **different** tenant than the request's                         |
| `SubjectErasureRepository`       | a subject spans tenants; the operation is not expressible inside one      |

Every one of those reasons is good. Taking the connection from the pool the
request already holds is not.

With `max: 10`, ten concurrent requests each hold one connection and each wait
for a second that only another of the ten can release. **That is a deadlock**,
and `pg`'s default `connectionTimeoutMillis` is `0` — wait for ever — so it
produced no error, no timeout and no log line. The pool never recovers. The
process has to be restarted.

`POST /admin/participants` alone took two connections per call.

### How it presented, and why it was hard to see

The browser showed every `/admin/*` request `(pending)` at 0.0 kB while the
`OPTIONS` preflight for the same path answered **204 in 20–42 ms** — preflight
short-circuits in CORS middleware and never touches the database. Object storage
kept serving media at 200/206, because that is a conversation with the bucket
the API is not part of. So the screen looked like a front-end fault and the
server logs were clean.

It is also the explanation for `Up 22 hours (unhealthy)`: `/health` runs
`SELECT 1`, which needs a connection, so the readiness probe timed out for
22 hours while Caddy and the static bundles carried on. Nothing was watching
that either — P140.

`pg_stat_activity`, taken while it was hanging, is the whole diagnosis in four
lines:

```
 active | idle_in_tx | waiting_on_lock | total
      1 |         10 |               0 |    11
```

Ten sessions `idle in transaction`, `wait_event = ClientRead` — Postgres waiting
for a client that is waiting for Postgres — all stuck within 20 ms of each
other, every one of them on the statement immediately before an audit write.
Not a slow query, not a lock: the application had stopped speaking.

### The comment that was already there, and wrong

`StorageAuditRecorder`'s header had reasoned about exactly this and written down
the wrong bound:

> "the pool must have room for two per in-flight upload; uploads are rare and
> the pool is sized in tens, but **a pool of one would deadlock** and that is
> worth knowing before somebody tunes it down."

The bound is not a pool of one. It is a pool of **N** under **N concurrent
requests** — which on this installation is ten people, or _one_ person opening
the Mediathek, because that screen asks for a signed URL per tile. This is
`CLAUDE.md` §9.10a in its purest form: a comment that names one consequence of
two, which stopped the next person looking for the other.

### The fix

1. **`PG_SIDE_POOL`** — a second pool (`max: 8`) built from the same settings by
   the same factory, for the six callers above. The request pool cannot starve
   it and it cannot starve the request pool.
2. **`guardReentry`** wraps `PG_POOL` so that `connect()` _and_ `query()` refuse
   a checkout from a context already holding one of its connections, naming the
   call site. Wrapping the pool rather than the call sites is §9.11: `pool.query`
   checks a connection out too, and does not look like it does — enumerating the
   callers would have missed four of the six and gone stale on the next one.
3. **P141's deadlines** underneath, so anything this misses is a 500 with a
   reason rather than a silent wedge.

The guard found **four of the six** on its first run. `ParticipantRepository`
and `ParticipantAuthRepository` were not on any list of mine — 43 integration
tests failed, every failure a real deadlock path, including
`POST /admin/participants`, `POST /admin/participants/merge` and
`GET /auth/participant/me`.

### The test, and watching it go red

`pool-deadlock.integration.test.ts` builds a real pool of **two** and drives two
concurrent operations shaped like requests. Three sabotages, run:

| Sabotage                                                                   | Result                                                 |
| -------------------------------------------------------------------------- | ------------------------------------------------------ |
| audit on the request pool, guard neutered, `connectionTimeoutMillis: 2000` | fails at 2.0 s — P141's backstop, visible              |
| the same with `connectionTimeoutMillis: 0`                                 | **hangs**; killed at 20 s. This is production, exactly |
| guard neutered                                                             | the refusal test and the wiring test both fail         |

The fourth case is the one §9.7 demands: the guard and the side pool are both
correct and both useless if the application still hands `AuditService` the
request pool — that turns a 22-hour hang into a 500 on every audited write,
which is a different outage rather than none. So the wiring test boots the real
module graph and asserts the two pools are distinct objects and that the request
pool is the guarded one.

### What this does not fix

The **deploy is still manual and this build is not on the server.** Production
runs `16c8852`; everything since — including P139's mail fix, P140 and P141 —
is on the branch. §9.9: the repository's state is not the installation's state.
