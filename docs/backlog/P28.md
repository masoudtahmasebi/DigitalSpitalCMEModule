# P28 · One test that walks the whole system, and the three bugs it found

> can you write and run tests that tests the whole system from start to the end,
> and if there are any issues, please fix it until the whole system is complete
> based on best practices and refactors?

Fifteen integration suites, 336 passing tests, everything green — and three
defects that would each have been visible to the first real user, sitting in the
seams _between_ those suites.

That is not an accident of effort. Each of the fifteen is a vertical slice, and
each **hand-seeds around the seam it does not care about**: `learning-flow`
inserts a course with SQL, `authoring` inserts a learner, `completion-flow`
inserts both. That is the right shape for a suite asking one question. It also
means no test had ever asked whether the halves fit together.

This phase adds the suite that asks, and fixes what it found.

---

## P28-01 · `journey.integration.test.ts` — the whole system over HTTP — **done**

- **Estimate:** 5 h

One suite, its own database, **no fixture SQL below the schema itself**. It
creates a database, applies `infra/postgres/init-roles.sql`, runs every migration
in order, boots the app, and then does everything else through the product's own
HTTP interfaces:

> an empty database → roles → migrations → the first operator → a customer → a
> department → a project → a course → a module → a chapter → a video → a
> Lernerfolgskontrolle → an Evaluationsbogen → the stamp and signature → a
> participant account → the participant signs in → changes their password → sees
> the catalogue → enrols → is refused a shortcut → watches → fails the quiz →
> passes it → evaluates → supplies an EFN → is issued a PDF → and appears in the
> operator's report with the same numbers they saw themselves.

22 tests. The negative cases are part of the journey, not an appendix: a
non-uuid tenant header, a video with no duration, a quiz question with no correct
option, completion before the gates are met, a percentage the client tried to
assert, and an EFN that must never come back.

**Acceptance criteria**

- [x] Creates and drops its own `ds_journey_*` database; a stray one after an
      interrupted run is named so it can be found.
- [x] Applies `init-roles.sql` and the migrations as the deploy does — so a
      missing GRANT or an `init-roles.sql` that has drifted fails here.
- [x] No `INSERT` outside the schema. Every row comes from an endpoint.
- [x] Asserts invariant 6 explicitly: the operator's `watchedPercent` equals the
      number the learner's own screen showed.
- [x] Asserts the EFN appears in no learner response and no admin response.

**Definition of done:** green, and the three defects below fixed.

## P28-02 · A `local` project could not authenticate anybody — **done**

- **Estimate:** 2 h · **Review gate: human — auth**

`ProjectBindingRepository.resolve` refused any project whose `keycloak_issuer`
or `keycloak_audience` was NULL, with a comment reading _"a project with no
Keycloak binding configured cannot authenticate anyone"_. That comment predates
ADR-0012's `local` provider and had become false: a `local` project
authenticates a password against our own tables and **has no issuer by design**.

So a participant signed in successfully — 200, cookie set — and was answered
`401 unknown or unbound project` on the very next request.

**Why no test caught it.** Every `local` project that worked had been written by
a seed, and the seeds wrote `''` into two columns they never read. That
placeholder was load-bearing by accident. The console writes NULL. Two rows
meaning the same thing behaved differently depending on which code path created
them, and the fixtures only ever exercised the lucky one.

**The fix, and why it is not a one-line null check**

`ProjectBinding` now carries `keycloak?: { issuer, audience }` instead of two
non-nullable `string` fields:

- Absent is representable, so a `local` project no longer has to lie.
- The pair is atomic. An issuer without an audience verifies a signature and
  then accepts a token minted for a different client — modelling them as
  siblings made half-configured representable, and half-configured is a hole
  rather than a smaller feature.
- A Keycloak-only field cannot be read without first proving the project is a
  Keycloak project. The compiler enforces that now; `KeycloakIdentityProvider`
  refuses with a new `provider_misconfigured` audit reason rather than building
  a JWKS URL out of the empty string.

`resolve` also treats `''` as absent, so a row written by the old seed is read
correctly without a backfill, and `seedPortalProject` clears the placeholder on
re-run.

**And the other half: a `local` project could not be created either.**
`projects.identity_provider` was in the schema, in the CHECK constraint, and
read on every learner request — and settable by **no API**. Every project
created through the console got the column default, which is `keycloak`. So the
console could not produce a working standalone-portal project at all, and the
only ones that existed came from a seed. Same shape as P28-03 below, one table
over: a column the system depends on with no way in.

`identityProvider` is now on `ProjectCreate` and `ProjectUpdate` in the
contract, the authoring DTO, service and repository, defaulting to `keycloak`
so nothing changes for an existing caller.

**Acceptance criteria**

- [x] A `local` project with NULL Keycloak columns authenticates a participant.
- [x] A `keycloak` project with an incomplete binding is still refused.
- [x] `POST /admin/projects` can create a `local` project, and the journey suite
      does — it is how its participant signs in at all.
- [x] The fixtures write what the console writes — `participant-auth`,
      `participants` and `participant-merge` no longer insert `''`.
- [x] Deliberate-violation probe: restoring the unconditional check fails four
      tests in `participant-auth`. Confirmed, then restored.

## P28-03 · The VNR could not be set, so nothing was ever reported — **done**

- **Estimate:** 2 h · **Review gate: human — eiv, certificates**

`courses.vnr` is the number every Punktemeldung is credited against.
`GET /admin/courses/{slug}` returned it. **Nothing could write it.** The console
could set the VNR _password_ — encrypted at rest, write-only, carefully done —
for a number no operator had any way to enter.

The consequence is the worst kind, because it is silent and it is on the
compliance path. `queueSubmission` skips a course whose VNR is null, and skipping
is the _correct_ behaviour there — a missing VNR is an authoring gap and failing
the learner's completion over it would be the wrong trade. So every completion on
every console-authored course recorded a pass, showed the learner a green
Zertifizierung, and reported **nothing** to the Ärztekammer. The certificate PDF
refused with a 409 for the same reason, since the Bescheid requires the VNR as
both barcodes.

This mattered more after the P9 trade lever was reversed and the console became
the authoring path anyone would actually use.

**The fix.** `vnr` is writable on `PATCH /admin/courses/{slug}`, surfaced in
`CourseSettings` above the password field, with a warning shown while it is
empty. An empty string is stored as NULL rather than as a VNR — `''` would pass
the `vnr === null` check and be sent to the EIV as the number to credit against.

**Not** format-validated beyond a length bound. The one specimen we have is 19
digits, and a regex built from a sample of one refuses a legitimate number from
another Ärztekammer at authoring time. `CLAUDE.md` §7 names this case: the EIV
harness validates against the real interface, and inventing a rule here is how a
correct VNR gets rejected where the operator cannot see why.

**Acceptance criteria**

- [x] `vnr` in `contracts/openapi.yaml`, the DTO, the service, the repository
      patch and the regenerated SDK.
- [x] `''` stored as NULL.
- [x] The console has the field, ordered before the password it authenticates.
- [x] The journey suite queues exactly one `queued` submission and downloads a
      real PDF.

## P28-04 · `pnpm dev` served hollow controllers — **done**

- **Estimate:** 1 h

`pnpm dev` was `tsx watch src/main.ts`. `tsx` transpiles with esbuild, and
esbuild implements `experimentalDecorators` but **not** `emitDecoratorMetadata`
— a documented non-goal, since the metadata needs a type checker. NestJS
resolves constructor injection from exactly that metadata, so every provider was
constructed with no arguments, every injected field was `undefined`, and the
first `this.service.method()` threw. `POST /admin/customers` answered 500 under
`pnpm dev` and 201 against a `tsc` build.

The failure is at request time rather than at boot, which is why it lasted: the
app starts, the routes register, only the handlers are hollow.

And the tests could not see it. Vitest transforms with rolldown/oxc, which
_does_ emit the metadata — so a fully green suite ran against code that could not
have served one request in development. Worth stating plainly: **green tests did
not mean a working dev server.**

Replaced with `apps/api/dev.mjs` — `tsc --watch` for the compile and
`node --watch` for the restart, no new dependency, and the compiler CI uses is
the compiler dev uses. The first version spawned through `npx` and leaked
orphaned watchers on Ctrl-C; it now resolves the binary and kills what it
started. `tsx` is dropped from `apps/api`.

## What this phase is really about

Three defects, one shape: **a control that looks implemented and does nothing.**
A `local` project with a login that authenticates and then refuses. A VNR field
that displays and cannot be written. A dev server that boots and cannot serve.

Each was invisible from inside a vertical slice, and each was found within an
hour of a test that walked the system end to end. That is the argument for
keeping this suite fast, hermetic, and free of fixture SQL — the moment it starts
seeding around a seam, it stops testing the one thing it exists to test.
