# P113 · Two guards that could not go red

Raised 25.08, from a client screenshot, thirteen days before launch.

## How it started

The client was shown a warning that the post-deploy smoke test might have filed
a Punktemeldung against the live Ärztekammer register, and answered with a
screenshot of EIV's own web application refusing the fixture VNR
`2760000000000000000` at form validation — red outline, disabled button — and
the question **"this doesn't work tho, are you sure this worked even?"**

They were right to ask. The warning was reasoned from the code path and stated
as though it had been observed; no `eiv_submissions` row on production was ever
checked. Pulling that thread found two guards that had never been capable of
firing, and one of them is the reason the warning was plausible in the first
place.

---

## P113-01 · The smoke's live-EIV guard read the wrong machine

**Status:** done · **needs-human-review** (touches `eiv`)

`scripts/run-smoke.mjs` refuses to drive an installation that reports
Punktemeldungen for real, because the journey publishes an accredited
Fortbildung, completes it, and queues a submission carrying a reserved VNR.

It decided by reading `process.env.EIV_ALLOW_LIVE`.

`EIV_ALLOW_LIVE` is set in the **host's** `config.env`. `run-smoke.mjs` runs in
a GitHub Actions runner, which has never had that variable set by anything. So
the guard read an always-empty string, concluded "not live", and let every run
through — including this morning's, against an installation pointed at
`backend.eiv-fobi.de` with the worker enabled.

This is CLAUDE.md §9.1 in its third form — _green because of what it is not
scanning_ — sitting in the single guard between a test fixture and a statutory
register. And §9.6's shape underneath it: a missing answer that was
indistinguishable from a legitimate "no".

**The fix is the pattern the workflow already uses and documents.** Where
`deploy.yml` asks the host for its own hostnames it says: _"Ask the host what it
believes its own API hostname is, rather than rebuilding the derivation here
from a copy of the configuration this workflow no longer holds. The smoke test
then cannot disagree with the server about where the server is."_ The EIV
posture was the one thing never asked. Now the `derive` step runs the host's own
`ds_eiv_worker_will_file_live` — the same function `deploy.sh` uses — over the
host's own `EIV_BASE_URL` and `EIV_WORKER_ENABLED`, and passes the answer
through as the job output `eiv_reports_live`.

`run-smoke.mjs` now **fails closed**: it refuses on `yes`, and refuses just as
loudly on unset or unrecognised, naming the workflow step responsible. Absence
was the failure mode for the life of the file, so absence is no longer allowed
to mean safety.

### Verification

Watched to go red, all four cases, rather than run twice (§9.1, §9.12 step 5):

| `EIV_REPORTS_LIVE`        | Result                                                       |
| ------------------------- | ------------------------------------------------------------ |
| unset                     | exit 2, "cannot establish…" — **the case that used to pass** |
| `EIV_ALLOW_LIVE=yes` only | exit 2 — the old variable no longer answers                  |
| `yes`                     | exit 2, "refusing to run…"                                   |
| `no`                      | proceeds into Playwright                                     |

And the remote snippet itself, run locally over the real `eiv-endpoint.sh`:
`backend.eiv-fobi.de` + worker unset or `yes` → `yes`; + `EIV_WORKER_ENABLED=no`
→ `no`; `backend-test.eiv-fobi.de` → `no`; `eiv-mock` → `no`; empty base URL →
`yes`, failing closed. Production's current configuration yields `yes`, so the
smoke would now refuse — which is the outcome that should have happened this
morning.

## P113-02 · `/metrics` was routed from the edge, and two comments said it was not

**Status:** done · **needs-human-review** (changes what the internet can reach)

`MetricsController` is `@Public()` — a Prometheus scraper cannot present a
bearer token. Both `health.controller.ts` and `observability/metrics.ts`
justified that with the same claim: that `infra/deploy/Caddyfile` _"does not
route `/metrics` from the edge, so an external scraper needs an SSH tunnel."_

`metrics.ts` then used that claim to decide where to put the build fingerprint:

> **Here and not on `/health`,** which is public … A version string on a public
> endpoint is a fingerprint that tells anyone which vulnerabilities to try.

The `{$API_DOMAIN}` site block's only handler was a bare `reverse_proxy
api:3000`. In Caddy that is a catch-all matching **every** path; nothing
filtered `/metrics` out. So the sentence described a matcher nobody had ever
written, and `ds_build_info{commit="…"}` — added on the strength of it — has
been served to anyone who asked, along with request counts and latency
histograms per route.

No tenant data, no identifier and nothing personal is exposed, so this is a
fingerprint and an operational-detail leak rather than a data breach. Two files
asserting a security property with nothing checking it is still §9.1, and it is
the third entry in this repository of that exact shape.

**Fixed** with an explicit matcher in the API block:

```
@metrics path /metrics /metrics/*
respond @metrics 404
```

`404` and not `403` — a 403 confirms something is there, which is the oracle
§9.5 refuses. An operator scrapes it the way the comment always claimed they
did: from inside the Docker network, against `api:3000`, where Caddy is not in
the path.

Both comments are corrected rather than deleted. A comment that was false is
worth keeping as a record of having been false (§9.9a).

### Verification

`infra/deploy/deploy-vars.test.sh` now asserts both lines, alongside the CSP
directives it already checks, and it is in `pnpm verify` via `check:shell` —
not CI-only (§9.11).

Broken and watched to go red: deleting the two lines gives exit 1 and
_"the API site block does not refuse /metrics from the edge"_; restoring them
returns `27 shell + 23 compose references checked, all guaranteed`.

**Not reproduced against a running Caddy.** The sandbox has the Docker CLI but
no daemon, so this is derived from source and from Caddy's documented matcher
semantics, and labelled as such. It is confirmable from any terminal in five
seconds:

```
curl -sS -o /dev/null -w '%{http_code}\n' https://<api-domain>/metrics
```

`404` after this deploys; anything else — particularly `200` — means the
Caddyfile on the host is not this one, which is §9.9a's own warning about a
mounted file the running process never re-read.

## What was deliberately not built

**A VNR check-digit validation.** The screenshot shows EIV computing one, and
Luhn fits both specimens we hold — the real Bescheid VNR passes, the fixture
fails. It is still one real specimen, which is a one-in-ten coincidence, and
`docs/show-stoppers.md` S23 already refused exactly this trade for the EFN's
Prüfziffer: a wrong Modulo rejects a _valid_ number at the last step of a
completed Fortbildung. Guessed wrong here, it stops MEDICE saving their own
accredited course.

S23 §2 now carries the evidence, the Luhn hypothesis, and a three-line
experiment in EIV's own form that settles it from observation. Implementing it
is a follow-up ticket once somebody runs that experiment or reads the page's
JavaScript.

Worth stating plainly, because it is the finding underneath the screenshot:
**nothing in the platform validates the VNR at all today** — not the console
field, not the authoring DTO, not the schema. A mistyped VNR is accepted,
answered "Gespeichert.", published, and surfaces eight days later as a
`failed_permanent` Punktemeldung with the statutory clock already spent.

## Still open

- Whether any `eiv_submissions` row on production carries
  `2760000000000000000`. Needs the live console's **Verwaltung →
  Punktemeldungen** or a query on the host; unreachable from the sandbox.
  Bounded either way: `authenticate()` runs before `pushTeilnahme`, a 401/403
  raises `EivError("auth")`, and `auth` is not retryable — so the worst case is
  one refused login and a `failed_permanent` row, not a Punktemeldung against a
  real physician.
- `zwei-module.spec.ts` fails against production and passes against the rig at
  the same commit. Unexplained; timing is a hypothesis, not a diagnosis.
