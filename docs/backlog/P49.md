## P49-01 · `\/+$` was in four places, and CodeQL is right — **done**

- **Estimate:** 2 h · **Review gate: none**

`value.replace(/\/+$/, "")` anchors a repetition at the end of the string, so a
regex engine answering "does a run of slashes reach the end?" restarts that scan
at every position: quadratic in the input's length.

The exposure was small — `apiBase` from `/config.js`, `PORTAL_BASE_URL` and
`S3_ENDPOINT` from a deployment's own environment, a slug from a title an
operator types. Only the widget's read-more trim ran on somebody else's text (a
course description out of the database). But the fix is four lines of obviously
linear code, so there was nothing to weigh.

`stripTrailing`, `stripTrailingSlashes`, `joinUrl` and `lastWhitespaceIndex` now
live in `@ds/domain` — the right home because they are pure, and one home
because four call sites got this right independently, which is exactly the
situation in which the fifth gets it wrong.

`characters` is a **set, not a pattern**. A caller cannot accidentally pass
something with its own backtracking in it, which would relocate the problem
rather than remove it.

### The lint rule, and why the first version was wrong

`security/detect-unsafe-regex` does not catch these: it looks for _exponential_
blow-up and this class is merely polynomial. So `no-restricted-syntax` now
rejects a repetition anchored at the end.

The first version flagged twelve `toMatch(/^[a-z0-9]+$/)` in tests — all of them
safe, because a pattern anchored at **both** ends has exactly one start position
and nothing to retry. A rule that noisy is a rule somebody switches off, so the
selector excludes patterns beginning with `^`. Two genuinely bounded cases
(base64 and base32 padding, both of our own output) carry a local disable naming
the bound.

It runs in `pnpm verify`, which is the point: CodeQL found this days after the
commit, and §9.11 says a check that only runs in CI is one the author does not
run.

## P49-02 · "The API refuses this configuration" — when the API had said nothing — **done**

- **Estimate:** 1.5 h · **Review gate: none**

```
==> Checking the API's configuration
unknown flag: --no-build
xx the API refuses this configuration — see the message above.
   Fix the value in /home/deploy/ds-education/config.env
```

Every word after the first line was false. `docker compose run` on that host
does not have `--no-build`; P45-01 treated **any** non-zero exit as a
configuration rejection, so a broken check blamed a correct `config.env` and the
operator's next move was to edit a file with nothing wrong with it.

That is P44-03's lesson one layer in: **a diagnostic that names the wrong thing
is worse than none, because it is followed.**

Two fixes:

- **The flag is gone**, from `deploy.sh` and from `dsc`. It was redundant
  anyway — the image is built moments earlier, `pull_policy: never` stops
  compose reaching for a registry that does not exist, and `ds_resolve_image_tag`
  has already established the image is on the disk. A flag that adds nothing
  here and is fatal on an older compose is not a trade.
- **`ds_classify_config_check`** distinguishes `invalid` (the API's own words,
  matched on `Invalid configuration`) from `old-image` (a rollback predating the
  entrypoint) from `unavailable` (everything else).

Only `invalid` stops a deploy. `unavailable` **warns and continues**: the API
still validates at boot, `deploy.sh` still refuses to swap a container that will
not start, and `ds_dump_broken_services` still prints its log. Blocking there is
what let a tooling problem stop a deployment that was otherwise fine.

`config-check.test.sh` needs no docker, because the classification is a pure
function of an exit status and some text — which is exactly why it was
extracted. `unknown flag: --no-build` is in it verbatim.

`deploy.sh` also now **prints the compose version** in its preflight. When
compose rejects a flag, that is the first thing anybody asks for.
