# P117 — Nineteen zeros is not a Veranstaltungsnummer

**Status:** P117-01 done. P117-02 is an operator action on the installation, not
code. **Human review required** — this touches `certificates` and `eiv`.

---

## The report

> "i just finished a course, and i was checking it, so i gave my efn as
> 123456789012345 and as it seems the course was done, but the vnr is not
> printed, and there is nothing in the https://punktemeldung.eiv-fobi.de/ and
> there are also no errors anywhere."

Three screenshots: a Teilnahmebescheinigung, the Zertifizierung tab, and the EIV
portal listing VNR `2760552025919300018` with _"Keine Teilnehmer erfasst"_.

## What actually happened

The VNR **was** printed. It was `0000000000000000000`.

That is `PLACEHOLDER_VNR` — the string `packages/seed` writes when it has no
accredited number, so a seeded course is structurally complete and the platform
is testable before the Anerkennungsbescheid arrives. P109-01 replaced the
default with the real number from the ÄKWL Bescheid and taught the seed's
`ON CONFLICT` to overwrite its own placeholder. **That seed has never run on
that installation** — §9.9's corollary, for the fourth time: the repository's
state is not the installation's state.

So the certificate names a Veranstaltung the ÄKWL register does not hold. The
EIV portal is empty for the same reason and is answering correctly: there is no
such event to have participants against, and the real event
(`2760552025919300018`) has none because nothing was ever filed against it.

**The certificate in the client's hands is not a valid document.** It went to
whoever completed the course.

## Why nothing objected — the finding

Every gate asked whether the VNR was **missing**, and it is not:

| Gate                                                 | Test                                   | Nineteen zeros |
| ---------------------------------------------------- | -------------------------------------- | -------------- |
| `publishBlockers` (`publishing.ts:95`)               | `isBlank(course.vnr)`                  | passes         |
| `missingCertificateFields` (`certificate.ts:149`)    | `isBlank(input.vnr)`                   | passes         |
| `courses_published_cme_is_complete` (migration 0042) | `vnr IS NOT NULL AND btrim(vnr) <> ''` | passes         |

Three independent checks, at three layers, written at three different times, all
asking one question — and the one value the platform itself writes most often is
the value none of them could see. CLAUDE.md §9.1: a gate that could not have
gone red for its most common input is not evidence.

It is also §9.3 wearing a new hat. P109-01 wrote a rule about the placeholder —
_"the seed replaces its own placeholder and nothing else"_ — and that rule lived
entirely inside one `ON CONFLICT` clause. Nothing else in the system knew the
string existed, so nothing else could refuse it.

## P117-01 — what was built

**The literal has one home.** `PLACEHOLDER_VNR` and `isPlaceholderVnr()` are in
`packages/domain/src/eiv.ts`; `packages/seed` imports the constant rather than
declaring its own copy (a new `@ds/domain` dependency on `@ds/seed`). Four
readings of one value instead of four copies of a literal.

**Three gates now refuse it**, at the three layers above:

- `publishBlockers` — the course cannot be published;
- `missingCertificateFields` — no Teilnahmebescheinigung is produced;
- `courses_published_cme_is_complete`, replaced by migration **0047** rather
  than supplemented, so there stays exactly one schema-level answer to "may this
  publish?" (§4 invariant 6 at the database).

**Migration 0047 also demotes** any published, point-awarding course carrying
the placeholder, and writes the count to `audit_log` — a course leaving the
catalogue must survive the deploy that caused it. It names the field, never the
value (§9.5), and does the `NO FORCE ROW LEVEL SECURITY` dance 0042 established,
because a migration writing to `courses` on the bare connection matches zero
rows and reports success (§9.6).

**The seed completes the repair.** The migration cannot: the real number is
per-installation, from `SEED_MEDICE_VNR` or the Bescheid default, and only the
seed has it. So the same `ON CONFLICT` statement that replaces the placeholder
VNR also puts `status` back to `published` — guarded by the **same sentinel**,
so it can only fire on a row still carrying our own placeholder. A course an
operator unpublished has a VNR they typed, so the `ELSE` keeps their decision
and P108-01's rule holds. Without this the deploy that fixes the VNR would leave
MEDICE's course a draft, off `/medice`, with nothing saying why — which is
exactly the report that opened P64-02.

### Why this refuses one string and not a VNR format

S23 is open: the check digit is documented in secondary sources and unconfirmed
by ÄKWL. A rule derived from a sample of one would refuse a legitimate number
from another Kammer at the moment an operator is configuring a course they
cannot report without — §9.2 inverted, and §7's _"an invented rule that ships is
worse than a delay"_. What this knows is narrower and certain: **this exact
string is ours, and no Ärztekammer issued it.**

### Evidence the checks can go red (§9.1)

Each was broken and watched to fail, then restored:

| Broken                                                      | Went red                                                                                                                                 |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `\|\| isPlaceholderVnr(...)` removed from both domain gates | 3 domain tests                                                                                                                           |
| Migration 0047's constraint reverted to the 0042 expression | 1 integration test — and the control case, a real VNR on the same row, stayed green, so the constraint is not simply refusing everything |
| The seed's `status = CASE …` line removed                   | 1 integration test                                                                                                                       |

Full run: 762 domain tests, 557 integration tests against real Postgres, and all
fourteen steps of `pnpm verify`.

## P117-02 — what the installation still needs (not code)

1. **Deploy this branch.** Migration 0047 and the repaired seed both run in it.
   After it, `/medice` should show ADHS Akademie adult carrying
   `2760552025919300018`.
2. **Treat the issued certificate as withdrawn.** It is a row in `certificates`
   and a PDF in the archive. Nothing here deletes either — destroying the
   evidence that an invalid document was issued would be worse than the document
   — but it must not be given to a physician, and the completion it belongs to
   needs re-issuing once the real VNR is in place.
3. **Check Verwaltung → Punktemeldungen** for that completion's row. "No errors
   anywhere" is the report; that screen is where an error would be, and P110-01
   built it for this.
4. **Set the real VNR password** through the console's write-only field. A VNR
   alone authenticates nothing, and until it is set a Punktemeldung abandons
   with `missing_vnr_password`.

## Open

- **S23** stays open and is now load-bearing in a second place: if ÄKWL confirms
  the check digit, `isPlaceholderVnr` can become the narrow case of a real
  format rule. Until then it stays narrow on purpose.
- Nothing in the product tells an operator _why_ a course was demoted. The
  audit row says it; the Fortbildung screen does not. Worth a line — §9.4.
