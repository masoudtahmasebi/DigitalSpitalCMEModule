## P259-01 — production on the patched Node, and a way to see it

**Review gate:** none · base image and a metric label

**Context**

Node published **v22.23.4 on 20.10.2026 as a security release** (Verified:
`https://nodejs.org/dist/index.json` lists `v22.23.4 2026-10-20 security:
true`; earlier 22.x security releases 22.23.2 on 28.07 and 22.23.0 on 17.06).

Both runtime stages were `FROM node:22-bookworm-slim`, a floating tag, and
`deploy.sh:795` builds with `--pull` — so production ran whatever the tag held
on the day of the last deploy. The last deploy was 19.10, the day before the
release. Nothing in the repository or on `/metrics` said which Node that was.

Verified: on 28.10, `22-bookworm-slim` and `22.23.4-bookworm-slim` have the same
digest (`sha256:4b150b48…`, both updated 05:38–05:39 UTC), from the Docker Hub
tags API.

**Scope**

- `Dockerfile`: both `FROM node:` lines pinned to `22.23.4-bookworm-slim`.
  Dependabot's weekly `docker` update (already configured for `/`) can now
  propose patch bumps — a floating tag gives it nothing to compare.
  `pnpm check:node-version`: passes.
- `/metrics`: `ds_build_info{commit=…,node=…}` carries `process.version`, so
  the runtime on the host can be read rather than inferred (§9.9). The e2e
  reader matches `commit` with `[^}]*` and is unaffected; no other reader.

**Acceptance criteria**

- [x] Observability tests: the new `node` label case and both updated
      `ds_build_info` cases red before, 26 passed after.
- [ ] After deploy, production `/metrics` reports `node="v22.23.4"`.

## P259-02 — the Node review's findings

**Review gate:** none · dev/e2e tooling only (`dev-keycloak` refuses to run in
production, `exitIfProduction`)

No blockers. The dependency bumps of P258-01 were checked and hold: every
override stays within its major, each package resolves to one version, express
5 with body-parser 2.4 answers 200/413 through the API's own `express.json`,
nodemailer's API as used by `packages/mail` is unchanged (7 tests), and all
`engines` floors are at or below Node 22.

Fixed — the stub Keycloak's key file (P258-09):

- **A corrupt file stopped the stub silently.** `main()` rejected with stdio
  ignored, so the harness only saw "dev-keycloak did not start". Now said on
  stderr, replaced, and the stub starts; the harness passes stderr through.
- **A predictable path in the shared temp dir.** `ds-e2e-keycloak-<ppid>.json`
  in `os.tmpdir()` could be pre-planted by another local user, `mode: 0o600`
  does not apply to an existing file, and a plain write follows a dangling
  symlink. Now: a private `mkdtemp` directory made in global setup (0700),
  removed in teardown; the file is created with `flag: "wx"`.

Verified (`dev-keycloak.test.ts`, 13 passed): "never writes a private key
through a symlink planted at the path" red with `flag: "w"`; "replaces a
corrupt file instead of refusing to start" red with the replacement removed.

Left, as nits: nodemailer 10.2 counts the greeting wait against
`connectionTimeout`, and its new `err.permanent` could replace `classify()`'s
code table.
