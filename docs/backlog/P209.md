# P209 — the tab labels were not on one line, and the fix for the last report caused it

The client, with the catalogue open:

> now icons are not in the same line.

The screenshot is the catalogue's tab row: **On Demand** selected and white,
**Weitere** teal beside it, and the two words visibly not on one line.

---

## P209-01 — bottom-aligned boxes of different heights do not share a baseline

This is the third report about this row, and the third was caused by the second.

| report                                                                                          | fix                                                                                                                         |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| a `py-4` and an `mb-4` that are not in the design                                               | P204-01 removed both                                                                                                        |
| _"the tabs which are not selected, should have a padding or margin bottom to match the design"_ | P204-01 added `sm:mb-1.5` to the unselected tabs, with `sm:items-end` so the margin lifts the box rather than shortening it |
| _"now icons are not in the same line"_                                                          | **this**                                                                                                                    |

`sm:items-end` aligns every tab's **margin box bottom** to the row's bottom. The
selected tab is 1 px taller than the others — it carries a top border and they
do not — and the unselected ones then carry 6 px of bottom margin. Bottom-aligned
boxes of different heights do not put their content on one line, so the label of
every unselected tab sat above the selected one's.

**Measured, not estimated.** Chromium, this project's own compiled Tailwind, the
two tabs' class strings exactly as they shipped:

```
label offset (inactive - active): -7.00 px
gap under inactive tab:            6.00 px
```

## The fix

The gap moves to where it structurally belongs. A folder tab is not shorter than
its neighbours and pushed up; the **selected** one is taller and reaches down
into the panel it merges with. So:

- `sm:items-start` on the row — every tab's top on one line;
- `sm:pb-4` on the selected tab — it grows 6 px further down, into the panel,
  which is the gap the drawing has under the others;
- `sm:mb-1.5` deleted from the unselected tabs;
- `sm:border-t sm:border-t-transparent` on the unselected tabs, because the
  selected one has a 1 px top border and they have none. Without it the labels
  land 1 px apart, and 1 px is exactly the kind of thing that is invisible until
  somebody measures and finds the fix was only nearly right.

Re-measured after recompiling the CSS:

```
label offset (inactive - active): 0.00 px
gap under inactive tab:            5.00 px
```

The gap is 5 px rather than 6 — the difference between `pb-4` and the arbitrary
`mb-1.5` I had picked in P204, neither of which came from the export. What the
client named is the alignment, and that is exact.

## The trap the measurement itself walked into

The first attempt measured the _candidate_ classes against the CSS compiled from
the **old** source and reported `label offset: -1.00 px, gap: 0.00 px` — a
plausible-looking answer for a fix that was doing nothing at all. Tailwind emits
only the utilities it finds by scanning source, so `sm:pb-4` and
`sm:border-t-transparent` did not exist in that stylesheet.

That is §9.1 inside the instrument rather than inside the product: a measurement
against a stylesheet that cannot express the change is a green reading of an
unapplied fix. The source is edited, then the CSS recompiled, then measured.

## The instrument, kept

Three reports about this row, all geometric, and **none of them was visible to
anything this repository runs**. jsdom has no layout, so the 418 widget tests
cannot see a 7 px offset; asserting class strings would be a test about the
class rather than about what a physician sees (§9.7).

A browser is the only witness, and the deploy already drives one. So
`journey.spec.ts` now measures it, at the point the catalogue is on screen:
every `role="tab"`'s **text** box — not the button's, because a button can grow
around its label without moving it, which is precisely the shape of this fix —
and the centres must fall within 1 px.

It carries its own floor: fewer than two tabs fails with _"the catalogue drew no
tabs at all, so the measurement below proves nothing"_, so a catalogue that
renders no row cannot pass by having nothing to compare.

## Verified

| claim                                         | command                                                                                                                            |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| the labels were 7.00 px apart                 | Chromium against the compiled `tw.css`, shipped class strings                                                                      |
| they are 0.00 px apart after the fix          | the same, after recompiling the CSS from the edited source                                                                         |
| the unselected tab still stands off the panel | same run — 5.00 px                                                                                                                 |
| nothing else referenced the old classes       | `grep -rn "items-end\|mb-1.5"` — two unrelated `items-end` call sites in other components, and this file's own history in comments |
| the widget still passes                       | 418 tests                                                                                                                          |
| typecheck                                     | 31/31                                                                                                                              |

**Not verified:** that the new journey assertion passes against the installation
— the rig needs Docker, which this sandbox does not have. What is verified is
the technique it uses: the same `Range`-based measurement produced the 7.00 and
the 0.00 above, so it would have caught this defect. The next deploy is where it
runs for real.
