# P17 · The server owns its own secrets, and Keycloak is per project

Two things the deployment got wrong, both visible once it was pointed at a real
server: GitHub was holding the database's credentials, and the platform was
being asked to name one customer's Keycloak realm.

**Review gate: human — auth.** P17-02 removes configuration the token validation
path used to declare.

---

## P17-01 · Credentials the machine generates and owns — **done**

- **Estimate:** 4 h · **Depends on:** P16-01

**Why**

`PRODUCTION_ENV` was a GitHub secret containing the whole production
environment — two database passwords, the Postgres superuser password and the
KMS key that decrypts the VNR password and SMTP credentials — which the deploy
workflow wrote to the host on every run. Three things were wrong with it:

1. **It made GitHub a credential store for the database.** Anyone who could read
   the repository's secrets held the platform.
2. **It put the configuration a browser tab away from the thing it
   configures.** Changing a domain meant editing a blob in a web form and
   running a deployment.
3. **It rotated nothing.** Four values a human generated once, saw, pasted, and
   never touched again.

None of the four encodes a decision. They are 32 random bytes each; nobody reads
them and nobody types them. There is no reason for a person to have ever seen
one.

**Scope**

- `infra/deploy/secrets.sh`: `ds_ensure_secrets` and `ds_check_secrets`.
- `~/ds-education/config.env` — written once by a human, never by a deploy.
- `~/ds-education/secrets.env` — generated, mode 600, never regenerated.
- `~/ds-education/images.env` — what the last deploy pinned.
- `infra/deploy/dsc` — `docker compose` with both files already loaded.
- The deploy workflow loses `PRODUCTION_ENV` and every repository variable
  except an optional `DEPLOY_REPO_DIR`.

**Acceptance criteria**

- [x] Four credentials generated with `openssl rand -base64 32` on first deploy
- [x] **Generated only if absent.** Regenerating `SECRETS_KMS_KEY` does not
      rotate anything — it makes every encrypted column permanently unreadable,
      and there is no plaintext fallback by design
- [x] The file is created under `umask 077` rather than created and then
      `chmod`ed, which has a window where it is world-readable
- [x] A secrets file anyone else can read is refused, not appended to
- [x] `config.env` missing is a message naming the two commands that fix it, not
      a default — a default would be guessing at somebody's domain
- [x] State lives **outside the git clone**, so a `git checkout` cannot touch a
      credential and `git status` on the server stays clean after a deploy
- [x] GitHub holds four secrets, none of which unlocks anything on its own
- [x] The deploy runs from the host's own clone at an exact SHA, detached —
      `main` may have moved since CI went green
- [x] `git rev-parse HEAD` on the server answers "what is running?" without
      trusting a workflow log
- [x] Image tags are not configuration: the workflow passes them, `deploy.sh`
      records them, and a bare re-run reuses what was recorded

**Verified against a real state directory.** A first run created `secrets.env`
and generated all four; a second changed nothing; the KMS key decodes to exactly
32 bytes. Seven deliberate faults were each refused with a message naming the
cause: no `config.env`, no `PROJECT_SLUG`, no `PORTAL_KEYCLOAK_ISSUER`, a pasted
URL as the base domain, the live EIV endpoint without its guard, a
world-readable `config.env`, a truncated KMS key, and no image tags anywhere.

**Note for whoever plans the backups.** `secrets.env` belongs in the same
backup as the database dump. A restore without the KMS key brings back rows
whose `_enc` columns can never be read again. `docs/deployment.md` §6 says so
where somebody planning off-host copies will meet it.

## P17-02 · Keycloak is a property of the project — **done**

- **Estimate:** 1 h · **Depends on:** —

**Why**

`KEYCLOAK_ISSUER`, `KEYCLOAK_AUDIENCE` and `KEYCLOAK_JWKS_URI` were declared in
the API's config schema, validated at boot, required by the deploy preflight,
documented in the runbook — and **read by nothing**.

The realm a learner's token is validated against comes from
`projects.keycloak_issuer`, resolved per request by `ProjectBindingRepository`
and handed to the guard. That is what lets one installation serve several
customers with separate realms, and it has been true since migration 0002.

The three variables were a deployment-wide answer to a per-tenant question.
Their only effect was to make a deployment name one customer's realm in a file
that is not about any customer — and to imply, to anyone reading the runbook,
that the platform has a single identity provider.

**Acceptance criteria**

- [x] The three variables are gone from the config schema, the compose file,
      the deploy preflight, the workflow and the runbook
- [x] `config.ts` carries a comment saying where the issuer actually comes from,
      so the next person meets the reasoning rather than the absence
- [x] The API service in `docker-compose.prod.yml` has no Keycloak environment
      at all — verified by reading back the resolved configuration
- [x] The portal keeps `PORTAL_KEYCLOAK_ISSUER` and
      `PORTAL_KEYCLOAK_CLIENT_ID`, because a browser app must know where to send
      a learner before it has spoken to any API
- [x] `deploy.sh` **warns** when the portal's issuer is not the issuer on the
      project row — a mismatch is a learner signing in successfully and then
      having every request refused, with a 401 that names nothing
- [x] The warning is not a refusal, and is skipped when the project row does not
      exist: on a first deploy it does not, and refusing would make the platform
      impossible to install
- [x] Three config tests disappeared with the variables — `it.each` generates
      one "refuses to start without X" per required key, and those three keys
      are exactly the behaviour being removed

**Still deployment-level, and why.** The portal's OIDC client duplicates the
project's realm: the portal sends the learner to `PORTAL_KEYCLOAK_ISSUER`, and
the API validates what comes back against `projects.keycloak_issuer`. Serving
those two values from a public per-project endpoint would remove the
duplication — but the branding endpoint deliberately withholds the Keycloak
binding, enforced by column grants in migrations 0007 and 0008, and reversing
that is an auth-path change under the review gate. The deploy-time warning is
the cheap half of the fix; the endpoint is the expensive half and is not in this
ticket.

## P17-03 · Why not Traefik — **answered, no change**

Asked directly, and worth writing down because it will be asked again.

Traefik's distinguishing feature is dynamic discovery: containers announce their
own routes through labels and the proxy reconfigures itself as they come and go.
That is worth a great deal when the set of services changes without anybody
editing a file — autoscaling, ephemeral preview environments, a platform team
that does not own the app.

None of that describes this deployment. There are four services, their names are
fixed, and the routing table changes when somebody edits this repository.
Against that, dynamic discovery is a cost:

- the routes move from one reviewable file into labels spread across the service
  definitions, so "what is exposed publicly?" stops being answerable by reading
  one thing;
- a mislabelled container publishes itself, so a typo's failure mode changes
  from "this service is unreachable" to "this service is reachable";
- the CSP and the body-size limits in the Caddyfile — compliance surface, not
  plumbing — become label strings.

Caddy also does the one thing this deployment genuinely needs automatically:
certificates, with no ACME client, no cron job and no renewal hook. The
Caddyfile is four site blocks and reads top to bottom.

Recorded in the header of `docker-compose.prod.yml`, next to the existing note
on why not nginx + certbot. Revisit if containers ever appear without a commit.
