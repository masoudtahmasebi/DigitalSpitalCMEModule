### `eslint-plugin-jsx-a11y` has an unmet peer, and still runs

6.10.2 is the latest and declares `eslint@^3 … ^9`. `pnpm install` warns. The
rules still fire — **verified by planting a violation, not by assuming**:

```
apps/widget/src/__a11y_probe.tsx
  2:10  error  img elements must have an alt prop …  jsx-a11y/alt-text
```

The probe was deleted. This is worth knowing rather than trusting: the a11y
floor is costed in CLAUDE.md §3, and it is currently enforced by a plugin that
does not claim to support the linter running it. If a later ESLint 10.x breaks
it, the failure mode is silence (§9.1) — the lint stays green with the rules
no longer applied. Re-run the probe when ESLint next moves.

## What was held, and why

Both are **migrations, not bumps**, and both were attempted and reverted rather
than assumed.

### TypeScript 7.0.2 — two hard blockers

```
$ pnpm typecheck
@ds/domain:build: src/branding.ts(232,15): error TS2304: Cannot find name 'URL'.
 Tasks:    0 successful, 13 total
```

`packages/domain` compiles with `lib: ["ES2022"]` and no `types`, because §4
invariant 4 makes it pure — zero I/O, zero framework imports. It reached `URL`
through TypeScript 5's automatic `@types/*` inclusion from the workspace root.
TS 7 does not, and there is no honest one-line fix: `lib: ["DOM"]` would let a
domain file reference `document` and compile, which is the invariant's whole
point; `@types/node` in a package forbidden to touch Node is the same problem
wearing a different hat. **This is a decision about how a pure package declares
WHATWG globals, and it belongs to whoever owns that invariant.**

And the one that ends the discussion for now:

```
$ pnpm --filter @ds/sdk generate
const BOOLEAN = ts.factory.createKeywordTypeNode(ts.SyntaxKind.BooleanKeyword);
TypeError: Cannot read properties of undefined (reading 'createKeywordTypeNode')
```

`openapi-typescript@7.13.0` declares `typescript@^5.x` and reads `ts.factory`,
which TypeScript 7's rewritten compiler API does not expose. The SDK is
generated from `contracts/openapi.yaml` (§2, contract-first) and `check:sdk`
is a `pnpm verify` gate. TypeScript 7 cannot land until that generator supports
it.

### Tailwind CSS 4.3.3 — a migration across three apps

```
Error: [postcss] It looks like you're trying to use `tailwindcss` directly as a
PostCSS plugin. The PostCSS plugin has moved to a separate package …
```

That is the first step of several. v4 also replaces the JS config with CSS
`@theme`, which is where `packages/config/tailwind.preset.js` keeps every
`--ds-*` brand token; and it removes `corePlugins`, which is how
`apps/widget/tailwind.config.js` turns preflight **off** — the single setting
the Shadow-DOM widget depends on, with a hand-written reset in `styles.css`
standing in for it.

So the work is: a PostCSS package swap in three apps, three CSS entry rewrites,
a preset rewrite, a replacement for `preflight: false`, and then a **visual**
re-verification of the CME module at 1920 px against the client's layout, plus
the admin console and the portal. Tailwind is the only dependency here whose
failure mode is a screen that renders wrongly rather than a suite that goes red
— and the product has been live since 06.09. Its own ticket.

### `@types/node` capped at 22.x

Latest is 26.6.2 and it is **not** the right version: `.nvmrc` says 22 and
`engines.node` is `>=22`. Types describing a Node 26 API surface on a Node 22
runtime is how a call typechecks and throws at runtime. Moved 22.20.1 → 22.20.4,
which is the latest of the line the platform actually runs.
