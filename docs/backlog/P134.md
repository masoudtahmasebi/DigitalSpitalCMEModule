## P134-01 — The §9.6 audit is a script now

0.5 asks whether every read of a tenant-scoped table happens inside
`runInTenant`. The answer today is yes. The answer is also worthless as a
one-off: twenty-four tables against every repository method is not something a
person re-checks when a repository is added, and the failure is silent by
construction — under FORCE ROW LEVEL SECURITY a read on the bare pool matches
zero rows and a method that maps `rows[0]` to nulls reports "not configured".
P40-03 shipped exactly that, answering 202 while sending nothing.

`scripts/tenant-reads.mjs` reads the RLS table list **out of the migrations**
rather than restating it, so a table added later is covered without anybody
remembering. Two exemptions are allow-listed and each names its reason — both are
`SECURITY DEFINER` lookups that exist precisely so the tables are never read
outside a tenant context. It is in `pnpm verify` and in CI.

Watched to go red: a `pool.query("SELECT id, vnr FROM courses …")` added to the
upload repository was reported by file, line and table.

## P134-02 — `unused-rules.mjs` was reporting live rules as dead

Two defects, and the second is the dangerous one.

**It reported 88 symbols and 56 were types.** The type filter matched only inline
`type Foo,` re-exports, and `index.ts` states most of its types in
`export type { … }` blocks whose members carry no keyword. Two thirds noise, and
§9.3's whole answer — _"somebody has to look"_ — stops being true at that ratio.

**It reported symbols the API demonstrably calls.** The scan shelled out to
`grep -arn … | grep -v … | grep -v …` and only the **first** stage carried `-a`.
`packages/domain/src/copy.test.ts` legitimately contains a NUL byte — it is the
fixture proving `invalidCopyKeys` rejects a control character in a copy override
— so a matching line put a NUL on the pipe, the second `grep` declared **stdin**
binary, printed `binary file matches` instead of the lines, and the count came
back 0. `invalidCopyKeys` and `COPY_MAX_LENGTH` were both reported dead.

That is P76-01 one pipe stage further along: the fix was applied where the
problem was seen and not downstream of it — §9.11 half-done. And it fails in the
direction that costs something, because a live compliance rule reported as dead
is a rule somebody deletes.

The scan is in JavaScript now; there are no stages, so no stage can decide a
stream is binary. **88 hits → 31**, of which 29 are helpers used inside the
domain by exported functions that are themselves called, leaving **two** that are
used nowhere at all:

- **`partRange` — deleted.** Written in P129 so the server's signing and the
  browser's `Blob.slice` would tile identically, and `multipart.test.ts`'s header
  said so. It could never have been true: `@ds/sdk` has **no runtime dependencies
  at all**, deliberately, because it is embedded in the widget and the console —
  so the browser cannot import a slicer from the domain and never did. The
  agreement is real and comes from somewhere else: `planMultipart` decides
  `partBytes` once, the ticket carries that number, and the browser slices on
  `ticket.partBytes`. One number, not two that must match. The header now says
  that instead, because a comment claiming a property the code does not keep is
  what stopped anybody looking.
- **`hasAdaptiveSource` — kept, with the reason written down.** Adaptive delivery
  needs media transcoding, deferred by name in §3, so there is no HLS source to
  ask about. It stays beside `orderSources`, which already knows the distinction.

## P134-03 — `pnpm verify` was not the local equivalent of CI

§9.11: _"`pnpm verify` is the local equivalent of CI and must stay that way. A
check that runs only in CI is a check the person writing the code does not run."_

It ran the API's **unit** tests. The 562 **integration** tests against a real
Postgres ran only in CI, so every tenant-isolation and RLS assertion in the
platform was invisible at the terminal where the code is written. That is §9.1's
first form — the check is not run where the work happens — applied to the
strongest suite the project has.

`test:integration` is in `verify` now. Without a database it fails with the
message `testdb` already prints, which names the compose command to run: a loud,
actionable failure is the right answer, and a suite silently not running is not.

**One friction found doing it:** the cluster address is two variables,
`TEST_DB_HOST` and `POSTGRES_SUPERUSER_URL`, and setting only one gets you a
confusing failure from the other half — it cost two runs here. Recorded, not
fixed; it is a §9.10a shape and deserves its own change rather than a drive-by.

## Interpreted and clean

- **The customer guard covers everything (0.4).** 14 view kinds; 3 are
  platform-scoped and exempt by name; the other 11 — 9 NAV screens plus `course`
  and `new-course` — are all covered, because P127-01 inverted the guard into a
  deny-list. A screen added tomorrow fails safe into "choose a customer" rather
  than into a spinner. The count mismatch this section expects was the old
  `TENANT_VIEWS` allow-list and no longer exists.
- **No `azp` anywhere (0.6).** The token verifier never mentions it, so
  show-stopper S17's weakening is absent rather than merely unused.
- **Answer keys cannot leave (0.7).** The learner-facing `QuizOption` has no
  field capable of carrying correctness, so a leak is a compile error rather
  than something a reviewer must notice. `adminGetQuiz` is the one route that
  returns `isCorrect` and is author-only. `revealCorrectAnswers` exists but a
  points-bearing course cannot set it — the database refuses with
  `courses_no_answer_key_for_points`.
- **One password in a log, and it is the right one (0.8).**
  `bootstrap-admin.ts` prints the generated super-admin password once to an
  operator's terminal, which is the same one-time disclosure the console makes
  in "nur jetzt sichtbar". CI runs that binary only with no arguments, to assert
  it refuses, so the value never reaches a build log.
