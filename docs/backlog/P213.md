## What was already true, and is why this is small at the edges

The MEDICE site has two logins. One goes through Keycloak and its access token
lands in `$_SESSION`; the other is DocCheck, a cookie, involving no realm of
ours. `class-ds-lms-token-source.php` has recorded since P96 that a DocCheck
visitor holds no token — _"DocCheck does not identify a physician to the
accreditation chain"_ — and `class-ds-lms-renderer.php:281` writes
`signed-in="no"` for them, because `DS_LMS_Token_Source::available()` is false.

So the plugin already routes such a visitor to the widget's signed-out branch.
Nothing in WordPress needed changing. What changed is what that branch does.

**Verified:** `grep -n 'signed_in' wordpress/ds-lms/includes/class-ds-lms-renderer.php`
→ line 281 `$signed_in = DS_LMS_Token_Source::available();`.

## P213-01 — `doccheck_login_allowed` and `keycloak_login_allowed`

Two columns on `projects` (migration `0055`), both editable in Verwaltung →
Organisation, with defaults chosen so an installation that runs the migration
changes no behaviour: DocCheck **false** (nothing starts disclosing its
catalogue) and Keycloak **true** (nobody is signed out).

### Why the DocCheck column is also the preview switch

Because they are one fact. A DocCheck login yields no platform token, so
"DocCheck is permitted here" and "somebody holding no token may read this
project's catalogue" are the same sentence. Two columns would be two names for
one thing and the pair would drift (§9.10b). The identity is written into
migration 0055's header rather than left to be inferred.

### The pair rule, and where it is enforced

A project with **neither** method permitted is a project nobody can open — a
screen offering a state the product cannot serve (§9.2). It is refused in three
places, and the three are not redundant:

| Where                                        | For whom                                                     |
| -------------------------------------------- | ------------------------------------------------------------ |
| `signInMethodsProblem` in `@ds/domain`       | the rule itself, unit-tested, with the two callers below     |
| `updateProject`, against the **merged** pair | the operator: a 422 with a German sentence, on the form      |
| `projects_sign_in_method_check`              | every writer that is not this route — a seed, a psql session |

The middle one is the one worth arguing about. This route is a **PATCH**, so a
request naming one flag does not carry the other. A check over the submitted
fields alone passes every obvious test and still lets a project reach "neither"
in two individually legal requests — at which point the database CHECK refuses
it with a constraint name, which is a 500 and tells the operator nothing (§9.4).
So `updateProject` reads the stored pair first and judges what the row would
become.

**Watched red, and this is the case that matters.** With the merged read
replaced by `?? true`, the one-request case still passes and
_"refuses the second request that would leave nobody able to sign in"_ fails
with `expected 200 to be 422`.

## P213-02 — `GET /preview/courses` and `GET /preview/courses/{slug}`

The catalogue and one course's description, for a caller with no token.

### Three things make it safe, and none of them is in the controller

1. **Whether the project opted in** is `resolve_catalogue_preview` (0055): a
   `SECURITY DEFINER` function owned by `ds_binding_resolver`, with a
   three-column grant, whose predicate is `doccheck_login_allowed`. The same
   shape as `resolve_project_branding` (0007), `resolve_project_signin` (0028)
   and `resolve_public_image` (0054). A project that has not opted in yields no
   row and is therefore indistinguishable from one that does not exist.

2. **Which courses are visible** is the ordinary catalogue query, run inside
   `runInTenant` with the customer that function returned, as `learner`. RLS
   applies exactly as it does for a signed-in learner and the published and
   validity rules are the same code — there is no second catalogue to drift
   (§9.10b, §4 invariant 6).

3. **What a preview reader may do** is bounded by there being no user at all —
   not by a filter somebody has to remember. `CatalogService` skips the
   enrolment query entirely for `undefined`, and every route that advances a
   Fortbildung is on a controller this file does not touch.

**Watched red.** Removing `AND p.doccheck_login_allowed` from the function makes
the two refusal cases answer 200 where they expect 404 — a project that never
opted in, served.

### Why a separate controller and not `@Public()` on the real one

`@Public()` makes the auth guard skip the route **entirely**, so a signed-in
learner's token would be ignored and their own enrolment state would vanish from
their own catalogue. Two audiences needing different answers from the same data
is two routes over one service, not one route with a weaker guard.

### The 404 is deliberately uninformative

Unknown project, opted-out project and a request with no `X-DS-Project` header
all answer the same 404 (ADR-0007, §9.5). The widget does not tell them apart
either: it renders the signed-out notice for all three, which is the screen such
a visitor saw before this existed.

### `NO_USER` is `undefined`, and the first attempt was `""`

Worse than wrong. `enrolments.user_id` is a `uuid`, so an empty string does not
quietly match nothing — Postgres rejects it and the request 500s.

## P213-03 — what the visitor sees

`PreviewApp` replaces the single-sentence signed-out screen **when the API says
the project permits it**, and renders that sentence unchanged when it does not.
It asks with one request (`/preview/courses?page=1&perPage=1`), and the
signed-out test now asserts the whole request list is exactly that one path.

- A notice above the catalogue says what this login covers, **before** it is met
  (§9.4) — finding out by pressing a button is worse than being told.
- The catalogue, the hero, Übersicht, Experten/Referenten and Zertifizierung are
  the **same components** the signed-in screens use.
- The Mediathek tab is absent: its contents come from a route that requires a
  principal, so it could only ever render an error (§9.2).
- **Fortbildung starten** opens a modal dialog — focus-trapped, Escape and
  backdrop close it, focus restored — that names what a MEDICE account is for
  (progress, the Lernerfolgskontrolle, the Teilnahmebescheinigung, the
  Punktemeldung) and links to the host's own sign-in. It makes no request:
  there is none a preview reader could make that would succeed.

**Watched red**, both halves: forcing the catalogue past the 404 fails
_"a project that has not opted in … is unchanged"_, and neutering the dialog
fails all four participation cases.

The preview test drives `App`, not `PreviewApp` — §9.7, name the caller. A test
of `PreviewApp` alone would pass on a widget that never reaches it, and the
branch it hangs off is precisely the one that must still show the old screen.

## And one repair that was not asked for, found by the ticket's own mistake

I wrote `anonymousAccess(methods)` in `@ds/domain` — a TypeScript restatement of
"DocCheck permitted means the catalogue is readable" — exported it, and gave it
four tests. **Nothing called it**, and nothing should have: that decision is
`resolve_catalogue_preview`'s predicate, in SQL, which is where a disclosure
gate for an unauthenticated caller belongs. A second home for one fact (§9.10b)
is the very thing the two columns were kept from becoming.

It is deleted, with the reason left in its place.

What is worth more than the deletion is **why no check said so**.
`scripts/unused-rules.mjs` exists precisely for §9.3 — a rule written, exported,
exhaustively tested, called from nowhere — and it did not report this one. Its
export parser matched a name alone on a line indented by two spaces, which is
what a _multi-line_ `export { … } from "…"` looks like. `index.ts` has **41**
single-line export statements, and every name in them had never been scanned:

```
$ grep -cE '^export (type )?\{[^}]+\} from' packages/domain/src/index.ts
41
```

Among them `contentGates`, `isCourseComplete`, `punktemeldungOutcome`,
`resolveTenantContext` and `evaluateGate` — five compliance rules whose being
called is the entire question that script asks.

The parser now matches the **statement**, not the line. Its output grew from 32
names to 42, and three of the new ones deserve a look in their own ticket rather
than in this one — `evaluateGate`, `coverageBars` and `mediaSourceProblems` have
no caller outside `packages/domain`, and `evaluateGate` looks superseded by
`contentGates` (P87-03) rather than forgotten. Not touched here: deleting gating
code is a §2 human-review change and has nothing to do with DocCheck.

This is §9.1's second form — _the check that silently covers less than it
claims_ — in the script written to catch §9.3, found only because a rule it was
supposed to catch was one I had just written and knew about.

## What is **not** in this ticket

- **No new sign-in flow.** The platform does not accept, verify or read a
  DocCheck cookie. It cannot: DocCheck authenticates to the customer's site, not
  to us. The preview is bounded by the project's own setting and by having no
  user, and that is the whole of it.
- **No participation without Keycloak, anywhere.** Enrolment, watch progress,
  the Lernerfolgskontrolle, the Evaluationsbogen, the EFN, the Punktemeldung and
  the certificate are untouched and still require a bearer validated against
  JWKS (§4 invariant 2).
- **The seed does not turn the preview on** for MEDICE or anyone else. It is an
  operator-editable column and a seed supplies a starting value where there is
  nothing, never a replacement (§9.10b). Turning it on is one tick in
  Verwaltung → Organisation.
