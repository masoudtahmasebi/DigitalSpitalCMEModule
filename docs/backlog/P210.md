# P210 — three tickets from the board: DEP-37, DEP-36, DEP-34

Three reports from Amruth, all Major, all _Ready for Work_. They are unrelated
to each other; what they share is that each one turned out to have a cause a
layer below where it was reported.

---

## P210-01 — the course list is ordered newest first (DEP-37)

> Newly added courses should appear at the top of the list so that
> administrators and users can immediately see the latest content without having
> to scroll through the entire catalogue.

Both lists were `ORDER BY title`:

| list                  | query                                         |
| --------------------- | --------------------------------------------- |
| the learner catalogue | `catalog.repository.ts` — paged, ten per page |
| Verwaltung            | `admin.repository.ts` — unpaged               |

Alphabetical is a real order and the wrong one for the question somebody is
asking when they open the screen: _what did I just make?_ Both now sort
`created_at DESC`.

**The title is the tiebreak, and it is not decoration.** `created_at` is a
`timestamptz`; two courses written by one seed can share a value, and a
`LIMIT`/`OFFSET` over a non-deterministic order is how a row appears on two
pages or on none. The tiebreak is what makes the paging total.

### The fixture that could not have told the two apart

`learning-flow`'s three courses were inserted in the order their titles sort, so
title-ascending and newest-first produce the same list. Confirmed while
sabotaging the fix — reverting the sort returned `lf-plain, lf-free, lf-course`,
which is what newest-first also returns. A case built on those three would have
passed either way (§9.1).

So both cases create a course named **"Zzz zuletzt angelegt"**: it sorts last
and is made last, which is the only shape that can distinguish the orders.

### A comment this change made false

`apps/e2e/support/catalogue.ts` explains its pager entirely in terms of the
alphabet — _"E2E Zwei Module sorts after every E2E Fortbildung … once ten titles
sort before it, it is on page two"_. True when written, and now history: this
run's course is the newest, so it is on page one.

The pager stays, because the property it defends is not the page number — a
second run in the same minute, or a seed that adds courses afterwards, puts it
back on page two. But the explanation is corrected rather than left standing.
A comment that explains live behaviour by an order the code no longer uses is
exactly the kind that gets believed (§11.9).

## P210-02 — a screen change puts the learner at the top (DEP-36)

> Opening a course from the course list navigates to the course detail page with
> the scroll position in the middle of the page. The top of the page (course
> header/hero section) is not visible on load.

The widget swaps screens **in place** — `Routed` renders either the catalogue or
the course into the same element, and `Loaded` swaps the outline for a player or
an exam inside that. Nothing navigates in the browser's sense: no document load,
no anchor. So the host page keeps whatever offset the previous screen left, and
a physician who scrolled the catalogue to find a course lands halfway down its
hero.

`useScrollToTopOnChange(key)` scrolls to the top when the key changes, in two
places:

- `Routed`, keyed on the selected course — the catalogue/course switch;
- `Loaded`, keyed on **the same route the address is written from** — so a
  screen that gets an address gets this too, without anybody remembering. That
  is the §9.3 failure avoided rather than repeated.

Deliberately **not** keyed on the tab: the tab row is already near the top, and
moving the page when somebody clicks a control they can see is its own defect.

### The half that a naive fix gets wrong

"Scroll to the top on mount" is the obvious implementation and is wrong. An
embed can sit anywhere on a customer's WordPress page, and yanking the reader
upward because the widget _finished loading_ is a defect nobody has reported
only because the widget did not do it. The first value of the key is recorded
and not acted on.

That absence is asserted as deliberately as the presence, with a sentinel rather
than a bare "not called" — P205-01's lesson: an absence assertion a tick after
render passes whether the rule holds or React simply has not flushed yet.

**Watched red twice:** removing the first-render guard fails both cases
(_"the widget moved the page before anybody navigated"_), and removing the
scroll itself fails the first (the reported defect).

## P210-03 — the content form says which fields it needs (DEP-34)

> Required fields are not visibly marked in the course creation form … The Add
> button is enabled only when required information is filled, making it unclear
> which fields need to be completed.

Two defects in one sentence, and the second is much the larger.

### 1. "Required" was inferred from an absence

The console marked **optional** fields — `(optional)` after the label — and left
required ones unmarked. On a form where which fields are required changes with a
dropdown at the top, that is a rule the author has to reconstruct.

`Field` now takes `required`. The asterisk is `aria-hidden` and the accessible
name carries the word, because _"Titel star"_ is not what a screen reader should
say and _"Titel (erforderlich)"_ is.

### 2. The rule existed, was tested, and the console did not call it

`contentProblems` in `@ds/domain` decides that a video needs a source and a
length and that a text lesson needs a body. It is exhaustively unit-tested. The
API calls it. **The console did not** — `ContentForm` disabled its submit on
`title.trim() === ""` and nothing else.

So the console offered **Hinzufügen** for a video with no source and no
duration, and the API answered 422. That is CLAUDE.md §9.3 — a rule written is
not a rule enforced — producing §9.2, a control that can only produce an error.

The form now calls the same function, over a draft that mirrors exactly what
`onSubmit` posts (`nullable`, blank-row filtering and all): a check over
different values from the ones that get sent would be a different check.

**Which fields carry an asterisk is derived from the same call**, not restated:

```ts
const requiredFields = new Set(contentProblems({ kind, title: "", … all empty }));
```

_What would this complain about if nothing were filled in?_ is precisely the set
of required fields. A hand-written map would be a second copy of a rule that
already has one home, and the kind whose requirements are least obvious —
`video` — is exactly the one it would eventually get wrong.

### 3. A disabled button that says why

The other half of §9.4. A control that refuses and gives no reason leaves the
person guessing, which is what the report is about. The form now prints
`de.newCourse.missing(...)` — the creation wizard's own sentence, so the console
says this one thing one way — naming **fields, never values** (§9.5).

`sourceMimeType` is excluded from that sentence on purpose: it is a _wrong_
value rather than a missing one, and _"Es fehlt noch: Format"_ would send an
author looking for an empty field they have already filled in.

The module and chapter form had the same shape one layer down — it computed
`some()` to disable the button, so it knew what was missing and told nobody. It
now maps to labels and prints the same sentence.

**Watched red:** with the old rule restored (title-only, no sentence, no
marker), both new cases fail.
