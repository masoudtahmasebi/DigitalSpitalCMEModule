# P22 · The console's own way in

Two things reported from the live deployment, and one gap they uncovered.

---

## P22-01 · A project with no Keycloak binding is still a project — **done**

- **Estimate:** 2 h · **Review gate: human — auth**

A super administrator signed in successfully and then:

```
GET /admin/customers  →  200
GET /admin/courses    →  401 Unauthenticated
```

It reads as "the login is broken". The session was fine.

### What was wrong

`authenticateStaffPlane` resolved the project through `resolve_project_binding`
(migration 0002), whose repository treats a NULL `keycloak_issuer` or
`keycloak_audience` as **not found**. That is right for a learner — a project
with no binding cannot validate anybody's token — and wrong for an operator: a
staff session is local to the platform and never touches an identity provider
at all (ADR-0012). The only field the staff plane wanted out of that lookup was
`customer_id`.

So an unrelated fact — "Keycloak is not configured here" — refused every
tenant-scoped console screen. Two ordinary ways to be in that state:

- **A project created through the console.** Its Keycloak fields are optional
  there, deliberately: they configure the learner plane, and a customer served
  only by the standalone portal may never need them.
- **A fresh installation.** It has no project at all until an operator makes
  one — through the screens that were refusing.

### And the refusals were indistinguishable

Three unrelated failures produced a bare `401` with no `detail`: an expired
session, an unknown project slug, and a tenant screen reached with no project
named. The console treats 401 as "session gone" and returns to the login form,
so a **configuration** problem presented as a **logout**. That is why this was
almost unreadable from the browser — which is where it was found.

**Acceptance criteria**

- [x] Migration 0026 adds `resolve_project_tenant`, returning two ids and no
      Keycloak fields — so it cannot be misused to validate a token, which is
      why it is a second function rather than a flag on the first
- [x] The staff plane resolves the tenant through it; the learner plane is
      untouched and still gets a generic 401 for an unknown _or unbound_ slug
- [x] An authenticated operator naming a project that does not exist gets a
      **404 with `detail`**, because whether a project exists is not a secret
      from somebody the platform has already identified
- [x] A tenant-scoped route reached with no `X-DS-Project` gets **422 with
      `detail`**, not 401 — it is a missing selection, not a missing credential
- [x] No grant reaching the resolved customer stays **403**
- [x] `contracts/openapi.yaml` states the policy per plane on `ProjectHeader`,
      which is the one place all 60 references read it from
- [x] Six integration cases in `hierarchy.integration.test.ts` reproduce the
      report and pin each answer

## P22-02 · Configurable second factor — **open**

- **Estimate:** 6 h · **Depends on:** — · **Review gate: human — auth**

Requested: _"it should be possible to turn off or on 2fa or make it mandatory or
not mandatory"_.

Today `requiresSecondFactor(role)` is a constant — `super_admin` always,
everybody else never — and there is **no way to remove or reset an enrolled
second factor at all**. An operator who loses their phone is locked out
permanently, with no recovery path anywhere in the product. That gap is not in
the request and is the more urgent half of it.

See the ticket body once implemented.

---

## P22-03 · The console picks its own project — **open**

- **Estimate:** 4 h · **Depends on:** P22-01

`ADMIN_DEFAULT_PROJECT_SLUG` in deploy config decides which tenant every console
screen acts within, which is why a fresh installation has no way in: the slug
names a project that does not exist yet, and cannot exist until an operator uses
the screens the slug is breaking.

Same removal P18-03 wants, now with a reproduction behind it.
