# P22 · The console's own way in

Two things reported from the live deployment, and one gap they uncovered.

---

## P22-01 · A project with no Keycloak binding is still a project — **done**

- **Estimate:** 2 h · **Review gate: human — auth**

A super administrator signed in successfully and then:

```
GET /admin/customers  →  200
GET /admin/courses    →  401 Unauthenticated
```

It reads as "the login is broken". The session was fine.

### What was wrong

`authenticateStaffPlane` resolved the project through `resolve_project_binding`
(migration 0002), whose repository treats a NULL `keycloak_issuer` or
`keycloak_audience` as **not found**. That is right for a learner — a project
with no binding cannot validate anybody's token — and wrong for an operator: a
staff session is local to the platform and never touches an identity provider
at all (ADR-0012). The only field the staff plane wanted out of that lookup was
`customer_id`.

So an unrelated fact — "Keycloak is not configured here" — refused every
tenant-scoped console screen. Two ordinary ways to be in that state:

- **A project created through the console.** Its Keycloak fields are optional
  there, deliberately: they configure the learner plane, and a customer served
  only by the standalone portal may never need them.
- **A fresh installation.** It has no project at all until an operator makes
  one — through the screens that were refusing.

### And the refusals were indistinguishable

Three unrelated failures produced a bare `401` with no `detail`: an expired
session, an unknown project slug, and a tenant screen reached with no project
named. The console treats 401 as "session gone" and returns to the login form,
so a **configuration** problem presented as a **logout**. That is why this was
almost unreadable from the browser — which is where it was found.

**Acceptance criteria**

- [x] Migration 0026 adds `resolve_project_tenant`, returning two ids and no
      Keycloak fields — so it cannot be misused to validate a token, which is
      why it is a second function rather than a flag on the first
- [x] The staff plane resolves the tenant through it; the learner plane is
      untouched and still gets a generic 401 for an unknown _or unbound_ slug
- [x] An authenticated operator naming a project that does not exist gets a
      **404 with `detail`**, because whether a project exists is not a secret
      from somebody the platform has already identified
- [x] A tenant-scoped route reached with no `X-DS-Project` gets **422 with
      `detail`**, not 401 — it is a missing selection, not a missing credential
- [x] No grant reaching the resolved customer stays **403**
- [x] `contracts/openapi.yaml` states the policy per plane on `ProjectHeader`,
      which is the one place all 60 references read it from
- [x] Six integration cases in `hierarchy.integration.test.ts` reproduce the
      report and pin each answer

## P22-02 · Configurable second factor — **done**

- **Estimate:** 6 h · **Review gate: human — auth**

Requested: _"it should be possible to turn off or on 2fa or make it mandatory or
not mandatory"_. `requiresSecondFactor(role)` was a constant — `super_admin`
always, everybody else never.

### The gap the request uncovered, which is the more urgent half

There was **no way to remove or reset an enrolled second factor at all**. No
endpoint, no admin action, nothing. An operator who lost their phone was locked
out permanently — and for a super administrator, the one role that was _forced_
to enrol, a lost device could end the platform's only unrestricted account with
no recovery whatsoever.

A lockout with no workaround is a worse failure than the credential theft strict
2FA prevents, because the theft at least has a response.

### Three values, and why `optional` is not "off"

| Value      | Means                                                         |
| ---------- | ------------------------------------------------------------- |
| `disabled` | Not offered, and an already-enrolled secret is not asked for. |
| `optional` | Enrol if you want to; **if you have, you must use it**.       |
| `required` | Everybody enrols, and is sent to enrolment if they have not.  |

Relaxing a policy must never make a stolen password sufficient for somebody who
had already protected themselves. Turning it off for such an account is
`disabled` — a different, audited choice, and the one that recovers a lost
device.

### Scope, and the strictest-wins rule

Per customer, plus one row for the platform itself, which is the scope a
`super_admin` belongs to since they belong to no customer. An account holding
grants in several scopes gets **the strictest**, and that direction is the whole
point: if the loosest won, a customer's `required` would be worth nothing the
moment somebody also held a grant somewhere relaxed, and finding that somewhere
would be an attacker's first move.

The platform default stays `required` — ADR-0012's reasoning has not stopped
being true. What changed is that it is a _default_ rather than a law, because a
policy nobody can change is not a policy. Only a super administrator may change
it; a customer administrator may set their own customer's and no other.

**Acceptance criteria**

- [x] Migration 0027 adds `admin_2fa_policy`, one row per customer plus exactly
      one platform row, enforced by two partial unique indexes — two platform
      rows would disagree about the strictest policy in the system
- [x] It lives beside the staff tables, not as a column on `customers`, because
      it is read during sign-in **before** any tenant context exists and
      `customers` is under FORCE RLS — a column there would read as empty and
      silently fall back to the default for everyone
- [x] `secondFactorStep(policy, enrolled)` and
      `applicableSecondFactorPolicy(grants, platform, perCustomer)` are pure and
      exhaustively tested: all six policy × enrolment combinations, plus
      order-independence of the strictest-wins fold
- [x] `GET`/`PUT /admin/auth/second-factor/policy`; every operator may read, the
      scope decides who may write
- [x] `DELETE /admin/auth/second-factor` — an operator removes their own,
      refused under `required`, which is what makes "mandatory" mean something
- [x] `POST /admin/staff/{id}/second-factor/reset` — the lost-device path.
      Clears the secret, the enrolment **and** the replay counter, revokes every
      session, and does not sign the target in: under `required` their next
      sign-in goes to enrolment, so access is restored without the bar moving
- [x] Nobody may reset their own. Self-reset would turn a stolen session into a
      permanently weakened account and would step around the `required` policy
- [x] Every change is audited with `weakened: true|false` carried in the entry,
      because "somebody relaxed a security policy" is the fact an auditor scans
      for, and making them diff two rows to find it is how it gets missed
- [x] 18 integration cases against a real database, covering the policy on the
      sign-in path and the whole reset flow

## P22-03 · The console names a customer, not a project — **done**

- **Estimate:** 4 h · **Depends on:** P22-01 · **Review gate: human — auth**

Reported after P22-01 landed, and only visible _because_ it landed — the
misleading 401 had been hiding it:

```
GET /admin/customers  →  200
GET /admin/courses    →  404  "Dieses Projekt existiert nicht."
```

### Two faults, and the second is the one that mattered

**`ADMIN_DEFAULT_PROJECT_SLUG` named one project for the whole console.** A
super administrator could therefore act inside exactly one customer, and if the
named project did not exist — which it does not on a fresh installation —
every tenant screen answered 404 while the platform screens worked.

**And creating a project is itself a tenant-scoped write.** `POST
/admin/projects` carries `@TenantDb()`, so it needed an `X-DS-Project` header,
which needed a project. A customer with none had no way to get one. That is
**every customer on the day it is created**, and every fresh installation: the
console could not be used to set up the thing it is used to set up.

`deploy.sh` does not seed, deliberately, and the MEDICE seed is not in the
image — so there was no path to a working installation that did not involve
somebody running SQL by hand.

### The way out

`X-DS-Customer` names the customer directly. It carries an **id** and needs no
lookup: `staffTenantContext` already decides whether an operator's grants reach
a customer, so an id they hold no grant for is a 403 whether or not it exists.
There is nothing to enumerate with, which is why this is a staff-plane header
with no learner equivalent.

Both headers end at the same `resolveStaffTenant`, so the two ways of naming a
tenant cannot drift apart on authorization — the only difference is how the
customer id was arrived at.

**Acceptance criteria**

- [x] A customer with no departments and no projects is reachable, and its first
      department and first project can be created through the console
- [x] Those rows land in the named customer and no other — asserted, because a
      header that named the tenant and then wrote somewhere else would be the
      worst possible version of this fix
- [x] An operator with no grant reaching the named customer gets 403, and an id
      that is not a customer at all gets the same 403 — no oracle
- [x] Neither header still answers 422 with a detail, unchanged from P22-01
- [x] The console shows a customer picker to a `super_admin` only. A
      `customer_admin` has exactly one, on their grant, so a picker would be a
      control with a single option
- [x] A tenant screen with no customer chosen says so, and says something
      different when no customer exists yet — "pick one above" is unhelpful
      advice when there is nothing to pick
- [x] `ADMIN_DEFAULT_PROJECT_SLUG` is gone from the console's config
- [x] Six integration cases; verified in Chromium against the built console

## P22-04 · The console could read but not write after a reload — **done**

- **Estimate:** 2 h · **Review gate: human — auth**

Reported from the live console, trying to create the very first customer:

```
GET  /admin/customers  →  200
POST /admin/customers  →  403   (no detail)
```

### What was wrong

The console kept its CSRF token in a **module variable**, set by `login` and
`verify` and by nothing else. The session cookie is `httpOnly` and survives a
page reload; the variable does not.

So a reloaded tab — or a second tab, or a restored browser session — could read
everything and write nothing. **CSRF is only checked on unsafe methods**, which
is precisely why every read went on working and hid it, and why the 403 read as
"you are not allowed to do this" when it meant "this tab has forgotten a token
it never had a way to recover".

There was no recovery short of signing out and back in, and nothing in the
product said so.

### The fix, and why it is not a weakening

The token is now also set as a cookie the page can read. That is the textbook
double-submit shape: the protection comes from a cross-origin attacker being
unable to **read** the token, not from the page being unable to — the page has
to send it.

What stays true:

- `httpOnly: true` on the session cookie, `httpOnly: false` on this one. The
  session token remains unreadable from JavaScript, which is the property that
  matters; a CSRF token alone authenticates nothing.
- The server still compares the header against `csrf_token_hash`. Nothing about
  verification changed — only where the client keeps its copy.
- `csrfCookieOptions()` derives from `cookieOptions()` rather than repeating it,
  so domain and `secure` cannot drift apart between the two cookies. Two cookies
  disagreeing about their scope is how one of them silently stops arriving.

**Acceptance criteria**

- [x] A session reconstructed from **cookies only** — the JSON body's token
      thrown away, which is exactly what a reload loses — can create a customer
- [x] A write with no CSRF token is still 403
- [x] A write with another session's CSRF token is still 403
- [x] The CSRF cookie is not `httpOnly`; the session cookie is
- [x] Both cookies carry identical `Path`, `Domain` and `Secure`
- [x] Both sign-in exits set both cookies. The TOTP exit was missed on the first
      attempt, and it is the exit **every `super_admin` takes** — so the accounts
      obliged to use a second factor would have been the ones still unable to
      write
- [x] Six integration cases
