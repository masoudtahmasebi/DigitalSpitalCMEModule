# P144 — Nothing in the API waits for ever, and saturation is visible

The client's ask, after two outages and a deploy flag that did not exist:

> "can we please make sure this does not happen again in the whole application
> that api hangs?"

P142 fixed the deadlock. This closes the rest of the class from P143 and makes
the next one visible in its first minute instead of its twenty-second hour.

---

## P144-01 — A deadline on every outbound call, and a check that keeps it true

**Status:** done.

### The rule

`fetch` has no default timeout. A request handler runs inside the RLS
transaction holding a pooled connection, so a call that never returns is a
connection never released — ten of those and the API stops answering. That is
P142's outage arriving by a second road, and P70-02 is the record of the exact
precondition (a container with no route out) lasting months without anything
saying so.

`shared/deadline-fetch.ts` is now the one way this application makes an outbound
request. Two budgets:

- `CONTROL_DEADLINE_MS` (15 s) — HEAD, DELETE, list, a token exchange, a webhook.
- `TRANSFER_DEADLINE_MS` (90 s) — the far side is doing real work while we wait.
  The ceiling is not arbitrary: the handler holds an open transaction and
  `idle_in_transaction_session_timeout` is 120 s (P141), so a longer deadline
  would be decided by Postgres killing the connection — the request fails either
  way and the reason is lost.

A caller's own `signal` is kept rather than combined. Combining would silently
shorten an explicit 90 s to the default 15 s and produce a bug report about
large files only, which is the hardest kind to reproduce.

Errors name **host and path, never the query.** Every storage URL is presigned,
so its query carries `X-Amz-Signature`; an error quoting the URL would put a
live capability into the log and any response that echoed it (§9.5).

### The check, and the version of it that was worthless

`scripts/check-deadlines.mjs`, in `pnpm verify` and CI. Two rules, and **the
first draft had only one**:

1. Every `fetch(` passes a `signal:` in the same argument list.
2. No `typeof fetch = fetch`. An injectable `fetchImpl` whose default is a bare
   `fetch` leaves every production caller unbounded while every test passes its
   own — and it is not a call site, so rule 1 cannot see it.

Rule 2 exists because the one-rule version **stayed green** when
`object-storage.ts` was reverted to the exact defect the script was written for.
That is §9.1 caught in the act: a check that cannot go red on its own subject.
With rule 2 added it immediately found two more files nobody had listed.

It also reported `media-url.ts:2` on its first run — the header says "something a
browser can fetch (P10-09)" and the regex matched the prose. Comments are blanked
before matching, offsets preserved so line numbers stay true. A check whose first
finding is a sentence is a check nobody trusts twice.

Three sabotages watched red: reverting the object-storage default, reverting the
certificate archive's, and removing the OIDC signal. One sabotage stayed green
and needed a **test** instead — deleting `completeMultipart`'s explicit
`TRANSFER_DEADLINE_MS` leaves the wrapped default in place, so the static rule is
satisfied and the property that broke is _which budget_. That is now an assertion
in `object-storage-multipart.test.ts`.

`deadline-fetch.test.ts` opens a server that accepts a connection and never
answers. Its first test is the control: a bare `fetch` against it does not
return. Without that, every other test would pass against a `withDeadline` that
did nothing.

## P144-02 — Pool saturation is a number, and something reads it

**Status:** done.

`ds_pg_pool_total`, `ds_pg_pool_idle` and `ds_pg_pool_waiting`, labelled by pool,
on `/metrics`. `Metrics.registerGauge` reads them at scrape time rather than
keeping a copy — a copy kept in step by an interval is wrong exactly while
nobody is looking.

**`ds_pg_pool_waiting` is the number that would have named the outage in its
first minute.** It was available all along as a synchronous property needing no
connection to read, on a process that could not answer `SELECT 1`. The one
component unable to reach its database was the one holding the explanation, and
nobody had exported it.

P140's watchdog now thresholds on it. A metric nobody reads is P140's own
lesson: `/metrics` was exposed for months and scraped by nothing.

## P144-03 — `deploy.sh --install-timers`

**Status:** done. Reported from the host:

```
$ sudo .../deploy.sh --install-timers
xx unknown option: --install-timers
```

The operator ran exactly what the deploy's own warning told them to run. The
flag had never existed — §9.2 in a shell script, and the same shape as
`course_editor` (P38-02): the offer and the acceptance live in different places
and nothing compared them.

Now they are compared. `infra/deploy/options.test.sh` derives both sides from the
file: every `--flag` the script tells an operator to type must be one its `case`
accepts, and every flag its refusal lists must be too. It cannot go stale. Both
halves watched red.

`unknown option` now names the valid options — the operator's real question is
"does this feature exist", and "unknown option" answers "you mistyped" (§9.4).

Two more defects found by **running it**, which is the only reason they were
found at all:

- The systemd guard tested for the `systemctl` **binary**, which exists in
  containers that have no systemd. The next line then failed with "Failed to
  connect to bus" and took an otherwise successful deploy down. It now asks
  whether systemd is usable, and under `--install-timers` — where installing
  was the whole job — it refuses loudly rather than exiting 0 and letting the
  operator believe timers exist.
- `enable --now` returning 0 says the command ran, not that three timers are
  armed. It now asserts the effect (§9.9a), which is the whole of why P140
  exists.
- A failed timer install no longer fails a deploy that swapped the containers
  and passed every check. It warns and names the command to run.

## What this does not do

**The storage round trip still happens inside the RLS transaction** (P143-05).
It is bounded now, so the worst case is a bounded stall rather than an outage —
but ten slow uploads still occupy ten database connections for up to 90 seconds.
Narrowing the interceptor is a real change to ADR-0002's safety argument and is
not a fix to make quietly.

**Browser-side calls still have no deadline** (P143-04). That is why the client
saw `(pending)` and no error rather than a message. It costs a spinner, not a
connection, and it is the next one.
