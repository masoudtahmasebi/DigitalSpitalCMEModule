# P212 — a stable public URL for an image

The client, on P211's answer:

> what do you mean? why doesn't the images have a link to our system that gets
> translated to a public s3 url? like you give aaaa.com/imageurl.jpg -> our
> system generates the public url and gives it back to the browser -> public url?

They were right, and P211's write-up gave a false choice — "nothing, or make a
bucket prefix public". The indirection is the third option and the standard one.

It also contained a number I had not traced: I wrote that the signed URL "works
for minutes". `config.ts` defaults `S3_URL_TTL_SEC` to `3600` and
`.env.example:297` sets `3600`. **One hour.**

---

## P212-01 — `GET /media/:id`

Media is addressed internally as `s3://<key>` and handed to a browser as a
presigned URL. That is right for a lecture video: the signature **is** the
authorisation, and it is the only kind that can travel on a `<video>` or `<img>`
request, because neither carries an Authorization header. Verified rather than
assumed — the three call sites are `CourseHeader.tsx:124`, `CourseList.tsx:617`
and `ExpertsTab.tsx:54`, all plain `<img src>`.

It is wrong for a course's Titelbild and a Referent's photograph. Those get
pasted into the customer's own site, and they are re-fetched on a page that may
have been open since yesterday.

So: the **id** is the stable part of the address, and the signature is minted
per request behind it. A 302, not a proxy — a redirect costs one small response,
while proxying would put every course cover on the API's event loop and through
its egress. `Cache-Control: no-store` on the redirect, because the _location_
expires while the URL the browser holds does not.

## Where the security decision actually lives

The route is `@Public()`. It has to be: there is no token on an `<img>` request
and the URL is meant for pages seen by people with no account. So what protects
it is that the id is an unguessable uuid — and **that is only acceptable because
of what it may serve.**

A course cover is a marketing image. A lecture video is gated content whose
watch percentage decides a CME point, and an unguessable id is not that gate.

The images-only rule is therefore **in SQL**, not in the controller:
`resolve_public_image` (migration 0054) is `SECURITY DEFINER`, owned by
`ds_binding_resolver`, granted exactly three columns of `media_assets`, with the
predicate `mime_type LIKE 'image/%'`. This follows `resolve_project_branding`
(0007) deliberately — the same shape, for the same reason, with the same comment
about widening it taking a migration in a diff.

A controller check would have been one line and could be edited in a hurry. This
one cannot serve a video even if the controller is wrong.

**A NULL `mime_type` is refused.** P79-01 records that null means "not
described"; an undescribed object is not evidence that it is an image.

**Watched red, and this is the case that matters.** With the predicate removed
from the function — the controller untouched — the video case answers **302 and
serves the lecture**. Both refusals go red together:

```
× refuses a video, because an unguessable id is not a watch gate
× refuses an object whose type was never described
  AssertionError: expected 302 to be 404
```

## `publicUrl`, built by the API

The console is **told** the URL rather than assembling one from its own
`DS_API_BASE`, which would be a second opinion that drifts the day the API moves
(§9.10b). It is null for a non-image, for an undescribed object, and for a
deployment that has not been told its own address — all three are "there is no
such URL", and offering one that 404s is §9.2.

`PUBLIC_API_BASE_URL` is **not** derived from the request's `Host` header, and
that is §9.5's rule about a reset link's origin, one step stronger: this URL is
**stored** in `courses.hero_image_url`, so a request through an unexpected host
would persist an address nobody else can resolve. The deploy passes
`API_DOMAIN_URL`, which it already derives for Caddy's CSP — the same fact
reaching a second reader rather than a new setting somebody must remember
(§9.9).

## In the console

- The Mediathek offers **URL kopieren** on images, and only on images — the
  client's _"the mediathek should also have a possibility to get the url, like
  the wordpress uploader"_. The confirmation is deliberate: a clipboard write is
  invisible, and the same person reported being unsure whether a save had
  happened. Where `navigator.clipboard` is unavailable, the URL is shown to copy
  by hand rather than a lie.
- **Picking an image hands the field the stable URL**, not the reference. A
  video still hands back the reference, and the existing case asserting that is
  unchanged and still right.
