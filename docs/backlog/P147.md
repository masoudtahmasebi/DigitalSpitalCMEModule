## 12.4 Structured findings

### 1

- **Section / case:** 3.1
- **Severity:** high
- **Summary:** Six tests asserted `not.toContain("isCorrect")` and would all
  have stayed green against a learner response carrying `correctAnswerIds`,
  `answer_key` or `solution`.
- **Root cause:** §9.1 — a check that silently covers less than it claims. The
  contract's words are "no correctness marker of any kind"; the assertion
  covered one field name.
- **Fix applied:** `apps/api/test/support/answer-leak.ts` matches the family on
  JSON _keys_, wired into the four suites that serve a learner a quiz.
- **Test added:** yes — `answer-leak.test.ts`, 13 cases, including the ones it
  must **not** fire on.
- **Status:** fixed

### 2

- **Section / case:** 3.1 (found while fixing 1)
- **Severity:** medium
- **Summary:** The first matcher globbed `*correct*` and failed two legitimate
  learner-facing fields — `correctionWindowUntil` and `correctCount`.
- **Root cause:** §9.1 again, inverted: a check that cries wolf gets switched
  off, and then protects nothing.
- **Fix applied:** the answer-key idioms named explicitly, with the trade
  written down — an invented `rightOption` would slip, and the real guarantee is
  structural (the learner `Quiz` type has no field to carry it, P4-01).
- **Test added:** yes — the four "must leave alone" cases.
- **Status:** fixed

### 3

- **Section / case:** 4.3
- **Severity:** high
- **Summary:** With `ALERT_WEBHOOK_URL` unset the alert sink is `undefined` and
  nothing says so; an EIV deadline alert then reaches the container log and
  nowhere else.
- **Root cause:** §9.10a — a setting whose second consequence nobody wrote down.
  It is a supported configuration, so nothing failed.
- **Fix applied:** `EivScheduler.onModuleInit` warns once at boot, naming what
  will not happen. Once, not per sweep — a warning on every tick is wallpaper.
- **Test added:** no — it is a boot log line with no branch behind it. The
  behaviour it warns about (log-only alerting) is already covered by
  `eiv-worker.integration.test.ts`.
- **Status:** fixed

### 4

- **Section / case:** 4.4
- **Severity:** high
- **Summary:** The VNR-password test asserted the **key name**
  (`not.toContain("vnrPassword")`), which passes against the secret under any
  other key — in a test whose neighbouring line already checked the stamp image
  _by value_.
- **Root cause:** §9.1, and the specific shape where one half of a rule stays
  right while the other drifts.
- **Fix applied:** the test now sets a password and asserts the **value** is
  absent from the write's own response and from the read.
- **Test added:** yes — rewritten in place.
- **Status:** fixed

### 5

- **Section / case:** 4.4 (a claim I nearly filed as critical)
- **Severity:** — (not a defect)
- **Summary:** Asserting `vnr_password_enc` holds ciphertext **failed**: under
  `NODE_ENV=test` with no `SECRETS_KMS_KEY` the column holds plaintext.
- **Root cause:** none. `createSecretCipher` returns `PlaintextSecretCipher`
  only without a key, and that class **throws at construction under
  `NODE_ENV=production`** — asserted in `packages/secrets`.
- **Fix applied:** none, deliberately. The finding is recorded _in the test_, so
  the next person to write that assertion does not conclude we store VNR
  passwords in the clear.
- **Test added:** no — the invariant is tested where it lives.
- **Status:** fixed (as documentation)

### 6

- **Section / case:** 7.9
- **Severity:** critical
- **Summary:** §4 invariant 8 requires **every** EIV attempt in the audit log
  "including failures". Only `eiv.submitted` was asserted; no test covered
  `eiv.attempt_failed`.
- **Root cause:** §9.7 — the happy path was tested and the path an auditor
  actually asks about was not. A Punktemeldung that did not land, leaving no
  trace, makes the log answer "we never tried".
- **Fix applied:** none needed in the product — the write exists. The evidence
  did not.
- **Test added:** yes — `eiv-worker.integration.test.ts`, "records
  eiv.attempt_failed, carrying neither the EFN nor the VNR password". The
  failure is produced by a **closed local port**, not the mock's behaviour
  header, because that header is set by the harness and not by the worker —
  using it would test the harness.
- **Status:** fixed. **Watched red:** with the audit write disabled it fails
  with "a failed attempt left no audit row: expected [] to have a length of 1".
- **Human review:** required — `eiv`.

### 7

- **Section / case:** 9.4
- **Severity:** medium
- **Summary:** All four seeds call `assertSchemaCurrent`; `bootstrap-admin.ts`,
  which also writes, did not.
- **Root cause:** §9.9 — a schema older than the code fails deep and blames the
  writer. This is the more dangerous omission of the five, because
  `bootstrap-admin` is what someone runs on a **fresh host**, which is exactly
  where a migration may not have run.
- **Fix applied:** it asserts before its first write.
- **Test added:** no new test — `journey.integration.test.ts` already runs
  `bootstrap-admin` end to end, and it is what caught finding 8 within one run.
- **Status:** fixed

### 8

- **Section / case:** 9.4 (exposed by fixing 7)
- **Severity:** medium
- **Summary:** `assertSchemaCurrent` resolved its migrations directory as
  `dirname(import.meta.url)/migrations` — correct in the image, wrong in a
  checkout. Run from source it failed with
  `ENOENT: scandir '.../apps/api/src/migrations'`.
- **Root cause:** §9.9 again — an error naming the wrong thing. It reads as a
  missing directory; it is one path meaning two things in two environments.
  Latent because every existing caller is a `dist/` entrypoint.
- **Fix applied:** the image's directory when it exists, the checkout's
  `db/migrations` otherwise, and a named error when neither does.
- **Test added:** no — `journey.integration.test.ts` exercises the from-source
  path and failed on it, which is what found this.
- **Status:** fixed

## Two QA items whose premise is wrong for this codebase

Recorded rather than "fixed", because acting on them would break working code.

- **8.2 — "no `X-DS-Project` header (this header was deprecated)."** It is not
  deprecated here; it is the **active** tenant header — 88 operations take it via
  the shared `ProjectHeader` `$ref` in `contracts/openapi.yaml` (the literal
  string appears 10 times; P148's verifier pass caught that conflation) and its own guard suite
  (`tenant-header.integration.test.ts`). Removing it would break every
  tenant-scoped route.
- **10.1 — "find the 2 GiB cap … no multipart."** The cap is 5 GiB and multipart
  exists (`MULTIPART_PART_BYTES`, `MULTIPART_MAX_PARTS`, P129). The prompt
  predates that work.
