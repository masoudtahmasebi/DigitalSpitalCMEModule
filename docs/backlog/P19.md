# P19 · The mobile layout

Seven screens at 430 px, delivered after the desktop pages. They are
authoritative for small viewports the same way `docs/design/screens/` is for
large ones, and the reviewer who checks them is the one who asks whether you
have eyes.

The screens are in [`docs/design/mobile/`](../design/mobile/), with a first
reading of what differs in that directory's README.

**Not started.** Written down now so the intake is recorded and the work is
estimable; the deployment came first.

---

## P19-01 · The sticky progress module — **done**

- **Estimate:** 4 h · **Depends on:** P15-04

The only screen in the mobile set that adds behaviour rather than rearranging
it, and the reason it led: it is the **resume affordance on the device most
learners will use**.

A teardrop floats over the course pages, closed by default, showing a progress
ring. Pressing it opens a teal card — "Ihr Fortschritt", a donut reading _2 von
3_, "Sie haben 2 von 3 Modulen abgeschlossen", and **Fortbildung fortsetzen**.

It exists because the wide layout's progress card has nowhere to go at 430 px:
the module count, the watch percentage and the resume button stacked cost a
third of the viewport, on pages whose whole purpose is a video.

**Acceptance criteria**

- [x] Every number comes from the same `EnrolmentState` the inline card reads,
      which only ever arrives from the API. A floating widget that computed its
      own progress would be a second answer to a question that decides a CME
      point
- [x] The inline card is hidden below `sm` and this replaces it. Two progress
      panels on one 430 px screen would be two places to read the same number,
      which is how they come to disagree
- [x] It renders on **every** course screen, not only the outline — its whole
      reason for existing is being the resume affordance _while a video is
      playing_, which is the one screen the inline card is not on
- [x] Dismissible. The drawing has no close control, so the heading is the
      toggle: it looks exactly as drawn and is operable by touch, by keyboard
      and by a screen reader. Escape closes it too
- [x] Focus follows the disclosure in both directions, from an effect rather
      than from the click handler — the element to focus does not exist yet at
      the moment the state changes, because the branch rendering it has just
      been unmounted
- [x] The closed button is named by the whole sentence. A button called
      "Fortschritt" tells a screen-reader user nothing they did not already
      suspect
- [x] `pb-[env(safe-area-inset-bottom)]`: on an iPhone the bottom of the
      viewport is the home indicator, and a button under it is a button that
      scrolls the page instead
- [x] The ring survives a course with **no modules** — `completed / total` is a
      division, and an unauthored course has a total of zero. `NaN` in a
      `stroke-dasharray` renders as nothing at all, silently
- [x] And never draws more than a full ring, whatever the server said: a ratio
      above one wraps the stroke back over itself and reads as _less_ progress
- [x] Seven component tests, and the open and closed states checked in Chromium
      at 430 px against the export

**One thing left open.** The card floats over the page content, which is what
"sticky" means and what the drawing shows — but nothing yet guarantees it
clears the _player's own controls_, because the player at 430 px is P19-03.
Checking that is part of that ticket rather than assumed here.

## P19-02 · The catalogue at 430 px — **done**

- **Estimate:** 3 h · **Depends on:** —

Verified in Chromium at 430 x 932 against the real production bundle, not by
reading CSS. The API is stubbed at the network layer, because this is a
question about layout and a real Postgres would have supplied the same three
fields more slowly.

| Element            | Verdict before                                      | Now                                                                                  |
| ------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Hero photograph    | **wrong** — `hidden sm:block`, flat teal below `sm` | a 27.5 rem full-bleed band, as drawn                                                 |
| Hero heading       | **wrong** — white on teal, over the photograph      | near-black on white, **below** the photograph                                        |
| CME seal           | **wrong** — hidden below `sm`                       | 11 rem, inside the photograph's bottom-left                                          |
| Gap above the hero | **wrong** — 40 px of nothing                        | gone; see below                                                                      |
| Section tabs       | **wrong** — folder tabs at 430 px, unreadable       | the selected one is the card's heading; the others are full-width buttons underneath |
| Filter selects     | ok — stacked full-width                             | unchanged                                                                            |
| Filter chevron     | **wrong** — inset rounded square                    | full-height block, rounded bottom-right                                              |
| Course cards       | ok — `sm:flex-row` already stacks them              | unchanged, and measured rather than rewritten                                        |
| Pagination         | **wrong** — one row, three groups squeezed          | numbers on their own line above Zurück / Vor                                         |
| Active page marker | **wrong** — against the number                      | on the rail above it, as drawn                                                       |
| Step arrows        | **wrong** — grey chevrons in a grey disc            | long arrows; disabled is a pale brand disc with a white arrow                        |

**Two arrangements, one tree.** The narrow catalogue is not the wide one
scaled: the heading moves out from on top of the photograph, the seal changes
anchor, and the tab row moves below the panel. It is still one DOM tree —
`sm:hidden` / `hidden sm:block` twins would put the `<h1>` and every tab label
in the document twice, and `display: none` only removes the duplicate for
something that has the stylesheet, which a screen reader walking the markup
does not.

**The 40 px of nothing** was not a mobile bug. `BrandLogo` returns `null` when
a customer has set no logo; its wrapper's `px-4 pt-4` inside a `space-y-6` did
not, so every project without a logo had 40 px of blank above a hero the layout
draws flush to the host page's header. Wrong at 1440 px too, and invisible
until the catalogue was screenshotted against a drawing that has no gap.

**Acceptance criteria**

- [x] Checked in a real browser at 430 px against the export, element by element
- [x] The wide layout is unchanged — re-shot at 1440 px and compared
- [x] One tree, no duplicated headings or labels
- [x] The tab row stays reachable on a phone. The drawing shows only "Weitere"
      below the card, which is what a two-section catalogue with one selected
      looks like — not a catalogue whose other sections are unreachable
- [x] Tailwind sees every class name spelled in full; nothing is interpolated
      into a class string, which is a class Tailwind never generates
- [x] No horizontal scroll at 320 px, the narrowest phone still in use.
      **It did scroll**, by 14 px, and the cause is one German word:
      "Fortbildungsbereich" is 302 px at the heading's size and a 320 px phone
      gives it 288. `break-words` on the two headings a customer writes — the
      hero's and the course title's — because a compound noun should wrap
      rather than widen the page. It breaks only when a word cannot fit, so
      nothing moves at any width where it does
- [x] Every interactive element meets **WCAG 2.2 AA target size, 24 x 24** —
      measured in the browser, smallest is 32 x 36. **Not 44 x 44**, and that
      is deliberate: the layout draws its own buttons at 38-40 px, so a 44 px
      floor would be this repository overruling the design on the reviewer's
      own screen. The AAA figure is worth raising with the client rather than
      imposing silently

## P19-03 · Course detail, player and completion at 430 px — **specified, not built**

- **Estimate:** 5 h · **Depends on:** P19-02

The itemised comparison, from the export at 2× against the real bundle
rendered in Chromium at 430 px. Written before any code, per the criterion
below.

### Course detail (`detailseite-uebersicht.png`)

| Element              | The export                                                                                              | Today                                             | Verdict                           |
| -------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | --------------------------------- |
| Course artwork       | full-bleed, edge to edge, **above** the title, no radius                                                | an inset rounded card, **below** the title        | **wrong**                         |
| Title band           | dark teal, full-bleed, white bold, **below** the artwork                                                | a rounded teal card **above** the artwork         | **wrong**                         |
| Meta card            | white, centred, **stacked**: points pill, then clock + duration, then modules, then a full-width button | one horizontal row, divider, right-aligned button | **wrong**                         |
| Points pill          | orange, `4                                                                                              | CME Punkte`, one pill with an internal rule       | an orange square beside grey text | **wrong** |
| Zurück zur Übersicht | below the card, outside it, with a long left arrow                                                      | present — placement to be measured                | check                             |
| Tabs                 | the selected one is a centred teal heading **inside** the card; the others are not folder tabs          | four folder tabs wrapping to two rows             | **wrong**                         |
| Sticky module        | drawn near the content card's top-right                                                                 | viewport bottom-right                             | see below                         |

**The tab treatment is the catalogue's**, already built in P19-02: the selected
section's name becomes the card's heading and the rest move out of the folder
row. That it appears twice in the export is the strongest evidence the pattern
is intended rather than incidental, and the implementation should share one
component rather than growing a second copy.

**The artwork and the title band are the same change as ticket #63's split
hero**, which is a desktop item. Doing them together is cheaper than doing
either alone and stops the two arrangements being derived from different
readings of the same drawing.

**Where the sticky module sits is genuinely ambiguous.** The export is a
full-page render, so a `position: fixed` element appears wherever the designer
parked it — near the content card's top-right here, and alone on its own sheet
in `progress-sticky-module.png`. It is currently at the viewport's bottom
right, which is the conventional place and does not cover the card's heading.
Worth one question to the designer rather than a guess that moves it twice.

**Acceptance criteria**

- [x] An itemised comparison per screen, with a verdict per element — done for
      the course detail above, outstanding for the other four
- [ ] Every screen checked in a real browser at 430 px
- [ ] The tab treatment is **one** component shared with the catalogue, not a
      second copy of the same idea
- [ ] The sticky module does not cover the player's own controls — the one
      thing P19-01 could not check, because the player at 430 px is this ticket
- [ ] No horizontal scroll at 320 px. The catalogue needed `break-words` on two
      German headings to get there; the course title is the same kind of string
- [ ] Every interactive element meets WCAG 2.2 AA target size, 24 × 24, measured
      rather than assumed
- [ ] The widget's Shadow DOM styles hold: nothing here may leak to a host page,
      and a host's media queries may not reach in

## Deliberately not in this ticket

**The admin console.** These seven screens are the learner surface. The console
is a desk tool used on a laptop, and making it responsive is real work with no
identified user — worth doing when somebody asks, not because the learner
frontend got there first.
