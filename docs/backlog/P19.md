# P19 · The mobile layout

Seven screens at 430 px, delivered after the desktop pages. They are
authoritative for small viewports the same way `docs/design/screens/` is for
large ones, and the reviewer who checks them is the one who asks whether you
have eyes.

The screens are in [`docs/design/mobile/`](../design/mobile/), with a first
reading of what differs in that directory's README.

**Not started.** Written down now so the intake is recorded and the work is
estimable; the deployment came first.

---

## P19-01 · The sticky progress module — **new component**

- **Estimate:** 4 h · **Depends on:** P15-04

The only screen here that adds behaviour rather than rearranging it, and the
reason it leads: it is the **resume affordance on the device most learners will
use**.

A teardrop button floats over the course pages, closed by default, showing a
progress ring. Pressing it opens a card — "Ihr Fortschritt", a donut reading
_2 von 3_, "Sie haben 2 von 3 Modulen abgeschlossen", and **Fortbildung
fortsetzen**.

It exists because the desktop's sticky meta bar has nowhere to go on a 430 px
screen: the clock, the module count and the resume button do not fit on one row,
and stacking them costs a third of a viewport whose whole purpose is a video.

**Acceptance criteria**

- [ ] Closed by default; open state is remembered for the session, not persisted
- [ ] The count and the ring come from the same rollup the desktop reads — one
      rollup path (CLAUDE.md §4 invariant 6), so a learner cannot see two
      different answers on two devices
- [ ] **Fortbildung fortsetzen** goes to `resumeContentId`, exactly as the
      catalogue's button does (P15-04) — not to the outline
- [ ] Hidden entirely on viewports where the desktop meta bar is shown, so the
      two are never both on screen
- [ ] Does not cover the player's controls when open — it is a floating element
      over a page with a video on it
- [ ] Reachable and operable from a keyboard and named for a screen reader; it
      is a button, not a decoration

## P19-02 · The catalogue at 430 px — **done**

- **Estimate:** 3 h · **Depends on:** —

Verified in Chromium at 430 x 932 against the real production bundle, not by
reading CSS. The API is stubbed at the network layer, because this is a
question about layout and a real Postgres would have supplied the same three
fields more slowly.

| Element            | Verdict before                                      | Now                                                                                  |
| ------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Hero photograph    | **wrong** — `hidden sm:block`, flat teal below `sm` | a 27.5 rem full-bleed band, as drawn                                                 |
| Hero heading       | **wrong** — white on teal, over the photograph      | near-black on white, **below** the photograph                                        |
| CME seal           | **wrong** — hidden below `sm`                       | 11 rem, inside the photograph's bottom-left                                          |
| Gap above the hero | **wrong** — 40 px of nothing                        | gone; see below                                                                      |
| Section tabs       | **wrong** — folder tabs at 430 px, unreadable       | the selected one is the card's heading; the others are full-width buttons underneath |
| Filter selects     | ok — stacked full-width                             | unchanged                                                                            |
| Filter chevron     | **wrong** — inset rounded square                    | full-height block, rounded bottom-right                                              |
| Course cards       | ok — `sm:flex-row` already stacks them              | unchanged, and measured rather than rewritten                                        |
| Pagination         | **wrong** — one row, three groups squeezed          | numbers on their own line above Zurück / Vor                                         |
| Active page marker | **wrong** — against the number                      | on the rail above it, as drawn                                                       |
| Step arrows        | **wrong** — grey chevrons in a grey disc            | long arrows; disabled is a pale brand disc with a white arrow                        |

**Two arrangements, one tree.** The narrow catalogue is not the wide one
scaled: the heading moves out from on top of the photograph, the seal changes
anchor, and the tab row moves below the panel. It is still one DOM tree —
`sm:hidden` / `hidden sm:block` twins would put the `<h1>` and every tab label
in the document twice, and `display: none` only removes the duplicate for
something that has the stylesheet, which a screen reader walking the markup
does not.

**The 40 px of nothing** was not a mobile bug. `BrandLogo` returns `null` when
a customer has set no logo; its wrapper's `px-4 pt-4` inside a `space-y-6` did
not, so every project without a logo had 40 px of blank above a hero the layout
draws flush to the host page's header. Wrong at 1440 px too, and invisible
until the catalogue was screenshotted against a drawing that has no gap.

**Acceptance criteria**

- [x] Checked in a real browser at 430 px against the export, element by element
- [x] The wide layout is unchanged — re-shot at 1440 px and compared
- [x] One tree, no duplicated headings or labels
- [x] The tab row stays reachable on a phone. The drawing shows only "Weitere"
      below the card, which is what a two-section catalogue with one selected
      looks like — not a catalogue whose other sections are unreachable
- [x] Tailwind sees every class name spelled in full; nothing is interpolated
      into a class string, which is a class Tailwind never generates
- [x] No horizontal scroll at 320 px, the narrowest phone still in use.
      **It did scroll**, by 14 px, and the cause is one German word:
      "Fortbildungsbereich" is 302 px at the heading's size and a 320 px phone
      gives it 288. `break-words` on the two headings a customer writes — the
      hero's and the course title's — because a compound noun should wrap
      rather than widen the page. It breaks only when a word cannot fit, so
      nothing moves at any width where it does
- [x] Every interactive element meets **WCAG 2.2 AA target size, 24 x 24** —
      measured in the browser, smallest is 32 x 36. **Not 44 x 44**, and that
      is deliberate: the layout draws its own buttons at 38-40 px, so a 44 px
      floor would be this repository overruling the design on the reviewer's
      own screen. The AAA figure is worth raising with the client rather than
      imposing silently

## P19-03 · Course detail, player and completion at 430 px — **open**

- **Estimate:** 5 h · **Depends on:** P19-02

The remaining four exports: `detailseite-uebersicht`,
`detailseite-experten-referenten`, `detailseite-zertifizierung`,
`player-zusammenfassung` and `player-ansicht-abgeschlossen`. Same method —
itemised comparison, then a browser at 430 px.

Known before starting: **navigation collapses to a hamburger**, which has no
desktop equivalent, so the menu's contents and its open state are both new
rather than rearranged.

**Acceptance criteria**

- [ ] An itemised comparison per screen, with a verdict per element
- [ ] Every screen checked in a real browser at 430 px
- [ ] No horizontal scroll at 320 px — the narrowest phone still in use
- [ ] Tap targets at least 44 px, which the filter chips currently are not
- [ ] The widget's Shadow DOM styles hold: nothing here may leak to a host page,
      and a host's media queries may not reach in

## Deliberately not in this ticket

**The admin console.** These seven screens are the learner surface. The console
is a desk tool used on a laptop, and making it responsive is real work with no
identified user — worth doing when somebody asks, not because the learner
frontend got there first.
