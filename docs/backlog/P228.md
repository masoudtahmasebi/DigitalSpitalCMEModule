# P228 — the console's design tokens are its own, and every one of them resolves

The review's **Package A**:

> **Admin design-token isolation** (`--ds-admin-*`); acceptance: admin token
> changes must not alter widget screenshots.

It turned out to have a defect inside it. The isolation was the ask; the thing
found on the way is that one of the console's tokens had never had a value.

---

## P228-01 — `--ds-surface-sunken` was read twice and defined nowhere

Introduced by **P88-01** on 17.08 and referenced at two sites:

| Site                  | What it is for                                |
| --------------------- | --------------------------------------------- |
| `MediaCard.tsx:171`   | the well a thumbnail sits in                  |
| `MediaDialog.tsx:390` | the tint on a drop target while dragging over |

Defined in `apps/admin/src/styles.css`? No. In the Tailwind preset? No. Written
by `brandingCssVars`? No. Nowhere, and with **no fallback** at either read site.

### What that renders

An unresolved custom property with no fallback does not fall back to the
property's previous value — it makes the **whole declaration invalid at
computed-value time**, so the property takes its inherited or initial value.
For `background-color` that is `transparent`.

Measured in Chromium rather than read off the spec:

```
defined    -> rgb(233, 233, 231)
undefined  -> rgba(0, 0, 0, 0)     <- what shipped
fallback   -> rgb(220, 220, 218)
```

So `MediaThumbnail`'s frame has been transparent for three and a half weeks,
and the drag-over state of the upload dialog tints with nothing — the only
feedback a person dragging a file gets is the border changing colour.

### Why nothing failed

Every layer answered politely.

- Tailwind emits `background-color: var(--ds-surface-sunken)` for **any** name.
  The arbitrary-value syntax `bg-[color:var(--x)]` is a string; there is no
  spelling it can reject.
- The browser drops the declaration without a console message.
- `getPropertyValue` for an undeclared custom property returns `""` — not
  `undefined`, not a throw.
- jsdom has no cascade, so all 352 admin component tests were blind to it.

And the comment directly above the first read site says:

> A grey rectangle where a picture should be is indistinguishable from a
> feature that was never built

which is true, and was describing a grey rectangle that was not there. §11.9 in
one line: a comment is a claim, not a fact.

**Fixed** with `--ds-admin-surface-sunken: #dcdcda` — `--ds-admin-surface`
(`#e9e9e7`) with 13 subtracted from each channel, 13/255 = 5.1 %. An equal
delta on all three keeps the neutral exactly as neutral as its parent (R = G,
B one step lower, before and after), so it is a darker shade of the page rather
than a fourth grey with its own cast.

## P228-02 — the namespace, which is what the review actually asked for

`--ds-brand-*`, `--ds-accent`, `--ds-font-family`, `--ds-radius`,
`--ds-content-max` are the **shared** namespace: declared with a fallback in
`packages/config/tailwind.preset.js`, written at runtime by `brandingCssVars`
in `@ds/domain` from a customer's project settings, rendered by the learner
widget.

`--ds-ink`, `--ds-ink-muted`, `--ds-surface`, `--ds-hairline` were the admin
console's alone — and **at a call site the two are typographically identical**.
A console author inventing a neutral and a branding author adding a
customer-settable colour were writing into one namespace under two different
sets of rules, and which rules applied to a given name was knowable only by
grepping.

That is how P228-01 happened: a bare `--ds-x` that only the console defines
reads exactly like a branding token a customer can set, so "somebody must be
setting this" is the natural assumption at the read site.

Renamed, 92 occurrences across 10 files, all inside `apps/admin/src`:

```
--ds-ink            -> --ds-admin-ink
--ds-ink-muted      -> --ds-admin-ink-muted
--ds-surface        -> --ds-admin-surface
--ds-hairline       -> --ds-admin-hairline
--ds-surface-sunken -> --ds-admin-surface-sunken
```

The console still **overrides** `--ds-brand-*` at `:root` with DigitalSpital's
own palette, which is deliberate and documented (P22-08): the console is not a
customer surface, and chrome that changed colour as the operator switched
customers would make "which customer am I in" a thing you read off the paint
instead of off the app bar.

### The acceptance criterion, proved at the source

> admin token changes must not alter widget screenshots

Rather than a screenshot-diff suite — which is slow, flaky, and would only
notice a regression after somebody made one — this is now true **by
construction** and checked statically:

- a `--ds-admin-*` token is defined in the admin's stylesheet and read by the
  admin and nothing else;
- a bare `--ds-*` token is shared: the console may **override** one and may
  never **invent** one.

An admin token change is therefore, by the rule, a change to something the
widget does not read and the shared preset does not declare.

And for this PR specifically, the stronger and simpler evidence:

```
$ git diff --stat HEAD -- apps/widget apps/portal packages/config
(no output)
```

## P228-03 — `scripts/check-design-tokens.mjs`, in `pnpm verify`

Three rules, each watched red on a real sabotage:

| Sabotage                                          | Reported                                                                  |
| ------------------------------------------------- | ------------------------------------------------------------------------- |
| delete the `--ds-admin-surface-sunken` definition | both original read sites, `MediaCard.tsx:171` and `MediaDialog.tsx:390`   |
| have the widget read `--ds-admin-ink`             | `apps/widget/src/layout.ts:53: the widget reads --ds-admin-ink …`         |
| define a bare `--ds-panel-tint` in the console    | `styles.css:84: … name it --ds-admin-panel-tint, or put it in the preset` |

A read **with** a fallback is deliberately not a finding: `var(--x, 1430px)` is
self-sufficient, and `--ds-content-max` is written that way on purpose.

### The checker's own defect, found by its first sabotage

It reported the right two files at the **wrong lines** — `MediaCard.tsx:104`
for a read on line 171. Cause: the comment stripper every checker in
`scripts/` uses replaces a block comment with **one space**, which collapses
every line it spanned, and the reported line is counted from the stripped text.

A correct finding pointing at the wrong place is how a checker gets distrusted
rather than read (§9.4). Comments are now replaced by as many spaces and
newlines as they occupied, preserving both line and column.

**And the same bug was in `scripts/screen-intros.mjs`** — §11.11, fix the class
in the same turn. Swept all three comment-stripping checkers:

| Script                    | Line reported from | Verdict                                                  |
| ------------------------- | ------------------ | -------------------------------------------------------- |
| `check-design-tokens.mjs` | stripped source    | **was wrong** — fixed                                    |
| `screen-intros.mjs`       | stripped source    | **was wrong** — fixed                                    |
| `aria-props.mjs`          | raw source         | correct; it strips only inside a props declaration block |

## P228-04 — and the same property one layer out, in the browser

`konsole-layout.spec.ts` now asserts that every `--ds-admin-*` token resolves
**in the bundle the browser was served**, and that an element backed by
`--ds-admin-surface-sunken` computes to something other than
`rgba(0, 0, 0, 0)`.

`check:design-tokens` reads source. This reads what Vite emitted, what the
browser parsed and what the cascade produced — §9.9 one layer down: a
definition in the repository is a definition in the stylesheet only if the
build kept it.

The token list is **named in the test**, not scraped from the stylesheet: a
test that derives its expectations from the thing under test agrees with it
however wrong it is (§9.1).

Watched red on the same sabotage, through a full rebuild of the admin image:

```
✘ jeder Design-Token der Verwaltung löst sich im ausgelieferten Bundle auf
  Error: --ds-admin-surface-sunken resolves to nothing in the served bundle,
  so every declaration reading it is invalid at computed-value time and the
  property renders as if it had never been set
  Expected: not ""
```

## What this ticket does not do

- **It does not restyle anything.** One token gains the value it always should
  have had; the other four are the same colours under new names.
- **It does not namespace the shared preset.** `--ds-brand-*` and friends stay
  where they are, because the widget and a customer's branding both read them.
- **It does not add a screenshot-diff suite.** See above for why.

## A finding that belongs to a different ticket

While confirming where this check would run, I found that **`pnpm verify` and
CI are not the same set**, in the direction CLAUDE.md §9.11 does not consider:

> `pnpm verify` is the local equivalent of CI and must stay that way. A check
> that runs only in CI is a check the person writing the code does not run.

The converse is now the live problem. Derived mechanically rather than by eye:
**16 of the 32 steps in `pnpm verify` are named in no workflow.** One of those,
`check:sdk`, is covered by a CI step spelled differently (_"Verify generated SDK
matches the contract"_ regenerates and diffs — the same property, and the header
of `check-sdk.mjs` says so). `check:runtime-config` is **not**: CI's _"The
console's runtime config is generated, and refuses bad input"_ runs the
entrypoint with explicit `-e` flags and tests the script's behaviour, while the
script asserts that `docker-compose.prod.yml` **supplies** every value the
entrypoint requires — which is the property P44-02 was written for, and a
different one.

So **15 checks cannot stop a merge**, among them `check:seed-overwrites`
(a seed silently replacing an operator's typed course values on every deploy,
§9.10b), `check:csp` (the class that blocked every video upload for months,
§9.13), `check:eiv-settings` (a §2 human-review area) and `check:docs-commands`
(§11's _"Run once: `sudo deploy.sh --install-timers`"_).

That is **P229**, not this ticket, and it is filed rather than absorbed here.
