# P182 — Monitoring, backup and restore, made usable rather than present

**Raised by:** the client, 03.09.2026:

> after that create a complete monitoring and backup and resotre section if it
> does not exist already and make it usable for our future usages.

**Branch** `claude/education-platform-roadmap-3vgrqh`.

---

## The honest starting position

Backups, health probes, metrics, a watchdog and a restore runbook all existed.
This ticket is three defects found by asking, of each of them, the question in
its own header — _would this have told anybody?_ — and two of the three answers
were no.

## P182-01 — The restore was a runbook, not a command

`docs/runbook-backup.md` §3 walked an operator through fetching the object,
decrypting it with `openssl` over a hex-converted key, and running `pg_restore`.
Every step correct, and roughly a dozen of them, to be performed at three in the
morning by somebody who did not write it.

The code to do all of it was already in the image — `backup database` decrypts
nothing but encrypts with exactly the inverse of those steps. So `backup list`
and `backup restore` now exist, the runbook's new §3.0 is the one command, and
the manual path stays below it for the case where the image itself is what you
have lost.

`restore` refuses when `RESTORE_DATABASE_URL` names the same database as
`BACKUP_DATABASE_URL`. Restoring over a live database because "the backup is
probably fine" is how a bad night becomes a bad week, and the refusal is the
runbook's own §3.3 advice made mechanical.

_Verified:_ five integration cases under _"the operator's restore, which is the
one that has to work at 22:00"_ — a real round trip into a database that was
empty, no copy of the database left on disk afterwards, an archive encrypted
with a different key refused rather than half-restored, a key that is not there
named, and `list` printing keys so one can be copied instead of guessed.

The refusal itself was shipped untested, which is §9.3 in the one place it costs
most, and is now `backup.test.ts`: ten cases, most of them pairs of strings that
are **not equal and name the same database** — a different role, a different
password, `?sslmode=require`, an omitted default port — because string equality
is what somebody would reach for and every one of those would pass it. Broken to
`a === b` and watched: six of the ten go red.

## P182-02 — CI went red for a reason that had nothing to do with the commit

On 03.09 `pnpm audit --prod` socket-timed-out against `registry.npmjs.org` for
four minutes on a push to `main`. The step exited non-zero, and because it was
**first** in the Security audit job, every step after it was **skipped** —
configuration drift, the role matrix, tenant reads, outbound deadlines, and
gitleaks. A registry outage silently disabled the secret scanner.

Two changes, and the ordering is the more important one:

- The audits go **last**. Everything above them runs offline and is evidence
  about the diff; everything below asks somebody else a question. Ordered this
  way, a bad answer costs the answer and nothing else.
- `scripts/audit-dependencies.mjs` judges the **report** rather than the exit
  code, so an advisory blocks and an unreachable registry warns loudly without
  blocking. That is not a weakening: `pnpm audit` exits non-zero for both, and a
  gate that cannot tell "you have a vulnerable dependency" from "npm is down" is
  a gate that gets disabled the first time it is wrong.

_Verified:_ `scripts/audit-dependencies.test.mjs`, ten assertions over recorded
reports — an advisory, a clean report, a network failure, malformed JSON — run
by `pnpm verify` and by CI immediately before the wrapper itself.

## P182-03 — A failed backup sent a heartbeat saying the host was healthy

The one worth the ticket, and it was in the systemd units.

`ds-backup.service` and `ds-backup-verify.service` both carry
`OnFailure=ds-watchdog.service`. That reads as "a failed backup raises the
alarm". It did not, because of what the watchdog checks: containers,
`/health/ready`, and callers queued for a database connection. A backup that
cannot reach the bucket leaves every one of those green. So:

1. the nightly backup fails;
2. systemd starts the watchdog because of `OnFailure=`;
3. the watchdog finds nothing wrong — correctly, nothing it looks at _is_ wrong;
4. it exits 0, and **sends the heartbeat**.

The failure of the backup therefore produced an _affirmative_ signal to the
external monitor that the installation was healthy. CLAUDE.md §9.1 in its purest
form — a gate green because of what it is not scanning — wired to a trigger that
made it look deliberate.

`infra/deploy/backup-state.sh` adds a fourth check, asked every two minutes from
systemd's own record rather than by starting a container: is the timer armed,
did the last run succeed, when did one last succeed (over 30 h is reported), and
did the last `backup verify` succeed. `OnFailure=` stays — it makes the report
immediate rather than up to two minutes late — but nothing depends on it any
more.

The 30 h threshold is arithmetic, not a number that sounds right:
`OnCalendar=02:15` with `RandomizedDelaySec=300` puts two successes at most
24 h 5 min apart, the unit's `TimeoutStartSec` allows the run 2 h, so 26 h 5 min
is the largest healthy gap. 30 h leaves just under four hours of slack and still
reports a single missed night the same morning.

The rule is pure and its host facts are gathered separately, because a host
where the backup has not run since Tuesday is not a fixture anybody can arrange.

_Verified:_ `backup-state.test.sh`, fourteen cases including both directions of
every rule and the 30 h boundary to the second. Broken twice and watched to go
red: the backup result ignored (which is the pre-P182-03 blind spot restored),
and the threshold widened to a week.

## P182-04 — `infra/deploy/backup.timer` was still telling people to install it by hand

P144-01 moved the systemd units into `deploy.sh`, which writes all six and arms
the three timers on every deploy and then asserts systemd lists them. The file
they came from stayed in the repository, and `docs/runbook-backup.md` §1 still
said to copy its four sections into `/etc/systemd/system/`.

It had diverged: hard-coded `/home/ds/…` paths, no watchdog units, and its
`OnFailure=` line **commented out**. An operator following the runbook would
have installed an older set of units that alert nobody. Two homes for one value,
and the stale one was the one the documentation pointed at (§9.10b).

Deleted. The units live in `ds_install_timers` and nowhere else, and the runbook
now says you do not install them.

## P182-05 — the deploy applies the setting it was telling a human to apply

P180-01 moved `EIV_WORKER_ENABLED`, `EIV_BASE_URL` and `EIV_ALLOW_LIVE` into
`platform_settings`, and the deploy **refused** while any of them remained in
`config.env` — with a good message naming the console screen and the `sed` to
run. A migration cannot read `config.env`, so the table starts with the worker
off and the register on `mock`, and the old setting reaches its new home only if
a person performs a step.

That is the mechanism §9.9 exists to reject, one level up: _documentation
instructing a human to apply a setting is a setting that is not applied._ The
consequence here is an installation that has silently stopped filing
Punktemeldungen while every screen looks well — which is exactly the failure the
refusal's own text warns about, left to a manual step to prevent.

§9.9's rule for this case is explicit — if a deploy _can_ apply a setting, it
applies it — and it can: it has `psql`, and it is holding the file. So
`ds_eiv_carry_forward` writes the endpoint and the worker flag into
`platform_settings`, then removes the three lines, then asserts the file
actually shrank (§9.9a: `sed -i` returns 0 on a file it changed nothing in, and
a variable left behind would be carried again on every future deploy, over
whatever the operator had since set).

**What it will not carry is the whole of the refusal.** Consent to file at the
live register was a string in a file that nobody signed; P180-01 made it a name
and a timestamp, because a Punktemeldung cannot be withdrawn once the correction
window closes (ADR-0005). So `EIV_ALLOW_LIVE`, an `EIV_BASE_URL` naming the live
register, and any host this platform does not recognise each stop the deploy and
ask for a person. The endpoint is judged **before** the flag, so an installation
pointed at the live register is told about the register — that is the thing that
decides whose record is touched.

It cannot overwrite a console edit, which is §9.10b's trap: the carry is driven
by the variables' own presence and ends by deleting them, so a second deploy
finds nothing to carry and does not touch the table.

_Verified:_ the decision is `ds_eiv_carry_plan` in `eiv-endpoint.sh`, pure and
separate from the half that needs a host, over 303 assertions in
`eiv-endpoint.test.sh` — every carry in both directions, every spelling of "on"
that has been written into a config file, and a property sweep over 210
combinations asserting that **no input produces a plan that carries `live`**.
Broken three ways and watched red: `live` carried instead of refused (18 red,
including the property), only `yes` read as on (11 red — a disabled worker armed
is the silent direction), and the "nothing left to carry" case dropped, which
would reset the table on every deploy.

### And the sweep that found four more, which is why §11 rule 11 is a rule

Having changed the deploy's reading of those three names, the same search over
the whole repository (§11 rule 11 — fix the class in the same turn, unprompted)
turned up four places P180-01 had missed, and none of them would have failed:

| Where                       | What was true                                                                                                                                                                                   |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/api/src/eiv-check.ts` | `./dsc eiv` read `EIV_BASE_URL` and `EIV_ALLOW_LIVE`, and told the operator they "must all be set in config.env" — the exact edit that now stops the next deploy                                |
| `infra/deploy/dsc`          | and it could not have worked anyway: `docker compose run` gives a container the environment the **compose file** declares, so `EIV_BASE_URL=… ./dsc eiv` set a variable the container never saw |
| five documents              | still instructing an operator to set the moved variables — `docs/eiv-test-system.md` told them to put `EIV_ALLOW_LIVE=yes` into `config.env`                                                    |
| `apps/e2e/support/stack.ts` | a dead `EIV_WORKER_ENABLED: "no"`, reading as the reason the browser suite is stable when what actually keeps it stable is the migration's default                                              |

`./dsc eiv` is the entrypoint an operator uses to prove the EIV connection, and
it could not be given a connection to prove. Its four variables are now
`EIV_CHECK_*` and `EIV_VNR*`, forwarded by `dsc` as bare `-e NAME` so the VNR
password is taken from the environment and never written into an argv.

_Assumed:_ that `docker compose run -e NAME` (no `=value`) forwards the value
from the invoking environment. The CLI accepts the flag — checked — but this
sandbox has no Docker daemon, so the forwarding itself is **not** executed here.
It is `docker run`'s documented behaviour and Compose inherits it; the first
`./dsc eiv` on a host is what confirms it.

**And the class fix, which is the part worth keeping.**
`check-eiv-settings.mjs` had reported success through all of this, because:

- it looked for `process.env["X"]`, `process.env.X` and `config.X`, and
  `eiv-check.ts` used its own `env("…")` helper — §9.1's second form, a check
  covering less than it claims. The rule is now the blunter and more honest one:
  the name anywhere outside a comment.
- its four globs all aimed at `src/`, so `apps/e2e` (which has none) and
  `scripts/` were never read at all;
- **it did not read documentation**, and documentation is the interface a person
  acts through. It now refuses a document that shows one of the three being
  _set_, while leaving a document free to _name_ them — which is what every one
  of them does when it explains where the setting went.

Its own exemptions got the same treatment they enforce: a dead one is a failure.
That found `.env.example` on its first run — exempted as "explains the move",
naming none of the three, and therefore also hidden from the assignment rule for
no reason.

_Verified:_ broken and watched red four ways on the document rule (an
instruction, a bare mention which must stay legal, a stale exemption, the glob
collapsed) and once on the read rule, by putting `env("EIV_BASE_URL")` back into
`eiv-check.ts`. It reads 4 config files, 322 source files and 51 documents.

### What the first deploy of it found, which is not a code defect

Deploy run 112 (03.09.2026 23:22 UTC) **refused**, and the refusal is the
finding:

```
xx EIV_BASE_URL in /home/…/ds-education/config.env names
   https://backend.eiv-fobi.de — 'live' — which this deploy will not carry
   into the database by itself.
```

**The production host's `config.env` names the LIVE Ärztekammer register.** Not
`backend-test`. That is the case the endpoint refusal exists for and it is
working exactly as intended — and it is a decision for the client, not for a
script (CLAUDE.md §7).

From the same log, and only what it actually says:

- migration `0051_platform_settings.sql` **was applied** at 23:22:27, so the
  table exists on production with the worker **off** and the register on `mock`;
- the refusal fired at 23:22:34, before the container swap, so the **previous
  build is still serving** and nothing is half-applied;
- `EIV_WORKER_ENABLED` and `EIV_ALLOW_LIVE` on that host are **not established** —
  neither appears in the log except inside the `sed` line the refusal prints.

That last gap is a defect in the refusal rather than in the deploy, and it is
§9.10's shape: the answer the operator immediately wants — _was it filing, then?_
— is derivable from two variables this script is holding and was not printing.
It now prints the verdict, in three forms, and says where the deploy stopped and
that re-running is safe.

### The correction, made before this ever reached a host

`refuse-consent` was wrong and is gone. The reasoning behind it was sound — a
live-register consent needs a named person — but the branch sat **after** the
endpoint check, so `live` and `unknown` had already returned by the time it was
reached. It could therefore only ever fire at `mock` or `test`: unreachable in
the case it was written for, reachable only where it is wrong.

And at a safe register the flag does not mean what its name says. Until P104-01
the rule matched `*eiv-fobi.de*`, so **reaching EIV's own test system required
`EIV_ALLOW_LIVE=yes`** — that ticket exists because a safety flag you must
switch off to do ordinary work is a flag that is always off. An installation
configured before it carries the flag meaning "may contact a non-local host".
Blocking a deploy over a flag that grants nothing, at a register that files
nothing, is §9.10 again.

So it is **dropped, loudly**: the plan carries a third field saying the flag was
found, and the deploy prints what replaced it. `refuse-endpoint` is now the only
refusal, which is the one that names a real register.

_Verified:_ 305 assertions, including both directions of the drop — a falsy
`EIV_ALLOW_LIVE` must **not** be reported as dropped, because a log line saying
so for a file that said `no` is a false statement about what was on the host —
and two rows asserting the flag never rescues a refused register.

## P182-08 — two commands named `check:shell`, and the local one covered less

P182-07 went to CI green locally and failed there, on `SC2006`: backticks around
a table name inside a `die` message, which shellcheck reads as a command
substitution.

`pnpm check:shell` was `for t in infra/deploy/*.test.sh; do "$t"; done`. CI's
step of the **same name** ran shellcheck first and then those tests. So a green
`pnpm verify` said nothing about shellcheck — CLAUDE.md §9.1's first form
exactly, and the shared name is what made it invisible: the command a person
runs covered less than the one that gates the merge.

**And CI's list was the second form.** It named fourteen files by hand. The
repository has 27 tracked `.sh` files plus `dsc`, so `eiv-endpoint.sh`,
`watchdog.sh`, `release-guards.sh`, `caddy-config.sh`, `backup-state.sh` and six
test scripts had **never been linted at all** — two of them written the same
day, one of them the file that decides whether an installation files
Punktemeldungen. A hand-maintained list of files to check stops matching the
directory the first time somebody adds a file, silently.

`scripts/check-shell.mjs` derives the list from `git ls-files`, runs
`shellcheck -x` from each file's own directory (so a relative `source` resolves,
and a function is checked with its caller), then runs the tests. CI installs
shellcheck and calls the same command. A missing shellcheck is an **error with
the install line**, not a skip — a skip is how a gate becomes decorative.

Linting six new files found three real complaints, all of them idioms rather
than defects, and each now carries a `# shellcheck disable` with its reason: the
CSP test's `$( export …; f … )` subshells are the mechanism that lets each case
see only its own variables; `options.test.sh`'s one-item loop is the shape that
takes a second script as a word; `verify-loop.sh`'s single-quoted `printf`
format holds markdown fence characters that must reach the prompt literally.

_Verified:_ 28 scripts linted, 13 test files green. Broken three ways and
watched red — the exact `SC2006` that reached CI; the same defect planted in
`backup-state.sh`, `eiv-endpoint.sh` and `watchdog.sh`, each of which the old
list did not cover and each of which now reports it; and the file list collapsed
to nothing, which the floor catches. One sabotage produced no finding and is
recorded as such rather than counted: `local now=$1` unquoted is legal shell and
shellcheck does not flag it.

## Where this leaves monitoring

`docs/observability.md` §7 is new and is the answer to "what is watching it, and
who does it tell": the four questions the watchdog asks, why `ALERT_WEBHOOK_URL`
gets the problems and `HEARTBEAT_URL` is pinged **only** on success, and why it
deliberately restarts nothing. §6 previously claimed "no alerting rules", which
overstated the absence — corrected to what is actually true: no Prometheus, no
evaluated PromQL, and a two-minute watchdog that asks from inside the host.

Still deliberately absent, and each has its reason in §6: no log shipper, no
tracing, no scraper.
