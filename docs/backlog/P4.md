# Epic P4 · Assessment & evaluation — 10 h

**Week 4.** The quiz engine, its scoring, and the Evaluationsbogen. Scoring
decides whether a physician receives CME points, so **every task in this epic is
behind the human review gate**.

**Demo at end of phase (M2 · learner MVP, 23.08):** the complete approved layout
is implemented and navigable; quiz and evaluation work.

---

### P4-01 · Quiz model and delivery

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 4 · **Depends on:** P3-06
- **Review gate:** human — assessment

**Context**
The single most common way to break a quiz is to ship the answer key to the
browser. It must be structurally impossible here, not merely omitted by
convention.

**Scope**
- Single-choice and multi-choice questions with options.
- Delivery endpoint returning questions and options **without** any correctness
  marker.
- Option order stable per attempt so a learner's selection cannot be
  misinterpreted after a refresh.

**Acceptance criteria**
- [ ] No endpoint at any role returns a correctness flag to a learner
- [ ] A contract test asserts the learner-facing schema has no field capable of
      carrying the answer key
- [ ] Option order is stable within an attempt
- [ ] Quiz content is tenant-scoped and gated like any other content

### P4-02 · Server-side scoring and threshold

- **jira:** _(unassigned)_
- **Estimate:** 2.5 h · **Week:** 4 · **Depends on:** P4-01
- **Review gate:** human — assessment

**Context**
Multi-choice is scored as an **exact set match** — partial credit is not awarded.
This is a compliance decision, not a UX preference, and it is stated here so it
cannot be quietly softened during implementation.

**Scope**
- `scoreQuiz` in `packages/domain`: single-choice, multi-choice exact-set,
  integer percentage, pass/fail against the enrolment's snapshot threshold.
- Scoring runs entirely server-side; the client submits selections only.

**Acceptance criteria**
- [ ] A multi-choice answer that is a strict subset of the correct set scores zero
      for that question
- [ ] A multi-choice answer that is a superset scores zero for that question
- [ ] The threshold comes from the enrolment snapshot, not the live course
- [ ] Percentages are integers; 70 % passes at a 70 % threshold, 69 % does not
- [ ] Scoring is pure, deterministic and exhaustively unit-tested
- [ ] A submission naming a question from another course is rejected

### P4-03 · Attempts, retry policy and audit

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 4 · **Depends on:** P4-02
- **Review gate:** human — assessment

**Context**
The attempts record is the evidence that a CME point was earned legitimately. It
has to be complete and immutable, including failed attempts.

**Scope**
- Attempt lifecycle with the course's retry policy enforced server-side.
- Every attempt and every answer persisted, including failures.
- Attempts are append-only.

**Acceptance criteria**
- [ ] Exceeding the retry limit is refused server-side, not merely hidden in the UI
- [ ] A failed attempt is persisted with its answers, never discarded
- [ ] An attempt record cannot be updated or deleted after submission
- [ ] Concurrent submissions of the same attempt produce exactly one scored result
- [ ] The passing attempt is identifiable for later certificate and EIV records

### P4-04 · Evaluationsbogen

- **jira:** _(unassigned)_
- **Estimate:** 2.5 h · **Week:** 4 · **Depends on:** P4-03
- **Review gate:** human — assessment

**Context**
The evaluation is a precondition for CME point award under German accreditation
practice, so it is part of the completion gate rather than an optional survey.

**Scope**
- Evaluation form model (scale, single choice, free text) per course.
- Submission stored per enrolment; one submission per enrolment.
- Free-text responses are personal data — never logged.

**Acceptance criteria**
- [ ] The evaluation is required before completion, enforced server-side
- [ ] One submission per enrolment; a second is refused
- [ ] Required questions are enforced server-side, not only in the widget
- [ ] Free-text content never appears in logs or error payloads

### P4-05 · Completion state machine

- **jira:** _(unassigned)_
- **Estimate:** 1 h · **Week:** 4 · **Depends on:** P4-04
- **Review gate:** human — assessment

**Context**
`isCourseComplete` is the single point at which the system decides a physician has
earned their points. Everything downstream — certificate, EIV submission — keys
off it, so it must have exactly one implementation.

**Scope**
- `isCourseComplete` in `packages/domain`: watched % ≥ required, quiz passed,
  evaluation submitted, EFN present.
- Completion timestamped and immutable once set.
- Emits the event that P7 and P8 consume.

**Acceptance criteria**
- [ ] All four conditions are required; removing any one in a test prevents
      completion
- [ ] Completion is idempotent — re-evaluating does not re-issue
- [ ] The completion timestamp is set once and never changes
- [ ] A later course-configuration change cannot revoke an existing completion
- [ ] The function is pure and exhaustively unit-tested across all sixteen
      combinations of the four conditions
