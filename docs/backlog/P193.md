# P193 — The shell that deploys this platform was the shell nothing checked

**Raised by:** the client, 04.09.2026: _"deployment job is failing, fix it and
deploy it"_. Deploys 116 and 117 both failed, and the cause was mine.

---

## What broke

P189-01 wrapped the two posture reads in `bash -lc '…'` and wrote, in the
warning that reports an unreadable answer:

```
${said:-nothing beyond compose's own warnings}
```

Inside `${parameter:-word}` the default word is **its own quoting context**, so
the apostrophe in "compose's" opens a single quote — **even though the whole
thing sits inside double quotes.** Bash never finds the close:

```
/home/runner/work/_temp/….sh: line 86: unexpected EOF while looking for matching `''
##[error]Process completed with exit code 2.
```

The step aborted before writing `eiv_reports_live`, which is how the log names
the culprit without saying so: the job set `api_domain`, `portal_domain` and
`admin_domain` and not the fourth output.

Both posture steps carried the same sentence, so both were broken. Two deploys
failed on it.

## Why nothing caught it

`pnpm check:shell` runs shellcheck over `git ls-files '*.sh'` plus
`infra/deploy/dsc`. **A shell script embedded in YAML is not a `.sh` file.** So
the largest and most consequential shell scripts in this repository — the ones
that deploy it — were the only ones nothing checked. CLAUDE.md §9.1's third
form: green because of what it is not scanning.

### And the verification I did run was worse than none

P189 was pushed with a `bash -n` check I wrote in the same turn. It passed. It
passed because it pulled the payload out of the `ssh "…"` string and **stripped
the backslashes** before parsing — which is not what bash receives. It was
checking a string that never existed, and it reported success about the exact
line that was broken.

A check that cannot go red is not evidence (§9.1); a check that goes green on
the broken input is worse, because it is _cited_. The fix for that is not a
better ad-hoc command — it is a check in the repository that runs the whole
step, the way the runner does.

## P193-01 — `check:workflow-shell`

`bash -n` over every `run:` block in every workflow, with `${{ … }}` replaced
first — GitHub substitutes those before a shell sees them, and leaving them in
would report syntax errors that cannot happen.

Both shapes are scanned: block scalars (`run: |`) and single-line `run: cmd`.
The first version scanned only blocks and _reported_ 24 single-line steps as
unscanned. Honest, and still a blind spot covering more steps than it checked —
which is the shape this file exists to close, so it closes it. **43 blocks** now
parse.

`MINIMUM_STEPS` refuses to report success over an empty scan: somebody pointing
this at the wrong directory should get a failure, not a green tick over nothing.

Watched red, both halves:

| Sabotage                                      | Result                                                         |
| --------------------------------------------- | -------------------------------------------------------------- |
| the original `${x:-compose's warnings}`       | `deploy.yml:573 — unexpected EOF while looking for matching '` |
| an unterminated quote in a single-line `run:` | `deploy.yml:913 — unexpected EOF while looking for matching "` |

It is in `pnpm verify` and in CI's "Shell scripts" step — §9.11: a check that
runs only in CI is a check the person writing the code does not run.

### What it does not do

It is a **parse**, not an execution. It catches unbalanced quotes, `if` without
`fi`, a stray `)`. It cannot catch a command missing on the runner, or a
variable that is empty at 03:00. Those want their own checks, and saying so is
the difference between a check and a claim.

## P193-02 — the message stops using the construct

`${said:-…}` is replaced by an `if` and an assignment in both steps. The
apostrophe was the trigger; the construct is the hazard, and it is not worth
keeping for two characters of brevity in a line that only ever prints when
something has already gone wrong.

- [x] Every `run:` block in every workflow parses, both shapes, no unscanned
      remainder.
- [x] The check is in `pnpm verify` and in CI.
- [x] Watched red on the real defect and on a second, different one.
- [x] The check's limits stated in its own header.

## Not done

- **No shellcheck on workflow steps, only `bash -n`.** shellcheck wants a file
  and a shebang, and the useful subset here — quoting, `SC2086` — would need
  every step to be written to a temp file with a directive header. A parse is
  the part that was actually missing; linting them is a bigger ticket and this
  one should not smuggle it in.
