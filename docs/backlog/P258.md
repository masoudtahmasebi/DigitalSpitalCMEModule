## P258-02 — the fullscreen control bar was grey on black

**Review gate:** none · learner presentation · found by Q1, Q3 and Q5

P256 made the whole player go fullscreen as `bg-black`, and `Controls` had no
surface of its own, so every control in `text-gray-700` sat on black. Inline
it had inherited the player's `bg-gray-100`. `Controls` now owns
`bg-gray-100`, which keeps every colour in it at the contrast it already had
inline.

Verified: the journey now computes the exit button's contrast against the
first painted background behind it — red at **2.04:1** before the fix
(`Expected: >= 3`), green after. The same block replaces P256's `screen − 120`
allowance with `video.height + bar.height ≥ screen − 1`, measured.

## P258-03 — one question for "is this player fullscreen"

**Review gate:** none · found by Q3 and Q4

## P258-07 — the profile hint, tightened

**Review gate:** human · touches auth (what a learner request carries) · found
by Q1, Q4 and Q5

- **A malformed hint no longer breaks every request.** `Headers#set` throws on
  a non-ByteString or a newline, before `fetch`, so raw JSON with a "Ł" in
  `learner-profile` took the whole widget down. The SDK now sends
  `X-DS-Profile` only for base64url of at most 4096 characters. Verified:
  three cases in `client-headers.test.ts` red before, green after; SDK 126
  passed.
- **A direct key, not a conditional spread** (`apps/widget/src/api.ts`):
  TypeScript never checks spread members against the target type, which is how
  the option was dropped for six weeks. The admin console's `createClient` has
  no spreads; the preview's had only this one.
- **The DocCheck preview no longer sends it.** Its routes are `@Public()` and
  the guard reads the hint only after verifying a learner credential, so a
  visitor's name and address travelled to be read by nothing.
- **Contract:** `X-DS-Profile` is described in `contracts/openapi.yaml`
  beside `X-DS-Project`. `pnpm check:sdk`: generated SDK matches.
- **Prose corrected** (P257, the SDK comment, the WordPress spec): the parser
  _was_ called — by the guard; what was untested was the sender. And the
  hint _replaces_ stored values on every request (`coalesce(p_email,
u.email)`), it does not only fill empty ones.
- **Harness:** `storedProfile` moved into `world.ts` beside a shared
  `withSuperuserPool`, so the "one hand-rolled idle-error handler" there is
  true again. The SDK test is `client-headers.test.ts`, no longer sharing a
  name with the API's parser test.

## P258-08 — only CI started by a push deploys

**Review gate:** none on review-area grounds · deploy guard · found by Q1 and Q2

Since the default branch became `main` (P254-01), three kinds of CI run on
`main` could deploy:

- the **weekly scheduled run** — scheduled CI 39238989995 (19.10.2026, 10:39,
  success) was followed by a Deploy at 10:42:58 of the unchanged `4034b08`,
  and every post-deploy journey creates another accredited course and learner
  in production;
- a **hand-started run** (P254-02), which does not share the push runs'
  concurrency group and so could finish after a newer push and deploy the
  older commit on top of it;
- **pull-request CI** from a fork branch named `main`, whose `head_branch` is
  also `main`.

`ds_release_ref_allowed` now takes the triggering run's event and allows a
`workflow_run` deploy only for `push`. Pushes to `main` cancel each other's CI,
so this is also what keeps deploys in commit order. The deploy job's `if:`
skips the other events, so a Monday audit is not a failed deploy every week;
the guard refuses them again, and it is the tested half. Manual deploys and
rollbacks are Deploy's own `workflow_dispatch`, unchanged.

Verified: `release-guards.test.sh` — four new rows (schedule, workflow_dispatch,
pull_request, unknown) red against the old guard ("24 passed, 4 failed"), 28
passed after. `workflow_run.event` is the triggering run object's own `event`
field — `"push"` on run 38731796489 and `"schedule"` on 38252472184, as the
runs API lists them in this session. `check:workflow-shell` parses.

Not verified: a real scheduled run being skipped — the next one is Monday.

## P258-09 — test-rig hygiene

**Review gate:** none · harness only · found by Q1, Q2 and Q5

- **One Keycloak key per e2e run.** `dev-keycloak` reads and writes its key at
  `DEV_KEYCLOAK_KEY_FILE` when set; the harness sets a per-run path. A CI retry
  restarts the stub, which used to re-key under the same `kid` and 401 the rest
  of the WordPress group. A new `kid` alone would not do: `jose` refetches an
  unknown `kid` at most once per 30 s. Verified: "nimmt nach einem Neustart des
  Keycloak-Stubs weiter Tokens an" red with the path emptied, green with it.
  Documented in `.env.example` (`check:env`).
- **Derived thresholds** in `katalog-abstaende.spec.ts`: 256 − 176 − 40 = 40
  above the seal, `pb-10` = 40 below the last button, ±1 px — instead of ≤ 48
  and ≥ 32.
- **`VideoPlayer.test.tsx` restores** the original property descriptors
  instead of deleting, so a future jsdom `requestFullscreen` is not removed for
  the rest of the file.

Verified, for the whole of P258: `pnpm verify` exit 0 — including
`check:shell` (shellcheck 0.9.0 installed for this run: 36 scripts, 17 shell
test files), `release-guards.test.sh` 28 passed and the production audit clean.
`pnpm test:e2e` 42 passed.
