## P114-01 · Retire an answered question instead of refusing the edit

**Status:** done · **needs-human-review** (touches `assessment`) · schema change

### What was happening, and why it was not a bug in the ordinary sense

`authoring.service.ts` refused to delete any question with recorded answers, and
the refusal was right about the thing it was protecting.
`quiz_answers.question_id` references `quiz_questions` under
`ON DELETE RESTRICT`, because that row is the evidence behind a CME point that
may already have been reported to an Ärztekammer. Delete it and the point stays
credited while the reason for it disappears.

The mistake was that the refusal answered a **second** question it was never
asked. It conflated:

| Claim                              | True?                                        |
| ---------------------------------- | -------------------------------------------- |
| the row must survive               | **yes**, always, non-negotiable              |
| the question must stay in the exam | **no** — no accreditation rule requires this |

So one physician answering one question froze that Lernerfolgskontrolle for
ever. The only way out was to build a replacement exam and abandon the old one,
which loses exactly the continuity the refusal existed to protect.

### The rule now

`questionRemoval(answerCount)` in `@ds/domain`:

- **never answered** → deleted outright. A question added and dropped in the
  same sitting leaves nothing anybody needs to reconstruct, and a tombstone for
  it is clutter that hides the real ones.
- **answered** → **retired**: `retired_at` is stamped, the row and its options
  and its `quiz_answers` all stay, and it is never served or scored again.

Nothing already earned moves. `quiz_attempts` stores each attempt's own
`correct_count`, `total_count`, `score_percent` and `passed`, so shortening the
exam cannot retroactively change what a physician scored or whether they passed.
That is the property that makes this safe at all, and it has its own test.

### Why a tombstone here, when `canDelete` rejects soft deletes in terms

`canDelete`'s own comment:

> Deliberately not a soft delete. A course tree with hidden tombstones in it is a
> tree where ordering, gating and the rollup all have to know about tombstones,
> and every one of those is a place to get a compliance answer wrong.

Correct, and it does not transfer. A quiz question is not in that tree: the
rollup counts contents, gating reads videos, and ordering inside one exam is
local to that exam. The blast radius is a single `contents` row, which is why
the tombstone is affordable here and nowhere above it.

The same comment ends: _"An author who genuinely needs the item gone after
learners have used it needs a conversation, not a button."_ That conversation
happened on 25.08. This is its outcome, and the reasoning is written into
`questionRemoval` so the next person meets it rather than re-deriving it.

### An asymmetry that is deliberate

Removing an **option** from an answered question is **still refused**. Retiring a
question removes a whole unit of meaning cleanly; deleting one option out from
under a recorded answer leaves `quiz_answers.selected_option_ids` pointing at a
label nobody can reconstruct, and the attempt becomes unreadable rather than
merely historical. An author who wants different options writes a new question
and lets the old one retire.

### Schema

`0046_quiz_question_retirement.sql` adds `retired_at timestamptz` and swaps the
table-wide `UNIQUE (content_id, ordinal)` for a **partial** unique index over
live rows only. Without that swap, retiring question 3 of 11 and renumbering the
survivors collides with the tombstone still sitting at ordinal 3.

A retired question keeps the ordinal it held when it was answered — that is
where it stood in the exam somebody sat, which is what an auditor
reconstructing an attempt would ask. `applyQuiz`'s "park the survivors" step
therefore gained `AND retired_at IS NULL`, or every tombstone would drift
negative on the next unrelated edit.

### What each surface does

| Surface                   | Behaviour                                                                     |
| ------------------------- | ----------------------------------------------------------------------------- |
| Learner: question list    | live only                                                                     |
| Learner: answer key       | live only — **separate query**, filtered separately, tested separately        |
| Learner with a stale form | `UnknownQuestionError` → an honest refusal, not a silently mis-scored attempt |
| Author: editor list       | live only; a retired row has no control that would work (§9.2)                |
| Author: `retiredCount`    | shown as a notice, so nine vanished questions read as a decision (§9.4)       |
| Author: remove control    | enabled; the confirm step says _what it will do_, not why it is refused       |

The two learner queries are the likeliest place for this to rot: filtering the
projection and forgetting the key gives an exam whose visible questions and
whose scoring disagree, and a retired question left in the key inflates
`totalCount` so every learner is measured against an exam they were never shown
— the pass threshold quietly becomes unreachable. Both halves are asserted, in
tests named for that failure.

### Verification

Everything below was run, not assumed.

**The migration, against a real Postgres 16.** All 46 migrations applied in
order through the project's own migrator. Then, with real rows:

- eleven questions → retire nine → `2 live, 9 retired, 11 rows kept`, which is
  the client's request exactly;
- retire the question at ordinal 0, then insert a **new live** question at
  ordinal 0 — accepted, which the old table-wide constraint would have refused;
- insert a second **live** question at ordinal 0 — still refused,
  `duplicate key value violates unique constraint "quiz_questions_live_ordinal"`.

Both directions, because a constraint that only permits is not a constraint.

**Tests, and watched to go red** (§9.1, §9.12 step 5):

- 752 domain tests. Stubbing `questionRemoval` to always return `"delete"` fails
  3 of the new ones by name.
- 553 integration tests across 20 files, against real Postgres and Redis.
  Making the service delete rather than retire fails 5 by name, starting with
  _"accepts an edit that drops it — this is the whole defect"_.
- 587 API unit, 294 widget, 237 admin, 30 portal.
- `lint`, `format`, `typecheck`, `check:roles`, `check:i18n`, `check:sdk`,
  `check:shell` all clean.

**One thing worth recording, because it was my error and the suite caught it.**
The first run of the new integration block retired a question the rest of the
file shares, and five later tests failed with _"expected 2, got 1"_ — pointing
at the learner endpoint rather than at the block that broke it. That is §9.8's
lesson one layer along: state that outlives a test is a failure attributed to
the wrong code. The block now appends its own question, retires that, and ends
with a test asserting it left the shared exam exactly as it found it — so if it
ever does leak again, the failure says so where the cause is.

Separately, while provisioning a scratch database I made `ds_app` a superuser to
get past a permissions error, and the tenant-isolation suite went red. That was
the suite doing precisely its job (ADR-0002); the grant was reverted and the
database rebuilt through `scripts/testdb.mjs`.

## What this does **not** decide, and must not be read as deciding

**Whether MEDICE may shorten _this_ exam.** The platform can now do it; whether
the Ärztekammer Westfalen-Lippe permits it for VNR `2760552025919300018` is not
a platform question. Two things in the Anerkennungsbescheid bear on it:

1. **70 % is an accreditation condition**, not a setting — _"Voraussetzung für
   die Punktevergaben ist, dass der Anteil der richtig beantworteten Fragen …
   mindestens 70 % beträgt."_ With two questions, 70 % means both correct;
   whether a two-question Lernerfolgskontrolle satisfies what was accredited is
   ÄKWL's call.
2. **Changes must be notified in writing** — _"Sollten sich nach der Anerkennung
   Änderungen jeglicher Art … ergeben … sind diese in jedem Fall zeitnah
   schriftlich der ÄKWL mitzuteilen, da die Anerkennung … bei Änderungen nicht
   automatisch bestehen bleibt."_ Replacing eleven questions with two is
   plausibly such a change.

`CLAUDE.md` §7: do not guess on compliance semantics. Editing freely on a
**draft** or on the `ds` test tenant is unaffected by any of this and is what
the client should use for iterating.
