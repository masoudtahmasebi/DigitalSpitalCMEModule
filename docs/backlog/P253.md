# P253 — the catalogue filters: answer, switch off, and stop offering empty ones

Answers and partly closes **DEP-48** (_Filter function Fortbildungen –
configuration_), filed by Philipp on 06.10.2026. One half is **not** built and
is a decision, not an omission — see the last section.

---

## What was asked, and the answers

> How is filtering configured for the Fortbildungen overview?

Two fixed categories, free-text items, server-side everything.
`courses.thema` and `courses.altersgruppe` are `text[]` columns; an operator
types the values per course under **Inhalte & Darstellung**. The API computes
the facets under the rest of the selection and the widget only holds the
selection — it never filters an array it already has, which is what makes the
counts beside each option correct across pages.

> Can the filters be changed flexibly in terms of their categories and filter
> items?

**Items: yes, today.** Anything typed into those two fields becomes an option,
per customer. There is no shared taxonomy to migrate — deliberately, because a
dermatology customer's Themen are not MEDICE's.

**Categories: no.** Two columns means a third filter is a migration, an API
change and a widget change. That is the half this ticket does not build; it is
P253-03 below.

> Could you update their labels in the CMS to Filter 1 and Filter 2?

**Already possible, with no code change.** `catalog.thema`,
`catalog.altersgruppe`, `catalog.selectThema` and `catalog.selectAltersgruppe`
are plain strings in `@ds/copy`, so `COPY_KEYS` contains them and the console's
**Texte** screen already draws a field for each, per project, with the
platform's default as the placeholder.

Not done from here on purpose. Those are a customer's words on a customer's
screen, and "Filter 1" would be what a physician reads — the one audience the
label is for. Changing it is one field in Texte, and §9.10 says the answer
belongs with the person already entitled to it rather than hard-coded into a
multi-tenant bundle.

## P253-01 — a filter with nothing in it is no longer offered

**Review gate:** none · learner-facing presentation only

**Context**

Found while answering the ticket, and it is probably what prompted it.
`FacetSelect` rendered unconditionally, so a project where no course carries an
Altersgruppe got a dropdown containing exactly one entry — "Altersgruppe
auswählen", its own placeholder. A control that can only produce the state it
is already in is CLAUDE.md §9.2, and it has been there since the catalogue's
first day.

This is fixed regardless of any setting. The facets are computed by the API
under the rest of the selection, so an empty one means there is genuinely
nothing to choose.

**Acceptance criteria**

- [x] A facet with no values draws no control. Red when the length check goes.
- [x] Both empty draws no filter row at all, rather than a heading over
      nothing.
- [x] A project that has values keeps both, unchanged.

## P253-02 — `Branding.catalogFilters`, so a project can switch them off

**Review gate:** none · `parseBranding` is pure and exhaustively tested

**Context**

> Since I'm not sure, if we need the filter at the moment, it should be good if
> we can disable them in the CMS.

A different question from P253-01: this is for a project that **has** Themen
and does not want to offer the filter anyway.

**Scope**

`"both" | "thema" | "altersgruppe" | "none"` on `Branding`, absent meaning
`both`. One `Select` under **Erscheinungsbild** rather than two checkboxes — an
operator picks the row they want, and the stored value says what a physician
sees instead of two flags somebody has to combine in their head.

The degradation is the part worth stating: an unrecognised value is dropped,
and dropping it means **both**, never **none**. A setting written by an older
console, or by hand, lands on the behaviour every project has today rather than
on a catalogue whose filters have silently gone.

An active chip survives the setting. A filter already applied stays removable,
or a learner who narrowed the list before an operator changed the setting is
left looking at a subset with no way back — §9.2 one turn on, where removing
the control is what leaves somebody with no next move.

**Acceptance criteria**

- [x] The four values parse; `""`, `"BOTH"`, `"alle"`, `1`, `true`, `null` and
      `["thema"]` are dropped and therefore mean both. Red when the membership
      check is removed.
- [x] `invalidBrandingFields` reports a rejected value, so the form can say so
      rather than saving and answering "Gespeichert." — §9.3's own instance
      (P41-01), which this field would otherwise rejoin.
- [x] The widget draws both / one / neither accordingly. Red when the setting
      is ignored.
- [x] Absent means both — MEDICE's catalogue is unchanged by this shipping.
- [x] The setting is reachable: a `Select` in Erscheinungsbild, with a hint
      that names the P253-01 behaviour, so an operator who picks "Thema und
      Altersgruppe" and still sees one dropdown knows why (§9.4).
- [x] `pnpm verify` exit 0 · `pnpm test:e2e` 39 passed.

### The gate that caught the comment

`purity.test.ts` went red on

```
branding.ts: I never looked
```

The doc comment contained the words `… apart from "I never looked"`, and the
import scanner reads `from "…"` wherever it appears. The gate was right and the
prose was wrong; the sentence is reworded. Worth recording that the scanner
reads comments as well as code — it errs loudly rather than quietly, which is
the correct direction, and it costs a rewording.

## P253-03 — flexible filter categories: **not built, and a decision**

**Review gate:** n/a · raised per CLAUDE.md §3

"Can the filters be changed flexibly in terms of their categories" is a
different product from the one that exists. Today the catalogue has exactly two
filter dimensions because `courses` has exactly two columns. Operator-defined
dimensions means:

- a `course_facets` table (customer, key, label, ordinal) and a values table,
  replacing both columns, with a migration that moves existing data;
- the facet query, which today is two `unnest`s, becoming a join over an
  arbitrary set;
- an authoring screen for the dimensions themselves, with the ordering, the
  renaming and the "what happens to courses that used this" that every
  taxonomy editor needs;
- the widget drawing N filters instead of 2, and the copy keys for their
  labels becoming data rather than `@ds/copy` entries — which is what would
  make "Filter 1" and "Filter 2" literally the defaults.

That is worth doing if the platform is going to have customers whose catalogues
are not shaped like MEDICE's. It is not a setting, and absorbing it into a
ticket that asked a question would be exactly what §3 forbids. Priced and
decided by the client, in a ticket of its own.
