# P108 — a setting that does not survive a deploy is not a setting

> **Extracted from `P106.md` (P160-01).** This ticket was written in the same sitting as P106 and filed under its heading, so its number appeared in commit messages and in no filename. The text is unchanged.

**Raised by:** the client, 24.08.2026:

> _"required_watch_percent should be configurable from the admin panel, the
> seed can be at 90%"_

**Estimate:** 1 h. **Actual:** 1.5 h.

## P108-01 — the seed overwrote what the console saved

It **was** configurable. The field is on Verwaltung → Fortbildungen → _ADHS
Akademie adult_, it validates, it saves. And `deploy.sh` runs the MEDICE seed on
every deploy, whose `ON CONFLICT DO UPDATE` named `required_watch_percent` — so
the value went back to 100 on the next push. Silently, on a green deploy, with
nothing anywhere reporting it. From the console it is indistinguishable from a
field that does not save.

Two fields had already been rescued from this, one at a time:

| Field              | Why it was rescued                                |
| ------------------ | ------------------------------------------------- |
| `status`           | a re-run must not republish an unpublished course |
| `vnr_password_enc` | a re-run must not replace a real credential       |

Same defect, found twice, fixed twice, never named. The rule now is: **the seed
creates, the console owns.** Only what the Anerkennungsbescheid is authoritative
over still updates — title, points, category. Everything an operator can edit is
theirs after the first insert, and the fields that need a starting value use
`COALESCE` so a fresh install still gets a working course.

### The field that mattered most was not the one reported

`stamp_image`. The seed writes a 1×1 placeholder PNG and the deploy's own output
tells the operator to replace it with the real Stempel before anything ships.
Had they, the next deploy would have restored the 1×1 — and a
Teilnahmebescheinigung without a stamp is not a valid document (S11). Nothing
would have failed. The PDF would simply have come out blank where the stamp
goes.

`courses_published_cme_is_complete` bounds this and it is worth being exact:
that constraint refuses to let a **published** CME course hold a null stamp, so
no course could ever have lost one entirely. It cannot check whether the stamp
is a _real_ one. The overwrite was live.

## P108-02 — the seed value is 90

Was 100, the stricter reading of an open conflict (layout says 80, MEDICE-292
says 100). Now 90 by the client's decision, and the seed's own output says so
and keeps the caveat: **90 is a decision, not the answer.** S-item unchanged.

## Verification

Ran against a real Postgres in the sandbox, not deferred to CI: 19/19 in
`seeds.integration.test.ts`.

The second new test **failed on its first run**, on its own setup — it nulled
the stamp on a published course and `courses_published_cme_is_complete` refused,
which is the constraint doing its job. Fixed by unpublishing first, and the
reason is now written into the test.

**Courses configured before this ships have already been reset by earlier
deploys.** Re-set the watch percent, and the Stempel if one was uploaded, after
the next deploy. From then on it holds.
