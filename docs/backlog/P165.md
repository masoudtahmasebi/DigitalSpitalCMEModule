# P165 — MEDICE's Veranstaltungsnummer is not the seed's to invent

**Raised by:** the client, 03.09.2026, closing the question P164-02 was standing
in front of — _"yes, seed can do it, but seed should be only on ds tenant, not
medice."_

## The line, and which side each seed was on

| Seed          | Tenant       | VNR it writes                     | Ours to make up?                                                       |
| ------------- | ------------ | --------------------------------- | ---------------------------------------------------------------------- |
| `ds-demo`     | `ds`         | `9999999999999999999`             | yes — its own comment says it is deliberately not a valid registration |
| `ds-default`  | `dscustomer` | none; the course awards no points | yes                                                                    |
| `ds-test`     | `dstest`     | none                              | yes                                                                    |
| `medice-adhs` | `medice`     | `2760552025919300018`             | **no**                                                                 |

The first three invent numbers about themselves. The fourth invented a fact
about somebody else's accreditation.

## It was not a fabricated number, which is why it survived

`2760552025919300018` was the client's own, given in P109-01: _"the vnr i have
already given you, you can set that for now."_ It went stale — the course's
number is now `2760012024200354002` — and a constant in this repository has no
way to notice. A VNR changes when a course is re-accredited, so the default
could only ever be right by accident and wrong by default, which is what
happened.

The reason it reached a certificate at all is P164-01, and that is fixed
separately. This is about why the value existed to be read.

## What changed

`seededVnr()` returns `SEED_MEDICE_VNR` or **null**, and the course is inserted
as a **draft** when it is null: `courses_published_cme_is_complete` refuses a
published, point-awarding course with no VNR, and that refusal is the correct
outcome rather than an obstacle. Nobody should be able to enrol in an accredited
course whose accreditation number the platform made up.

The P109-01/P117-01 repair — a row still carrying the zero placeholder, demoted
by migration 0047, that only a seed run can fix — still exists and now has a
precondition: it fires only when `SEED_MEDICE_VNR` supplies a number. With
nothing supplied the seed writes nothing and touches nothing.

**A comment that was false, and load-bearing.** The ON CONFLICT clause explained
its sentinel with _"COALESCE cannot express this: vnr is NOT NULL, so there is no
empty state to fall back from"_. `courses.vnr` is `text` — nullable — at
`0001_init.sql:105`, and migration 0042 tests `vnr IS NULL` explicitly. Only
`eiv_submissions.vnr` is NOT NULL. §11 rule 9: a comment is a claim, and this
one had shaped the design around a constraint that does not exist.

**And the same import-time bug as P151-02.** `const VNR = process.env[…]` binds
at module load, so the value depends on import order — and the supplied-number
test was unreachable, because a test that sets the variable has already imported
the seed. Read per call now.

## What the operator is told

The deploy's report used to end _"ADHS Akademie adult is PUBLISHED and visible to
participants now"_ and name the VNR. Both are false by default now, so it says
the opposite and what to do about it: the course is a draft, it has no VNR, the
number is issued to MEDICE by the Ärztekammer, and here is the screen to enter
it on. §9.9's corollary — the deploy's own output is the only thing an operator
reads, and P64-02 is what an unexplained empty catalogue costs.

## Acceptance criteria

- [x] `medice-adhs` writes no VNR unless `SEED_MEDICE_VNR` supplies one
- [x] The seeded MEDICE course is a draft when it has no VNR
- [x] The placeholder repair still works, and only with a supplied number
- [x] The deploy's report says the course is a draft and why
- [ ] Confirmed on a fresh install — the client's, and only visible there

## Not done

**The client's own installation is unaffected and untested by this.** Their
course carries a real VNR they typed, so the ON CONFLICT keeps it and the status
branch does not fire. Everything above is about what a _fresh_ install gets, and
nothing here has been run against one.

**Three seeded courses still carry invented accreditation bodies, organisers and
a 1×1 placeholder stamp** on the MEDICE tenant. The VNR was the one that reached
a legal document, so it is the one this ticket fixes; whether the rest belong in
a seed at all is the same question one layer out and is not answered here.
