# P67 — The browser refused the upload before a byte moved

Reported 12.08: _"the video upload to s3 does not even work!"_ The console
showed **"the connection to object storage failed"**. There was no connection,
and nothing had failed yet.

---

## P67-01 · The console's CSP did not name the bucket · 1.5 h

### What was wrong

The browser said it, exactly:

```
Connecting to 'https://nbg1.your-objectstorage.com/dscme/7c8d0be3-…&Signature=e2139f3…'
violates the following Content Security Policy directive:
"connect-src 'self' https://api.digitalspital.com".
The action has been blocked.
```

A course video is uploaded **by the browser, straight to object storage**, with
a presigned PUT the API mints (P23-01). The API never sees the bytes — 2 GB
through a Node process is a Node process falling over. So the browser opens a
connection to a host that is not ours, and the console's `connect-src` named
only itself and the API.

Every upload was blocked before a request was made. Nothing reached a server, so
nothing was in any log, and the only evidence was a line in the operator's own
browser console.

### What changed

`S3_ORIGIN` is derived from `S3_ENDPOINT` by `domains.sh` and added to the
console's `connect-src`. Derived, not written again, because the origin the
policy allows and the origin the presigned URL points at are the same fact —
two copies drift the first time the bucket moves region, and the symptom is this
one.

`origin_of` strips the path: a CSP names origins, and the whole endpoint URL in
a `connect-src` is a directive the browser reads as a path match, which fails in
exactly the way this exists to prevent.

Empty when no bucket is configured, which collapses the directive back to what
it was and is correct: no bucket, no uploads.

### The check, and the half of it that was not obvious

Two, because one was not enough:

1. `domains.test.sh` — the origin is derived, a path is stripped, an absent
   endpoint leaves the directive alone, and a mismatched `S3_ORIGIN` is refused.
2. `deploy-vars.test.sh` — **the Caddyfile's CSP actually names it.**

The second is the one that matters and the one I nearly missed. Deriving a value
and passing it to Caddy is worth nothing if the policy does not use it, and the
existing reference check cannot tell: it verifies that every `{$VAR}` the
Caddyfile _uses_ is provided, which stays green when a placeholder is deleted.
Verified by deleting it:

```
xx the admin CSP does not name {$S3_ORIGIN} in connect-src.
1 unguaranteed reference(s)
```

### Still open, and not fixed here

The banner read **"the connection to object storage failed"** — English, on a
German screen, and wrong: there was no connection. `messageOf` in
`UploadField.tsx` maps that text to a German sentence, so something is rendering
the raw error past it. Not chased in this ticket because the CSP was the reason
nothing worked; recorded here rather than left for somebody to rediscover.
