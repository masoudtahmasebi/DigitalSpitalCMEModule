## The gap, stated exactly

`certificate-delivery.integration.test.ts` holds 22 cases. Every one ends at a
fake `DeliveryChannel` and asserts what the service **handed** it. Nothing in
this repository had ever opened a socket to a mail server.

So the last link of the chain — compose a message, connect, negotiate STARTTLS,
authenticate, transfer the PDF — had exactly the coverage the CSP header had
before P68 and the bucket's CORS rule had before P70: none, with everything
green and `delivered` written on the row.

CLAUDE.md §9.13, in one sentence: an API test cannot assert that a byte reached
a mail server.

## P187-01 — the harness runs an SMTP server

`apps/e2e/support/mail-sink.ts`, ~250 lines of `node:net` and `node:tls`.

It speaks real SMTP because it has to. `SmtpDeliveryChannel` sets
`requireTLS: true`, so nodemailer refuses to send unless the server offers
**STARTTLS** and the upgrade succeeds — a sink that accepted plaintext would
model a server nobody runs and would hide the failure this setting exists to
prevent. It refuses `AUTH` before the upgrade and discards everything
negotiated across it, per RFC 3207 §4.2. It demands authentication before
`MAIL FROM`, for the same reason `object-store.ts` verifies SigV4: a fixture
that accepts anything cannot fail on a credential the product forgot to send.

The certificate is `tls.ts`'s, already trusted by the API through
`NODE_EXTRA_CA_CERTS` for the bucket — one throwaway CA for the whole rig.

It writes each accepted message as a line of JSON. The sink runs in Playwright's
**runner** process and the specs run in workers spawned afterwards, so the
in-memory array is unreachable from a test — the same constraint `globalSetup`
already records about `globalThis`, and a file is the channel, as `api.log` is.

## P187-02 — the delivery worker is on, and the journey waits for the message

`CERTIFICATE_DELIVERY_ENABLED` was `"no"` in the rig, and the comment said why:
a background sweep changing a row mid-assertion is the definition of a flaky
test. True while there was no sender — rows churn through retry states — and it
is also why the link had no browser coverage.

With a real sender configured the state machine is monotonic, issued then
delivered, and no spec asserts on delivery state on the way past. Two seconds
rather than the production five minutes: a browser test waiting out a sweep
interval is a test nobody runs.

**Act 0** configures Sicherheit → E-Mail-Versand der Plattform, through the
console, in its own browser context — the journey deliberately runs its operator
and its learner in one cookie jar (P66-01) and a third sign-in there would
replace the operator's session. **Act 16** waits for the message and asserts:

| Assertion                           | What it would catch                                                              |
| ----------------------------------- | -------------------------------------------------------------------------------- |
| `secure`                            | a certificate sent over a plain socket                                           |
| `authenticated`                     | a credential the product never offered                                           |
| `from` is the platform's            | P185's fallback merging two identities — the SPF failure that looks like success |
| the body contains `application/pdf` | P59-02 regressing: copy promising an attachment that is not there                |

Configured **through the screen**, not by a SQL fixture — §9.13's second rule.
The rig comes up in the state a real installation is created in, with no sender,
and the product's own tooling is what configures it, as `stack.ts` spawns the
deploy's own `bucket-cors.js` rather than pre-configuring the bucket.

Watched red: with `deliverySender`'s platform branch removed, the journey fails
with

```
no e-mail reached the harness's mail server for e2e-mrw3ch@dstest.example
within 60s. Nothing at all arrived — the delivery worker is off, the sender is
not configured, or the certificate was abandoned. api.log says which.
```

Green, the sink holds one message: 13 078 bytes, TLS, authenticated, from
`fortbildung@harness.digitalspital.example`, carrying a PDF.

## Local only, and that is not a gap being tolerated

Against a deployment this would overwrite the client's real sender and post to
real mailboxes. There is no safe version of it there, so both acts are guarded
on `currentTarget().kind` and the post-deploy run keeps the coverage it can
have: the journey proves the certificate is issued, and P188-03 reports what the
installation's sender actually is.
