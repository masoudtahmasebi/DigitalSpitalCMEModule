## GDPR erasure backlog

**The compliance question: how many erasures were silently skipped, and have
they drained?**

**Answer: none were skipped. Zero erasure requests were affected, because the
defect never ran on any deployed build.**

### The defect and its window

`ObjectErasureService.drain()` reaches the database with `pool.query` on a bare
connection — deliberately, because `claim_object_erasures` is `SECURITY DEFINER`
and an erasure spans customers. `moderation.controller.ts` built it on
`PG_POOL`, which P142 wrapped in `guardReentry`, so the call became a second
checkout inside a request and was refused into `.catch(() => undefined)`.

| Fixed      | `58e9bfb2e327c08d5a436450b1c834c62cfdbc29` (P146-03) | 2026-09-01 14:59:08 |

**Window: 2 h 58 m 37 s, on one day, in the repository only.**

### A correction to my own P146 commit message

That commit says the inline drain was "dead and silent **for four days**". That
is **false**. P142 landed at 12:00 on 2026-09-01 and was fixed at 14:59 the same
day, and it was never deployed. The true figure is under three hours, in the
repository only, with no production exposure. Corrected here because a wrong
number in a compliance record is worse than no number.

### The confirming query, for whoever has production database access

This sandbox has no route to the production database — `digitalspital.com` is
blocked at the egress proxy and there is no SSH client. The evidence above is
from git and the deploy history, which is sufficient to answer the question, but
the following confirms it against the data:

```sql
-- Expect 0 rows. Any row is an erasure obligation still outstanding.
SELECT id, object_key, attempts, created_at, last_error
  FROM object_erasures
 WHERE erased_at IS NULL
 ORDER BY created_at;

-- And the erasures performed in the window, with whether their objects went.
SELECT a.created_at AS erasure_requested,
       count(o.id) FILTER (WHERE o.erased_at IS NULL) AS still_outstanding,
       count(o.id) AS queued_total
  FROM audit_log a
  LEFT JOIN object_erasures o
         ON o.created_at BETWEEN a.created_at AND a.created_at + interval '1 minute'
 WHERE a.action = 'gdpr.subject.erased'
   AND a.created_at BETWEEN '2026-09-01 12:00:31Z' AND '2026-09-01 14:59:08Z'
 GROUP BY a.created_at;
```

Run it as `./dsc as-migrator psql`. **Status: answered from deploy history;
confirmation query provided. No human action required unless the first query
returns rows.**

## P148-01 — P147 broke first boot on a fresh host

**Severity: high. Deployed. Found by running the browser suite, which P147 could
not.**

P147 finding 7 added `assertSchemaCurrent(migrationDatabaseUrl())` to
`bootstrap-admin.ts`. The reasoning was sound; the change was wrong.

```
$ pnpm test:e2e
Error: bootstrap-admin failed:
Bootstrap failed: MIGRATION_DATABASE_URL is required (the ds_migrator role).
```

`assertSchemaCurrent` reads `schema_migrations`, on which `ds_app` holds no
`GRANT` — deliberately (ADR-0002: the application role owns nothing and is not
the migrator). The documented invocation is

```
docker compose run --rm --entrypoint node api dist/bootstrap-admin.js …
```

which runs in the **api** service, where `MIGRATION_DATABASE_URL` is not set and
must not be — verified absent from both `infra/docker-compose.yml` and
`infra/deploy/docker-compose.prod.yml`.

So the platform's first-boot step became a hard failure on every fresh host:
§9.2, in the one command an operator runs before anything else works. And it was
deployed as `d3175957`.

**Fix:** the call is removed, and the file now carries the reasoning so it is not
re-added. The exposure it guarded is genuinely smaller here than for a seed — the
seeds are run by hand months later against whatever schema the host has, this
runs seconds after `deploy.sh` has migrated.

**Open decision for a human:** granting `ds_app` `SELECT` on `schema_migrations`
would make the check possible everywhere. It widens the application role for a
diagnostic, which is a database-permissions decision, not a fix to take here.

## P148-02 — `wordpress.spec.ts` has asserted a removed defect since 19.08.2026

**Severity: medium (a test, not the product). The product is correct.**

The one browser failure in this session:

```
✘ tests/wordpress.spec.ts:172 › sagt es, wenn WordPress keinen Token hat
  Timeout 20000ms exceeded … .toContain("Sitzung ist abgelaufen")
```

What the widget actually renders:

> Diese Seite konnte keine Anmeldedaten für das Lernmodul abrufen. **Das liegt
> nicht an Ihrem Konto** — … Technische Angabe: Token-Endpunkt — `endpoint_404`.

The test demands the sentence that `cf6c8c1` (P101-03, 2026-08-19) **removed as a
client-reported bug**: the widget used to blame the physician's session whenever
the token endpoint answered anything but 200, so an uninstalled plugin and an
expired token produced identical screens — and signing in again cannot fix a 404.

The test was written 2026-08-18 (`bdc3b75`), one day before the fix, and has
asserted the defect ever since.

**Why thirteen days passed:** the post-deploy smoke runs only two specs —

```
apps/e2e/playwright.smoke.config.ts:50
  testMatch: /(journey|zwei-module)\.spec\.ts$/u
```

— and nothing runs the full browser suite in CI or on deploy. Twenty-six of the
twenty-eight browser tests execute only when a person types `pnpm test:e2e`.
That is §9.1's first form: the check is not run where the work happens. It is
also the third time this exact shape has appeared (P86-02, P86-03, now this).

**Fix:** the assertion now pins the three properties P101-03 established — the
page could not get credentials; it is not the physician's account; the technical
cause reaches whoever maintains the site — and explicitly refuses the old
sentence as a regression.

## P148-03 — `subject-erasure.ts` does not assert schema freshness

**Severity: medium. NOT FIXED — GDPR-erasure surface, human review required.**

`schema-freshness.ts`'s own header says the check exists for "the seeds **and the
erasure tool**". The erasure tool does not call it:

```
$ grep -n assertSchemaCurrent apps/api/src/subject-erasure.ts
(no match)
```

Unlike `bootstrap-admin`, the credentials are available — `subject-erasure`
already requires `MIGRATION_DATABASE_URL` (line 165) and is invoked as
`./dsc as-migrator dist/subject-erasure.js` (`docs/gdpr.md:432`). So the one-line
change would work.

It is **not** made here. This is GDPR erasure, and an assertion that can refuse
to run is a behavioural change on a path with a statutory one-month deadline: a
tool that refuses because a migration is pending could block a lawful erasure.
Whether that trade is right is a compliance decision.

**The change, for review:**

```ts
// after the MIGRATION_DATABASE_URL check, before the pool is opened
await assertSchemaCurrent(connectionString);
```
