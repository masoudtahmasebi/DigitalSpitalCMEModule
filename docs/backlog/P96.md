# P96 — the widget updates without the plugin updating

**Raised by:** the client, 18.08.2026, twice and in this order.

First a URL that did not resolve, from the WordPress staging install:

> `https://gemeinsamadhsbegegnen-medice-kunden.digitalspital.de/wp-content/plugins/ds-lms/assets/ds-lms.js?ver=0.1.0` — this is not found

And then, having understood what caused it, the fix they actually wanted:

> _"please make it in a way that with updates to the js, we do not need to
> update the plugin, can we load the js from our api? so the plugin stays the
> same, but the updates come from our side?"_

Both are one ticket, because the second is the correct answer to the first.

And then, having seen it working, the shape they want it to keep:

> _"please version the plugin, and also make the js possible to be loaded from
> the staging and other logins, and make it in a structure that there is no need
> to update the plugin all the time when we update something"_

**Estimate:** 3 h + 3 h. **Actual:** 6 h.

---

## P96-01 — the bundle comes from the platform

### What was wrong

`DS_LMS_Renderer::register()` enqueued `DS_LMS_URL . 'assets/ds-lms.js'` with
`DS_LMS_VERSION` as its cache-busting query string — a file placed inside the
plugin by `pnpm wp:bundle`.

That file is a build artefact of `apps/widget` and is gitignored, deliberately,
so that a committed copy cannot drift from the source it was built from. The
consequence was never written down: **every copy of the plugin taken from this
repository was missing the only file that makes it do anything.** The failure is
silent on our side and near-silent on theirs — `wp_register_script` is happy to
point at a URL that 404s, the page renders a `<ds-lms>` element, the element
never upgrades because nothing ever defined it, and the shadow root that would
have said so is closed. Nothing is logged anywhere. It took a person opening the
URL by hand.

The mechanism that was supposed to prevent it was a sentence in
`wordpress/ds-lms/README.md` telling a human to run `pnpm wp:bundle` first.
CLAUDE.md §9.9, in its strongest form: _documentation instructing a human to
apply a setting is a setting that is not applied._ P92-04 had already noticed
this shape and proposed a release checklist, which is the same mistake written
one level larger.

### The part that was already built

`infra/nginx/widget.conf` and the `widget` stage of the `Dockerfile` have
existed since P10-04, and the Dockerfile's own comment states the intent
verbatim:

> a customer whose site should load the widget from a URL we control, so a fix
> reaches them without them redeploying a plugin

`infra/deploy/domains.sh` derives `WIDGET_URL=https://widget.${BASE_DOMAIN}/ds-lms.js`
and Caddy routes it. The host was deployed, correct, CORS-enabled and unused:
the plugin — the one host that needed it — was the one host not pointing at it.

### What changed

|                             | before                                 | after                                     |
| --------------------------- | -------------------------------------- | ----------------------------------------- |
| Source                      | `assets/ds-lms.js` in the plugin       | `https://widget.<Basis-Domain>/ds-lms.js` |
| Version                     | `?ver=<plugin version>`                | none — the cache header decides           |
| Install                     | build the bundle, then copy the folder | copy the folder                           |
| A widget fix reaches a site | when they update the plugin            | on our next deploy                        |

The address is resolved in three steps, in `DS_LMS_Settings::resolve_widget_url()`:

1. **an explicit `widget_url`**, for a customer serving the file from their own
   CDN or a developer pointing at a local build;
2. **derived from `base_domain`**, by exactly the rule `domains.sh` uses, so the
   plugin and the deploy cannot disagree about where the file is;
3. **derived from `api_base`**, but only when its first label is literally
   `api` — an install configured before P16-03 has no `base_domain`, and
   `https://api.X` is enough to know the sibling. Anything else answers empty
   and asks, rather than emitting a plausible URL that 404s.

Step 3 is deliberately narrow for the reason the whole ticket exists: a guess
that is wrong fails in a browser, far from the field that caused it.

### What a person sees

`render()` gained a second guard, separate from the API-base one. Folding them
together would tell an editor to fill in a field they have already filled in;
this one names the widget and the two fields that set it (§9.4). A visitor sees
nothing at all, as before — a broken widget is worse than an absent one.

The settings screen gained the **Widget-JavaScript-URL (optional)** field and
prints the resolved address under Basis-Domain beside the resolved API address.
Without the field the setting would be one the sanitiser accepts and no screen
offers, which is §9.2 from the other direction.

### The checks, and watching them go red

`wordpress/ds-lms/tests/security-test.php`: 53 checks → **69**. The sixteen new
ones cover both derivations, the override, the refusal to guess, the registered
URL, the absent version, the two guard messages, and that the shortcode is still
registered when there is no bundle to register — otherwise `[ds_lms]` renders as
literal text on a live page instead of as the editor's message.

Broken twice, deliberately:

- reverting the registration to `DS_LMS_URL . 'assets/ds-lms.js'` with
  `DS_LMS_VERSION` → 3 red;
- neutering the render guard → 2 red.

The harness needed two changes to make that possible, and both are §9.1 in
miniature: `wp_register_script` was discarding the version argument, so no test
could have seen `?ver=`; and `ds_test_reset()` was not clearing `scripts`, which
is §9.8's ambient-state rule — the store a new assertion reads is exactly the
store nobody had needed to reset yet.

### The rig now loads the bundle across an origin, because the product does

`apps/e2e/support/wordpress.ts` served `/ds-lms.js` from the WordPress origin
itself. That was faithful to the old plugin and is not faithful to this one, and
the difference is the entire class of defect this change moves into: a missing
`Access-Control-Allow-Origin`, a `Cross-Origin-Resource-Policy` of
`same-origin`, a content type a `nosniff` refuses. Every one of those fails in a
conversation between the browser and the file server that neither the API nor
WordPress is part of — P70-01's bucket and P74-07's `media-src`, one origin over.

So `apps/e2e/support/widget-host.ts` serves the bundle on `127.0.0.1:4183`
under headers **parsed out of `infra/nginx/widget.conf`**, not copied from it.
A copy would be a second policy, and the day it drifted the suite would be
asserting a policy no installation serves — which is the failure mode of the
thing it exists to catch (§9.13, rule 2).

### And the deploy asks the question a customer's browser will

Every embedded Fortbildung on the platform now depends on one host, so
`deploy.sh` gained step 6d: `HEAD ${WIDGET_URL}`, retried through ACME, and a
`grep` for the CORS header. A host that does not answer, or answers without it,
fails the deploy — because otherwise it fails in a browser we do not own, with a
clean server log, which is exactly how the bucket's CORS rule survived from
P23-04 to P70.

## What MEDICE has to do, and it is not nothing

Two settings on their side, neither of which we can apply for them:

1. **Their `Content-Security-Policy`, if they send one, must name the widget
   host in `script-src`** — `script-src 'self' https://widget.digitalspital.de`.
   A missing entry looks identical to a broken widget: the file downloads, the
   browser refuses to execute it, and the only evidence is a line in the
   visitor's console.
2. **Their site's origin must be in the project's Erlaubte Einbettungs-Domains**
   (P94-04), or every request the widget makes to the API is refused by CORS.

Both are in `wordpress/ds-lms/README.md` under "What the customer's site has to
allow", and both belong on the launch checklist rather than in a sentence
somebody reads once — see P92-03.

## Deliberately not done

**A version or hash in the URL.** It would restore the coupling this removes:
the plugin would once again decide which bundle a visitor gets, and a widget fix
would once again wait for a plugin release. Five minutes of `must-revalidate`
is the trade, and it is the right one for a file whose whole purpose is to be
updatable without anybody's involvement.

**Serving the bundle from the API.** The client asked "can we load the js from
our api?" and the answer is: from the platform, yes — but from `widget.<base>`
rather than `api.<base>`. They are the same deploy and the same TLS certificate
authority, and the separation is load-bearing: the API's CORS policy is narrow
and per-project by design, and the bundle's has to be `*` because it is public
JavaScript loaded by origins we do not know in advance. Putting them on one
host would mean one of those two policies is wrong.

## P96-02 — one version, in three places that cannot drift

`0.1.0` appeared twice — the `Version:` header WordPress reads, and the
`DS_LMS_VERSION` constant PHP can see — with nothing checking they agreed, and
nowhere at all that an operator could read either.

Now **1.0.0**, with `CHANGELOG.md` beside it, and a check that refuses a release
where the header, the constant and the changelog's newest entry disagree. A
plugin whose three answers differ is worse than one with no version, because the
wrong answer is the one somebody will act on. The test reads the version out of
the plugin instead of restating it — a test carrying its own copy of the number
it is checking cannot notice the number changing. Watched go red by bumping the
constant alone: 2 failures.

1.0.0 rather than 0.2.0 because the promise changed. The number can now stand
still while the product moves: the learner widget is released with the platform,
so a change to a screen, a rule, a message or a request never reaches this
changelog. What does is the six things the plugin still decides — where to look
for the platform, what the settings are called, what markup goes on the page,
who may call the token endpoint, what the editor is told, and the WordPress and
PHP floors.

The version is on the settings screen and on the element as `data-ds-plugin`,
beside the `data-ds-build` the widget writes for its own. Between them, §9.9's
first question — _which build?_ — is answerable from a browser rather than over
FTP.

## P96-03 — the plugin emits data, not JavaScript

`attach_token_provider()` wrote about forty lines of JavaScript into every page
carrying the widget: fetch the endpoint, set `X-WP-Nonce`, add `refresh=1` on a
retry, handle the failures, and assign `element.tokenProvider` in a way that
survives the element upgrading late.

Every one of those lines already existed in `apps/widget/src/token.ts`. The cost
of the duplicate was specific and is exactly the one the client named: **a change
to how a token is fetched needed a plugin update on every customer site.** A
retry, a timeout, a different failure — frozen at whatever version of the plugin
that site last installed.

The page now carries:

```html
token-endpoint="/wp-json/ds-lms/v1/token" token-header="X-WP-Nonce: …"
```

and no script at all. `token-endpoint` already existed in the widget; `token-header`
is new, and is deliberately **one header rather than a mechanism**. WordPress
needs exactly this one — a nonce proving the request came from a page it
rendered rather than from another origin borrowing the visitor's cookie — and a
general header facility would be a way for a page to make the widget send
anything anywhere. The name is checked against RFC 7230's `token` production and
the value against control characters, so neither can smuggle a second header;
a malformed value is dropped rather than handed to `fetch`, which would throw
_inside_ the provider and surface as "no token" — a message that sends whoever
is debugging it to the wrong system.

Nothing is exposed that was not before: the nonce was already in the page, in
the script that is gone, and it is not a credential — it is bound to this
visitor's session and worthless without their cookie. No token has ever been in
the markup and none is now.

Watched go red properly, in a browser: removing `token-header` from the rig's
page fails the WordPress journey, because the endpoint refuses without the nonce
and the widget renders a signed-out state for a signed-in visitor. That is the
one place this can be checked — an API test cannot see an attribute a screen
does not send.

## P96-04 — "is it actually reachable from here?"

This whole ticket exists because the way the 404 was found was **a person typing
a URL into a browser.** Nothing on the WordPress side ever asked whether the
addresses it was configured with led anywhere, and since P96-01 that matters
more rather than less: a site can point at production, at staging or at an
installation that does not exist, and the three look identical on the settings
screen.

**Verbindung prüfen** now asks. It reports, for the bundle: unreachable, a
status that is not 200, a 200 without `Access-Control-Allow-Origin` — which is a
file the browser downloads and refuses to run, indistinguishable from the site
owner's chair from a widget that does nothing — or reachable and loadable. For
the API: unreachable, a status, or reachable.

Two things it deliberately does not do, and both are §9.1:

- **It never fetches a URL from the request.** A check that took its target from
  a query parameter would be an SSRF primitive: anyone who could get an
  administrator to follow a link could make this server request an address of
  their choosing and read the outcome. The addresses come from the stored
  settings, the trigger is nonce-bound, and it needs `manage_options`. There is
  a test that names `169.254.169.254` in `$_GET` and asserts it is not fetched.
- **The API line does not claim to have checked CORS.** A server-to-server
  request carries no `Origin`, so it would pass while every visitor's browser
  was refused. It says so, and names where the answer lives — the project's
  Erlaubte Einbettungs-Domains in the console.

Bodies are never echoed, only statuses and header presence: a response body from
an unexpected host is the last thing that should be printed into an admin
screen.

## On "loaded from the staging and other logins"

Nothing needed building for this, and saying why is worth more than a change
would have been:

- **The bundle** is served with `Access-Control-Allow-Origin: *`. That is correct
  and is not a weakening — it is public JavaScript with no credentials and no
  cookies — so production, staging, a second customer and a developer's
  `localhost` can all load the same file.
- **Which platform a site talks to** is one field: Basis-Domain, from which both
  `api.<domain>` and `widget.<domain>` derive. A staging WordPress fills in the
  staging domain and nothing else about the plugin differs.
- **Which sites the API will answer** is the narrow policy, and it is per project
  with patterns — `https://*.medice.de`, `http://localhost:*` — built in P94-04.

So the capability was there and the visibility was not, which is what P96-04
fixes and what the plugin README now states in one place.
