# P120 — The two video rules were built, and only half-proven

**Status:** built. Both behaviours already existed; what was missing was
anything that could show they still work.

---

## What the client asked for

> "the video should not scrollable be to forward. the user can go back in time
> in video, but they can not go forward to just for example seek to end of the
> video without watching it. so the user has to watch the video."
>
> "when the user leaves the video section and comes back and does not finish the
> video, they come back to the start minute of the video, for example I am
> watching a video which is 18 minutes, at 12:34 i pause or close the window,
> and after a day i resume the learning, my video starts from 12:01."

## What was already there

Both, and to the second.

| Behaviour                                | Where                                                                                                                                                             | Since            |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| Forward seeking clamped to watched + 5 s | `seekCeiling` / `clampSeekToLimit` / `playerSeekLimit` in `@ds/domain`, enforced in `VideoPlayer` on every seek path **and** on the element's own `seeking` event | before `8ae85f3` |
| Backwards seeking untouched              | same                                                                                                                                                              | same             |
| Resume at the last whole minute          | `resumePosition` — `RESUME_GRANULARITY_SEC = 60`, so 12:34 → 12:00                                                                                                | same             |

`resume.test.ts` already asserts `875 → 840`, which is the client's example in
seconds. `learning-flow.integration.test.ts` already asserts the API returns
`resumeAtSec: 540` for a stored position of 600, and that it never exceeds the
ceiling. `<video controls={false}>` — the scrub bar is the widget's own, so
there is no native control to fight.

So the report is **not** "this was never built". It is either a real defect
somewhere the tests do not reach, or a build the browser was running that was
not this one. Two hypotheses were checked and closed:

- **A stale deployment (§9.9).** `packages/domain/src/resume.ts` is present in
  `8ae85f3`, the commit production was on. Not it.
- **A cached bundle.** `infra/nginx/widget.conf` serves `ds-lms.js` with
  `public, max-age=300, must-revalidate`. Five minutes, then revalidated. Not
  it either.

Which leaves the layer nothing was testing.

## The gap, which is the actual finding

### P120-01 · The clamp was never exercised in a browser

Four component tests cover it and pass. They drive a **jsdom** element whose
`currentTime` is a plain property: writing it fires nothing a browser would
fire, and the element never buffers, never re-ranges, and has no native controls.
Every one of those is a way the clamp could hold in the suite and not in
Chromium — CLAUDE.md §9.13, a function covered exhaustively that proves nothing
about the product.

`journey.spec.ts` now performs the seek the physician described, on a real
element, and asserts the playhead did not move meaningfully past where it
already was. Deliberately a _small_ forward jump from ~17 s into an 18 s
fixture, because a large one is the easy case.

With a control: a **backwards** seek must still work. A player that refused
every seek would pass the first assertion and be a worse product — re-watching
a passage is the ordinary use of a scrub bar, and the accreditation asks that
the material be seen, not endured in one pass.

### P120-02 · `startAtSec: 875` sat in the fixture and nothing read it

The default fixture in `VideoPlayer.test.tsx` has carried a resume position
since the prop existed, and **no case asserted the element ever opens there** —
every seeking case overrides it to 0, which is right for those cases and left
the resume covered by nobody.

The rule is tested. The API's answer is tested. Between them sat one
`handleLoadedMetadata`, untested: §9.7 exactly — name the caller, or the call
site is the thing that is untested.

Three cases now:

- it opens at the stored minute **after** `loadedmetadata`, and not before —
  writing `currentTime` before the element knows its duration is silently
  discarded by every browser, so the ordering _is_ the behaviour;
- it does not seek past the end of a file shorter than the stored position — a
  re-encode leaves a player that will not start;
- it leaves a learner who is already somewhere alone. `loadedmetadata` can fire
  more than once, and a resume that re-applied itself would drag somebody
  backwards mid-lesson, which is what P71-01 was.

## Evidence the checks can go red (§9.1)

| Broken                                        | Went red       |
| --------------------------------------------- | -------------- |
| `if (false)` in place of the resume condition | 2 widget tests |
| the resume re-applies over a moved playhead   | 1 widget test  |

The journey's two assertions are not listed: they run against a deployed
installation, not in `pnpm verify`, and their first real run is the deploy that
carries them. Claiming them as proven before that would be the overstatement
§9.1 is about.

## What the fixture cannot show, said plainly

The e2e video is eighteen **seconds** and the resume granularity is sixty, so
every resume in that rig floors to 0. The journey therefore cannot demonstrate
minute-granular resume, and no assertion pretends to — lengthening the fixture
past a minute would add more than a minute of real playback to every run for a
rule three other layers already pin.

A check whose reach is overstated is how the last four defects survived.

## Still open

**Whether the client's original observation reproduces on the current build.**
Nothing found in the code explains it, and the two obvious environmental causes
are ruled out above. The journey now asks the question on every deploy, which is
the only instrument that could have answered it — and if it stays green while a
browser still allows the seek, that difference is itself the next finding.
