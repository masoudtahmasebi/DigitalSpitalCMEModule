## ⚠️ This is new scope, not a defect

Per-module assessment is **Teilprüfung**, and it is deferred by name:

- `docs/requirements/medice-adhs.md` §6.1 puts it outside the 140 h budget.
- `apps/widget/src/components/PlayerScreen.tsx`'s header records the decision
  and its reason: _"A Teilprüfung is a per-module assessment and is explicitly
  out of the 140 h scope; the quiz engine models one course-level
  Lernerfolgskontrolle."_

The client has asked for it directly, so it is theirs to have. CLAUDE.md §3
requires the deviation be named rather than absorbed: this costs budget against
a fixed 06.09.2026 date, and the declared trade lever is the admin console
(P9, 18 h).

**Estimate: 10–14 h.** Not a small change — it touches gating, the player, the
authoring rules and the completion arithmetic, and gating decides CME points.
Needs human review before merge (CLAUDE.md §2).

## P87-01 — the bug this starts from

A course with a quiz on each of two modules is **unfinishable today**, and the
three pieces that make it so each look correct on their own:

| Where                                       | What it does                                                      | Consequence                                       |
| ------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------- |
| `hasPassedQuiz` (`learning.service.ts`)     | `quizIds.every(passed)` — every quiz in the course must be passed | correct for the new model, and already right      |
| `findQuizContent` (`widget/player.ts`)      | `return`s the **first** quiz found in the whole course            | the second is never offered to anybody            |
| `nextAvailableContent` (`widget/player.ts`) | `if (content.kind === "quiz") continue`                           | the second cannot be reached by **Weiter** either |

So the learner passes quiz 1, quiz 2 is unreachable by any route,
`courseComplete` stays false for ever, and no certificate is issued. Since
P82-01 they at least get an honest _"für die CME-Punkte fehlen noch
Abschnitte"_ rather than a 409 — but they still cannot finish.

Derived from source, and since **reproduced and fixed**. The journey in P87-05
now walks the shape end to end and issues the Bescheinigung.

### And a fourth piece, which only the browser found

A quiz sitting in the same chapter as its video was reachable **at nought per
cent watched**, on every course the platform has ever had. Content inherits its
chapter's gate — `buildModuleStates` says so in as many words, _"a content item
is exactly as reachable as the chapter containing it"_ — which is right for two
videos in one chapter and wrong for the one shape every author actually builds.

It was invisible from every direction at once: the API was consistent with
itself, the widget rendered the gate it was given, and no test asserted on
_which_ of the two controls was under the player. It surfaced the moment the
journey started asking, and it is what P87-04 below now decides.

---

## The model, as the client stated it

1. A module **may** have a Lernerfolgskontrolle. Zero or one, not several.
2. Its videos come first; the quiz is the last thing in the module.
3. **Passing it opens the next module.** That is the gate — not merely watching.
4. A module without one behaves as today: finishing its content opens the next.
5. The course is complete when every module's requirements are met, which the
   API already computes correctly.

## The work

### P87-02 — the player offers _this module's_ quiz (3 h)

> **Done 17.08.2026.** The client answered the question below — _"each module
> part, can have quiz or not, if it has the tab is shown, if not it is not
> shown"_ — which is the tab rule at module granularity, and the five tests were
> migrated rather than deleted. The `PlayerScreen` fixture now carries exams on
> modules **2 and 3** with the lesson in module 3, so a course-wide search
> returns the wrong one and the tests can go red (§9.1); both were watched to
> fail with the old search restored.
>
> The record of the first attempt, kept because it is the cost:
>
> **Attempted and reverted earlier the same day.** The change itself is small —
> `findQuizContent` takes the current content id, `locateContent` gives its
> module, the search stays inside it, and `nextAvailableContent` stops skipping
> quizzes. It compiled. It then failed **five** existing tests, and each failure
> is the old model written down rather than a mistake:
>
> - `never slides into the Lernerfolgskontrolle` asserts the skip that P87-03
>   deliberately removes;
> - four `PlayerScreen` cases put the fixture's only quiz in module 5 and drive
>   a lesson in module 1, so under module scoping there is correctly no quiz.
>
> Migrating those five is the actual work of P87-02, not an afterthought, and it
> was reverted rather than committed half-done.
>
> **And it has a consequence for MEDICE that needs a decision.** Their course
> has one exam, in the last module. Today every module shows a locked
> Lernerfolgskontrolle tab; under module scoping only the last one would. That
> is arguably more honest — it is P82-03's rule at module granularity — but it
> changes a live course's screens and is not a silent refactor. **Ask before
> shipping it.**

`findQuizContent` takes the current content and returns the quiz belonging to
**its** module, or `undefined`. The course-wide search goes.

The Lernerfolgskontrolle tab follows it: present when this module has one,
absent when it does not — P82-03 already established that a tab which can never
unlock must not be drawn, and this is the same rule at module granularity.

### P87-03 — the way forward runs through the quiz (2 h)

`nextAvailableContent` stops skipping quizzes. After a module's last video the
next thing is that module's Lernerfolgskontrolle, and after passing it, the next
module's first content.

The quiz-passed screen already offers `onNext` (P82-01); it will simply now have
somewhere to point.

### P87-04 — gating (4 h, `packages/domain`, human review) — **done**

Not where this ticket expected. `evaluateSequence` already gets the second half
right: gating runs over the **chapter** sequence and a chapter is complete only
when every content in it is, so a module whose exam is outstanding already locks
every later module. Nothing needed to change there.

What was missing is the other direction — the exam opening **early**. The rule
is now `contentGates` in `packages/domain/src/module-quiz.ts`: a module's
Lernerfolgskontrolle is locked until that module's videos are complete, names the
first outstanding one as `blockedBy`, and is never re-locked once passed.

Enforced in `assertReachable` as well as rendered, so a direct `GET` or `POST`
to the quiz is refused with the same answer the screen gives — hiding a control
is not a gate (§4 invariant 1).

**Only videos count as the precondition**, and that is a decision rather than an
oversight: `text` and `details` are in the compliance tree and have no completion
event, so a rule that waited for them would produce an exam that never unlocks.
See P87-08.

Thirteen unit tests, five of which were watched to fail against the old
inheritance. Sixteen API tests and thirty integration tests were reaching a quiz
whose module was unwatched — the rule proving itself — and were reordered to
watch first, with the refusal given its own assertions at both layers.

Note the interaction with P82-05: content completion uses the enrolment's
`requiredWatchPercent`. A module gate is watch **and** quiz, not one or the
other.

### P87-05 — the journey the client asked for (3 h)

An e2e spec that does what was requested end to end: create an organisation,
author a course with two modules and a Lernerfolgskontrolle on each, publish,
then as a physician watch module 1, pass its quiz, verify module 2 opened, watch
it, pass its quiz, and download the Teilnahmebescheinigung.

This is the check that would have caught P87-01, and its absence is why the
platform shipped a shape it cannot complete.

**Run it against a locally deployed stack before believing it** — three stale
assertions in the existing journey surfaced today only because the whole
application was stood up and driven, and the journey does not run on branches
(see the open question below).

**Done**, as `apps/e2e/tests/zwei-module.spec.ts`, green against the local rig
together with the other twenty specs. It took four runs to get there and each
failure was real:

| Run | Failed on                                       | What it was                                                                                       |
| --- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 1   | the video content never appeared                | „Hinzufügen" pressed before the measured length arrived, and the form refuses a video without one |
| 2   | `getByText("Modul 2 · Therapie")` was ambiguous | the console draws an **"In anderes Modul verschieben"** select whose `<option>` carries the title |
| 3   | the exam's start button                         | the screen calls every exam **Abschlussprüfung** — see below                                      |
| 4   | —                                               | passed                                                                                            |

Run 3 is a finding, not a harness problem. With one exam per course a single
word for it was enough; with one per module the sidebar names them individually
and the screen two inches away did not, so a physician could not tell which exam
they were sitting or — on a failed attempt — which one to repeat (§9.4). The
heading, the start button, the pass banner and the retry button now carry the
exam's own title, from `indexTitles`, which is the same map the outline draws
from.

### P87-06 — authoring refuses what the model cannot express (1 h) — **done**

One quiz per module. A second is refused at the API with a message naming the
module, rather than being accepted and silently ignored — which is the shape
that produced P87-01 in the first place.

`assertOnlyQuizInModule` covers creation _and_ an update that moves a content
into `quiz` from another kind. The message names the module by its title and no
identifiers (§9.5). Asserted from the console in P87-05's journey, so it is an
affordance an author meets rather than a 422 nobody sees, and watched to go red
with the refusal neutered.

### P87-07 — the video's length is the file's length (not started)

The client, four times over: _"i have seen the whole video, but it still says
95 % angesehen"_, and then the diagnosis in their own screenshot — _"Diese
Stellen fehlen noch: 0:19–0:20"_ on a video that is 0:19 long.

The console already measures the object and says so on the form (_"Aus der
Videodatei gelesen und nicht von Hand gepflegt"_), so **new** content is right;
what remains is content authored before that, or with a hand-typed figure, which
carries a `durationSec` larger than the file and a watch gate nobody can satisfy.

Two parts, and only the first is small:

1. **Derive it server-side, at confirm time.** The API already fetches the
   object to verify the upload; reading the duration out of the container header
   — an MP4 `mvhd` box, a WebM Segment Info — is tens of lines and no
   dependency. This is _not_ transcoding, so it does not touch deferred scope.
   The client asked for exactly this: _"maybe we can even check the length of
   the video on the fly, as this would remove soooo many of our problems."_
2. **Repair what is already stored**, for the courses that have the problem now.

What is **not** done, and why (CLAUDE.md §4 invariant 1): _"if the video is
done, that video part of the module is done"_ — as a client-reported `ended`.
The browser saying it finished is trivially forgeable and would make the watch
gate decorative on a document that carries CME points. Deriving the true length
server-side gets the client the outcome they are asking for — a video watched to
its end reaching 100 % — without the client ever being the authority.

### P87-08 — a text lesson can never be completed (not started)

Found while writing P87-04. `POST contents/:id/progress` accepts `video` alone,
and `text` and `details` are in the compliance tree — so a chapter containing one
is **permanently incomplete**, and every later module in the course is locked for
ever. The console offers both kinds in its "Art" dropdown.

Exactly the shape of P87-01: a course the platform accepts and nobody can
finish. `isComplianceContent` already records this reasoning for `material` and
it was never applied to the kind beside it (§9.2, §9.3).

Not reproduced yet — no seeded or authored course uses a text content — which is
also why nothing has caught it. Either opening it is the completion event,
recorded server-side, or the kind leaves the compliance tree; the first is
closer to what an author means.

## Acceptance criteria

- [x] A module with a Lernerfolgskontrolle does not open the next module until
      that quiz is passed. _(Already true — the chapter sequence does it. Pinned
      by the journey's assertion that Modul 2 is padlocked.)_
- [x] A module without one is unaffected.
- [x] Every module's quiz is reachable, from the player and from **Weiter**.
- [x] A course with a quiz on each of two modules can be completed and yields a
      Teilnahmebescheinigung.
- [x] Authoring refuses a second quiz in one module, naming it.
- [x] The domain rule has exhaustive unit tests, and each was watched to fail
      against the old behaviour.
- [x] P87-05 runs green against a stack deployed locally — with the whole e2e
      suite, 21 specs.

Added along the way, beyond what was asked:

- [x] A module's Lernerfolgskontrolle does not open **before** that module's
      videos are watched, at the endpoint as well as on the screen (P87-04).
- [x] Each exam is named by its own title wherever a learner meets it.

Not done, and carried as their own items above: P87-07 (the stored duration) and
P87-08 (a text lesson that cannot be completed).

## Open question, for DigitalSpital rather than the client

The existing journey does not run on branches, so a change to any screen it
touches is unverified until a post-deploy run — where it fails with the code
already on the server and looks like a product fault. Three of today's failures
were exactly that. Running the rig in CI costs minutes per push; leaving it
costs finding these in production. **Not decided here** — it is a judgement
about the pipeline's economics, and it is the client's money.
