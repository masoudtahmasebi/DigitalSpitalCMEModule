# P140 — Nothing was watching, and nothing was backed up

**Status:** built. One thing still needs a human: the external heartbeat account.

---

## What the incident exposed

The API container reported `unhealthy` for **twenty-two hours** while serving
every request put to it, and the way anybody found out was the client opening
the console and asking. Then the client said the thing that matters:

> _"this really shows us that we have a problem in monitoring and seeing what
> the issue was and also in backup and restore!"_

Both halves are correct, and the evidence is worse than "we lack monitoring".

**Nothing scrapes `/metrics`.** The endpoint exists, exposes request counts,
durations and `ds_build_info`, is deliberately public, and is read by no
Prometheus, no Grafana, no uptime check — nothing at all. §9.3 at the
infrastructure layer: a rule written that nothing calls.

**`ALERT_WEBHOOK_URL` is wired to EIV deadlines and to nothing else.** The one
alert channel the platform has fires for one condition.

**The backup timers were never installed.** Confirmed by the client:
_"They were never installed."_ So this platform has run for weeks with **no
backup of any kind** — behind a meticulous runbook, an encrypted dump, a
retention policy and a freshness check, none of which had a file to act on.

That is P70-01 exactly. `backup.timer` was a file in the repository whose header
says _"Copy the four sections below into /etc/systemd/system/"_ — and §9.9's
strongest form is that **documentation instructing a human to apply a setting is
a setting that is not applied.**

**And it could not have worked anyway.** The units hard-coded `User=ds` and
`/home/ds/ds-education/repo/…`. The installation runs as `deploy` out of
`~/Repositories/DigitalSpitalCMEModule`. An operator who followed the runbook to
the letter would have installed three units that fail on every fire. The manual
step was not merely skipped; it was impossible to complete correctly.

## What was built

### The deploy installs the timers

`deploy.sh` writes the units from the paths it is actually running from and
enables them — backup, backup-verify and the new watchdog. No copying, no
`User=` to get wrong, and it rewrites them every deploy so a unit cannot drift
from the checkout (the §9.9a lesson, applied before it costs anything).

Where it cannot — no systemd, or no passwordless `sudo` — it says so loudly and
names the one command to run, rather than continuing quietly.

### A watchdog, in two halves that need each other

`watchdog.sh`, every two minutes:

- **Local.** Every container from `docker compose ps` (so a service added to the
  compose file is watched without anybody remembering), plus `/health/ready`
  from inside. Problems POST to `ALERT_WEBHOOK_URL`. This half sees what only
  the host can see — "Redis is running and not answering" is invisible from
  outside, because every route that avoids Redis keeps working.
- **Remote.** When everything is healthy it pings `HEARTBEAT_URL`, and an
  external dead-man's-switch raises the alarm when the pings stop.

Neither is enough alone, and the reason is the whole design: **a watchdog on a
dead host reports nothing** — the failure that silences the alarm is the failure
the alarm is for — so "this host is gone" has to be noticed somewhere that is
not this host.

The heartbeat is sent **only on success**. An unconditional ping is a heartbeat
that says "fine" while the building burns.

It never restarts anything. A watchdog that restarts on unhealthy turns a
recoverable dependency failure into a restart loop — the argument
`health.service.ts` already makes about liveness.

## Still open, and it needs an account rather than code

`HEARTBEAT_URL` is empty until somebody creates a check at healthchecks.io,
Better Stack or Cronitor and pastes the URL into `config.env`. The deploy warns
when it is unset. That is a genuine remaining gap and it is named here rather
than left as a green tick.

## The one that is a launch blocker

**There is no backup of production.** The timers are installed now, so the first
one runs at 02:15. Until a `backup verify` has passed and a restore has been
performed into a scratch database, this platform has no recovery path at all —
and a CME platform losing its enrolments loses evidence for points already
awarded.

`backup verify` also still checks **freshness only**: that a recent file exists,
not that it decrypts or is a readable `pg_dump` archive. A backup nobody has
restored is a hypothesis. Named, not fixed.
