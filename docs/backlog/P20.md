# P20 · A second customer

The platform is multi-tenant and had one tenant. Everything that spans
customers — the console's registry, the project picker, the `customer_admin`
scope — was therefore correct by having nothing to be wrong about.

---

## P20-01 · The DS test tenant — **done**

- **Estimate:** 3 h · **Depends on:** —

**Why**

Asked for directly: _"please be mindful of two customers, one medice, and
second named ds for testing purposes."_

The tenant-isolation suite already proves cross-tenant reads return zero rows.
That is the claim that matters and it is not a claim anybody can _look at_. An
operator signing into the console met a customer registry with one entry, and a
"which customer?" question with one answer — so a screen that quietly ignored
the customer scope was indistinguishable from one that honoured it.

**Scope**

- `packages/seed` — a new workspace package, `@ds/seed`.
- `db/seed/ds-demo.ts` — the developer's `tsx` runner over it.
- `apps/api/src/seed-ds.ts` — the same, from inside the API image.
- `db/seed/adhs.ts` — moved onto the shared library, losing its own copies of
  the connection guard, the tenant context and the content teardown.
- CI runs both seeds against the real Postgres, twice each.

**Two courses, and the second is the point**

| Course           | Points | VNR   | Quiz | Why                                         |
| ---------------- | ------ | ----- | ---- | ------------------------------------------- |
| `ds-cme-demo`    | 3      | dummy | yes  | the full path, to a Punktemeldung and a PDF |
| `ds-ohne-punkte` | none   | none  | no   | a course without CME points, which is real  |

A course without points is a case the client stated and nothing exercised.
Everything downstream has to cope: the card's metadata line has no "4 CME
Punkte" to print, the Zertifizierung tab has no accreditation to describe,
completion produces no EIV submission and issues no certificate. `cme_points`
is **null**, not zero — `cme_points > 0` is a check constraint, and zero would
anyway mean "accredited for nothing" rather than "not accredited".

**Acceptance criteria**

- [x] The seed runs **from the production image**, not only from a checkout.
      A seed that needs `tsx` and the workspace can never be run against the
      deployment it was written for — which is what `@ds/migrator` and
      `apps/api/src/db-migrate.ts` already say about the migrator
- [x] **One implementation**, two `main()`s. The last time this repository had
      two copies of something like this, both copies shared a bug that only
      production could expose
- [x] The connection guard, the tenant context and the content teardown exist
      once. The copies that matter are the safety ones: a pasted-then-edited
      "refuse a non-local database" check is how learner progress gets deleted
      in production because somebody widened the host list in one file
- [x] The DS project has its **own Keycloak issuer**. Two projects sharing one
      realm would pass every test and prove nothing — the interesting question
      is whether a token minted for one customer's realm is refused by the
      other's project, and asking it needs two issuers
- [x] The accreditation columns travel as one group. Passing them separately is
      how a seed produces a course with points and no VNR, which is a state the
      EIV worker has no idea what to do with
- [x] CI runs both seeds **twice**, because they claim to be idempotent and a
      second run is the only thing that checks the claim
- [x] CI asserts the outcome, not just the exit code: courses across two
      distinct `customer_id`s, and one course with no points, no VNR and no
      accreditation body
- [x] The VNR is a documented dummy and the Ärztekammer is named as fictional.
      Nothing here can reach the live EIV endpoint — the deploy refuses that
      without `EIV_ALLOW_LIVE=yes` (ADR-0005)
- [x] `docs/deployment.md` §5 says what `--force` actually destroys, which is
      learner progress on those two courses and nothing belonging to any other
      customer

**The point-free course was then checked in a browser**, at 430 px against the
real bundle, because "the schema allows it" and "the frontend survives it" are
different claims. With `cmePoints`, `vnr`, `cmeCategory` and
`accreditationBody` all null the meta card simply drops the orange pill and
centres what is left — no empty chip, no "null CME Punkte", no hole where the
points were — and the Zertifizierung tab renders without error. Nothing in the
console.

What that tab _shows_ is still the course outline rather than certification
detail, which is ticket #60's job and predates this. Worth stating so the
screenshot is not mistaken for a regression introduced here.

**Deliberately not seeded: a staff account.** Creating one here would mean
choosing a password in a file. The ordinary flow — `bootstrap-admin`, then an
invitation scoped to this customer — is also the flow being tested: a
`customer_admin` on `ds` who can see MEDICE is the bug this tenant exists to
make visible.

**Deliberately not moved: the MEDICE seed.** Its content belongs to a customer
and reaches production through the admin console, not through a script.
Seeding a course that carries a real VNR from a file in this repository is how
a placeholder gets a Punktemeldung. It stays a development fixture.
