### P2-01 · Customer, Department and Project CRUD

- **jira:** _(unassigned)_
- **Estimate:** 3 h · **Week:** 2 · **Depends on:** P1-05
- **Review gate:** none

**Context**
Department exists so that MEDICE's therapeutic areas get per-area admin scoping
and reporting without becoming separate customers, which would break billing and
admin access (roadmap §3).

**Scope**

- CRUD for the three levels, respecting the role model from P1-04.
- Project holds SMTP settings, branding and the Keycloak realm/issuer/audience
  binding. SMTP credentials are write-only — encrypted at rest, never returned.
- Slug/identifier uniqueness scoped to the parent, not global.

**Acceptance criteria**

- [ ] `department_admin` sees only their own department's projects
- [ ] SMTP credentials are never present in any response body, at any role
- [ ] Deleting a parent with children is refused with a clear error rather than
      silently cascading
- [ ] Two customers can hold departments with the same name without collision

### P2-02 · Course CRUD with compliance fields

- **jira:** _(unassigned)_
- **Estimate:** 3 h · **Week:** 2 · **Depends on:** P2-01
- **Review gate:** human — assessment
- **Implements:** ADR-0002

**Context**
Course is where every compliance setting lives. `required_watch_percent` is
configurable per course precisely because the layout says 80 % and MEDICE-292
says 100 % (roadmap §11) — the system takes no position, the course record does.

**Scope**

- VNR, encrypted VNR password, `cme_points`, `cme_category`,
  `accreditation_body`, `valid_from`/`valid_to`, `fortbildungsnummer`,
  `pass_threshold_percent`, `required_watch_percent`, `retry_policy`.
- Validation: percentages are integers 0–100; validity window ordered; CME points
  positive.

**Acceptance criteria**

- [ ] `required_watch_percent` accepts any integer 0–100 and defaults to the
      MEDICE value of 100 on the seeded course
- [ ] `pass_threshold_percent` defaults to 70 on the seeded course
- [ ] The VNR password is write-only, encrypted at rest, and absent from every
      response
- [ ] A validity window ending before it starts is rejected
- [ ] Changing a threshold does **not** retroactively alter already-issued
      completions or certificates

### P2-03 · Module, Chapter and Content CRUD with ordering

- **jira:** _(unassigned)_
- **Estimate:** 3 h · **Week:** 2 · **Depends on:** P2-02
- **Review gate:** none

**Context**
Ordering is load-bearing: sequential gating in P3-03 is defined by it, so an
ambiguous or duplicate ordinal becomes a gating bug that looks like a content bug.

**Scope**

- CRUD for modules, chapters and content items (video, text, quiz, details).
- Explicit ordinal per level, with a reorder operation that is atomic.
- Content type discriminated so a chapter can carry video + text + quiz.

**Acceptance criteria**

- [ ] Ordinals are unique within their parent, enforced by the schema
- [ ] Reordering is atomic — a failure leaves the previous order intact, never a
      partial one
- [ ] Deleting a chapter with recorded learner progress is refused, not cascaded
- [ ] Video content carries a duration, without which the watch gate cannot be
      evaluated

### P2-04 · Tenant isolation enforcement in the API layer

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 2 · **Depends on:** P2-03
- **Review gate:** human — tenant isolation
- **Implements:** ADR-0002

**Context**
RLS is the guarantee; this task is the defence in depth on top of it, and the
place where `customer_id` gets correctly denormalised onto every inserted row.

**Scope**

- Repository layer sets `customer_id` on insert from the tenant context, never
  from client input.
- Application-level scoping in queries as a second layer.
- A test suite that attempts cross-tenant reads and writes at every level of the
  hierarchy.

**Acceptance criteria**

- [ ] Every cross-tenant read returns zero rows; every cross-tenant write is
      rejected by the database `with check`, proving RLS is doing the work
- [ ] A deliberately introduced missing application-level filter still leaks
      nothing — verified by a test that removes it
- [ ] `customer_id` on a nested insert is derived from the parent, never supplied
      by the client

### P2-05 · Public catalog read API

- **jira:** _(unassigned)_
- **Estimate:** 3 h · **Week:** 2 · **Depends on:** P2-04
- **Review gate:** none

**Context**
What the widget renders: the course list with its filters and the full course
tree for the detail view.

**Scope**

- Course list with `Thema` and `Altersgruppe` filters and their facets.
- Course detail returning the module/chapter/content tree in one request, so the
  widget does not waterfall.
- Quiz answer keys are **never** included in any catalog response.

**Acceptance criteria**

- [ ] Course detail returns the whole tree in a single request
- [ ] No response at any endpoint contains a correct-answer flag
- [ ] Filters return correct facet counts against the seeded data
- [ ] An unauthenticated request for a course the user cannot see returns 404,
      not 403 — existence is not disclosed

### P2-06 · Freeze the OpenAPI contract and generate the SDK

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 2 · **Depends on:** P2-05
- **Review gate:** none

**Context**
This is the task that makes the schedule arithmetic work. Once frozen, P3/P4
(backend) and P5 (frontend) proceed in parallel through weeks 3–4 (ADR-0001).

**Scope**

- Complete `contracts/openapi.yaml` for everything built so far, including the
  problem-details error shape.
- Generate `packages/sdk` from it; generate widget types from the same source.
- Contract tests asserting live responses match the contract.

**Acceptance criteria**

- [ ] The SDK is generated, never hand-edited — a check fails CI if it drifts
- [ ] A response that violates the contract fails CI
- [ ] Every error response conforms to the problem-details shape, with no stack
      trace or internal identifier
- [ ] The contract is sufficient to build a screen against without reading API
      source code
