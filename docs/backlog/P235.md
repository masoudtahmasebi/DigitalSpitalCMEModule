# P235 — server-side idempotency, because a disabled button is not a guarantee

**Status: specified, not implemented.** This is a work order raised by the
review of PR #77 (P230), which fixed a client-side defect and must not be read
as having fixed the server-side one underneath it.

> **Client-side single-flight is not idempotency.** … two tabs, two admins, lost
> responses, direct API calls.

That is correct and it is the whole ticket. P230 disabled three controls while
their own request was open. It did nothing to the API, and every one of the four
cases above goes straight past a disabled button:

| Case                                                                 | What the button does about it                          |
| -------------------------------------------------------------------- | ------------------------------------------------------ |
| Two browser tabs, same operator                                      | nothing — each tab has its own React state             |
| Two operators on the same record                                     | nothing — they are different browsers                  |
| A **lost response** — the request succeeded, the reply never arrived | nothing — the operator sees an error and presses again |
| A direct API call (curl, a script, a future integration)             | nothing — there is no button                           |

P230's own PR description said _"no server behaviour changes"_, which was true
and was the wrong thing to be reassured by. The accurate statement, and the one
that belongs on that PR, is **no server-side implementation or API-contract
changes; the PR changes client-side operation guarding and feedback behaviour
on auth- and GDPR-sensitive screens.**

---

## P235-01 — an idempotency key on every write that changes a person's record

**Scope: the three routes P230 guarded, plus any write reaching the same
tables.** `adminEraseSubject`, `Learners.correct`'s correction route, and
`adminSetSecondFactorPolicy`.

The shape, which is the standard one and is named here so it is not reinvented:

- The client mints a key per **user intent** — not per request — and sends it in
  an `Idempotency-Key` header. A retry of the same intent carries the same key;
  pressing the button again after deciding to really do it is a new intent and a
  new key.
- The API stores `(customer_id, route, key) → (status, response body, created_at)`
  in a table under RLS like everything else, written **in the same transaction
  as the effect**. Two rows cannot disagree about whether the work happened.
- A repeat of a key whose row exists replays the stored response and performs no
  work. A repeat **while the first is still open** answers 409 with a
  problem-details `detail` saying the request is in progress, rather than
  queueing behind it.
- Retention: long enough to cover a client retry and an operator's second
  attempt, short enough not to become a second copy of the audit log. 24 h is
  the usual answer and is a decision for this ticket, not an assumption.

`contracts/openapi.yaml` is written first (CLAUDE.md §2, contract-first), and
the SDK and contract tests derive from it.

## P235-02 — erasure must be safe to repeat, and must say which thing happened

`moderation.service.ts` begins `eraseSubject` with `findEnrolment(enrolmentId)`
and throws `notFound` when it is gone. The erasure removes the enrolment. So:

**A repeated erasure of a subject already erased is indistinguishable from an
erasure of a subject that never existed**, and both answer 404.

That is wrong in two directions at once, and the second is a compliance
problem rather than a usability one:

1. **The operator is told an Art. 17 erasure failed when it succeeded.** They
   are looking at an empty row and an error message. The reasonable next action
   is to try again, which 404s again, and the reasonable conclusion is that the
   platform did not erase the record — which is precisely the claim a data
   subject's request turns into a supervisory-authority complaint.
2. **§9.6 in its usual form.** On a tenant-scoped table an RLS-hidden row and an
   absent row are already the same 404. Adding "already erased" to that set
   means one status code carries three different facts.

**What this ticket must produce:**

- `DELETE`-shaped semantics: erasing an already-erased subject answers
  **success**, not 404, and says so — the erasure record survives the enrolment
  and is what the second call reads. An erasure that leaves no trace cannot
  answer this question and cannot evidence compliance either.
- A distinct answer for "no such enrolment in this tenant", which stays
  deliberately indistinguishable from "another tenant's enrolment" (§9.5: an
  answer must not be an oracle).
- The audit record distinguishing the first erasure from a replayed one, so a
  count of erasures is a count of erasures.

### The lost-response scenario, stated as a compliance risk

The sequence, which needs no unusual conditions:

1. An operator confirms an Art. 17 erasure for a named physician.
2. The API erases the record and commits.
3. The response is lost — a dropped connection, a proxy timeout, a closed
   laptop. P230's `useSaver` reports a failure, correctly, because it does not
   know.
4. The operator sees a failure beside a row that has disappeared, and has no way
   to tell "it worked and the reply was lost" from "it did not work".

Today there is **no read that answers this**. The enrolment is gone, so the
screen cannot show it; the erasure is not surfaced anywhere the operator can
look. The risk is not that data survives — the erasure committed — it is that
**the platform cannot demonstrate to the operator, or later to a regulator, that
it did**, and the operator's honest report of what they saw is "the deletion
failed".

Recorded here as a compliance risk carried by the current design, and it is the
strongest single argument for P235-01: with an idempotency key, step 4 becomes a
retry that replays the stored success.

## P235-03 — concurrency control on corrections and policy updates

Two time-of-check/time-of-use questions P230 explicitly did not touch, both
real without any double-click:

- **Corrections.** Two concurrent corrections both read the enrolment's stage
  before either writes, so both pass the "already submitted to EIV" conflict
  check and both write a `learner.name_corrected` row into an **append-only**
  audit log. One correction reads as two, and the later one may be based on a
  record the earlier one changed.
- **The second-factor policy.** Two writes for the same scope, and the one that
  sticks is decided by **network ordering** rather than by what any operator
  chose. On the rule governing whether an operator must carry a second factor,
  the losing write is not cosmetic. P230 made a second write unreachable _from
  one browser tab_; it did nothing about two.

The mechanism is the ordinary one — a version or `updated_at` carried out to the
client and back, refused with 409 if it has moved — and it is the same shape as
the `if_version` discipline the rest of this repository already uses. The
decision this ticket owes is **where the version lives** for a policy row that
today has no natural entity to hang it on.

## P235-04 — the same question asked of every other write

§9.11 and §11.11: the three routes above are the ones the review reached by
reading one PR. The ticket is not done until the same question — _what happens
if this arrives twice?_ — has been asked of every mutation route in
`contracts/openapi.yaml`, with the answer written down per route, including the
ones where the answer is "nothing, it is naturally idempotent".

A route whose answer is unknown is a route that has not been checked, and that
distinction is the point of writing it down.

## Why this is not a rider on P230

P230 is a console change: three controls, a check and its tests. Everything here
is API, schema, contract and migration, on three surfaces two of which are under
the §2 human-review gate. Bundling them would make a reviewable PR unreviewable,
and would let a client-side guard be mistaken for the fix — which is the exact
misreading this ticket exists to prevent.

## Acceptance criteria

- [ ] `contracts/openapi.yaml` describes the idempotency header, the replay
      response and the in-progress 409, written **before** implementation
- [ ] An idempotency table under RLS, written in the same transaction as the
      effect, with a stated retention
- [ ] Repeated erasure answers success and is distinguishable in the audit
      record from a first erasure
- [ ] "No such enrolment" stays indistinguishable from "another tenant's
      enrolment" (§9.5)
- [ ] A read that lets an operator answer "did this erasure happen?" after a
      lost response
- [ ] Version-based concurrency control on corrections and on policy writes,
      with 409 on a stale version
- [ ] Every mutation route in the contract carries a written answer to "what
      happens if this arrives twice?"
- [ ] Integration tests firing `Promise.all` of N concurrent callers per route —
      §11.10: a sequential test proves nothing here — shown red on the current
      code and green on the new
- [ ] `needs-human-review`: auth, GDPR erasure
