# P153 — Watched seconds discarded: two constants in media time that had to be in real time

Reported as DEP-25, with screenshots: a physician watches a 41:30 video to the
end and the screen says **29 % angesehen**, **„0 % der Fortbildung absolviert"**,
and names passages as missing that they are certain they saw.

Two mechanisms, both reproduced by execution before anything was changed. They
are the same defect in two places: **a bound written in media seconds, applied to
something that happens in real time.**

Base commit: `7812e84`, confirmed with `git rev-parse HEAD`.

---

## P153-01 — the server rejected every playback rate the player offers

### Reproduced first

`validateSegments` budgets a report at `elapsedWallClockSec + tolerance`, with
the tolerance a flat **2 s** (`DEFAULT_WALL_CLOCK_TOLERANCE_SEC`). The widget
flushes every **15 s** (`LessonScreen.tsx` `FLUSH_INTERVAL_MS`). So:

```
$ node -e '… for each PLAYBACK_RATES, validateSegments([{0, 15*rate}], {elapsedWallClockSec: 15})'
0.75  claims 11.25 s -> ACCEPTED
1     claims    15 s -> ACCEPTED
1.25  claims 18.75 s -> REJECTED faster_than_wallclock
1.5   claims  22.5 s -> REJECTED faster_than_wallclock
1.75  claims 26.25 s -> REJECTED faster_than_wallclock
2     claims    30 s -> REJECTED faster_than_wallclock
```

**Every rate above 1× that the speed menu offers was refused**, and refused
_whole_ — `validateSegments` rejects a segment, not the excess — so fifteen
seconds of genuinely watched video became nothing, once per heartbeat, for as
long as the learner kept the speed up.

### The comment that stopped anybody looking

`playback.ts`'s own header said:

> Capped at 2×. Not a UI preference: the API rejects a report claiming more
> media seconds than wall-clock seconds allow (`faster_than_wallclock`) …
> **The tolerance leaves room for 2× and not for 4×.**

The tolerance is two **seconds**, flat. It left room for 1×. The sentence read
as settled, so the menu grew entries the server had never credited. CLAUDE.md
§11 rule 9 — a comment is a claim, and this one had never been run.

There was even a green test pinning the wrong half: `playback.test.ts` asserted
`Math.max(...PLAYBACK_RATES) <= 2` against a literal `2`, which is true and
proves nothing about what the server credits. §9.1's second form.

### The fix

`MAX_PLAYBACK_RATE = 2` in `watch.ts`, and the budget becomes
`elapsedWallClockSec * MAX_PLAYBACK_RATE + tolerance`.

A multiplier rather than a bigger constant, because the overclaim grows with the
reporting interval: any flat number that fits a 15-second heartbeat at 2× is a
number a slow reporter can hide a skip behind. The honest bound is the product's
own cap — a learner may watch at up to 2×, so up to two media seconds per real
second may be credited, and not one more.

**The anti-skip property is unchanged in kind.** A client posting
`[0, duration]` in one call is still refused: a whole video is far more than
twice the elapsed time. The bound is weakened by exactly the factor the speed
menu already hands every learner. The test that pins this — "still refuses a
whole video claimed at more than the fastest rate on offer" — is in the same
describe block.

`PLAYBACK_RATES` now lives downstream of `MAX_PLAYBACK_RATE` and
`playback.test.ts` asserts the menu offers no rate the budget will not credit,
so adding a 3× entry fails a test rather than quietly costing somebody a CME
point (§9.11 — one rule, not two opinions).

## P153-02 — the client discarded the span across a throttled sample

### Reproduced first

`WatchTracker.observe` treats a position jump greater than `SEEK_TOLERANCE_SEC`
(2 s) as a seek: it banks the open interval and starts fresh at the new
position, so the media between is never recorded. Executed:

```
observe(100) observe(101) observe(104) observe(105)
  -> [{100,101}, {104,105}]          101–104 is gone
```

`timeupdate` is throttled by every browser — a background tab, a GC pause, a
slow frame. At 1× that needs a two-second stall; **at 2× the media advances
twice as fast, so one second of stall is enough.** The faster a physician
watches, the more they lose, which is the opposite of what a speed control
promises. This is the mechanism that produces the small, scattered gaps in the
report's screenshot — `1:26–1:31, 1:31–1:36, 1:37–1:42`.

### The fix

The tolerance is scaled by the rate that produced the samples, so it keeps the
wall-clock meaning it was written to have. `rate` travels with the tick:
`onTick(positionSec, playing, rate)` → `observe(positionSec, playing, rate)`,
from `video.playbackRate`.

Clamped at `MAX_PLAYBACK_RATE`, from the same constant the server credits
against, so a tampered `playbackRate` cannot widen it. A real forward seek is a
jump of many seconds and stays a seek at every rate — asserted.

## Why the screenshot shows 0 % and 29 % at once

They are two different figures and both are consistent with the above.
„29 % angesehen" is this video's credited union. „0 % der Fortbildung
absolviert" counts _contents completed_, and a content completes at the
enrolment's `required_watch_percent` — which defaults to **100**
(`schema.ts:220`) and is 100 on the MEDICE course. Nothing had completed, so the
course figure was 0.

The gap list names **at most three** spans by design (`LessonScreen.tsx`), so
three five-second gaps on screen is not the whole of what was missing.

This is **not** P76-03's cause. That one is a configured length longer than the
file, and it has its own message; here the header reads `41:00 / 41:30` and the
player `noch 0:30`, so the two agree.

One rule, one caller. Every flat constant in the watch path:

| Constant                             | Where              | Verdict                                  |
| ------------------------------------ | ------------------ | ---------------------------------------- |
| `DEFAULT_WALL_CLOCK_TOLERANCE_SEC` 2 | `watch.ts`         | now jitter only, correct                 |
| `SEEK_TOLERANCE_SEC` 2               | `watch-tracker.ts` | **fixed (P153-02)**                      |
| `TAIL_GRACE_SEC` 3                   | `watch.ts`         | measured against the file, not real time |
| `BOUNDARY_TOLERANCE_SEC` 0.5         | `watch.ts`         | interval arithmetic, rate-free           |
| `MIN_SEGMENT_SEC` 0.25               | `watch-tracker.ts` | noise floor, rate-free                   |

The two that had the defect are the two that compare a media quantity against
something happening in real time. The other three do not.

**Required.** Both changes are on the path that decides whether a physician has
watched enough of an accredited Fortbildung to be credited a CME point —
`assessment`/gating in CLAUDE.md §2's sense.

## What this does not fix

- **Existing enrolments keep the gaps already stored.** The union is what was
  credited at the time; nothing back-fills it. A learner who lost seconds must
  re-watch those passages, which the gap list already names. Whether to
  re-credit affected enrolments is a compliance decision, not mine (§7).
- **The post-deploy smoke's `98 % angesehen`** (`zwei-module.spec.ts`, run
  33615653131, on production) is not proven to be either mechanism: that suite
  does not change playback rate, so P153-01 cannot be it, and whether it is
  P153-02 under CI throttling is unverified. Stated rather than assumed.
