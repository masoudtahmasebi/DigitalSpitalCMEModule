# P139 — The console did not send the CSRF token on an authenticated POST

**Status:** three fixes, three tests, all watched red. **Touches auth — needs
human review before merge (CLAUDE.md §2).**

---

## What was reported

> _"i also set the email and it is giving 401"_

It was a **403**, and the distinction is the whole diagnosis. The response body
in the network pane says so:

```json
{
  "type": "…/errors/forbidden",
  "status": 403,
  "title": "Forbidden",
  "instance": "/admin/auth/platform-smtp/test"
}
```

`AppError.forbidden("missing or invalid CSRF token")`. The API was right. The
console was not asking properly.

## P139-01 — `post()` sent no CSRF token

`apps/admin/src/staff-auth.ts` has a shared `post()` helper. It sent
`content-type` and `accept` and **no `x-ds-csrf`** — which every mutating staff
request requires (P22-04).

It cost nothing visible for a long time, and the reason is worth writing down:
**every other caller of that helper is a `@Public()` route** — sign-in, TOTP
enrolment, TOTP verification, credential redemption, password reset — and the
CSRF check only applies to a request carrying a staff session. So the omission
was unreachable until the first _authenticated_ POST went through it.

"Send test email" was that first POST.

`PUT /admin/auth/platform-smtp` builds its own `fetch` and **does** send the
token, which is why "Saved." worked on the same screen, in the same session, two
buttons away from the one that did not.

## P139-02 — Sign-out read a variable the page loses on reload

Found while fixing the above, and it is the more serious of the two.

```ts
...(csrfToken === undefined ? {} : { [CSRF_HEADER]: csrfToken })
```

`csrfToken` is a module variable set when _this module_ signs somebody in. It is
gone the moment the page reloads. The cookie the API sets beside the session is
not — that is what `currentCsrfToken()` falls back to, and sign-out did not use
it.

So an operator who reloaded the console and then signed out sent no header, the
API refused with 403, the `.catch(() => undefined)` swallowed it, and the next
lines cleared the local state regardless. The result is the worst available
shape:

**the console says you are signed out and the server session is still live**,
with its cookie still in the browser. Pressing Back is enough to be signed in
again.

That is Section 6.5 of the QA audit — _"Sign out. Press the browser back button.
Confirm: no signed-in content is visible"_ — reached from a different direction.

## P139-03 — A refusal reported as a network problem

`sendPlatformTestMail` mapped every non-2xx to `unreachable`, which the screen
renders as:

> _"The request could not be made. Please check your connection and whether you
> are still signed in."_

The API had answered `403` — a complete, deliberate answer — and the console
turned it into a suggestion to check the wi-fi. §9.4: the sentence is the only
thing the person acts on, so it has to name what happened. A 4xx is `refused`
now, with copy that says the request was declined and who is allowed to perform
it. A genuine transport failure still says `unreachable`.

## Why nothing caught it

Every one of these functions is exercised. Sign-in has browser coverage, the
platform sender has `PlatformSender.test.tsx`, sign-out is in the journey. **All
of them stub `fetch` and assert on what comes back; not one asserted what goes
out.** A missing header is invisible to a stub that answers 200 regardless.

CLAUDE.md §9.7, exactly: the tests covered the functions and proved nothing about
the requests.

`staff-auth.test.ts` asserts the outgoing headers now. Watched red against the
original code — three failures, and the fourth case (a real transport failure
still reporting `unreachable`) stayed green, which is what stops the fix being
"call everything a refusal":

```
× carries the CSRF token, without which the API answers 403
    expected undefined to be 'token-from-the-cookie'
× reports a refusal as a refusal, not as a network problem
    expected 'unreachable' to be 'refused'
× sends the token from the cookie, so a reload does not break sign-out
    expected undefined to be 'token-from-the-cookie'
```

## What this says about the audit

Section 1 swept the API's guards and found them sound. It could not have found
this: the API refused correctly every time. The gap is one layer out — **the
console failing to ask correctly** — and the instrument for that is the browser
journey, which does not press "Send test email".
