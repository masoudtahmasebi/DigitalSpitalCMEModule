# P39 · Passwort vergessen — and what was found on the way there

> forget password is not there at all

---

## P39-01 · A credential token that never expired, never spent and could not be revoked — **done**

- **Estimate:** 4 h · **Review gate: human — auth**

### How it was found

Looking for where a "Passwort vergessen" flow would attach. The schema already
anticipated one: `admin_credential_tokens.kind IN ('invite', 'reset')`, with
`issued_by` nullable and commented _"Null for a self-service reset, which nobody
issued"_. `@ds/domain` already had `INVITE_VALID_DAYS = 7`,
`RESET_VALID_MINUTES = 60`, `inviteStatus` and `resetStatus`, all exported and
unit-tested against their boundaries.

`grep` for either function in `apps/api` returns nothing.

### What redemption actually did

```ts
const row = await this.deps.repository.findCredentialToken(hashToken(input.token));
if (row === undefined) return false;
await this.deps.repository.setPassword(row.adminUserId, input.passwordHash);
```

It read `created_at`, `accepted_at` and `revoked_at` out of the database and
used none of them. Three consequences, each an account takeover on the console:

| Property                                | Written where                                       | Enforced    |
| --------------------------------------- | --------------------------------------------------- | ----------- |
| An invitation expires after 7 days      | `INVITE_VALID_DAYS`, unit-tested                    | **nowhere** |
| A reset link expires after 60 minutes   | `RESET_VALID_MINUTES`, unit-tested                  | **nowhere** |
| A token is single-use                   | `acceptCredentialToken … WHERE accepted_at IS NULL` | **nowhere** |
| Issuing a new token revokes the old one | `issueCredentialToken`'s `UPDATE … SET revoked_at`  | **nowhere** |

The single-use one is the sharpest. `acceptCredentialToken` only updates a row
whose `accepted_at` is null, so a second redemption changed nothing — but
`setPassword` had already run above it. The same link could be replayed
indefinitely, each time choosing a new password for an account that by then
belonged to somebody. An invitation email forwarded, quoted in a ticket, or left
in a mailbox was a permanent key.

### The fix

`redeemCredentialToken` consults the rule, keyed off `kind` so the two
lifetimes stay apart, and refuses anything that is not `valid`. Every refusal
answers identically — "this link is no longer valid" — so a spent link cannot be
told from one that never existed, and the verdict goes to `audit_log` instead,
where a _revoked_ link being presented is worth somebody's attention.

### Covered

Six integration tests against the HTTP surface, because what is being asserted
is what somebody holding a link can do with it: redeem once, replay, replay
without changing the stored hash, revoked, past the invitation window, and a
`reset` token at two hours old — fine for an invitation, long dead for a reset.

Verified by removing the check: six red. Put back: 87 green.

### Not changed

The 422 and its wording. `AppError.badRequest` produces a `validation` problem
and the controller's message is deliberately the same for every cause.
