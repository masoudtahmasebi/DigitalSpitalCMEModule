## P222-01 — the meta strip has one divider, and it is between the duration and the modules (DEP-27)

> - The time icon and module icon size needs to be a bit bigger
> - Remove the divider between punkte button and timer, Once the divider is
>   removed, reduce the gap between the two.
> - There should be only one divider which is before the module info, with
>   border pixel of 2px width.

Measured before being believed — `docs/design/screens/page-02.png`, ×1920/1400,
scanning every column of the 86 px bar:

| element                | design x  |
| ---------------------- | --------- |
| CME pill               | 280 … 459 |
| clock glyph            | 487 … 514 |
| duration text          | 528 … 705 |
| **the only grey rule** | **731**   |
| modules glyph          | 757 … 784 |
| modules text           | 800 … 872 |

Exactly one grey vertical run in the whole bar, and it falls between the
duration text and the modules glyph. The report and the drawing agree on all
three points, and the build was wrong in both directions at once: it drew a rule
to the left of the duration that the drawing does not have, and gave the one it
does have none of the weight it carries.

### What changed

|                | before                        | after                           | drawing              |
| -------------- | ----------------------------- | ------------------------------- | -------------------- |
| glyphs         | `h-5 w-5` (20 px)             | `h-7 w-7` (28 px)               | 28–29 wide, 30 tall  |
| dividers       | `border-l` on **both** groups | one element, before the modules | one, at design x 731 |
| divider height | the 30 px line it hung off    | 55 px                           | 55                   |
| divider colour | `gray-200` `#e5e7eb`          | `#dddddd`                       | `#dddddd`            |
| bar gap        | `gap-x-6` (24)                | `gap-x-[1.625rem]` (26)         | 27 / 26 / 25         |
| glyph → label  | `gap-2` (8)                   | `gap-3.5` (14)                  | 14 / 16              |

The rule is its **own element** rather than a border on the modules group. It is
55 design px tall on an 86 px bar — a third taller than the 30 px line of icon
and text it used to hang off, so a border could not be that height without
padding the content to match it. And a border belongs to whatever it is drawn
on, which is how a rule that should appear once came to be written twice.

It is drawn only when there is something on **both** sides of it, which is the
condition `max-sm:border-l-0` used to be patching over one element at a time.

### The one deviation, recorded rather than absorbed

**2 px is the client's figure, not the drawing's.** Measured, the export's rule
is a single fully-saturated column at 1400 px — the neighbouring columns are
`(255,255,255)` exactly — so it is a hairline, somewhere between 1 and 1.4 px at
1920 and not distinguishable from 1 px at that resolution. Amruth asked for 2 px
explicitly. Visual weight on a rule is the designer's call and not a compliance
rule, so it is implemented as asked and the measurement is stated here and on
the ticket (CLAUDE.md §3).

### Watched red

Four new cases in `primitives.test.tsx`. Three of them fail on the previous
component:

```
× draws exactly one divider, and it is not between the points and the duration
    the bar should carry exactly one divider: expected +0 to be 1
× hangs no border on the duration or the modules themselves
    expected 'flex items-center gap-2 border-l bord…' not to contain 'border-l'
× gives the two glyphs the drawing's size rather than the default 20 px
    expected 'h-5 w-5 text-cta-500' to contain 'h-7 w-7'
```

The fourth — that the divider disappears when one side of it is empty — passes
on the old code, because the old code had no such element to disappear. It
guards the new one rather than reproducing an old defect, and that is stated
here rather than counted as evidence it never was.

## P222-02 — the gap beneath the tabs, measured in a browser (DEP-28)

> There should be gap beneath the tabs

Measured on the same render, reading the panel's top edge at design x 1234 where
it is clear of every tab: the teal tabs end at design y **682** and the panel
begins at **690**. **Seven design px of white.**

It was already there. **P209-01** built it, four days after the comment asked
for it, while fixing the third report about this row — and built it the right
way round: the selected tab reaches _further down_ into the panel rather than
the others being pushed up, because pushing them up moved their labels with
them, which is the 7.00 px misalignment that report was about. Nobody connected
the two, so DEP-28 sat open with its remaining item silently done.

**And it was two pixels short.** Measured in Chromium against this project's own
compiled CSS, `sm:pb-4` produced a **5 px** gap. `sm:pb-[1.125rem]` — 18 px
against the row's own `py-2.5`, less the 1 px the `-mb-px` overlap takes back —
produces **7**, which is the drawing's figure. Two pixels is exactly the kind of
nearly-right that this row has now generated three client reports about.

### The check

In `journey.spec.ts`, beside the assertion that the tab labels sit on one line,
because **the two are the same measurement from opposite ends** and fixing
either one silently spends the other. It is a distance between two boxes, which
jsdom does not lay out: a component test could only assert that `sm:pb-4` is in
a class string, which is a test about Tailwind and would stay green if the panel
moved (§9.7).

It is anchored on the tablist **element**, not on `document`. The widget's
shadow root is open in this browser only so Playwright's own locators can pierce
it; a bare `document.querySelectorAll` inside `evaluate` does not pierce an open
shadow root and would have returned nothing — a null this assertion would have
reported as "no tab to measure" on a page full of tabs. That is the §9.1 trap
one layer down, and it was found by writing the check the wrong way first.

Sabotaged by removing the padding:

```
Error: an unselected tab does not stand off the panel — the gap beneath it is
       0.0 px, and the drawing has 7. Gaps: 0.0
```

and with the padding it reports `MEASURED tab gaps: [7]`.

## The reconciliation itself, which is the reusable part

Neither ticket was stale. Both were **half-answered**, and the half that was
missing lived in a comment rather than in the description — which is where the
repository's own record could not see it. `docs/backlog/P159.md` was written
against the descriptions and was accurate about them.

**So:** when a ticket's status disagrees with the repository, read the ticket's
**comments** before concluding the board is out of date. A description is what
was asked for first; a comment is what was asked for after seeing it, and on a
design ticket the second is usually the one that matters.
