# P226 — Back-to-catalogue navigation can restore the course URL fragment after unmount

**A learner-widget bug. It is deliberately not fixed in P223–P225**, which are
the admin console redesign and must stay separable from anything that reaches a
physician's screen.

`OPEN` — reproduction harness not yet written, so the cause below is **reasoned
from source and not observed**. That distinction is the whole point of this
ticket and is carried into every claim in it.

---

## How it surfaced

CI on PR #73 failed one widget test:

```
apps/widget/src/App.route.test.tsx:678
  expect(window.location.hash).toBe("")
  Received: #ds/kurs/adhs-akademie-adult/referenten
```

That is `returning to the catalogue › clears the course fragment, so a reload
lands on the list` — the regression test for **DEP-33**.

**It is not PR #73's doing**, and that is checkable:

```
git diff --stat origin/main...HEAD -- apps/widget packages   →   (empty)
```

`apps/widget` and `packages` are byte-identical to `main` on that branch. 442 of
443 widget tests passed, and re-running the same job on the same commit passed.

**The re-run is not the resolution.** A test that is red then green on an
unchanged tree is an intermittent failure, and an intermittent failure on the
regression test for a routing defect is worth more than a green tick — it is the
product telling us the property is not actually guaranteed.

## What could not be reproduced

The first hypothesis was a `waitFor` timeout under CI load, since that job runs
30 turbo tasks in parallel. **It did not reproduce**: ten local runs of the file,
six unloaded and four under 3× CPU oversubscription (12 spinners on 4 cores),
all 25/25 green. So load is not being claimed as the cause; it was tested and
discarded.

## The mechanism, read from source and **not yet observed**

`apps/widget/src/App.tsx` — the back-to-catalogue handler:

```ts
clearCourseFragment(); // synchronous: clears the hash now
setSelected(undefined); // batched: unmounts the course on a later commit
```

The only writer of that fragment is an effect **inside the course component**
(`App.tsx`, deps `[screen, tab, addressCourseSlug, course.data]`), which writes
whenever the current hash is empty or one this router owns:

```ts
const current = window.location.hash;
const ours = current === "" || current === "#" || decode(current) !== undefined;
if (!ours) return;
const fragment = `#${encode(routeForScreen(screen, tab), addressCourseSlug)}`;
if (window.location.hash === fragment) return;
window.history.replaceState(null, "", fragment);
```

An **empty** hash passes the `ours` test. So if any pending update flushes
between the clear and the unmount — a request resolving, for instance — that
effect can run once more, see an empty hash, judge it "ours", and write the
course fragment back. Nothing clears it again, because the component then
unmounts and `clearCourseFragment` is only ever called from the click handler.

That would be **DEP-33 reappearing under a race**, which is why the test that
caught it is DEP-33's own.

## Why this matters to a learner

1. They click **Zurück zur Übersicht**.
2. The fragment is cleared.
3. A pending update causes the course component to write it again.
4. The catalogue is on screen while the URL still names the course.
5. A reload reopens the course they deliberately left.

That is §9.8's third symptom — the screen changing without the URL changing —
and it only shows up on F5, which is why it was reported three times before
DEP-33 pinned it.

## The fix this points at

**Make the property idempotent rather than ordered.** Today the rule is "clear
the fragment at the moment of the click", which depends on nothing else running
between the clear and the unmount. The rule it should be is:

> While the catalogue is on screen, the address must not name a course.

Expressed as an effect that runs whenever `selected === undefined`, no ordering
between the clear and the unmount can defeat it, and the click handler stops
being the single point where it can be missed. `clearCourseFragment` already
refuses to touch a fragment this router does not own, so a host page's
`#kontakt` stays safe either way.

**Not implemented here.** A fix that cannot be watched go red first is a guess
that compiled (§11.6), and the harness comes first.

## Acceptance criteria

- [ ] Clicking **Zurück zur Übersicht** leaves the learner on the catalogue route.
- [ ] The course fragment remains empty after **all pending requests settle** —
      not merely at the moment of the click.
- [ ] Reloading after returning to the catalogue does not reopen the previous
      course.
- [ ] The test **forces** a delayed response or pending state that reproduces
      the race, and is watched red on the current code before the fix.
- [ ] Direct deep links into a course still work.
- [ ] Browser back/forward behaviour is unchanged.
- [ ] A foreign fragment (`#kontakt`) is still never touched.
- [ ] The fix is deployed and verified **separately** from the admin redesign.

## Definition of done

The harness reproduces the failure deterministically on the current code. Not
"CI went green on a re-run" — this ticket exists because that already happened
once.
