# P226 — Back-to-catalogue navigation can restore the course URL fragment after unmount

**A learner-widget bug. It is deliberately not fixed in P223–P225**, which are
the admin console redesign and must stay separable from anything that reaches a
physician's screen.

`REPRODUCED AND FIXED` (P226-01, 12.09). The cause below was reasoned from
source; it has since been **observed**, and it was right. What follows is the
original ticket, then the evidence, then the fix.

> The original status line read: _"OPEN — reproduction harness not yet written,
> so the cause below is reasoned from source and not observed."_ That
> distinction was the point of the ticket and it is kept here rather than
> edited away, because the whole value of the record is that the reasoning was
> committed to **before** the evidence arrived.

## How it surfaced

CI on PR #73 failed one widget test:

```
apps/widget/src/App.route.test.tsx:678
  expect(window.location.hash).toBe("")
  Received: #ds/kurs/adhs-akademie-adult/referenten
```

That is `returning to the catalogue › clears the course fragment, so a reload
lands on the list` — the regression test for **DEP-33**.

**It is not PR #73's doing**, and that is checkable:

```
git diff --stat origin/main...HEAD -- apps/widget packages   →   (empty)
```

`apps/widget` and `packages` are byte-identical to `main` on that branch. 442 of
443 widget tests passed, and re-running the same job on the same commit passed.

**The re-run is not the resolution.** A test that is red then green on an
unchanged tree is an intermittent failure, and an intermittent failure on the
regression test for a routing defect is worth more than a green tick — it is the
product telling us the property is not actually guaranteed.

## What could not be reproduced

The first hypothesis was a `waitFor` timeout under CI load, since that job runs
30 turbo tasks in parallel. **It did not reproduce**: ten local runs of the file,
six unloaded and four under 3× CPU oversubscription (12 spinners on 4 cores),
all 25/25 green. So load is not being claimed as the cause; it was tested and
discarded.

## The mechanism, read from source and **not yet observed**

`apps/widget/src/App.tsx` — the back-to-catalogue handler:

```ts
clearCourseFragment(); // synchronous: clears the hash now
setSelected(undefined); // batched: unmounts the course on a later commit
```

The only writer of that fragment is an effect **inside the course component**
(`App.tsx`, deps `[screen, tab, addressCourseSlug, course.data]`), which writes
whenever the current hash is empty or one this router owns:

```ts
const current = window.location.hash;
const ours = current === "" || current === "#" || decode(current) !== undefined;
if (!ours) return;
const fragment = `#${encode(routeForScreen(screen, tab), addressCourseSlug)}`;
if (window.location.hash === fragment) return;
window.history.replaceState(null, "", fragment);
```

An **empty** hash passes the `ours` test. So if any pending update flushes
between the clear and the unmount — a request resolving, for instance — that
effect can run once more, see an empty hash, judge it "ours", and write the
course fragment back. Nothing clears it again, because the component then
unmounts and `clearCourseFragment` is only ever called from the click handler.

That would be **DEP-33 reappearing under a race**, which is why the test that
caught it is DEP-33's own.

## Why this matters to a learner

1. They click **Zurück zur Übersicht**.
2. The fragment is cleared.
3. A pending update causes the course component to write it again.
4. The catalogue is on screen while the URL still names the course.
5. A reload reopens the course they deliberately left.

That is §9.8's third symptom — the screen changing without the URL changing —
and it only shows up on F5, which is why it was reported three times before
DEP-33 pinned it.

## The fix this points at

**Make the property idempotent rather than ordered.** Today the rule is "clear
the fragment at the moment of the click", which depends on nothing else running
between the clear and the unmount. The rule it should be is:

> While the catalogue is on screen, the address must not name a course.

Expressed as an effect that runs whenever `selected === undefined`, no ordering
between the clear and the unmount can defeat it, and the click handler stops
being the single point where it can be missed. `clearCourseFragment` already
refuses to touch a fragment this router does not own, so a host page's
`#kontakt` stays safe either way.

**Not implemented here.** A fix that cannot be watched go red first is a guess
that compiled (§11.6), and the harness comes first.

# P226-01 — reproduced, and the cause was the one written down

## What the definition of done asked for

> The harness reproduces the failure deterministically on the current code. Not
> "CI went green on a re-run" — that has already happened once.

Taken in two parts, because they turned out to be different questions.

## 1. It reproduces, by repetition

The scenario is the DEP-33 regression case in `App.route.test.tsx`, unchanged.
Run once it passes; run it many times in one process and it does not:

| Run                  | Result                   |
| -------------------- | ------------------------ |
| 120 repeats, unfixed | **1 failed**, 119 passed |
| 200 repeats, unfixed | **6 failed**, 194 passed |
| 200 repeats, fixed   | 200 passed               |

Combined that is **7 failures in 320**, about **2.2 %** — which is exactly why
this looked like a flake. A single run is a coin weighted roughly 49:1, and
CLAUDE.md §9.1's "two green runs is not proof" understates it: forty-nine green
runs would not be proof either.

The failure is the one CI reported, to the character:

```
AssertionError: expected '#ds/kurs/adhs-akademie-adult/referent…' to be ''
```

## 2. The cause, observed

`history.replaceState` was spied on for the whole scenario. On a failing
iteration:

```
  #ds/kurs/adhs-akademie-adult                 <- App.tsx:654, the address effect
  === clicking ===
  /                                            <- route.ts:242, clearCourseFragment
  #ds/kurs/adhs-akademie-adult/referenten      <- App.tsx:654, the address effect AGAIN
  === after click, hash = #ds/kurs/adhs-akademie-adult/referenten ===
```

**The hypothesis in this ticket was correct.** The address effect runs once more
after the clear, sees an empty hash, judges it one of ours — `current === "" ||
current === "#" || decode(current) !== undefined`, and empty passes — and
writes the course fragment back.

### The detail that explains the timing, which was not in the original ticket

Look at the first line. On a **failing** run the load had written only
`…/adhs-akademie-adult`; on a passing run it writes `…/adhs-akademie-adult`
**and** `…/referenten`. So on the failing runs the commit that moved `tab` to
`referenten` had not yet flushed its passive effects when the click landed.
React defers `useEffect` past the event handler; that deferred effect then ran
after `clearCourseFragment`, and restored the tab the learner had been on.

That is why it is rare and why load decides it: it needs a commit in flight at
the moment of the click.

## 3. Deterministically — what could and could not be done

**Could not:** force the race itself. It needs a commit whose passive effects
have not flushed when the click lands, and nothing in a test can schedule that.
Two `fireEvent`s in one tick was tried on purpose — click a tab, then click
back, in one synchronous block — and it does **not** reproduce, because
testing-library flushes effects between them. Reported here rather than left
out, per §11.10: if the real condition cannot be forced, say so instead of
substituting something easier and calling it the same thing.

**Could:** assert the invariant the fix installs, which is the property that
makes the race _impossible_ rather than _unlikely_ —

> on any commit where no course is selected, a course fragment is removed.

`takes the fragment off again if anything puts it back` writes the course
fragment back by hand, exactly as the late effect did, forces a commit, and
asserts it is gone. **Red every time on the unfixed code**, green on the fixed:

```
AssertionError: a course fragment survived a commit on which the catalogue was
the screen — so whatever writes one wins, and a reload reopens a course the
learner has left: expected '#ds/kurs/adhs-akademie-adult/referent…' to be ''
```

So the suite gets a deterministic gate, and the 2.2 % measurement is the
evidence for the race rather than the gate for it.

## 4. The fix

The proposal in this ticket, unchanged:

> Make the property idempotent rather than ordered.

`clearCourseFragment()` is gone from the click handler. In its place, in
`Routed`:

```tsx
useEffect(() => {
  if (selected !== undefined) return;
  clearCourseFragment();
});
```

No dependency array: every commit where the catalogue is the screen enforces
it. `clearCourseFragment` is already idempotent — an empty hash and a foreign
one are both left alone — so running it on every commit costs a string compare.

A host page's own `#kontakt` is still never touched. That rule lives in
`clearCourseFragment` and is unchanged, and the existing test for it still
passes.

## What is deliberately not changed

`Loaded`'s address effect still treats an empty hash as one of ours. That is
**correct and load-bearing**: on a catalogue embed the learner opens a course
from a page with no fragment, and the effect has to be able to write the first
one. Narrowing it would break opening a course to fix leaving one.

The invariant is the right place for the rule, because it states what must be
true rather than what must happen first.
