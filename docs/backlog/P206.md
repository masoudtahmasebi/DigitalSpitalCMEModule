# P206 — The evaluation was mandatory, and the reason given for it was not sourceable

**Raised by:** the client, twice — 04.09.2026 relaying their PM's challenge, and
07.09.2026 directly: _"then do the evaluation text … it is not mandatory."_

**Closes:** S35.

---

## The sentence

```
Der Anerkennungsbescheid verlangt eine Evaluation.
Ohne Fragen kann die Fortbildung nicht abgeschlossen werden.
```

Two claims, and both were wrong in different ways.

**The first** is a statement about a legal document. S35 traced it: the client
brief mentions an Evaluationsbogen once, as scope, never as a requirement; no
ADR; never in show-stoppers, so nobody was ever asked. The condition arrived in
the initial scaffold and the German sentence in `c065d97`, and the code comment
justifying the design cites nothing. Their PM asked for the evidence and said
they had never read anything like it. They were right.

**The second** was true — of our software, and only because of the defect beside
it. `evaluation` was an unconditional `CompletionCondition`, so a course whose
author had written no questions had a gate **nothing could ever open**: no
response row could exist, so the condition stood outstanding for ever.

## The change

`evaluation` is conditional now, exactly as `efn` already was:

```ts
const needsEvaluation = input.hasEvaluation ?? true;
if (needsEvaluation && !input.evaluationSubmitted) outstanding.push("evaluation");
```

`?? true` for the same reason `awardsCmePoints` has it: a caller that has not
been updated keeps the stricter behaviour. Waiting for an evaluation that exists
is a delay; skipping one that exists would certify somebody the operator wanted
to hear from.

`hasEvaluation` is read from the **course**, not the enrolment — §9.10b. An
operator who adds the first question should have it asked of everyone still in
progress, and one who removes the last should not leave people holding a gate
nothing can open.

The repository read is `LIMIT 1` inside `runInTenant`: the question is
existence, and on the bare pool RLS would match zero rows and report a course
that _has_ questions as having none — §9.6 aimed straight at a completion gate.

## Where else the claim was made

`docs/gdpr.md` asserted the same thing as a **lawful basis**: evaluation answers
under Art. 6(1)(c), "required for the Anerkennung". That is now corrected — the
answers are collected only where a customer has authored questions, so the basis
is their own interest in feedback, not a legal obligation nobody can produce.

A wrong sentence in a processing record is worse than a wrong sentence on a
screen: one misleads an author, the other misleads a data-protection review.

## The copy that replaces it

> Wenn Sie Fragen anlegen, füllen Teilnehmende den Evaluationsbogen vor der
> Teilnahmebescheinigung aus. Ohne Fragen entfällt dieser Schritt.

It says what the screen actually decides — whether learners are asked — which is
the thing the author on that tab controls. It claims nothing about the Bescheid.

## Watched red

| sabotage                              | result                                                       |
| ------------------------------------- | ------------------------------------------------------------ |
| `evaluation` unconditional again      | `completes without one` fails — the reported defect          |
| skip it whenever the caller is silent | three existing cases fail — the safe default is load-bearing |

The second matters as much as the first. `?? true` is what keeps every caller
that predates this — the admin re-scoring path among them — asking for an
evaluation rather than certifying by omission.

## What is still not known

**Whether the Anerkennungsbescheid requires one.** We hold no document either
way; S35 records that. What changed is that the platform no longer _asserts_ it,
in the console or in the processing record. If the Bescheid does turn out to
require it for a given course, that course's author adds questions and the
condition applies again — which is the behaviour a per-course setting should
have had from the start.

## P206-02 — the integration suite met the rule, and the rule met the suite

Eight cases in `learning-flow.integration.test.ts` went red on the first CI run
of this change, and both directions of that are findings.

### The fixture that could not have gone red

Every failing case asserted the evaluation gate — `outstanding` containing
`"evaluation"`, a 409 naming it, `complete` withheld for it — against **courses
with no evaluation questions**. Neither the accredited course nor the
points-free one had ever had an `INSERT INTO evaluations`. They passed because
the condition was unconditional: the suite was testing a gate on a course where
the thing being gated on does not exist.

That is CLAUDE.md §9.1 in a fixture. Those cases could not have distinguished a
working evaluation gate from a hard-coded one, which is exactly the defect this
ticket fixes, and they had covered it since P51.

So they were **migrated rather than weakened** — one `scale` question on each of
the two courses, and their assertions unchanged. They now test what their names
say. The other side of the conditional needed a course of its own, because "the
evaluation is outstanding" and "there is no evaluation" cannot both be asserted
against one fixture: `lf-plain-…`, no points and no questions, with three cases
covering the outstanding list, the rollup and the completion the evaluation used
to block.

Those three are the caller tests for `hasEvaluationQuestions` (§9.7). The rule
lives in `packages/domain` and is covered there; what a domain test cannot show
is that the API _asks the database_ the question.

**Watched red:** with `hasEvaluation: input.hasEvaluation` replaced by
`undefined` at `learning.service.ts:1054` — the service still reading the column,
still passing it around, just not handing it to the rule — all three fail and
every domain test stays green. That is the wiring, and it is now covered.

### The bounded resource four files had each worked around locally

Adding one legitimate `POST /completion` near the top of the file made a case
four hundred lines below it fail:

```
× refuses completion, for the retraction rather than the missing conditions
  AssertionError: expected 429 to be 409
```

`@RateLimit("completion")` is five per subject per sixty seconds. A whole
integration file runs in about twelve seconds against one seeded learner, so the
budget is a bounded resource shared by the entire file, spent in source order and
never replenished. `learning-flow` had spent exactly five of it.

The failure lands on whichever case happens to be sixth — a rate limit reported
as a defect in an unrelated feature. §9.8's ambient-state lesson at the level of
a service: state that outlives a case is a failure attributed to the wrong code.

§9.11 says fix the class, and the class was already visible in the repository.
`hierarchy` carries a comment explaining that it creates **one** account across
four cases "on purpose" because "a suite that spends the bucket makes later,
unrelated tests fail with 429". `participant-auth`, `participant-merge` and
`participants` each hand-roll a clear of the one bucket that bit them. Four files
had met this and each solved it locally, which is how the fifth was still able to.

`support/reset-each-file.ts` now clears `ratelimit:*` before every case, beside
the truncation it already does per file and under the same `requested()` gate —
so a developer whose `REDIS_URL` points at something shared is not affected by
running a test command. The three narrower clears are left in place: idempotent,
and each records why it was added.

**What it must not break:** two cases deliberately exhaust a bucket and assert
the 429. Both spend their requests _inside a single `it`_, so a `beforeEach`
cannot reach between them — checked by grep, not assumed, and named in the
setup file's header as the property to re-check before anyone writes a
throttling assertion split across two cases.

**Watched red:** with the key list stubbed to `[]`, `learning-flow` fails on the
same unrelated case with the same `expected 429 to be 409`.
