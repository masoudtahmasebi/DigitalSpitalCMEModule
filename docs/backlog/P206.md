# P206 — The evaluation was mandatory, and the reason given for it was not sourceable

**Raised by:** the client, twice — 04.09.2026 relaying their PM's challenge, and
07.09.2026 directly: _"then do the evaluation text … it is not mandatory."_

**Closes:** S35.

---

## The sentence

```
Der Anerkennungsbescheid verlangt eine Evaluation.
Ohne Fragen kann die Fortbildung nicht abgeschlossen werden.
```

Two claims, and both were wrong in different ways.

**The first** is a statement about a legal document. S35 traced it: the client
brief mentions an Evaluationsbogen once, as scope, never as a requirement; no
ADR; never in show-stoppers, so nobody was ever asked. The condition arrived in
the initial scaffold and the German sentence in `c065d97`, and the code comment
justifying the design cites nothing. Their PM asked for the evidence and said
they had never read anything like it. They were right.

**The second** was true — of our software, and only because of the defect beside
it. `evaluation` was an unconditional `CompletionCondition`, so a course whose
author had written no questions had a gate **nothing could ever open**: no
response row could exist, so the condition stood outstanding for ever.

## The change

`evaluation` is conditional now, exactly as `efn` already was:

```ts
const needsEvaluation = input.hasEvaluation ?? true;
if (needsEvaluation && !input.evaluationSubmitted) outstanding.push("evaluation");
```

`?? true` for the same reason `awardsCmePoints` has it: a caller that has not
been updated keeps the stricter behaviour. Waiting for an evaluation that exists
is a delay; skipping one that exists would certify somebody the operator wanted
to hear from.

`hasEvaluation` is read from the **course**, not the enrolment — §9.10b. An
operator who adds the first question should have it asked of everyone still in
progress, and one who removes the last should not leave people holding a gate
nothing can open.

The repository read is `LIMIT 1` inside `runInTenant`: the question is
existence, and on the bare pool RLS would match zero rows and report a course
that _has_ questions as having none — §9.6 aimed straight at a completion gate.

## Where else the claim was made

`docs/gdpr.md` asserted the same thing as a **lawful basis**: evaluation answers
under Art. 6(1)(c), "required for the Anerkennung". That is now corrected — the
answers are collected only where a customer has authored questions, so the basis
is their own interest in feedback, not a legal obligation nobody can produce.

A wrong sentence in a processing record is worse than a wrong sentence on a
screen: one misleads an author, the other misleads a data-protection review.

## The copy that replaces it

> Wenn Sie Fragen anlegen, füllen Teilnehmende den Evaluationsbogen vor der
> Teilnahmebescheinigung aus. Ohne Fragen entfällt dieser Schritt.

It says what the screen actually decides — whether learners are asked — which is
the thing the author on that tab controls. It claims nothing about the Bescheid.

## Watched red

| sabotage                              | result                                                       |
| ------------------------------------- | ------------------------------------------------------------ |
| `evaluation` unconditional again      | `completes without one` fails — the reported defect          |
| skip it whenever the caller is silent | three existing cases fail — the safe default is load-bearing |

The second matters as much as the first. `?? true` is what keeps every caller
that predates this — the admin re-scoring path among them — asking for an
evaluation rather than certifying by omission.

## What is still not known

**Whether the Anerkennungsbescheid requires one.** We hold no document either
way; S35 records that. What changed is that the platform no longer _asserts_ it,
in the console or in the processing record. If the Bescheid does turn out to
require it for a given course, that course's author adds questions and the
condition applies again — which is the behaviour a per-course setting should
have had from the start.
