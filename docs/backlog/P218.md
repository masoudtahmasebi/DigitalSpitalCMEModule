### Row 2 is a comment that was false

P190-01 changed the heading on the reasoning that _"every player and exam page
of the layout heads this column **Fortbildungsfortschritt**"_. Pages 06 and 12
both head it `Modul Übersicht`. The argument was sound and the fact under it was
never checked — §11.9, and the reason the client's ticket and our code had drifted
in **opposite** directions from the same drawing.

### Row 5 is the one that did not need doing

`Lernerfolgskontrolle` is an accreditation term: it appears on the Bescheid and
in the EIV-FOBI interface, and P88-03 records why that vocabulary is deliberately
not translated or renamed. The render agreeing with the code is what let this be
a no-op rather than a compliance decision taken inside a layout ticket.

### And one thing the removal exposed

`LessonScreen` held `watchedPercent` in state purely to print that line. With the
line gone it was written and never read. It is removed; `covered` and
`seekCeilingSec` stay, because both are the **gate's** state and both are read.
The number itself has not gone anywhere — `PlayerProgressCard` reads it from the
enrolment, which is where the drawing puts it.

## P218-02 — DEP-41, the Lernerfolgskontrolle page

### The panel split, and the measurement that stopped it being wrong

The ticket says the left panel is grey and the right is white. Sampled inside
the white card on the 1400 px renders:

| Page                                  | Left                   | Right              |
| ------------------------------------- | ---------------------- | ------------------ |
| 06, 07 — player                       | `rgb(255,255,255)`     | `rgb(255,255,255)` |
| 08, 09, 11, 12 — Lernerfolgskontrolle | **`rgb(250,250,250)`** | `rgb(255,255,255)` |
| 13 — Punktemeldung                    | **`rgb(250,250,250)`** | `rgb(255,255,255)` |

So the grey belongs to the **exam and the Punktemeldung**, not to the shell. A
shell that greyed both columns everywhere would have got the player wrong, on a
screen a physician spends half an hour on — and the ticket's title says
"Lernerfolgskontrolle page", which is exactly the distinction. `CourseShell`
takes a `surface` prop; `App` passes `"white"` for the player and `"muted"` for
everything after it. Divider `#e0e0e0`, `lg:` only, because below that the grid
is one column and a vertical rule separates nothing.

**Watched red in both directions**, which matters here more than usual: greying
the player fails _"leaves the player white"_, and greying nothing fails _"puts
the Lernerfolgskontrolle on the grey one"_. A single-direction test would have
passed on the version that greys everything.

The cases drive `App`, not `CourseShell` — the shell will render either value on
either screen, so the property is the wiring (§9.7).

### The badge

The ticket is right: the glyph inside the scalloped badge was a **checkmark**,
which reads as "verified" — the mark a form uses to say a field is valid. The
drawing has a five-pointed star. Replaced, generated rather than hand-drawn: ten
points alternating between radii 6.4 and 2.6 about (16, 15.6) from −90°.

Measured while there: the badge is 35 px in the 1400 render — **48 px** at the
1920 frame — and was `h-9 w-9` (36 px). Now `h-12 w-12`.

The heading was already right: `passedTitle` composes `"Abschlussprüfung
bestanden!"` and the drawing agrees.

## P218-03 — the white-label colours had no screen at all

The client could not find the colour settings because **they do not exist.**

`primaryColor` is declared on `Branding`, parsed by `parseBranding` against
`HEX_COLOR`, refused by `invalidBrandingFields` when malformed, and written to
`--ds-brand-600` and `--ds-brand-700` by `brandingCssVars`. All of that has been
true since P10-08. And:

```
$ grep -rn "primaryColor" apps/admin/src --include=*.tsx | grep -v .test.
(nothing)
```

A working engine with no steering wheel — §9.3 in its most expensive form,
because the capability was demonstrably built and the product behaved as though
it were not. It is also why I twice told the client where to set a colour and was
twice wrong: first the customer's Erscheinungsbild screen (which holds the
**font**, and says so itself), then Organisation → project (which holds the
catalogue's texts and the privacy link, and no colour).

`Primärfarbe` and `Schriftfarbe auf der Primärfarbe` are now on the project form,
each a colour well beside a hex field — the text input is the authoritative one,
because an operator pastes `#007f95` from a brand guide far more often than they
pick from a wheel, and the well is what makes it recognisable as a colour.

**Both halves tested, and the first sabotage is why there are two.** Breaking the
_write_ path fails "sends the primary colour an operator typed". Breaking the
_load_ path left that green — it types a value before saving — so there is a
second case: an operator opening the form over a configured colour would have
seen an empty field and no way to know which was true.

### What this means for DEP-38 on the live installation

P216 changed the palette **default**. For a project that has a `primaryColor`
stored, the default is never read. Until now nothing could have stored one, so
the default is almost certainly what MEDICE are seeing — and the teal should
already be `#007f95` after this deploy. If it is not, the project now has a field
that says why, and one that can fix it.
