# P189 — The guard that decides whether the journey runs could not say why it failed

**Raised by:** deploy run 114, the first successful deploy after P188.

**Branch** `claude/education-platform-roadmap-3vgrqh`. Touches **eiv** (the
posture read that gates the post-deploy journey), so `needs-human-review`.

---

## What happened

The deploy succeeded and `deploy.sh`, on the host, printed:

```
==> EIV posture: endpoint=live armed=false live-consent=false
```

Exactly what P188-01 intended. Then both workflow steps that read the same
database over SSH answered nothing:

```
##[warning]platform_settings could not be read on the host. This run fails
closed and treats the installation as reporting live, so the journey will not
run.
Files Punktemeldungen live: yes (platform_settings: unreadable)

##[warning]The host's mail posture could not be read.
```

So the post-deploy journey — the end-to-end test the client asked for — did not
drive anything, and P188-03's whole output was a shrug.

**And the log could not say why**, because both reads ended `2>/dev/null`. That
is CLAUDE.md §9.1's third form — green because of what it is not looking at —
sitting on the one decision about whether the product gets driven at all, with
§9.4 on top: the message named the symptom and nothing an operator could act
on.

## What is verified, and what is not

**Verified, from the run's own log:**

- `deploy.sh` read `platform_settings` on the host and printed the three values.
- Both workflow steps got an empty string from the same query, seconds later.
- Both discarded the reason.
- The Deploy step invokes the host with `ssh -tt`; both posture steps use plain
  `ssh`.

**Not verified:** _why_ the reads came back empty. I cannot reach the host. The
`-tt` difference is the one I can see in the diff between the invocation that
works and the two that do not — a candidate, not a diagnosis, and it is
deliberately **not** the argument for this change.

## P189-01 — the read says what happened

Two changes, and the second is the one that stands on its own.

- **`bash -lc`.** The step that reads this table successfully gets a login
  shell; these did not. `-tt` would be the wrong way to get one: it allocates a
  TTY, whose carriage returns and login banner would land in the string being
  parsed — which is presumably why plain `ssh` was chosen for a parsed read in
  the first place.
- **The psql stderr is captured and printed.** Whether or not the shell is the
  cause, the next run states it. That is the part that makes this fix correct
  even if the first half is wrong.

`unreadable:<reason>` now flows into the warning, and the mail step reports
`psql said: …`.

## P189-02 — the query moved out of the workflow

The mail-posture SQL was inline in `deploy.yml`, inside an `ssh "…"` inside a
YAML block scalar. An empty SQL string literal is `''`, which cannot appear
inside the single-quoted `bash -lc '…'` the read now uses, and the escape that
avoids it (`$$$$`, Postgres dollar-quoting) is unreviewable — I wrote it, looked
at it, and could not convince myself it was right.

`eiv-endpoint.sh` already solved this for the EIV posture by putting the query
in a function. `infra/deploy/mail-posture.sh` does the same, and gains what a
string in a workflow can never have: `mail-posture.test.sh`, sixteen assertions
over the query and the arithmetic.

### The sabotage that produced silence

Worth recording, because it is §9.1 aimed at the check meant to prove a guard.

`ds_mail_posture_fallback_count` refuses a non-numeric answer before reaching
`$(( ))`. Removing that guard and re-running the tests printed **nothing at
all** — under `set -u`, `$(( ERROR - x ))` does not return non-zero, it kills
the shell, and it took the test file down with it. A sabotage whose result is
silence is indistinguishable from one that was never applied.

The two refusal cases now run in a subshell, so a crash is a non-zero status the
case can see. With that, removing the guard fails loudly. It is also how the
deploy calls it: a step that died mid-read would report the deploy as broken
rather than the question as unanswerable (§9.6).

## Acceptance criteria

- [x] Both posture reads report the error instead of discarding it.
- [x] The mail query is a sourced function, not a string in a workflow.
- [x] The query and the arithmetic are driven by tests, watched red.
- [x] A crash in the arithmetic is a visible failure, not silence.
- [ ] **The reads actually answer on the next deploy.** Cannot be verified from
      here; the next run's log settles it either way, which is the whole point
      of this ticket.

## Not done

- **No change to failing closed.** An unreadable posture still skips the
  journey. That is right: the alternative is driving a Fortbildung to completion
  on an installation that might be filing real Punktemeldungen, and a guard that
  fails open on its own confusion is not a guard.
