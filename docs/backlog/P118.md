# P118 — Correcting an EFN fixes the certificate and not the Punktemeldung

**Status:** built. **Human review required** — `eiv` and `certificates`.
The second half is a refusal, not a resolution: the rule behind it is **S30**.

Derived from source while answering a support question, not reproduced in a
browser. Labelled as such (§9.9).

---

## The question that found it

> "in here for my certificate says abandoned, how can i as a support fix this and
> recreate the certificate with correct efn and send it?"

A fair question with a partly wrong answer available, which is the worst kind.

## What support can and cannot do

| Step                      | Path                                                     | Works              |
| ------------------------- | -------------------------------------------------------- | ------------------ |
| Re-issue the certificate  | Zertifikate → **Neu ausstellen**, then **Erneut senden** | yes                |
| Re-file the Punktemeldung | Teilnehmende / Punktemeldungen → **erneut einreihen**    | yes                |
| **Correct the EFN**       | —                                                        | **no path exists** |

The third is deliberate and right. `PUT /profile/efn` is `@Roles(LEARNER_ROLES)`
and its own comment says why: _"the subject is the principal, never a
parameter. Adding a `:userId` to this path would turn a self-service field into
an EFN lookup service."_ ADR-0004. Support must not be able to set or read
another physician's EFN, so the physician corrects their own in the portal.

## The defect

**`efn_profiles` and `eiv_submissions.efn` are two copies, and only one is
followed.**

`certificate.repository.ts` reads the EFN **live** from `efn_profiles`, and its
comment states the intended invariant exactly:

> _an EFN is permanent and unique per physician (ADR-0004), so a correction to
> it means the earlier value was wrong — including on a certificate already
> issued. **Snapshotting would keep the typo on the paper while the
> Punktemeldung went to the corrected number.**_

The real behaviour is that sentence inverted. `eiv_submissions.efn` is a column
frozen at completion, `saveEfn` writes only `efn_profiles`, and
`EivAdminRepository.requeue` sets `status`, `attemptCount`, `lastError` and
`nextAttemptAt` — and does not touch `efn`.

So the support flow that looks correct produces two documents that disagree:

1. physician corrects their EFN in the portal → `efn_profiles` updated;
2. support clicks **Neu ausstellen** → certificate rebuilt with the **new** EFN;
3. support clicks **erneut einreihen** → Punktemeldung filed with the **old** one.

Nothing reports a problem. The Kammer credits the points to whoever holds the
old number, and the physician holds a certificate saying otherwise. ADR-0004
calls this the worst available failure _because it looks like success_.

It is §9.2 — the console offers a control that cannot do the thing the person
clicking it needs — and §9.3 one layer down: the rule is written, in a comment,
on the half that obeys it.

## What was built

### The half that is unambiguous — done

For a submission **never accepted** — `queued`, `held`, `failed_retryable`,
`failed_permanent`, `window_closed` — nothing was reported, so refreshing the
EFN from `efn_profiles` on requeue is plainly right. It is the same argument
`nameCorrection` already makes for a name, on the same `SubmissionStage`:

> _`abandoned` is allowed for the same reason from the other direction: nothing
> was reported, so there is nothing for the record to disagree with._

`efnRefresh` in `@ds/domain` decides it, and `requeue` obeys. The repository
takes an optional `efn` and applies it only when told to — adopting the newest
value unconditionally is exactly the decision a repository must not be making,
and it is the one that would silently re-file an accepted Meldung.

`loadForAction` gained the profile's EFN by **LEFT** join. An erased subject has
no profile row and a submission still owed; an inner join would have turned "no
newer EFN" into "no submission", which is §9.6's shape one table over.

### The half that is a compliance question — refused, not guessed

For `submitted` or `withdrawn`, the points reached a real physician's record
under the **old** EFN. Re-filing under a new one does not move them; it credits
a second person. The right sequence is presumably withdraw-then-refile, plus a
written correction to the Kammer — but "presumably" is exactly what §7 forbids.

`requeue` now refuses when the EFN would change on a row that was accepted, and
the message names the field and the next step — stornieren, or the Ärztekammer —
never either EFN. An operator is not entitled to the physician's identifier
(ADR-0004) and an error string reaches a log (§9.5). `describeError` already
carries the server's sentence onto the Teilnehmende screen, so the operator
meets a reason rather than a 409.

The audit row records `efnRefreshed` as a **boolean**, for the same reason: that
the identifier moved is the auditable fact; what it moved to is the physician's.

Raised as **S30** in `docs/show-stoppers.md` with the German wording.

### A third thing, found on the way

`submissionStage` now exists in `@ds/domain` as the pure twin of `STAGE_SQL` in
`moderation.repository.ts` — two implementations of one collapse, which is what
§4 invariant 6 warns about. They are named on each other, and the domain test
enumerates **every** member of `eiv_status` rather than sampling: a value added
to the enum and not to both falls through to `pending`, which is a wrong
compliance answer rather than a type error.

## Evidence the checks can go red (§9.1)

Each was broken and watched to fail, then restored:

| Broken                                                                                  | Went red           |
| --------------------------------------------------------------------------------------- | ------------------ |
| the refusal branch in `efnRefresh`                                                      | 1 domain test      |
| the trim on both sides                                                                  | 1 domain test      |
| the service's `efn` argument to `requeue` — the rule still called, its answer discarded | 1 integration test |
| the service's refusal branch                                                            | 1 integration test |

The third is the §9.7 case specifically: a pure rule with exhaustive unit tests
proves nothing if nothing calls it, and the test that catches a severed call
site has to live at the call site.

762 domain tests, 561 integration tests against real Postgres, and all fourteen
steps of `pnpm verify`.

## What support should be told today

Until this is fixed, an EFN correction is **not** a self-service repair:

1. the physician corrects their EFN themselves in the portal;
2. **do not** click _erneut einreihen_ — it will re-file the old number;
3. re-issue the certificate, which does follow the correction;
4. the Punktemeldung has to be handled with the Ärztekammer directly.

# P118-02 — "unzustellbar" was the whole story, and the reason was in the table

The same screenshot, the other column. Found by asking what an operator does
next and finding the screen had no answer.

## The defect

`delivery_abandoned_reason` has been written since P8-03 and **returned by no
API**. So `bounced` was everything the console knew, and it offered **Erneut
senden** on every such row. The three reasons want three different actions, and
for two of them that button can only fail again:

| reason                | what it means                            | resending     |
| --------------------- | ---------------------------------------- | ------------- |
| `no_recipient`        | no address on file for the participant   | cannot work   |
| `permanent_rejection` | the receiving server refused the address | cannot work   |
| `attempts_exhausted`  | transient failures ran out of retries    | exactly right |

§9.2, and §9.3 underneath it: the domain already knew the distinction mattered.
`delivery-retry.test.ts` carries a case whose comment reads _"…which sends
whoever reads it looking for a mail…"_ — the rule was written, tested, and
reached nobody.

## What was built

`CertificateRecord.deliveryAbandonedReason` in the contract, the repository and
the SDK. An **enum**, never the far end's message: a rejection string can carry
the address and the receiving server, and a fixed vocabulary cannot (§9.5).

The screen renders the reason as a sentence under the status — where somebody
asking _"why can I not send this?"_ is already looking, rather than in a tooltip
they have to find — and disables **Erneut senden** for the two reasons it cannot
help.

Four component tests, and the third is the control: `attempts_exhausted` **must**
still offer the resend, or the fix would be a refusal with no defect behind it.
Watched to go red — `resendable` neutered to `return true` failed exactly the
two cases that should fail and left the control green.

## What this does not answer

**Why** that certificate bounced on the installation. The reason is now visible;
read it off the Bescheinigungen screen. If it says `attempts_exhausted`, the
platform's SMTP settings are the place to look (Verwaltung → Einstellungen).
