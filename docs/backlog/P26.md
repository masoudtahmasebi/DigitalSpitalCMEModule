> there should be a first customer with test lorem ipsum data with customer

One ticket, and a second thing found while doing it that had been broken for
three releases.

---

## P26-01 · The default customer — **done**

- **Estimate:** 3 h

### The problem

A deploy created no content. That was a deliberate rule — "a deploy that writes
rows is a deploy that can write the wrong ones into a live database" — and its
consequence was that the first operator to sign in met a console with no
customer, no department, no project and no course, four things to create in the
right order, and no example of a filled-in one to copy.

Neither existing seed was that example:

- `seedMediceAdhs` carries a real VNR and a real accreditation, so running it to
  "have a look" seeds a course that could file a Punktemeldung.
- `seedDsDemo` is the second tenant the isolation tests need — its name says
  Testkunde and its Ärztekammer is fictional but its CME course carries a dummy
  VNR and points.

### What was built

`packages/seed/src/ds-default.ts`, and two `main()`s over it —
`db/seed/ds-default.ts` for a checkout, `apps/api/src/seed-ds-default.js` in the
image — following `db-migrate.ts`'s rule about never having two copies of
something like this.

`DSCustomer` → `DSOrganisation` → `DSProject` → one course with one module
`DSModule`, five chapters with real durations, five materials, a
Lernerfolgskontrolle of five questions and a three-question Evaluationsbogen.
Lorem ipsum throughout, and obviously so: a placeholder somebody might mistake
for content is a placeholder that ships.

Slugs are lower-case (`dscustomer`, `dsproject`, …) even though the names are
not, because a slug reaches a URL path and an `X-DS-Project` header.

### Why a deploy may run this one

`deploy.sh` runs it after migrations, and it is the only seed on that path.
Three properties make it different in kind rather than in degree:

| Property                                     | Consequence                                                                                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `--if-missing`                               | reads one row and returns **before the first write** once the customer exists, so a redeploy is a no-op rather than a content rebuild |
| no VNR, no accreditation body, no CME points | nothing it seeds can reach the EIV interface — a course with points is a course the worker tries to report                            |
| prints no password when unattended           | the deploy runs from a GitHub Actions job, so its stdout is a workflow log                                                            |

`SEED_DEFAULT_CUSTOMER=no` switches it off, for an installation whose only
tenant is a customer's real content.

The demo participant therefore exists on production with a password nobody
holds. That is the right trade: an administrator sets one under **Teilnehmende**,
which is the path a real physician's credential arrives by anyway.

### How the two flags are tested

`apps/api/test/integration/seed-default.integration.test.ts`, and by **effect**
rather than by row counts. `onlyIfMissing` is exactly the shape of control this
repository has now shipped broken three times — one that looks implemented, is
never exercised, and whose failure is silent — so the test edits a course title
by hand, inserts a content row by hand, runs the seed, and requires both to
still be there. Counting rows would pass just as happily against a seed that
deleted the tree and rebuilt it, which is the failure that costs a learner their
progress.

Both flags were probed by deliberate violation: reverting the early return fails
the `onlyIfMissing` test, and forcing the password line on fails the withholding
test.

### Deliberately not done

- **No automatic seeding of anything else.** The other two seeds rebuild their
  courses' content unconditionally and stay manual.
- **No "is this installation empty?" check.** It cannot be asked from
  `ds_migrator` — `customers` is RLS-scoped to a single tenant and the registry
  function that escapes that is owned by a `BYPASSRLS` role granted to `ds_app`
  alone. Widening that surface for a convenience check would be the wrong trade;
  "does _this_ customer exist" answers the same question inside the tenant.

## P26-02 · Three documented commands that could never have worked — **done**

- **Estimate:** 1 h

Found while writing P26-01's runbook section.

Every seed and the subject-erasure tool connects as `ds_migrator`. The guides
told an operator to run:

```bash
./dsc run --rm --entrypoint node api dist/seed-ds.js --force
```

which refuses with `MIGRATION_DATABASE_URL is not set` before opening a
connection — `dsc` sources `config.env` and `secrets.env`, but nothing puts that
variable into the container. Adding the `-e` by hand does not fix it either:
`${DS_MIGRATOR_PASSWORD_URL}` expands in the caller's shell, which has never
seen `secrets.env`.

The erasure runbook had the same shape with two further faults: it read
`--env-file .env.production`, a file that has not existed since the
configuration moved out of the clone, and it interpolated the **un-encoded**
password, which produces an invalid URL as soon as a generated password contains
a `/` or a `+` — which is most of them, and is the bug that killed the first
deploy to reach the server.

`dsc` now has `as-migrator`, and `seed` as sugar over it:

```bash
./dsc seed default          # or ds, or medice
./dsc as-migrator dist/subject-erasure.js --subject … --reason …
```

Both start a one-shot container and touch no running service, so `dsc`'s rule
about never deploying still holds. The API container does **not** carry
`MIGRATION_DATABASE_URL`: `ds_app` is deliberately not `ds_migrator` (ADR-0002),
and injecting the URL into one container that exits is the narrow version of the
same convenience.

`secrets.test.sh` asserts the whole variable — encoding included — off the
argument vector compose was handed, with `docker` stubbed on PATH. A probe that
swaps `DS_MIGRATOR_PASSWORD_URL` back for `DS_MIGRATOR_PASSWORD` fails it.

### Also corrected

The guides claimed `--force` was required for a seed on the server. It is not:
`openSeedPool` counts the compose network's `postgres` host as local. A flag
typed out of habit is how that guard stops meaning anything.
