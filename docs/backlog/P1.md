# Epic P1 · Auth & user profile — 10 h

**Weeks 1 (6 h) and 2 (4 h).** Implements ADR-0003. The governing rule is that the
API never trusts WordPress's assertion that a user is authenticated — every token
is validated independently against Keycloak JWKS.

**Every task in this epic is behind the human review gate.**

**Demo at end of phase:** a token minted by the dev Keycloak realm is accepted; a
tampered, misaddressed, wrong-issuer or expired token is rejected with a distinct
error; the resolved user is bound to a tenant context.

---

### P1-01 · Keycloak JWKS token validation

- **jira:** _(unassigned)_
- **Estimate:** 3 h · **Week:** 1 · **Depends on:** P0-03
- **Review gate:** human — auth
- **Implements:** ADR-0003

**Context**
The trust anchor for the whole system. Validating only the signature is the
common mistake: a validly-signed token minted for a different client or realm
would then be accepted here.

**Scope**
- Fetch and cache the realm JWKS; verify RS256 signature.
- Verify `iss` against the project's configured issuer, `aud` against its
  configured audience, and `exp`/`nbf` with a small configurable clock skew.
- Reject unsigned and `alg: none` tokens explicitly.
- A distinct, non-leaking error per failure reason; the client sees a generic
  401, the audit log sees the specific reason.

**Acceptance criteria**
- [ ] A valid dev-realm token is accepted
- [ ] Each of these is rejected, each with its own internal reason: tampered
      signature, wrong audience, wrong issuer, expired, `alg: none`, malformed
- [ ] Issuer and audience come from the project's binding, never from the token
- [ ] No token, or fragment of one, appears in any log
- [ ] Validation is unit-tested against locally generated keys, so tests need no
      running Keycloak

### P1-02 · User identity resolution and provisioning

- **jira:** _(unassigned)_
- **Estimate:** 2 h · **Week:** 1 · **Depends on:** P1-01
- **Review gate:** human — auth
- **Implements:** ADR-0003

**Context**
CME points attach to a person. Keycloak `sub` is the primary key precisely
because email changes when a physician moves practice or changes name, and a
split identity would fragment their participation record.

**Scope**
- Resolve `sub` → local user; provision just-in-time on first sight.
- `email` as a documented, audited fallback for reconciling pre-existing records
  only.
- Profile (name, email) refreshed from the validated token on each request; no
  separate profile maintenance.

**Acceptance criteria**
- [ ] First request for an unknown `sub` creates exactly one user
- [ ] Concurrent first requests for the same `sub` create exactly one user
- [ ] A changed email on an existing `sub` updates the profile and does **not**
      create a second user
- [ ] The email fallback path writes an audit entry every time it is taken
- [ ] A `sub` collision across realms is impossible — realm is part of the key

### P1-03 · JWKS caching and key rotation

- **jira:** _(unassigned)_
- **Estimate:** 1 h · **Week:** 1 · **Depends on:** P1-01
- **Review gate:** human — auth

**Context**
ADR-0003 accepts a coupling to Keycloak's availability. Caching is what keeps a
brief Keycloak outage from rejecting every valid token, and rotation handling is
what stops the cache becoming the outage.

**Scope**
- Cache JWKS in Redis with a TTL; serve from cache on fetch failure.
- On an unknown `kid`, refetch once, rate-limited, before rejecting.
- Metrics: cache hit rate, refetch count, validation failures by reason.

**Acceptance criteria**
- [ ] Validation continues to succeed while Keycloak is unreachable and the cache
      is warm
- [ ] A rotated signing key is picked up without a restart
- [ ] An unknown `kid` triggers at most one refetch per rate-limit window, so a
      flood of bad tokens cannot hammer Keycloak

### P1-04 · Role model and guards

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 2 · **Depends on:** P1-02
- **Review gate:** human — auth

**Context**
Four roles with materially different blast radius. Super admin is deliberately
not a bypass — see ADR-0002.

**Scope**
- Roles `super_admin`, `customer_admin`, `department_admin`, `learner`, resolved
  from validated token claims plus local assignment.
- NestJS guards; deny by default — an endpoint with no explicit role requirement
  is unreachable rather than public.
- Super admin acts as exactly one customer at a time, audited.

**Acceptance criteria**
- [ ] An endpoint without an explicit role decorator returns 403, not 200
- [ ] `department_admin` cannot read another department within the same customer
- [ ] `customer_admin` cannot read another customer even with a valid token
- [ ] Super-admin "act as customer" writes an audit entry naming the customer
- [ ] Role escalation via a crafted token claim is impossible — roles are checked
      against local assignment, not taken from the token alone

### P1-05 · Tenant context interceptor

- **jira:** _(unassigned)_
- **Estimate:** 1.5 h · **Week:** 2 · **Depends on:** P1-04, P0-04
- **Review gate:** human — auth
- **Implements:** ADR-0002

**Context**
The bridge between a validated token and PostgreSQL RLS. The failure mode this
task exists to prevent is a pooled connection leaking one request's tenant into
the next.

**Scope**
- Per-request transaction; `set_config('app.customer_id', …, true)` and
  `app.role`, transaction-scoped so pooling cannot leak them.
- Values derived from the validated token and local role assignment, **never**
  from a request parameter, header or body field.

**Acceptance criteria**
- [ ] Every request runs inside a transaction with the setting applied
- [ ] A client-supplied `customer_id` in any part of the request is ignored
- [ ] A test that issues interleaved requests for two customers over a pool of
      one connection shows no leakage
- [ ] A request whose tenant cannot be resolved fails closed, with no query run

### P1-06 · EFN profile field

- **jira:** _(unassigned)_
- **Estimate:** 1 h · **Week:** 2 · **Depends on:** P1-02
- **Review gate:** human — auth
- **Implements:** ADR-0004

**Context**
`efn_profiles` is the system of record. One EFN per person, not per enrolment —
divergent EFNs across courses would let a submission credit the wrong physician's
account, which looks like success and is the worst available failure.

**Scope**
- Read/write endpoints for the current user's EFN, tenant-scoped.
- Format validation (15 digits, checksum where defined) at write **and** again at
  submission time.
- Treated as personal data: never logged, redacted in error reporting.

**Acceptance criteria**
- [ ] One EFN per user, enforced by the schema
- [ ] An invalid EFN is rejected with a message the learner can act on
- [ ] The EFN never appears in application logs or error payloads
- [ ] A user cannot read or write another user's EFN, including within the same
      customer
