# P238 — the console could say that something failed and had no way to say it worked

The client, after the nine-PR admin redesign landed:

> the tokens spent on the admin redesign, have been the most useless token spent
> on the whole project until now, i don't see any difference in ui/ux and **not
> even a toast for success** and correct error blocking is there.

The first half of that is a judgement. The second half is a fact, and it is
derivable from source in two greps.

---

## What was actually true

`useSaver` has computed a `"saved"` state since P9-02. Counted across the nine
components that own a saver:

|                            | inline failure rendered | inline success rendered |
| -------------------------- | ----------------------- | ----------------------- |
| CourseStructure (3 savers) | yes                     | **no**                  |
| EivCheck (1)               | yes                     | **no**                  |
| Learners (2)               | yes                     | **no**                  |
| NewCourse (1)              | yes                     | **no**                  |
| Organisation (4)           | yes                     | **no**                  |
| EvaluationEditor (1)       | yes                     | yes                     |
| ExpertsEditor (1)          | yes                     | yes                     |
| QuizEditor (1)             | yes                     | yes                     |
| Security (1)               | yes                     | yes                     |

**Eleven of fifteen mutations reported nothing on success.** Delete a module,
reorder a course, correct a physician's name, erase a participant's record,
create a project — the operator got no acknowledgement at all. Every one of the
nine reports its _failures_, because P202/P205 did that audit and closed it.
Nobody had ever done the other half.

And the mechanism for it was sitting there unused: `toasts.tsx` has exported
`useToasts` since the day it was written and **nothing called it**. The host had
exactly one publisher — the failure net in `api.ts`. §9.3, in the file whose
entire purpose is to prevent silence.

## P238-01 — the confirmation is part of the mutation, not part of the screen

`Saver.run` now takes the sentence:

```ts
readonly run: (success: string, action: () => Promise<unknown>) => Promise<boolean>;
```

**Required**, because an optional argument would have left this exactly as
enforceable as it was — which is to say not at all. The compiler named all
fifteen call sites, and each had to answer what it had just done.

**At `run` rather than at `useSaver`**, because one saver serves several
actions: `CourseStructure`'s `mutate` is threaded down to delete a module, a
chapter and a content, and to reorder the tree. A single "Gespeichert." would
have satisfied the compiler and thrown away the point — it is true after erasing
a subject's data and it is the wrong word for it (§9.4).

`useSaver` publishes through `useToasts`, so it is a net rather than fifteen
decisions — the argument P205-01 already makes for failures, one paragraph over
in the same file: _a net under every request cannot be forgotten by a screen
that has not been written yet._

Screens keep their inline `Notice tone="success"` where they have one. That is
deliberate and matches what the project already does for errors: the inline
message carries context beside the form, the toast is the floor. Four screens
now say it twice, in different words, in different places.

### Two live regions, not one

A live region's urgency belongs to the **region**, not to what is put into it.
One `aria-live="assertive"` container announces a confirmation by interrupting
whatever a screen reader was saying to report that a save worked. So there are
two regions in one fixed wrapper — polite/`role="status"` for confirmations,
assertive/`role="alert"` for failures — with the errors rendered last so they
hold the lower corner nearest the eye. A confirmation is also dismissed after
5 s rather than 12 s: it carries no reference id and nothing to copy.

### A defect found while separating them, not reported

`CourseStructure` adopted a child form's result by calling
`onMutate(async () => next)` — an "action" that performs no request and cannot
fail, routed through the parent's saver anyway. Two consequences, and only the
first is new:

1. With `run` announcing, it would publish a **second** confirmation on top of
   the one the child form's own saver had just published.
2. It already ran the parent's state machine, so adopting a result set the
   parent to `"saved"` and **cleared `problem`** — a reorder that had failed a
   moment earlier had its error wiped by an unrelated form finishing.

Split into `onMutate` and `onAdopt`. The second point is read from the state
machine in `hooks.ts`, not observed in a browser, and is labelled as such.

| `confirmations.test.tsx` — the a11y   | polite vs assertive. A screenshot cannot see this any more than it can see a missing label                                                              |

Watched red, one sabotage each:

| Sabotage                                  | Red                                                                 |
| ----------------------------------------- | ------------------------------------------------------------------- |
| `publish` removed from the success path   | "announces a mutation that worked…" + "confirms a created project…" |
| `publish` also called on the failure path | "says nothing when the mutation failed"                             |
| the `alive` guard dropped                 | "does not announce to a screen the operator has already left"       |
| the polite region made assertive          | "puts a confirmation in a polite region…"                           |
| `publish` removed, in the browser         | the journey, at `getByRole('status')`                               |

### And one of my own tests could not go red (§9.1)

The unmount case first called `view.unmount()` — which takes the `ToastProvider`
down with the screen, so there was nowhere for a toast to appear and the
assertion held whether the guard existed or not. Removing the guard left all
five cases green. It now unmounts only the child, through a switch the provider
owns, which is also the shape of the real case: the shell keeps its toast host
while the operator moves between screens.

## What this deliberately does **not** do

- **No visual redesign.** The client's "i don't see any difference in ui/ux" is
  answered by the console now responding to what an operator does, not by moving
  boxes. Speculative restyling is what the sentence was complaining about.
- **The per-row `quiet` buttons stay as they are.** They read as bare text in a
  screenshot because their border is drawn on hover, which is P22-07's
  deliberate decision against sixty bordered boxes on an authoring tree. If the
  client wants that revisited it is a decision, not a cleanup.
- **"correct error blocking" is not changed**, because the audit above found
  nothing missing: all nine screens render `saver.problem`, the net in `api.ts`
  toasts every announceable rejection, and `run` resolves `false` so callers
  already refuse to proceed. If the client meant something else by the phrase,
  it needs a case — asked rather than guessed (§7).
