## 2. The sizing decision, with numbers

PR #41 today, **VERIFIED**:

```
$ git diff --shortstat origin/main...HEAD
 351 files changed, 40449 insertions(+), 2819 deletions(-)
$ git rev-list --count origin/main..HEAD
117
```

and, from the GitHub API in this session, it carries `needs-human-review`, is
open and unmerged, and `get_reviews` returns `[]` — **no human has reviewed any
of it yet.**

The requested harness is not one feature. It is three compliance-critical
changes, each of which independently trips CLAUDE.md §2's review gate:

1. **A per-course EIV environment.** New column, migration, a safe default for
   every existing course, token-cache separation so a test token can never be
   presented to production, an audit event, and a second endpoint-resolution
   path beside the deployment-level one that `eiv-endpoint.sh` mirrors. Two
   implementations of "which endpoint" is precisely the shape §9.11 warns about.
2. **A `push_teilnahme` reachable from an admin screen.** Today no admin surface
   can reach it, in code and by explicit design — `EivCheck.tsx`'s header says
   so, `eiv-admin.service.ts` contains no such call, and `./dsc eiv` omits the
   capability from its entrypoint. Reversing that is not an extension; it is
   undoing a designed-in guard on the one operation that cannot be taken back.
   And it needs its own storage, because `eiv_submissions` is enrolment-unique.
3. **A watermarked certificate through the real renderer.** A renderer change, a
   render path that does not go through `findSourceByEnrolment`, a new storage
   namespace, and a new data-retention behaviour.

The work order forbids introducing "a schema migration, new role, new secret,
new storage namespace, or new data-retention behaviour" without documentation —
this needs **three of the five** — and forbids adding a broad new subsystem to
an already large PR. Both point the same way.

**And the acceptance criterion cannot be met in this environment.** The harness's
central claim is "EIV accepts the test submission". Every EIV host is refused
before the TLS handshake:

```
$ curl -sS -o /dev/null -w '%{http_code}' --max-time 20 https://backend-test.eiv-fobi.de
curl: (56) CONNECT tunnel failed, response 403      curl_exit=56

$ curl -sS "$HTTPS_PROXY/__agentproxy/status"
"recentRelayFailures": [{ "kind": "connect_rejected",
  "detail": "gateway answered 403 to CONNECT (policy denial or upstream failure)",
  "host": "backend-test.eiv-fobi.de:443" }]
```

Same result for `veranstalter-swagger-ui.eiv-fobi.de` and
`punktemeldung-test.eiv-fobi.de`. So the Swagger definition cannot be read
either, and per the work order's own instruction endpoint paths must come only
from checked-in contracts — which they do, in §1.6 above.

Building an admin-reachable path to `push_teilnahme` that has **never once
spoken to the real test server**, into a 351-file PR that no human has reviewed,
and reporting it as done, is the exact shape of §9.1 and §9.9 together: a green
suite standing in for a system nobody has exercised.

## 3. Proposed breakdown

Four slices, in dependency order. Each is independently reviewable, independently
deployable, and independently useful. Slices 2–4 must not start before Masoud has
decided the open question in §4.

### Slice 1 — Preflight and environment visibility (read-only)

Branch `P153-eiv-preflight`. **No schema change, no submission, no renderer
change.**

Extend the existing `checkConnection` report and `EivCheckPanel` with:

- the **server-resolved** endpoint tier and hostname label (`mock` / `test` /
  `live`), from `eivEndpointTier()` — never an editable URL;
- a `preflight` step: VNR present, not the placeholder VNR, password stored,
  certificate fields complete (`missingCertificateFields`), points configured;
- a persistent environment badge — Testumgebung / Produktivumgebung.

Acceptance criteria:

1. The panel names the environment the **server** resolved, and no request body
   or query parameter can change it. Test: a request carrying a `baseUrl` field
   is ignored, asserted by response equality against the same request without it.
2. `preflight` reports each missing item by **field name**, never by value (§9.5).
3. The password remains absent from every response and every error payload,
   asserted by the existing leak-check helper
   (`apps/api/test/support/answer-leak.ts`).
4. A `customer_admin` of another tenant gets a refusal, not empty data (§9.6).
5. Sabotage: route `test` to the live label → red.

### Slice 2 — Per-course EIV environment

Branch `P154-course-eiv-environment`. **Schema migration. Human review.**

Acceptance criteria:

1. Existing courses default to the environment that preserves today's behaviour
   exactly, proven by an integration test that asserts the resolved endpoint for
   a course migrated from the pre-migration schema is byte-identical to the
   deployment-level `EIV_BASE_URL` it used before.
2. One resolution function, shared with `eiv-endpoint.sh`'s fixture table — not
   a second opinion.
3. Changing the environment requires `super_admin`, an explicit confirmation
   naming the destination, and writes an audit row containing neither the VNR
   password nor a full EFN.
4. Token caches are keyed by environment; a test token presented against
   production is refused. Sabotage: share the cache → red.
5. An in-flight submission keeps the target it started with. Tested with
   `Promise.all`, per §11 rule 10 — a sequential test proves nothing here.

### Slice 3 — Diagnostic test participation (TEST only)

Branch `P155-eiv-diagnostic-submission`. **Human review. Blocked on §4.**

Acceptance criteria:

1. The route refuses unless the resolved tier is `test` **or** `mock`. A
   production/live target refuses a synthetic EFN with a named refusal, never a
   simulated success. Sabotage: permit it → red.
2. Diagnostic runs live in their own table, keyed by course + run id. No
   `enrolments`, `eiv_submissions`, `content_progress`, `quiz_attempts` or
   `certificates` row is created or modified — asserted by row-count deltas
   across the whole request.
3. Every attempt, success or failure, writes an audit row.
4. Repeated clicks cannot file twice: an idempotency key per run, tested with
   `Promise.all` of N concurrent requests.
5. Nothing logs or returns the password, the JWT, or an unmasked EFN.

### Slice 4 — Diagnostic certificate

Branch `P156-diagnostic-certificate`. **Human review.**

Acceptance criteria:

1. Rendered by `renderCertificatePdf()` — the production renderer — with a
   watermark parameter. Sabotage: omit the watermark → red.
2. The PDF is non-empty and contains the expected markers, asserted the way
   `certificate.renderer.test.ts` already asserts PDFs.
3. The artefact is never written under `<customer>/certificates/…`, never
   creates a `certificates` row, and is never delivered by e-mail. Sabotage:
   write it to the participant namespace → red.
4. A documented retention: the shortest that still exercises the archive adapter.

## 4. The open question only Masoud can answer

**Is the per-course environment (Slice 2) wanted at all, or is the real request
"let me run the existing check, plus a test filing and a test certificate,
against the installation's already-configured test endpoint"?**

It matters, because the second reading needs no schema migration and no second
endpoint-resolution path — the platform already points at one EIV endpoint,
already knows its tier, and `docs/eiv-test-system.md` already describes pointing
an installation at `backend-test.eiv-fobi.de`. That reading is Slices 1, 3 and 4
without Slice 2, and it is markedly cheaper and safer.

The first reading — one installation serving some courses against test and some
against production — is a real capability, and it is the one that puts a
production filing one dropdown away from a test one, for ever.

This is a product decision with a permanent safety cost. CLAUDE.md §7: do not
guess on compliance semantics.

## 6. Not verified, and why

- **The real EIV test backend.** Unreachable from this environment (above). No
  claim is made that it accepts anything. `./dsc eiv` from the host is the tool
  that settles it, and `docs/eiv-test-system.md` documents how.
- **The Swagger/OpenAPI definition.** Same refusal. Endpoint paths in §1.6 come
  from checked-in client code, not from external documentation.
- **Whether all three supplied VNRs share one password.** Not testable here, and
  the work order is right that it must not be assumed. `./dsc eiv` answers it
  one VNR at a time.
