**Raised by:** the client, 04.09.2026, on the support panel P179 built:

> now in the section says: `No e-mail address is on file for this person.
Resending cannot succeed — download the certificate and send it another way.`
> we should have the email of the person from the keycloak, and also in the last
> layout design that people can provide their efn, we should have a input field
> like efn, that people can see and are able to change their email address . we
> should have a similar field in the admin section for each participant so that
> we can give them the certificate, it can be the case that they want to have the
> certificate in another email or so.

**Branch** `claude/education-platform-roadmap-3vgrqh`.

---

## Why the sentence is there, which is not a defect

`delivery.repository.ts` reads the recipient as `users.email`, live, at send
time — migration `0012` explains why it is not copied onto the certificate: it
is personal data, and ADR-0008's erasure nulls exactly one column. When that
column is null, `planDeliveryAttempt` abandons with `no_recipient` rather than
posting a Teilnahmebescheinigung to nobody, and P179 put that reason on screen.

So the panel is telling the truth. What is missing is that **nothing on the
platform can supply the address** — not the physician, not an operator. That is
CLAUDE.md §9.4: the screen says what happened and not what the person holding it
does next, and §9.2's mirror — an absent affordance where an action is possible.

## Where the address was supposed to come from (§9.9 first)

The chain already exists and this ticket does not replace it:

1. the **token**'s `email` claim, through `syncFromToken` → `provision_learner`,
   which `coalesce`s so an absent claim never erases a stored value;
2. failing that, the **host page's profile hint** — P105-01 built it precisely
   because _"MEDICE's realm sends no `email`, `given_name` or `family_name`"_,
   and the WordPress plugin passes what `getUserInfoByToken()` returns.

A federated learner therefore has an address whenever MEDICE's realm maps the
claim **or** the site runs a plugin new enough to send the hint. Which of those
is true on the running MEDICE site is not established here and is not derivable
from this repository — §9.9, the installation's state is not the repository's.
What is derivable is that a physician can arrive with neither, and today that is
a dead end.

## P183-01 — `enrolments.delivery_email`

A nullable column on the **enrolment**, and every part of that is a decision:

- **Not `users.email`.** For a `local` participant the address _is_ the
  credential: `user_identities.subject` holds it, and `createPerson` writes both
  from one input. Changing `users.email` alone would leave somebody signing in
  with the old address while every screen shows the new one — §9.10b, two homes
  for one value. Changing both is an account-email change, which without
  verification is an account-takeover path, and that is a ticket of its own with
  a security argument to make rather than a field to add here.
- **Not on `certificates`.** A re-created certificate would lose it, and
  re-creating is one of the two buttons beside this field.
- **On the enrolment, which is tenant-scoped**, so RLS bounds an operator of one
  customer to their own participants. `users` carries no RLS by design — it
  spans tenants — so a per-person address would be a cross-tenant write from a
  customer administrator's screen.

The identity address and the delivery address are **different values**, which is
what makes two columns right rather than a §9.10b violation: one is who this
person is to their identity provider, the other is where this document goes.
Delivery reads `COALESCE(enrolments.delivery_email, users.email)`, so the
default is unchanged and nothing has to be set for the ordinary case.

**Erasure.** A second place a subject's address lives is a second place
`erase_subject` must find, and a column it misses is a GDPR defect that no test
would notice. Nulled beside `attested_name`, and `docs/gdpr.md` §2 and §4 record
it.

## P183-02 — the rule, with two callers

`deliveryEmail({ proposed, current })` in `packages/domain`: pure, exhaustively
tested, and — the part §9.3 exists for — **called from both routes**, the
learner's and the operator's. A rule with one caller is half a rule; a rule with
none is what `inviteStatus` was.

It answers `ok` / `unchanged` / `malformed`, and `malformed` names the field and
never the value: an address is personal data and the case that exercises
validation is somebody's typo containing their name.

## P183-03 — the physician's own field

Beside the EFN on the Zertifizierung tab, because that is where they already
supply the one other thing the platform needs from them, and it is the screen
they are on when the certificate is the subject. It shows the address that will
be used and where it came from — their account, or their own override — because
a field that shows an empty box when an address exists invites somebody to
retype what is already right.

## P183-04 — the operator's field

In the support panel, under the cause. Where an address is missing the panel
stops saying only "download it and send it another way" and offers the thing
that fixes it. Where one is present it can still be overridden, which is the
client's case: _"it can be the case that they want to have the certificate in
another email"_.

Setting an address on a `no_recipient` certificate does not send anything by
itself — the operator then presses the resend that P179 already put there, and
the withheld-resend gate lifts because the cause is gone.

## Not in this ticket, and named rather than absorbed

- **Changing the sign-in address** of a portal account. See P183-01.
- **Verifying the address.** Nothing sends a confirmation link to it. For the
  operator's field that is right — they are trusted and audited. For the
  physician's own it is a real question, and the answer today is that the worst
  case is a certificate they already hold going to an address they typed
  themselves.
- **The delivery address in the CSV export.** An address per row turns a
  participant export into a mailing list; the export keeps the delivery
  _problem_ columns P179 added and not the addresses.

## What the cross-tenant case actually proved

The isolation test needed **both** application guards removed before it would go
red: the read's `undefined → 404` and the write's `rowCount === 0 → 404` each
produce the refusal on their own. Breaking either alone left it green.

That is worth writing down rather than tidying away, because it means the test
cannot tell "one guard works" from "both work" — and because of what the
sabotaged run showed: with both guards gone the route answered **200**, and the
foreign enrolment's `delivery_email` was **still null**. Postgres refused the
write with no application code left to help it, which is ADR-0002's claim
demonstrated rather than asserted.

The fixture is built, not found. P177-01 is the record of what `LIMIT 1` over a
shared table costs: locally it returns this tenant's row and the case passes, in
CI it returns somebody else's and RLS hides it from the query meant to count it.

## One thing the browser decides, not us

`<input type="email">` applies HTML's value sanitisation and strips surrounding
whitespace before any handler reads it, so a pasted `"  a@b.de \n"` cannot reach
the API through either field. The console test asserts the trimmed value and
says why; the untrimmed case is covered in `deliveryAddress`'s own tests, for a
caller that reaches the API directly. Found by an assertion failing and reported
rather than argued with (§11 rule 5).
