## P151-01 — the erasure's "can never be blocked" guarantee had a hole outside every `try`/`catch`

**GDPR-erasure surface. Human review required.**

P149-02 built `schemaCheckOutcome()` so that a failed schema check can never
refuse a statutory erasure, and argued the guarantee is _structural_: the
function returns a value on every path, so `main` has nothing to catch.

The argument has one hole, and it is a hole no `try`/`catch` in this repository
can cover: **a module-evaluation throw happens before any caller exists.**
`schema-freshness.ts` opened with

```ts
const MIGRATIONS_DIR = resolveMigrationsDir(); // throws when neither path exists
```

so with neither candidate directory present the erasure CLI died at
`ModuleJob.run`, before `main()` ran at all.

### Observed, both sides

```
$ mv db/migrations db/_migrations_probe
$ npx tsx apps/api/src/subject-erasure.ts --user-id … --reason p151 --confirm
Error: schema-freshness: no migrations directory at …/apps/api/src/migrations
  or …/db/migrations. …
    at resolveMigrationsDir (…/schema-freshness.ts:81:9)
    at <anonymous>          (…/schema-freshness.ts:62:24)     <- module evaluation
    at ModuleJob.run        (node:internal/modules/esm/module_job:343:25)
PROBE_EXIT=1
```

against the control with the directory present, which reaches the CLI's own
handler and prints its own sentence:

```
Erasure failed: unknown argument: --user
CONTROL_EXIT=1
```

An operator working a one-month Article 17 deadline got a stack trace naming an
internal module — §9.9/P43-02's shape, an error naming the innocent thing —
instead of the erasure a human decided must never be refused.

### Latent, not live — and that is not the same as fine

`Dockerfile:216` copies `db/migrations` to `dist/migrations`, so no shipped
image reaches the old path today. Verified:

```
$ grep -n "migrations" Dockerfile
216:COPY --from=build-api --chown=node:node /repo/db/migrations ./dist/migrations
```

A guarantee that holds only while an unrelated `COPY` survives is not the
guarantee that was asked for.

### The fix

Resolve on first use and remember it, so the throw lands **inside**
`assertSchemaCurrent`, where each caller's existing policy already applies:
`bootstrap-admin` fails closed and says so in its own words; `subject-erasure`
warns loudly and erases anyway. After the fix, the same probe reaches the CLI's
own handler.

### The test, watched red first

`subject-erasure-cli.integration.test.ts` gained a second case that runs the
compiled entrypoint from `apps/api/build/probe/`, where **both** candidate paths
miss. `build/` is gitignored at any depth, which is why the copy lives there.

| Code                                   | Result                                                                                                                             |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| pre-fix `schema-freshness.ts`, rebuilt | **RED** — `the process threw at module load, before main() — the erasure never ran: expected '…' not to match /at ModuleJob\.run/` |

The existing P149-02 case passed in **both** runs, which is the point of adding

## P151-02 — `ds_app` was never without a grant on `schema_migrations`

**A false claim, in four places, none of which had been run against a database.**

P148, P149, migration 0049's header, `init-roles.sql`, `bootstrap-admin.ts` and
`schema-freshness.ts` all say some form of:

> `ds_app` holds no grant on `schema_migrations` (ADR-0002, the application role
> owns nothing)

It is false. `init-roles.sql` itself, further down the same file, runs

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE ds_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO ds_app;
```

which covers every table the migrator creates, and the ledger is one of them.
Live, on a database built from this branch:

```
== any relation whose ACL names ds_schema_reader ==
 schema_migrations | r | ds_migrator=arwdDxt/ds_migrator
 schema_migrations | r | ds_app=arwd/ds_migrator          <- read AND write
 schema_migrations | r | ds_schema_reader=r/ds_migrator

$ as ds_app:  select count(*) from schema_migrations       -> 49
$ as ds_app:  begin; insert into schema_migrations(filename)
              values ('zzz_probe.sql'); rollback;          -> INSERT 0 1
```

So the application role can read the migration ledger **and rewrite it**.

This does not make `ds_schema_reader` wrong; it makes it more necessary. A check
on schema freshness should not rest on a blanket default privilege we would
rather narrow, least of all one that also grants writes to the thing being
checked. The comments now say that, in all four places, with the evidence.

**Not changed here:** narrowing `ds_app`'s privilege on `schema_migrations`. It
is a privilege change on the application role, it needs its own migration and
its own review, and it **predates this branch** — verified:

```
$ git show origin/main:infra/postgres/init-roles.sql | grep -A2 "DEFAULT PRIVILEGES"
ALTER DEFAULT PRIVILEGES FOR ROLE ds_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO ds_app;

$ git diff origin/main...HEAD -- infra/postgres/init-roles.sql | grep "DEFAULT PRIVILEGES"
(no change on this branch)
```

Left as somebody's decision rather than absorbed quietly while doing something
else (§3).

exit 1. Recorded because "the check stayed green" was momentarily the more
alarming reading, and the honest resolution was to look at the scanner rather
than to restate the claim.

## Why this was not merged

Two reasons, either of which is sufficient.

1. **No human has reviewed it.** `pull_request_read: get_reviews` on PR #41
   returns `[]`. CLAUDE.md §2 requires human review before merge for anything
   touching auth, assessment, eiv or certificates; this branch is 114 commits
   and 350 files and touches all four, plus GDPR erasure and RLS. The
   `needs-human-review` label is on the PR and stays on.

2. **This session changed GDPR-erasure code.** P151-01 is a fix to the code path
   a statutory erasure runs through. The instruction for this run was explicit
   that a fix touching auth, EIV, certificates, GDPR erasure or RLS beyond what
   was already reviewed stops before the merge, because the diff a human would
   be approving is no longer the diff they were asked about.
