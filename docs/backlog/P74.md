# P74 — the content form, as the person filling it in sees it

Five reports on 14.08, from an operator with the console open. Four of them are
about the same screen and one is about the Sicherheit screen. They are collected
here because three of the four turned out to share a cause: **the console holds
`s3://` references, and a browser cannot do anything with one.**

---

## P74-01 · "why is this like this still? i want to remove it!"

Of the panel refusing to remove a second factor.

The notice was already right and already said what to do — set the rule to
„Freigestellt" first, then remove. What it did not say is **which** rule. The
screen draws a platform row and a customer row and said "stellen Sie zuerst oben
die Regel", naming neither; the obvious move is the customer row under the
cursor, which for a super administrator changes nothing about their own account.

Underneath was a worse version. The console decided which policy governed the
reader from `props.customers` — the list an operator may _pick_ from, fetched
only for an account holding the `customer` capability. For a super administrator
that is every customer, none of which they hold a grant in; for a customer
administrator it is empty, so the screen concluded their rule was the platform's
and drew no row at all for the one that governs them.

The grants are not in the console, so the API answers it:

```
own: { policy, scopes: [{ customerId, name, mayChange }] }
```

- `governingSecondFactorScopes` (`@ds/domain`) says which scopes produced the
  strictest-wins answer — every scope at that level, because relaxing one of two
  `required` customers changes nothing.
- `mayChange` is `maySetSecondFactorPolicy`, **extracted from**
  `setSecondFactorPolicy` rather than restated, so what the screen offers and
  what `PUT` refuses cannot drift (§9.2).
- the name comes through `list_customer_registry()`, because `customers` is
  under FORCE ROW LEVEL SECURITY and the staff pool carries no tenant context —
  a plain `SELECT` matches zero rows and the screen would name nothing (§9.6).

The screen marks the governing row „für Sie maßgeblich", names it in the
sentence, draws a row for it even when the console's customer list has no such
entry, and — where the operator may not set that policy at all — says who to ask
instead of pointing at a control they do not have (§9.4, the P38-07 lesson).

### Acceptance criteria

- [x] The row governing the reader is marked, and only that row
- [x] The notice names it rather than saying "oben"
- [x] A customer administrator sees a row for their own customer
- [x] An operator who may not change it is told, not sent to it
- [x] Red-checked in both the console and the domain

## P74-02 · a readable URL for an uploaded object

The open P68 item, and the prerequisite for the two below.

`POST /admin/courses/{slug}/uploads/view` takes the stored reference and answers
with a signed `GET` valid for ten minutes. Three checks, each ruling out a
different mistake:

1. the reference must be an `s3://` one — a plain URL needs no signature and is
   refused rather than echoed, so this route can never bless an arbitrary
   address;
2. the key must sit under the caller's **customer** prefix, the same boundary
   `complete` enforces on a store with no RLS beneath it;
3. the key must sit under **this course's** prefix — stricter, and the reason is
   that an author who may edit one course must not be able to read every object
   the customer owns by naming a key from another.

All three refuse with the same 404. Every issued URL is a `read` row in the
storage audit log: a signed GET is a capability that leaves the building.

`consoleUploadRule` gains `GET`. That was predicted in `bucket-cors.ts`'s own
header, which is why it was a one-line change rather than a fortnight of "the
length button does nothing" — and the deploy's probe now walks **every method
the rule claims**, not `PUT` alone, because a check that covers less than it
claims is §9.1's second form.

## P74-03 · "can we have the preview of the video, and of images uploaded?"

The form showed a filename. `MediaPreview` shows the file: an `<img>` for a
poster, a `<video controls preload="metadata">` for a recording, an opening link
for a PDF or a caption file. One preview under the source list rather than one
per row — the rows are renditions of the same recording, and three players would
fetch the same film three times.

`media-preview.ts` caches by reference **and shares the in-flight promise**,
without which the cache is useless in the case it exists for: a content form
mounts three previews in one tick and would mint three signatures for what may
be one object.

### And the defect the journey found doing it

The console's CSP had **no `media-src`**:

```
Refused to load media from 'https://…/video-….webm' because it violates the
following Content Security Policy directive: "default-src 'self'". Note that
'media-src' was not explicitly set, so 'default-src' is used as a fallback.
```

Exactly P67-01 one directive along: `connect-src` was fixed for the upload and
the read half was never needed, so it was never added. The portal's policy has
carried a `media-src` since it was written, for the learner's player.

This is §9.13 in its purest form — a header set by Caddy, invisible to every API
test, and it would have shipped with the feature. `deploy-vars.test.sh` now
greps for each directive separately, because one pattern over the whole header
goes green as soon as any part of it matches.

## P74-04 · "can the length in seconds be calculated automatically?"

It could, and the control existed — and it was **absent for an uploaded video**,
which is the normal way a video gets here. `probeableSourceUrl` skipped `s3://`,
so the one control that gets `durationSec` right disappeared precisely when the
author used the console's own uploader, and the field went back to being typed.
That is the silent accreditation defect `media-duration.ts` exists to prevent:
the watch gate is a percentage of this number.

The reference is now resolved first. The rule stays pure — choosing _which_
source is a rule, resolving one is I/O.

The journey no longer types `18`. It clicks „Aus Video ermitteln" and asserts the
value, which walks the whole chain in one act: the API mints a read signature →
the bucket's CORS rule allows `GET` from the console's origin → the browser reads
the container header → the field holds the fixture's real length. Not one of
those four is visible to an API test, and the CSP defect above was found by
exactly this assertion on its first run.

### Acceptance criteria

- [x] An uploaded video offers the length control
- [x] The journey measures rather than types, with no fallback that would keep
      a broken probe green
- [x] The console's CSP names the bucket in `media-src`, with a shell check
- [x] The deploy probes every method its own rule claims

## P74-07 · the deploy copied the Caddyfile and nobody re-read it

Found by the post-deploy journey on 14.08, on the deploy that shipped P74-03.
The browser said, **on production**, exactly what it had said locally before
the fix:

```
Refused to load media from 'https://nbg1.your-objectstorage.com/dscme/…'
because it violates the following Content Security Policy directive:
"default-src 'self'". Note that 'media-src' was not explicitly set…
```

against a checkout that contained the `media-src`.

`caddy` runs a stock image with `./Caddyfile:/etc/caddy/Caddyfile:ro` — a bind
mount — and **two** things go wrong. The second only surfaced once the first was
fixed and the check was there to disagree, which is the whole argument for
asserting the effect rather than the command:

1. `docker compose up -d` recreates a container when its **image** or its
   **compose-level configuration** changes, and a changed mounted file is
   neither. Nothing restarted Caddy.
2. A bind mount of a **file** resolves to an **inode** at container creation,
   and `git checkout` replaces a file rather than editing it in place. The
   container keeps the old inode for good, so `caddy reload` re-reads the path,
   gets the previous bytes and exits 0. Only recreating the container
   re-resolves the mount.

Deploy #49 shipped the fix for (1) and failed on the check, printing the exact
diff — the file carrying `media-src`, the server still answering without it —
which is what identified (2).

This is not about one directive. **Every header, route and redirect ever
changed in that file has had the same fate**, back to whenever Caddy last
restarted for an unrelated reason — and nothing anywhere said so. It is
CLAUDE.md §9.9 one layer below where that rule is usually applied: not "the
seed was never run", but "the file was copied and the process that reads it was
never told".

The deploy now reloads Caddy and then **checks the served header against the
file**, per site. A reload returning 0 proves the command ran, not that the
running server answers differently — §9.1 — so the assertion is on the effect.
Placeholders are expanded from the deploy's own shell, in bash rather than
`envsubst`, which is not among the tools the preflight checks for.

### What it covers, and what it does not

The Content-Security-Policy of each site that declares one, including a changed
value inside an existing directive. **Not** the rest of the Caddyfile: a
changed route or redirect is applied by the reload and is not verified. Stating
that is the point — a check whose reach is overstated is how the last several
defects survived.

### Acceptance criteria

- [x] The deploy reloads Caddy, checks, escalates to a force-recreate when the
      check disagrees, and checks again — the served header decides, not a
      guess about which of the two causes is in play
- [x] It then proves the served policy is the one in the checkout, per site
- [x] The check is retried briefly, so a reload in flight cannot fail a deploy
      that is fine
- [x] `caddy-config.test.sh` covers expansion, block bounding, normalisation
      and — the half that matters — that normalisation does **not** forgive a
      missing directive
- [x] Red-checked twice: breaking the expander fails three cases, deleting the
      `media-src` from the real Caddyfile fails one
- [x] Every assertion is made in the parent shell, because a `check` inside a
      subshell increments a counter nobody reads

## P74-05 · "can we make the subtitle be also in srt format?"

Of the field labelled "Untertitel-Datei (WebVTT)". Reasonable — SRT is what
comes out of every transcription service — and it cannot simply be allowed
through: `<track src>` takes **WebVTT and nothing else**. A browser handed an
`.srt` fires `error` on the track and shows no captions, silently, with the
video playing perfectly. So the author sees an upload that worked and the
physician who needs the captions sees nothing.

`srtToVtt` in `@ds/domain` converts, and the console converts **before**
uploading — so the object in the bucket is genuinely `text/vtt`, the API learns
no second format, nothing converts on the learner's path, and a file downloaded
from the Mediathek is what its name says.

Four differences matter, and each is a way a real subtitle file differs from the
textbook one: the `WEBVTT` signature (its absence is the commonest reason a
renamed `.srt` shows nothing), the fraction comma, hours that some tools omit,
and a leading byte-order mark. Milliseconds pad on the **right** — `,5` is half
a second, and padding it like the other components would make every such cue
arrive half a second early.

Nothing is repaired: a file that is not subtitles is passed through and refused
by the server with a German message written for that screen. A converter that
guessed would produce a `.vtt` of plausible nonsense whose failure surfaces to a
physician.

### Acceptance criteria

- [x] The picker offers `.srt`, and the label says both formats
- [x] An SRT reaches the bucket as WebVTT, under a `.vtt` name
- [x] A WebVTT file is uploaded untouched
- [x] Exhaustive unit tests, and the call site red-checked

## P74-06 · "i can not easily go back to the inhalt darstellung"

Said of the quiz editor, after adding a question. Two things were true at once.

**The way back was only at the top.** The breadcrumb names every level above and
is one click away — and after writing eleven questions it is several screens
above where the author is working. There is now a named exit at the bottom, next
to Speichern: „Zurück zu den Inhalten". Named rather than "Zurück", because this
screen is two levels down and "back" has two plausible answers — and the
neighbouring tab is called „Inhalte & Darstellung", so the wording has to point
at exactly one of them.

**The quiz had no address.** It was React state and nothing else, so Back left
the console, F5 lost it, and there was nothing to send anybody. That is §9.8,
and `routes.ts`'s own header names _"somebody deep in a course's quiz editor who
pressed F5"_ as P42-01's motivating case — the fix stopped at the tab. The route
now carries `/quiz/<contentId>`.

The route regex was replaced by splitting on `/`: an optional group after a
greedy one backtracks on input built to make it, and this reads a value straight
out of the address bar. The same rewrite was needed in `subtitles.ts` and in the
filename helper, all three caught by lint rather than by review.

### Acceptance criteria

- [x] An exit at the bottom of the editor, naming where it goes
- [x] The open quiz is in the fragment, and closing it returns to the tab
- [x] `App.test.tsx` asserts the **wiring**, not only `encode`/`decode` — the
      §9.7 trap this console has fallen into before
- [x] The journey clicks it, and red-checks by ignoring the routed id
