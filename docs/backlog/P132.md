# P132 — The course-creation wizard, the Pause step, and two things the rig could not say

**Status:** built. Three items, one of which is a defect the browser journey
found in the work of the same ticket.

---

## P132-01 — The journey's Pause step, correctly diagnosed this time

### What was reported

> _"The whole journey, in a browser — Failed in 2 minutes and 43 seconds"_

```
TimeoutError: locator.click: Timeout 30000ms exceeded.
  waiting for getByRole('button', { name: 'Pause', exact: true }).first()
  at journey.spec.ts:878:81
```

### The first fix was wrong, and shipped

P124-01 read the same failure as _"the video ends during the 500 ms wait"_ and
moved the seek from `duration - 1` to `duration - 5`. The run of 31.08 failed on
the same line with that fix demonstrably in it — the line number had moved with
the comment. The theory was tested against production by shipping it, which is
the wrong instrument, and it was wrong.

### What is actually happening

The player draws **one button with three names**: `Pause` while playing, `Erneut
abspielen` once the video has ended, `Abspielen` otherwise —
`VideoPlayer.tsx`, where `publish()` derives `playing` as
`!video.paused && !video.ended`. By the time the step runs, the element is not
playing:

- the watch loop above it exits at sixteen seconds of an eighteen-second
  fixture, and the seeks and waits that follow are easily the remaining two;
- the forward-seek probe sets `currentTime = duration` on purpose, which is the
  fastest way there is to end a video;
- **a seek does not resume an ended element.** More runway cannot help, because
  the playhead is not moving.

That last point was the assumption that had never been checked, so it was
checked — a bare `<video>` in the same Chromium, played to the end, then seeked
backwards:

```
at end:                { paused: true, ended: true,  at: 18, dur: 18 }
after backwards seek:  { paused: true, ended: false, at: 13 }
```

`ended` clears and `paused` does not, so the button reads `Abspielen` and `Pause`
never appears.

### The fix, and why it is not a conditional click

The step now **establishes the precondition** rather than assuming it: if the
element is not playing, it presses the player's own play control — whichever of
the two names it is wearing — waits for the element to report that it is
playing, and only then clicks Pause.

Making the click conditional instead would leave a broken pause button green for
ever (§9.1). Calling `video.play()` from the test would prove the element works
and nothing about the widget.

## P132-02 — Two things the rig could not tell you

Both were found by running the journey locally for the first time in a while,
and both cost more time than the defect they were hiding.

**Redis.** The journey failed at Act 2 with `POST /admin/participants → 500` and
an empty participant list. Nothing was wrong with participant creation: the
rate limiter is backed by Redis, none was running, and the API boots and answers
`/health` regardless. Postgres already fails loudly because the migrator cannot
connect; Redis now gets the same courtesy — a TCP check before the first browser
opens, naming the thing to start.

**The API's own log.** It lived in an array that was printed only if the process
exited non-zero, so an API that booted fine and then answered one request with a
500 left nothing behind at all: the browser showed a screen that had not changed
and the trace held a correlation id whose log had been discarded. It is written
to `apps/e2e/test-results/api.log` on every run now, synchronously, because the
interesting case is a crash. That file is what identified the 500 above.

**And a third, found with it: the demo tenant had no Keycloak binding.** Both
WordPress cases were failing, each displaying the _other_ one's error message,
because the API answered every widget request `401 unknown or unbound project
slug=ds-demo`. `wordpress.ts` says _"the stub binds this, and the seeds'
`keycloak_issuer` names it"_ — and that stopped being true at P101-03, which
made the seed write the issuer **stated or absent, never invented**. Correct for
a real installation; it left the rig relying on `DS_DEMO_KEYCLOAK_ISSUER` being
exported by whoever ran it, which nobody did. §9.9 again: an environment
variable a developer is expected to set is a setting that is not applied. The
rig now hands the seed the address of its own stub, from one shared constant.

**And one left alone, deliberately.** With the binding fixed, the first WordPress
case passes and the second does not — and it is not a rig problem. A visitor who
is not signed in to WordPress gets a token endpoint that answers 404; the widget
classifies that as **misconfiguration** ("Diese Seite konnte keine Anmeldedaten
für das Lernmodul abrufen … Technische Angabe: Token-Endpunkt — endpoint_404")
and the test expects **an expired session** ("Ihre Sitzung ist abgelaufen. Bitte
laden Sie die Seite neu und melden Sie sich erneut an").

The two are not interchangeable, and the test says why: one sends the physician
to the site operator, the other tells them to sign in again. Which is correct is
a product decision about what a physician sees, it is auth-adjacent, and the
client's standing instruction is that **there is no WordPress login for any
physician at all** — DocCheck and MEDICE Keycloak are the channels. So the
premise of the case is worth asking about rather than picking a side inside a
ticket about a creation form (§7). Nothing in `apps/widget` or `wordpress/` was
touched here; the disagreement predates this ticket and was hidden behind the
binding failure, which made both cases fail with each other's message.

**One more, in passing.** `rollen.spec.ts` matched a course by
`getByRole("button", { name: title })`, and the row's delete control carries the
same title inside its accessible name — so the locator resolves to two elements
the moment the course has no enrolments and the delete button is drawn. It was
green only on the state where that button was hidden. Now `exact: true`.

## P132-03 — The course-creation wizard

> _"i still do not like the ui of course creation, you can take inspiration from
> the ones that i uploaded"_

### What was built

Three steps — **Grunddaten**, **Darstellung**, **Prüfen & anlegen** — a step
rail that is a control rather than decoration, and a live catalogue-card preview
beside the form.

### What was deliberately not built

**No new fields.** `CourseCreate` is minimal on purpose, and the reason is in the
contract: everything a Teilnahmebescheinigung needs is set afterwards on the
settings screen, which already refuses a pass threshold below the accredited
minimum and reports what is missing. A creation form that asked for the VNR
would be a second place to get a compliance answer wrong.

**No step the API would refuse (§9.2).** The reference designs have a _Pricing_
step and an _Upload course materials_ step. There is no pricing on this
platform, and materials belong to a content item that cannot exist before the
course does. Either one would be a control whose only possible outcome is an
error.

### Why a wizard for four fields

Two of the references' ideas earn their place here:

- **The title and the address are one decision made twice.** The slug is derived
  from the title and cannot be changed afterwards; on the flat form that
  permanence was a hint under a field halfway down. It is a step now, with the
  address in the preview exactly as it will read.
- **Nothing on this screen is what the author came to do.** The last step says
  what the next three screens are — Inhalte, Zertifizierung, Veröffentlichen —
  because the flat form dropped the author on an empty structure page with no
  statement of what still had to happen before a physician could see anything
  (§9.4).

### The defect the journey found, in this ticket's own work

The first version put "Weiter" and "Fortbildung anlegen" in the **same position**
in the tree. React reuses one `<button>` node for both and only rewrites its
text and its `type`. A click is dispatched, React's handler runs and flushes
synchronously — a click is a discrete event — and _then_ the browser performs the
node's activation behaviour, by which time the node is `type="submit"`. So:

**the last press of Weiter created the course.** The review step was never shown.
Every time, for every author.

Two things about it are worth keeping:

1. **The component test passes on the broken build.** "writes nothing before the
   last step" clicks Weiter twice and asserts the API was never called, and it
   was green — jsdom does not run the activation behaviour the way a browser
   does. §9.13 is not a slogan here: an API test cannot see this, and neither
   can a component test.
2. **The journey saw it within one run of the feature existing**, and the
   evidence was a screenshot of a course editor for a course nobody had asked to
   create.

The fix is distinct React `key`s on the two buttons, so they are distinct
elements: React unmounts one and mounts the other, and the click's default
action lands on a node that is no longer in any form. The back/cancel pair is
keyed too, before the two ever differ in `type`.

### The class, not the instance (§9.11)

The shape is: **a control that changes what it is, in place, in response to its
own click.** A sweep of the console found one other candidate — `SignIn.tsx`
swaps whole `<form>` elements between steps — but its transitions are driven by
an async response rather than by the click itself, so no single dispatch can
cross them. Recorded here so the next person looking has the search term.
