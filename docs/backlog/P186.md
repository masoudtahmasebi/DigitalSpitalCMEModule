# P186 — A corrected VNR does not reach the Punktemeldungen already queued

**Raised by:** found while answering the client's question of 04.09.2026:

> based on what we learned, can you check the complete procedure in the complete
> system so we can make sure our system will work correctly with the given vnr,
> given vnr password, and when the user gives their efn, and their email?

**Branch** `claude/education-platform-roadmap-3vgrqh`. Touches **eiv**, so
`needs-human-review` and no self-merge (CLAUDE.md §2).

---

## The defect

`eiv.repository.ts`'s `load` builds one row out of two sources:

| Field                                            | Read from                                     |
| ------------------------------------------------ | --------------------------------------------- |
| `vnrPassword`, `punkteBasis`, `punkteLernerfolg` | `courses` (live)                              |
| `vnr`                                            | `eiv_submissions` (snapshotted at completion) |

`eiv_submissions.vnr` is written by `queueSubmission` at the moment a learner
completes and is **never updated**. So a course whose VNR is corrected in
Verwaltung produces a submission that authenticates with **last week's number
and this week's password**.

The VNR is not in the Meldung body — the specification has no such field,
because the VNR is what the Basic credential authenticates as, and the register
attributes the record to whatever authenticated. So the number that reaches the
Ärztekammer is the queued copy, not the corrected one.

### What actually happens, observed rather than reasoned

The failing case, before the fix:

```
AssertionError: expected 'failed_permanent' to be 'submitted'
```

Not a retry, not a warning — **abandoned**. The register answers 401, the worker
classifies that as `auth`, `planEivAttempt` stops, and the physician's points are
never filed. A one-digit typo correction silently costs every already-completed
participant their Punktemeldung, and the only trace is a `failed_permanent` row
whose `last_error` says `auth`.

### Why this is the same defect the client has already reported twice

CLAUDE.md §9.10b, fifth instance:

> _How can you set these hard coded when there are values in course!_

A VNR is not what the learner did. It is what the event **is** — the number the
Ärztekammer accredited — and correcting it has to correct every Meldung not yet
filed. An enrolment or submission snapshot is right for the learner's own facts
(their attested name, their EFN, the instant they finished) and wrong for the
identity of the event.

## P186-01 — the course's VNR, and the stored one becomes history

- `load` reads `courses.vnr`, beside the password and points it already read
  there. One home, one reader.
- **A cleared VNR abandons rather than falling back.** An operator who removed
  the number has said this course is not the accredited event they thought;
  filing against the queued copy anyway is the irreversible mistake ADR-0005 is
  about. New reason `missing_vnr`, `failure_kind` `auth` — the same shape as
  `missing_vnr_password`, because in both cases nothing was sent and what has to
  be fixed is a course setting rather than anything the physician did.
- **`recordSuccess` writes the VNR that authenticated onto the row.** Once
  `submitted`, that column is the historical record of what a physician's
  Ärztekammer entry is attributed to, and a retraction has to name it. Leaving
  the completion-time copy would have the console report a Punktemeldung against
  a registration that never received one.

Three integration cases, all watched red against the snapshot read:

```
× files the Meldung against the course's current VNR, not the queued copy
× stores the number that actually authenticated
× abandons rather than filing against a VNR the operator removed
```

The mock refuses authentication with a VNR other than `expectedVnr`, exactly as
the real interface answers 401 — so the suite asserts which number was
**presented**, not which one was stored. A test reading the column back would
have passed on the broken system (§9.7).

## The class sweep (§11 rule 11)

Every column on `enrolments`, `certificates`, `eiv_submissions` and
`quiz_attempts` that names a `courses` column, and who reads it today:

| Column                                                                             | Verdict                                          |
| ---------------------------------------------------------------------------------- | ------------------------------------------------ |
| `eiv_submissions.vnr`                                                              | **the instance above** — now read from `courses` |
| `enrolments.vnr`                                                                   | no readers (P164-01)                             |
| `enrolments.cme_category`                                                          | no readers (P171-01)                             |
| `enrolments.cme_points`                                                            | one, in `createEnrolment`'s `RETURNING`          |
| `enrolments.required_watch_percent`, `pass_threshold_percent`, `max_quiz_attempts` | same `RETURNING`                                 |
| `certificates.*`                                                                   | no course property is snapshotted at all         |

The `RETURNING` is not a fifth instance: it returns the row the same statement
just inserted **from `input.course`**, and on conflict `onConflictDoNothing`
returns nothing and the code falls through to `findEnrolment`, which reads
`courses.required_watch_percent`, `courses.pass_threshold_percent` and
`courses.max_quiz_attempts`. Verified by reading both paths, not assumed from
the comment that already said so (§11 rule 9).

The columns themselves are left in place: dropping them is a migration against
live data for no behavioural gain, and they are the record of what an enrolment
was created under.

## Acceptance criteria

- [x] A Punktemeldung queued before a VNR correction is filed against the
      corrected number.
- [x] The submission row records the number that was actually filed.
- [x] A cleared VNR abandons with a reason naming the course setting, and
      nothing reaches the register.
- [x] Every assertion watched red before it was green.
- [x] The class swept, with the full result list above.

## Not done, and deliberately

- **No automatic re-queue of rows already abandoned** by this defect. Those are
  `failed_permanent` with `last_error = 'auth'`, indistinguishable from a
  genuinely wrong password, and re-queueing them in bulk would file
  Punktemeldungen nobody reviewed. The Verwaltung screen already lists them and
  the existing resubmit path takes them one at a time, which is the right
  granularity for something irreversible.
