# Configuration — which file, where it lives, who reads it

Two templates, and it was not obvious which one anybody meant. This is the
answer, and `scripts/env-audit.mjs` is what keeps it true.

Introduced by **P24-01**.

---

## The short version

| You are…                   | The file                               | Where it lives                                    |
| -------------------------- | -------------------------------------- | ------------------------------------------------- |
| running the stack locally  | `.env` from `.env.example`             | in your checkout, gitignored                      |
| configuring the **server** | `config.env` from `config.env.example` | `~/ds-education/config.env` — **not in the repo** |

**`config.env` is not in the git clone, and never will be.** That is the answer
to "there is no config.env": you were looking in
`~/Repositories/DigitalSpitalCMEModule`, and it lives in `~/ds-education`. The
repo has the _template_; the server has the _file_.

```
~/ds-education/                     the server's state, outside any clone
  config.env                        decisions a human made        (mode 600)
  secrets.env                       generated once, never rotated (mode 600)
  sites/                            per-surface runtime config

~/Repositories/DigitalSpitalCMEModule/
  .env.example                      local development template
  infra/deploy/config.env.example   the template config.env is copied from
```

`deploy.sh` copies the template into place on first run and then stops, telling
you to fill it in. It never rewrites it afterwards — the file holds decisions,
and a deploy that overwrote them would be a deploy that undid a domain change.

---

## Why two files rather than one

They configure different things and are edited by different people at different
times, and merging them would mean a production server carrying a Mailpit port
and a developer carrying an ACME e-mail address.

- **`.env.example`** — a local checkout. Container ports, the development
  Keycloak realm, the mail catcher, connection strings pointing at
  `127.0.0.1`. Nothing here is ever true in production.
- **`config.env.example`** — one server. `BASE_DOMAIN`, the ACME contact,
  object storage, backups. Everything else is _derived_ from `BASE_DOMAIN` by
  `domains.sh` or _generated_ into `secrets.env`.

Eighteen names appear in both. That is not duplication to be removed — a
Postgres database name is genuinely a setting in both places — but it is drift
waiting to happen, which is why the audit exists.

---

## What is derived, and must not be set by hand

`domains.sh` computes these from `BASE_DOMAIN`. They are read by the Caddyfile
and the compose file and appear in **no** template on purpose:

```
API_DOMAIN        api.<BASE_DOMAIN>
ADMIN_DOMAIN      verwaltung.<BASE_DOMAIN>
PORTAL_DOMAIN     fortbildung.<BASE_DOMAIN>
DS_*_API_BASE     the runtime /config.js each frontend reads
KEYCLOAK_ORIGIN   for the CSP, from PORTAL_KEYCLOAK_ISSUER
```

A second place to set a hostname is a second answer to "what is the API's
hostname?", and the first deployment lost an afternoon to exactly that. One
configuration point, derived everywhere else.

Likewise, `secrets.env` is generated by `deploy.sh` and **never** regenerated:

```
POSTGRES_SUPERUSER_PASSWORD   consumed once, when the data directory is made
DS_MIGRATOR_PASSWORD          }  the login roles
DS_APP_PASSWORD               }
SECRETS_KMS_KEY               decrypts VNR and SMTP credentials in the database
BACKUP_ENCRYPTION_KEY         decrypts every stored backup
```

The last two are not rotatable. A new value does not re-encrypt anything — it
makes the existing data unreadable. Both belong in the password manager, in
**separate entries**: one compromise should not open both the backup and the
credentials inside it.

---

## What is not configured here at all

**SMTP.** Each project's mail server, sender and credentials live in the
database, per project, encrypted with `SECRETS_KMS_KEY` and set through the
admin console. A customer's mail leaves from their own server with their own
sender; a platform-wide SMTP setting could not express that.

`SMTP_HOST`, `SMTP_PORT` and `SMTP_SECURE` were in `.env.example` for months
after that became true, directly under a comment saying SMTP is per project.
The audit found them.

**Keycloak realms.** Per project, in the database, for the same reason: one
installation serves several customers with separate realms.

## The audit

```bash
pnpm lint:env
```

Fails on either direction of drift:

- a variable **documented** in a template that nothing reads — delete it, or
  add it to `DOCUMENTED_WITHOUT_READER` with a reason;
- a variable **read** by something and in no template — document it, or add it
  to `READ_WITHOUT_DOCUMENTATION` with a reason.

Both directions have already shipped, which is why it runs in CI:

- `PORTAL_PROJECT_SLUG` and `ADMIN_DEFAULT_PROJECT_SLUG` lost their last readers
  in P21-03 and P22-03 and stayed in `deploy.sh`'s **required** list. A fresh
  installation was refused until somebody set two variables that do nothing,
  and the only way to discover that was to read the script.
- `ALLOWED_ORIGINS` was spelled `CORS_ALLOWED_ORIGINS` in the compose file. The
  allow-list arrived empty and every request from the MEDICE WordPress site was
  refused by CORS — a browser-side failure with no server-side trace at all.

Every exception carries a reason. An exception list without reasons is how a
check stops meaning anything.

## Setting the S3 credentials, concretely

The question that started this file.

```bash
ssh deploy@<server>
cd ~/ds-education
nano config.env        # NOT in the git clone
```

```bash
S3_ENDPOINT=https://fsn1.your-objectstorage.com
S3_REGION=fsn1
S3_BUCKET=ds-education-prod
S3_ACCESS_KEY_ID=…
S3_SECRET_ACCESS_KEY=…
S3_FORCE_PATH_STYLE=yes

BACKUP_BUCKET=ds-education-backup
BACKUP_S3_ACCESS_KEY_ID=…
BACKUP_S3_SECRET_ACCESS_KEY=…
```

All six S3 values or none — a partial set leaves `s3://` media locked and
uploads reporting "kein Dateispeicher eingerichtet", which is deliberate and
looks like a bug if you are not expecting it.

Then:

```bash
chmod 600 config.env
cd ~/Repositories/DigitalSpitalCMEModule/infra/deploy
./deploy.sh --check     # validates, changes nothing
./deploy.sh
```

Two things still have to be done at the bucket itself — CORS for `PUT` from the
console's origin, and confirming the bucket is not public-read. Both are in
`infra/deploy/config.env.example`, next to the variables they concern.

**Not GitHub secrets.** The deploy workflow carries no credentials: host, SSH
user, key, known-hosts, and nothing else. `PRODUCTION_ENV` used to be a
repository secret holding the whole environment and was removed in P17-01 —
anyone who could read the repository's secrets held the platform.
