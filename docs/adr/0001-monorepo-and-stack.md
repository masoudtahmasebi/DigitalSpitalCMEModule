# ADR-0001 — Monorepo and technology stack

- **Status:** Accepted
- **Date:** 2026-07-27
- **Ticket:** P0-02
- **Deciders:** Masoud Tahmasebi

## Context

The delivery plan allocates 140 h across an API, a learner widget embedded in a
third-party WordPress site, an admin console, a pure compliance-logic core and an
EIV integration harness — inside six weeks, with most implementation generated by
Claude Code against written specs.

Two properties dominate the choice:

1. **Frontend and backend must be built in parallel.** There is no room for a
   sequential "API first, then UI" schedule. That requires a contract both sides
   can derive from before either exists.
2. **The compliance core must be trivially testable.** Watch-percentage, quiz
   scoring, gating and EIV deadlines decide whether a doctor legally receives CME
   points. Those rules must be unit-testable with zero infrastructure.

The Confluence plan fixes React + Tailwind, PostgreSQL, Redis, Keycloak, Docker
and Hetzner, but does not name a backend runtime.

## Decision

**A single pnpm-workspaces + turborepo monorepo, TypeScript end to end, with
NestJS on the API and Drizzle over PostgreSQL.**

```
apps/api          NestJS
apps/widget       React + Tailwind → Shadow-DOM custom element
apps/admin        React + Tailwind + Vite SPA
apps/eiv-harness  CLI + mock server
packages/domain   pure TypeScript, zero I/O
packages/sdk      generated from contracts/openapi.yaml
packages/config   shared eslint / tsconfig / tailwind presets
```

`contracts/openapi.yaml` is authored before implementation. `packages/sdk` and the
widget's types are generated from it, and contract tests assert the API matches it.

## Rationale

**One language across all five deliverables.** The domain types — a course with
its `required_watch_percent`, a quiz attempt, a progress rollup — are written once
in `packages/domain` and consumed unchanged by the API, the widget and the admin
console. In a two-language stack those types are transcribed by hand at every
boundary, and every transcription is a place where a compliance rule can silently
diverge between what the server enforces and what the UI displays. At 140 h we
cannot afford to test that boundary as thoroughly as it would need to be tested.

**NestJS over Fastify.** Fastify is leaner, and for a plain CRUD service it would
win. This service is not plain CRUD: it needs role-based guards (`super_admin`,
`customer_admin`, `department_admin`, `learner`), a per-request interceptor that
sets the RLS session variable on the pooled connection (ADR-0002), and a
human-reviewable module boundary around the four compliance-sensitive areas.
NestJS provides guards, interceptors and module boundaries as first-class,
conventional structures. That convention is worth more than the overhead here,
precisely because most of the code is generated: a generator produces better
output against a well-known framework idiom than against a bespoke structure, and
a human reviewer checking an auth change finds it where they expect it.

**Drizzle over Prisma.** Tenant isolation is enforced by PostgreSQL RLS, which
requires the application to hold a real connection with a session variable set,
and requires the migrations to be plain SQL we can read and review line by line.
Drizzle is a thin typed layer over SQL that keeps both possible; Prisma's engine
and its migration abstraction make the RLS setup fight the tool.

**turborepo** gives task caching and dependency-aware ordering across seven
workspaces for near-zero configuration cost, which matters when CI runs on every
generated commit.

## Consequences

**Positive**

- The OpenAPI contract can be frozen in week 2, letting P3/P4 (backend) and P5
  (frontend) proceed in parallel in weeks 3–4, which is what makes the schedule
  arithmetic work at all.
- One toolchain, one lint config, one test runner; one CI pipeline shape.
- Compliance logic is a dependency-free package that can be reviewed and tested in
  isolation from everything else.

**Negative**

- TypeScript's type system is erased at runtime; API input validation must be
  explicit (Zod at the boundary), not assumed from types.
- NestJS carries decorator/DI overhead that a 140 h project does not strictly
  need, and its startup cost is higher than Fastify's.
- The team's existing MEDICE ADHS work is PHP/WordPress. This introduces a second
  ecosystem to operate. Mitigated by the WordPress surface being deliberately tiny
  — one shortcode and one token endpoint (ADR-0003).

## Alternatives considered

**PHP / Laravel** — closest to the existing MEDICE ADHS platform and its SMTP
configuration, and would have kept the team on one ecosystem. Rejected because it
forfeits shared types with the widget and the generated SDK, which is the specific
mechanism this plan relies on to build frontend and backend concurrently.

**Python / FastAPI** — excellent OpenAPI generation and a very clean pure-domain
testing story. Rejected for the same reason: it splits the codebase into two
languages and re-introduces a hand-maintained type boundary.

**Fastify** — see rationale above; viable, and the right choice if the guard and
interceptor requirements were simpler.
