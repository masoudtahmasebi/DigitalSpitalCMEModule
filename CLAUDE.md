# CLAUDE.md — standing rules for the DS Education Platform

This file is the standing instruction set for every Claude Code session in this
repository. It is not a description of the project (that is `docs/roadmap.md`) —
it is the set of rules that hold across all tickets.

Read this first. If a work order contradicts this file, the work order wins for
that ticket only, and the deviation is noted in the PR description.

---

## 1. What this project is

A multi-tenant CME (Continuing Medical Education) platform for German healthcare
education. Learners watch accredited course material, pass a quiz, complete an
evaluation, supply their EFN (Einheitliche Fortbildungsnummer), and receive CME
points reported to the EIV-FOBI accreditation interface plus a PDF certificate.

First client: **MEDICE**, therapeutic area **ADHS**, delivered inside their
existing WordPress site.

Budget is fixed at **140 h** and the launch date is fixed at **06.09.2026**.
Scope discipline is therefore a correctness property, not a preference — see
§3.

## 2. The AI-first working model

Documentation is generated by the process, not written afterwards.

| Rule                    | Detail                                                                                                                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ticket = work order** | Every task lives in `docs/backlog/` with context, scope, acceptance criteria, definition of done and an hour estimate. No ticket, no code.                                               |
| **Branch naming**       | `DEP-123-short-slug` (see §9 for the interim ID scheme)                                                                                                                                  |
| **Commit format**       | `DEP-123: imperative summary` — Jira links the commit to the ticket automatically                                                                                                        |
| **PR description**      | References the ticket, lists acceptance criteria with checkmarks, notes any deviation from the spec                                                                                      |
| **Docs**                | Entries in `docs/` reference the ticket key that introduced them. ADRs record irreversible decisions.                                                                                    |
| **Contract-first**      | `contracts/openapi.yaml` is written **before** the implementation. The SDK, widget types and contract tests derive from it. This is what lets frontend and backend be built in parallel. |

### Human review gate

Anything touching **auth**, **assessment**, **eiv** or **certificates** requires
human review before merge. A wrong result in those four areas is a compliance
incident, not a bug. Mark such PRs with the `needs-human-review` label and do not
self-merge.

## 3. Scope is contractual

The in-scope list in `docs/roadmap.md` §4 is exhaustive. The deferred list is
equally binding — **do not build deferred items opportunistically**, even when
they look cheap. Specifically not, in this budget:

Storyblok integration, Vue wrapper, analytics dashboards or charts, exports
beyond CSV, SCORM/xAPI, gamification, self-service signup or billing, Salesforce
sync, rich WYSIWYG authoring, media transcoding, second-customer onboarding.

If a ticket appears to require a deferred item, stop and flag it rather than
widening scope.

The declared trade lever if the date comes under pressure is the **admin console
(P9, 18 h)** — DigitalSpital seeds content manually instead. Nothing else is
negotiable; in particular the security baseline, tenant isolation, server-side
compliance logic and the responsive/a11y floor are costed in and are not
reducible.

## 4. Architecture rules

### Stack

- **Monorepo**: pnpm workspaces + turborepo
- **API**: NestJS (TypeScript), PostgreSQL via Drizzle, Redis for cache/queues
- **Frontend**: React + Tailwind. The learner widget builds to a Shadow-DOM
  custom element `<ds-lms>`; the admin console is a normal Vite SPA.
- **Auth**: Keycloak, validated server-side against JWKS
- **Hosting**: Hetzner Cloud (EU/Germany), containerised and portable

### Non-negotiable technical invariants

1. **All compliance logic is server-side.** Watch percentage, quiz scoring,
   gating, completion and EIV deadlines are decided by the API. The client is a
   renderer and may never be the source of truth for anything that affects a
   CME point.

2. **Never trust WordPress that a user is authenticated.** The API independently
   validates every bearer token against Keycloak JWKS: signature, issuer,
   audience, expiry. See ADR-0003.

3. **Tenant isolation is enforced by PostgreSQL RLS, not by application code.**
   `customer_id` is present on every tenant-scoped table. The application role is
   not `BYPASSRLS`. Application code that filters by `customer_id` in a `WHERE`
   clause is defence in depth, never the only defence. See ADR-0002.

4. **`packages/domain` is pure.** Zero I/O, zero framework imports, zero clock or
   randomness reads — time is always an argument. Everything that decides a
   compliance outcome lives there and is unit-tested exhaustively, because that
   is what makes the rest safe to generate.

5. **Watched percentage is the union of watched intervals**, never the maximum
   playback position. A max-position implementation makes any gate trivially
   skippable by dragging the scrub bar.

6. **One rollup path.** Learner progress and admin reporting read the same
   rollup function over the same repository method. Two implementations would
   eventually disagree, and disagreeing numbers on a CME record is a compliance
   problem.

7. **Secrets are encrypted at rest in the database** (VNR passwords, SMTP
   credentials) using the application KMS key, never stored plaintext, never
   logged, never returned by any API — write-only fields.

8. **Every EIV submission attempt is written to an append-only audit log**,
   including failures. A submission approaching its deadline raises an alert
   rather than failing silently.

## 5. Code conventions

- TypeScript `strict: true` everywhere. No `any` without a comment justifying it.
- No default exports except where a framework requires it.
- Money-like and score-like values: integers, never floats. Percentages are
  integers 0–100.
- All timestamps stored as `timestamptz`, always UTC. German local time is a
  presentation concern only.
- Database identifiers `snake_case`; TypeScript `camelCase`; the Drizzle schema
  is the single mapping point between them.
- Errors thrown across the API boundary use the problem-details shape defined in
  `contracts/openapi.yaml`. No stack traces or internal identifiers leak to the
  client.
- German user-facing copy lives in the widget's locale file, never inline in
  components. The layout copy is authoritative — match it exactly, including
  capitalisation of terms like _Zertifizierung_, _Mediathek_, _Referenten_.

## 6. Testing

- `packages/domain` — exhaustive unit tests, including boundary cases. This is
  the one place where coverage is expected to be effectively total.
- API — integration tests against a real Postgres from docker-compose, not
  mocks. Tenant isolation gets its own dedicated test suite that attempts
  cross-tenant reads and asserts zero rows.
- Contract tests derive from `contracts/openapi.yaml`; a response that does not
  match the contract fails CI.
- Frontend — component tests for gating and status rendering. Full E2E is not
  in this budget; do not build a Playwright suite unless a ticket asks for it.

## 7. What to do when blocked

Do not guess on compliance semantics. If the EIV contract, the accreditation
rules, the CME point calculation or the certificate content is ambiguous, stop
and raise it in the ticket. An invented rule that ships is worse than a delay.

For everything else, prefer the smallest change that satisfies the acceptance
criteria, and note assumptions in the PR.

## 9. Interim ticket IDs

Jira project **DEP** is not yet populated. Until it is, tasks use the internal
IDs assigned in `docs/backlog/` (`P0-01`, `P0-02`, …) and commits use those IDs
in place of the Jira key.

When DEP is populated, `docs/backlog/README.md` §"Remapping to Jira" describes
the one-time migration: each task's `jira:` field is filled in, and from that
point branches and commits use the `DEP-123` form. Historic commits are not
rewritten.
