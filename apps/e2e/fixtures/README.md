# The fixtures the journey uses

## `kurzvideo.webm` — what the journey actually plays

VP8/WebM, 320x180, eighteen seconds. Generated by `make-kurzvideo.py`, so
"where did this binary come from" has an answer that is not "somebody's laptop".

Eighteen seconds and not eight because the widget flushes progress every
fifteen, and a shorter fixture means no flush ever lands _during_ playback —
so everything that can go wrong across a mid-video re-render was unreachable
from the journey (P71-01).

**It is WebM because the test browser can decode nothing better.** See below.

## `fortbildung-modul.mp4` — a real recording, committed and not yet playable

H.264, 1920x1080, 25 fps, 20.3 seconds, 9.8 MB, progressive (the `moov` atom
precedes `mdat`, so a browser can start playing before the file has arrived).
**Supplied by the client** on 13.08 with the instruction _"make all of the data,
images, videos and so on, real ones, no fake urls. create real data to test real
data."_

It is committed and the journey does **not** play it, for one reason:

```
canPlayType('video/mp4; codecs="avc1.42E01E"')  →  ""        cannot play
canPlayType('video/webm; codecs="vp8"')         →  "probably"
```

**Playwright's bundled Chromium has no H.264 decoder.** It is the open-source
build and proprietary codecs are not in it. Every physician watching a
Fortbildung uses Chrome, Edge or Safari, and all three play H.264 — which is
what real course material is, including the client's own `1-720.mp4`
renditions. So this suite has never played the codec the product serves, and
with a WebM fixture it never noticed. `tests/codecs.spec.ts` now asserts both
halves so the gap cannot go quiet again.

### Closing it — two ways, and the choice is the client's

1. **A VP9 or WebM export of the same recording.** Then the fixture is a real
   recording _and_ playable here, and this file loses its last generated
   artefact. Cheapest if the source is still to hand.
2. **Real Chrome in CI** — `playwright install chrome`, then `channel: "chrome"`
   in `playwright.config.ts`. Then the journey plays the real MP4 exactly as a
   learner does. This sandbox's network policy refuses Google's CDN, so it could
   not be tried here; a GitHub runner has no such restriction.

Option 2 is the stronger one: it tests the real file in the real codec. Option 1
is the faster one.

### Why the fixture was generated in the first place

It was, until P71-02: a 320×180 slideshow of JPEGs at 24 kbit/s, eight seconds
long, produced by a Python script. That was defensible on provenance grounds and
wrong on every ground that matters to a video player, because it differed from a
course recording in the three ways that decide how one behaves:

|                 | Generated slideshow                                                                                   | Real recording                                                                           |
| --------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **Length**      | 8 s — shorter than the 15 s progress-flush interval, so no flush ever landed during playback          | 20 s — one lands, every run                                                              |
| **Keyframes**   | Everywhere. Seeking was exact, and the player's one-second grace in `enforceSeekLimit` never mattered | Seconds apart. `currentTime` lands on the previous one, as it does for a physician       |
| **Decode load** | 24 kbit/s. Never buffered, so `waiting` and `seeking` never fired on their own                        | 1080p. They do — and those are the events under which a stale seek limit becomes visible |

The anti-skip rule is **not** weakened for any of this. The API still measures
watched time against elapsed real time, `requiredWatchPercent` keeps its
production value, and the journey watches the whole fixture on the clock. The
fixture is short; nothing about the gate is.

Two of those three are closed — the fixture is eighteen seconds and the journey
watches a flush land. The third, the codec, is not, and is recorded above rather
than hidden.

## `stempel.png` and `unterschrift.png`

Generated, and **deliberately still generated**. They stand in for the
Originalstempel and the signature of the ärztliche Leitung on a
Teilnahmebescheinigung. A real stamp and a real physician's signature are
credentials: committing them to a repository would put a reproducible copy of
somebody's professional mark in every clone and every CI runner, which is a
worse idea than an unrealistic fixture.

What the journey asserts about them is that the PDF pipeline accepts an image,
places it, and produces a document of a plausible size — none of which needs the
mark to be genuine. See `docs/show-stoppers.md` S11 for the open question about
whether an embedded stamp is a valid _Originalstempel_ at all.
